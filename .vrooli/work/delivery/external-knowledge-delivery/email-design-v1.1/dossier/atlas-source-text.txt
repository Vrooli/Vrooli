1. Read the design, not a claim of live software
This atlas presents the selected full-client direction through 84 rendered variants of 21 representative screen families in four viewport/theme combinations: desktop light, desktop dark, mobile light and mobile dark. Multiple Gmail accounts, All inboxes and account filtering are first-release requirements. The specification owns exact behavior, boundaries and acceptance. Static design specimens do not establish working integration, model quality, secure rendering or accessibility conformance.
The complete full-resolution PDF and original asset package are the zoomable review sources. Native Docs embeds overview boards for navigation and discussion. The original individual PNGs, responsive HTML/CSS and manifest retain the usable-resolution source; the boards are not the only handoff. Actual capture counts, file hashes and checked variants are recorded in the delivery receipt and asset manifest rather than inferred from a checklist.

2. Visual and interaction contract
Working surfaces are full-width and compact. Desktop uses appropriate navigation/list/detail panes; mobile uses edge-to-edge list → full-page detail and full-page compose, with saved back-stack context. Do not reproduce desktop split panes as vertically stacked mobile panels. Settings is a sectioned compact list, and source/code viewers get a complete usable content area.
Light mode uses warm porcelain with dark ink and restrained evergreen actions. Dark mode uses distinct dark surface levels and readable status colors. The typography and spacing prioritize real mail density; original source content stays more prominent than optional AI assistance. Realistic fictional Aster Studio messages demonstrate the design without exposing private mail.
All actions need accessible names and visible focus, touch alternatives to hover, non-color status cues and recovery feedback. Primary mobile controls respect the device safe area and keyboard. Reduced motion removes decorative movement. Static images demonstrate the intended composition only; keyboard, screen-reader, contrast, native-device and motion checks remain future product acceptance work.
Detailed state and acceptance definitions: specification §§15–16. Requirement families R01–R08 and acceptance IDs A01–A18 are stable cross-references. R08 and A16–A18 specify first-release multiple accounts. Each section distinguishes representative visual intent from behaviors a static image cannot prove.
EM01. Unified inbox
All inboxes combines connected Gmail mailboxes without merging their messages or conversations. Account badges and a persistent view filter keep ownership visible. Desktop can use list/reader panes; mobile stays an edge-to-edge list.
Review focus: Inspect account chips, per-row identity, counts and partial coverage. All inboxes is the first-run default; switching the view never silently changes an open draft sender.
Mapping: R01, R04, R06, R07, R08. Acceptance: A01, A02, A06, A09, A13, A16, A17. Four visual variants: desktop light/dark and mobile light/dark.
EM02. Thread and reading
Every conversation belongs to one receiving account; same subject or RFC Message-ID in another mailbox never merges it. Original message headers, bodies, quoted history and attachments remain distinct from cited AI derivations.
Review focus: Inspect the receiving account, source identity, safe rendering and full-page mobile back navigation. Reply uses the receiving mailbox and verified alias, never a global last-used account.
Mapping: R01, R04, R06, R07, R08. Acceptance: A03, A05, A13, A16, A17. Four visual variants: desktop light/dark and mobile light/dark.
EM03. Reply and draft
This reply retains the Work receiving account and verified From identity. Draft ownership, local save and Gmail save are separate. Mobile uses a full page above keyboard and safe area. New mail begins in MA05.
Review focus: Inspect From, To/Cc/Bcc, attachments, signature and save receipts. Changing account/alias invalidates prior send approval; unavailable source-account send never silently falls through to another mailbox.
Mapping: R02, R06, R07, R08. Acceptance: A07, A08, A13, A18. Four visual variants: desktop light/dark and mobile light/dark.
EM04. Search and evidence
Exact filters and natural-language recall share a clear source-result surface. Every useful passage resolves to account, thread, message or attachment provenance. Numbers, IDs and quoted phrases keep lexical semantics.
Review focus: Inspect interpreted filters, match locations, source citations, query scope and freshness. Duplicate derivations collapse to one source. No hidden-account metadata or remote fallback is permitted after an empty private result.
Mapping: R03, R06, R07, R08. Acceptance: A01, A04, A05, A13, A16, A17. Four visual variants: desktop light/dark and mobile light/dark.
EM05. Agent proposal review
One coherent suggestion includes source evidence, a meaningful reason, exact proposed action and affected account/people. Approval and receipts are routed through existing shared mechanisms. No suggestion is applied merely because it exists.
Review focus: Inspect source quotations, before/after or final-draft preview, stale/permission state and focused choices. Deduplication and a small useful digest must prevent an exhausting approval queue.
Mapping: R04, R06, R07, R08. Acceptance: A01, A05, A10, A14, A18. Four visual variants: desktop light/dark and mobile light/dark.
EM06. Waiting
Open-loop tracking shows what is awaited, from whom, source evidence and last activity. Suggested waiting is separate from user-confirmed tracking; a reply does not automatically prove resolution.
Review focus: Inspect tracking state, follow-up timing, snooze, resolution and original-thread links. Drafting a reminder is separate from sending it. Planner remains owner of accepted scheduled commitments.
Mapping: R04, R05, R07, R08. Acceptance: A06, A10, A11, A13. Four visual variants: desktop light/dark and mobile light/dark.
EM07. Projects
Project collections connect relevant mail and evidence without copying mailboxes into another owner. Explicit, suggested and corrected associations are distinct. Cross-account membership never creates new access.
Review focus: Inspect source account, membership explanation, related attachment and Planner links. Removing a local project association must not silently remove a Gmail label.
Mapping: R03, R04, R05, R06, R08. Acceptance: A01, A06, A11. Four visual variants: desktop light/dark and mobile light/dark.
EM08. Attachment preview
Original attachment availability and derived understanding are separate. Download-on-demand, coverage by page/range and precise limits remain visible. Code/JSON has a proper full viewer, not a clipped decorative snippet.
Review focus: Inspect preview/text/source choices, filename/type/size, provenance, covered range and download status. No fabricated malware-scanning badge. Unsupported, encrypted, policy-blocked and OCR-failed cases remain specified obligations.

EM09. Accounts and setup
Manage multiple independent Gmail accounts with their own capabilities, health and mailbox selection. Integration Hub owns connection and consent. A successful callback confirms identity and scope before explicit capture selection.
Review focus: Inspect Work and Personal account rows and Add account. Connecting the same verified identity renews the existing binding without duplication or automatic scope expansion. Other providers remain future.

EM10. Settings and privacy
Compact rows and sections expose effective grants, sync, appearance, notifications, retention and inference policy. Embedding, generation, reranking and OCR can have different allowed processing locations.
Review focus: Inspect scannability, plain-language consequences and separate pause/unbind, local erase and Google revocation. A local-first label alone does not certify encryption, residency or a remote processor.

EM11. Per-account sync and recovery
Work and Personal show independent sync, coverage and capability state. One disconnected account does not block a healthy account. Captured, exact-searchable, semantic-pending and stale remain distinct.
Review focus: Inspect account-specific cause and recovery. Unified results label missing or stale coverage and avoid a misleading complete total. Cached content remains readable only while current access permits it.

EM12. Original and source viewer
A complete technical viewer supports original headers/MIME, plain text and JSON/code with line numbers, search, wrap and copy. Nothing in the viewer executes as code or agent instructions.
Review focus: Inspect reading room, long-line behavior, provenance and raw/pretty distinctions. A retained extracted passage may be available when historical original layout is not; show that difference rather than substituting a current link.

EX01. Reconnect
Reconnect preserves local drafts and distinguishes a failed renewal attempt from an actually unusable prior grant. Same-account renewal differs from choosing a new account. Consent does not automatically start capture.
Review focus: Inspect the precise failure cause and account impact. Credential-authority failure should not demand a new Google login. Revocation can affect sibling Google services and must show confirmed, pending or unknown state.
Mapping: R01, R06, R07, R08. Acceptance: A01, A02, A07, A14, A16, A17. Four visual variants: desktop light/dark and mobile light/dark.
EX02. Genuinely empty inbox
An actual empty inbox has a calm, useful next step. It is different from no connected account, no captured content, no matching results, denied access and a failed request.
Review focus: Inspect copy, coverage and a proportionate action. Never use zero results to imply a mailbox was checked completely when indexing is incomplete or permission failed.
Mapping: R01, R03, R06, R07, R08. Acceptance: A02, A04, A13, A16, A17. Four visual variants: desktop light/dark and mobile light/dark.
EX03. Semantic search degraded
The query is preserved while exact matches remain useful. The interface names the active mode and missing coverage instead of inventing a semantic answer or quietly switching to a remote service.
Review focus: Inspect fallback explanation, exact filters, source snippets and recovery. Model-disabled-by-policy, index-pending and service-unavailable are different underlying causes with honest labels.

EX04. Send review
The final review binds the chosen account/alias, To/Cc/Bcc, subject, body and attachments. Any change invalidates approval. A bounded local Undo hold delays submission; ambiguous timeout requires checking whether sent.
Review focus: Inspect the exact Work account, audience and matching reply content. This static specimen cannot send. Viewing another inbox never retargets the reviewed draft or approval. The send-enabled fixture is separately authorized; the read-only setup example does not grant send.

MA01. Account chooser and view filter
Choose All inboxes or one connected Gmail account. The selected view is explicit and preserved across navigation. Count and freshness belong to the selected scope, with each account retaining its own grants.
Review focus: Inspect both account identities, the current scope and the distinction between changing the view and choosing a sender. Switching views never changes an open draft.

Gmail is the only first-release provider. The generic Add account entry leaves room for future adapters without suggesting those providers already work. Connection, secure credentials and consent stay in Integration Hub.
Review focus: Inspect Gmail availability, future-provider labels and explicit capability review. Duplicate verified identities renew the existing account; broadening scopes still requires the normal consent route.

MA03. Specific-account inbox
The Work filter shows only that mailbox, with its own unread count, labels and freshness. Return to All inboxes is obvious. Thread, draft, label and sync identifiers remain account-scoped even when provider IDs collide.
Review focus: Inspect the selected account title and account-local mail. Search inherits visible scope unless deliberately broadened, and authorization runs before private ranking or snippets.

MA04. Partial unified inbox
A disconnected Personal account leaves Work usable. The combined view states its incomplete coverage and shows the affected account and recovery. It never presents partial counts or results as complete.
Review focus: Inspect healthy-account continuity, precise recovery and authorized cached freshness. When revocation is observed or requested locally, protected results are withdrawn; provider propagation can still be pending.

New mail from All inboxes starts without a silently inferred sender. Choose an authorized account and verified alias, or use a deliberately configured default shown prominently. This is a blank message, separate from EM03’s reply.
Review focus: Inspect unset From and disabled send. Unassigned text may be recovered locally without provider-draft mapping or account/agent access. A scoped compose may visibly preselect that account; view changes never migrate drafts, and sender changes invalidate approval.

3. Coverage and honest limits
The atlas covers 21 representative screen/state families with 84 rendered variants: desktop 1440 × 1000 CSS pixels and mobile 430 × 932 CSS pixels, each in light and dark, with 2× original PNGs. The final manifest records actual files and dimensions. Captures do not establish that every error, permission combination, viewport or workflow was tested.
Specified but not exhaustively captured: bulk/mixed labels and undo partial failure; long hostile MIME and RTL mail; draft conflict and crash recovery; ambiguous send timeout; Personal-only inbox and Work-prefilled new compose; all account/grant combinations; source deletion and cache invalidation; every unsupported/encrypted/oversize attachment; every keyboard/screen-reader/reduced-motion interaction; narrow widths below the mobile specimen; real phone browser and external OAuth behavior. These remain explicitly required by the specification.
The mockup prototype supports bounded review navigation only. It must not request real credentials, connect a mailbox, send mail, mutate provider state or call an AI service. Use it to inspect layout and transition intent; use the future actual build to qualify behavior. Owner acceptance, design artifact QA and implementation acceptance are distinct records.
