Start with the design
The selected direction is a full local email client with familiar inbox, reading and composing; exact and semantic retrieval; correctable classifications; and evidence-backed local-agent proposals. First release supports multiple Gmail accounts, a combined All inboxes view and specific-account filtering/switching behind a minimal provider-neutral email scenario. Future Communications expansion may add Slack, Discord and other channels; those are outside this design’s immediate build scope.
The v1.1 package provides the full product specification, decision log and acceptance inventory, a visual atlas with 84 rendered variants of 21 representative screen families across desktop/mobile light/dark, and a portable source/asset package. The owner endorsed the overall visual direction and selected this multi-account revision. Revised-artifact acceptance, native import and implementation qualification remain distinct.

Current route and intended route
Current working route: use the connected Gmail plugin for actual email. This package did not connect an account, read private mail for mockups, send email or change mailbox state.
Intended mature route: use the local email scenario first after actual read/search/compose/send/organization/attachment/assistance journeys and their permission/recovery behavior are qualified. Gmail remains the fallback for unsupported or unhealthy paths. Design, code presence and a health response alone do not establish cutover.
Project/context route: this Drive home retains knowledge, decisions, sources and review artifacts. It is not a duplicate mailbox or runtime database. The wider Vrooli entry and Biosphere map preserve their own authority; historical folders and sources were not renamed or moved.
What was selected, and by whom
Owner-selected: the full-client destination, familiar core email workflows, semantic search/classification, asynchronous local-agent proposals and existing approval/notification integration, with later Communications expansion. At 20:59 UTC on 14 October 2026, the owner liked the overall visual design and made multiple Gmail accounts, a combined Inbox, account filtering/switching and natural future-provider extensibility explicit first-release requirements. Routine design decisions were explicitly delegated so completion did not depend on reopening replacement-versus-companion positioning.
Fixed architecture: Integration Hub owns connection/credentials/capabilities; Email owns the mailbox and corpus; Document Manager derives supported attachments under parent grants; Personal Planner owns accepted planning; Search Hub federates authorized scenario-owned providers; shared search/AI Gateway are reused. Agent Inbox and Signal Inbox remain distinct products.
Designer-selected choices retained in v1.1: Mail as a working interface name, porcelain/ink/evergreen visual language, dedicated mobile full-page flows, progressive assistance, local-first inference recommendation with per-operation policy, explicit send review/recovery, optional local snooze after core, and deferred send-later/templates/automatic modify rules. These are documented choices under delegated design authority, not fictitious individual owner approvals.
The first foundation integration is read-only indexing. A read-only slice or single-account build does not satisfy the selected first full-client release. Draft, modify and send capabilities need their own qualified contracts and consent before live use across the intended accounts.
Account behavior: first run opens All inboxes; remember the owner’s deliberate viewing scope afterward. Each account retains its own messages/threads, sync, errors, grants, drafts and labels. Unified results disclose partial coverage. Replies use the receiving account; new compose chooses an explicit sender/default. Changing a view never changes an open draft’s sender or an approved action’s account. Provider-neutral means reusing Integration Hub plus a small email adapter seam, with Gmail-specific capability extensions; no non-Gmail provider is included in this release.

Inspect Accounts, Sync, Reconnect and Send review for identity and recovery. The decision log explains tradeoffs; future-build acceptance includes multi-account isolation and partial results.
