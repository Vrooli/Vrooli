# Question-aware retrieval for external knowledge

Status: research and proposed design; no implementation or recipe promotion.
Observed: 2026-10-14. Team: `external-knowledge-delivery`.

## Recommendation and what the operator recalled

Use source-grounded retrieval views: keep exact, citable units and lexical search; add deterministic context first; evaluate a small number of summaries and anticipated questions as optional indexing aids. Multiple representations can help a short user question find a passage that uses different language. They must resolve to actual source units before producing a snippet, citation or answer.

The operator's recollection has concrete support in current code. CLI Health folds a measure's authored questions into its embedded command text. Search Hub separately embeds positive routing examples, intent and answer-space segments and scores the best segment for each provider. These are real index-time question mechanisms, not merely eval labels. Knowledge Observatory embeds context-enriched document chunks. However, the inspected document/code/domain pipelines do not establish a general implementation that generates several hypothetical questions per document chunk and stores independent question vectors linked to source passages. “Question families,” “contextual text,” “multiple chunks,” “multiple vectors,” and “generated question views” describe different mechanisms. [L16–L31]

For selected Drive folders, preserve Document Manager's extraction, anchor, enrichment and retrieval ownership. Extend the shared search mechanics where repeated portable work warrants it. Search Hub should route private queries with verified identity and federate provider-owned evidence; its provider-description index should not hold private corpus content. Keep its routing-question views distinct from a provider's passage-question views. Preserve Document Manager's SQLite/FTS/vector choice rather than transplanting Knowledge Observatory's Qdrant layout. [L01, L37, L41]

**Latest operator sequencing (FB-004):** after explicit later activation, making Integration Hub's Google connection API/CLI/UI mature, repeatable and commercial-compatible is an early team outcome. Human Cloud client setup and consent are later checkpoints once the native callback/credential/refresh route can guide the operator. Live OAuth consent gates dependent live work, not all implementation or enablement. The current architecture, GOAL, SETUP and candidate queue now record that amendment; earlier preparation receipts remain historical evidence. This research does not activate the team. Native readback during this investigation remains enabled=false, teamEnabled=false, scheduled=false, taskStarted=false and dispatchStarted=false.

All quantities below are proposed experiment/admission defaults unless explicitly labelled observed. No external private data, model/inference calls, installs, product changes or product tests were used. Existing test source is evidence of intended checks, not a fresh passing test run. No model, chunk size, view count or quality gain is declared optimal.

## Proposed bounded representation design

This section is a recommendation for owner review, not an implementation contract silently added to a PRD. Document Manager's `derivation` parses a source into normalized structure; `anchors` segments and cites it; `enrichment` creates views/embeddings; `retrieval` assembles authorized source evidence. Email and Planner later use the same portable view/retrieval mechanics but retain their source semantics. [L01, L37–L42]

### Evidence units and view families

| Representation | Content and support | Proposed starting posture |
|---|---|---|
| Raw unit and lexical record | Exact normalized passage; original structural locator/version; literal names, codes, cell values and dates | Required baseline. Keep lossless normalized evidence distinct from the embedding string. Lexical/typed lookup works when enrichment or embeddings fail. |
| Contextual passage vector | Source title, document type, section path and relevant deterministic entity/time/table headers plus unit text | First semantic baseline: one contextual vector per raw unit. Reserve model input for evidence; avoid boilerplate/privacy or sensitivity labels as ranking prose. |
| Document/section overview | Source-grounded scope, topics and bounded list of support units | Optional broad-document discovery. Overview hit identifies a parent; the provider must locate relevant real passages before returning an answer citation. |
| Local summary/context view | Concise supported explanation of a section or the chunk's role in its parent | Optional arm for ambiguous chunks; preserve exact unit links. Do not claim a summary sentence is an original quote. |
| Anticipated question/paraphrase view | A small number of answerable questions drawn from declared demand families, each mapped to supporting unit(s) | Optional arm after contextual baseline. Questions are indexed hints, never source-backed answers in their own right. Unsupported, duplicate or generic questions are omitted. |
| Image/table/slide description | Known metadata/OCR, or explicitly permitted generated description, mapped to actual region/table/slide | Only when the extraction/vision owner supports it and source policy permits. Text descriptions do not establish semantic image vectors or accurate chart reading. |

An initial experiment budget is **at most two anticipated questions per eligible evidence unit, one optional section summary, and one optional document overview**, with no mandatory quota. Default generated enrichment is off until a candidate clears evaluation and privacy gates. Deterministic context is the low-cost starting recipe. For a large document, cap the eligible units and total generated tokens at the collection admission budget; do not generate two questions for every spreadsheet row or duplicate questions across all overlapped chunks. These are complexity limits chosen to make the first experiment falsifiable, not research-derived optimum values.

Declare question families per collection/source shape: document discovery; procedure and prerequisites; owner/decision/rationale; examples/exceptions; compare versions; locate a metric/range; identify a chart/diagram; later recall a message/attachment/commitment and find a calendar obligation. The family vocabulary can inform generation, but eval query text and expected labels are excluded. Questions answerable only from unsupported context, whole unrelated corpora or future events are rejected. Reuse authored titles, FAQ questions and verified glossary terms where available before adding generative cost.

### Identity, recipe, support and lifetime

Use a domain-owned view record with at least these fields:

| Field family | Proposed meaning |
|---|---|
| Source identity | Provider + connection/account + remote object ID, with domain collection membership. Content dedup never merges grants. |
| Evidence identity | Source version, normalized derivation ID/version, unit ID and locator/anchor mapping. Distinguish observed current revision from extracted/indexed revision. |
| View identity | Stable key derived from source-version/unit-or-parent ID + view kind + deterministic slot + recipe identity; store text digest and realized generation output. Identical reruns reuse the stored record; nondeterministic regeneration creates a new candidate revision rather than silently replacing selected bytes. |
| Recipe identity | Chunk policy, context/summary/question prompt version, generator model/version/parameters, language, embedding model/version/dimension/normalization/task prefix, lexical recipe, policy schema and relevant support/context digests. A source body hash alone cannot identify these. |
| Support | One or more exact source unit IDs with version/locator; generated view type, source-grounding status and rejection reason. Support mapping is not a citation to synthetic text. |
| Policy | Collection/account/sensitivity membership plus current catalog authorization and retention policy references. Record all sources used to compose a view, including overview/context. |
| Status | Pending/generated/verified/rejected/embedded/published/stale/withdrawn, with generation/catalog checkpoint and reason. View failure does not mark source capture failed or erase the lexical baseline. |

If a section overview combines units with different grants, either partition it by equivalent policy or constrain it to the intersection of every supporting unit's permissions. Do not create a broad public summary of a narrower private passage. The generation worker uses least-required source access; its credentials are not a grant for later search callers. Keep verified identity, scenario capabilities, connection/object grants and commercially owned entitlements separate. Any selected feature entitlement joins existing access policy; it never substitutes for a source grant or creates a new billing/identity store in the retrieval owner.

A citation resolves to the evidence version actually read. Mutable Drive file IDs are not permanent page/cell coordinates. Version replacement withdraws all views for old serving revisions unless the product explicitly supports authorized historical retrieval. Removed/out-of-scope/revoked sources become non-serving immediately under the local visibility gate, including shadow generations, cache entries and parent-fetch paths; physical cleanup can follow the retention policy. A rollback must recheck current visibility. Remote ACL change detection has a bounded age and disclosed offline policy, not an instantaneous claim. [L01]

Recipe invalidation needs explicit owner work. In the legacy non-streaming reconciler, `sourceUnchanged` uses SourceHash and ChunkTotal before composition, while recipe hashing occurs later in `buildChunkPayload`. A recipe-only change can therefore be skipped unless an owner reindex/generation boundary invalidates it; this source inspection is not a runtime reproduction or new defect certification. Streaming completeness checks Model and ChunkPolicy, so view/prompt/context policy can be incorporated in a full recipe digest there. Do not assume the existing `RecipeEmbedder` payload hash alone covers every source-level skip. Admit a focused desired-behavior regression for unchanged source + changed question/context/model recipe, including partial budgets and restart. [L07–L08]

Current Document Manager embedding IDs/hash:unit:role and ContentVersion=1 are not a complete multi-view identity scheme. Extend the owning domain record/contract through governed schema and package routes, retain model/role/dimension metadata, and make duplicate-content remote memberships separately authorized. No schema or generator was changed in this research. [L39–L41]

### Generation and model-input bounds

An optional generator receives a bounded source/version envelope, actual evidence unit text and selected ancestor context. It emits structured records containing view kind, question/summary text and exact supporting unit IDs. Require that a question can be answered from those supports; allow zero results. Check IDs, lengths, empty/duplicate questions, copied boilerplate, impossible scope and unsupported entities before embedding. An entailment/relevance scorer or round-trip extraction can be a later measured filter; a second model's agreement alone is not proof. Human-reviewed sampling should inspect whether supporting text actually answers the question, especially negation, exceptions, dates and quantities.

Treat source-contained instructions as content, including email text that asks an agent to ignore policy. The generator must neither follow those instructions nor invoke tools/account actions. Generated views retain content-policy classification. Summaries may simplify phrasing; they must not upgrade uncertainty, policy authority, commitments or ownership.

Tokenize the **actual composed input** with the selected adapter's tokenizer/bound contract: model task prefix + source context + raw unit/question + reserved wrappers. The current Markdown estimate is runes/4, target 900, overlap 135, nominal hard max 1200; a single large table or fence can exceed the nominal maximum. Therefore a true input-bound check is owed after composition. Do not silently truncate exact cells, exceptions or source anchors. Split an oversized semantic unit using the owning format-aware segmentation route, select a bounded support window, or mark that semantic view unavailable while preserving full lexical/raw evidence. [L05–L06; Nomic/E5 primary model cards above]

For indexed question views, start with the same documented document-role recipe as the indexed corpus. Test question-role/symmetric question-question embedding only as an explicit separate recipe with compatible query encoding and measured support retrieval; the fact that the text ends with a question mark does not establish which prefix is trained for the task. Unknown models need an owner-declared recipe, not a string-name guess. Preserve existing guarded KO settings; a Drive trial does not rewrite all document/command tuning. [L06, L13, L18]

A document/section context input must stay within both generator and embedder limits. For long documents, use normalized section hierarchy and bounded ancestor/sibling facts instead of repeatedly submitting the entire file. A hierarchical overview is a candidate derivation with accumulated support links, not a new source. Record truncation/omission explicitly and avoid claims of complete-document coverage when the generator saw only part of it.

### Retrieval, deduplication, fusion and returned context

1. Verify the caller and delegated collection grants at the producing owner. Resolve permitted account/collection/source/catalog policy before any content candidate generation or scoring. Pass the same policy constraints to lexical, raw/contextual vectors, overview/question vectors and caches. A post-filter cannot undo unauthorized reranker/inference exposure. The query itself may be private and follows the same inference policy.
2. Preserve exact structured queries/filters and lexical candidates. Run semantic contextual retrieval independently; optional view legs add candidates. Start with bounded per-family candidate quotas and a total shortlist budget. If an overview matches, descend to supporting real units under current authorization; do not make a whole document a pseudo-passage answer.
3. Resolve view hits to canonical `(source identity, source version, evidence unit)` candidates before the public ranking page. Within a semantic family, use the best matching view per unit as the first experiment, retaining each contributing view/rank for diagnosis. Fuse the distinct lexical/contextual/optional-family rankings by rank rather than treating heterogeneous cosine/BM25/RRF values as comparable probabilities.
4. Cap a unit's contribution per view family and enforce a final per-source/window diversity policy. Otherwise two questions plus summary plus overlapping raw chunks can occupy the whole top-k and multiply relevance votes. Distinct source identities with identical content keep separate authorization and provenance; combine them for display only after both are authorized.
5. Rerank a bounded list of canonical source-backed passages with needed deterministic context. Do not rerank a synthetic question as if it were the evidence. Compare pure ordering versus rank blending and rerank-off; existing measurements show reranking/enrichment can hurt another corpus, so no automatic stacking claim is made. Retain raw retrieval rank, post-dedup rank and final rank. [L11, L15]
6. Fetch bounded adjacent/parent source units through the same owner and current version/grant checks; use structure to return enough procedure/table/thread context. Limit units/tokens and prohibit ACL expansion through a parent. Construct snippets and citations from real evidence only. Generated overview/question text can explain retrieval in a labelled debug view, subject to permission and logging policy.
7. Expose degradation and source/index/permission freshness. Enrichment/generator/reranker outages preserve captured work and raw lexical evidence; embedding outage does not declare a source empty. Cache keys include effective principal/grant/policy/catalog-version fence plus source/index recipe generation; authorization changes invalidate visibility independent of cached rank.

This is portable semantic-view grouping, not necessarily Qdrant's token-level “multivector”/late-interaction storage feature. Independent question/summary vectors can be rows in a domain repository. Shared `ConcurrentFusion` merges by hit.ID; passing raw distinct view IDs directly would fail canonical-unit dedup and risk multiple votes. The owner must normalize to evidence IDs and bound family contributions before reuse, or add a tested portable grouping seam. Shared Filter/PostFilter hooks and model metadata are building blocks, not a complete private-access policy. [L04, L10–L11]

## Chunking interaction and service extensions

Do not build another parser to make question views. Preserve Document Manager's normalized document model and anchor owner. The chunker receives format-aware units and creates searchable windows; view generation sits after this structure is known. Keep extraction, segmentation, contextualization/question and embedding versions separate so changing enrichment need not redownload original bytes. [L01, L37–L42]

| Source shape | Evidence/chunk boundary | Optional view use and failure to avoid |
|---|---|---|
| SOPs, Docs, Markdown/Word | Heading/step/exception units and bounded overlap; source-version logical anchors | Procedure/precondition/owner questions and chunk-specific context. A question requiring a prerequisite in another section maps both supports. Do not duplicate overlapping questions for each repeated paragraph. |
| Sheets/Excel/CSV | Sheet/table schema, typed cells, headers, units, formulas and displayed values; bounded row groups | Table overview locates the correct range. Exact value, date comparison and aggregate result are computed/read from structured source cells, not summary embeddings. A generated question cannot invent an uncomputed total. |
| PDF text and OCR | Preserve page/geometry, reading order, OCR confidence, table units | Context/question views identify passages; uncertain OCR remains uncertain. Keep scanned-text uncertainty out of invented exact-value answers. |
| Images/charts/diagrams/slides | Metadata/OCR or qualified permitted vision description; slide/notes/region distinction | Descriptive view points to actual original region. If visual interpretation is unavailable, say so; a text embedding is not a multimodal result. |
| Email later | Account/message/thread/MIME part and sent time; distinguish newest body from quote/signature; attachment part provenance | Optional message/thread overview and decision/commitment/attachment questions. Thread overview uses the intersection of support grants and maps precise messages. A proposal in mail is not an accepted task. Mailbox owner controls deletion/labels/retention; Document Manager derives attachments under inherited authorization. |
| Calendar later | Account/calendar/provider event and occurrence identity; civil dates/timezone/recurrence/cancellation plus source freshness | Mostly deterministic event context; questions about the obligation's purpose can be optional. Structured scheduling/time filters answer when/busy/cancelled questions. Embeddings do not compute availability or turn missing sync into free time. Existing Planner owner admits the coordinated slice. |

Do not combine separate providers' private documents into a single enriched view as the default. Cross-source comparison is a query/agent reasoning task over independently authorized and cited evidence. A controlled cross-source summary would need explicit multi-source support, intersected policy, retention and update dependencies.

## Held-out evaluation and recipe promotion

The comparison asks whether views improve **source-backed retrieval**, not whether a model can reproduce its own generated question. Begin with deterministic public/synthetic fixtures covering supported source shapes; later add a separately authorized operator-local overlay. Keep private queries, content, identifiers and credentials out of committed fixtures/telemetry. No eval was run here.

Create reviewed demand families with multiple documents and near-duplicates. Fix the raw normalized corpus, extraction/chunk policy, source/catalog snapshot, query recipe and final k/token budgets across comparisons. Store relevant source/version/unit IDs and acceptable alternative supporting windows. Score units and source coverage separately; a document-title match is insufficient if the precise answering passage is missing.

**Anti-leakage split:** assign whole source families before generation/tuning/evaluation, grouping versions, duplicate copies, overlapping chunks, related messages in a thread and recurring event series. Recipe/prompt selection uses the development family set. Hold out different documents/project families for final generalization. Held-out documents remain searchable and their views can be produced using the frozen recipe and source text; their eval questions/answers/labels must never be shown to the generator or used to choose that recipe. Add an independent authored query set, held-out paraphrases and time/version drift cases. Generated eval candidates require review and do not substitute for independent holdout demand.

Existing Search Hub corpus semantics force `generated` positives out of the tuning fold, separate candidates from reviewed acceptance cases and enforce required question groups. Its sweep uses deterministic case-ID splitting, paired bootstrap significance, held-out non-regression, junk/latency feasibility and simpler/incumbent tie-breaking. Reuse those guards where applicable, but a case-ID split does not establish independence when two IDs share a source/overlap/question template. Add source-family grouping for this study and make frozen recipe/manifest evidence explicit. The new view-count/context/prompt factors are not currently automatic sweep taxonomy fields; admit a bounded measured recipe comparison rather than claiming the existing sweep already supports them. [L12–L14, L32–L33]

| Arm | What changes | What remains fixed |
|---|---|---|
| A0 | Raw lexical/structured evidence only | Source, authorization, labels, extraction, return budget |
| A1 | One raw-unit semantic vector + lexical | Same as A0; known trained query/document recipe |
| A2 | Deterministic title/heading/table-context vector + lexical | Same evidence units; isolates contextual input effect |
| A3 | Bounded grounded context/summary view | Freeze view budget and grounding checks; no question views |
| A4 | At most two generated questions per eligible unit | Same contextual baseline/supports; independent views, canonical dedup |
| A5 | Filtered expansion text versus separate question view rows | Separate experiment; compare storage, exact-query degradation and support recall |
| A6 | Rerank-off/pure ordering/blend on candidate shortlist | Reuse selected indexing arm; no hidden reindex change |

A3–A5 are optional comparisons; stop adding arms when the admitted budget cannot measure them meaningfully. Query-time HyDE or query-paraphrase expansion is a later independent arm because it changes runtime latency, query privacy and failure behavior. Do not confound its generation cost with document-time enrichment.

Required cases include paraphrased SOP steps; missing prerequisites; changed negation or exception; exact IDs/error codes; numeric spreadsheet/cell/range/aggregation requests; headings shared by unrelated documents; duplicate versions/copied content; moved/deleted/revoked source and rollback; unsupported format/OCR uncertainty; sparse/embedding/generator/reranker outage; account/grant isolation and guessed IDs; gibberish/hard negatives; malicious embedded instructions; source edits that invalidate only part of a view's supports; stale email commitment/date and cancelled/rescheduled events. Test documented grant scopes before snippets/reranking, not only whether final unauthorized results are empty.

Measure recall@k of supporting units, source coverage, MRR/nDCG when relevance labels justify them, precision and false-strong/junk rate, redundant-unit/source fraction and citation/support correctness. Report raw shortlist, deduplicated shortlist and final rerank stages separately. Measure exact/structured-query retention, multilingual/format family slices and grounded-view rejection rates. A broad mean cannot conceal an unauthorized leak, catastrophic exact-fact regression or an unsupported source family.

Run both **provider_direct** and **federated** evidence paths against the same pinned allowed sources/caller. Existing direct evaluator reports provider_direct; federated runner exercises the ordinary ranked path and separately measures routing precision/retrieval recall. Retain wrong-provider routing, withheld/degraded providers and non-gradeable exclusions. A passing direct recipe cannot prove router reachability, delegation or remote API/MCP consumer access. Keep corpus-capable versus end-to-end-answerable distinct. [L34–L36]

Before a recipe is promoted, the owner records a predeclared metric target/minimum useful gain, family floors, exact-fact non-regression allowance, p95/timeout/compute/spend/storage/update-lag budgets and corpus version. Paired improvement must exceed the noise band on the development comparison and preserve the untouched final source-family holdout, negatives and all authorization/source-citation gates. If the sample is too small, label the finding inconclusive and retain the baseline. Use confidence intervals at the independent family level when repeated queries/units are correlated. Promote no recipe on generated-question recall alone. Equal-quality candidates prefer fewer views, cheaper generation and no runtime rerank dependence. Human product selection may set utility thresholds; it is not a required per-view approval queue.

## Cost, residency and operational policy

A source-view recipe stores text copies as well as vectors; summaries, question strings, FTS terms, snippets and cache/debug artifacts are content retention. Price the entire representation, not only vector bytes. Choose residency for query embedding, source embedding, generation, reranking, OCR/vision and logs individually through existing AI Gateway roles/profiles.
