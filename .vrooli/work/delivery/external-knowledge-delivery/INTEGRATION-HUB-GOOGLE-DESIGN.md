# Integration Hub Google connection design investigation

Date: 2026-10-14. Status: research and proposed contracts; no implementation, account connection, credential creation, product certification, publishing, or team activation. Official online sources were accessed on 2026-10-14. Local observations concern this shared checkout and must be rechecked when work is admitted.

## Decision summary and delivery posture

Integration Hub should become the repeatable operator-facing home for Google account authorization, connection inspection, recovery, and consumer bindings. Build the mature CLI, actual UI, verified-principal boundary, durable lifecycle, and bounded Google read driver together. Qualify those capabilities against controlled provider fixtures before asking the operator to configure a real Google client and consent. Later team enablement requires explicit operator authorization, but **live Google setup is an operator checkpoint after the capability is ready, not a prerequisite that forces a one-off bootstrap before team enablement**. Only dependent live integration and live-evidence outcomes wait at that checkpoint. Contract, CLI/UI, security, storage, driver, and fixture qualification work can make substantial progress independently.

This ordering follows the latest operator steering. Earlier wording in this goal home's `SETUP.md` Stage A.6 and `QUEUE.md` suggested a possible separately authorized bootstrap before team enablement. That is historical preparation guidance to reconcile, not the recommendation here. This report does not change native team state or those shared documents.

The first product capability remains selected-folder Drive retrieval with read-only operations. Calendar and Gmail reuse connection infrastructure only when their owning domains and approved experiences are ready. Preserve OpenRouter's pilot and document-manager's explicitly enabled legacy archival behavior. Google connection infrastructure does not become a corpus, email, calendar, billing, or identity authority.

Labels used below:

- **Observed**: read directly from local code or a current official source; no product test was run for this investigation.
- **Recommended**: architectural default proposed for acceptance and later governed contract reconciliation.
- **Proposed UX/contract**: concrete design, not a shipped endpoint, command, screen, or selected visual original.
- **Open decision**: owner input needed before the affected delivery claim or slice; unrelated work may proceed.

## Current official Google constraints

The following facts change the design. They are intentionally narrower than a generic OAuth checklist.

| Fact | Design consequence | Official source |
|---|---|---|
| Web-server authorization supports offline refresh, exact registered redirect matching, and incremental grants. Google may omit a new refresh token on a later authorization. Revocation affects that user's project-wide OAuth grant across clients. | Preserve an existing valid refresh token on same-account reauthorization when no replacement is returned. Show project/service impact before revoke. A stable callback is configuration, not the current random scenario port. | [Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) |
| Desktop authorization supports PKCE and loopback IP callbacks. Its documentation says installed apps do not support incremental authorization. OOB copy/paste authorization is unsupported. | Distinguish server and desktop client strategies. For desktop service expansion, request the needed supported grant set through a new explicit flow; do not claim web incremental behavior. | [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app) |
| `drive.file` is non-sensitive per-file access and can modify selected files; `drive.readonly` and `drive.metadata.readonly` are restricted. Metadata scope does not provide document bodies. | Read-only product capability is enforced separately even with `drive.file`. Do not label file selection as recursive folder OAuth authorization. | [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) |
| Google Picker supports user file selection with `drive.file`. | Evaluate it as a scoped selection route. Folder display/selection is not evidence that existing and future descendants gain permission. | [Google Picker](https://developers.google.com/workspace/drive/api/guides/picker) |
| External Testing projects issue seven-day refresh tokens for Drive scope requests. Refresh tokens can also expire/be revoked; token limits can invalidate older grants. | Testing-mode consent is useful qualification evidence, not dependable unattended operation. Status needs reconnect guidance and known expiry where supplied. | [OAuth overview](https://developers.google.com/identity/protocols/oauth2) |
| Publishing status and verification status differ; production publishing does not automatically remove sensitive/restricted warnings. Personal-use/internal/testing verification exceptions depend on the real deployment. | Configure the actual audience and release posture. Do not extend a personal-use exemption to a distributed commercial product or describe “In production” as a permanent-token guarantee. | [App audience](https://support.google.com/cloud/answer/15549945), [Verification exceptions](https://support.google.com/cloud/answer/13464323?hl=en) |
| Restricted-scope access through third-party servers can require an annual assessment; permitted application type and scope justification matter. Sensitive-scope and branding reviews have distinct requirements. | Commercial managed-client/server delivery needs a scope, data-flow, verification, and assessment release gate. Confirm its actual applicability before promising availability; personal deployment does not establish the commercial posture. | [Restricted verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [Sensitive verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [Brand verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification) |
| Clients must match platform; Google requires secure client/token handling, minimum scopes, separate environment projects, owned/authorized callback domains, and a secure external browser. Partial consent must disable denied features. | Ship no confidential web-client secret in a distributed binary. Do not embed Google's authorization screen in an app-controlled webview or invent cross-platform callback behavior. | [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies) |
| Google's device flow permits a limited scope list: Drive `drive.file`/appdata, but no `drive.readonly`, Gmail, or Calendar read scopes are listed. | No generic “headless device fallback” for the intended broad Drive/Calendar/Gmail capability. Headless server CLI should direct the user to a reachable server callback, or an explicitly qualified desktop/SSH topology. | [Limited-input device OAuth](https://developers.google.com/identity/protocols/oauth2/limited-input-device) |
| OIDC `sub` is the stable Google account identity; email is a display/contact field. | Verify ID-token signature, issuer, audience, expiry and nonce before mapping `(issuer, sub)`. Never link Google account ownership by email equality. | [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) |
| Data use and transfers must match disclosed user-facing purposes, including derived data. Workspace policy restricts model training beyond the particular user's personalized appropriate feature and requires affirmative disclosure/consent for access. | Explain background sync, retained text/embeddings/question views, allowed agents, and external inference recipients. AI Gateway use is not itself permission to transfer Google content. Broad training, advertising use, and selling corpus access are outside this delivery design. | [API User Data Policy](https://developers.google.com/terms/api-services-user-data-policy), [Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) |

Recommended security references are [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) for authorization-code/PKCE, exact redirect and replay defenses, and [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) for native external-browser/loopback flows. These inform the recommendations below; they do not certify a Vrooli runtime.

### Minimum workable Drive grant

Recommended qualification order: attempt the per-file `drive.file` product with an explicit picker/selection experience and enforce read-only driver behavior; measure whether it meets accepted selected-folder synchronization. Include existing descendants, nested descendants, new descendants created after consent, moves into/out of selection, shortcuts outside the tree, shared items, and any selected shared-drive mode. Official per-file documentation does not establish recursive authorization inheritance. Until live evidence resolves it, narrow-folder behavior remains **unverified**, not available.

If recursive unattended folder capture cannot satisfy the accepted outcome, recommend explicit `drive.readonly` with clear account-wide Google permission and Vrooli's selected-folder restriction. Do not silently combine broad metadata and narrow body scopes and present that as account-wide body access. A restricted grant has commercial release consequences; choosing it is an operator/business decision supported by the evidence. Never request Drive writes, Gmail, Calendar, or Cloud Platform privileges merely to prepare for future work.

## Provider-neutral domain and API proposal

Use the existing shared lifecycle service as the safe metadata seam. Add typed contracts through the owning protobuf sources; method names here are proposals, not usable commands.

### Records and ownership

| Record | Minimum proposed fields | Owner and boundary |
|---|---|---|
| Client profile | provider/connector, client strategy, deployment/environment, nonsecret client ID, configured callback base/path, credential reference, declared scopes, setup/verification state, profile version | Integration Hub configuration; secret value in credential authority. Operator-managed and vendor-managed profiles are distinct. |
| Connection | opaque Hub-generated ID, installation/realm/tenant, owning verified principal, verified provider `(issuer, sub)`, account label, client-profile version, granted OAuth scopes, effective supported capabilities, state/reason, verification/expiry times, credential-bundle version, policy version | Hub. Email/label never keys ownership. Return only fields caller may see. Preserve existing pilot IDs/refs under an explicit migration rule. |
| Authorization attempt | opaque ID, actor/owner/tenant, intended connection/action, client-profile version, requested capability/scopes, exact redirect, state digest, expiry, nonce binding, completion/cancellation state, idempotency fingerprint | Hub. Verifier/code/tokens remain ephemeral or authority-protected; no cleartext secret in metadata JSON. |
| Consumer binding | tenant/connection, consuming scenario, domain resource context, approved capabilities, grant source/version, approved actor/service principal, status | Hub owns connection binding; domain owner owns collection/calendar/mailbox selection and grants. Reconcile operator-state as choice/projection rather than create competing binding authorities. |
| Lifecycle operation | operation ID, actor/tenant, action, expected policy/connection version, deadline, safe result/reason, retryability, terminal evidence timestamps | Hub. Bounded server-owned continuation permits CLI/browser reconnect without repeating consent or revocation. |

Recommended lifecycle additions:

| Proposed method | Input | Safe result / behavior |
|---|---|---|
| `ListConnectorCapabilities` / `GetClientSetup` | connector/profile and verified principal | Available strategies, operation names, required purposes/scopes, exact callback from deployed configuration, setup/verification gaps; no client secret. |
| `ConfigureClientProfile` | nonsecret profile plus write-only credential input; expected config version | Validated profile and authority receipt. Require installation configuration permission, not merely connection ownership. |
| `BeginAuthorization` | connector/client profile, wanted capabilities, optional existing connection, idempotency key | Attempt ID, official authorization URL, expiry, safe requested/granted difference. Actor/tenant derives from verified context. |
| `GetAuthorizationAttempt` / `WaitAuthorizationAttempt` / `CancelAuthorizationAttempt` | attempt ID; bounded wait deadline | Pending/complete/denied/expired/cancelled receipt for the authorized owner. No code or token. |
| `ProbeConnection` / `RefreshConnection` | existing ID, expected version, idempotency key | Distinguish actual authenticated probe from authority presence; refresh does token exchange when supported. No fake last-verified time on credential presence alone. |
| `BindConnection` / `UnbindConnection` | ID, target scenario/domain context, required capability, expected version | Verify scenario requirement and actor's target-domain permission; store selected binding. Caller-supplied empty scopes cannot bypass the real requirement. |
| `RevokeConnection` | ID, provider-grant impact acknowledgement, expected version, request key | Immediately disable local use; report provider-confirmed versus pending/unknown revocation and related affected connections. Never call an outage a completed Google revoke. |
| `DeleteConnection` | disabled/revoked ID and chosen domain-retention action | Remove metadata with durable tombstone/withdrawal delivery; no loss of pending provider-revocation truth. |

Represent attempt/operation state separately from the existing connection status enum. A connection can have a failed renewal attempt while its earlier valid grant still works. Derived supported actions come from connector, state, deployment, actor permission, and optional entitlement; UI never invents an unsupported action. Typed error payloads include `reason_code`, `retryable`, optional `retry_after`, safe recovery action, operation ID, and capability impact.

Idempotency is scoped by tenant, verified actor, operation, connection and normalized request fingerprint. A reused key with different operation/payload returns a conflict; retries return the original terminal receipt. Bound key retention and store explicit delete/revoke tombstones. Metadata/credential writes span owners, so use versioned candidate activation plus a durable operation record and restart repair, not an assumed cross-store transaction. External calls must not hold the pilot's single store mutex across all accounts.

### Bounded authenticated operation seam

Recommended: Hub owns provider-specific typed driver services and a shared operation-context envelope. For Google Drive, advertise only bounded metadata listing, permitted file metadata/body read or export, and change-feed operations needed by document-manager. Later Calendar/mail services have their own typed methods and capabilities. Do not expose arbitrary URL/path/method/header forwarding or a generic “get token” endpoint.

Every request carries a verified service/agent actor, an exact connection binding, domain resource context, and bounded operation constraints. The Hub validates the caller audience/capability, tenant, connection owner or explicit binding, effective provider grant, binding policy version, and target-domain authorization. Domain policy comes from the owning service's trusted decision seam or an audience-bound, short-lived, versioned grant whose revocation/freshness is checked; an unverified `collection_id`, `folder_id`, or caller-signed assertion is not a grant.

For selected-folder content, the domain owner resolves membership under its accepted recursion/exclusion/shortcut rules. The Hub independently rejects unbound or out-of-grant file IDs before authenticated body fetch, using that trusted membership proof/current decision. This prevents a consumer from guessing an outside file ID or using a valid connection as account-wide exfiltration authority. Tree membership uncertainty fails closed for content. Legitimate bounded folder-selection discovery is a separate management capability: allow only necessary metadata for the verified owner, explain whether broad metadata is exposed, and do not return arbitrary file bodies.

Apply max page size, response bytes, export MIME allowlist, execution deadline, per-account rate/concurrency limits, approved provider origin, and opaque scoped cursor validation. Redirects cannot forward bearer values to another origin. Even `drive.file` drivers reject uploads, edits, deletion, permission mutation, and arbitrary endpoint escape. [Download/export documentation](https://developers.google.com/workspace/drive/api/guides/manage-downloads) defines distinct blob/export shapes; [change retrieval](https://developers.google.com/workspace/drive/api/guides/manage-changes) distinguishes next-page from new-start tokens and notifications from actual change contents. Preserve those distinctions; document-manager owns applying changes and advancing its committed cursor.

Search grants are narrower than ingestion service grants. An agent authorized to search an existing collection does not thereby gain Hub file-read, scope escalation, OAuth management, or connection administration. Search-hub propagates verified caller/delegation to the producer; document-manager applies retrieval policy before scoring, snippets, context fetch, and caches.

## Native Google authorization, refresh, and revocation

Recommended authorization sequence:

1. Authenticate the Vrooli actor through shared `api-core/authn`; check Hub management capability and exact connection/configuration policy. Present background-read purpose and data handling before affirmative Connect action.
2. Resolve a configured client profile with an approved callback. Create a short-lived, one-use attempt bound to actor, installation/tenant, target connection, exact redirect, profile version, requested scope set, and PKCE challenge/nonce where supported. Recommend S256 PKCE for code flow; qualify Google support for the chosen server library/client type rather than assume a library parameter was honored.
3. Open Google's official consent in the external browser. Server flow requests offline access and service-specific incremental consent. Desktop flow uses its supported full requested set and explicit service expansion UX. `login_hint` and `select_account` improve account choice; they are not account ownership proof.
4. Callback checks the one-use attempt, expiry, redirect/profile binding, CSRF/session correlation, state and applicable nonce/PKCE before exchanging the code server-side. Browser callback may lack a bearer identity: attempt validation binds it to the authenticated initiation. Reject forged/replayed callbacks; never obtain tenant/owner from callback query parameters.
5. Verify Google identity and actual returned grants. For reconnect, require the same provider subject by default; a different selected account is an explicit replacement/new-connection flow and invalidates prior consumer bindings pending review. Never overwrite an old refresh token with empty input or transplant it to another client/account.
6. Persist token material through the credential authority, publish metadata only after credential activation and scope/probe qualification, and return a safe completion page/operation receipt. Callback pages have no third-party scripts; redact query logging, use no-store/referrer protections, and replace the code-bearing URL immediately. Token/code values never cross into UI state, browser localStorage, CLI stdout, telemetry, committed fixtures, or scenario state JSON.
7. Record safe actor/target/scope-change audit events and notify bound consumers of capability changes. Incomplete refresh or failed authority persistence remains a recoverable operation state, not connected success.

Refresh is automatic inside the Hub's trusted driver. Use the canonical credential client to resolve only the required token/client fields into Hub process memory. Key refresh serialization by tenant/connection/client/credential version; coalesce concurrent reads and avoid a global lock. Refresh before known access expiry with clock skew. On success preserve omitted refresh tokens; if replaced, commit the new bundle/version recoverably. Reject stale completion after revoke, client rotation, or account replacement by checking policy/credential epochs. Google refresh does not imply rotating refresh tokens on every request; that is distinct from Vrooli identity-token rotation.

For invalid access tokens, allow at most one eligible refresh/retry of the bounded read. `invalid_grant` becomes reauthorization required; `invalid_client` becomes client setup/rotation required; 429/5xx/transport failures use bounded backoff without manufacturing reconsent. A 403 can mean insufficient scope, object permission, organizational policy, or disabled API, so parse safe provider reason and preserve the distinction. An unavailable/locked authority is an authority recovery state; do not prompt the user to recreate an otherwise valid Google grant or launch private host repair from Hub.

Revoke local capability immediately and increment its policy epoch; bound serving owners withdraw access before physical purge. Attempt Google revocation and record confirmed/pending/unknown result separately. If the provider is unreachable, either keep only authority-protected material necessary for a short, bounded revoke retry or offer immediate local deletion plus instructions for Google Account revocation; expose the tradeoff. Never keep plaintext tokens in the retry queue. Deleting local keys is not proof of remote revocation. Because Google revoke affects the user's grant to the project, enumerate known Drive/Calendar/Gmail/client siblings and warn that unknown other installations may also need reconnect. Unbind or pause one service is a local permission change; it does not claim Google scopes were reduced. Actual scope removal requires a supported revoke/reconsent strategy, including its shared-service impact.

Client profile identity includes deployment/environment and client strategy; connector identity remains provider-neutral. Development/testing and production use distinct project profiles. Callback URI is derived from trusted deployment configuration, never untrusted `Host`/forwarded headers or a arbitrary caller return URL. Permit only predeclared same-origin return locations. The runtime's changing internal port stays behind discovery; external URI remains stable. Do not publish a real domain, reserve a port, or register a client during this investigation.

Operator BYO is the recommended initial self-hosted path because it preserves custody and fits free-self-host doctrine. It must receive professional guided setup/import/status/recovery—not an undocumented burden or a throwaway script. Managed convenience is a separate undecided commercial choice. Do not gate core BYO authorization, local account inspection, revoke/unbind/delete, data export/deletion, or authority recovery on payment. A paid managed path may gate its actual service use and metered processing at the server, using the declared LPBS entitlement authority. BYO is not a technique for bypassing Google verification policy when the real product is publicly distributed.

## Tenant, account, and commercial isolation

Enforce separate keys for installation/realm/tenant, verified Vrooli owner, Google subject, client profile, connection, and domain resource. Generate opaque IDs and preserve existing pilot refs under migration; tenant uniqueness cannot depend on display name or a guessed connection slug. Store Google account link records explicitly. Never infer that a Google email equals an LPBS customer or a local principal. Multiple accounts under one user remain independent; a tenant admin has connection-management privileges only through declared policy, not universal read access to members' personal Drive contents.

Every list/get/mutation/attempt/operation/cursor/cache/audit lookup applies tenant and object authorization. Unauthorized IDs produce a consistent safe response without account labels, scopes, or existence leakage. Background service credentials need bounded target-domain permissions and authentic delegated owner context; arbitrary scenario slug/context headers cannot mint them. Changing account/client/policy version fences stale in-flight reads, cache entries and refresh completion. Policy withdrawal events use a durable delivery/outbox seam, and consumer serving checks must reject stale epochs even if physical cleanup is delayed. Define and evidence the maximum remote-permission detection staleness; neither polling nor cached metadata gives instantaneous Google revocation detection.

Four checks remain distinct: verified principal, coarse Hub capability, connection/domain authorization, and commercial entitlement. Paid customer status never grants access to another user's connection or selected folder. Google consent never grants local scenario administration. Cancellation of a subscription should disable only the relevant managed service after its accepted lease/grace policy; it does not confiscate BYO credentials or permit retention/sale of private data. Keep account management, local withdrawal/deletion/export, and conversion to BYO available under their own permissions. Determine managed-token revocation/deletion and data-retention behavior explicitly when ending the service; show resulting sync/retrieval changes.

Use LPBS's account-bound lease/provider seam and catalog ownership; do not create an Integration Hub billing database or trust UI feature labels. Offline cached entitlement is accepted only under its signed deadline/bindings, not renewed by a failed refresh. Local BYO may run without LPBS; Google network reads still require Google connectivity. Separate provider health, domain sync/index freshness, identity availability, and commercial service state in status and metrics.

## Storage and dependency boundary

Hub stores connection metadata, profile metadata, authorization-attempt digests, bounded lifecycle/idempotency/revocation state, audit metadata, and binding/withdrawal delivery records behind per-domain repositories. Credential authority stores client secrets, refresh tokens and any persisted access-token bundle/secret verifier. Treat provider labels/scopes and IDs as private metadata even though they are not secrets. Content never enters Hub diagnostic state or audit bodies.

Recommend SQLite for transactional Hub metadata when durable attempts, operation recovery and concurrent lifecycle require it, behind engine-independent repository interfaces and per-domain embedded schema using `SchemaProvider`/`EnsureSchemas`. Preserve pilot data via an explicit importer; no destructive recreation or hand-migration of credential addresses. Keep single-replica local operation simple; require appropriate shared coordination before claiming multi-replica refresh/revoke correctness. Do not add Postgres, Redis, Qdrant or Vault by default. Any required SDK, OAuth library, database adapter, CLI/UI module or shared package adoption goes through Scenario Dependency Analyzer and governed generated sources. A existing library being available is not approval to bypass dependency governance.

Document-manager owns original archival mode, normalized text/structure, passages and vectors under collection retention policy. Remote-backed default has no permanent original archive; this change must not remove explicit legacy archival functions. Cursor/collection policy belongs beside that owner's code. Integration Hub cannot solve document retention by placing content in its metadata database.
