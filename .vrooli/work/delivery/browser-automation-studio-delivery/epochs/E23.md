Owner map and boundary:

- The generated `WorkflowDefinitionV2` proto is the persisted/executable V2 model. Go workflow ingress/normalization (`api/services/workflow/normalize_v2.go`, `v2_flow_builder.go`, and `converter.go`) is a typed server boundary with separate import handling; it remains an owner in this tranche.
- `api/automation/compiler` owns conversion from the canonical workflow definition to execution plans. It is an execution projection, not another editor-state owner; leave it intact.
- `ui/src/domains/workflows/utils/normalizers.ts` owns React Flow node/edge ingress and builder-specific helpers. `ui/src/stores/workflow/utils/normalization.ts` assembles API/proto payloads into store state. `ui/src/stores/workflow/utils/serialization.ts` separately strips canvas state and builds persisted flow definitions. The store calls these in sequence for load/save/fingerprint/restore; E23 replaces that chain with one generated-proto-backed codec and keeps React Flow state as a projection.
- Preserve behavior for external workflow import, node/edge editing and layout, preview/transient data stripping, execution viewport settings, dirty fingerprints, sync/version conflicts, save, and restore. Keep unrelated builder helpers and workflow metadata/version parsing in their current owners.

## Gate amendments

- 2026-10-07 — **Round-trip field scope corrected.** Admission combined typed V2 fields with arbitrary unknown JSON keys. The generated `WorkflowDefinitionV2` schema is the persistence contract, and the current `workflowDefinitionToProto` conversion uses `fromJson(..., {ignoreUnknownFields:true})`; arbitrary keys are not represented by that schema. The pre-E23 `workflowApi.ts` conversion used the same generated-schema conversion and dropped those keys, so requiring them to survive protobuf encoding would require a proto/runtime contract change expressly excluded from E23. The gate is therefore schema-supported V2 field round-trip through the codec, plus retention of unknown keys during raw JSON↔canvas projection before protobuf encoding. Existing codec tests cover both sides. Typed actions, IDs, node/edge positions and handles, metadata/settings, execution viewport, and transient-state filtering remain required.
