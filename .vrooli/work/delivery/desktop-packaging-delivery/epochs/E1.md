## Modules and budgets

1. **Contract (`packaged-launch.v1`).**
   - Define the marks and metrics of design §6.1 as a generated proto contract
     under `packages/proto/schemas/performance-health/v1/` (new `packaged`
     package or an extension of `startup`; choose by fit and record why).
   - Generate only through the governed route:
     `cd packages/proto && make generate SCENARIO=performance-health` (and
     `SCENARIO=scenario-to-desktop` if it consumes the types). Verify with
     `make verify-committed-gen`.
   - Mobile-ready rules (design §6.1, §7). The Android ramp must be able to
     emit the same message later:
     - nothing in the contract names Electron or desktop-only concepts;
     - every mark carries an availability state and a reason (for example,
       Android cannot observe `shell_ready`);
     - `platform_detail` is a `oneof` of per-platform messages, with a
       `linux_desktop` member only in E1;
     - process roles are a string taxonomy: the generic roles (`shell_main`,
       `webview_renderer`, `webview_gpu`, `webview_other`, `backend`,
       `unknown`) are required, and engine-specific roles each map to one
       generic role.
2. **Producer (scenario-to-desktop).**
   - Extend the existing launch path (`api/smoketest/launchtrace.go`,
     `performance.go`, `platform_resolver.go`) to emit `packaged-launch.v1`.
     Map the `launch-trace.v1` events onto the new marks and record the
     mapping. `launch-trace.v1` stays readable for old evidence, but no new
     code writes it once v1 is emitted (one owner).
   - `api/procmetrics`: add PSS and USS from `/proc/<pid>/smaps_rollup` per
     process, summed by role. RSS stays reported, never compared. Add an idle
     CPU window (60 s after `app_interactive`, no input) and steady PSS after
     the scenario journey plus 60 s.
   - Add `webview_*` and `shell_main` roles to the taxonomy for later shells.
     For E1 they are only a tested classification path.
   - Cold method without root: fresh install directory and fresh user-data
     directory, then evict the artifact files from the page cache with
     `posix_fadvise(POSIX_FADV_DONTNEED)` from a small Go helper. Do not use
     `drop_caches` or `sudo`. Verify eviction with `mincore` residency before
     launch and record the residency percentage in each cold sample.
   - `app_interactive`: honor `performance.mark('app-interactive')` when the
     UI emits it, read through the renderer. Otherwise use the fallback
     "first contentful paint and the first completed API response, then 500 ms
     without a long task", labelled `app_interactive_source=fallback`. Adding
     the mark to a reference scenario's UI is allowed if it takes ≤10 lines
     there. The template-wide mark is an E6 proposal, not E1 work.
   - Sizes: `artifact_bytes` (AppImage), `installed_bytes` (extracted tree).
     `update_bytes` stays `unavailable` until a strategy supports delta
     updates.
   - Add a measured-launch operation callable by performance-health:
     `LaunchMeasured(artifact, mode cold|warm, journey?)` returning one
     `packaged-launch.v1` sample. Put it next to the smoke-test service, reuse
     its Xvfb, isolation and platform resolver, and add no second launcher.
3. **Consumer (performance-health).**
   - A `packaged` domain under `api/internal/` that runs N launches through
     scenario-to-desktop and stores samples.
   - `perf_samples` (or a sibling table, if one-column-per-metric does not
     fit) gains `target`, `strategy`, `platform`, `experiment_id`,
     `host_fingerprint`, `artifact_digest`, `condition` (cold/warm), `display`,
     `profiler_mode`, `power_state`.
   - Aggregation uses nearest-rank p50/p95 plus min, max and spread. The
     comparability rule is in design §6.2; non-comparable samples are never
     merged.
   - Budgets: parse `performance.budgets.packaged.desktop` from the measured
     scenario's own `.vrooli/testing.json` (`api/internal/budgets/config.go`).
     Advisory in E1, so no reference scenario's file needs to change.
   - CLI:
     - `performance-health packaged capture --scenario <s> --ramp desktop --strategy electron-sidecar --runs 10 --condition cold|warm --json`
     - `performance-health packaged report ... --json`
     - `performance-health packaged compare <a> <b> --json`
4. **Baselines.**
   - Build each reference scenario with today's ramp, through the CLI or API,
     never by running binaries directly.
   - Capture 10 cold + 10 warm runs each, after one discarded warm-up.
   - Store the JSON under `~/.vrooli/evidence/desktop-packaging/E1/`.
   - Write `scenarios/scenario-to-desktop/docs/internal/packaging-baseline.md`
     with:
     - the median table: first window, backend ready, FCP, interactive, PSS,
       idle CPU, sizes;
     - host and artifact identity;
     - any substitution of a reference scenario (also update TARGETS.md
       through a slice-log request).
5. **Waterfall explanation.**
   - For hello-desktop, attribute the ~6.2 s `runtime_spawn_to_ready` to
     concrete buckets: process exec, token and IPC port, each service's
     spawn, its first successful health check, and polling slack. Candidates
     to test:
     - `health_success` readiness polling at 500 ms × retries
       (`runtime/health/checker.go:115-140`);
     - the Electron main-process 350 ms `/healthz`→`/readyz` loop
       (`templates/vanilla/main.ts:1340-1353`);
     - service start ordering in `runtime/supervisor.go`;
     - the hello-desktop API's own start.
   - Use experiments, not code reading: time each bucket with trace marks, and
     test a candidate cause with a temporary local change that is reverted
     before the next unit.
   - Record the findings in `packaging-baseline.md`, as the ranked fix list
     for E3. **Do not ship optimizations in E1.**
