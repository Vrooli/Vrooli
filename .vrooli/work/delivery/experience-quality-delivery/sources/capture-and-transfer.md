### F. HORIZONTAL ARTIFACT TRANSFER: CHATGPT/CLOUD ↔ LOCAL MACHINE

Use this procedure for an authorized artifact handoff in either direction, including a single file. It extends BW05 without moving project authority or creating a second specification. The earlier semantic reconciliation and identity gate still apply.

1. Identify the handoff before choosing a route

State the source and receiving environment, responsible sender and receiver, purpose, required artifact types and permitted destination. Read the current project entry and selected source, not only a search hit or summary. Record which source governs and whether each item is an original, derivative, illustration, candidate or historical reference. Possession in the cloud does not establish possession on the local machine.

2. Pin the exact artifact and its custody

Use the existing project manifest or receipt: stable source ID/link; source revision/version and observation time; selected filename/MIME type; byte size and SHA-256 of exact transferable bytes; target path or stable Library/Drive ID; route and receiving task; transformations and exclusions. Record archive file count and relevant entry list, image dimensions, or PDF page count as applicable. Keep source and derivative hashes distinct. A native document revision and an exported byte hash answer different questions; record both when exporting. Note inaccessible fields as unknown rather than inventing them.

Retain who prepared, transported and received each version, with timestamps and acknowledgement. Do not record signed URLs, credentials or transient bearer descriptors in ordinary project docs. Pin the non-secret source identity and supported preparation method instead. Recheck source drift before use; a successful earlier transfer is not a freshness guarantee.

3. Choose by artifact type and direction

Inspect both the receiver’s declared built-in tools and hosted connector tools before concluding that materialization is unavailable. A connector may return a file reference for a separate supported downloader rather than a workspace path. Match the reference scheme to that tool’s actual contract; do not invent a downloader or use an unqualified bearer URL.

Text and native Docs: prefer the receiver reading the authoritative source through its supported authenticated connector. If a snapshot is needed, transfer an authorized export with revision, format and transformation noted. Plain-text extraction can omit chips, links, tables or images; inspect the native structure or preserve the full document when those features govern the work. Pasting an excerpt may unblock a bounded text question, but must be labeled partial and cannot stand in for an entire specification.

Images and PDFs: for small original-image cloud→local handoffs, prefer the private Drive receiving recipe qualified in section G when its required access and capabilities are present. For other cases, qualify the route for the actual artifact and environment. Transfer original bytes through a supported materialization/download route, verify size/hash and decode at the receiver. For image-dependent work, the receiving agent must actually inspect the selected pixels at useful resolution. For a PDF, verify page count and render the relevant pages. An asset-pointer string, thumbnail, contact sheet or prose description is not original-image access. A successful decode alone is not evidence of visual inspection or implementation fidelity.

Source ZIPs and asset bundles: preserve the original archive and hash, list entries and compare expected counts before extraction. Extract into the authorized destination without overwriting unrelated or dirty local work. Verify required files, paths, manifests and hashes after extraction; exclude secrets and unsafe archive paths. A source package is not a running build. For reverse local→Library updates, preserve the intended file identity and version history when replacing an existing deliverable.

Installed helper bundles must include the dependency-complete official layout, including nested companion directories and relative-import targets, rather than only root scripts and assets. Inventory required paths before transfer and verify them after extraction. For Sites packaging, include the installed skills/sites/scripts/prepare-site-build.cjs companion when the helper depends on it. Preserve the installed source unchanged; record missing source revision information as unknown. The receiver must verify both exact bytes and the intended packaging step. Section G records the scoped Flywheel recovery that exposed this requirement.

Metadata and receipts: return IDs, revisions, hashes, counts, qualified errors and acknowledgement through the existing task/project record. A text message can carry this receipt; it cannot carry binary bytes merely by naming a file. Keep metadata delivery, byte delivery and useful target access as separate states.

Secrets: credentials, keys, tokens and signed bearer material are excluded from ordinary transfer packets, ZIPs, Docs and receipts. Use the supported secure authentication/handoff route under the applicable controls. Do not invent credentials, copy browser sessions or weaken access to complete a transfer.

4. Classify failure before a fallback

Record exact operation, artifact/version, direction, receiving environment, returned status/error and whether bytes or any mutation actually occurred. Distinguish unavailable tool/schema, pointer-only response, expired descriptor, transport/service error, explicit policy/access denial, corrupt/incomplete bytes, and semantic/version mismatch. HTTP 403 alone does not establish which of these causes applies or that owner permission is missing.

A fallback is eligible only when supported in the actual environment, within the same authorized data/destination/effect, and consistent with the enforcing controls. A technical capability gap may justify another supported route; a real denial is a boundary, not an invitation to route around it. After denial, pause the dependent action and report the exact blocker. Owner approval and admission remain separate. Retry only when the applicable control permits it, with changed evidence or a supported recovery; stop when a permitted retry is denied or reproduces the unresolved failure. Never automatically change domains, encode bytes into prompts, use public hosting or broaden sharing to evade a denial.

5. Verify receipt and next use

The receiver acknowledges exact source/version, destination and observed checks; missing items remain explicit. A fresh receiving reader then opens the normal project entry and required sources/assets without author coaching and performs the representative intended read or inspection. Record coverage and limits. Only then label the scoped handoff verified. Team enablement and implementation acceptance still follow their existing project contracts.
