# Product mockup craft and lifecycle

## Set the standard with actual pixels

Inspect the original references beside the current candidate before diagnosing quality. Identify concrete differences in hierarchy, density, typography, content, surfaces, imagery, navigation and compact reflow. Do not claim that all newer work is lower-fidelity when only explanatory specimens are, or assume that visually appealing historical samples have correct data and behavior.

Separate three deliverables: a product-fidelity screen depicts a believable finished application; a behavioral diagram explains relationships or transitions; a component/state specimen compares focused behavior. Each is useful, but none substitutes for the others. A minimal or missing-image screen should preserve the same premium product grammar, not become a wireframe.

Pin a project-owned visual contract: shell, navigation labels/order, typography roles, semantic colors, controls, icon family, spacing, image treatment and content hierarchy. Keep the project's palette and domain fixtures out of this generic method. A consistent system matters more than repeating a decorative style.

Write the state brief before generation: screen/job, concrete scenario, selected data revision, known and unknown facts, one primary action, secondary actions, outcomes and compact reflow. Resolve cross-screen arithmetic and scope first. Do not let generation invent data, controls, destinations, acceptance, hostnames or completion claims.

For main-screen mockups, put desktop and mobile together in one review image when that is the project convention or user request. Both must depict the same selected state and consequential content. Reflow rather than shrink. Place less important content below the compact fold instead of forcing illegible microtype. A composed board is not measured viewport, touch-target or runtime evidence.

Use the applicable image or native-design skill. Supply the actual inspected reference images, naming the role of each, and preserve the exact generation/edit prompts. Prefer one representative exemplar and targeted corrections before a broad batch. Distinguish author inspection, independent critique and owner acceptance. Do not scale an unaccepted visual direction when the owner explicitly requested a checkpoint.

## Save versions during authoring

Persist artifacts as they are authored, not as a cleanup operation after approval. Use the project's existing storage and identifiers. Keep image/source, exact prompt or authoring source, reference pins, state brief, source specification basis and validation evidence together, with durable locators and byte digests. Scratch paths alone are not durable project storage.

Give every immutable content version a stable ID. Never silently replace its pixels, prompt, fixture or source pins; create a new version. Preserve originals and existing provider file identities. A status or current-pointer change should not copy, relocate or regenerate the artifact. Use archival state where adequate; move files only when that genuinely improves the project's established organization.

For historical imports, record the actual knowledge boundary: recovered exact prompt, reconstructed description, authoring script, not applicable, or unknown. Do not invent a generation date, model, seed, prompt, input revision or approval. A retrospective component or requirement mapping must be labeled retrospective, not presented as generation-time provenance.

## Queryable per-version records

Adapt these fields to the project's native records; do not mandate this exact schema:

- Version ID, stable family/resource ID, parent/superseded version and creation/observation date with its evidence basis
- Artifact kind, screen/state, device coverage, durable file IDs/links, editable source and SHA-256/other exact revision identity
- Exact generation and edit prompts, tool/model/settings when known, reference image/version pins and their roles
- Source specification section/revision/hash; relevant assumptions and components with versions when known
- Relationship type for each source: used-to-generate, normative constraint, visual reference, retrospective mapping or unrelated context
- Validation evidence, reviewer type, acceptance scope/source, unresolved limitations and linked project decision/question IDs
- Independent production/review, approval, freshness, retirement, implementation and display/current-pointer dimensions

Keep one canonical version record set and one existing decision queue. Derive current/approved/stale views from those records; do not maintain a competing mutable JSON “current” catalogue, sheet, document and Page. A dated export may be a snapshot, clearly labeled with its source and revision. Preserve lifecycle-event history, exact approval evidence and the immutable content basis when mutable status fields change.

Approval is scoped: visual direction, exact pixels, behavior, specification and implementation are different. Record the actual accepted portion and residual scope. A visual approval never validates runtime behavior or authorizes external actions. A newer image does not inherit an older image's approval.

Freshness is independent of approval and retirement. Compare relevant source/dependency pins with current source truth and record changed IDs, dimensions, affected regions, consequence and check date. A changed dependency means affected scope needs review; it does not automatically revoke unrelated visual approval or delete/archive the image. If pins are missing, freshness is unknown or needs-review, never silently current. A retired version may remain current with respect to its old inputs; an approved version may be stale.

Implementation status requires separate dated runtime evidence. “Source-applied”, “rendered”, “self-reviewed”, “approved visually” and “implemented” are not synonyms.

## Review and registration gates

Check important text verbatim, labels/order, selected date/state, units and arithmetic, synthetic versus actual facts, depiction of unknowns, meaningful action outcomes, image/recipe identity, desktop/mobile equivalence and visibility of primary controls. Compare pixels at a practical common scale with the original. Check visual quality separately from behavioral consistency and document-layout quality.

Before declaring the catalog ready, verify that an independent reader can find:

1. The current exact image and why it is current
2. Its prompt/edit chain, references and source/assumption/component basis
3. What the owner accepted and what remains undecided
4. Stale or unknown dependencies without losing unaffected approval history
5. Retired alternatives and original provenance gaps
6. The actual implementation evidence, or its absence

Exercise current-view derivation, duplicate-ID rejection, missing-reference detection and status separation with synthetic fixtures outside live records. Do not insert invented approvals merely to test the workflow. Preserve query bounds and update discovery pointers only after artifacts and records pass readback. Report any incomplete migration or unavailable evidence.

## Adopt locally without coupling

Pin or copy the chosen method revision into project documentation and preserve local exceptions. A future shared-skill update should not silently change project authority, schema or accepted design. Reuse craft and review techniques across projects; keep their registries, product assumptions, decision queues and ownership independent.
