## Explicit setup and existing-source adoption

Normal acquisition remains `scenario-dependency-analyzer deps install source/openrgb@1.1 --scenario openrgb --surface host-tool --exact --apply`, through an explicitly selected resource source. It stages bounded verified bytes without starting the program or changing hardware permissions. Startup does not acquire or update. Native profile selection never implies resource enablement.

Linux extracts the pinned SquashFS with a pre-existing root-owned `/usr/bin/unsquashfs` using the exact profile offset and no downloaded code execution. If absent, use the governed optional `system/squashfs-tools` host-tool route; setup never installs it implicitly. macOS/Windows extract ZIP offline in Go. Extraction bounds entries and total bytes, rejects path aliases/traversal/foreign bundle roots and delays relative symlink creation until all regular writes and link-parent directory preparation finish. Every link parent is checked component by component as an actual directory; earlier queued aliases cannot redirect later link creation. macOS retains `OpenRGB.app` and framework symlinks. Each stage publishes exclusively after complete verification and platform sealing. Native control-plane launchers use the same root-sealed store and exact admitted image digest. Explicit setup exposes a no-path launcher preparation API that opens only the immutable installed supervisor image selected by its protected native boot definition; generic Windows process-image observation is never substituted. Public setup validates the current native host profile before account or service provisioning. Native artifact selection and provenance sidecars use only OS/architecture facts, never generic GPU inventory or machine-home acceleration preferences. Native publication locks use read-only admitted machine-owned handles; per-user lock setup never chmods/chowns their sealed parents or files.

Existing-source selection fingerprints before any vendor program runs. Only an exact profile envelope or payload is accepted. A payload requires its complete enclosing native bundle, whole-tree digest and ABI. The owner copies the closure into its sealed artifact store, preserves the installed original, and retains the selected artifact identity for recovery. Standard macOS `/Applications` and user `Applications`, Windows KnownFolder ProgramFiles, and explicit PATH installations are considered only during requested adoption. An arbitrary matching version string is insufficient.

On macOS, new artifact publication requires explicit privileged setup under the separate root-owned `/Library/PrivilegedHelperTools/com.vrooli.openrgb` store. The operator-writable admission/capsule root cannot contain an executable or dependency. Existing exact sealed stages can be reused read-only. Root-owned ancestry, nonwritable sealed files and native extended ACLs prevent an ordinary operator from replacing the checked path before Darwin same-PID path execution. The shared native immutable-path verifier is used by both observer and executor; native CGO/ACL/exec behavior still needs target qualification. macOS framework symlinks remain confined and their real targets/parents are independently root sealed.

Windows publishes through explicit elevated setup to KnownFolder ProgramFiles/Vrooli/OpenRGB. Objects are atomically Administrators-owned from first creation. Protected DACLs retain SYSTEM/Administrators full control and grant the actual ordinary operator read/execute. Code ancestors grant that reader metadata/traverse/READ_CONTROL; no broad Users/Everyone grant is added. Reparse points and multiply-linked files are refused. The complete code/DLL/plugin closure stays machine-owned outside mutable operator state; runtime executes as the actual non-elevated operator. No separate service identity or same-SID read-denial claim remains.

## Windows HID serving derivation

The official source bundle has22 regular files:16 PE images and6 PawnIO data modules. Upstream bus initialization can access PawnIO before per-controller detector flags. The serving recipe first verifies the complete original source tree, verifies each module's exact hash/size, omits exactly those six executable-adjacent modules, and verifies a separately pinned complete derived tree. It changes no payload or library bytes and preserves the installed original during adoption. This is a declared derived serving profile, not an incomplete official bundle accepted under its original digest.

## Native dependencies and configuration

The bundles include upstream Qt/HID/libusb/crypto libraries and plugins, not every OS ABI dependency. The entire Linux closure requires GLIBC2.39, GLIBCXX3.4.32 and CXXABI1.3.15-compatible native providers (the main executable alone understates the floor). Read-only preflight inspects the exact native ELF interpreter, root-owned system libraries and required symbol-version definitions for every external dependency; architecture alone is insufficient. Private libraries remain in sealed `usr/lib`. Both macOS closures contain minimum-OS15.0 images. Preflight reads the product version and checks each declared system image in the active dyld cache through Apple's metadata API, without loading a library; CGO/SDK support is required and no-CGO explicitly reports unsupported. Complete loader metadata covers normal/weak/reexport/upward/lazy commands, custom dyld, runpaths and embedded environment. Private dependency graph and immutable stage layout checks resolve framework imports; canonical system frameworks and `/usr/lib` remain OS dependencies. The [complete loader proof](MACOS-COMPLETE-LOADER-PROOF.md) records the bounded inert build-runpath evidence and explicit derived app-resource-signature limitation. Linux's actual current-host library metadata passed, but no new ARM/macOS backend was executed here.

Windows's portable ZIP omits Microsoft C++ redistributable DLLs. `internal/tools/msvc-runtime` owns the optional system prerequisite through SDA's existing native host-tool/Winget route (`Microsoft.VCRedist.2015+.x64`). No standalone DLL download, arbitrary PATH lookup or app-local runtime substitution is permitted. The resource's read-only preflight requires native System32 x64 PE files for MSVCP140, MSVCP140_1, MSVCP140_2, MSVCP140_CODECVT_IDS and VCRUNTIME140/140_1, v14>=14.44, cached Windows signature trust, actual Microsoft Corporation signer identity, and the named MSVC exports imported by the sealed bundle. OS10+ UCRT is checked separately. The frozen Qt6.8 closure additionally requires [Windows10 1809 or later](https://doc.qt.io/qt-6.8/windows.html); current-host setup checks native build17763 before account/service effects. The six-provider list is shared by ABI/version/provenance and named-export admission; an unknown Microsoft runtime-family import refuses qualification. The official executable's PE linker14.44 and VS2022/Qt6.8.3 build source establish the toolset family; import checks avoid inferring patch ABI from a version string. Missing prerequisites refuse startup with the governed installation route. This source route has cross-build evidence only; Windows installer, signature cache, ABI and native boot-task execution remain unqualified until observed on a target.

ResourceManager accesses preferences before CLI `--config`. Both `XDG_CONFIG_HOME` (Linux/macOS) and `APPDATA` (Windows) point to the private resource config root before program construction, while CLI config points to its `OpenRGB` child. Ambient preferences are never imported or modified. Saved remote clients and all automatic profile hooks remain explicitly disabled. The exact PE RT_MANIFEST resource is parsed and requires `requestedExecutionLevel=asInvoker`, `uiAccess=false` in every resource language. Pinned startup source has no required elevation/relaunch branch for the server path. This permits a narrow headless launch in source without proving native boot-task execution. Upstream constructs QApplication only in START_GUI; intended headless server startup does not require the Windows ZIP's absent offscreen QPA plugin. Runtime/headless qualification remains separate from this source finding.

The [Mac headless source assessment](MACOS-HEADLESS-SOURCE-ASSESSMENT.md) records the corresponding exact startup branches, Cocoa-only QPA bundle contents and early Intel macUSPCIO initialization. No offscreen-plugin or ordinary-UID transport-denial assumption substitutes for native qualification.
