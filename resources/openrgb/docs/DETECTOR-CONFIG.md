# OpenRGB detector map

`config/detectors-release_1.1.json` is an explicit detector map for the pinned
OpenRGB 1.1 source revision. It enables only the ASUS Aura SMBus motherboard
and ASUS TUF RTX 4070 Ti SUPER detectors. The generator walks active C++
registration calls, resolves simple string-name macros, deduplicates names,
and rejects unknown registration macros, unresolved names, source changes, or
unexpected counts.

The map has **1,948 active static settings keys** from **2,160 static
registration calls**. Multiple calls can share a user-facing key, such as
different PCI subsystem IDs for one GPU model. The pre-generator 1,954-key
asset had six stale names from commented-out registration calls: Cooler Master MM531,
FL ESPORTS F11, LG 38GL950G Monitor, Razer Blackwidow V3 Pro (Bluetooth), Razer
Basilisk V3 Pro (Bluetooth), and Razer Basilisk V3 Pro 35K Phantom Green
(Bluetooth). OpenRGB removes unknown detector settings during initialization,
so these names are not active detector registrations and are omitted from the
regenerated 1,948-key asset.

The source union is larger than the Linux runtime inventory. The pinned
`OpenRGB.pro` source selection and `_WIN32` guards account for 17 keys omitted
from a Linux build: two in Windows-only detector files (`Creative SoundBlaster
AE-5` and `HP Omen 4-Zone Laptop Keyboard`), two Logitech registrations guarded
for Windows/macOS (`Logitech G Powerplay Mousepad` and
`Logitech Lightspeed Receiver`), and 13 MSI Mystic Light USB registrations
guarded by `_WIN32` in `MSIMotherboardControllerDetect.cpp`. Those MSI keys are
`MS_3EA4`, `MS_4459`, `MS_7B10`, `MS_7B94`, `MS_7B96`, `MS_7C42`, `MS_7C70`,
`MS_7C85`, `MS_7C88`, `MS_7C89`, `MS_7C96`, `MS_7C99`, and `MS_905D`. That
leaves **1,931** keys in
the Linux runtime detector registry. The generated map intentionally describes
the cross-platform source union; OpenRGB prunes entries not compiled into the
current platform binary.

The old 1,008-key census matched only macro names ending exactly in
`DETECTOR`. It missed static macro families whose names continue with HID
filters, including `_I`, `_IP`, `_IPU`, `_P`, `_PU`, `_BP`, `_BPU`, and
`_PU_ONLY`, plus `REGISTER_WOOTING_DETECTOR` and wrapped HID variants. The
generator classifies 2,160 calls across 17 source-defined static macro
families. The large groups are `REGISTER_I2C_PCI_DETECTOR` (902 calls),
`REGISTER_HID_DETECTOR_IPU` (411), `_IP` (242), `_PU` (208), basic HID (177),
and `_I` (118); it also covers the basic, filtered and wrapped HID variants,
Wooting, generic device, and I2C DRAM/I2C detector registrations. This is the
source of the gap between the incomplete 1,008-name scan and the full static
inventory.

The QMK OpenRGB and QMK VialRGB entries use `REGISTER_DYNAMIC_DETECTOR`.
OpenRGB invokes those callbacks through `ProcessDynamicDetectors`; they are not
entries in `Detectors.detectors`. The resource config writer therefore clears
the `devices` arrays in `QMKOpenRGBDevices` and `QMKVialRGBDevices` on every
startup, including seeding explicit empty arrays on first launch, while
retaining other settings in those objects such as QMK update tuning. This
prevents user-configured dynamic HID registrations from extending the two-entry
static startup allowlist.

The pinned source has no other `REGISTER_DYNAMIC_DETECTOR` callback. Other
user-configured device lists (for example DDP, DMX, Govee, LIFX, Nanoleaf,
Philips Hue/Wiz, and Yeelight) are read from within their corresponding static
detector callbacks. The generated map contains every active static detector
key and enables only the two listed above, so those callbacks are skipped.
OpenRGB still invokes its I2C bus detector functions independently of this
device allowlist; startup may enumerate bus interfaces even when all other
device detectors are disabled. The allowlist bounds controller detector
callbacks, not all operating-system device enumeration.

## Regenerate and verify

Pinned source identity: commit `8e16de27858cf2be6af54a33ce003df74cb9fd3e`,
source tree `a5c3f7581615f912226cfc57078b150a36bfb102`. The generated asset
SHA-256 is `1fcc3b911bf1b900579916498f273f465550398f14f2a1c0d1a0ea7bb863270b`.

Use a clean checkout of the pinned upstream source. No OpenRGB executable is
run by this script.

```sh
git clone --depth 1 --branch release_1.1 https://gitlab.com/CalcProgrammer1/OpenRGB.git /tmp/openrgb-release-1.1
python3 resources/openrgb/scripts/generate-detectors.py --check --source /tmp/openrgb-release-1.1
python3 resources/openrgb/scripts/generate-detectors.py --write --source /tmp/openrgb-release-1.1
```

`--check` compares the generated bytes with the versioned asset. `--write`
replaces that asset only after the source tag, commit, registration coverage,
call count, key count, and the exact two enabled detector names all pass. The
script covers static registrations across the pinned source tree; it does not
model per-platform preprocessor selection. A platform build may prune names
whose registration source is not compiled for that target.
