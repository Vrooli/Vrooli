# Native OpenRGB ownership and qualification

This design extends the existing resource owner; the accepted target remains the delivery SPEC. Source compatibility, native runtime qualification, and observed physical output are separate facts. The release-profile targets are Linux amd64/arm64, Darwin amd64/arm64 and Windows amd64. Windows arm64 has no official 1.1 native asset and remains unsupported. Profiles never imply installation or enablement: acquisition requires explicit optional source/setup action, while managed process launch and hardware access require enablement and completed admission.

## Ownership and persisted identity

The platform package owns native service containment, exact invocation identity, inspection, stop, release and uncertain-submit lookup. The resource owns durable logical admission, once-only execution claim, frozen artifact/config/device scope, initial start and update/rollback/recovery. Lighting Runtime owns desired policy and reconciles through the authenticated private binding. The scenario retains the single controller roster. Hostreqkit owns selected-device permission evidence and setup. Native adapters do not duplicate these state machines.

Legacy Linux ServiceRef and device policy bytes remain valid, with no new mandatory field. Native records add an explicit versioned, platform-tagged identity and reject mixtures of cgroup fields with native manager facts. The adopted actual-operator contract is version2; earlier dedicated-account candidates are historical source evidence. Native identity binds manager/domain/name, exact intent and invocation, account, containment and root incarnation. A PID, service name, executable pathname or launch success alone is insufficient. Native process disappearance and full containment absence must both be observed before retirement; unknown observations retain the fence and fail closed. Source evolution uses the canonical persistent-state classification and fingerprint, including nested launch/service/device records.

Darwin boot setup publishes one machine-owned LaunchDaemon whose UserName is the actual operator. The same ordinary RuntimeSupervisor owns operator state and reconciliation without a desktop session. Per-role ownership uses the operator's native launchd user domain; boot-domain availability and exact orphan retirement remain explicit implementation/target qualification gates. A process-only contract may deny fork/spawn where that is required to prove exact native ownership; it must be demonstrated for the controlled release. UID-wide discovery or termination is forbidden. A login LaunchAgent cannot substitute for logged-out boot operation.

Windows boot setup uses the maintained Task Scheduler BootTrigger/S4U owner with least-privilege run level and the actual operator. It stores no operator password. Its documented lack of network/EFS credentials is assessed separately from local signing/storage availability. Exact task definition, instance/action identity and lifetime must be observed; engine PID alone is not action identity. Per-role native ownership uses a protected, non-breakaway Job and the same standard, non-elevated operator token. Superseded unoperated dedicated-account candidate receipts are rejected rather than silently reinterpreted. No per-resource account or permanent privileged Vrooli broker is required by this design.

Each Windows role is submitted through an exact create-only on-demand Task under that same operator. Direct child submission cannot provide persistent lifetime because a CLI/API caller may already be inside a kill-on-close Job. The Task action is the existing immutable capsule wrapper, with no triggers, retries or time cutoff. The wrapper proves its exact singleton Task instance/action and joins/retains its UUID-specific non-breakaway Job before any device or vendor work. A durable RunIssued marker precedes the only Run request; uncertain acknowledgements never authorize redispatch. Stop revokes admission, disables and stops the exact Task on every retry, and requires fresh Task/Job absence. After boot changes, the old Job must be absent; old PID values never authorize a signal or inspection of a reused process.

Windows has no same-process exec replacement. Its serving executable is a typed child of the admitted wrapper in the same Job. Prepare the verified image suspended, observe its inherited narrow account/Job/image/argv/environment/working directory, durably claim this exact child, and only then resume it. The wrapper remains supervised until child exit; a crash before claim/resume cannot leave a serving unowned payload. Child incarnation and image identity are persisted separately from wrapper identity, and every readiness/listener/stop check uses the appropriate identity. Linux and Darwin retain same-root execution where verified-image semantics support it.

## Artifact and configuration boundary

Official 1.1 artifacts must be acquired through Scenario Dependency Analyzer, with actual bytes, release/asset identity, exact length and measured SHA256 pinned per platform. Offline extraction must never execute the GUI/detectors or expose the SDK. Qualification checks native executable headers and the complete sealed AppDir/bundle/dependency closure, not just the launch binary. Adoption must match the same qualified profile. Startup cannot silently upgrade; update and rollback preserve exact retained envelopes, selected policies and detector catalogs.

Original-source identity and serving identity are distinct. Windows verifies the complete official 22-file source before omitting six fixed PawnIO modules and proving the separately pinned 16-PE serving tree. Both Mac profiles verify their complete official bundles before omitting the exact unreferenced QtCore5Compat framework, whose four absolute Homebrew imports prevent a closed serving graph. The resulting 77-image bundles preserve every remaining executable, library and page-signature byte. Adoption requires the complete original source and preserves it; an already-derived bundle is not an original-source substitute. Recipe-addressed stages and sealed metadata bind the original source, selected envelope/payload, recipe and complete serving tree for initial launch, update, rollback and recovery.

The Mac gate uses the shared held-reader Mach-O parser for normal, weak, reexport, upward and lazy loads, alternate flags, dynamic linker, runpaths and embedded dyld environment. It verifies the full private dependency graph and all 32 declared system images against native cache metadata, refusing custom dyld, embedded environment, unresolved or competing private targets. Exact stage inventory and immutable ancestry preserve adjacent plugin-search-path absence. Three fixed C libraries' build runpaths require exact image/path evidence and cannot flow into declared runpath-dependent descendants; this is not a general arbitrary-dlopen confinement claim. See [the complete loader proof](MACOS-COMPLETE-LOADER-PROOF.md) and [pinned release profiles](NATIVE-RELEASE-PROFILES.md).

The derived Mac bundle has no unchanged whole-app resource-signature guarantee. Apple Silicon's original CodeResources requires the omitted framework, so the original complete resource seal cannot remain valid after omission; the Intel archive has neither a signed main executable nor root CodeResources. Keeping all remaining Mach-O page-signature bytes unchanged does not establish native object validation, AMFI, Gatekeeper, notarization or direct-execution acceptance. The maintained caller performs project byte/path/loader admission followed by direct exec, not Security.framework validation. [Exact artifact and caller facts](MACOS-SIGNATURE-ARTIFACT-FACTS.md) keep these distinctions explicit. Those native checks, constructors and actual headless SDK/HID behavior remain target qualification obligations.

Private configuration isolation is established before program construction: Linux/Darwin XDG_CONFIG_HOME and Windows APPDATA point inside the owned role directory. CLI --config alone is insufficient. Ambient desktop preferences remain untouched. Remote clients, dynamic HID registration, automatic profiles and external plugin paths are disabled. Native platform environments are explicit and profile-bound; inherited environment is never silently accepted.

## Selected-device and transport boundary

Device records retain the stable physical selector, controller/detector capability and account, independently of transient node paths. Linux keeps its exact udev recipe and access witness. Darwin and Windows use tagged HID selectors and native access/generation evidence; they do not serialize invented udev/group grants. Before enabling a detector, enumerate only its qualified HID class and require complete enrollment of all matching current routes so that an enabled global detector cannot probe an unselected peer. No blind bus discovery, generic vendor-only selector, wildcard administrator access or broad driver installation is admitted.

Native safe HID support is qualified separately from motherboard/RAM/SMBus drivers. A transport requiring broad privileged access without a narrow supported owner is explicitly unsupported for that transport. This does not render all native lighting unsupported. Actual hardware classes require pinned-source applicability plus target account/access/SDK/output evidence. SDK acceptance is not visible light proof.

## Execution and private endpoint proof

Before the once-only claim, the owner verifies the frozen artifact closure, exact resolved invocation and final native account/security/containment plus selected-device generation/access. After launch it re-observes actual executable, argv, environment, working directory, configuration scope, native identity and sole literal loopback listener. Native APIs must attribute the socket to the exact serving process and reject wildcard/foreign/ambiguous listeners. Linux procfs is one adapter, not a portable contract. The local resource-to-scenario channel must authenticate native peer ownership on each OS; Vrooli authentication/transport remains the only remote surface.

Boot reconciliation must recover its own local credentials and desired policy independently of a desktop session. Disable quiesces public bindings, reconciler and all retained native roles before acknowledging retirement. Update/rollback/reconnect use the existing exclusive lifecycle and generation semantics, not a second supervisor.

## Qualification gates

Hermetic gates cover legacy decoding, strict tagged identity, PID reuse, changed manager/account/job, uncertain submit, descendant escape, claim-before-resume, crash recovery, retirement absence, frozen image/closure mismatch, ambient config preservation, no implicit enablement, detector scope, native listener attribution, update/rollback and durable Off reconciliation. Cross-compilation is required but does not certify native SDK linkage or hardware.

The resource manifest uses the existing `partial` platform-support value for macOS and Windows: maintained source and bounded build/fixture evidence exist, while native execution, access and physical behavior remain unqualified as listed below. The declaration stays readable by the qualified Linux root owner; it does not mark a target ready or bypass native prerequisites.

Every target matrix row records profile-byte proof, source/fixture/crossbuild proof, native compile/link proof, real narrow-account access, actual SDK/static/Off output, update/rollback, logout/boot/resume and device return separately. Pending native observations stay unqualified; no Linux proof is promoted to a Mac/Windows physical claim.

## Existing supervisor and operator context

Native boot composition runs the maintained ordinary RuntimeSupervisor as the actual operator. Explicit privileged setup publishes only the immutable maintained CLI, exact boot definition and any independently required reviewed selected-device setup. Governed software acquisition runs normally as the operator before publication; elevated setup never executes a user-writable dependency CLI. Native setup metadata identifies canonical operator HOME and the installed image. Ordinary private state, capacity admission, signing and scenario lifecycle reuse their existing owners. Root resource IPC, private root capacity and a second worker handoff have been removed from the adopted source path.

Normal resource commands and reconciliation enter the same durable lighting transaction. The intent operation lock precedes resource lifecycle ownership, so disable fences selection before quiescence and native retirement. Initial and update admission use the existing single-use claim protocol and canonical private operator-owned IPC. Every claim frame authenticates the exact admitted native peer and incarnation.

The trusted, governed OpenRGB release runs as the same ordinary operator as Linux. Independent containment against an arbitrarily compromised same-user vendor is outside the accepted requirement; no restricting capability SID, owner-state sandbox or privileged device-ACL rewrite is required merely to reproduce that hypothetical boundary. The concrete safeguards remain exact immutable code/dependencies, constructor configuration isolation, standard non-elevated identity, native process/Job lifetime, once-only claim, literal loopback listener, complete enrolled detector scope and current device generation. Windows observes selected HID access under the same standard token used by its suspended child and claims the exact child before resume. Darwin no-fork policy is retained only where factual process ownership needs it and the actual controlled release can satisfy it.

The native vendor and launcher remain in a machine-owned immutable code store through loader use. The approved Windows safe HID and Mac headless profiles use the source-verified derivations above. No unreadable-file receipt, incomplete original bundle or driver-absence race substitutes for exact serving-tree verification. Darwin also excludes the pinned macUSPCIO transport before HID evidence. Selected-device permissions, constructor/loader behavior, native boot and visible light output still require target observation.

## Current source migration status

The actual-operator architecture is implemented in the maintained isolated source. Resource root-broker delegation and its private capacity extension are removed; unique one-shot admission, boot/reconnect/disable and image-retention protections remain under ordinary owners. Platform version2 identities, native Task ownership and retained-role recovery have source implementations and fixtures. Public durable update/rollback/recovery fixtures exercise native policy/ref records with modeled OS edges, alongside separate real fence/capsule executor fixtures.

The artifact component has retained official-byte proof, complete Mac loader/derivation and managed/adopted recovery regressions, four target source test-compiles, and consecutive fresh independent M/N reviews with no material source findings. Earlier K/L reviews precede the complete-loader repair. These component results do not close producer/full-source checks, fresh combined integration reviews or target qualification. Historical source/proof is archived under the isolated workspace's `.vrooli/work/native-portability-history`, outside product source. Main Linux qualification and operator-reserved physical recovery remain separate. No native runtime, signature acceptance, ACL, SDK, HID access or physical output qualification is claimed by these source results.

## Isolated source verification environment

An isolated checkout must scope both project source lookup and the separate governed Proto runtime artifact store before generation or source-aware tests. `VROOLI_ROOT` and `VROOLI_SOURCE_ROOT` alone do not redirect Proto publication; its default is the operator's shared runtime store. Use an absolute private path inside the isolated workspace and retain the generation/snapshot provenance:

```sh
export VROOLI_ROOT=/absolute/isolated/Vrooli
export VROOLI_SOURCE_ROOT="$VROOLI_ROOT"
export VROOLI_PROTO_ARTIFACT_ROOT="$VROOLI_ROOT/.vrooli/work/proto-artifacts"
```

Run the canonical `packages/proto` Makefile generator/verifier with that environment. Never transfer `gen/.vrooli-proto-artifact.json`: it is runtime selection state, explicitly excluded by the canonical generated-output comparison, rather than schema output. A source merge transfers schemas/generated code/descriptor and lets the destination's governed owner publish/select its own coherent artifact. Keep observed artifact-selection effects separate from source-only test claims.
