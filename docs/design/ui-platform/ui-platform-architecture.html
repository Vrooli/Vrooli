Architecture review · pre-plan

The UI platform, as built and as it should be

Two SSOTs are authored and sound. Two coverage engines compute correct answers and nothing consumes them. The question this page settles is where each new piece belongs, so the plan adds capability without adding surface area.

01 — The ruleWhere validation belongs

Python is the wrong answer, and so is a new scenario. The repo already has a settled pattern for this, used by 26 scenarios, and both new artifacts fit it without inventing anything.

Validation in Vrooli attaches to a test-genie phase provider. A scenario declares .vrooli/test-genie.json — a phase name, an applicability predicate, a policy.resultGating, and a maturity ladder — and test-genie orchestrates it. A dedicated provider-conformance phase validates the providers themselves.

Within that, there are two document classes, and they are validated by different owners:

The mechanical answer

Catalog validation goes in react-component-library, which already provides the component-tests phase. Capability-registry validation goes in experience-manager, which already provides experience. Both use santhosh-tekuri/jsonschema/v5 — already a repo dependency — following the shape at cli-health/api/internal/services/manifestvalidation/schemaval.go: compile lazily, cache, return (findings, nil) for violations and (nil, err) only when the validator itself could not run.

Net new scenarios: zero. Net new phases: zero or one. Schema conformance is cheap enough to fold into the existing phases. Only the cross-registry checks — asset→capability references, dependency-rank direction, cycles — are worth considering as their own catalog phase, and only because they are the gate the 407-asset build-out runs against.

03 — The four fixesWhat to close before planning, and the options for each

Fix 1 · Schema enforcement for both SSOTs

no runner

407 assets and 12 registry files carry $schema hints that nothing reads. The only validator is a Python script in a prior session's /tmp, which will not survive the week. Beyond JSON Schema, the real value is the cross-registry checks: asset→capability references resolving with the correct facet, dependency-rank direction, and cycle detection.

  1. Go validators inside each owning scenario, surfaced through its existing phase. Schema conformance in component-tests and experience; cross-registry checks alongside. Mirrors cli-health's schemaval.go exactly.
  2. A new catalog phase provider in RCL. Cleaner separation and its own maturity ladder, at the cost of one more phase in the pipeline.
  3. A fleet *-health scenario owns both. Wrong: neither artifact is a fleet contract, and it splits ownership from authorship.

Recommend A now, B later. Start inside the existing phases; promote to a dedicated phase only when the catalog build-out begins and needs its own gating ladder.

Fix 2 · Give the two engines a consumer

islands

Both engines are pure functions over on-disk state with passing tests and no callers. Everything downstream — progress tracking, agent work selection, your ability to see whether any of this is working — depends on the numbers being reachable.

  1. CLI verbs first (rcl catalog coverage, rcl catalog next, experience-manager capabilities status), then a Connect handler, then a UI tab. The CLI is what an agent loop calls.
  2. Handler first, CLI as a thin wrapper. Matches the house rule that CLIs wrap the API, but delays the agent-facing surface.
  3. Emit as phase findings only. Insufficient — findings report defects, and most of this is progress against a target, not a defect.

Recommend B's ordering with A's priority: handler and CLI in the same change, since the house rule is that the CLI is a thin wrapper over the API. The UI tab can follow.

Blocked by Q4. Do not surface these numbers before the maturity model lands. A presence-based figure would publish "16 of 407 built" and have to be retracted the moment achieved maturity is derived.

Fix 3 · The fixture-adversarial gate

no runner

Of 17 declared gates, 6 have runners. The one flagged in the decision log as build this early has none. It is the only gate that is deterministic against fixture JSON with no browser involved, which makes it both the cheapest to build and the precondition for the fixture and page-template asset kinds — page templates receive data through typed ports, and nothing currently checks that a template has a fixture able to satisfy its data-source port.

  1. Build it now as a pure Go check in RCL over catalog/assets/fixtures/*, gating on adversarial-case presence and port satisfaction. No browser, no BAS, runs in milliseconds.
  2. Defer until page templates are authored. Risks authoring 21 templates against no contract.

Recommend A. It is a day of work that de-risks the largest asset domain.

Fix 4 · targets in the coverage join

seam exists

This is your message-16 requirement — scenarios free to use any language or framework — and it is half-honoured. The schema doctrine states it, all 407 assets carry targets: ["react-vite"], gate runners are per-target maps, and catalogcoverage.Asset has a Targets field. But Compute ignores it: Row has no target dimension, so the join is 1-D, not the declared (asset × target) matrix.

  1. Add the target dimension now, while there is one target and the change is mechanical.
  2. Add it when a second target appears. Every consumer written in between will assume one target and need rewriting.

Recommend A. Cheap now, structural later. The placement half of the same requirement is question 5 below.

04 — Open questionsDecisions only you can make

Q1 · Where do the ramp values live?

blocks 302 assets

The proposed ramps — 8 spacing, 8 text styles, 4 elevation, 4 radius, 7 layers, 2 borders, 3 opacities — have no approved values, and foundations.tokens is the single largest blocker in the catalog. The investigation answers where even if not what: today templates/design/<kit>/adapters/react-vite-tailwind/tokens.css carries 32 colour variables, 4 radius, 2 font, 1 spacing and 1 touch-target. The ramps are almost entirely absent, and the decision log already says the kits are the beauty profiles.

  1. Ramps live in the design kit, per target adapter. Primitive ramps shared across kits, semantic values per kit. brand-manager validates them via the existing branding phase; RCL consumes them; the catalog references them but never defines them.
  2. Ramps in catalog/config.json. Wrong layer — it puts taste in the inventory and breaks the second target.
  3. Ramps in brand-manager as authored data. Plausible, but kits are template-owned artifacts and brand-manager currently validates against them rather than owning them.

Recommend A — it needs no new home. Still needs you: the actual numbers.

Q2 · Are the reconciler changes fleet-wide semantics?

uncommitted

The uncommitted reconcile.go edits drop <header> from the chrome vocabulary and suppress overflow reporting for preview-canvas descendants. They are written as generic rules but were motivated by RCL's preview workspace. floor_chrome_pinned and floor_no_document_horizontal_overflow are gating errors for every scenario with an experience spec.

  1. Treat as fleet-wide, re-run the experience phase across all spec-carrying scenarios, and accept the diff as the new baseline.
  2. Scope the suppression to RCL via a spec-declared exemption, keeping fleet semantics unchanged.
  3. Revert and solve it in RCL's markup instead.

Recommend A if the re-run is clean, B if it is not. Either way the re-run has to happen before these are trusted — they are currently unverified beyond RCL.

Q3 · Port precedence for double-satisfied ports

undefined

icon-registry and telemetry-adapter each have two satisfiers. With no precedence rule, closure resolution is non-deterministic — which breaks the guarantee that an agent loop always has exactly one correct next target.

  1. Template provides wins over an adopted asset; among adopted assets, the lower dependency rank wins; ties are an authoring error the validator rejects.
  2. Explicit precedence field on the port in the capability registry.

Recommend A. It is a rule rather than data, so it cannot drift, and it makes the tie a validation failure instead of a silent pick.

Q4 · Pre-catalog components, and the bug they expose

model defect

All 30 existing components predate the catalog. The catalog was authored from what a world-class library would need; the library is what happened to get built before that question was asked. Even where the two share a name, the implementation does not meet the standard — which is the problem that started this work.

That fact exposes a defect in the coverage engine I validated too generously. catalogcoverage.Asset carries a Maturity field that LoadCatalog populates and Compute never reads. Bucketing is presence-only: any implementation with a matching catalogId becomes planned-built. So the 16 already-linked components report as built today, and linking the other 14 would make coverage read 30 of 407 built when roughly zero meet the declared bar.

The maturity trap, wearing a new costume

This is the same failure this page warns about in section 6 — a thing that proves nothing reporting complete. It is already shipped in the engine. catalogId must mean identity — "this implementation claims this slot" — and never quality.

The catalog already declares target maturity per asset: 182 production-ready, 179 verified, 46 implemented. Coverage has to compute achieved maturity from gate evidence and compare it against that target. Headline coverage becomes assets at or above target, not assets with an implementation. With 6 of 17 gates wired, nothing can honestly climb past the lower rungs today — which is the correct answer, not a problem to hide.

  1. Link all 30 now and let derived maturity carry the truth. Bucketing decomposes into rungs; every pre-catalog component sits at the lowest non-missing rung until gates say otherwise. NextWork ranks by the target-minus-achieved gap weighted by blocking leverage, so a built-but-childish asset is correctly still work.
  2. Leave them unlinked until rebuilt. Reads as honest but is worse: it hides that code exists, is adopted by scenarios, and occupies the slot.
  3. Delete and rebuild from scratch. Discards adoption history and drift records for no gain — see the version note below.

Recommend A. The upgrade path needs no new machinery: component.json already carries latest, draft and deprecatedVersions over semver version directories. Button is already at 2.0.0 across 5 versions. A rebuild to catalog standard is 3.0.0 authored as draft, promoted to latest when gates pass; adopters move to behind through the drift machinery that already exists.

Q5 · The dropped thread — placement abstraction

unanswered

Your pushback in the prior conversation — that you want genuine multi-language, multi-framework freedom rather than a conformance test — was never answered; the reply repeated an earlier message verbatim. The catalog layer honoured it anyway. The placement layer did not.

Two concrete defects sit here. pathresolver.go branches 3 and 4 hardcode ui/src/components, ui/src/hooks and friends, so a differently-structured template gets silently mis-placed files rather than an error. And the overlay is split-brain: ui-health's validator reads .vrooli/ui-manifest.json via loadOverlayManifest and merges it, while RCL's uimanifest.FSLoader — the loader that drives adoption placement and inventory scan — has no overlay branch at all. The docs promise the resolver will read it, and the resolver is precisely what does not.

  1. ui-manifest v2 with role-named slots, provides, idiom, gates and targets; a manifest miss becomes an error for templates declaring full slot coverage; the heuristic survives only for unmigrated scenarios; the overlay branch is ported from ui-health.
  2. Fix the overlay and the hardcoded paths only, defer v2. Smaller, but leaves the slot vocabulary unable to express services, providers, adapters, patterns, page templates or fixtures.

Recommend A, as its own plan phase. This is the difference between a React component library and a UI platform, and it should not be a footnote.

05 — The hingeAdoption closure is the one decision everything else rests on

The catalog declares 845 requires, 60 suggests, 220 expects and 25 satisfies, each with a reason. In Go, AssetDependency is still {LibraryID, Version} — no edge kind — and resolveAdoptionClosure copies the whole transitive set. The most load-bearing decision in the design is fully authored and entirely unimplemented.

Why this is the hinge

A 407-asset catalog is only viable if layering is deep. Deep layering is only affordable if closure is selective. Selective closure requires edge kinds. Until AssetDependency carries a kind and resolveAdoptionClosure honours it, every asset authored beyond the primitive layer is authoring a liability.

The four numbers that make it an instrument

Once wired, four independent measures drive all downstream work, and none of them is a single percentage:

  • Catalog coverage — planned vs. present per (asset × target), with supplemental counted separately rather than hidden. Presence only; makes no quality claim.
  • Maturity coverage — assets at or above their declared target rung. This is the headline number, and the one that answers "is the library good yet." It should read near zero on day one and that will be correct.
  • Capability coverage — declared vs. provable. Today computed-style alone blocks 18 capabilities; that fact is currently one warning line in a log that reports status=passed.
  • Next work — deterministic, ranked by target-minus-achieved weighted by blocking leverage. Currently foundations.tokens, blocking 302 of 407.
What actually measures "childish"

Maturity is only as honest as the gates behind it, and 11 of 17 have no runner. The two that would catch aesthetic failure specifically are visual (wired — preview-e2e.mjs, light and dark, rejects blank and identical captures) and the static ramp check that does not exist yet: once ramps are component tokens in the kit, "every control height is one of the declared values" becomes a lint rather than a matter of taste. That check is the closest thing to a machine-readable definition of polish, and it is downstream of Q1.

The maturity trap, already known

Every capability must default to required. A ladder over a capability that emits nothing reports complete — the existing providers handle this with clean_requirement: required, which lowers the rung without failing the phase. If the new capabilities default to optional, day one reads green across 407 assets and the instrument is worthless.

07 — SequenceHow this becomes a plan

The goal of this pass is agreement on the architecture, not implementation. What follows is the shape the plan should take once the five questions are settled.

  1. Hardening — fixes 1–4, plus the maturity model from Q4, which lands before the engines are surfaced. Schema + cross-registry validation in the owning scenarios; achieved-vs-target maturity in the join; target dimension in the join; fixture-adversarial gate; then API and CLI. After this the numbers are trustworthy and quotable.
  2. The hinge — edge kinds on AssetDependency, selective closure, three-set adopt reporting, port precedence. Nothing above the primitive layer should be authored before this lands.
  3. Placement — ui-manifest v2, overlay ported into the resolver, hardcoded react-vite paths replaced with manifest-or-error. This is the answer to the dropped thread and deserves its own phase.
  4. Validator reach — computed-style evidence, capture axes past viewport, the four-way state vocabulary reconciled against states.json. Each one converts a block of capabilities from declared to provable.
  5. Then, and only then — agents work the catalog, using coverage as the progress signal and next-work as the target selector.
Two things that will rot if left

states.json is consumed by zero Go code — the four-way state vocabulary split is untouched, so the registry currently documents a canon nothing enforces. And StateCoverageCheck parses a ## UX-State Contract section that exists in 0 of 50 DESIGN.md files, so it has never emitted a finding fleet-wide. Both are pre-existing, both are in scope for step 4, and both are the kind of thing that makes a system feel messier than it is.
