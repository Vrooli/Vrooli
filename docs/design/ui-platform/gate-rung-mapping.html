Gate → rung mapping · needs approval

The definition of done for 407 assets — and the holes it exposes

Mapping seventeen gates onto four rungs took an hour. What it revealed is that the catalog is not uniformly measurable: 104 assets have almost no quality bar, including the one that blocks 302 others.

01 — The ladderFour rungs, plus a zero state

The schema already defines the target vocabulary. What was missing is which gates prove which rung. Each rung adds gates and inherits everything below it, so the ladder is monotonic: an asset is at rung N when every applicable blocking gate at N and below passes.

All 17 gates are placed, none twice. Two rules complete the model:

  • missing is the zero state. No implementation at the catalog id. It is not in the schema enum because nothing ever targets missing — but coverage needs it, so achieved maturity has five values where target has four.
  • deprecated is not a rung. It is an orthogonal status already carried by component.json's deprecatedVersions. Mixing it into the ladder would make the scale non-monotonic.
One placement decided against the obvious

fixture-adversarial reads like a production-readiness gate, but all 9 fixtures target verified and it is their only applicable gate. Placed at rung 4 it would sit above every fixture's target and no fixture could ever reach it. It belongs at verified: a fixture whose adversarial cases hold genuinely is verified data.

What this says

The 303 assets in the component family — component, pattern, page-template, navigation, primitive — are well gated at 10–13 blocking checks each. The other 104 assets have between 1 and 3, and four kinds have rungs that pass with zero applicable gates.

Worst case: foundation has exactly one blocking gate — types. That means foundations.tokens, the asset blocking 302 others and the home of every ramp you just approved, reaches production-ready by compiling. There is no check that a ramp is well-formed, on-grid, or complete.

03 — The ruleA rung with no gates must not pass

Without a rule, 86 assets — every hook, service, adapter and generator — leap from implemented to verified for free, because none of the rung-3 gates apply to them. That is the maturity trap arriving through the side door.

Proposed rule: for any asset, every rung at or below its declared target must have at least one applicable blocking gate. A rung with none is an authoring error surfaced by the catalog validator — not a silent pass and not a silent skip.

This revises my earlier advice

I recommended building fixture-adversarial first because it is cheap and deterministic. The matrix says otherwise: api is the single gate standing between 303 of 407 assets and the implemented rung. It is equally cheap — a static check that declared variants, modes and parts match actual exports, no browser involved — and it unblocks seven times as much of the catalog.

Revised gate build order: api → tokens → lifecycle → fixture-adversarial, then the rest. The first two also happen to be the two that make your approved ramps enforceable.
