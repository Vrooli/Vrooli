How long can you talk before it breaks?

Three independent ceilings sit between you and a fifteen-minute dictation, and none of them is in the part of the stack that looks fragile. The transcription engine is fine. The recovery journal is the bug — it was designed to be compacted by an acknowledgement the server never sends, so it grows for the whole session until it hits a wall, silently.

Orientation

What the stack actually is

You asked where a problem could live. There are five layers, and the ownership boundaries are mostly good — the confusion is that two of them contain copies of each other.

Root cause

One missing edge explains both ceilings

The design is a standard durable-stream protocol: the client keeps captured audio until the server confirms it has processed it, then discards it. That confirmation is called a processed acknowledgement, and both sides implement their half of it correctly.

At the audit baseline it was never sent during the session: the event type existed, but the live Kyutai adapter only used its processed_batches signal for transport credits. The current implementation closes that edge. Kyutai maps each backend-confirmed processed batch to its exact chunk identity and emits StreamEventAcknowledgement; the browser ledger compacts only from that event. Providers without a backend cursor retain the generic strategy cursor, while the Passthrough strategy does not double-ack Kyutai.

Why it survives review. The client compacts only on acknowledgement. The Kyutai adapter now waits for backend processing confirmation, the resource orders the final processed cursor before terminal done, the writer remains back-pressure-proof, and the resume path is idempotent. Accelerated interval accounting and all eleven deterministic fault controls are now green; the remaining promotion gap is full paced quality for the batch strategies, current routed Swarm Manager product-path credit, native target publication, and target smoke evidence. Automated PipeWire device qualification is already evidenced for Audio Tools; it proves the operating-system capture path, not a specific analog microphone. A bounded-overlap repair and provider-failure retention tests are now in the active validation run; they do not count as qualification until that run finishes.

The trap in the obvious fix

The natural implementation is to acknowledge when a segment commits. That would not work, and it would fail in a way that looks like success in short tests.

A prior investigation on 2026-07-07 measured the live Kyutai path and found that a durable segment committed only after a run of ~1.3 s of silence (SILENCE_COMMIT_FRAMES=16) or on an explicit flush. The resource now also force-commits at a word boundary after KYUTAI_STT_MAX_SEGMENT_FRAMES=48, but that text policy is not the retention proof: processed-audio coverage is still emitted independently of segment commit. The remaining question is whether the full browser and real-time evidence exercises that contract without gaps.

The acknowledgement must therefore be driven by processed-audio coverage — “the provider has consumed samples up to sequence N” — which is knowable continuously and independent of whether any text has settled. Coverage is what the retention invariant is actually about; segment commit is a text event that happens to correlate with it when people pause.

The two-speed transcript

Yes — there are two streams, and they run at different speeds

Your recollection is accurate, and it is worth being precise about because it changes the fix. The pipeline emits two distinct message classes with genuinely different latency and confidence characteristics:

  • partial — the engine’s current rolling hypothesis. Fast, arrives continuously, and may revise words it already emitted as more audio arrives. This is what fed the tooltip.
  • segment-final — a committed segment, produced when the active strategy decides a span is settled. Slower, arrives in chunks, never revised. This is what streams into the composer.

So the composer was receiving a live stream — just the settled one, which is why it felt correct but lagged. What is missing is that the fast stream has no representation in the box.

Which streams you get depends entirely on the strategy

StrategyWhen auto selects itfast partialssettled segments
Passthrough Provider streams natively — Kyutai, Deepgram. First choice. yes yes
VADSegment Batch-only provider — local Whisper. Today’s effective default. none at each silence
OverlapAgree Never on auto — explicit overlap preference only yes yes
BufferedFallback Streaming off, or nothing else fits none one, at the end

With Kyutai up you get the two-speed behaviour you remember. When Kyutai is unavailable, auto-selection lands on VADSegment, the tooltip stays blank, and text arrives only at silence boundaries. Nothing “breaks”; the fast lane simply does not exist on the fallback path. The managed Kyutai resource is currently healthy, so the primary path is available for qualification.

What I propose to build instead

Your iPhone comparison is the right model, and it is worth doing properly rather than just moving the tooltip’s text into the box. Three pieces:

Rendering. A plain <textarea> cannot style a sub-range, and contenteditable would cost us IME, mobile keyboards, and native selection. The robust approach is the standard overlay: a transparent textarea over a mirror layer that draws committed text normally and interim text with the dotted underline. Native input behaviour is untouched.

Rules that keep it from fighting you. Interim text never enters undo history — only commits do. If your caret enters the interim region, that text commits as-is rather than being contested, which is what iOS does. On turn end, any remaining interim is promoted through the uncommittedRemainder path that already exists.

And the fast lane needs to exist on the default path. Underlining unsettled text is worth nothing if the default strategy emits none. That is a measurement question, not a taste question — either bring OverlapAgree back to auto once the harness shows its latency is acceptable (which is precisely why it was parked), or synthesise partials from VADSegment’s in-flight buffer. One more reason the harness comes first.

Findings

Nineteen defects, by layer

Severity is about your stated goal — uninterrupted long-form dictation that never drops anything — not about general code health.

Reliability · shared capture package
F1

Capture stops feeding the socket at 8m44s, silently

Because no acknowledgement arrives (above), TurnJournal.append hits its 16 MiB quota and throws. The throw lands inside the this.writes promise chain, which has no .catch — so the chain is permanently rejected and every subsequent frame’s callback is skipped. No audio is sent, no done is sent, and no error surfaces to the UI. 16 MiB ÷ 32,000 B/s = 524 s.

turnJournal.ts:76,86 · pcmVoiceStreamProvider.ts:205,262,393,413

F2

Both journals rewrite the entire retained buffer on every frame

Client: append() calls persist(), which deep-copies every retained chunk and writes the whole snapshot to IndexedDB — once per capture quantum. Server: stream_ws.go calls PersistContext per chunk; that marshals all retained audio to JSON (base64, ×1.33), creates a temp file and renames it, under a process-global mutex. Cost per frame is proportional to session length, so total work is quadratic. Because both writes are awaited, the deficit does not appear as I/O — it appears as unbounded lag between speaking and transmitting.

turnJournal.ts:83,99–104,112–114 · stream_ws.go:349 · session/registry.go:121,126–166 · session/ledger.go:226–232

F3

Server retains the whole session in RAM; terminates at ~35 minutes

Ledger.Receive keeps every chunk until acknowledged. With the default 64 MiB cap that is 2,097 seconds of speech, after which the session ends resource_exhausted. Concurrent sessions multiply the footprint.

session/ledger.go:130–140 · session/registry.go:47

F5

The 10-second stop-fallback double-appends the entire transcript

stop() arms a fixed 10 s timer; if the trailing segment has not arrived, fallback() re-transcribes all retained PCM over HTTP and calls onResult. But onResult appends, and every committed segment has already been appended by onSegmentFinal. On a long turn — where the tail legitimately takes more than 10 s, and under F2 certainly will — the whole dictation is written into the box twice.

pcmVoiceStreamProvider.ts:362–363,423 · useVoiceCore.ts:1140

F4

No frame batching: 375 WebSocket messages per second, 41% header

Each AudioWorklet render quantum (128 samples ≈ 2.7 ms at 48 kHz) becomes one SHA-256, one journal append, one server ledger receive-and-persist, and one WebSocket frame carrying ~86 bytes of audio behind a 60-byte header. Batching to ~100 ms cuts message rate 37× and header overhead to under 2%.

pcmCapture.ts:59–66 · pcmVoiceStreamProvider.ts:190–215 · stream_ws.go:45

The auto-stop boundary
F18

Live text and ring updates share one slot and delete each other

wsCoalescingWriter.enqueue keeps exactly one progress slot — it assigns w.partial = &mm for every message whose class is DeliveryProgress. And wsMessageDeliveryClass puts partial, vad-state and status in that class. All three overwrite one another. The server emits VAD ticks at ~20 Hz during silence; partials arrive at engine cadence. Under any writer backlog — which the quadratic persistence guarantees — a VAD tick discards your pending live text, and a partial discards your pending ring update.

The downstream effect is exactly the reported symptom. useServerVadStateStore states the contract plainly: the ring interpolates server ticks so it completes at the moment the server cuts, and falls back to the client VAD when no tick has arrived within SERVER_VAD_STALE_MS (250 ms). Dropped ticks push it past that threshold, so the ring switches clock mid-fill. decideAutoStop switches source at the same threshold — so the ring and the actual stop decision can disagree about the same moment.

There is precedent, and it is only half-locked. A 2026-05-17 regression had server VAD at 700 ms while the ring showed 1200 ms, filling to ~58% before the cut. DefaultVADSilenceMs and two parity tests now lock the value. Nothing locks delivery.

stream_ws.go:117–130,143–148 · voice/useServerVadStateStore.ts · voice/activity.ts:67–70 · voice/autoStopDecision.ts:157

The plan

Build the instrument, then fix what it measures

You have asked about this several times and the fixes have not stuck. The reason is visible in F11 and F13: there has never been a test that could tell a fix from a regression, so every round has been guesswork. So the first two phases are not fixes — they are the harness, run against the current code, expected to fail.

The finalized plan is audio-dictation-reliability-v2-2. Its fourteen phases are listed here in execution order.

1–2

The soak harness — two lanes, both permanent

Accelerated lane (Phase 1, under 60 seconds, runs in every gate): a virtual clock and a synthetic capture source drive the real provider and a real Go StreamWSHandler for a simulated 60 minutes. It asserts what matters — retained bytes bounded, every captured interval present exactly once, no duplicate segments, no silent terminal, flat memory, constant per-frame cost.

Real-time lane (Phase 2, 15 and 60 minutes wall-clock): the same assertions against the genuine browser path via swarm-manager, plus the ones only real time can make — first-partial latency flat across the run, committed-text lag never growing, word error rate steady end to start.

Both emit browser_product_path evidence into the trust-floor ledger, so the rubric that already knows what "stable" means finally receives input. Deliverable: a baseline showing exactly where today's code fails.

Sequencing

Phases 1–2 first, alone, with the failing baseline published. Then Phase 3 as one change — acknowledgement, batching, and persistence are a single durability contract and it is cheaper to verify them as a set. Re-run the soak: that is the moment we find out whether the diagnosis is complete. Phases 4–12 are largely independent and can be reordered. Phase 13 is the closing gate and must be last. Phase 14 blocks nothing.

What this plan inherits

Substantial prior work is already banked and this plan builds on it rather than repeating it. voice-dictation-and-the-control-system… (13 of 14 phases done) delivered the shared package’s test lifecycle, the ControlBase primitive, the token contract, and the adoption machinery. audio-tools-reliability-fix-live-capture-path… collapsed 26 of 46 integration files to re-export shims. Those are why the substrate is in good enough shape to fix rather than rewrite.

What none of them addressed — and what this plan exists for — is duration. Every prior plan measured structure, ownership, and whether the capture path was alive at all. None asked how long it stays alive under continuous load, which is why the acknowledgement gap, the quadratic persistence, and both ceilings survived every one of them. This plan absorbs the two still-open phases that overlap it (shared-package promotion and RCL reconciliation, here Phases 11 and 12) and supersedes nothing else.

Two session shapes, always

Duration is not the only axis, and a lane that only pushes continuous speech would miss how dictation actually happens. In one-shot mode you speak, pause below the timeout, and resume; the ring shows the time remaining. A realistic hour is therefore many speech runs separated by sub-timeout pauses — so a continuous-only lane never exercises the auto-stop boundary at all.

Every duration profile runs in both shapes, and neither substitutes for the other. The realistic shape is the only one that exercises the boundary, the ring, and the repeated VAD transitions. The continuous shape is the only one that breaks commit-driven acknowledgement — the trap named above. Running one without the other hides a different half of this work.

Boundary profiles sit at the edge: resume 200 ms before the timeout, resume 50 ms before it, stop 50 ms after it. Then repeat the boundary 50 times in one session and assert ring accuracy at the 50th matches the 1st.

Not every strategy earns the same ladder

Testing all four to 60 minutes would be wrong — and testing only the “streaming” ones would miss the default. The dividing line is not streaming versus batch; it is what each strategy is architecturally capable of, and for the one that cannot go the distance the test asserts its failure mode rather than its capability.

That last row is the one that matters most for trust. A strategy that cannot do sixty minutes is acceptable; a strategy that cannot do sixty minutes and does not say so is the bug you have been living with.

Working agreement

The loop — with four amendments

Your proposed method is right, and it is the thing that has been missing: build the instrument, record the baseline, drain the list one item at a time, re-run, fix regressions before moving on, re-audit, repeat. Four adjustments, because agreeing with all of it uncritically is how the last few rounds went.

1

Tier the test cadence, or the loop is too slow to actually run

A 60-minute real-time lane cannot run after every change — you would get one iteration per hour. So: the accelerated lane runs after every single change (seconds, simulates 60 minutes); the 15-minute real-time lane runs at each phase boundary; the 60-minute lane runs nightly and before any claim that something is solved. The accelerated lane is the loop; the real-time lanes are the proof.

2

P1–P3 is one item, not three

“One thing at a time” is right almost everywhere, and wrong here. The acknowledgement, the batching, and the incremental persistence are one change to the durability contract. Shipping the acknowledgement alone changes the retention window’s shape before the write path is ready for it, and you would spend a day chasing a regression that is really an intermediate state. One change, one verification.

3

Fix and tidy as two steps, not one

You want the code left more professional than I found it — agreed, and it is overdue. But a commit that both fixes behaviour and restructures the file makes a regression unattributable. So each item is: fix until the test goes green, then clean up while it stays green. You get both, and we never lose the ability to say which change caused what.

4

The loop needs a stopping condition, not just a repeat

“Keep re-auditing and draining until it works” can quietly hide a wrong model — you drain list after list and each one looks like progress. So each round gets recorded, and we watch the shape of the new list: if a round produces mostly deeper instances of known categories, the model is right and we keep draining. If it produces mostly new categories, the model is wrong, and we stop and re-derive rather than grind. That distinction is the difference between converging and looking busy.

And one commitment on my side. The baseline gets captured before any fix, including the obvious ones, and every subsequent claim is stated against it. If a phase does not move a number, I will say that it did not move rather than describing the work I did.
