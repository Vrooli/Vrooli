The answer to "where does this logic go"

Four layers, each owning one question

Your instinct — that the bridge should be the hub for everything you control — is right about reach and wrong about operation. Bridge's value is being the single place that answers "what do I control, is it online, and am I allowed to send it this." If it also contained ADB, WebDriverAgent, and mirroring logic it would become a mobile toolkit, and every new device platform would bloat the trust plane. So device control becomes its own capability that bridge reaches, and the ramps consume.

Why device-control is its own scenario, not part of a ramp

You named the reason yourself: you will want to drive these phones for general automation, not just deployment validation. If the ADB and WebDriverAgent logic lives inside scenario-to-android, every non-deployment consumer has to depend on a deployment ramp to tap a button. As its own meta-scenario it becomes a capability others build on — which is the whole point of the scenario model. device-sync-hub is adjacent but genuinely different: it moves files between your devices; this drives them. Same fleet, opposite direction.

The one concept bridge is missing

A phone is not a node — it is a peripheral of one

Bridge today assumes fleet member = machine running the bridge agent. That already covers your VPS fleet, so Tier 4 needs nothing new. But a phone cannot run the agent — not reliably on Android, not at all on iOS. Rather than weakening what a node means, add a second member kind that is explicitly reachable only through a host node. That keeps every existing node invariant intact and makes the dependency honest: unplug the phone, or take its host offline, and it goes unreachable for a stated reason.

Device control

Three adapters — and the iPhone gets two of them

The phone-harness link you sent changes the iOS plan for the better. It uses iPhone Mirroring plus synthetic HID events and Vision OCR — no jailbreak, no Xcode, no WebDriverAgent, and crucially no developer account. That is a fundamentally different trade from the industrial WebDriverAgent path, and the right move is to support both rather than pick one, because they are strong in exactly the places the other is weak.

Adapters are selected by what the task needs to prove, not by preference.
Adapter Mechanism Sees Needs Good for Cannot do
android-adb ADB + UiAutomator2 Semantic view hierarchy USB or wireless debugging; no account Everything — conformance and general automation Little. Wireless pairing expires on reboot.
ios-xcuitest devicectl + WebDriverAgent Semantic accessibility tree Mac node, Xcode, code signing, dev account Release-grade conformance on our own apps Apps we did not sign

Why this unblocks you immediately

ios-xcuitest sits behind rungs 1 and 3 of the Apple ladder — it cannot work until you enroll. ios-mirror needs none of that. So physical-iPhone work can start now via the mirror adapter, and the XCUITest adapter becomes the release-grade path once enrollment happens. The readiness model expresses this natively: with no account, ios-xcuitest reports unavailable with "enroll in the Apple Developer Program" as its next action, while ios-mirror reports available.

A constraint worth stating plainly

Mirror-driven evidence should never gate a release. OCR reads pixels, not meaning — it cannot tell a correctly-rendered greeting from a convincing screenshot of one, and it has no stable element identity to assert against. Treat ios-mirror as an exploration and general-automation adapter whose journeys are recorded as unavailable for release purposes. Anything gating a release runs on a semantic adapter.

The payoff from choosing Capacitor

One flow, four surfaces

Because every ramp wraps the same web bundle, the scenario's actual UX is web content everywhere — so a BAS flow authored once replays on all four surfaces. Only the attach mechanism differs, and BAS already has the seam for that: EngineCapabilities advertises what an engine supports, the compiler derives a CapabilityRequirement from the workflow, and CheckCompatibility computes the gap before execution. The existing ENGINE_OVERRIDE=desktop path and the ElectronTarget renderer attach are the precedent — mobile is two more engines on a proven seam, not a new architecture.

Where BAS stops

BAS owns web content and nothing else. Permission dialogs, biometric prompts, share sheets, the app switcher, notifications, install and update — all native chrome, all outside the WebView. That is precisely the boundary between the two journey kinds below: device-control drives the shell, BAS drives the content, and a conformance journey is the two interleaved on one timeline.

Journeys

Two kinds, and they are orthogonal

Ramp-owned conformance journeys

"Does a generated app behave like a Vrooli app on this platform?" Same chapters for every scenario; different chapters per platform. This is the existing journey-evidence.v2 model — registered capability plans, chapters with purpose, bounded readiness, settle policy, expected vs observed, and capture refs. hello-desktop proves it for desktop with hello-desktop.baseline.v2; hello-mobile will do the same job here. The runner has no scenario-name branch, which is what keeps it generic.

Scenario-owned journeys

"Does this scenario work in the generated app?" Same flow for every platform; different flow per scenario. These are BAS cases, authored once by whoever owns the scenario, replayed on browser, desktop, Android, and iOS. A scenario author never writes a mobile-specific flow — if they have to, the shell abstraction has leaked.

The orthogonality is the design

Conformance journeys vary by platform and are constant across scenarios. Scenario journeys vary by scenario and are constant across platforms. Every cell in that matrix is covered by exactly one owner, and neither axis has to know about the other.

The readiness model

Two axes, one vocabulary

Getting an Apple account and passing Google's developer verification is not paperwork beside the engineering — it is the other half of whether a ramp can do its job. So it is modeled exactly like target capability: probed, evidence-backed, answered with the same words. The enrollment walkthrough you asked for is simply this lane, rendered.

pass

Proven, with evidence references — locally or on a reachable target that returned them.

unavailable

Missing right now. Must name the exact missing capability and the next action.

unsupported

Categorically impossible on any reachable target. Terminal, not a degraded pass.

failed

Attempted and did not hold. Distinct from never having been attempted.

The constraint that shapes the architecture

macOS 26 was the last Intel release and Xcode 27 dropped Intel entirely, so minimouse has roughly a year of release capability left — though it stays a useful validation node indefinitely. The design therefore never names it: "iOS build and signing host" is a bridge-node role, and satisfying it with an Apple Silicon machine later is a node registration, not a rewrite.

Xcode is not a resource

It is a host capability with a verify-and-instruct path. We cannot install, license, or version it, and pretending otherwise would put a permanently failing acquisition step in the resource fleet. android-sdk is the opposite case — fully scriptable, so it earns real resource treatment.

Still open

Decisions I would rather you make than assume

Device leases — who arbitrates when two things want the same phone?

One phone, one session, and the mirror adapter enforces that in hardware. Without an explicit lease, a deployment journey and a general-automation task will silently corrupt each other's runs. My lean is leases in bridge alongside the fleet record — same place that already owns scopes and audit — with device-control refusing any verb that lacks a held lease.

Wireless ADB or USB for the Android phones?

Wireless means a phone is not chained to a host and can sit on a shelf; but pairing expires on reboot and the link is flakier, which shows up as intermittent evidence failures — the worst kind. USB is boringly reliable and ties each phone to one host node. My lean is to support both transports from the start but default conformance runs to USB, because release evidence should not be able to fail for network reasons.

Does the spine get extracted before or after the new ramps are built?

You chose the full retrofit, which is right long-term. Extract-first gives both ramps a real spine immediately but destabilizes a monetization-critical ramp early. Build-then-retrofit keeps desktop untouched but leaves two implementations alive for a while. My lean is extract-first with desktop retrofitted last — the interface gets shaped by two new consumers before the incumbent is moved onto it.

How is a capability this powerful scoped and consented?

This is the one I would most like your thinking on. device-control can tap anything on your personal phone, read anything on screen, and install software. That is a serious capability to leave running, and the honest framing is that it deserves the same treatment as a credential: scoped grants per consumer, a visible indicator while a session is live, full audit of every verb, and a hard kill. Whether an agent should ever hold it unattended is a policy question, not a technical one.
