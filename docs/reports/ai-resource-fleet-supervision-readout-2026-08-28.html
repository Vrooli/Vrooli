A daemonized service and an orphan look identical, so the healer kills the fleet

Why it kept going

The false-unhealthy verdict from my last report is the fuel. Autoheal's own words about a resource that was resident on CUDA and answering queries the whole time:

resource-reranker  actionId=start  success=false
"start completed but verification failed"
"reranker resource is degraded but still serving"
   (failed after 13 attempts in 33.449s)

A bookkeeping sidecar owns the verdict for the service beside it. Autoheal believes the heal failed and retries. The orphan kill is the ignition; the false verdict is the fuel.

Four ways to fix it

OptionMechanismVerdict
Registry-authoritative classificationA process the runtime registry claims is never an orphan, whatever its ppid. Orphan means artifact process with no live claim.Selected
Extend ancestry to sessions and process groupsTrack the starter's SID/PGID and match descendants.Rejected daemonizing calls setsid, so the session is new by construction
Make the orphan check advisoryReport, never kill.Interim stops the bleeding in minutes; real orphans then accumulate
Heal interlockRefuse to kill a target another check started inside a cooldown window.Defence in depth would have contained this even with the bug present

The governing principle

A live owner, not a process ancestry, decides whether a process is claimed. The registry already knows which pid it started for which resource — that is how vrooli resource status answers running: true for the very pid the orphan check condemns. Any classifier reaching a different answer about the same pid in the same second is wrong by construction.

What I'd do next

Supervision before consolidation

Ranked by how much they change what you experience day to day. The first four are worth more than every remaining refactor combined, because they are the difference between a fleet that works and a fleet that works when you happen to check.

P0

Stop the orphan check from killing, today

Dropping the kill action is a minutes-long change that ends the oscillation immediately. It is a deliberate, temporary regression in orphan cleanup — accepted because the check currently cannot tell an orphan from a healthy service.

P0

Make orphan classification registry-authoritative

A process the runtime registry claims is never an orphan, whatever its ppid. This is the actual fix, and it makes the orphan check agree with resource status by construction. Verify claim liveness, not just existence, so a stale claim over a reused pid cannot protect the wrong process.

P0

Add a heal interlock

No check may destroy a target another check started inside a cooldown window, and every refusal is recorded with both check ids. This would have contained the incident even with the misclassification present — which is why it is worth having regardless.

P0

Supervise required: true from one declaration

Two resources declare themselves required. Both were down, and nothing noticed. Wire onboarding's core seed → dependency closure → autoheal targets, and delete the hardcoded 7-resource literal in the same change.

P0

Separate the probe outcome from the verdict

Report probe, serving, placement and companion as four independent fields, and have the fleet table render the verdict rather than the probe. This kills D2 and D3 together — a stopped service stops reading green, and a serving one stops reading red because a sidecar died.

P0

Make resource start exit non-zero when it fails

It currently prints a startup-timeout error and returns 0. Any automation trusting the exit code — autoheal, setup, CI — believes speech started.

P1

Add the third placement state

idle / no workload resident is not cpu. Only raise mode_drift when a workload is actually resident on the wrong backend. Without this, every lazily-loading server generates false drift the moment it goes quiet.

P1

Give the startup gate a per-resource readiness budget

Kokoro needs about ninety seconds to cold-start Torch. The gate gave up well before that and reported failure for a resource that was going to be fine.

P1

Build the CUDA whisper artifact

This is your biggest live capability gap. Transcription takes 9.98 s on twelve CPU threads while roughly 13 GB of a 16 GB card sits free. Phase 5 made the declaration honest by dropping to cpu; it did not make it fast. Pinning a CUDA build is the fix, and it also resolves the manifest that declares CPU while claiming 5 GB of VRAM.

P1

Stop marking an unavailable engine active

kyutai is the selected STT engine and never starts; whisper quietly serves. Either selection falls back explicitly and says so, or it refuses to select an engine that cannot serve.

P2

Update the plan ledger before anything else touches it

Eight phases are complete and recorded as todo. Left alone, the next execution pass re-does finished work, or a reviewer concludes the programme stalled. Neither is true.

P2

Finish the three phases genuinely left

Collapse ollama's degrade onto the shared companion (P13, the last of three). Reconcile ledger retention (P15) — 13,076 claims against a 500 target, still growing. Fill in the 17 health checks with no interval (P12).

P2

Give autoheal a record worth keeping

Write autoheal_actions or delete the table. Add a downtime measure — total unavailable seconds and distinct outage count per member — so this class of failure is visible next time without a forensic dig. Bound retries with escalation, and reap the 9.35 GB orphaned database.

P3

Decide sherpa-onnx, one way or the other

Qualify it through phases 17–19 and gain four capabilities on three platforms, or disable it and stop advertising it as an STT engine. The current state — enabled and unsupported everywhere — is the worst of both.
