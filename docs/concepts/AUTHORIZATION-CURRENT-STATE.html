Authorization & Approval — Current-State Map

October 17 correction. Grants apply only to explicitly governed operations. Ordinary operator-authorized maintenance needs no additional grant. Verified owner-launched Web Console runs carry session-bound baseline capabilities; an operation grant is separate. The shared CLI can still replace baseline identity with a grant token (open A75 defect); that is not a new maintenance permission. A71 propagates verified scopes through minting, recovery launch and attachment within source-proof expiry. Missing or stale proof remains unqualified. See the normative model and source/native evidence. Reliability ratings and incident diagnoses below are an October 16 source assessment, not current end-to-end certification or an established cause for every later scheduler refusal.

A single visual map of how authorization and human approval work in Vrooli today, after the consolidation efforts removed the finite effort-authority broker, added the invariant/smoke rigor net, and unified human approval onto one shared operatordecision substrate with per-scenario domain effects and a single web-console approvals inbox. Line numbers are pointers accurate as of the trace, not contracts.

1Executive summary & reliability verdict

The system is highly centralized (one shared auth package, one standing-grant authority, one approval registry, one service-principal endpoint — no duplicated decision logic) and fails closed on every cryptographic axis. The residual risk is operational, not cryptographic: on the unattended heartbeat edge it fails toward unqualified-proceed only when VROOLI_AUTH01_ENFORCE is off (the default) and the service credential/standing grant is unprovisioned — which was exactly the week-long "fleet heartbeat 401." That was a provisioning gap, not a code defect.

Scope of this map. Human approval now runs on one shared substrate — packages/api-core/operatordecision — which several scenarios emit onto and resolve back through their own domain effects, surfaced in the single web-console approvals inbox (§3). Sections §4–§5 detail the richest producer (agent-manager authorization); deployment-manager and swarm-manager are now peers on the same rail. A small, deliberate set of gates stays off the rail on principle — the base-of-trust gates and GCT's git proposals — documented in AUTHORIZATION-KEEP-SYNC-BOUNDARY.md. Don't read §4–§5 as "the only approval in the system."

3The approval landscape — one substrate, per-scenario effects, one inbox

"Human approval" is now one shared pattern with per-scenario tailoring. The consolidation extracted the generic "ask a human, act on the answer" primitive into packages/api-core/operatordecision: a scenario builds a Facts payload, publishes a <scenario>.<kind>.decision_requested.v1 event, and registers a DomainEffect that applies the operator's ask.resolved.v1 answer. notification-hub turns any such event into an Ask with no per-scenario code, and the single web-console approvals inbox is the one surface where a human sees and answers them. agent-manager, deployment-manager and swarm-manager are now peers on this rail, not four structurally different mechanisms. A small, principled set stays off the rail — the base-of-trust gates and GCT's git proposals — see AUTHORIZATION-KEEP-SYNC-BOUNDARY.md.

All three share the same substrate: operatordecision.Facts/EventID/Publisher/Webhook and the same signed-webhook verification (operatordecision.ValidSignature). The producer event-building and the resolution effect are the only per-scenario code; the ask intake, the inbox, and the resolution transport are shared.

"Wired" ≠ "exercised live" — read before trusting the round-trip. All three producers are wired onto the substrate (code + unit tests). Only agent-manager's round-trip is verified live-capable end to end today. deployment-manager, swarm-manager and autoheal are wired but their live resolution round-trip depends on the signed-webhook secret resolving at each service — now zero-config via the credential-authority fallback (the four resolve the secret without manual env), but the full live raise→inbox→answer→effect path for the non-agent-manager producers has not been witnessed live in this trace. Treat it as expected-to-work, not yet observed until a live witness runs (needs the control plane up). The secret dependency is tracked in §10 (H7).

Three things adjacent to approval — don't confuse them

  • autoheal remediation — notify-then-manual fallback (by design, high-risk+privileged). The risk-gated autoheal loop auto-applies low-risk remediations; a high-risk + privileged candidate is not auto-resolved — it raises a notification and waits for the operator to approve via the manual POST .../approve route, retained as the documented risk-gated fallback, not retired (vrooli-autoheal/api/internal/incidents/service.go).
  • Cryptographic, not human-in-the-loop — release-authority signs release manifests with an OS-keystore key (production trust mode). It gates a release by signature, independent of any human-approval decision. See docs/configuration/release-authority.md.
  • Not approval at all — the parallel FYI rail **.notification.v1 (agent-manager run outcomes, web-console session notices, GCT's "proposals waiting" daily digest) carries no operator choice. It is easy to mistake for approval; it is just a push notification.

4agent-manager — what triggers an authorization approval

This section and the next zoom into the agent-manager producer — the richest one, whose ask-don't-block run.create path mints a standing grant. deployment-manager and swarm-manager are peers on the same shared rail (§3); their producers and effects are summarized there.

The "needs operator approval" (HTTP 202) surface in agent-manager is narrow and precise: today it is run.create on target agent-manager:*, and only for a verified service principal with no covering standing grant. Everything else is allow/deny.

AUTH-01 is off by default (create_run_enforcement.go:20, operator decision P-18). So in practice the service-principal path is the only hard approval gate that fires; the broad anonymous gate sits behind an off-by-default switch. Budget/concurrency are not approval cases — an over-limit covered grant is a 403, because approval cannot raise a limit.

5agent-manager — the three ways authorization approval is granted

All three mint a proof-anchored primitive; they differ only in how it is minted. Paths 1 & 2 share the same downstream evaluator. (These are the three provision paths for agent-manager authorization; the other producers in §3 record their answer through their own domain effect.)

Path 1 — Operator-issued standing grant (CLI, --local-owner)

Trust root: kernel SO_PEERCRED on the local Unix socket → machine binding → operator account, re-verified server-side. Agent runs blocked both client- and server-side. Refs: cmd_standing_grants.go:57-75,116-132, authn/local_exchange.go:82-106, authorization.go:178-218.

Path 2 — Ask-don't-block decision loop

sequenceDiagram participant Svc as Verified service principal participant AM as agent-manager participant Hub as notification-hub participant Op as Operator Svc->>AM: POST /api/v1/runs (no covering grant) AM->>AM: AuthorizeOperation to ErrNeedsApproval AM->>AM: idempotent raise (corr = sha256); per-subject cap 3 AM->>Hub: publish ...authorization.decision_requested.v1 AM-->>Svc: 202 approval_pending Hub->>Op: Ask (hub owns copy) Op->>Hub: Answer RPC (answerer = verified subject) Hub->>AM: ...ask.resolved.v1 (echoes answered_by) AM->>AM: webhook verifies signature; refuse mint if AnsweredBy empty AM->>AM: CreateStandingGrant(Approver = answerer) Svc->>AM: retry to now admitted
⚠ Trust-root asymmetry (honest gap). Path 2 has the weakest root of the three: it mints a durable grant (up to 30 days) trusting the hub's attestation of who answered plus the webhook signature — it does not require a live independent-human proof or process binding at mint time, unlike the interactive ApproveAuthorization path (authorization.go:485-499). A deliberate trade, and fine today because Path 2 only grants run.create — but the thing to watch if that scope ever widens.

6How authority crosses boundaries

Two boundary types, one rule: a hop can only narrow authority.

Sub-agent spawn (attenuation)

effective child scopes = Attenuate(parentScopes, requested)
                         ∩ OwnerScopes
                         ∩ profile.IdentityScopeCeiling()
                         ∩ child.RequestedScopes
expiry ≤ parent ; owner unchanged
  • MintDelegatedIdentity verifies the parent token from the authenticated request header, never the body; confirms lineage, active+unrevoked, same owner; clamps expiry (orchestration/delegation.go:102-192).
  • IntersectScopes: nil = "did not narrow", explicit empty = "grants nothing"; survives only if it matches every non-nil layer (identity/scopes.go:12-38).
  • Interactive operator grants are non-inheritable by design (identity/attenuation.go:28-30).
  • Proven by TestInvariantChildRunNeverBroadensParent and TestChildUnderApprovedParentInheritsAttenuatedAuthorityEndToEnd.

11Bottom line

  • "Approval" is now one substrate, not four mechanisms (§3). agent-manager, deployment-manager and swarm-manager all build operatordecision.Facts, publish <scenario>.<kind>.decision_requested.v1, and resolve the operator's answer through their own DomainEffect — surfaced in the one web-console approvals inbox. A principled few gates stay off the rail (the base-of-trust gates and GCT's git proposals), per AUTHORIZATION-KEEP-SYNC-BOUNDARY.md.
  • Clear and centralized. One shared substrate, one evaluator, one approval inbox, one minter per path; the convoluted duplicate/conflicting approaches that caused a week of friction are gone, and the finite broker is fully purged. Per-scenario code is now just the Facts producer and the resolution effect.
  • Secure where it counts. Fails closed on every cryptographic axis, each pinned by a test; sub-agent and inter-scenario hops can only narrow authority.
  • The remaining risk is operational. Provisioning gaps and best-effort notification/self-check degrade loudly-in-logs rather than blocking — the heartbeat-401 was exactly this, and the fix was provisioning, not code.
  • The weakest design seam is Path 2's trust root (a durable grant minted on a hub-attested answerer rather than a live cryptographic human proof) — fine today because Path 2 only grants run.create, but the thing to watch if that scope ever widens.
  • Prevention vs detection. The rigor net is strong at detecting regressions; turning that into prevention depends on CI running the suite and (optionally) flipping VROOLI_AUTH01_ENFORCE on.
