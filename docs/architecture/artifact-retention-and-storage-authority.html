Vrooli · Artifact retention

Twenty-one gigabytes nobody owns

Four classes of generated artifact accumulate in the repo tree. One is a healthy cache missing an eviction policy, one is a location the migration forgot, one is a build leak with no reaper. But the deeper finding is that none of this is an open design question — the destination, the retention policy, and the cleanup owner are all already declared in the repo contract. What's missing is one helper, and the adoption that follows it.

Root cause

The rebuild's cleanup cannot run

The self-rebuild builds to a sibling temp path, renames it over the live binary, then execs into it. The defer that removes the temp file sits after the build — but the function's tail is execFn = platform.ReplaceProcess, a syscall.Exec that replaces the process image. Deferred functions never run on that path.

On a successful rebuild that is harmless: the rename already consumed the file. The problem is the window before the rename. A go build of a 26 MB binary takes roughly thirty seconds, and for that entire span the only thing protecting the temp file is a defer that dies with the process.

The professional fix

There are already two atomic-install implementations

This is the part worth fixing properly rather than patching. The repo already has a sanctioned atomic-install seam — cliinstall.AtomicInstall — which acquires the binary lock, preserves the root fallback, writes through config.WriteOwnedFileAtomic, and fsyncs the parent directory. buildinfo.go hand-rolls a second, weaker version of the same operation.

Three changes, in the order they should land:

  1. Ignore the shape now

    A one-line .gitignore entry for vrooli.tmp.*. Independent of everything below, and the only thing standing between a routine git add -A and four 26 MB binaries in history. The sidecar variant vrooli.fp.tmp.<pid> is already covered by *.fp.

  2. Build outside the repo tree, install through the existing seam

    Build into the runtime home — .vrooli/build is already in the repo contract's project_config_allowlist — then hand the result to cliinstall.AtomicInstall. A leak then lands in a directory that is already governed by storage-manager's tmp provider instead of at the repo root, and the two implementations collapse into one.

    One snag to design around: AtomicInstall calls AcquireBinaryInstallLock itself, and the rebuild path already holds that lock. It needs a lock-free inner variant, or reentrancy.

  3. Sweep stale siblings at rebuild start

    The defer can't be repaired — the function ends in exec by design. So the only mechanism that reclaims an already-leaked file is a sweep. Under the lock the rebuild already holds, glob the sibling temp shape and remove entries whose owning pid is dead or whose mtime is beyond a short horizon.

    There is precedent on both sides: tools/portability-evidence asserts in test that no .native-evidence-*.tmp survive, and storage-manager's file provider already carries an activePath guard for exactly this class of decision.

Why not just fix the defer

Because there is no defer that survives syscall.Exec, and no defer at all if the process is killed. Cleanup that depends on the writer staying alive is not cleanup — it's an assumption. The sweep is what makes the guarantee independent of how the previous run ended.

Greenfield

Delete the legacy path, don't maintain it

Per your call: no legacy handling. That means RemoveLegacyArtifactDirs and LegacyArtifactDirs come out of test-genie/api/internal/shared/artifacts/migrate.go entirely, along with their call from EnsureCoverageStructure — rather than being extended to cover test/artifacts/. The legacy data is removed directly, once, and the code stops carrying a migration it no longer needs.

Two things travel with that deletion and shouldn't be missed:

  • A live writer still targets the retired location. app-monitor writes lighthouse output to scenarios/<name>/test/artifacts/lighthouse today. Deleting the directories without redirecting that writer just restarts the accumulation under a different owner.
  • Two scenario test configs also point there — vrooli-autoheal/ui/vite.config.ts and chart-generator/playwright.config.ts. Both are one-line redirects to the runID-keyed layout.

Once those three writers move, **/test/artifacts/ can leave .gitignore and the strings.HasSuffix(rel, "/test/artifacts") skip can leave quality-health's contractscan. The convention stops existing rather than becoming a third thing to remember.

The architecture question

Two lines of defense — both already exist

You asked whether storage-manager supports scenario-declared glob locations, and especially locations inside other scenarios. The short answer is that it doesn't support globs — and that it shouldn't need to, because the cross-scenario problem already has a better answer in the codebase.

Both halves of the two-lines design are built. They have simply never been pointed at test-genie's artifacts.

The gap

The declaration vocabulary is richer than expected. service.json already carries both a storage surface and a retention block, and the retention target supports directory as a first-class kind alongside sqlite_table. vrooli-autoheal and architecture-cartographer already use it in anger.

The loop that already closes

Declare an entry, get a cleanup provider

You asked whether storage-manager supports a scenario declaring locations for it to govern. For ~/.vrooli the answer is yes — declaratively, today, with no Go changes. storage-manager/api/handlers/cleanup/module.go:257 walks the contract's runtime-home entries and synthesizes a cleanup provider from each declaration:

  • Skip anything Protected, non-Regenerable, not owned by storage_manager, or without a Retention block.
  • For the rest, emit a FileProviderConfig carrying the declared RetentionMaxAge, RetentionMaxBytes, and ProtectActive.

Its own comment explains why it reads the declaration rather than naming keys: bin used to be hardcoded there and again in the retention enforcer, "so the two guards could disagree and any third consumer inherited neither. Protection now travels with the entry."

That is exactly the two-lines-of-defense design you described, already built and already contract-driven. It has one limit, and it is the whole problem:

The boundary

The loop is keyed on runtime-home entries. A path in the repo tree has no contract entry, no class root, no owner, and no retention block — so it cannot be declared, cannot generate a provider, and cannot be governed. scenarios/*/coverage/ is not an unsupported case; it is outside the model entirely. That is why it grew to 17 GB unobserved.

The storage steer already names this as a red flag in its own checklist — "Filesystem runtime writes bypass package:api-core/storage" — and storage-manager validate scenario test-genie is the command that reports it. The 42 hand-built paths are not an undiscovered problem. They are an unadopted standard.

Never join a path

Redis and Qdrant already have the API. The filesystem doesn't.

Your question — how far to standardize so scenarios never join file paths — has a precise answer, because the target shape already ships for two of the three engines. api-core/storage/namespace.go gives a domain-scoped, variant-aware helper where the caller names a domain and segments, never a location:

StoreCaller writesCaller must know a path?
Redisstorage.RedisKey("auth", "session", id)No
Qdrantstorage.Collection("notes")No
SQLitestorage.ScenarioNamespace(slug) as Options.ScenarioIDNo
FilesystemResolver.Path(opts, class, rel) — caller builds relYes — this is the gap

Every filesystem call site therefore composes its own relative path, which is precisely where 42 hand-built joins come from. The fix is symmetry, not a new subsystem: give the filesystem the same domain-scoped shape the other three already have, so a caller asks for a logical artifact and never learns where it lives.

The helpers' own doc comment already states the contract this would complete: "Hardcoding the scenario name in a collection, key prefix, or path scope BYPASSES shadow isolation and is exactly what storage-steer / test-genie flag as a finding." Paths are named in that sentence. They just have no helper behind them yet.

Typed parameters, not globs

My earlier framing treated per-scenario paths as a wildcard problem. The contract already solved it with a better primitive. runtime_home.scoped holds parameterized templates, expanded by RuntimeHomeScopedPath(home, key, params):

  • scenario_secrets → scenarios/{scenario}/secrets.json
  • project_state → state/projects/{project_key}

A {scenario} parameter is strictly better than scenarios/*/coverage: it is enumerable, it is typed, it cannot silently widen, and it fails loudly on an unknown key. Adding test_runs_scenario as a scoped template is a contract edit, not a schema capability — and it closes the glob question without ever adding globs.

Shared data

The reader calls the owner, never the owner's disk

The hardest part of your question: some of these really are shared — test-genie writes a run result and other scenarios read it. Four consumers do this today, and all four do it by reading test-genie's files:

  • scenario-completeness-scoring reads coverage/runs and coverage/phase-results
  • app-monitor writes coverage/phase-results/lighthouse.json into test-genie's tree
  • internal/cli/scenariohandlers — the control plane — reads coverage/requirements-sync/latest.json
  • packages/freshness-go reads coverage/runs.index.json via its duplicate definition

Every one of those is an independent copy of an assumption about test-genie's layout, and nothing keeps them in sync. A shared path convention is not an interface — it is four guesses that happen to agree today.

The repo has already answered this shape three separate times, each time the same way: the owner publishes a typed surface; consumers call it.

The ArtifactCatalog precedent is the exact one to follow, because it already does the right thing for external API consumers and the wrong thing is only happening for in-repo readers who took the shortcut. Its doc comment is unambiguous: the catalog "stores private storage locators on disk; API projections expose only opaque artifact IDs." Extend that boundary to cover the four in-repo readers and the drift problem disappears — not because the paths agree, but because nobody outside test-genie has a path at all.

The one genuine wrinkle is app-monitor writing into test-genie's tree. That is not a read-sharing problem, it's a second writer to someone else's store, and no locator API fixes it. It needs to become a submission — app-monitor hands test-genie a phase result through an API and test-genie decides where it lands.

How far to standardize

All the way, and the bar is concrete rather than aspirational: no scenario code contains a filesystem path segment that names a location. Domains and logical names only, resolved by a helper, with the physical layout owned by the contract. Redis, Qdrant, and SQLite already meet that bar. The filesystem is the last engine that doesn't, and closing it is what makes every future move a contract edit rather than a migration.
