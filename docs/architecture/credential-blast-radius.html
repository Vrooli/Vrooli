Vrooli · credential architecture · monetization path

Minted, Not Given

Five of the nine credentials the business suite declares are things no operator can ever supply — there is nowhere to obtain them. The design question is not who types them in. It is what happens the day one goes missing on a host with real customers on it.

The model

Two questions, asked of every secret

The manifest schema already answers the first one — provisioning is an enum of operator, derived, generated, defined in .vrooli/schemas/common.schema.json:727. The second question has no name in the codebase yet, and it is the one that decides whether a bad day is an inconvenience or an outage.

Where does the value come from?

Already modelled. Only an operator-supplied value may block configuration while it is absent.

operator
A person obtains it from an external issuer and provides it. Stripe, SendGrid, AWS, Apple.
derived
The declaring component fetches it once a named source credential exists. Tunnel Manager's account and tunnel IDs work this way.
generated
The component mints it out of nothing, because there is no issuer to ask. Calendar's JWT signing secret is the reference.

What breaks if the value changes?

Not modelled anywhere today. This is the axis worth adding.

benign
A re-handshake. Nothing is lost, no one is locked out for longer than it takes to re-provision both ends.
disruptive
Live sessions die. Every customer signs in again, every device re-pairs. Recoverable, loud, and expensive in trust.
destructive
Data at rest becomes permanently undecryptable. This is not a lockout. It is data loss.

The two axes are not independent. A secret with an external issuer can always be replaced by asking the issuer again — so everything operator is benign, including every Stripe and S3 key.

A secret Vrooli mints itself exists in exactly one place on earth. What it protects decides whether losing it costs a re-login or costs the data.

The mechanism

Generate-on-miss, and the branch that is missing

Calendar already implements most of what you want, and it already defends against the fear you named. resolveJWTSecretFromAuthority in scenarios/calendar/api/jwt_secret.go:46 does not treat "no value" as one condition. It splits three ways, and its own comment states the reasoning: minting a replacement when the store merely failed to answer "would silently invalidate every token issued against the secret that is still in there, so refuse instead of guessing."

What it does not cover is the case where the store answers truthfully that the value is gone: a restore from a recovery bundle older than the secret, a TPM2 host-binding that stops unwrapping after a firmware or Secure Boot change, a store re-initialised on a rebuilt host. In all three, ErrUnconfigured is the honest answer — and today that is the branch that mints.

The debt

The same mistake, seventeen more times

Calendar's three-way split is not a convention. It is one file that got it right. Every scenario that reads a credential re-implements the policy by hand, and almost none of them reproduce it.

A store outage looks exactly like an unset credential

Including LPBS itself.

resolveSecret at landing-page-business-suite/api/auth.go:80 ends if err != nil { return "" }. So when the store is merely unreachable, LPBS does not fail — it degrades. An empty api-key-encryption-key means API keys get written unencrypted. An empty admin-default-password means an ephemeral one is generated. An empty consumer-auth-private-key falls through to the local development key path.

This is the same root cause as the missing witness branch: not distinguishing broken from absent. The docs even record the incident that motivated the taxonomy — an unreachable session bus once reported as "credential is not configured", sending an operator to re-provision a key that was already there.

The consolidationPut the policy in packages/credential-authority-go, not in twenty-one scenarios. A Require() helper for operator credentials and a ResolveOrMint() helper carrying the witness gate for generated ones. Calendar's correctness stops being an example nobody copied and becomes the only way to call it.

The shared helper that replaces twenty-one hand-rolled shims

This is the piece that makes the rest cheap. The witness is an interface, so the authority package never learns what a database is — LPBS passes an implementation backed by its own tables, calendar passes one backed by its event store, and a scenario with nothing at stake passes nil and keeps today's behaviour explicitly rather than by omission.

packages/credential-authority-go/mint.go new file 
// Witness testifies whether a deployment has history. It is implemented by
// the caller against the data the secret protects - never against the store,
// which is the thing whose absence we are trying to interpret.
type Witness interface {
	// Minted reports whether this identity+field has ever been minted here.
	Minted(identity Identity, field string) (bool, error)
	// RecordMint notes that minting happened. It never stores the value.
	RecordMint(identity Identity, field string) error
}

// ResolveOrMint returns a generated credential, minting it only on a genuine
// first start. It is the single implementation of the policy that calendar
// got right and seventeen other call sites did not.
func (a *Authority) ResolveOrMint(
	identity Identity, field string, w Witness, mint func() (string, error),
) (string, error) {
	value, err := a.Resolve(identity, field)
	switch {
	case err == nil:
		return value, nil
	case errors.Is(err, ErrUnconfigured):
		// fall through to the witness gate
	default:
		// Store unreachable or absent. Minting now would invalidate every
		// token issued against the value that is still in there.
		return "", fmt.Errorf("resolve %s:%s: %w", identity, field, err)
	}

	if w != nil {
		minted, werr := w.Minted(identity, field)
		if werr != nil {
			return "", fmt.Errorf("witness check %s:%s: %w", identity, field, werr)
		}
		if minted {
			return "", &MintRefusedError{Identity: identity, Field: field}
		}
	}

	generated, err := mint()
	if err != nil {
		return "", err
	}
	if err := a.Put(identity, field, generated); err != nil {
		return "", fmt.Errorf("store generated %s:%s: %w", identity, field, err)
	}
	if w != nil {
		if err := w.RecordMint(identity, field); err != nil {
			return "", fmt.Errorf("record mint %s:%s: %w", identity, field, err)
		}
	}
	return generated, nil
}

MintRefusedError is the whole point of the exercise, so its message is the deliverable — it is what you will read at three in the morning:

packages/credential-authority-go/mint.go new · the message that matters 
func (e *MintRefusedError) Error() string {
	return fmt.Sprintf(
		"%s:%s has been minted on this deployment before and is now absent "+
			"from the credential store. This is credential loss, not a first "+
			"start. Restore the store from your recovery bundle "+
			"(`vrooli credentials recovery restore`). Re-minting would "+
			"invalidate every token and every value sealed with it; if that "+
			"is genuinely what you want, pass --accept-credential-loss.",
		e.Identity, e.Field,
	)
}

The witness table

One table in LPBS's own database. It holds no secret material — only the fact that minting happened, which is exactly the fact the credential store cannot testify to once it has lost the value.

CREATE TABLE IF NOT EXISTS credential_mint_witness (
  logical_id  TEXT NOT NULL,
  field       TEXT NOT NULL,
  minted_at   TIMESTAMP NOT NULL DEFAULT NOW(),
  PRIMARY KEY (logical_id, field)
);
-- No value column, by design. This table can be read by anyone and

The playbook

What each blast radius is allowed to do

The rule that falls out of the model: provisioning: generated is safe at benign and disruptive. It must never be applied at destructive without a key ring, because generate-on-miss plus a truthful ErrUnconfigured equals silent, permanent data loss.

benign

Re-handshake. No history to preserve.

Mint or re-provision freely; pass nil as the witness. For service-secret, the only requirement is that both ends read the same logical_id so there is one value, not two that can drift.

disruptive

Live sessions die. Recoverable, but visible to customers.

Generation is fine on a genuine first start, and it must be gated by the witness. Rotation must be overlapping, never a swap: publish the new key while the old one still verifies, let outstanding tokens expire, then retire the old one.

You already have this for the hardest case. resolvePreviousConsumerKeys at api/main.go:349 reads a previous-key set and serves it from the JWKS endpoint, so a device holding a token signed by last month's key still verifies. Give session-secret the same shape and cookie rotation stops logging everyone out.

destructive

Ciphertext outlives the key. There is no recovery.

Never a single key. Store a versioned ring, tag each encrypted row with the version that sealed it, decrypt with any version in the ring, encrypt new writes with the active one. Rotation becomes a background re-encrypt rather than an event.

Precedent exists: prompt-manager declares a key-ring field described as "versioned Ed25519 signing keys" for exactly this reason, and LPBS already tracks a per-row encryption_state column on api_keys — most of the bookkeeping a ring needs. securevalue is LPBS-private today and would be the natural home for the ring, or the natural thing to promote into packages/.

The work

Order of operations

Nothing before step 6 needs a secret from you. Each step is independently shippable, and the cleanup is folded into the step that already opens the file rather than deferred to a tidy-up pass that never comes.

  1. Land the shared helper unblocks 2–5

    Add ResolveOrMint, Require, Witness, and MintRefusedError to packages/credential-authority-go. Port calendar to it first — it is the one call site whose current behaviour is already correct, so any diff in behaviour is a bug in the helper.

    Then sweep the other twenty. Most collapse to a one-line Require call; the seventeen that swallow errors get correct behaviour as a side effect.

  2. Declare the nine missing descriptors

    Stripe's three and delivery's two on LPBS; the shared LPBS identity plus the signing set on scenario-to-desktop. Nothing on scenario-to-cloud — its Cloudflare token is already governed under vrooli/tunnel-manager.

    Declaring is what puts a secret into doctor, onboarding, recovery export, and the deployment manifest secrets-manager builds. Omit env everywhere except stripe-publishable-key and the signing set — electron-builder is a process Vrooli does not author, so env injection is correct there.

  3. Reclassify the five, add the witness table

    Set provisioning: generated and drop env on the five self-minted values, add credential_mint_witness, and route them through ResolveOrMint. This is the step that removes them from your list entirely.

    Hold api-key-encryption-key and remote-profile-encryption-key back until step 5 — they are destructive, and generating them before the ring exists builds the trap this whole plan is about avoiding.

  4. Get Stripe and S3 out of cleartext, and out of api/ root

    Route loadStripeConfig and newS3Storage through the resolver instead of envx.Get. Have the admin UI write through to the authority rather than into payment_settings and download_storage_settings; bucket, region, endpoint and prefix stay in the database, because those are configuration.

    While these files are open: move the Stripe admin and webhook implementations into internal/commerce, keep the root StripeService as a thin composition adapter until the broader architecture migration moves its dependent adapters together, and delete compat shims for moved implementations. Write-through matters more than encrypting in place — it is what makes recovery export actually contain your billing configuration.

  5. Build the key ring, then generate the two encryption keys

    Versioned ring in securevalue, a version tag per encrypted row, decrypt-with-any / encrypt-with-active. Then and only then flip the two destructive keys to generated.

    This also closes a live gap: both keys are unset today, so remote deployment profiles are being written unencrypted with only a warn log.

  6. Fix the descriptors that report green while broken

    Flip admin-default-password to required: true; move admin-default-email and auth-magic-link-base-url out of the credential store into ordinary configuration. Today doctor shows required_absent: [] on a host where admin sign-in is not production-ready.

  7. Copy the store off this host, then provision

    doctor currently reports no encrypted credential-store copy receipt exists. Configure one before live keys land — a host-bound TPM2 wrap is exactly the thing that stops unwrapping after a firmware update, and that is the scenario the witness gate turns from a disaster into a refusal.

    Only then does your list matter: Stripe restricted key (rk_, not sk_), webhook secret, publishable key, S3 key pair, SendGrid key, admin password, and signing material when desktop publishing goes live.

  8. Unify the deployment-secret address optional

    Make BundleSecretPlan name the descriptor it satisfies, so a value can be traced from a deployed bundle back to a declaration. This is the only item that does not block monetization — but it is what would let you audit a deployment against the credential ledger instead of trusting it.

The thing worth holding onto: you are not building a way to store secrets — that exists and it is good. You are building a way for a scenario to tell the difference between a machine that has never run and a machine that has forgotten. Only the second one is an emergency, and only the data can testify which it is.
