Where scenario start time actually goes

Across 598 recorded starts, a scenario takes a median of 41 seconds to come up. On a measured restart, 69% of the wall clock is hardcoded sleep — the service answered its own health endpoint 0.4s after launch and the lifecycle engine waited another 15.1s before believing it. Every fix below is checked against four non-negotiables: portable, scenario-agnostic, production-UI-preserving, and leaving the engine cleaner than it was.

01The four constraints

These bound every recommendation. Where a fix would violate one, the design changes — not the constraint.

Hard requirement
Scenarios always serve the production UI
A scenario's UI is served from its built artifact, never a dev server, watch mode, or unbuilt source. Speed is never bought with this.
Portability
Linux, macOS, Windows — no host assumptions
No new /proc reads, no POSIX-only signalling, no shelling to platform binaries. New OS knowledge goes behind platform-go's build-tag seams.
Agnosticism
No scenario names, no framework assumptions
The engine may not name a scenario or a toolchain. Language knowledge lives only in builderRegistry, keyed by declared build.kind.
Craft
Leave it cleaner than we found it
Each fix deletes more than it adds, is unit-testable through the existing injected clock, and closes a latent defect rather than routing around it.
On the production-UI rule specifically. This was verified, not assumed: 104 of 120 UI components run node server.js serving ./dist, the rest are near-identical static servers, and zero scenarios invoke a dev server, --watch, or nodemon anywhere in a develop phase. The invariant holds today by convention only — nothing in internal/deployability or internal/templatevalidation enforces it. Since the work below touches the build path, it must add that enforcement, so the rule stops depending on everyone remembering it.

04Findings, with portability and agnosticism verdicts

Each finding names the code, the measured cost, and what the constraints force the design to be.

F1

The health gate sleeps 15 seconds before its first probe

141.7 min · 25.3%96 of 120 scenarioshealth.go:22

WaitForHealth blocks on startup_grace_period before entering the poll loop. 96 of 120 manifests declare 15000. The distribution proves it is a constant, not real startup: p50 = 15.02s, p90 = 15.07s. Measured directly, the service was serving 200s 0.40s after launch; the engine declared health 15.11s after.

if health.StartupGracePeriod > 0 {
    deps.sleep(time.Duration(health.StartupGracePeriod) * time.Millisecond)
}
err := Await(r.awaitClock(), healthAwaitPolicy(health.Timeout, health.Interval), ...)

The investigation turned up something better than “delete the sleep”. The declared-component model already has a first-class per-component readiness probe — run.readiness with types port_open and http, polled every 100ms against a deadline in awaitComponentReadiness (phases.go:645). It is correct, portable, typed, and completely dead: only 2 of 236 components declare it, and zero components use the dependsOn edge that is its only caller.

It can be revived with no manifest edits at all: 234 of 236 components already declare run.port, so a component's default readiness is “its declared port accepts a connection.” The two that declare no port (a sidecar and an electron daemon) legitimately mean “ready when the process is alive.”

Portable
yes Probes are net.DialTimeout and net/http — pure Go, no host calls. No health check type shells out.
Agnostic
yes Readiness is declared per component and typed. The engine learns nothing about any language.
Production UI
unaffected Changes when we look, not what is running.
FixWait on derived per-component readiness (default: port_open on run.port), then evaluate lifecycle.health as the verdict. startup_grace_period becomes a ceiling — it suppresses failure before the deadline, it never delays success. Net effect on the codebase: one sleep deleted, one dead mechanism brought into the main path, 236 components covered by derivation instead of by hand.
Agnosticism defect to close while herePerformHealthCheck supports a hardcoded "postgres" check type (internal/scenario/scenario.go) that dials 127.0.0.1:5432. A named service in a generic engine — it should be a plain tcp check with the address supplied by the manifest.
F2

Dependencies start strictly one at a time

142.2 min · 25.4%p90 = 123s, max = 728sdependencies.go:81

ensureDependencies is a plain for loop over alphabetically sorted names, each doing a full recursive start. The graph does not require this: transitive closures reach 44 scenarios (scenario-to-ios, persona, token-economy) while the critical-path depth is at most 18 and typically 1. Even the warm path is serial — a fully-running, fresh scenario still costs ~0.47s per node to load, look up, check freshness, and probe.

Portable
yes Goroutines and the existing per-scenario advisory lock. Nothing OS-specific.
Agnostic
yes Fan-out is driven by the declared dependency graph.
Blocked by
prerequisite There is no portable memory signal to govern the fan-out. See below.

This is the one fix that cannot ship first. A 44-node fan-out runs dozens of concurrent Node builds — pnpm install alone peaked at 752 MB and system sampling caught node at 1.83 GB. That needs a memory-aware gate, and today the only source of host memory facts is /proc/meminfo (internal/hostinventory/collector.go:306), which exists on Linux and nowhere else; macOS and Windows get a warning and no total. internal/capacity is correctly build-tagged and degrades cleanly, but “degrades cleanly” here means unknown owner, no attribution — a gate built on it would govern on Linux and be unbounded everywhere else.

FixTwo steps, in order. (a) Add a portable TotalMemoryBytes/AvailableMemoryBytes seam alongside the existing load_platform_{linux,darwin,windows,other}.go build-tag set — the pattern is already established in that package. (b) Fan out per DAG level under a concurrency budget derived from available memory and a per-builder-kind memory reservation declared on BuilderSpec, so the budget is a declared property of a build kind rather than a guess about a scenario.
F3

Restart unconditionally rebuilds, ignoring freshness

76.6 min · 38% of restart timelifecycle.go:996

Restart() sets opts.ForceSetup = true, and evaluateSetupChecks short-circuits to "Forced rebuild (restart)". Setup ran in 160 of 160 recorded restarts at a 28.7s mean. Restart is not “stop then start” — it is “stop, rebuild everything, start”, whether or not a byte changed. For an unchanged scenario that decomposes as:

go mod download          0.00s     14 MB   ← already satisfied, still invoked
go build (warm)          0.73s    340 MB
pnpm install             1.20s    752 MB   ← lockfile unchanged, still invoked
pnpm run build           4.29s    413 MB
  ├─ strings:gen         0.01s
  ├─ tsc --noEmit        2.33s    368 MB   ← full typecheck in the hot path
  └─ vite build          2.09s    419 MB   ← the production artifact — stays
Explicitly off limits: none of this may become a development build. The vite build line stays exactly where it is, and the UI keeps being served from dist/. The savings here come only from not repeating work whose inputs did not change — never from producing a cheaper artifact. Concretely, all of the following are ruled out: swapping pnpm run build for vite dev or vite --watch; serving src/ through a dev middleware; setting NODE_ENV=development; skipping minification, chunking, or strings:gen; and any “fast path” that lets a scenario come up without a current production bundle on disk.

Three separable wins, all input-gated rather than output-weakened:

  • Restart honours freshness unless --force is passed. Same artifact, computed once.
  • Install gets an input gate. spec.Install runs unconditionally today. The inputs are uniform and already on disk: go.sum (117 scenarios), pnpm-lock.yaml (115), plus pnpm's own node_modules/.modules.yaml install-state marker (112). Gate on a digest of those, declared as InstallInputs on BuilderSpec — never as an if kind == "pnpm_vite" in the engine.
  • The typecheck moves to the test gate. tsc --noEmit appears in 85 of ~103 UI build scripts and is over half the UI build time. It is a correctness gate, not a build input — vite produces the identical bundle without it. Moving it does not weaken the artifact; leaving it unmoved just pays for a typecheck on every service start.
Portable
yes File hashing and a CLI flag.
Agnostic
requires care Install inputs must be declared per build.kind, extending the registry rather than special-casing.
Production UI
preserved Same vite build, same dist/, plus a conformance rule so it stays that way.
Guard to addBecause this work touches the build path, add a conformance rule in internal/deployability asserting that every component whose builder declares a DefaultOutput is actually served from that artifact, and that no run.argv in a develop phase invokes a dev/watch mode. That converts the production-UI requirement from a convention into a check. Nothing enforces it today.
F4

Stop kills by stopwatch — and is not tree-correct on Windows

3.5s per restartlifecycle.go:933portability defect

Teardown terminates the process group, sleeps a flat 2s, escalates to a force kill, sleeps another 0.5s. No poll for actual exit. The caller then sleeps stopSettleDelay = 1s more. Measured stop: 3.10s wall, 2.50s of it sleeping, with the processes gone in well under a second.

Replacing those sleeps with a poll is easy and portable — platform.IsPIDRunning is genuinely implemented on all three platforms (syscall.Kill(pid,0) on Unix, OpenProcess + WaitForSingleObject on Windows), and isPIDRunning is already in scope two lines below the sleep. But doing so exposes a defect the sleep has been masking:

// packages/platform-go/process_linux.go
func signalProcessGroup(groupID int, force bool) error {
    ...
    return syscall.Kill(-groupID, signal)     // whole tree
}

// packages/platform-go/process_windows.go
func signalProcessGroup(groupID int, force bool) error { return signalPID(groupID, force) }
                                                     // ^ group leader ONLY

On Windows the “process group” signal degrades to signalling one PID, so a scenario's grandchildren survive a stop. The platform layer already ships the correct primitive — AssignProcessContainment, backed by a Job Object — but the control plane never calls it. It has zero callers under internal/; the only two users in the whole repo are unit-health and scenario-to-desktop. The lifecycle engine's own launcher (phases.go:564) does not.

Portable
makes it portable Today's stop is tree-correct on Linux only. This fix closes the gap.
Agnostic
yes Operates on tracked process records, not on scenario identity.
FixPoll every tracked record PID for exit — not the group leader, which is the same thing as the PID on Windows and therefore proves nothing about children. The 2s becomes a timeout instead of a cost. Then wire AssignProcessContainment into startTrackedProcess so Windows gets real tree containment, and apply the same poll-instead-of-sleep treatment to the two sibling sites at lifecycle.go:1179 and :1281, which repeat the pattern verbatim.
F5

Shared-package edits invalidate the fleet — correctly, and expensively

structuralfreshness.gorevised

Correcting my earlier framing: this is not a false-positive problem. Freshness derives a Go component's inputs from go list -deps -json and hashes the repo-local closure, skipping _test.go. When it says a scenario is stale because packages/api-core/discovery/default_remote.go is a new input, the consuming binary genuinely would differ. The engine is right. A previously drafted plan describing mtime-walk false positives (binariesNeedSetup, anyFileNewerWithDeps, no memoization) is superseded — those functions no longer exist, digests replaced mtimes, and setupCache memoizes per start.

What remains is cost, in two places:

  • The Go side is cheap — the build cache absorbs a total invalidation in 0.73s.
  • The UI side is not. One shared-package change (shared_package:@vrooli/proto-types:generate) invalidates a 4.3s production build per consuming scenario, and observed live it cascaded across the dependency tree.

The go list probe itself costs 0.33s per Go component and is memoized within a start but not across starts — worth caching by (module, go.sum digest), though it is a minor line item, not the headline I originally implied.

FixDo not weaken freshness to make this faster — that would trade correctness for latency and risk serving a stale UI. Make the fan-out cheap instead: build each shared package once per start operation (the machinery is already there in provisionSharedPackages), and cache the go list closure across starts.
F6

scenario start on a healthy scenario can take it down

availabilitylifecycle.go:566

If freshness says stale, startScenario takes the decisionStopThenStart branch: it stops a running, healthy instance and rebuilds. If the rebuild fails, the scenario is left failed — an observation-shaped command caused an outage. This happened three times during this investigation, because five scenario go.mod files carried a malformed require block.

Build-before-stop turns out to be viable on Linux and needs a platform seam elsewhere. Verified empirically: go build -o over the binary of a currently running process succeeds (Go unlinks and recreates rather than truncating), the running process keeps its old inode, and it stayed healthy throughout. On Windows, removing a running .exe fails with a sharing violation, so the swap needs the rename-away-then-replace dance.

The UI side needs care for a different reason: vite build writes into the same dist/ the static server is serving, so there is a window where a viewer can be handed a half-written production bundle. That is a live correctness bug against the production-UI requirement, independent of any performance work.

Portable
needs a seam Artifact swap semantics differ on Windows; belongs behind platform-go.
Agnostic
yes Staging path derives from the builder's declared DefaultOutput.
Production UI
strengthened Atomic dist/ swap removes the torn-bundle window.
FixBuild to a staged path under the existing internal/artifactlock cross-process lock, then swap atomically, and only then stop and relaunch. A stale-but-healthy instance keeps serving until the new artifact exists. The rebuild_only freshness policy already does exactly this for shared dependencies — it simply is not applied to the target scenario itself.

08What must change before this is safe

Three structural properties the engine does not have yet. Two of them the fixes above quietly depend on.

The encouraging part first: golangci-lint, go vet and gofumpt are all clean across internal/lifecycle, and the test-to-code ratio is 0.92. This is tidy code. The debt is structural — the kind tooling cannot see — and it sits precisely where the concurrency work would land.

The Runner is not safe to share across goroutines

Progress events fan out through r.sinks, an unsynchronized slice field on a shared *Runner. publish ranges over it (progress.go:91) while attachSink appends to it and its detach closure splices it (operation_record.go:285-292). Today that is fine, because a start is one goroutine start to finish.

F2 ends that. The moment sibling dependencies start concurrently, every one of them calls r.publish while the top-level recorder is attached — a textbook data race on a slice header, and one that will surface as corrupted progress output or a panic under -race, not as a clean failure.

PrerequisiteMake the sink set immutable-after-construction, or guard it with a mutex and range over a copy. This is a small change, but it must land before any fan-out, not alongside it — and the fan-out work should run its tests under -race as a gate.

There is no cancellation story

internal/lifecycle calls context.Background() 34 times; only 6 methods accept a ctx. Interruption is handled by a signal handler that marks the operation abandoned and re-raises (operation_record.go:88-101) — a workaround for having no context to cancel.

Serially this is survivable. With fan-out it is not: when one dependency fails, its siblings must be cancelled, or a failed start leaves a dozen orphaned builds running. The signal-handler trick cannot do that — it only knows about the whole process.

PrerequisiteThread a real context.Context from the CLI edge through Start / startScenario / ensureDependencies. Mechanical, wide, and best done as its own change with no behaviour in it — which also lets the signal-handler workaround be deleted rather than accumulated around.

Recursion state wants to be a session object

startWithState(name, opts, ready, setupCache, stack) threads three accumulators through six functions by hand. ready and setupCache are plain maps shared down the recursion — which under F2 become concurrently written maps, the second race.

Refactor that pays for itselfFold ready, setupCache, stack and the cancellation context into one startSession value with the synchronization inside it. Six signatures get shorter, the two race classes disappear by construction, and the fan-out becomes a small change to one loop instead of a careful audit of every callee.

The test suite is red, and it is red for an instructive reason

go test ./internal/lifecycle currently fails, at 75.8% coverage. Not from a code defect — from a leaked process:

port 22009 is already in use by pid 1392618
  (/tmp/TestStartWritesOperationRecord1681876751/001/scenarios/alpha/api/mock-api)

$ ps -o lstart,etime -p 1392618
  Sat Aug 22 19:18:00 2026   1-05:30:53      ← still listening on 22009

A test-spawned server from two days ago is still running and still holding the port, and it deterministically breaks a different test on every run until someone kills it by hand. The test that leaked it does have a teardown — t.Cleanup(func() { _ = runner.Stop("alpha", StopOptions{}) }) — but the error is discarded, so when teardown fails the process simply outlives the suite, silently, forever.

There is an uncomfortable symmetry here worth stating plainly: the package that owns process teardown leaks processes in its own tests. The same instinct that produced sleep(2s) instead of a poll produced _ = runner.Stop(...) instead of a checked teardown. Fixing the tests is not housekeeping before the real work — it is the same fix, applied to the same blind spot, and it has to come first because the suite is the only thing that will tell us the stop rewrite is correct.
PrerequisiteAssert teardown succeeded instead of discarding it; register cleanup at spawn rather than after setup; allocate test ports from the OS rather than a fixed range; and add a suite-level check that no child process survives the run. Then make -race the default for this package. Immediate unblock for whoever picks this up: kill 1392618 and remove /tmp/TestStartWritesOperationRecord1681876751.

The missing piece: nothing reports this data

This entire investigation ran on hand-written SQL against ~/.vrooli/state/runtime.db. The engine records per-step timings on every start and the only consumer is an ETA hint during scenario wait. There is no command that answers “what is start time doing?”

That matters beyond convenience. Without a reporting surface, none of the work below is verifiable after it lands, and nothing stops the 15-second sleep from being reintroduced by a well-meaning manifest six months from now. A perf fix with no measurement is a perf fix with a half-life.

AddA read-only timing surface over the records that already exist — per-scenario and fleet-wide step breakdowns, start vs restart, p50/p90. It is a query and a renderer over data already being written. Pair it with one regression assertion in CI: time from process launch to health verdict must not exceed a small multiple of measured readiness — which is exactly the invariant F1 establishes, and the one most likely to silently rot.

Items 1 and 3–5 alone take the measured structure-health restart from 26.8s to roughly 6s without touching the dependency graph, without a single manifest edit, and without changing what gets served. Every one of them routes through the injected deps.sleep and hostProbeDeps seams, so each lands with deterministic unit tests rather than timing-sensitive ones.

P0 through P4 carry no user-visible improvement, and skipping them is the obvious temptation. Two of them are not optional: without P4 the F2 fan-out is a data race on r.sinks and on the shared ready/setupCache maps, and without P0 there is no trustworthy signal that the stop rewrite in F4 is correct. P1 and P2 are what keep the result from decaying — one pins the production-UI requirement, the other makes the numbers in this report reproducible by anyone, at any time, without SQL.

The net effect on the codebase

  • Deleted: fixed-duration lifecycle sleeps, duplicated terminate-kill blocks, one hardcoded ui/package.json path, one hardcoded package name, one hardcoded service name in the health evaluator, and the signal-handler cancellation workaround.
  • Revived: awaitComponentReadiness, FollowsWorkspaceFileDeps and RegisteredBuilderKinds — three abstractions that are already correct and already dead.
  • Closed: Windows process-tree containment, the torn dist/ window, the missing memory seam, schema-vs-registry drift, the three conflicting grace-period defaults, and the “start took down a healthy service” failure mode.
  • Added: a mechanical guard for the production-UI requirement, a timing surface over data already being recorded, and a regression assertion on readiness-to-verdict latency.
  • Left alone deliberately: the error-taxonomy split, the 19-field lifecycleDeps, and the unpruned registry tables — real, but not on this path, and worth their own decisions rather than being swept into a performance change.
