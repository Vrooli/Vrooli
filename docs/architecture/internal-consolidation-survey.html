Revision note — rev. 4 · post-change

Rev. 1 measured the root CLI's connect-rpc adoption (7 of 163) against the scenario fleet's (80%) and read it as a stalled migration. That was the wrong yardstick. A work record from the original effort states the intent plainly: vrooli.cli.v1 was built as a message-only proto package, deliberately not a scenario, so proto-health does not cover it by design. The goal was typed --json output, not putting the control plane behind RPC. Rev. 3 resolved the architecture questions; the plan consolidate-internal-close-the-cli-migration-boundary produced the rev. 4 measurements below. The four residual families now have typed app/CLI/handler boundaries, manifest-built declared commands, and matching primitive evidence. The namespace-grouping recommendation remains withdrawn (section 07, D1).

Three migrations, one boundary

The CLI is not messy because nobody had a plan. It is messy because three good plans each got most of the way and stopped at exactly the same line — the edge of internal/cli/vroolicli.

Those three efforts are: the layering pattern (app/X → Xcli → Xhandlers), the typed-JSON contract (cliv1 protos via cliout.WriteProtoJSON), and the manifest-as-source-of-truth model that all 79 scenario CLIs use. Measured separately they look like three problems. Measured together they are one 5,534-line block of code.

The manifest question, answered

Your recollection is correct: for scenario CLIs the manifest is the source of truth. cliapp.LoadFromManifest parses cli/manifest.json and builds the live SubcommandGroup — flags, positionals, arg schema, and the rendered help text all derive from it. 65 of 79 scenario CLIs call it. The root CLI calls it once, for scenario list, which is also the only root command carrying primitive evidence.

But there is a hard constraint sitting in the way, and it is worth seeing in the original:

// packages/cli-core/cliapp/manifest.go — loadFromManifest() switch c.Binding.Kind { case "connect-rpc": handler = bindings[c.Binding.Method] needsAPI = true case "local": handler = bindings[c.Binding.Handler] default: return SubcommandGroup{}, unsupportedBinding(c.Binding.Kind) }

cli-core now builds local-bound commands as well as Connect commands. A local binding carries a stable handler key, while Connect bindings retain their service/method lookup and API requirement. Both paths share the same manifest-derived flags, positionals, argument schema, and help renderer.

The control plane still keeps local execution where it is correct: setup, credentials, host installation, and other commands must work before an API exists. The four residual families now use manifest construction for every declared leaf, while undeclared legacy leaves remain explicit future adoption work. The generated evidence artifact records 31 manifest-built root commands, and the scenario fleet remains source-compatible.

This is the real fork in the road

The local bindings are not debt to be paid down — they are a control-plane design constraint the framework now serves. The remaining work is adoption breadth, not a second architecture decision: the root manifest is constructive for the declared families, and the CI checker continues to protect the rest of the command tree.

And the manifest has already drifted

You asked whether the manifest's grouping matches the CLI's. It does not — and because nothing enforces it, the drift is silent.

Your constraint, restated

You said the manifest should match the CLI and the CLI shape shouldn't change. That points at a specific, cheap first move: a CI check that diffs the manifest against the binary's own command tree. It fixes workload, catches the next omission automatically, and commits you to nothing about SSOT direction — which is the decision that should wait until after the vroolicli extraction settles the tree.

07

The three open decisions, resolved

Each of these was left open in rev. 2 because it needed evidence rather than taste. The evidence arrived — and it reversed one recommendation and shrank another by an order of magnitude.

D1namespace groupingrecommendation reversed

Don't nest the package families. The repo already tried it.

What we know. The repo contract permits nesting — the control-plane target declares roots ["cmd", "internal"] with no per-package glob, so only internal/tools/* and internal/safeguards/* are depth-constrained. Nesting is allowed. It is just not good, for three measured reasons.

First, the short leaf names collide. Renaming hostinventory → host/inventory means the package is now called inventory at every call site. Run that transformation across all four families and this is what falls out:

Second, 84 files import two or more members of a single family — 57 for host* alone, one of them (internal/runtime/runtime.go) importing five. Every one of those files needs an import alias the moment the leaf names shorten.

Third, and decisively: this experiment has already been run in this repo, and the result is visible in the import lines. internal/resources/ nests exactly this way — env, runtime, manifest, control. Look at what call sites had to do:

// the aliases the existing nesting forced back onto call sites manifestpkg "…/internal/resources/manifest" // 41 files vrooliruntime "…/internal/resources/runtime" // 18 files resourceenv "…/internal/resources/env" // 10 files resourcecontrol "…/internal/resources/control" // 9 files

Every one of those aliases is the flat compound name, reconstructed by hand. The nesting bought directory tidiness and paid for it in 216 aliased internal imports across the tree. Doing it again to host* would produce hostinventory "…/internal/host/inventory" in 116 files — the original name, now with extra steps.

Go's convention is that the import path carries context so the package name can be short. That works when the leaf name is unambiguous in its file. Here it is not: hostreqspec.Kind tells a reader more than reqspec.Kind, and credentialauthority.Issue more than authority.Issue. In this codebase the compound name is the disambiguation, and the flat tree is what makes it work.

D2cli-core local bindingsmuch smaller than it looked

This is a ~3-day cli-core feature, not an architecture project

What we know. Rev. 2 called this "the one genuine architecture decision." Reading the implementation, that overstated it. Here is what loadFromManifest actually builds after the local guard:

// packages/cli-core/cliapp/manifest.go:334 subs = append(subs, Command{ Name: c.Name, // from manifest Description: c.Description, // from manifest Args: args, // ManifestArgs() — flags, positionals, binds RunCtx: handler.run, // func(RunContext) error — supplied by the caller Architecture: declared, primitiveEvidence: handler.evidence, })

Nothing in that construction is Connect-specific. RunCtx is an ordinary function the owning CLI hands in. ManifestArgs reads flags and positionals with no proto involved. renderHelp derives help text from Command.Args, also with no proto involved. Flag.LocalOnly and Positional.LocalOnly already exist in the schema. The only thing a Connect binding uniquely supplies is the lookup key — Service.Method — that maps a manifest entry to a handler in the bindings map.

So the blockers are three small, specific things:

D3the smaller callsnow evidence-backed

Three defaults, two confirmed and one reframed

gocyclo — confirmed, but better than I proposed

Rev. 2 said leave it out of CI because it would fail 22 existing functions on day one. golangci-lint v1.64 has --new-from-rev, which reports only issues introduced after a given revision. Add gocyclo to CI gated that way: new code is held to the threshold, the existing 22 stay visible without blocking, and nobody runs a decomposition campaign. This is strictly better than omitting it.

resources/ root split — confirmed defer, and the seam is already obvious

Deferring past Wave 3 stands: 10,574 LOC in 29 flat files competes for the same attention as the CLI extraction. Worth recording that the seam needs no discovery when you get there — the filenames already cluster into drivers (5 files), managed_service (4), vault (3), legacy (3), broker (3). Note this is the one place where nesting is right: these are cohesive subsystems with non-colliding names, unlike D1's families.

The "import leakage" — reframed; it isn't leakage

I proposed assuming the leakage was intentional. Measuring it says something more useful. Counting distinct symbols used from each bypassed package:

And the layer being bypassed is thin: internal/app/resource is 191 lines. So the picture is not "three families drifted off the pattern." It is that the app/ layer fits the six small command families and is vestigial for the three large ones — resourcecli talks to resources directly because a 191-line facade in front of a 21,742-line subsystem was never going to carry the traffic.

That reframes row 10 entirely. The move is not to force resourcecli back behind app/resource — that would manufacture pass-through code. It is to decide, per family, whether the app/ package earns its existence, and delete the ones that do not. Cheaper, more honest, and it leaves one documented shape instead of a rule with three silent exceptions.

Net effect on the plan

Wave 2 loses the namespace grouping (1–2 days) and gains doc.go coverage (~half day). Wave 1 gains the gocyclo gate (~1 hour). A new Wave 4 holds the cli-core local-binding work, and row 10 turns from a week of restructuring into a two-day pruning decision. The total shrinks and the risk drops.
