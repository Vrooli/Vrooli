The Security Phase Ratchet

Capacity admission reserves 17,974 MB for Test Genie's security phase — 29% of this host's RAM. The heaviest thing the phase actually runs, measured directly, is 2.5 GiB. The gap is not a modelling error. The number is not a measurement of the phase at all.

01 · what it is

What the phase actually does

A delegated security scan, not a test suite.

The security phase runs no code of its own. Test Genie resolves the provider security-health, opens a Connect RPC to that scenario's already-running API server, and asks it to validate one target. Everything after that happens inside a different, long-lived process.

That server detects which substrates the target contains, then runs five scanners in a fixed sequence — gitleaks for secrets, gosec for Go SAST, govulncheck for reachable Go vulnerabilities, pnpm audit and osv-scanner for dependency advisories. Each is a forked subprocess. gosec and govulncheck fork once per Go module, and 111 of 123 scenarios carry two modules (api/ and cli/), so a routine run is seven forks, not five.

The design is careful in the ways that matter: a scanner whose binary is missing degrades to an advisory finding rather than failing the phase, results are content-fingerprinted and cached, and a shared admission gate bounds how many scanner subprocesses run at once. None of that is the problem.

02 · the defect

Why the number is so large

Because it is a high-water mark of a process, read absolutely, and reported as if it were a measurement of one phase.

Every other resource number in this pipeline is a delta: sample at the start, sample at the end, subtract. Peak RSS is the one field that is not.

// packages/api-core/metrics/metrics.go:238
func (c *Collector) resourceUsage(start, end rusageSample) *commonv1.ResourceUsage {
	usage := &commonv1.ResourceUsage{}
	rel := c.cpuMemReliability(start, end)
	if rel != commonv1.Reliability_RELIABILITY_UNAVAILABLE {
		usage.CpuUserMs = end.cpuUserMs - start.cpuUserMs   // delta
		usage.CpuSysMs  = end.cpuSysMs  - start.cpuSysMs    // delta
		usage.PeakRssBytes = end.maxRSSBytes                // absolute
	}

M1 ru_maxrss only goes up, so an absolute read is a lifetime figure

The kernel's ru_maxrss is a monotonic high-water mark for the life of a process. Subtracting two samples of it would be meaningless, which is presumably why the code does not — but taking the endpoint absolutely means every phase inherits the largest moment in the provider's entire history, including work done for other phases, other runs, and background timers.

The sampler takes max(RUSAGE_SELF, RUSAGE_CHILDREN). Both terms ratchet. Neither resets between requests. The provider server is started once and serves for days.

M2 2,338 phase rows report memory for zero work

If the field measured the phase, a phase that did nothing would report nothing. Across the corpus, 2,338 rows record 0 ms wall clock and 0 ms CPU — cache hits and skips that forked no process at all — and those same rows carry a mean peak RSS of 811 MB, with a maximum of 3,608 MB.

That is the whole argument in one query. There is no phase-level work those numbers could be describing.

evidencesqlite3 test-genie.db "SELECT count(*), avg(peak_rss_bytes), max(peak_rss_bytes) FROM suite_execution_phases WHERE peak_rss_bytes > 0 AND wall_clock_ms = 0 AND cpu_user_ms = 0 AND cpu_sys_ms = 0;" → 2338 | 811 MB | 3608 MB

M3 Consecutive executions form a staircase that never descends

Plotting the last 46 security executions in order shows a step function with three plateaus. Within a plateau every execution reports a byte-identical figure — the run that burned 89 CPU-seconds and the run that returned from cache in under a second are indistinguishable.

The steps are the moments the provider process reached a new high. The plateaus are everything after.

M4 The p90 lands inside the plateau by a 7.9-point margin

368 of 2,055 samples — 17.9% — sit above 8 GB, all of them from one long-lived provider process that once reached ~17.9 GB. Because 17.9% exceeds 10%, the 90th percentile falls inside that band and returns 17,974 MB. The median of the same 2,055 samples is 93 MB.

A 193× gap between p50 and p90 is not a heavy tail. It is two different quantities in one column. And the reservation is decided by how many stale rows one process happened to leave behind: had that provider been restarted a little more often, the same p90 would read double digits.

evidencen=2055 · p50 93 MB · p90 17,974 MB · max 18,950 MB · rows >8 GB = 368 (17.9%) p90 = 29.3% of a 60 GiB host, reserved for every admission of this phase
Why this matters beyond one phase

This is the number the capacity ledger reserves RAM from. The adaptive-admission plan re-derives the fallback reservation from measured p90s precisely because the current 512 MB default is too low. Feeding that same machinery a 17,974 MB figure for security does not make admission safer — it makes one phase's claim large enough to serialize the scheduler against a cost that was never incurred.

03 · the real cost

What the phase actually costs

Every scanner, run by hand on this host, under /usr/bin/time -v.

With the instrument discredited, the only way to size the phase is to run its parts directly. The result is a phase that is genuinely expensive — just not in the dimension the ledger is watching.

C1 The dimension that is actually over-committed is CPU, not RAM

A single gosec fork drove 2,115% CPU — 21 of 32 cores — for its whole 0.8-second run. A routine phase forks two of them. Meanwhile the batch reservation the scheduler falls back to is DefaultReservationCPUMilli = 500: half of one core.

So the ledger reserves ~7× more RAM than the phase can possibly use and ~42× less CPU than one of its seven children demonstrably takes. Both errors point the same way — toward a scheduler that admits work whose real contention it cannot see.

C2 Sequential scanners are the reason RAM is fine

Worth stating plainly, because it is the one place the current design is doing exactly the right thing: ValidateTarget iterates scanners in a for loop, so the two multi-gigabyte scanners never overlap within a phase. Parallelising them for speed would turn a 2.5 GiB phase into a 4.5 GiB one. That trade is available but it is not free, and it should be made deliberately rather than as a side effect of a refactor.

04 · the work nobody asked for

The provider does more than the phase

Two background behaviours dominate the process the phase is measured inside.

The security-health scenario is two products in one server: the per-target validator the phase calls, and a fleet-wide dependency intelligence corpus. The second one runs on a timer, and it is much larger than the first.

C3 A full-fleet walk every five minutes

DiscoverFleet walks all 123 scenario trees, parsing every go.mod and pnpm-lock.yaml it finds, then Annotate fans out over the scenarios at concurrency 4. The loop fires every five minutes for the life of the process.

Warm, this is cheaper than it looks — the lockfile fingerprint pass is 0.27 s across 17,246 directories, and I want to be accurate about that rather than inflate it. The durable cost is the YAML: 19.4 MiB of pnpm-lock.yaml re-parsed every five minutes, about 5.6 GiB/day of allocation churn through yaml.v3, in the same heap whose high-water mark becomes the phase's reservation.

evidenceapi/main.go:145 defaultReconcileInterval = 5 * time.Minute 124 pnpm-lock.yaml · 19.4 MiB · 651 lockfiles fingerprinted per pass · 123 scenarios

C4 The advisory epoch makes the whole fleet go cold at midnight UTC

Cache identity for osv-scanner, govulncheck and pnpm-audit folds in now.UTC().Format("2006-01-02"), so that advisory-backed evidence cannot be reused across a database refresh. Correct in intent — but it means every key for every scenario changes simultaneously at the day boundary, and the five-minute timer walks straight into it.

The cache table shows the result without ambiguity: 118 of 190 rows were written today, against one yesterday and one the day before. That is ~118 osv-scanner forks at ~2.0 GiB and ~8.3 s each, four at a time — roughly 4 minutes of wall clock at ~8 GiB resident and ~10 cores, arriving as a step function once a day.

C5 Duplicate work exists, and it is smaller than it looks

gosec and govulncheck each call walkModuleEvidenceFiles over the same module set, so the identical walk-and-hash of every Go source file runs twice per validation. It is real duplication and worth collapsing.

It is not, however, a performance finding: measured across three scenarios the doubled pass costs 3–11 ms. I had expected this to be significant before measuring it and it is not. Fix it for the sake of one fingerprint definition, not for the milliseconds.

05 · options

How to mature it

Ordered by evidence, not by appeal. The first one is worth more than the rest combined.

Fixing the instrument comes first, because every other decision here — reservations, concurrency, whether the phase is even expensive — is currently being made against a number that does not mean what it says.

O1

Measure each fork, not the process

execCommander.Run already waits on every scanner subprocess. cmd.ProcessState.SysUsage().(*syscall.Rusage).Maxrss is the exact peak RSS of that one child, available for free at the point it exits. Return it alongside the exit code, take the max across the scanners a phase ran, and the phase reports what the phase cost.

This replaces a lifetime high-water mark with a per-operation measurement without adding a sampler, a goroutine, or a dependency. It is a smaller change than the workaround the current comment in metrics_unix.go describes.

fixes M1–M4~1 file + call sitesno new deps
O2

Make an unattributable measurement say so

The schema already carries memory_reliability. Where a collector cannot isolate an operation's memory — a long-lived server with no per-fork attribution — it should report UNAVAILABLE rather than a confident wrong number, exactly as it already does when getrusage fails.

Capacity admission then falls back to a declared reservation, which is a known-approximate value, instead of trusting a precise-looking one. Wrong-and-confident is the failure mode that produced the 17,974 MB reservation.

fail-honestpairs with O1
O3

Quarantine the poisoned samples

368 rows above 8 GB will keep steering the estimator after the collector is fixed. Bump a metrics-schema version on the row and have PhaseCostEstimate ignore samples written by the old collector, rather than deleting history.

Without this, O1 changes nothing for weeks — the p90 is computed over a 30-day window and the plateau rows outnumber the corrected ones for most of it.

required for O1 to take effectmigration + one query
O4

Bound scanner CPU instead of guessing it

One gosec fork takes 21 of 32 cores. Two suites each forking two of them oversubscribe the host by a wide margin, and the ledger books 500 millicores for the batch. Set GOMAXPROCS on the scanner children to a value the broker chose, and reserve CPU from the measured figure.

This is the dimension where over-admission actually bites: RAM is over-reserved by ~7× and CPU is under-reserved by ~42×, so the scheduler is simultaneously too timid and too reckless.

real contention winenv on exec.Cmdneeds a broker input
O5

Stagger the advisory epoch per scenario

Replace the shared YYYY-MM-DD in the fingerprint with a per-scenario offset — hash the scenario id into a bucket and roll that scenario's epoch at its own hour. Freshness stays bounded by 24 hours; the cliff becomes a slope.

The cheapest large win available. It converts a once-daily ~4-minute, ~8 GiB, ~10-core stampede into roughly five scenarios rescanned per hour, and it changes no correctness property — every scenario is still rescanned within a day.

removes the daily cliff~10 linesno contract change
O6

Key advisory freshness to the database, not the calendar

The stronger version of O5: the reason to invalidate is that the advisory data changed, and both osv-scanner and govulncheck can report the database version they used. Fold that identity into the fingerprint instead of the date, and evidence survives until there is a real reason to discard it.

Correct rather than merely smoother. It costs a probe per scanner per pass and needs a fallback for tools that will not report a version — the date is that fallback, so O5 and O6 compose.

strictly better invalidationper-tool probe
O7

Move the fleet reconcile out of the serving process

The five-minute fleet walk shares a heap, a CPU budget and — until O1 — a resource metric with the RPC the phase calls. Splitting it into its own process or a scheduled job separates the two failure domains.

Deliberately listed below O1: once per-fork attribution exists, co-location stops corrupting the measurement, and this becomes an ordinary isolation argument rather than an urgent one. Worth doing, not worth doing first.

isolationlifecycle + ownership change
O8

Back the reconcile off when nothing changed

The interval is a flat five minutes regardless of outcome. Track consecutive no-change passes and widen the interval up to a ceiling, resetting on any observed change. The 19.4 MiB of YAML re-parsed on every idle pass is pure churn.

Straightforward, but measure before and after — the fingerprint pass is only 0.27 s warm, so the saving is the YAML parse and allocation, not the walk.

~5.6 GiB/day of parse churnverify the win
O9

Collapse the duplicated evidence walk

Compute the module evidence fingerprint once per (target, module set) and let both gosec and govulncheck read it.

Tidiness, honestly priced: the measured saving is 3–11 ms. Do it so there is one definition of what a Go module's evidence is, not for the time.

one definition, not twonegligible perf win
If only three things get done

O1 + O3 together, then O5. The first pair makes the phase's cost knowable and stops the estimator being steered by 368 stale rows; the third removes the largest recurring load on the host. O4 follows once there is a trustworthy CPU figure to reserve from.

06 · leave alone

What not to change

Each of these looks like a defect and is not.

Looks wrongWhy it is right
Scanners run sequentially, not in parallelIt is the only reason the phase's resident peak is ~2.5 GiB rather than ~4.5 GiB. Parallelising is a real option, but it is a RAM-for-latency trade to be taken deliberately.
ru_maxrss takes max, not sum, of self and childrenCorrect and well argued in the source comment: RUSAGE_CHILDREN is already a peak over all reaped children, and summing would invent a concurrent peak that never existed. The bug is the absolute read, not the max.
A missing scanner binary does not fail the phaseDeliberate degradation. It keeps a host without osv-scanner installed from turning every scenario red, and the gap is still surfaced as a finding.
Advisory evidence expires on a 25-hour TTLThe TTL is right; the shared epoch is what needs staggering (O5). Do not lengthen the TTL to hide the cliff.
Full scanner stdout is buffered in memoryMeasured at 250–706 KB per scanner. Streaming would add complexity for no measurable gain.

Method, and what this does not establish

Every figure above came from one of three places: the live Test Genie database at scenarios/test-genie/data/test-genie.db (2,055 security rows of 57,954 phase rows), the security-health database at scenarios/security-health/data/security-health.db, or a scanner run by hand on this host under /usr/bin/time -v. No number here is modelled or extrapolated.

  • The ~17.9 GB event itself is not explained. I can show the field is a ratchet, that 368 rows share one plateau, and that no scanner I measured comes within 7× of it. I cannot say what the security-health process was doing when it reached that height — the logs do not cover it and the process has since restarted. O1 would make the next such event attributable; until then, treat the plateau's origin as unknown rather than assuming a leak.
  • Scanner costs are single measurements on a warm host, not distributions. gosec's 21-core figure in particular will vary with the module and the build cache; the order of magnitude is the claim, not the digits.
  • I expected the duplicated fingerprint walk to matter and it does not. It measured 3–11 ms. It is listed as tidiness (O9) rather than performance because that is what the measurement supports.
  • The 5.6 GiB/day YAML figure is bytes parsed, not bytes resident. It is an allocation-churn argument for O8, not evidence that the reconcile holds gigabytes.
  • Concurrency interactions were not measured end to end. Two suites plus the fleet reconcile can plausibly put ~10 GiB of scanner processes on the host at once; that is arithmetic over measured parts, not an observation.

Commands, table and column names appear inline beside each finding so any number here can be re-derived rather than taken on trust. Companion page: Test Genie's Two Schedulers, whose phase-cost chart raised this question.
