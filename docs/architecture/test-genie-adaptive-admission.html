Test Genie's Two Schedulers

Test Genie does not have one concurrency control. It has two, built years apart, and only one of them can see the host. The adaptive machinery everyone wants already exists — it runs one layer below the cap that is actually binding.

Six defects, a staged design for suite-level adaptation, and eleven debt items sitting in the files that work has to touch anyway.

Over the last 30 days this host completed 2,543 comprehensive suites. The average one executed for 217 seconds and waited 223 seconds before it started. Thirty percent of runs waited more than five minutes. Git Control Tower fans a 12-member baseline collection at a service whose per-caller queue is four deep, so it spends most of a collection deferring and retrying — 460 admission rejections are recorded on the current process lifetime.

None of that waiting was caused by a full host. It was caused by an integer.

Finding 1 · the shape of the system

The suite gate counts. The phase gate measures.

A run passes through two independent admission decisions. The outer one — the suite gate in the run manager — asks only how many other runs are there. The inner one — the phase gate inside the orchestrator — asks the shared capacity ledger whether this specific phase's measured memory and CPU footprint fits on this specific host right now, takes a lease, and releases it when the phase ends.

The two never talk. The suite gate has no reference to the broker, the ledger, or a host snapshot, even though both are constructed in the same bootstrap function, twenty lines apart.

The suite gate in full

Four integers, one conflict check

Lever Default What it gates On breach

TEST_GENIE_MAX_QUEUED_RUNS 16 Total durable queued records Retryable RESOURCE_EXHAUSTED

Only the first three are load governors, and only the first is the throughput ceiling. The per-scenario cap is a genuine correctness invariant and must stay at 1. The resource-name check is real mutual exclusion and should stay exactly as it is — it is the one piece of the suite gate that encodes something a resource measurement cannot.

Finding 2 · the measurement layer is real

Phase costs span 350×, and the estimator already knows it

Test Genie has persisted 57,954 phase records; 35,528 of them carry RELIABILITY_RELIABLE for both CPU and memory. The estimator takes the nearest-rank p90 of the last 30 days for that phase name, scoped to the scenario when it has five or more samples and falling back to the fleet otherwise. This is not a stub — the capacity ledger currently holds 11,903 operation claims from 389 distinct Test Genie runs.

The spread is the whole argument for measuring rather than guessing. A workflow phase peaks at 52 MB. A security phase peaks at 17.5 GB. One fixed number cannot stand in for both — and the one currently standing in for both is set wrong.

What is actually broken

Six defects, in the order they cost you throughput

D1

The fallback reservation is documented as the fleet p90. It is the p73 for memory and the p48 for CPU.new

DefaultReservationRAMBytes = 512 MB and DefaultReservationCPUMilli = 500 carry the comment "these reservations approximate the fleet p90 of observed phase resource claims." Against 35,528 reliable samples from the last 30 days the real fleet p90 is 1,094 MB and 1,609 millicores. 512 MB sits at the 72.7th percentile; 500 millicores sits at the 47.5th — barely above the median.

Consequence: every phase admitted on the fallback under-claims, so the ledger believes the host has more room than it does, and batches are admitted that overcommit. The revisit trigger in the comment ("when durable fallback admissions exceed 10%") never fires because nothing counts fallback admissions — Admit returns the count and the caller discards it.

scenarios/test-genie/api/internal/orchestrator/phasebatch/phasebatch.go:118–124 · phaseadmission/admission.go:73–77
D2

A phase that runs alone claims nothing at all.new

Admit opens with if len(batch) <= 1 { return ... }. A phase that is exclusive, or that the timeout guard held back, or that simply ended up last, takes zero leases. The ledger sees nothing.

The ledger confirms the size of the hole: 389 runs recorded a mean of 15.0 claimed phases against a comprehensive suite of roughly 19. unit — p90 10,843 millicores, the most CPU-hungry phase in the fleet — claimed capacity in only 157 of those 389 runs. architecture appears in 4. The phases most worth accounting for are the ones most often unaccounted.

scenarios/test-genie/api/internal/orchestrator/phaseadmission/admission.go:53–55
D3

The suite gate is host-blind by construction — this is the throughput ceiling.

maxConcurrentRunsFromEnv() is read once at manager construction and never re-evaluated. No CPU, RAM, swap, load, or historical signal enters the decision. The comment is honest about why (a 2026-06-21 incident where three concurrent baselines stalled an executor) — but the fix chosen then was a constant, and the machinery that would let it be a measurement was built afterwards, one layer down.

The cost is quantified above: 223 s mean queue wait against a 217 s mean execution, while 43 GB and 22 cores sat free.

scenarios/test-genie/api/internal/runmanager/manager.go:72–101, 552–568
D4

A queued run's ETA counts down to zero while it is still queued.

snapshot() computes remaining = etaTotal − elapsed from startedAt, which is stamped at admission. etaTotal is the plan-preview estimate of execution only. A run that waits four minutes therefore reports "0 seconds remaining" for four minutes and looks stalled.

The dispatcher does re-stamp startedAt on promotion, so ETA is correct once running. The gap is narrower than it looks and entirely fixable: there is no estimated queue wait anywhere, even though the data to compute one — position in the FIFO, and the p90 duration of every running suite — is already in hand.

scenarios/test-genie/api/internal/runmanager/manager.go:1453–1485 (snapshot) · 659–694 (dispatch)
D5

The platform capacity policy says advisory; the phase gate enforces anyway.new

vrooli capacity policy get reports enforce = advisory, which by contract means "record a claim, run Decide, log the verdict, and always let the caller proceed." That mode is honored by the resource-lifecycle admission hook in internal/capacity/admission.go. It is not consulted by packages/capacity.Broker.Acquire, which is the path Test Genie uses — a non-grant verdict there truncates the batch and serializes the run.

An operator who sets enforce = off to debug a capacity problem will change resource behavior and leave Test Genie's scheduler untouched, with nothing saying so.

One correction to the earlier read.

The saturation message is not ambiguous at the source: SaturatedError carries a Limit field and renders as "test-genie admission is saturated (caller queued run capacity)" versus "(queued run capacity)". The distinction survives to the wire. It is discarded one hop later — Git Control Tower's isTransientAdmissionSaturation matches both strings identically and defers the member either way. Fixing the phrasing would change nothing; giving GCT a reason to back off differently for a per-caller limit than for a global one would.

Finding 3 · feasibility

The seam already exists, and the ledger is already shared

The question was whether resource-aware suite concurrency is feasible. It is, and the reason is structural rather than optimistic: phase claims from different runs already land in one ledger, which Decide reads fresh on every acquisition. Two concurrent suites that both reach their security phase already contend correctly — the second one's 17.5 GB claim is refused and it drops to serial.

That inverts the usual risk calculus. Raising the suite cap is not "hoping the host copes"; the phase gate is the safety net, and it is already load-bearing. What the suite gate needs to add is not a second policy but a cheap up-front check so that a suite which cannot possibly fit waits in the queue instead of being admitted and then thrashing through serialized phases.

Three ingredients are missing, and each has an obvious source:

Missing Where it comes from Cost to build
A suite envelope — the RAM/CPU a whole run holds concurrently p90 over historical runs of max simultaneous claimed bytes, derivable from the same suite_execution_phases table joined to batch membership One repository method beside PhaseCostEstimate. Today's proxy: mean largest single phase is 3.78 GB, worst observed 18.05 GB.

The policy, stated concretely

What "adaptive" has to commit to

An adaptive limit is only professional if it answers the six questions that make it falsifiable. These are the answers this system's own evidence supports:

QuestionCommitment
What is measured RAM and CPU millicores only, through the existing ledger. Not GPU — no Test Genie phase claims VRAM today, and inventing a claim it cannot substantiate would be worse than omitting it.
Which signal wins Whichever denies. Decide already evaluates RAM and CPU independently and releases the first claim if the second fails. Swap pressure above 50% is an unconditional RAM deny and stays that way — this host currently sits at 38%, which is close enough to matter.
How much headroom is reserved The p90 envelope of the candidate suite, plus whatever Decide's existing conservatism gives: available = total − max(observed, committed). No new headroom constant — a second one would drift out of agreement with the first.
How fast it moves Up by at most one slot per admission, and only when the last N admissions granted without degrade. Down immediately on any deny. Asymmetric by design: the cost of being one too high is a thrashing host; the cost of being one too low is a queue.
What happens to running suites Nothing. Never preempt a running suite — preempt_enabled is false platform-wide and should stay false here. Pressure reduces admissions, not survivors.
What happens with no data Hold at the current effective cap. A scenario with no envelope history is admitted under the old rule and measured; it never justifies a raise. This is the single rule that makes the whole thing safe to ship.

Rollout · each stage is shippable and reversible

Five stages, and the gate that opens each one

Stage 1

Correct what already measuresno new behavior

Re-derive the fallback reservation from the fleet p90 the data actually shows (1,094 MB / 1,609 millicores), and record the fallback-admission count that Admit already computes and throws away. Close D2 by claiming for a batch of one as well — a solo phase is exactly the one whose footprint should be visible to another suite.

Gate: fallback-admission rate is observable, and it is under 10%.

Stage 2

Build the suite envelope, publish nothing

Add the repository method that returns a scenario+preset's p90 max-concurrent claimed bytes and millicores. Emit it on the admission diagnostic endpoint. Compare it against what runs actually peak at for two weeks.

Gate: the envelope predicts observed peak within 25% for the top ten scenarios by run count.

Stage 3

Shadow the decision

Wire the broker into the run manager and run the suite-scoped acquire on every admission — then discard the verdict and admit by today's integer. Log would_admit / would_defer beside the real outcome, the host state, and how the run subsequently behaved.

Gate: no case where shadow said admit and the run that did start degraded, timed out, or drove swap past 50%.

Stage 4

Enforce beneath a ceiling of 4

Effective concurrency becomes a measurement bounded by floor 2 and ceiling 4. Every transition is recorded with the verdict that caused it, so a regression is attributable rather than mysterious.

Gate: mean queue wait falls materially and phase-level serialization warnings do not rise.

Stage 5

Give Git Control Tower a real reservation

A 12-member baseline collection is one logical unit of work, not twelve competing strangers. Let a trusted caller declare a collection and receive a bounded slice of queue capacity for it, so the fan-out stops rediscovering the per-caller limit twelve times through a 30-second reconciler. Raise the ceiling above 4 only after this exists — otherwise the extra slots are consumed by retry churn.

Gate: a collection capture completes without any member entering the deferred state.

Second pass · debt in the same blast radius

Eleven things to delete, merge, or move while you are in here

None of these is the reason your queue is slow. All of them are in the files the work above has to touch anyway, and several are load-bearing for it — you cannot make a lever dynamic while two of six levers are hard-wired to a private reader, and you should not build a shadow log on top of a percentile function that returns the maximum.

Grouped by whether they block the adaptive work, sit on the shared seam, or are simply cheap and verifiable.

Correction to an earlier version of this page.

A2 previously claimed that ceil(0.9n) − 1 returning the maximum for n ≤ 9 was a correctness defect. It is not: that is the textbook inclusive nearest-rank definition, the code's own comment names it as such, and both cost.go functions were deliberately aligned on it. The related divergence count also fell from 21 to 18 — the first calculation used Python's banker's rounding for what Go's math.Round does half-away-from-zero, which made selfhealth and profileplanner look like two conventions when they are one. What survives is stronger and narrower: two conventions in one scenario against a written intent that they agree (A2), and one helper serving a claim and a deadline guard that want opposite tails (A3).

A1

The shared env-lever helper already exists. The run manager wrote a fourth one.deduplication

Test Genie has internal/shared/config.go with EnvInt(key, default). runmanager ignores it and defines boundedIntFromEnv, then maxRunsPerScenarioFromEnv and maxConcurrentRunsFromEnv — which are that function with the name and default inlined, byte for byte. Four of the six admission levers go through the generic reader; the two that matter most go through single-purpose copies.

This is the incomplete half of a refactor that already happened, and it is directly in the way: making the concurrency cap dynamic means touching the one lever that has its own private accessor. Net deletion, roughly 30 lines.

scenarios/test-genie/api/internal/runmanager/manager.go:62–110 · internal/shared/config.go:47
A2

"p90" means two different things inside one scenario, and both make scheduling decisions.unification

execution/cost.go uses inclusive nearest-rank, ceil(0.9n) − 1. selfhealth/ledger.go and profileplanner/planner.go use round-half-up on n−1, round(0.9(n−1)). internal/scenarioruntime/startop.go interpolates linearly. The two integer conventions return different ranks at 18 of the 58 sample sizes between n=2 and n=59 — n=7,8,9, then 17,18,19, then 27,28,29, and so on.

The comment at cost.go:339 states the intent plainly: "use the same nearest-rank ceiling as PhaseCostEstimate so the scheduler and cost report agree about what p90 means, especially for small samples." That intent is half-achieved — the two functions inside cost.go agree with each other, and disagree with the two other percentile implementations in the same scenario. One shared helper, one written definition, and the stated intent becomes true.

A3

One percentile serves two purposes with opposite risk postures.design

Inclusive nearest-rank returns the maximum whenever n ≤ 9 — mathematically correct, and deliberately chosen. PhaseCostEstimate keeps scenario-scoped samples at five and above, so 147 of 1,727 scenario-phase pairs (8.5%) are currently sized from their worst observed run.

For a capacity claim that conservatism is correct: over-reserving is safe. The same helper also feeds PhaseDurationEstimate → phasebatch.TimeoutRisk, where conservative means the opposite — a phase guarded against worst-ever × 1.5 is excluded from every batch, which is the over-serialization ContentionAllowance was lowered to 1.5 to prevent. The two consumers want different tails, and neither the code nor the docs say so. Decide it explicitly rather than inheriting it.

execution/cost.go:260 (claims) · cost.go:287–345 (deadline guard) · phasebatch/phasebatch.go:104–128
A4

The admission contract crosses the process boundary as English prose.architecture

Test Genie returns connect.NewError(CodeResourceExhausted, err), which carries the code and the message string. Nothing in the service attaches a connect.ErrorDetail — there is not one call site in the whole API. Git Control Tower then recovers the meaning with four strings.Contains checks against that message.

Rewording SaturatedError.Error() — a sentence no test pins — silently reclassifies durable backpressure as a terminal baseline failure. A small proto detail carrying limit_kind, queue_depth, and retry_after deletes the substring matching, and is the same message the queue-wait estimate in D4 needs to return anyway.

If you only do part of this

What I would fix first

Ordered so that each item makes the next one cheaper, and so the debt lands inside work that was already going to happen rather than as a separate cleanup nobody schedules.

  1. A2, then A3, then D1 and D2. One shared percentile helper with its convention written down, then the explicit decision about which tail the deadline guard should use, then the corrected fallback reservation and claiming for solo phases. In that order the estimator has one definition before anything is measured against it. This is the whole input layer, and it is days rather than weeks.
  2. A1, in the same commit range. Route all six admission levers through shared.EnvInt and delete the two single-purpose readers. It is a net deletion, and it is the file you have to open to make the cap dynamic anyway.
  3. C3 and D6 together. Fix uptime in api-core so the trap closes for all 107 call sites, then let the four affected scenarios inherit it. Roughly the same effort as patching test-genie alone, with 103 more scenarios protected.
  4. The queue-wait estimate (D4), carried on A4's new error detail. These are one piece of work, not two: the structured saturation reply is where the estimated wait belongs, and shipping it lets Git Control Tower delete its substring matching in the same change. A run that says "queued, position 3, about 6 minutes" is a different experience from one that says "0 seconds remaining" for six minutes, at identical throughput.
  5. Then Stage 2 and 3. The shadow log turns this from an argument into evidence, and costs nothing in risk because nothing acts on it. Settle B2 before it starts — the second claim producer is the wrong time to discover the owner key has no structure.
  6. B1 and D5 as one decision, not two. Either fold packages/capacity into the frozen contract and make the broker honor enforce, or write into doc.go that the broker is deliberately outside it and why. Both are defensible; diverging silently is not, and eight resource CLIs depend on the answer.
  7. C1, C2, C4 and B3 as filler. Each is mechanical, individually reviewable, and needs no design input — the right shape for the work that gets done between the items above rather than as its own initiative. C2 in particular is rmdir with a listing in front of it.

One thing not to do.

Do not raise TEST_GENIE_MAX_CONCURRENT_RUNS on its own as a stopgap. With D1 and D2 unfixed the ledger under-counts by an unknown margin, and the phase gate — the thing that would otherwise catch the overcommit — is exactly the component operating on bad numbers. The current cap of 2 is too low, but it is currently the only honest limit in the system.

Method. Every figure comes from live state on this host, not from documentation. Run history: scenarios/test-genie/data/test-genie.db — 3,334 suite executions, 57,954 phase rows; percentiles are nearest-rank over completions in the trailing 30 days filtered to RELIABILITY_RELIABLE on both CPU and memory (35,528 rows). Claim counts: vrooli capacity list against ~/.vrooli/state/capacity.db — 12,561 claims, 11,903 of kind op, across 389 distinct run identities inside the 24-hour terminal retention window. Admission counters and the uptime figure: live GET /api/v1/admission and GET /health on port 15421. Host figures: nproc, free, /proc/loadavg, swapon.

Caveats worth naming. Queue-wait statistics cover the 818 executions in the window carrying both a requested_at and a started_at; 2,348 older rows predate the requested_at column and are excluded, so the sample skews recent. 24.5% of August phase rows carry no reliability marker at all and are excluded from every percentile here — instrumentation coverage is itself a gap, and three phase names (monetization-conformance, event-capture-conformance, ai-conformance) have no reliable sample on record and therefore always take the fallback. The suite-envelope figures quoted in the feasibility table are per-execution maxima and sums, not true max-concurrent — that number requires joining batch membership and is precisely what Stage 2 is for.
