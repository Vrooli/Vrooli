Layer 1 · where a value lives

One authority per host, chosen once at setup

Every credential ends up in exactly one backend. Vrooli picks it during vrooli setup, writes the decision to disk, and never re-decides — because a backend that flips with session health splits your secrets in half.

Why your host landed on the file store

Setup probed the GNOME keyring with a write/read/delete cycle in August and it failed — which, given the keyring's history on this machine, is the correct call. The practical consequence is the good news: Vrooli's credentials no longer live behind the lock that prompts you. The 43 values in the encrypted store are reachable at boot whether you answer that dialog or not.

Layer 2 · what protects the key

One data key, several ways in

The file store doesn't encrypt each secret with your passphrase. It seals every entry with a single data key, then wraps that key several times over. Any one wrap opens the store — which is how a machine can gain a TPM later and get unattended access without re-encrypting a single value.

Layer 3 · how a secret reaches code

Declared in a manifest, resolved at the last possible moment

Nothing hardcodes a path to a backend. A manifest declares a descriptor — a backend-neutral name — and the authority resolves it on demand. Whether the value ever touches an environment variable is a deliberate, documented choice.

A real modeling gap

The control-plane host has no way to say so

You're right that swarminator is deliberately a node. The problem is that bridge has no kind that expresses it. The enum is AGENT / SSH / ATTACHED — nothing for "this is the control plane." So it is registered as an agent, never dials itself, and therefore reads permanently OFFLINE.

Why the terminology matters more than cosmetics here

Once credentials can be pushed to nodes, "which nodes may receive a credential" becomes a security-relevant list — and the control-plane host is the one entry that must never be on it, because it is the source. Today nothing in the model distinguishes it, so any push targeting "all nodes" would include the machine it came from. Naming the kind is not polish; it is a precondition for the fleet work.

  • The kind is missing, not the concept. The enum's own comment says it describes "which Bridge capabilities the node can provide" and that a host with no agent is "a first-class, honestly limited fleet member" — so a NODE_KIND_CONTROL_PLANE (or a self flag on the record) fits the existing design rather than bending it.
  • Presence should be derived, not dialed. The control-plane host's liveness is the API's own liveness. It should report ready by definition instead of failing a heartbeat rung it structurally cannot pass.
  • Readiness advice must not be nonsense. "Restart the node agent" is actively misleading on the control plane, and this is exactly the rung an operator hits first when something looks wrong.
  • It also affects dispatch today. dispatchable=false means the control-plane host cannot receive a job — which may be correct, but it is currently an accident of the transport model rather than a decision anyone made.

Fleet · your minimouse question

Sharing keys across nodes: every part exists, and nothing connects them

You're right that this is the correct goal, and right that it's annoying today. The honest status: bridge deliberately refuses to carry secrets, secrets-manager owns them but has no fleet awareness, and the seam between them is documented as P2 and unbuilt. The fleet itself is not the gap — minimouse has been paired since 2026-08-17 and is online and dispatchable right now.

Built and solid

Node identity

Per-node Ed25519 keypair, pinned in both directions at pairing, no TOFU fallback. A node that finds no pin fails hard. This is exactly the trust anchor a secret-distribution seam needs — and it already exists.

Built and solid

Portable envelope

recovery export/verify/restore already produces a passphrase-wrapped bundle that restores into any host's authority regardless of that host's own wrap. The cross-machine format is not the missing piece.

Missing

Everything in between

No per-node credential scope, no "push this set to node N", no rotation fan-out, no receipt of which node holds which version. secrets-manager has no concept of a node; bridge has no concept of a credential.

What the shape probably wants to be

Not "share the store." The store's host-bound wrap is deliberately host-bound — a shared data key would undo the property that makes disk theft useless. The shape that fits what already exists is scoped replication: declare per-node which logical IDs a node may hold, seal each value to that node's registered Ed25519 public key, push it over the channel bridge already authenticates, and have the node's own authority ingest it under its own local wrap.

  • Scope is the safety property. minimouse gets vrooli/openrouter because it needs to validate ai-gateway; it does not get your Cloudflare token. A fleet-wide "share all" is the thing to design against, not toward.
  • Rotation is the actual feature. Provisioning once is annoying; re-provisioning six machines on every rotate is the thing that makes people stop rotating. A rotation that fans out to every node scoped to that logical ID — with a per-node receipt of which version landed — is the whole point.
  • Test fixtures beat real keys where they can. Bridge's own doctrine is "validation jobs prefer fixtures over real secrets." Some of what feels like a distribution problem is really a "does this OS build and run" problem that never needed a live OpenRouter key.
  • The receipt matters as much as the push. The current recovery flow already writes a receipt; a fleet version needs "which node holds which version of which logical ID, as of when" — otherwise you cannot answer whether a rotation actually completed.

This is a real scenario-sized piece of work, and it's genuinely unstarted — bridge lists it as OT-P2, and its integration table marks secrets-manager "optional (P2), seam only." Worth scoping deliberately rather than bolting onto either side.

Decided · 2026-08-24

Where we landed

Recorded so the plans can be written against it rather than re-deriving it. No plan has been authored yet — plan-manager holds 23 plans and none of them touch credentials, secrets, keyring, or fleet.

Decided

Durable node storage, with ephemeral as a retention mode

A shared credential lands durably in the node's own authority under that node's local wrap. Ephemeral delivery is not a second mechanism: sealing, transport, and scope are identical, and only the sink differs — the agent either hands the value to its authority or holds it for one job and zeroes it.

So retention is a field on a scoped grant. Bridge already has the in-memory-then-zero pattern to copy: its SSH first-touch holds an owner password for exactly one dial and zeroes it, with a test asserting the zeroing.

Decided

Ephemeral earns its keep on two cases durable can't cover

Infrastructure-class credentials — the ones whose rule is that they never ship. Ephemeral makes them usable for a single validation job without breaking the rule; durable-only forces a choice between "minimouse can't test this" and "the rule is void."

Short-lived or frequently-rotated tokens, where a durable copy is mostly a staleness liability.

Decided

Ownership splits three ways

Control plane owns the sealing and ingest primitive — it already owns the authority and the portable envelope. secrets-manager owns scope policy and the console. bridge contributes node identity and transport only, and its "secrets verb is never dispatchable" test stays exactly as it is.

Consequence to plan for: one initiative touches three codebases, so the contracts between them need naming before the first phase.

Decided

All cleanup lands first

Full cleanup pass before the fleet work — envelope consolidation, the missing tests, CLI reconciliation, the autoheal seam, the storeadmin split, and the renames.

One ordering note carried into the plan: put the renames last within that pass. They touch the same files the fleet work will rewrite, so landing them after the hardening keeps the churn where it costs least.

Decided

Migrate consumers off the login keyring

The structural option, not the opt-in. Remote-desktop credentials and other desktop-stack state move to the encrypted store, so the boot prompt becomes genuinely inconsequential rather than merely non-blocking — and a whole class of incidents this host has already had stops being possible.

Tracked as its own line of work: it is independent of both the cleanup and the fleet plans.

Newly required

Name the control-plane node kind

Not a decision you made — a precondition the reconnaissance turned up. Before any push can target "the fleet," the model has to be able to say which node is the source. This belongs at the front of the fleet plan, not in its polish phase.

Cleanup · duplication, drift, and polish

Where the same idea is implemented more than once

A second pass, looking only for redundancy rather than defects. The pattern that recurs: this stack was built carefully in several places at several times, and the places have started to overlap without anyone declaring which one is canonical.

Three AES-GCM envelopes, and the portable one is the loosest

Dedupe

Sealing plaintext with AES-GCM is implemented independently in secrets/recovery.go, securestore/keyprovider.go, and securestore/sealedfile.go. They share exactly one thing — the PBKDF2 iteration count, via the five-line credentialpolicy package — and nothing else.

The asymmetry is the interesting part. The key-wrap path binds additional authenticated data (wrapAAD(provider)), so a wrap cannot be lifted out of its provider slot and replayed elsewhere. The recovery envelope binds nothing. That is the portable artifact — the one that travels between machines, and the one your fleet plan would lean on hardest.

keyprovider.go:117 gcm.Seal(nonce, nonce, dataKey, wrapAAD(provider))
recovery.go:149 gcm.Seal(nil, nonce, plain, nil)

Do: lift one sealing helper — key derivation, nonce handling, AAD, versioned envelope header — into credentialpolicy (which is currently a constant wearing a package's clothes) and have all three call it. Bind the envelope's own version and purpose as AAD while you're in there.

Resolved · every remaining question

Ten decisions, and the one that reorders the work

Each carries a recommendation and the reason it beats the alternative. The last one was not on anyone's list — it came out of reading the pairing code, and it moves work to the front of the fleet track.

Was open

Real keys or fixtures on a node?

Fixtures by default. Real credentials only when the test asserts third-party behavior itself.

"Does ai-gateway start and route on darwin" is a fixture test. "Does OpenRouter answer a live model list with our key" is not. The split is per test case, not per credential, and it shrinks the population the distribution machinery must serve to the handful of cases that genuinely need a live secret.

Was open

Push or pull?

Control-plane push, node-side consent.

Pull would need nodes to poll, which the no-polling discipline forbids everywhere else in this codebase. And "push" here is not an inbound connection — it is a server frame on the channel the node already dials out and holds, so the NAT-proof property is untouched. The node still checks its own local grant before accepting, so consent stays on the node.

Was open

Why do 7 and 17 disagree?

Treat it as a defect, not a definition. One inventory becomes authoritative.

The root CLI's inventory becomes the single source; secrets-manager consumes it rather than computing its own. Until both surfaces answer from the same source, no coverage number can be an acceptance criterion — which is why this lands in the cleanup track before anything else depends on it.

Was open

Refresh the stale recovery bundle first?

Yes — it is step one, before any code changes.

The cleanup track's second phase rewrites envelope code. Doing that while the only good backup is 20 days old and missing 17 credentials — including all five Kopia repository passphrases, which are the keys to your other backups — inverts the risk order for no reason. It costs one command.

Surfaced

New enum value or a boolean flag for the control-plane node?

A new NODE_KIND_CONTROL_PLANE enum value.

The enum's own comment says kind describes which capabilities a node provides, and the control plane provides different ones — so this is the existing concept, not a new axis. A boolean would have to be consulted at every site that already switches on kind. The protocol's stated back-compat policy makes an additive enum value safe for the agent already running on minimouse.

Surfaced

Who decides, at push time, whether a node may hold a credential?

Grants are data in the control plane. secrets-manager authors them; the control plane enforces them.

secrets-manager never holds a value and never makes a runtime decision — it is the console that writes grant records through an API. Both the decision point and the enforcement point stay in the control plane, next to the crypto. That keeps the three-way ownership split from becoming a three-way trust dependency.

Surfaced

How does an ephemeral value reach the process that needs it?

Through the existing envkit boundary — and only for foreign processes.

The agent's privilege-separation runner already uses envkit.WithOverlay(…, ForeignScenario, …), which is the sanctioned way to hand a child process values it must not inherit. That is the same rule the credential descriptors already state: env is for processes Vrooli does not author; everything Vrooli writes resolves in-process and never touches the environment. No new mechanism, and the existing doctrine decides the case.

Surfaced

What happens to a durable copy when the source rotates?

Rotation fans out automatically, and every address carries a generation counter.

Rotating at the source re-pushes to every node holding a grant for that address. Nodes offline at rotation time receive it on their next channel connect. The generation counter is what makes "did the rotation actually complete" answerable — without it, a fleet-wide rotate has no honest success condition.

Surfaced · honest limit

What does revoking a node do to credentials it already holds?

It purges on receipt — and a node that never comes back keeps what it had.

Revocation stops further pushes, marks grants revoked, and instructs the agent to purge. But the control plane cannot reach into a machine that is gone. Durable distribution therefore has to be designed as compromise-on-revoke: the operator remedy for a lost node is rotating the credential, not recalling it. This is the single most important limitation to write down explicitly, because it is the one an operator will otherwise assume away — and it is an argument for keeping the durable population as small as the fixtures decision allows.

Surfaced · blocking

What key seals a credential to a node?

None exists yet. Add a per-node X25519 encryption key, distinct from the identity key.

Bridge's pairing stores exactly one key per node: an Ed25519 signing key, in a single public_key column, with the private half never leaving the node. Ed25519 signs; it does not encrypt. There is no key material anywhere in the fleet that can receive a sealed secret.

Ed25519 keys can be birationally mapped to X25519 for key agreement, and that is the tempting shortcut. Reject it: reusing one key for signatures and encryption is a well-known footgun, the conversion is subtle enough to get quietly wrong, and a separate key can be rotated without disturbing node identity. The node_credentials table already has the right shape to hold a second purposed row.

The consequence is a sequencing one. minimouse is already paired, so this needs a key-add exchange authenticated by the node's existing Ed25519 identity — not a re-pair. Build it that way and the same exchange becomes the encryption-key rotation path later.

Six conflicts, and how each is resolved

Conflict

Bridge says it never ships secrets. We are about to ship secrets.

Resolved: distribution is not a dispatch job. It is a separate typed channel frame governed by grants, not a verb in the dispatch allowlist. The secrets verb is never dispatchable test stays green and untouched, because the thing it protects — arbitrary remote invocation of credential commands — remains impossible. Record it in bridge's decision log so the next reader does not think the rule eroded.

Conflict

deployment-manager's classes describe deployment targets. Nodes are not targets.

Resolved: reuse the four class names as an intrinsic property of each credential; do not reuse deployment-manager's per-target plan mechanism or its code. A node grant then references a class. Same vocabulary, separate machinery — which is what stops two systems from having to agree on more than a word.

Conflict

Three surfaces own this, so who does a reader blame?

Resolved: control plane owns key material, sealing, grant enforcement, and ingest. secrets-manager owns grant authoring and the console. bridge owns identity and transport and holds no credential logic. Each of the three gets one sentence in its own docs naming what it does not own.

Conflict

test-genie owns runs. Where does injection happen?

Resolved: in the agent, before it execs the node's local vrooli CLI. test-genie is not modified and does not learn about credentials. The injection point is the same boundary the agent already crosses for every job.

Conflict

Host remediation belongs to the control plane, but autoheal models the keyring.

Resolved: the control plane exposes the derived keyring verdict it already computes; autoheal consumes that and deletes its journal-marker constant. Autoheal keeps observing and reporting, which it is entitled to do. Only the derivation moves.

Conflict

Two CLI front doors reporting different truths.

Resolved: the root CLI owns store lifecycle, recovery, and the authoritative inventory. secrets-manager consumes that inventory and adds coverage, campaigns, and the console. Counts become self-describing — a number always says whether instances are included.
