01

What the environment actually is

There is no queryable source of truth for what a scenario receives. There is a code source of truth: BuildEnvironmentWithRuntimeClaims in internal/ports/ports.go:174. Five sources merge in order, each overwriting the last, and the whole result lands on top of the inherited parent environment.

02

Two names, two meanings, one namespace

API_PORT and AGENT_MANAGER_API_PORT are not two spellings of one variable. They answer different questions.

NameReferenceMeansResolved by
API_PORT relative “the API port of the scenario this process belongs to” context — who am I?
AGENT_MANAGER_API_PORT absolute “agent-manager’s API port” the name itself

Environment is a flat, transitively-inherited, unscoped dictionary. That medium carries absolute names correctly. It cannot carry relative ones, because the context that resolves them isn’t transmitted — it was decided by an ancestor, and every exec since has preserved the value while changing the context. This is a category error, and it is observable on the host right now.

Live process 2468907 — qdrant
SCENARIO_NAME=infrastructure-manager
SCENARIO_PATH=/home/matthalloran8/Vrooli/scenarios/web-console
SCENARIO_DATA_DIR=.../scenarios/web-console/data
VROOLI_SCENARIO_DIR=.../scenarios/web-console
# VROOLI_SCENARIO absent entirely — the builtin set is torn
OLLAMA_BASE_URL=http://localhost:11434   # qdrant declares no ollama dependency

Two ancestors each answered “who am I?” and each overwrote a partial slice of the relative set. Neither assembly was buggy; the result is incoherent anyway. A second live instance shows minio carrying browser-automation-studio over web-console paths.

Why the generic name must survive

The tempting fix — use the prefixed name everywhere — is wrong. API_PORT=18800 inside the agent-manager API server is exactly correct: a server binding its own listener should not know its own name. Templates, generated scaffolds, and shared api-core all depend on that. Both names are legitimate. Three things are broken:

  • Only the relative name is injected, so every absolute lookup misses and falls through to a fork.
  • Nothing states which name answers which question — so AGENT_MANAGER_API_PORT is used with both meanings. StandardScenarioEnv derives it as self; park.go and identity.go hardcode it as other. For ports these coincide numerically. The same derivation produces _API_TOKEN and _CONFIG_DIR, where they do not.
  • Relative names survive exec boundaries where they become false.

The comment that was a workaround

// Avoid the generic API_PORT to prevent cross-scenario port leakage; rely on
// per-scenario env vars and the port detector instead.

cliapp/scenario_env.go:38. Not a design decision — one library privately compensating for a missing inheritance rule, invisible to the injector it defends against. It is also what makes the fast path permanently dead, and therefore what causes the fork.

03

Three propagation classes

“Lifetime” is really two properties. Extent is how long a binding stays valid; propagation is whether it crosses an exec boundary and which kind. The fix is to make both declared properties rather than accidents.

ClassExamplesPropagationExtent
Relative / self API_PORT, UI_PORT,
SCENARIO_*, VROOLI_SCENARIO*		 replaced at any scenario boundary — never merely inherited process
Absolute / peer POSTGRES_URL,
<SLUG>_API_PORT		 free, but provisioned by declared need scenario run
Delegated credential VROOLI_AGENT_
IDENTITY_TOKEN		 deep within a delegation subtree only bounded by exp

The middle row’s qualifier is the qdrant evidence — free propagation is not a licence for indiscriminate provisioning. The third row is where “never removed at the right time” stops being hygiene: a bearer token outliving its run is a different severity than a stale port. It is also the clearest case for rule-based rather than drain-everything, since the identity token must cross boundaries the relative set must not.

A fourth group deserves naming: inbound harness observations (CLAUDE_CODE_SESSION_ID, CODEX_THREAD_ID), which identity.go already marks as “observations, never identity proof.” Their rule is inbound-only — never re-emitted as identity.

The API shape this implies

A Set/Unset utility preserves the current failure mode: someone must remember to unset. There are 163 cmd.Env = sites and six separate mergeEnv* helpers, every one allow-by-default. The primitive should be deriving a child environment from a declared relationship, with dropping as the default.

Current — six variants of this
stepEnv := mergeEnv(os.Environ(), overrides)

// allow-by-default: the child receives
// every relative name its parent held,
// including ones that now describe
// a different scenario.
Target — envkit-go
env := envkit.ForChild(parent, envkit.Resource)

// deny-by-default. Relationship selects
// the propagation policy:
//   SameScenario    keeps the relative set
//   ForeignScenario replaces it
//   Resource        drops it
//   DelegatedAgent  identity yes, self no

Portability is the real argument for shared code

  • Case sensitivity. Windows env names are case-insensitive; POSIX is not. All six helpers use strings.HasPrefix(entry, key+"="). On Windows a parent’s Path plus an overlay’s PATH yields two entries with undefined precedence.
  • You cannot drop everything. Windows process creation needs SYSTEMROOT, COMSPEC, PATHEXT, TEMP, and hidden =C: drive-cwd entries. Deny-by-default breaks there without a platform floor set — knowledge no individual call site should carry.
  • Block limits. Windows caps the environment block; unbounded accretion across nested spawns fails process creation outright rather than degrading.

Ports were never an environment question

Keep the declaration, drop the projection

dependencies.scenarios carries two separable things. The declaration — required, startup_policy, the edge itself — governs ordering, admission, and graph visibility. It is not stale, and it is what validation checks against. Keep and enforce it. The bindings[].env_var projection freezes a dynamic address into a variable. Delete it.

Measured: the fork was never necessary

runtime_registry.go:381 writes a record unconditionally for any scenario with a durable process, and peerrecord.Read rejects records whose owner is dead — so the 43 records against 25 running scenarios self-clean on read rather than lying.

Limits of this measurement

Records hardcode Tier: 1, so this covers local peers only; remote still needs the bridge relay. The 9.216 µs is warm page cache. The SQLite fallback used when a record is absent was not measured.

Validation: what exists, and the precedent that already works

What env_validation covers

The rule lives in structure-health and backs test-genie’s Structure phase. It handles Go, Bash, and JS/TS with three violation types: read-without-validation (medium), sensitive-value-logged (high), and dangerous-default-on-a-critical-var (high). It is strict and good.

Two limits matter.

Limit 1 — the message names only the symptom

// content and path only. It physically

Satisfiability is one central check, not per-scenario validation

“Can the system ever supply this variable?” is a property of the (code, manifest) pair, evaluated once, centrally. Scenarios do not each implement it. The existing read-site discipline stays exactly as it is — the point is that passing it does not imply the configuration is possible.

vrooli-autoheal is fully rule-compliant and permanently impossible: it fails loudly with “must be set by the lifecycle system” while declaring no resources, so nothing can ever set them. Loud-but-impossible is still broken.

The precedent: ai-conformance

This shape is already built. The ai-conformance phase is descriptor-backed by ai-gateway, applies only when a target declares an AI capability, and reports capability ladders with findings that cap a capability until cleared.

FindingCapabilitySeverityFails phase
ai.invalid_provider_secret_envresource_boundaryerroryes

Note what ai.invalid_provider_secret_env is: “you are reading a provider’s environment variable directly instead of going through the boundary that owns it.” That is exactly the check we want for postgres, redis, and qdrant.

So the environment work should be a sibling of ai-conformance, not an extension of env_validation — which is content-only and cannot host it anyway. The phase already uses a remediation-doc skeleton where a scorecard topic resolves to the exact remediation section, so guidance lives in versioned docs rather than string literals. It also already models honest non-failing debt: WARNING and INFO findings are real signal without blocking.

Message design

State what, why, and both exits — without prescribing. Every value below is derived, never hardcoded; see §07.

undeclared resource producer

POSTGRES_HOST is read in api/internal/config/config.go:46 but postgres is not declared in this scenario’s .vrooli/service.json. POSTGRES_HOST is injected only when postgres is declared under dependencies.resources. If this scenario uses postgres, add the dependency. If it does not, remove the read.

shared package bypassed

POSTGRES_HOST, POSTGRES_PORT, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB are read directly in api/internal/config/config.go:46-50 to build a connection string. api-core declares ownership of the postgres resource environment and already handles POSTGRES_URL/DATABASE_URL precedence and POSTGRES_SSLMODE. Adopt it, or record a reviewed exception.

cross-scenario address in the environment

AI_GATEWAY_URL is read in api/main.go:88. Nothing in the system sets it, so this read always falls back to its default. A scenario’s address is resolved at call time through api-core/discovery, which stays correct across peer restarts and works across tiers. Replace the read with a discovery call and declare ai-gateway under dependencies.scenarios.

producer resource does not exist

N8N_BASE_URL is read in api/main.go:936. There is no n8n resource in this repository. This read cannot succeed; remove it along with the code path it feeds.

no producer anywhere

BAS_SIDECAR_STARTUP_TIMEOUT_MS is read in api/internal/sidecar/run.go:52 and is set by nothing in the repository — it always takes its fallback, and no operator or end user can change it. Scenario-tunable values belong in <scenario>/.vrooli/config.json, where they are schema-checked and reachable from UI settings.

07

The resolver: two layers, no drift

Every message above names a producer, a package, or a mechanism. None of that may be hardcoded in the validator — a table of POSTGRES_HOST → api-core/database would recreate exactly the drift this whole document is about. Both layers derive from artifacts that already exist.

Layer 1 — derivation. No new configuration.

one shared util answering “who can produce X?”
resources/*/resource.json  → environment_exports{static, from_ports,
                               from_runtime_env, derived}    → var → resource
scenarios/*/service.json   → ports[*].env_var                → var → scenario port
scenario slug set          → <SLUG>_*                        → var → scenario (absolute)
internal/ports             → builtins                        → var → lifecycle

If postgres adds an export tomorrow, the resolver picks it up with no edit anywhere. This is what makes drift structurally impossible, and both the validator and any runtime helper consume it. repo-contract-go is the right shape to extend or mirror. Do this unconditionally.

Layer 2 — package ownership. One field, holding resource names.

The “adopt api-core” message needs to know which package owns a resource’s environment surface. The machinery for this is already built: structure-health’s catalog carries 71 rules across eight target kinds —

rules/catalog.go — TargetKind distribution
scenario 24 · project 17 · package 13 · team 4 · resource 4 · tool 3 · safeguard 3 · docs 2

— and 37 packages already carry a .vrooli/package.json governance manifest with an adoption block. There is even a PACKAGE_CONSUMER_CLASS_VIOLATION rule that discovers consumers and validates them against declared classes. The addition is one field:

Today — packages/api-core/.vrooli/package.json
"adoption": {
  "scenario_adoptable": true,
  "allowed_consumers": ["scenario_api", …],
  "adoption_modes": ["go_module_replace"]
}
Proposed — one field added
"adoption": {
  "scenario_adoptable": true,
  "allowed_consumers": ["scenario_api", …],
  "adoption_modes": ["go_module_replace"],
  "owns_resource_environment": ["postgres"]
}

Why this is drift-free

The field holds a resource name — already an SSOT identifier — never a variable name. The variable list stays derived from that resource’s environment_exports. So the validator hardcodes nothing, the package manifest hardcodes nothing, and when no package claims a resource the message degrades honestly to the generic form (“declare the dependency and read the derived REDIS_URL”) rather than inventing advice.

09

Tier semantics: seamless local, explicit remote

The addressing grammar already encodes the intended behaviour. SplitAddress parses [node/]scenario[@variant] — the node prefix is optional.

AddressRouteExplicitnessStatus
agent-managerlocal port lookupseamless — no ceremonyworks
agent-manager@shadowlocal, variant-scopedseamlessworks
node-b/agent-managerbridge relay, scope-admittedexplicit — the prefix is the flagunwired

Cross-machine calls carry authenticated relay, scope admission against the derived catalog, and bounded responses. Local calls carry none of that ceremony. The distinction is structural rather than a runtime flag, which is stronger — you cannot reach another machine by accident.

The remote half is a capability, not a live default

TargetResolver and Relay are optional config fields on ResolverConfig, and nothing in the repo injects them. Any node-addressed call today returns ErrRemoteTransportUnavailable — “target resolver is not configured”. The design is right and the failure is clean, but tier transparency is architecturally true and operationally conditional until this is wired.

Still open

  • SQLite fallback cost — unmeasured. Used when a peer record is absent; if expensive, phase 1 needs a caveat for the cold path.
  • Non-Go consumers. Shell lifecycle steps read 473 distinct names, vite configs 165, Python 45. None can link api-core. They need a fork-free CLI verb or language siblings — and shell is both the largest surface and the least statically tractable. The biggest unscoped piece of work here.
  • Language parity. repo-contract-go is the model for the resolver, but it has no non-Go sibling — the multi-language half of that standard is aspirational, not proven.
  • Declared-but-unused validation. Only sound with multi-component scanning; a Go-only scan would report vite- and shell-consumed variables as dead and invite deleting live declarations. Ship the used-undeclared direction first.
  • Phantom conventions. OLLAMA_ROLE and OLLAMA_EMBEDDING_ROLE are read by four scenarios, produced by nothing, and always fall back to a default. Either scenario config or part of ai-gateway’s typed-inference contract — a decision to make once, not per-scenario.
  • How much residual is dead code? The N8N_BASE_URL case suggests a real deletion tail currently counted as migration work.
