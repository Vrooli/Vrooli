01

What the ramp already shipped

The scenario-to-plugin plan completed, and it moved more of this problem than I expected. Verified in the working tree:

  • The top-level skills/ tree is gone, along with docs/skills/ and the dead scenario-to-mcp scenario. The publication doctrine now lives inside the ramp at scenarios/scenario-to-plugin/docs/concepts/SKILL-PUBLICATION.md.
  • The plugin declaration schema exists. .vrooli/schemas/service.schema.json now carries a plugin key: "Absence means this scenario is not publishable." That is the scenario↔skill link that was missing everywhere.
  • Scenarios now own their skills. scenarios/hello-plugin/skills/hello/SKILL.md and scenarios/workspace-sandbox/skills/sandbox/SKILL.md both exist — one folder per skill, with valid YAML frontmatter, in the location the Agent Skills spec expects.
  • The drift gate is real code. api/handlers/pipeline/conformance.go reads the wrapped scenario's cli/manifest.json, resolves every command in the skill body against it, and emits PLG-CONF-DRIFT when a command — or even a flag — is absent, pinned to a recorded manifest revision.
Recommendation already delivered

Rev 1 of this review argued that the separate skills/ publication tree should collapse into the ramp, and that skills should live with the scenario they describe in spec format. Both are now the shipped convention. Everything below builds on that rather than proposing it.

The publication doctrine now describes the shipped topology: scenario-owned scenarios/<slug>/skills/<id>/SKILL.md sources, prompt-manager's governed packs, the inactive vendor pack, registry resolution, bounded native projection, and signed publication. It is one skill format with several governed surfaces, not two competing skill systems.

02

What remains governed

The authored corpus is spec-format files, not database rows — prompt-manager practice packs and scenario-owned skills/<id>/SKILL.md folders. SQLite is an index over them. skill.json is generated compatibility metadata, not a second authored source.

All 143 authored prompt-manager skills now carry the same specification frontmatter as scenario-owned skills. The open Agent Skills specification fields (name, description, license, and optional runtime fields) are at the top level; Vrooli-private fields remain under metadata (modes, targetDimensions, programmaticHome, writes_to). The generated skill.json sidecar preserves compatibility for existing registry consumers.

The remaining distinction is ownership and governance, not format: scenario-owned skills travel with their scenario, repo-wide practice skills remain in prompt-manager, imported skills stay quarantined until review, and native projection exposes only the bounded pack selected for a runtime.

No import lane, and importing is the dangerous part

still unbuilt

prompt-manager skill exposes list · show · read · add · update · delete · sync · rate · versions · revert · variants. There is no import, and nothing in skill.json can record where a skill came from — no source URL, no commit, no license, no checksum, no importer, no review verdict. An imported skill would be indistinguishable from one you wrote.

The external evidence says that gap is the whole game. Snyk's ToxicSkills audit scanned 3,984 registry skills: 36.8% carried at least one security flaw, 13.4% a critical one, 76 confirmed malicious payloads. ClawHavoc poisoned 1,184 skills before remediation began. And Trail of Bits bypassed every public skill scanner inside an hour — one researcher-built malicious skill reached 26,000 agents while every scanner cleared it.

Design consequence

Scanners are a filter, never a gate. An import lane whose safety story is "we scan it" is not safe. The gate has to be quarantine by default: imports land inactive, are never projected into a session, and require a recorded human verdict against an immutable origin record before activation.

The ramp's SECURITY-POSTURE.md now owns the outbound posture. Inbound has no owner at all, and it is the higher-risk direction — outbound risk is your reputation, inbound risk is your host.

The corpus rides along with any distribution

monetization blocker

Because the 143 authored skills are git-tracked files inside prompt-manager, a tier-2 install could ship all of them. 106 reference vrooli scenario, swarm-manager, test-genie, or prompt-manager skill read — commands a standalone buyer does not have. And 61 distinct cross-skill skill read <id> edges mean shipping a subset is not a matter of deleting folders; you would break references.

The fix is now cheap, because the mechanism exists: conformance.go already resolves documented commands against a target's cli/manifest.json. Point that same check at a tier-2 bundle's CLI surface and "which skills may ship?" stops being a judgment call. This is the same failure mode Skills Are Not Islands measures at registry scale — dependency-bearing artifacts with implicit provenance. Your corpus has the dependency graph; it just isn't declared.

03

Projection: does it actually cost context?

You were right to push on this. The answer is yes, but only the descriptions — and it is consistent across the harnesses that matter, because they all implement the same three-tier progressive disclosure the spec defines.

RuntimeAt startupOn activation
Claude CodeScans every skill dir, loads name + description only — ~100 tokens eachFull body, <5k tokens
Codex CLIDiscovers .agents/skills, keeps descriptions in context for matchingBody, lazily
Spec baselinename + description for all skillsInstructions, then resources

There is direct evidence in this session, which you can check yourself: my own system prompt carries an enumerated list of available skills, each with a one-line description, none with a body. That is the startup tier, visible in the wild. It is not a "list them when asked" tool — the descriptions are resident so the model can match without a round trip.

Which makes the arithmetic decisive:

So your instinct — a few always-projected, the rest per-profile — is the right shape, and it is the shape the token math independently arrives at.

Per-run projection is an env problem, not a directory problem

You worried this would mean hooking each harness's skill-reading command. It doesn't — there is no read to intercept, only a filesystem to prepare. But which filesystem is the whole design, and Vrooli's setup rules out the obvious answer.

Both harnesses read two scopes. Claude Code's order is enterprise → personal (~/.claude/skills) → project (.claude/skills) → plugin; Codex reads repo .agents/skills alongside the home equivalent. The tempting move is to write each run's pack into the project scope, since agent-manager already launches every run with a WorkingDir.

Why that fails here

Vrooli runs many agents concurrently in one checkout, without worktrees. Both discoverable scopes are therefore shared: one project directory, one home directory, many sessions. Writing a per-run pack into either means the last writer wins and every other live agent silently sees another agent's skill set. Hot-reload makes this worse rather than better — it removes the process-start boundary that would otherwise contain the damage, so a mid-run injection reaches every concurrent session within seconds. Any design that scopes skills by filesystem location is wrong for this setup.

The scope has to move with the process instead. Both runtimes root their user scope at an env-var-controlled directory: Codex resolves everything under CODEX_HOME (your own resources/codex/resource.json already documents this — "state, sessions, configuration, memories, and authentication are rooted at CODEX_HOME"), and Claude Code honours CLAUDE_CONFIG_DIR to relocate ~/.claude wholesale. Give each run its own config dir and each run gets its own user scope, on the same checkout, with no worktree.

That seam already exists. phases.AssembleRunEnv merges custom, sandbox, and identity env per run — and system vars deliberately override custom ones, which is exactly the precedence a skill scope needs, since a run must not be able to widen its own. Adding a skill-scope source there is a small change to a mechanism agent-manager already relies on.

Measured, not assumed — Claude Code 2.1.241, 2026-08-23

I ran the experiment rather than leaving it as a risk. Four canary skills across two config directories and one project directory, five headless runs. All three properties the design depends on hold.

CheckMethodResult
Skills follow the relocated config dir Canary at $CFG/skills/zzprobe-canary-alpha/, asked a headless run to enumerate its skills yes — canary listed with CLAUDE_CONFIG_DIR set, absent from the otherwise-identical control
Concurrent runs stay isolated Two config dirs, two different canaries, launched simultaneously from the same working directory yes — each run saw only its own canary, neither saw the other's
Shared project scope still layers Project canary at <cwd>/.claude/skills/ with the config dir relocated yes — both the private and the shared canary were visible in one run
Mid-session hot-reload in a private scope — untested — headless -p is one-shot, so an in-flight rescan cannot be observed this way

That third row is the one that matters most: the two-tier model is not a theory. A base pack in the shared project scope and a profile pack in a per-run config dir compose, and the per-run half is invisible to every other agent on the same checkout.

What else moves — answered the hard way

The first run failed with Not logged in · Please run /login. Credentials relocate with the config dir, and so does session state: the runs created projects/, sessions/, and backups/ inside the relocated directory, with each transcript written under $CFG/projects/<encoded-cwd>/<uuid>.jsonl. Two consequences for agent-manager. It must seed or link .credentials.json into every per-run dir, or every run starts logged out. And its transcript-import path must read from the run's own config dir, because transcripts no longer land in ~/.claude/projects — a per-run scope silently breaks transcript import otherwise.

A scenario's skills/ folder is not a discovery path

Worth being precise, because it is easy to assume otherwise: scenarios/<slug>/skills/ is package source. It matches the layout Agent Plugins expects inside a plugin (plugin.json + skills/), which is why the ramp puts it there. No harness discovers it, at any working directory. The discovery paths are .claude/skills and .agents/skills, and a bare skills/ is neither.

Claude Code does document nested discovery — editing a file in packages/frontend/ triggers a scan of packages/frontend/.claude/skills/ — so a per-scenario runtime scope is theoretically reachable at scenarios/<slug>/.claude/skills/. But it is on-demand rather than upfront, and there are open issues reporting it silently skips subdirectories even after files there are read and edited. Treat nested discovery as a bonus, not a mechanism: project into the project-root scope, which is reliable, and let per-scenario scopes be an opportunistic addition once the base works.

Hot-reload: a liability in a shared scope, an asset in a private one

Claude Code 2.1.0 added automatic skill hot-reload — skills created or modified in ~/.claude/skills or .claude/skills become available mid-session with no restart. Whether that helps depends entirely on the scope decision above, and it cuts both ways:

  • Against a shared scope it is a hazard, and the reason the project-directory approach cannot simply be accepted with a warning. Without hot-reload, a stray write only affects sessions started afterwards; with it, the write lands in every running agent.
  • Against a per-run scope it is exactly the mechanism the heartbeat case needs. A member heartbeat that decides its member now needs a skill writes into that run's own config dir, and only that run picks it up.

So hot-reload doesn't change the recommendation — it raises the cost of getting the scope wrong and raises the payoff for getting it right. Two caveats bound it either way: skills delivered as a plugin are reported not to reload, and there is an open bug where available-skills context is not re-injected after a plugin upgrade — so injected skills should be plain directories, not plugin packages. And it is a Claude Code capability, not a cross-harness guarantee, so the launch-time pack must still be correct for runtimes that scan once.

The precedent works, and shows exactly what to fix

vrooli-memory already does this for memory, and the seam is well-shaped: api/internal/harness/projection.go holds a Projector with a per-runtime target table — path, byte cap, line cap, section markers — and a Project(ctx, runtime, dryRun) entry point covering claude-code, codex, gemini, grok, and antigravity. Skill projection is the same operation against a directory instead of a file.

Two things it gets right and one it gets wrong, and the wrong one is precisely your concern:

  • right The curated-instruction topology is data-driven — curated-files.json, embedded, with canonical AGENTS.md plus workspace and home aliases.
  • right Projected regions are marked and generated (vrooli-memory:wake:start/end), so hand edits and generated content never fight.
  • wrong The projection target map is hardcoded in Go — and one entry contains the literal path ~/.claude/projects/-home-matthalloran8-Vrooli/memory/MEMORY.md. A machine-specific string compiled into a scenario binary.

So build the skill projector on this pattern, and take the target map out of Go. The natural home is the coding-agent resources, which already declare exactly this: resources/claude-code/resource.json declares $USER_HOME/.claude as the runtime home with a typed path table beneath it, and resources/codex/resource.json does the same for $USER_HOME/.codex. Five such resources exist — claude-code, codex, opencode, antigravity, grok. Adding a skills path entry per resource gives you the data-driven projection map you described, makes a new harness a data change rather than a code change, and gives vrooli-memory somewhere to retire its hardcoded table to.

04

The target: one source, four planes

Separate four things that "the skills folder in prompt-manager" currently fuses: where a skill is authored, what indexes and governs it, where a runtime reads it, and what gets published. Storage is the authoring plane only. Everything else is generated, never hand-maintained.

Plane 1 · Authoringpartly done

Skills live next to what they steer

Now the shipped convention for publishable skills. Extend it inward: a skill about a scenario's interface moves to scenarios/<slug>/skills/<id>/ so it versions with the code it describes. Repo-wide practice skills — triage, writing standards, planning — have no owner scenario and stay in prompt-manager. Imports land in a separate vendor root, never edited in place.

Plane 2 · Registryto build

prompt-manager indexes roots, stops owning bytes

It keeps what makes it valuable — search, variants, experiments, ratings, telemetry, the authoring quality bars — and gains a multi-root scan. Smaller than it sounds: memberflow/prose_scan.go already walks <configDir>/skills/packs/** across scan roots.

Plane 3 · Projectionto build

Generate skill dirs per scope

An always-on base pack in the shared scope, plus a per-run profile pack in a private config dir the run's env points at — because many agents share one checkout, the scope must travel with the process, not the path. Targets come from the coding-agent resources, not from Go. Generated, gitignored, rebuilt on change.

Plane 4 · Publicationshipped

scenario-to-plugin packages what the scenario owns

Declaration schema, composition, drift gate, attestation, clean-room rehearsal, gate-bound publication. Because the skill already sits in the scenario in spec format, composition is a copy plus a manifest.

Format: adopt the spec, keep your extras where they belong

Frontmatter is the single source of metadata truth, matching the 12 scenario-owned skills currently in the tree. Spec fields (name, description, license, allowed-tools, compatibility) are at the top level; everything Vrooli-specific stays under metadata:, which the spec leaves open and conformant runtimes ignore safely. skill.json is generated compatibility metadata, not authored source.

Two additions to metadata pay for themselves immediately:

  • requires: — the scenario slugs and CLI commands this skill needs. This is what feeds the existing drift gate and turns "which skills may ship to tier 2" into a query.
  • origin: — for vendored skills: source URL, commit SHA, SPDX license id, checksum, importer, review verdict, upstream version. Immutable. This is your attribution and provenance record, and also your freshness record — when upstream moves you can tell which vendored skills went stale.

Local changes to a vendored skill should be an overlay or patch, not an edit; otherwise the next upstream update forces a manual three-way merge and, in practice, never happens.

On moving skills into scenarios — mostly yes, and it is a spectrum

Move a skill when its content is about a scenario's interface. Roughly 11 core skills are already named for one (api-steer, storage-steer, cli-steer, knowledge-observatory-tools, visited-tracker-tools, swarm-manager-backlog-tools…), and the 106 that name internal CLIs are the population to triage. Skills that encode judgment rather than an interface — triage methodology, skill authoring, systematic exploration — have no owner scenario and should stay central. Forced ownership is worse than none.

The 61 cross-skill edges are the migration hazard. They resolve today only because everything shares one namespace. Before moving anything, those references must resolve through the registry by skill id rather than by storage location — which is also what makes projection and publication possible.

05

Six decisions the plan needs

Each of these was open before writing the plan. Each is now investigated, with a recommendation and the evidence behind it.

D1 · The frontmatter schema carries everything

I checked whether the migration is a chance to prune. It is not: every one of the 19 on-disk keys is read by at least two non-test Go files — kind by 13, status by 20, down to writes_to, defaultScope, targetDimensions, and programmaticHome at 2 each. Nothing is vestigial.

Decide: spec fields at the top level (name, description, license, allowed-tools); every existing Vrooli key moves under metadata: keeping its current name; add requires and origin. Do not rename anything during the migration — a rename is a separate, revertible change, and bundling it into the authored-corpus rewrite makes both harder to review. entry is the single deletable key, since the spec fixes the body at SKILL.md.

D2 · Generate skill.json, don't delete it

17 non-test Go files read the current shape, and all their fields stay live. Decide: during migration, write frontmatter as the source of truth and generate skill.json from it, so all 17 consumers keep working untouched. Retire the sidecar per-consumer afterwards. This turns one large irreversible change into a safe change plus an unhurried cleanup lane, and it means step 1 can land without coordinating 17 call sites.

D3 · The real risk is telemetry, not variants

I had this wrong, and the correction matters. Variants are not endangered by projection: read.go gates variant selection behind an explicit experiment ID, with the comment "Organic reads remain observational and must never be silently assigned treatment." Experiments pass IDs deliberately and can keep using the CLI. Nothing breaks.

What breaks is counting. The read is the telemetry point. Every skill read fires ReadRecorder.Record → RecordUsage, writes skill_reads and discovery_calls, and records exposure receipts with run, execution, node, and attempt attribution. The header comment on read_telemetry.go says why it exists: UsageCount was previously incremented only by an explicit command, so it undercounted, and skill-optimizer's "high usage" selection rung was unpowered.

Projection reintroduces a bug you already fixed

A projected skill is read off disk by the agent. prompt-manager never sees it. Usage counts stop incrementing, discovery attribution goes dark, and skill-optimizer's high-usage rung is unpowered again — precisely for the base-pack skills, because you project the ones that get used most. Worse than the original bug: those skills will report zero reads, which reads as "unused" rather than "uncounted", and the natural response to an unused skill is to retire it.

Decide: ship an activation hook in the same step as the first projection, not later. Skill activation is a tool call, so a PreToolUse hook matching the skill tool can report it to prompt-manager. The infrastructure already exists on this host — ~/.claude/settings.json carries PreToolUse hooks with Bash and * matchers, and ~/.claude/.vrooli-hooks/ holds a working hook script. This is an addition to a running system, not a new one. Until the hook exists, mark projected skills in the usage report so nobody reads a zero as a verdict.

The hook must be fail-open and time-boxed. It sits in front of every skill activation; a prompt-manager that is slow or down must degrade to "no telemetry", never to "the agent waits" or "the activation fails". Telemetry is worth a best-effort call, never a blocked turn.

D3b · Resolve experiments at pack composition, not at read

The tempting extension is to use the same hook to substitute content — serve a variant to 30% of reads. It is mechanically possible: PreToolUse can return hookSpecificOutput.updatedInput to rewrite tool arguments and additionalContext to inject text (PostToolUse cannot — it observes a completed call and cannot replace its result). But it is the wrong unit, and prompt-manager's own schema says so.

QuestionSubstitute at readResolve at composition
Randomization unitEach read — one agent can see control and treatment in a single sessionThe run, matching experiment_assignments' own key
Hot pathEvery activation waits on a local callOnce, at launch, before the process starts
If prompt-manager is downSilent reversion to control mid-experiment, unevenlyLaunch fails loudly or proceeds with the base pack
ReproducibilityA rerun can draw differentlyAssignment and content hash are recorded up front

experiment_assignments is keyed on execution_id, node_id, and attempt_key — not on a read — and it stores content and content_hash at assignment time. The design already decided that a variant is assigned to a run and frozen. Per-read substitution would contradict the table it is meant to populate.

Decide: the projector asks prompt-manager for the run's assignment when it composes the pack, and writes the assigned content into the run's private scope. A 30% exposure rate means 30% of runs, not 30% of reads — same rate, clean units, no service in the hot path. And the long tail keeps working unchanged: skills read through the CLI already resolve variants server-side, so the only set needing pre-resolution is the projected set, which is exactly the set you can resolve in advance.

D3c · The assignment seam you described is already built — for prompts

Your instinct is right, and it is better than a hash. agent-manager's workflow runtime already carries this exact shape:

PieceWhere it lives
PromptAssignmentIdentity{ExecutionID, NodeID, AttemptKey, IdempotencyKey}workflowruntime/engine.go
PromptResolver.Resolve(ctx, ref, assignment) → PromptResolution{ExperimentID, VariantID, Content, ContentHash}same
Resolution frozen onto the attempt, then passed to the child as VROOLI_WORKFLOW_{EXPERIMENT,VARIANT}_IDorchestration/workflow_execution.go
experiment_assignments(experiment_id, skill_id, variant_id, execution_id, node_id, attempt_key, idempotency_key, content, content_hash)prompt-manager SQLite

Note what that is: not a deterministic hash but an idempotency-keyed assignment record. Ask once, store the answer, and every re-ask returns the stored answer rather than recomputing. That beats hashing on three counts — arm weights can change mid-experiment without re-bucketing units already assigned; the served content is frozen alongside the choice, so editing a variant mid-run cannot change what a running agent was given; and it is auditable, because you can read what was served instead of recomputing what should have been.

Two experiment surfaces exist, and they disagree

The mature one arms a prompt on a workflow node: assignment-keyed, frozen, agent-manager-driven. The immature one lives in skills/read.go and fires a rand.Float64() weighted draw per call, with no assignment record — so two reads in one session can legitimately land on different arms. experiment_assignments has 0 rows; the durable half has never been exercised. This is why skill experimentation feels unclear: the skill path is a second, weaker design sitting beside a finished one.

Decide: the skill surface adopts the prompt surface's model rather than inventing a third. Generalize PromptAssignmentIdentity to an assignment identity that also covers non-workflow runs (where the key degrades to the run id), have pack composition call that same seam, and write the experiment_assignments row with frozen content. Then remove the per-call random draw from the read path, or restrict it to an explicitly requested one-off read. Projection makes this natural rather than harder: composing a pack happens at precisely the boundary where PromptResolver.Resolve already runs.

"30% of the time" then means 30% of assignment units — the draw happens once, when the unit is assigned, and every read by that agent returns the stored arm.

D4 · Split the projector on what each scenario already owns

Decide: prompt-manager composes packs — it owns the corpus, the telemetry, the variants, and the quality bars. agent-manager writes a pack into the run's scope and owns the env that points at it, since it already owns AssembleRunEnv and the run lifecycle. The path map lives in the coding-agent resources. The write mechanics are shared with vrooli-memory/harness, which is the same operation against a directory instead of a file. Neither scenario has to learn the other's domain.

D5 · Whoever creates a per-run config dir deletes it

Decide: agent-manager owns the lifecycle, so agent-manager reaps — removal bound to the run reaching a terminal state, plus a sweep for orphans left by crashes. This is not hypothetical bookkeeping: this host has reached 100% disk once, and ~/.vrooli/bin is append-only in practice because nothing was ever given the job. A per-run directory holding transcripts and session state, created once per run with no owner, is the same shape of debt. Give it an owner in the plan.

07

What I could not settle

  • Whether mid-session hot-reload works inside a per-run config dir. The one property the experiment could not reach, because headless runs are one-shot. It only affects heartbeat injection into a live run — the launch-time pack works regardless — so it can be settled during step 3 rather than before it.
  • Which parts of the config dir stay shared. Credentials must be linked in or every run starts logged out. Transcripts, sessions, and backups now land per-run, which is arguably an improvement for attribution but changes what agent-manager reads. Settings and plugins are a genuine choice: shared keeps behavior uniform, per-run allows profile-specific permissions.
  • Whether CODEX_HOME behaves the same way. The Claude Code result is measured; the Codex equivalent is inferred from its documented rooting. Same experiment, second runtime — cheap, and worth doing before the resource-declared map claims to cover both.
  • Whether per-scenario runtime scopes are worth chasing. A scenarios/<slug>/.claude/skills/ scope would let an agent working inside a scenario see that scenario's skills automatically — but nested discovery is on-demand and has open reliability issues. Cheap to try after the base pack works; not something to design around.
  • What belongs in the always-on base pack. The token math says 8–15. Which ones is a judgment about which reflexes must fire without being asked — the situational-loading table in AGENTS.md is the obvious starting list.
  • Whether the registry caches scenario-owned skills or only indexes them. Indexing is cleaner; caching is faster and survives a scenario being absent. I lean toward indexing with a rebuildable cache.
  • Licensing for your own published skills. The forming norm is CC BY 4.0 for prose plus a code license for bundled scripts. Worth deciding before the first curated-registry submission, not after.
  • Agent Plugins durability. The ramp's own decisions flag it: the standard is weeks old, Anthropic is not on its steering committee, and Claude Code keeps an incompatible .claude-plugin/plugin.json. The pluggable distributor seam is the right hedge and is already in the contract.
