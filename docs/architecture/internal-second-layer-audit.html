Vrooli control plane branch agi · 2026-08-26 second-pass audit

The Second Layer of internal/

A 13-phase consolidation plan just completed on this tree. It did what it said: one CLI shape, typed JSON, lint in CI, no sequence-named files, every package documented. Re-measuring immediately afterward, clone density did not move — 234 source and 218 test clone entries at dupl -t 60, against 229 and 216 before. The same six files still top the list.

That is not a failure of the plan. It is evidence that the remaining debt is a different shape, and it has one signature: the canonical abstraction already exists, and the call sites bypass it. Six independent instances, below.

Eight findings

1

26 files hand-roll an atomic write that already exists — and the copies are less safe

duplication correctness mechanical ~400 lines

internal/config/ownedwrite.go is the canonical writer. It creates the temp file in the destination directory, chmods before the rename, Sync()s, defer os.Removes the temp on every failure path, and — critically — chowns the result back to the invoking user when running under sudo. Fourteen packages use it. Thirteen call sites total.

Twenty-six other files re-implement the same idea by hand. Every one I read does path + ".tmp" → os.WriteFile → os.Rename with no fsync, no temp cleanup on failure, and no ownership repair.

That last one is not cosmetic. Any of these writers reached during sudo vrooli setup leaves a root-owned file in the operator's home — the exact failure class that made a healthy required safeguard read as a permanent blocker once already.

// internal/config/ownedwrite.go — canonical
tmp, _ := os.CreateTemp(filepath.Dir(path), ".vrooli-owned-*")
defer os.Remove(tmpPath)
tmp.Chmod(perm); tmp.Write(data); tmp.Sync(); tmp.Close()
chownPathToInvokingUser(tmpPath)
os.Rename(tmpPath, path)
return chownPathToInvokingUser(path)

// internal/resources/broker_storage.go — one of 26
tmp := s.Path + ".tmp"
os.WriteFile(tmp, data, 0o600)   // no sync, no cleanup, no chown
os.Rename(tmp, s.Path)

6

cliout.RenderTable exists, is correct, and has zero callers

duplication UX defect

Parsing is in good shape — Parse*Request already routes through a shared parse() with FlagValue/HasFlag, and there are only 7 raw flag.NewFlagSet users. Rendering is where the layer stopped.

Every Render* re-opens with the same if format == cliout.FormatJSON branch — 73 occurrences — and then hand-builds a table with tab characters inside Fprintf. There are 412 raw Fprintf(w, …) calls across internal/cli and internal/app, and the only two text/tabwriter references in the whole tree are both inside internal/cliout/cliout.go itself. Raw tab characters in Fprintf do not align in a terminal; they align only when every value happens to be the same width.

The fix does not need designing. cliout.RenderTable(w, headers, rows) is already written, already correct, already builds a tabwriter with a two-space gutter — and grep finds zero call sites for it anywhere in internal/.

Empty states are ad-hoc too: "no active engagements", "no capacity claims", "no root" — three phrasings, three authors.

func RenderList(w io.Writer, format cliout.Format, resp recoveryapp.ListOutput) error {
  if format == cliout.FormatJSON { return writeRecoveryJSON(w, ...) }   // ×73
  if len(resp.Engagements) == 0 { fmt.Fprintln(w, "no active engagements"); return nil }
  for _, e := range resp.Engagements {
    fmt.Fprintf(w, "%s\t%s\t%s\t%s\t%s\n", ...)   // never aligns
  }
}
The win

A cliout.Table{Headers, Rows, Empty} that owns the JSON branch, the empty state, and a real tabwriter. Each renderer becomes a row-mapping function. This is the one finding on the list that a user will notice immediately — the CLI's tables start lining up.
