The pattern that keeps surviving

The canonical helper exists in the tree · the call sites do not use it

Both previous plans named this pattern and retired the instances they found. It is not exhausted. Seven more, each measured, each with a canonical implementation already present and already imported by at least one of its own bypassers.

01The resource binder pushes format resolution onto every call site~130 linesmechanical

rootcli.BindService takes newService func(C) (cliout.Format, Service, error) — it resolves the output format once, inside the binder. rootcli.BindResourceCommand, defined 20 lines below it, instead takes run func(...) (cliout.Format, Resp, error), which forces every one of its 18 call sites to fetch the format itself and thread a zero value through each error return.

Handler packages using BindService1 × OutputFormat(ctx) eachauth, capacity, contract, hygiene, package, recovery
Packages using BindResourceCommand22 in resourcehandlers · 10 in scenariohandlersplus 86 return "", Zero{}, err lines tree-wide
// internal/cli/resourcehandlers/handlers.go — this block appears 22 times
format, err := deps.OutputFormat(ctx)
if err != nil {
    return "", resources.DeprecationReport{}, err
}
return format, report, nil

There is a second seam with the same defect. scenariohandlers.scenarioServiceCommand calls BindService and passes "" as the format, then re-threads the real format through a private boundResponse wrapper — actively defeating the resolution BindService performs. That is why its 19 call sites carry the other 10 prologues. Fixing only BindResourceCommand leaves a third of the problem in place.

Give both the format func(C) (cliout.Format, error) shape BindService already has, and 32 four-line prologues collapse to nothing. This also accounts for 23 of the 209 source clone entries — the single densest cluster in the tree.

Three sibling wrappers already have the correct shape and prove it works: contractCommand, projectServiceCommand, and recoveryCommand. Each resolves the format once; each carries exactly one OutputFormat(ctx) call.

0571 command executions bypass the injectable shell seamtestability

internal/shell exists precisely so host probes can be faked without a new hand-written interface per package — the census metric duplicate_runner_interfaces reads 0 because the duplicate interfaces were retired. The call sites were not: 71 direct exec.Command / exec.CommandContext calls remain outside internal/shell. 06The typed error vocabulary is used by 13 filesboundaries only

internal/vroolierr.Error carries Code, Category, Hint, Suggestions, HTTPStatus, and ExitCode — everything the CLI and the API need to turn a failure into an exit code and an actionable message. It is constructed in 13 files. The tree has 2,350 fmt.Errorf calls and 148 errors.New calls.

Most of those are correct: internal wrapping should stay cheap. The gap is at the boundaries — every place a control-plane error becomes an exit code or an HTTP status without a Code the operator can search for. That is a bounded set worth typing, not a 2,350-site sweep.

0733 timing levers, named by magnitude, tunable only by rebuildcontrol surface

internal/tuning is real work and 141 files consume it. But the previous plan's goal — re-cut tuning by purpose so every timing lever has an owner — is only half landed. The constants are still ordered by duration and named after their size:

ShortOperationTimeout    = 1  * time.Second
ShortOperationDeadline   = 2  * time.Second
StandardOperationTimeout = 30 * time.Second
ExtendedOperationTimeout = 2  * time.Minute
LongOperationTimeout     = 5  * time.Minute

ShortOperationTimeout tells a reader how long it is, not what it bounds or who owns it — the same failure the mnd*NumberValue constants had, one abstraction level up. Meanwhile the neighbouring levers are named by purpose (CredentialRepairTimeout, SupervisorHealthInterval), which shows the intended shape.

Two things are missing outright. 25 of 49 context.WithTimeout sites still pass a literal rather than a named lever. And nothing in tuning is a var or a function — every value is a compile-time const, so an operator on a slow host cannot raise a single timeout without rebuilding the binary. A package named "tuning" that cannot be tuned is a naming claim, not a control surface.

Why a bespoke census exists at all

28 phase providers · 7 can target the control plane

You asked whether vrooli-debt-census should be needed if the fleet were good enough. The honest answer is that tidiness-manager already measures most of what the census measures — it wraps dupl for Go, it computes complexity and coupling, it is wired into CI at .github/workflows/test.yml:215, and it reported 3,340 duplicated lines in internal/ on its last run. It is not blind. Its budget was written at the observed value.

So the census is not compensating for a measurement gap. It is compensating for one specific thing no fleet provider can express: "this symbol is canonical, and these other shapes are bypasses of it." That is the rule behind 15 of the census's 24 metrics and all seven findings above. Nothing in the fleet has a place to declare it.

The shape of the fix

Give tidiness-manager a declarative canonical-seam rule kind, read from a file in the tree being scanned — {canonical: "cliout.RenderTable", bypass: "fmt.Fprintf with 2+ literal tabs", scope: "internal/cli/**"} — and emit a BYPASSED_SEAM finding per hit.

Every metric in the census that counts "X used instead of canonical Y" becomes one row in a repo-owned rules file instead of a Go function in a private binary. The census shrinks to the handful of metrics that genuinely need a Go AST walk. And the same rule kind immediately works for all 123 scenarios, which have the same problem and no instrument at all.

Which providers could grade the control plane, and which honestly cannot

The census metric phase_providers_without_control_plane reads 21 against a budget of 21. It counts every provider that does not declare the control-plane target kind as debt — which means it can never reach zero, because most of those providers are correctly scenario-scoped. It is the same dead gate as os_rename_outside_config pinned at 4. The metric needs an applicability declaration, not a budget.

What I would do first

A half-day that changes the board

Moves 1–4 are about five hours of entirely mechanical work with no design decisions in them, and together they remove roughly 250 lines, the largest clone cluster in the tree, a real environment-resolution divergence, and four private copies of one parser. None of them needs a plan.

Move 8 is the one I would not skip, because it is the difference between a board that is honest and a board that is decorative. Right now golangci-lint reports zero findings on internal/ while 75 functions sit above the configured threshold, and nothing anywhere records that. Counting the 78 suppressions costs two hours and makes every future reading of that gate mean something.

Move 10 is the one that answers your actual question. The census exists because the fleet has no way to say "this is the canonical helper." Give tidiness-manager that rule kind and the census stops being a parallel instrument and becomes a thin AST tier — and every scenario in the repo inherits the check for free.
