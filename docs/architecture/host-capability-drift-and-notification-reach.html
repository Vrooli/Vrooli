Host drift · post-incident analysis & target design

The Half-Frozen Package Set

A GPU vanished from this host on 22 August. Vrooli detected it within four hours, named the exact missing package, and told no one for three days. The driver is the symptom; the coupling model and the silent notification path are the defects.

Host swarminator · linux/amd64 Evidence collected 2026-08-25 Kernel 7.0.0-30-generic Status repaired 2026-08-25 · design open
The four claims

What this comes down to

The trigger was our own mitigation

An unmanaged file written on 20 August froze the NVIDIA module packages but not the kernel that they must match. Two days later the kernel moved alone.

Detection worked, precisely

host-kernel-module-drift went critical at 18:56 on 22 August — the first check cycle after the reboot — and named linux-modules-nvidia-580-open-7.0.0-30-generic with its apt candidate confirmed available.

Nothing was allowed to act, and nothing spoke

The check is not registered as healable, its incident carries remediation: none, and vrooli-autoheal has no notification path of any kind. 23 incidents sit open; the oldest is from 12 June.

The fix is probably not scary

The safeguard gates restoring an absent driver behind the same maintenance window as swapping a live one. Those are different risks and the first likely needs no reboot at all.

Part one · what happened

One rail was frozen. The other kept moving.

On 20 August at 06:18, unattended-upgrades replaced nvidia-driver-580-open (580.159.03 → 580.173.02) underneath a running gnome-shell. The module reload destroyed /dev/dri/card0 and the GPU reappeared as card2. Mutter picks its primary GPU once at startup and cannot re-pick, so the compositor fell back to the 512 MiB integrated AMD iGPU, which then emitted roughly 970 amdgpu out-of-memory messages per second and collapsed journal retention to about two and a half hours.

Five hours later, someone wrote a mitigation.

Unmanaged host state · created 2026-08-20 11:10, root:root, no owning dpkg package

/etc/apt/apt.conf.d/52unattended-upgrades-nvidia-blacklist

Unattended-Upgrade::Package-Blacklist {
    "^nvidia-";
    "^libnvidia-";
    "^linux-modules-nvidia-";
    "^xserver-xorg-video-nvidia";
};

Nothing in the Vrooli repository writes, references, or validates this file. dpkg -S finds no owner. It is a real, load-bearing host mutation with a careful rationale comment, living entirely outside the safeguard system that exists to own exactly this.

The mitigation was correct in intent and wrong in extent. It froze ^linux-modules-nvidia- — including the meta-package linux-modules-nvidia-580-open-generic-hwe-24.04, which is Ubuntu's own mechanism for keeping the module in step with the kernel. It did not freeze linux-generic-hwe-24.04. One half of a coupled pair was pinned; the other half stayed eligible.

The host rebooted into 7.0.0-30-generic at 14:29. No NVIDIA module exists for it, so modprobe nvidia reports the module is not found and nvidia-smi cannot reach the driver. The userspace stack is untouched and still installed, which is why every surface stayed green: Ollama simply resolved to the CPU backend and kept answering requests correctly, ten to fifty times slower.

Did Vrooli have control over this?

Three answers, and separating them is the whole point:

  • Historical state: yes. The original 22 August mitigation was written outside the safeguard registry, so the evidence record correctly described an unowned host mutation at the time.
  • Current control-plane ownership: explicit. The NVIDIA safeguard now declares /etc/apt/apt.conf.d/52-vrooli-nvidia-coupling in storage.entries and declares the coupled-update invariant beside the module-loadability invariant.
  • The failure was Vrooli-shaped. The mitigation created a hazard — a partially-frozen coupled package set — that was previously not modeled. The invariant aggregator, host-state audit, and provider verdict now make that coupling and its coverage observable.

Autoheal's live runtime config carries an enabled and autoHeal toggle for every infra-*, resource-*, and system-* check — and contains no host-* entries at all. The instrument cannot see its own blind spotstructural

This is why nobody noticed. The substrate projection grades SB5 — do the running kernel, module inventory and driver bindings agree? as NOW, and by its own contract that is correct: the space measures whether a condition is readable, and it was read perfectly. The recovery projection then measures R1 success rate, R2 heal loops, R3 episode duration — all of which only apply to checks that already have actions.

So a critical finding with zero remediation paths and zero delivery is invisible to both projections simultaneously. There is no cell asking what fraction of critical findings are actionable, and none asking whether a critical finding ever reached a human. Adding those two cells makes this class of gap self-reporting instead of something a person has to trip over three days later.

Part three · target design

Three things to build, none of them about NVIDIA

1 · Capability coupling invariants

Do not build NVIDIA driver management. The general failure class is:

A host capability is delivered by a set of packages that must stay version-coherent. Something moved half the set.

NVIDIA is one instance. So are every DKMS module (ZFS, VirtualBox, WireGuard), kdump-tools against the running kernel, linux-modules-extra for any driver a resource depends on, and container runtime against kernel cgroup version. Same shape, same detection, same remedy.

You are already most of the way there and it is hidden by one line. internal/hostinventory/integrity_collector.go computes MissingModulePackage generically from installed-package inventory versus uname -r. The narrowing happens in the check, not the collector:

// scenarios/vrooli-autoheal/api/internal/checks/host/kernel_module_drift.go
for _, driver := range inv.Packages.Drivers {
    if driver.Vendor != "nvidia" { continue }   // ← the only thing making this NVIDIA-specific
    ...
}

Lift that into a declared invariant keyed on the capability field safeguards already carry — nvidia_driver declares "capability": "gpu-driver-health". Then "capability X requires package set P to stay coherent with the running kernel" becomes data rather than Go, and a second vendor costs a manifest entry instead of a code change.

This also solves the portability worry cleanly: the invariant is OS-neutral — "the driver stack backing this capability must be loadable on the running kernel" — and only the resolver is apt-specific. macOS and Windows get their own resolvers or a truthful not-applicable, exactly as the existing platform_status block already models. Worth noting the current one claims linux: unqualified, meaning no host has ever confirmed it works; this host just did, twice, in opposite directions.

2 · Update control as an operator-config spectrum

Not a binary. The middle position is the one this incident argues for.

ModeWhat Vrooli doesIntended for
observe Never touches update configuration. Detects drift, reports it, offers a remediation script. Default. Other people's machines, once this project is shared.
guard Owns update policy for capability-coupled package sets. Still never applies updates itself, but guarantees no set is ever half-frozen — freeze the modules and the kernel freezes with them. Machines where Vrooli is a major tenant.
own Disables unattended-upgrades, runs its own update windows with reboot coordination and post-update capability verification. This host.

The 20 August mitigation is the argument for guard existing. Someone reached for a correct idea and implemented it incompletely because the coupling was modelled nowhere. Under guard, that apt.conf.d file is a declared safeguard artifact whose invariant is "these packages move together or not at all", and 22 August never happens.

Corollary worth acting on independently. That file is load-bearing host state with no owner, no validation, and no drift check — and it caused this outage. Safeguards already have a storage.entries concept for declaring owned host paths, and nvidia_driver currently declares the empty set. Beyond this fix, "what host state have Vrooli or its agents mutated that nothing declares?" is a question with no answer today.

3 · Risk classes, so the right fix stops sounding frightening

You were told to schedule a maintenance window with console recovery. That advice came from a gate that does not distinguish between two very different operations. internal/safeguards/nvidia-driver/handler.go:280 checks for an active remote-desktop server and refuses without --maintenance-window, regardless of whether any NVIDIA module is currently loaded.

Risk classExampleWhat can actually breakProportionate gate
restore-absent Install the module matching the running kernel when nothing is loaded Little. There is no live module to unload and no device to renumber — the compositor is already on the iGPU. Consent. No window, and likely no reboot.
reload-live The 20 August driver upgrade under a running gnome-shell Device renumbering, compositor fallback, session loss. This genuinely happened. Maintenance window.
boot-critical GRUB cmdline edits, initramfs rebuilds — e.g. the pstore_ramoops safeguard The host may not come back. Window + console or SSH recovery + verified backout.

Your current situation is the first row. The package version matches the running kernel exactly, the userspace is already installed, and nothing holds the device — so installing it and running modprobe nvidia should restore the GPU without a reboot.

Confirmed 2026-08-25. The install resolved to exactly one new package — 0 upgraded, 1 newly installed, 0 to remove — and pulled none of the blacklisted userspace packages, so the 20 August live-driver swap did not repeat. No reboot was required. The module auto-loaded via udev coldplug; nvidia-smi now reports driver 580.173.02 and ollama holds three models entirely in VRAM.

One cost that the risk table did not predict: loading the module renumbered the DRM devices (card0 disappeared; amdgpu is now card1, nvidia is card2) and gnome-shell restarted once. It recovered on its own, gnome-remote-desktop never dropped, and the kernel log stayed clean — no amdgpu storm. So restore-absent is the right class and needs no window, but "zero visible effect" overstated it. The row should say brief compositor restart possible.

A second gate with the same defect

Repairing the GPU exposed the same failure shape one level down. Placement is read by matching the resource against nvidia-smi's compute rows — correctly, including the llama-server child of ollama serve. But with no model loaded, ollama holds no CUDA context at all, so there is genuinely no compute row, and the reader returns cpu with mode_drift.

Which means vrooli resource start ollama cannot pass its own health gate: at startup nothing is resident, so drift is always true and the check times out — while the process is up and serving. It happened twice during this repair, reported as "start failed" both times.

Placement is unknowable until first load, and the gate scores unknown as bad. That is the identical mistake the whole report opens with, and it argues for a general rule rather than two point fixes: a health verdict must distinguish not-yet-determinable from determined-bad, and only the second may block.

Where the policy should live — and why

Your question was whether autoheal sends to the hub directly or through vrooli-events, and whether "what do I want to be told about" is configured in autoheal or in the hub. My recommendation: autoheal emits facts to vrooli-events; notification-hub owns all routing policy. Three reasons:

  • Autoheal already speaks in facts. "Incident opened", "severity changed", "resolved" are observations about the world, not requests to notify. Emitting one is cheap and commits to nothing.
  • Otherwise every producer grows recipients. If autoheal decided who to tell, it would need quiet hours, channel preferences, and escalation chains — duplicating precisely what notification-hub was built to centralise, and doing it again in the next producer.
  • The subscription pattern is already the knob. It lives in vrooli-events as data (event_pattern), so "what reaches me" is one declarative record you can change without touching autoheal's code.

But there is a leak that has to be fixed for that split to be real. EventWebhook currently maps payload.Title, payload.Body, and payload.SensitivityLabel straight out of the event into hub.SendInput. That forces the producer to author notification copy — which means autoheal would be writing user-facing prose and choosing sensitivity labels, and the "hub owns policy" split becomes fiction. Notification-hub needs a rendering step: event type plus payload in, title and body and sensitivity out. Producers emit domain facts; the hub decides how they read and who sees them.

A phasing that doesn't require finishing everything first

P0Move the configuration off environment variables, then make the wiring real

Environment variables are the wrong home for this: they are invisible to the operator, undeclared in any manifest, and only changeable by restarting the scenario. The repository already has the right pattern — a scenario-owned .vrooli/config.json, distinct from service.json, read through a scenario config package. Seven scenarios use it.

Two variants exist and the difference matters here. git-control-tower loads its config once at boot (config.Load(scenarioDir) in main.go). vrooli-autoheal instead serves a live, API-backed runtime config with show, defaults, validate, import, export, and per-item setters over CLI and UI, changeable without a restart. Notification routing belongs in the second kind, and autoheal is the model to copy.

Secrets do not move with it. The VAPID private key and SMTP credentials stay in the credential store; only endpoints, subscription patterns, and routing preferences become operator-editable config.

Then make the subscription actually register, and make EnsureEventSubscription report loudly when unconfigured instead of returning nil. Separately, confirm the bus carries current traffic — the store's newest event is from 11 August.

The proof bar is intake, not arrival. A recorded row in delivery_attempts with outcome "no recipient configured" demonstrates that intake, routing, sensitivity, and dispatch all ran — which takes SMTP credentials, VAPID keys, and the Cloudflare origin off the critical path entirely. Real delivery becomes its own later phase rather than a prerequisite.

P1Autoheal emits incident lifecycle events

Three event types — opened, severity-changed, resolved — carrying the incident's own fields. No recipients, no copy, no policy. This is the smallest change that makes autoheal legible to anything downstream, and it is independently useful even if nothing subscribes yet.

P2Hub-side rendering

Event type → notification template, so producers never write copy and sensitivity is assigned by the component that understands channels. This is the change that makes the ownership split honest rather than nominal.

P3Triage before volume

The live ledger was dispositioned before notification volume was enabled: incidents with a current OK result were resolved with evidence; the remaining open findings carry an owner/action disposition. Severity maps to notification sensitivity, unchanged open incidents are transition-only, and the saturation guard records every suppression.

P4The return leg

The blocking ask is now wired to remediation authorization. Notification-hub renders the approval request and owns the answer; autoheal verifies the durable answer, binds it to the incident fingerprint and candidate, re-runs script preflight, and consumes the authorization once before execution. A caller cannot supply an approval boolean.

The platform vocabulary cannot say "impossible here"schema

platformStatusToken now distinguishes not_implemented portability debt from not_applicable platform closure. Windows can report an unwritten provider as debt while macOS can report NVIDIA as not applicable, making the remaining backlog countable.

Splitting not_implemented (debt, countable, closable) from not_applicable (closed, with a reason) turns a flat wall of "unsupported" into a portability backlog you can actually measure.

.vrooli/schemas/common.schema.json — definitions.platformStatusToken

Invariants want a shared schema fragment, not a new registrydecided

Define invariant once in common.schema.json and $ref it from safeguard.schema.json and any other schema that later grows one. The declaration stays with whatever owns it; only the shape is shared, so no migration is ever forced. What replaces the registry is an aggregator that walks every declaration site and collects the declared invariants into one evaluable set — and it must report declared-versus-evaluated coverage, or a site that is silently not walked looks exactly like a site with no invariants.

The invariant also needs its own applicability, independent of its host manifest: nvidia_driver declares platforms: ["linux"], but an OS-neutral invariant must be able to answer not applicable on macOS by its own logic rather than vanishing because the file it lives in is Linux-only.

Performance

Cache TTL and check interval are an order of magnitude apartminor

The six host checks share a CachedIntegrityCollector with a 30-second TTL, but each runs on a 300-second interval with an independent random startup offset spread across that window. Offsets more than 30 s apart each miss the cache, so the intended one collection per cycle is closer to six. Measured cost: 0.66 s cold, 0.08 s warm — so roughly 4 s of probing per 300 s rather than 0.7 s.

Small in absolute terms, and worth fixing anyway because the sharing was clearly intended and silently does not happen. Either align the TTL to the check interval, or collect once per cycle and pass the snapshot to all six.

Polish & hygiene

A silent no-op in an integration seambug

EnsureEventSubscription returns nil — success — when its configuration is absent. An unconfigured integration and a working one are indistinguishable from the outside, which is why this went unnoticed for a week. Any seam that can be "configured off" should say so once at startup.

Filed problems that aren't therehygiene

notification-hub's PROGRESS.md records "opened three PROBLEMS.md entries" on 17 August and "filed three new problems" — including the vrooli-events fan-out gap — on 18 August. PROBLEMS.md's ## Entries section is empty. Either they were resolved without a note or they were lost; either way the known-issues register is the thing a future agent trusts.

A generic action renderer over a specific blockerUX

Setup prints vrooli setup explain <name> even when the blocker is precisely maintenance_window and the resumable command is fully known. Blocker-aware rendering — the full command for maintenance_window, the reboot-and-verify sequence for reboot_required — turns a dead end into a next step.

Nothing compares "kernel we booted" against "kernel our capability packages target" at boot, at setup, or during resource reconciliation. The data to do it is already collected every 300 seconds; it just never reaches a decision.

Part six

If you only do three things

  1. Establish which risk class the repair is in, then repair it. If restore-absent holds, this is an install and a modprobe, not a maintenance window — and the GPU comes back today.
  2. Give the blacklist file an owner. It is the actual cause, it is undeclared, and the same mitigation will be reached for again the next time a driver upgrade breaks a session. Declaring the coupling is what stops the repeat.
  3. Do P0 of the notification path. Not the whole spine — just make the subscription register and confirm the bus is live. Everything else in Part four is blocked behind it, and it is the smallest piece.

The uncomfortable framing. The system detected this correctly, at the right severity, with the exact remedy in the evidence payload, four hours after it happened — and the outcome was identical to having no detection at all. Building more detection is the tempting move and the wrong one. Everything valuable here is downstream of the check that already works.
