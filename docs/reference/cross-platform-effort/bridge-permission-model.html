Architecture reference · measured 2026-08-18 · branch agi

Node and agent authorization is derived from one catalog vocabulary.

Vrooli does not maintain a hand-written list of remotely-invocable commands. The authorization vocabulary is derived at init from every CLI manifest in the repository — 2,251 governed commands compress to 164 grantable scope strings. Bridge admission, discovery's relay pre-check, and agent identity now share that vocabulary. Node authority is keyed by scenario namespace and effect, so adding a command requires no Bridge or node-record edit while a new destructive command remains excluded from read/write grants.

The model

One derivation, three consumers

Everything flows from CLI manifests. Nothing in the middle is hand-maintained; the checked-in artifact on the Bridge side, dispatch.manifest.json, is six lines long and names no commands at all.

Source of truth

cli/manifest.json ×74

The root project manifest plus one per scenario. Each command declares a governance block:

  • effect — read / write / destructive
  • run_eligible — may an agent invoke it, or humans only
  • permissions — filesystem/network/admin classes
  • binding — the connect-rpc service+method, when there is one
→

Derivation · no I/O at call time

api-core/scopecatalog

Schema-validates every manifest, then emits a deterministic catalog of <scenario>:<effect> scopes. Also:

  • gives each omitted RPC the scenario's most restrictive effect — the safe default
  • Reconcile() checks the catalog against proto descriptors for completeness
  • Resolve() implements the wildcard grammar
  • Materialize() expands wildcards at token-mint time and drops human-only commands
→

Relying parties

Three, one vocabulary

  • Bridge dispatch — dispatch.Allow admits a typed job against a node's scopes
  • Discovery relay — ResolveScenario admits an addressed node@scenario call
  • Agent identity — agent-manager mints run tokens via Materialize

A fourth party, scenario-authenticator, stores grants but deliberately never interprets them.

The separation that makes this work

scenario-authenticator's authorization package says it outright: "It does not derive, validate, or enforce scope meaning; relying parties own those decisions." That is the correct IAM split, and it is the reason no second vocabulary is needed. The catalog defines what scopes exist, the authenticator stores who holds which, and each relying party enforces at its own boundary. Any proposal that teaches the authenticator about command semantics is moving in the wrong direction.

The grammar

Scope strings, and how a grant is decided

Format

Every scope is <namespace>:<effect>. The namespace is a scenario name, or vrooli for the project CLI — kept explicit so a scenario named "vrooli" cannot collide with the root identity.

Held grantCovers
web-console:readevery read command of web-console
web-console:*every effect within web-console
*:readevery read command, any scenario
*everything

Matching is exact and case-sensitive, and whitespace is deliberately not normalized so a malformed scope string can never grant access.

Resolved 2026-08-18

Three narrow defects, now closed

The architecture did not need replacement. The shipped change corrected derivation, re-keyed grants, and migrated the active fleet.

D1
Resolved: active nodes hold complete grant pairs

Allow still requires two independent grants: vrooli-bridge:<effect> permits typed work over the transport, while <namespace>:<effect> selects commands. The active records were migrated through the registry CLI, never by editing its database.

The capabilities column remains self-reported evidence and is never merged into owner-granted Scopes. That separation prevents a node from widening its own authority.

dispatch admission and the discovery pre-check both call scopecatalog.Resolve

D2
Resolved: derived verbs honor real CLI argv

The catalog now reads Group.flat. Flat organizational groups emit the command name alone; routed groups retain group.Name + " " + command.Name.

"top-level hygiene"        vrooli hygiene
"lifecycle-commands setup" vrooli setup
"scenario status"          vrooli scenario status   ← correct by coincidence

A repository conformance test walks the installed owning CLIs and reports manifest/runtime disagreements explicitly.

scopecatalog derives setup and hygiene, never their organizational prefixes

D3
Resolved: the second axis is namespace and effect

The dual requirement remains, but the command-name glob has been replaced with the catalog pair already attached to every derived command. Exact grants and the catalog wildcards are resolved case-sensitively by one function.

Registry and pairing writes reject command-named or unknown grants with typed errors, so the retired vocabulary cannot re-enter persisted state.

accepted: namespace:effect · namespace:* · *:effect · * · declared transport capabilities

Delivered sequence

  1. D2 first — teach scopecatalog to honour Group.flat. Until derived verbs match real argv, nothing downstream can be tested honestly.
  2. D3 next — re-key the second axis, delete the machine-specific test, and express node grants in catalog scopes.

Add a regression test that runs the actual persisted node records through Allow, so a tightening can never again brick every node silently.

Keep these — they are already right

  • Shell-metacharacter rejection on every token, as defence in depth. A typed job never reaches a shell (the node-agent execs an argv, never sh -c), so a metacharacter can only be a smuggling attempt.
  • Pure decision function. Allow does no I/O, which is exactly why the probe above was possible — the highest-stakes decision in the scenario is exhaustively table-testable.
  • Audited rejections. A denial is recorded before any run is created or anything is pushed.
  • Ordered, typed rejection reasons — invalid job, unsafe token, verb not in manifest, verb out of scope — each distinct and separately testable.

Two constraints worth writing down

Things a plan will get wrong if nobody says them

There is no inbound endpoint on a node

Discovery already implements the node axis — ResolveScenario(ctx, "node@scenario", …), local path unchanged, remote path relayed. But a remote resolution deliberately carries no URL. From the source: "nodes dial out, so inventing an inbound endpoint would violate the bridge contract."

So remote scenario interaction is typed command relay — a bounded, single-shot RelayRequest/RelayResponse — not Connect-RPC against a remote scenario. This is exactly why the CLI manifest is the right authorization surface: for a remote caller, the CLI verb is the API.

Interactive work is a different transport

Streaming and PTY sessions do not ride the relay. They use a separate binary WebSocket channel with explicit owner re-authentication, a bounded flow-control window, an idle timeout and a hard lifetime — gated on vrooli-bridge:session, which is a capability grant rather than a command scope.

A remote scenario status and a remote agent terminal are therefore not the same mechanism. Any plan that treats "federate to a remote scenario" as one thing will mis-scope; there are two doors and they have different locks.

A coverage gap the model cannot see

52 of 123 scenarios have no cli/manifest.json, so they contribute zero scopes to the catalog. They are not denied by policy — they are invisible to the vocabulary entirely, which means there is no grantable string that could ever authorize them remotely. Before the namespace model can be called complete, that gap needs either a manifest per scenario or an explicit, recorded decision that these scenarios are local-only.

Invariants

What keeps this from drifting back

The model has already drifted once — the verb-glob axis is itself the drift. Four rules, each mechanically checkable, keep the derivation load-bearing rather than decorative.

  1. No relying party may declare a scope vocabulary. Every scope string a component enforces must pass Catalog.HasScope. The Bridge dispatch manifest already validates its default grants this way — generalize it, and the check becomes a structural rule rather than one component's discipline.
  2. No grant may name a command. A stored grant is namespace:effect or a wildcard over it. If a grant string contains a space or a trailing glob over a verb, reject it at write time — that is the shape of the current defect, and it should become unrepresentable.
  3. Derived verbs must match real invocation. The flat field is one instance of a general problem: manifest structure and argv structure are different things. A conformance test should invoke each derived verb's help path and fail when it is not a real command.
  4. Admission decisions must be tested against persisted records, not fixtures. D1 was invisible because every test used hand-built scopes. One test that reads the real node rows would have caught it the day it landed.

The short version, for anyone arriving mid-thread

Bridge does not hardcode scenario commands and does not need changing when a scenario gains one — that part of the design is already built and correct. The friction everyone keeps hitting comes from a single mis-keyed axis: node grants are expressed as command-name globs instead of the scenario:effect namespace the catalog already derives. Fix the key, honour Group.flat, and add a regression test that uses real node records. Everything else in the model can stay exactly as it is.
