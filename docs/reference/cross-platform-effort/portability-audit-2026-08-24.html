How to split a file without making it worse

The stated worry is the right one: an agent asked to "split this file" will often re-implement rather than move, leaving two copies of logic that then drift. That failure is preventable, and it is preventable mechanically rather than by review diligence. Six rules, and the third is the one that actually catches it.

Split protocol

Every rule below is checkable by a machine. If a split cannot satisfy all six, it is not a split — it is a rewrite wearing a split's clothes, and it needs a design first.

  1. Document before you divide. Write the package doc first. If the purpose cannot be stated in two sentences, stop — that is the finding, and no split will improve a package nobody can describe. This is also why R-07 must land before R-09.
  2. Move whole declarations; never retype one. Cut and paste entire functions, types and constants. No reformatting, no renaming, no signature changes, no "while I'm here."
  3. Diff the symbol set, not the diff. Enumerate every declaration in the package before and after — exported and unexported. The two sets must be byte-identical in names and equal in count. This single check catches re-implementation, accidental duplication and silent drops, and it is a short script over go/ast.
  4. Zero test edits in a split commit. If a test had to change, the behaviour changed, so it was not a split. Revert and separate the two concerns.
  5. Behaviour changes land afterward, separately. One commit moves code; the next changes it. Never the same commit — a reviewer cannot see a logic change buried in a 2,000-line move.
  6. Run the duplication scan after each split. Tidiness Manager already owns duplication detection. Make it the closing gate of the split, so a leftover copy is caught by the tool rather than by whoever hits the bug in six months.

Applied to the concrete list: internal/cliinstall is the right first target — two files, 2,462 lines, an obvious install/uninstall seam, and a small enough blast radius to validate the protocol itself. Do not start with internal/lifecycle (8,305 LOC, 13 dependents, no package doc, no subpackages). It needs R-07's documentation pass and a deliberate subpackage design before anyone touches it.

D-06

process-containment is a resolver bug, not a missing declaration Derived

Corrected diagnosis. I reported it as "a vocabulary entry with zero declarers." It has five: autoheal_watchdog, emergency_watchdog, host_hardening, kernel_config and workspace_sandbox_userns. Every one is capability_role: control, and the resolver only reports implemented when a primary or peer provider resolves. Controls are AND-required but never resolve a capability themselves — so a capability implemented entirely by safeguards is peerless by construction, on every OS including Linux.

The model's own rule makes this a latent trap rather than a one-off: "Every safeguard is a control." Any future capability implemented purely by safeguards will hit exactly this.

Ruling Fix the resolver, not the manifest. A capability whose declarers are all controls resolves when every control resolves. Promoting one safeguard to primary would clear the symptom while contradicting the doctrine and leaving the trap armed for the next one.

With 155 platform-gated skips, "the suite passed on macOS" is not a claim anyone can evaluate. The fix is not to eliminate every skip — some are legitimate platform limits — but to make the number a first-class part of the result.

D-10

system-monitor is the right first target — one line of resolver logic is wrong Corrected

I had this backwards. I read the fleet's ineligible verdict as a property of system-monitor and recommended routing around it. It is a property of the verdict logic, and the scenario was built for exactly the outcome the operator described.

service.platform_capabilities is a scenario's provides declaration — the per-OS status of capabilities the scenario implements. scenario-dependency-analyzer's authoredPlatformOverrides consumes it as a requires list: one entry marked unsupported sets the whole scenario to blocked on that OS.

The asymmetry in that same switch statement proves the intent was never this. partial, experimental, unqualified and build-verified all correctly downgrade the scenario to degraded — a non-blocking state. Only unsupported blocks. But on a provided capability, unsupported means "this one feature is unavailable here," which is a degradation by definition.

The runtime already behaves correctly, and the manifest says so in its own evidence strings: the darwin backend "grades memory errors not-applicable" and the windows backend "grades memory errors unmeasurable." The code degrades. Only the eligibility verdict blocks.

Ruling Fix platform_verdict.go: unsupported on an authored provided capability degrades the scenario; it does not block it. Add an opt-in essential: true per capability, defaulting false, for the rare scenario that genuinely cannot function without one. Also fix the reason string — it reports only the first blocker via if blocking == "", so macOS is named as blocked by memory-errors when thermal is unsupported there too.

Blast radius is three scenarios. Only storage-manager, system-monitor and vrooli-autoheal author platform_capabilities at all, and system-monitor is the only one currently blocked by it.
