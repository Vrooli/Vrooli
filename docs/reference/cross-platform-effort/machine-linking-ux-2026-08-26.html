Design proposal · companion to the Bridge Reach Map

Linking a Machine

Seven screens for the flow that has to work before any of the fleet features matter: a person adds a second machine, decides what it may do, and then uses it — without ever opening vrooli-bridge.

Palettes the apps’ real tokens web-console slate-950 / cyan-400 system-monitor graphite / phosphor Status proposal, nothing built
Part one — web-console

Machines, as a first-class thing the app owns

Today web-console surfaces one placeholder row labelled “Bridge node” and tells you to start a service that is already running. The replacement is not a better error message — it is treating machines as an object the app manages, the way it already manages sessions.

SCREEN 01

The machines panel

Every machine the user has linked, with the two facts that decide whether it is usable: is it reachable, and what is it allowed to do.

Permission is shown as a sentence, not a scope string. The underlying grant is still *:read — but nobody should have to know that to understand what a machine can do.
Staleness is stated, never implied. Today a node that vanished a week ago can still report heartbeat_fresh: true. Any surface that hides age inherits that bug.

SCREEN 02

Adding one, on the spot

Three ways in, ordered by how likely they are. Most people are adding a laptop on the same network; that case should need no address, no SSH password, and no typing.

Uses the shared mDNS responder. Bridge publishes _vrooli-bridge._tcp.local on a trusted LAN; the manual URL remains the fallback when multicast is unavailable or the control plane is off-network.
The code path is the fallback, not the default. It is the only one that works today — and it currently also requires a source checkout and make setup on the joining machine.

Three doors, one destination. The RPCs behind the first two already exist — RequestPairing/ApprovePairing and IssuePairingCode/RedeemPairingCode. The third is onboard start, which is the right tool for a VPS and the wrong one for a laptop.

SCREEN 03

Confirming it is the right machine

The joining machine shows three words. The approving machine shows the same three words. The person checks that they match.

This is the one piece with no backing at all today. PairingRequest carries name, OS, arch and endpoint — every field chosen by whoever sent the request. On a shared network there is currently nothing to distinguish your laptop from someone else’s claiming to be it.
Derive the phrase from the key exchange, the way SSH fingerprints and Signal safety numbers do — so matching words mean matching keys, not matching labels.

SCREEN 04

Deciding what it may do

ApprovePairingRequest already takes a list of granted scopes. What is missing is any human vocabulary for choosing them.

Presets are the product; scopes are the implementation. The chips show the real grant so an advanced user can audit it, and Custom opens the full derived catalog.
Today every node lands on *:read / *:write wildcards, which quietly defeats the per-scenario allowlist the design promises. Presets are how a narrower default becomes the easy path rather than the expert one.

Part two — system-monitor

Switching the whole instrument to another machine

system-monitor has no reference to nodes or Bridge anywhere in its source today, so this is greenfield. That is an advantage: the machine axis can be a property of the whole app from the first commit rather than a filter bolted onto each page.

SCREEN 05

The machine is app state, not a page filter

One control in the header sets the subject of every panel, every query and every cached series below it.

Add a machine… is in this menu deliberately. If linking a machine is only reachable from vrooli-bridge, then every app that wants a second machine inherits a detour through an app the user has no other reason to open.
Reachability belongs in the picker, not in an error after you pick. Choosing a machine that cannot answer should be visibly a choice you are making.

SCREEN 06

Viewing another machine

Everything below the header is now minimouse. The identity strip stays visible for as long as that is true.

The strip is a safety feature, not decoration. The failure this prevents is reading one machine’s 94% disk and acting on a different machine.
Read-only is stated up front. The grant is known before any action is offered, so disabled controls carry a reason instead of a permission error after the click.

SCREEN 07

When the machine stops answering

A remote view will lose its subject — a lid closes, a network drops. The readings do not vanish and they do not silently keep looking live.

This screen is why the presence bug matters. Bridge can currently report a node that vanished a week ago as fresh. A surface that renders age honestly turns that defect into a visible wrong number instead of a silent one.
Every reading is stamped, and the stamp is the same age. Freezing the whole view at one timestamp is more truthful than letting some panels update and others not.

Part three — what has to exist

Every screen, against what is actually built

Most of this is not new construction. Four of the ten capabilities below already work end to end; four more exist as one finished half waiting on the other.

Screen Capability it needs State What is actually there
Machines list01 List machines with reachability and grants Built Registry ListNodes returns all five readiness facts. Needs the shared node client so each app is not re-deriving them, and honest age — presence can still report a week-old node as fresh.
Add › this network02 Control plane advertises itself on the LAN Missing The agent browses _vrooli-bridge._tcp.local and falls back cleanly when multicast is unavailable. Bridge publishes the record through the shared packages/mdns-go responder, including the control-plane URL in DNS-SD TXT data.
Add › appears by itself02 Joining machine asks; owner approves Half RequestPairing, ApprovePairing and ListPairingRequests exist as RPCs, with four CLI verbs on top. The agent never calls any of them. The flow designed for this exact case has no client.
Add › enter a code02 Single-use code, issued and redeemed Built Works end to end and pins the control-plane key. It is the only join path that functions today — and it still lands on a machine that must build Vrooli from source first.
Add › remote server02 Drive a raw host from bare OS to online Built A genuinely strong durable, resumable, step-evented SSH orchestration. Right for a VPS; wrong for a laptop, which has no SSH password to give and should not be cloned into.
Verification words03 Confirm the key, not the label Missing PairingRequest carries name, OS, arch and endpoint — every one chosen by the sender. Nothing derives a comparable phrase from the exchanged keys, so approval currently trusts a self-declared name.
Permission presets04 Choose a grant in human words Half ApprovePairingRequest.scopes already takes the grant, and the catalog derives every legal scope. There is no preset vocabulary above it, and the shipped default is read + write wildcards.
Machine switcher05 Machine as app-wide state Missing system-monitor has zero references to Bridge or nodes. Needs machine context, a per-machine API base, a machine-scoped cache and the indicator — all of which are the same four pieces every other app would need, which is the argument for building them once.
Live remote readings06 Stream a scenario’s data from another machine Half The interactive session transport carries binary frames over a WebSocket today, outside the typed Connect contract Bridge otherwise holds to, and web-console is its only consumer. There is no open() verb any other app can call.
Honest staleness07 Age that is true, everywhere Blocked Until presence stops reporting stale nodes as fresh, every surface that renders reachability inherits the same wrong answer — and a screen designed to be honest about age becomes the place the defect finally shows.
The deployment consequence

A desktop user cannot run make setup

Every path onto a new machine today ends in the same place. bootstrap.sh does git clone and then make setup — a full source build on the joining machine. The alternative, the control plane cross-building the node binaries itself, refuses unless Go is installed and a repository checkout is present on the control plane. Both assume a developer workstation on both ends.

In the desktop deployment neither assumption holds. There is no checkout, no Go toolchain, and no terminal in the story. The person has an app, and the machine they want to add will also have that app. So the node agent has to become something the installer already placed on disk rather than something built on arrival — and “link this machine” has to be an action inside whichever app they happen to have open.

That is the real shape of the gap you were sensing. It is not that vrooli-bridge is wrong — its admission model is the most generic thing in the repository, and its SSH onboarding is genuinely good at the job it was built for. It is that every join path was designed for an operator with a shell, and the deployment target is a person with a window.

The encouraging part: the pull-based flow that fits a person with a window is already specified, already has RPCs, and already has a CLI. It is waiting on a node-side caller, an mDNS responder of maybe a hundred lines, a verification phrase, and a bundled binary. None of that is architecture work. The architecture was done correctly the first time.
