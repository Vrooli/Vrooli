RUNG 03
Your first question

Is nodeclient legitimate?

Partly. Your suspicion is aimed at the right place but one layer off.

nodeclient is not a wrapper around Bridge commands, and it is not compensating for a Bridge defect. It is the client half of Bridge's authorization protocol — owner-token and re-auth header formatting, local scope pre-validation so a call is refused with a named missing grant instead of a generic 403, a typed nine-value error taxonomy, bounded timeouts, and the WebSocket upgrade for PTY sessions. None of that is discovery's job.

It also builds on discovery rather than replacing it: its default endpoint resolver is literally discovery.ResolveScenarioURLDefault(ctx, "vrooli-bridge").

But the real problem is exactly the one you sensed: "reach a scenario" means two incompatible things in this codebase, and only one of them lives in api-core.

What discovery actually is today

discovery.Resolver routes through cliutil.LookupScenarioPort, a three-rung ladder that is designed to answer from a file and only fork as a last resort, and returns http://localhost:<port>. It caches, collapses concurrent lookups, and handles shadow routing. It is entirely local — and its fast rungs never fire (Rung 04).

It carries a Node field on its Error struct — and nothing anywhere in the repository ever sets it. That vestige is the fossil of the intent you described: discovery was meant to be node-aware, and isn't.

gap  There is no WithNode(id), no remote resolution, no proxied base URL.

Why relay can't just become discovery

RelayService.Call is exec-and-capture, not a proxy. Its request is {node_id, scenario, command, args, timeout, max_response_bytes} and its response is {data bytes, exit_code, reason}. It runs a CLI and hands you stdout.

So a remote caller gets a subprocess, not a service. No streaming, no request headers, no stdin (so a stdin-reading verb cannot be relayed), and the response has to be re-parsed from JSON that the CLI happened to print.

consequence  system-monitor's remote path is a separate handler branch from its local path — not the same code with a different address.

RUNG 04
Correction · a live defect

The fast path that never fires

An earlier draft of this page said discovery "shells out to the Vrooli CLI." That was wrong as a description of the design — and, for a reason nobody wants, right as a description of what runs.

cliutil.LookupScenarioPort is a three-rung ladder whose first rung is a plain file read. It was built exactly as intended. Rungs 1 and 2 miss one hundred percent of the time in production because of a port-key vocabulary mismatch, so every port lookup in the repository falls through to the fork that was supposed to be the last resort.

RUNG 05
The keystone

What would make discovery node-aware

The missing piece is not in api-core — it is one frame kind in the Bridge channel. Today the channel carries jobs, provisioning commands, cleanup, credential pushes, PTY session frames and relay requests. It does not carry a request to a scenario's HTTP surface. Add that, and discovery.ResolveScenarioURL(ctx, slug, WithNode(id)) can return a real base URL that happens to be proxied, and every scenario's existing typed Connect client works against a remote node with no second code path.

Why this is safe, not a hole

The obvious objection to "proxy HTTP to a node" is that it bypasses Bridge's per-verb scope admission. It doesn't have to. scopecatalog.Scope already carries {Scenario, Service, Method, Effect, Permissions}, and Catalog.Reconcile([]RPCMethod) already reports which proto methods have a scope.

Measured across every scenario manifest in the tree: 1,894 of 2,392 governed commands (79%) are already bound to a concrete connect-rpc service and method. A proxy admitted at RPC-method granularity is the same authorization model that admits relay today — arguably tighter, because it names a method rather than a CLI string.

What has to be built

  • A ScenarioRequest / ScenarioResponse pair in the ServerFrame / NodeFrame oneofs. The envelope is already signed, correlated and cancellable — this extends it rather than inventing a channel.
  • A proxy endpoint on Bridge that admits per method from the scope catalog and forwards the frame.
  • A WithNode(id) option on discovery.ResolveScenarioURL, plus the credential and scope plumbing folded in from nodeclient.
  • For secrets, not a new relay field: route the operator-input secret kind to the credential grant/push path that already seals, delivers and receipts values end to end (Rung 12).

payoff  Every scenario becomes target-aware for the cost of a base-URL parameter. system-monitor's two branches collapse to one. Onboarding gets a target for free.

RUNG 06
Your second question

service.json vs operator-state.json

Keep both. This split is already correct, and it is the one thing in this map that needs no redesign.

They are not two places to configure the same thing — they are a declaration layer and a selection layer, and the schema says so in its own words: operator-state holds "what was selected on this install", while "what scenarios/resources/tools/safeguards exist and what they declare lives in scenario service.json, resource.json, tool.json, and safeguard.json".

The decisive proof is in .gitignore: .vrooli/service.json is committed; .vrooli/operator-state.json is ignored. Collapsing them would mean either committing per-machine choices into the repo or losing the manifests. Neither is acceptable.

The layering works in practice, not just on paper. The project manifest declares 26 host safeguards; operator-state records 9 opted in, several with typed config values (remote_desktop_access carries seven booleans and a provider choice). The setup path genuinely reads it — internal/hostreq and internal/resources/catalog both load it at their resolver boundary.

So: is operator-state sufficient to describe a machine? Two honest gaps.

Gap 1 — environment is a preset masquerading as a setting

--environment development|production|minimal appears nowhere in the operator-state schema, and on inspection it should not. Its only mechanism anywhere in the system is filtering host tool and safeguard declarations by their environments list. No resource manifest declares environments at all, and nothing reads it after setup.

Repo-wide there are exactly two distinct declared sets: development (17 declarations, all of them the build toolchain — go, node, pnpm, python, java, quint, buf, the protoc plugins) and development,production,minimal (8, which filters nothing). So the three-valued enum carries one bit — is this a machine that compiles Vrooli — and production and minimal select identical requirement sets today. Operator-state's host_tools.<name>.opted_in already expresses that axis with 17 booleans instead of one bit.

fix  Do not add the field. Make environment a named preset that expands into an operator-state document — the same treatment Bridge's six profiles get — so the coarse form disappears from the wire instead of being persisted beside the fine one.

Gap 2 — it is addressed by path, not by target

Every consumer constructs operatorstate.New(Config{RepoRoot: root}). The document is reachable only as a file inside a checkout on the local filesystem. There is no Load(ctx, target), no proto representation, and no way to hold two machines' documents side by side.

That is the structural reason Bridge invented a parallel vocabulary instead of just reading operator-state: it had nothing to read. Give the document a target and a wire form and Bridge's six-profile enum has no reason to exist.

fix  A proto contract plus a remote loader that goes through Fig. 5's proxy.

Direct answer to what you asked: operator-state.json should be the source of truth for how a node gets set up, including a remote one, and it is one change away from being able to be: it needs an address, not a new field. Nothing needs to be merged or deleted, and environment should be retired into a preset rather than persisted.

RUNG 09
Rendering

Is the component library ready to carry this?

Your instinct was right about the direction and half right about the readiness. RCL has built the pieces you would render with. It has not built the seam you would feed them through — and that seam is the whole point of a data-driven form.

Built and directly usable

  • GeneratedForm v1.0.8 — schema-driven, sections, controlled/uncontrolled
  • Form · FormField · FormSection · FormActions · ValidationSummary
  • ConditionalField · ComputedField · ArrayField · ObjectField · AsyncOptionsField
  • FormStore scoped store service
  • ProgressLadder · AsyncFormFlow · ApprovalPrompt · AuditTrail · ConflictResolutionFlow
  • DiffViewer · VerdictSummary · FindingList · EditableResource

Missing and needed here

  • FormWizard — multi-step controller with per-step validation and resumable drafts. Onboarding is a wizard; this is the shape-defining gap.
  • PasswordInput — the SSH password field
  • PinInput — the pairing code field
  • GeneratedSettingsForm — the "re-apply config to an existing node" surface
  • MultiSelect — scenario and resource pickers
  • AutosaveIndicator

The decisive gap

GeneratedForm's field spec is function-valued: when, compute, format, renderItem, objectChildren. It is declarative in TypeScript — not serializable, so a server-supplied JSON schema cannot drive it as-is.

The catalog anticipated this: GeneratedForm declares expects: validation-adapter, and there is a whole adapters domain describing exactly this seam. Zero of its 17 adapters are built.

01

Complete the configuration contract

Make operator-state genuinely sufficient, and make it addressable. Nothing merges, nothing is deleted.

  • Retire environment into a preset that expands into an operator-state document, rather than adding it as a field. It carries one bit today (build toolchain or not) and operator-state already says that more precisely.
  • Publish operator-state and operatorinput.Request as proto (setup/v1), each carrying a target. The queue is already a validated eight-kind typed schema — this is a serialization, not a redesign.
  • Add Load(ctx, target) to internal/operatorstate alongside the existing RepoRoot path.

unlocks  One document can describe any machine. Everything below depends on this.

02

Make reach uniform

The architectural keystone, and the direct answer to your suspicion about nodeclient. Repair the local ladder first — it is a small fix and everything else inherits it.

  • Fix the port-key mismatch (Rung 04). Normalize in cliutil — share internal/scenario.runtimePortCandidates, or lift it into a package both can import — so rungs 1 and 2 can actually match. Then replace the stubbed ladder tests with a fixture peer record and a fixture DB row, and rewrite the eight stale comments across discovery and cliutil that describe the fork as the operation.
  • Add ScenarioRequest/ScenarioResponse to the channel's ServerFrame/NodeFrame oneofs, admitted per RPC method from the scope catalog (which already indexes {scenario, service, method} for 79% of governed commands).
  • Leave secrets out of the relay — the credential grant/push path already carries them sealed and receipted (Rung 12). Add sealed_stdin only if some non-credential stdin verb turns out to need it.
  • Give discovery.ResolveScenarioURL a WithNode(id) option that returns the proxy base URL — the same shape as the local answer.
  • Relocate nodeclient to api-core/nodereach and shrink it to owner credentials, scope pre-validation and the admission taxonomy. Fix secrets-manager's single call, which only ever wanted discovery.ResolveScenarioURLDefault.

unlocks  Every scenario becomes target-aware for the price of a base-URL parameter. system-monitor's two branches collapse to one.

03

Give vrooli-onboarding a target

The same move you made on system-monitor — but landing on Pattern B rather than Pattern A.

  • Author scenarios/vrooli-onboarding/cli/manifest.json declaring its existing verbs with effects and RPC bindings. Cheapest unblock in this document; it works even before Phase 2 lands.
  • Thread a target through the API handlers so every step resolves against a chosen machine rather than the local repo root.
  • Put a machine picker in the wizard shell. The wizard's own ten steps do not change.

unlocks  minimouse's two credential blockers become answerable from your laptop.

04

Bridge stops flattening

Once operator-state has an address, Bridge's parallel vocabulary has no reason to exist.

  • StartOnboarding takes an operator-state document instead of four setup strings.
  • The six built-in profiles become named presets over that document — keeping the useful naming while dropping the lossy schema. Their currently-empty scenario lists become real.
  • Bridge's onboard form renders the same GeneratedForm the wizard renders, sourced from the target machine's actual closure rather than from typing.

unlocks  The struck-through fields in Rung 06 stop being dropped. Bridge's 843-line onboard form becomes a schema plus a target.

05

Web Console gains the fourth door

Pure plumbing by this point. Bridge remains the only implementation of SSH onboarding.

  • Expose the onboard domain through api-core/nodereach — it currently wraps registry, pairing, relay, session, dispatch, gate, machines and runs, but not onboard.
  • Add Preflight · Start · Get · Wait · Cancel to web-console's MachineService as a thin proxy.
  • Replace the "server" door's printed CLI string with a real form and a live step ladder.
  • Add a machine detail surface — re-apply configuration, view drift, view the audit trail — from EditableResource, ProgressLadder, AuditTrail, VerdictSummary.

unlocks  A desktop-only Web Console user can bring a machine from bare OS to fully configured without opening Bridge.

06

Commission three RCL assets, then collapse the forks

Build them through components draft-begin so they land as governed, versioned, story-covered assets rather than one scenario's private code.

  • ValidationAdapter — the schema-to-fields seam GeneratedForm already declares it expects. This is the asset that makes "data-driven" mean "wire-driven".
  • FormWizard — per-step validation boundaries, optional branches, resumable drafts. Every wizard in the system currently hand-rolls this.
  • PasswordInput and PinInput — one place where reveal-toggle, paste handling, autocomplete hints and never-log discipline are decided.
  • Then adoptions suggest → batch-apply on Bridge and onboarding; delete their private forks and replace onboarding's vacuous adoption test with one that asserts the import boundary.

unlocks  One renderer any surface can point at any machine's question set.

RUNG 11
Guardrails

Three things not to build

Don't iframe the onboarding UI

Both scenarios already depend on @vrooli/iframe-bridge, so it looks like the obvious reuse path. It isn't: that package does child-side storage shimming and shortcut relay, and — decisively — the onboarding UI talks to localhost and has no concept of which machine. Embedding it would show this host's configuration inside a page about a different host. The target parameter has to come first; after that, embedding is unnecessary anyway.

Don't delete nodeclient before Phase 2

It holds real behaviour that discovery does not: owner-credential formatting, local scope pre-validation, the typed admission taxonomy, and the PTY websocket upgrade. Removing it without first giving discovery a node would push all of that into six scenarios. Relocate and shrink it — don't delete it.

Don't build a private form kit

The tempting shortcut is a bespoke Web Console wizard, because RCL's wizard doesn't exist yet. That is exactly how three Button forks happened. Commissioning FormWizard as a catalog asset costs more once and removes the fourth, fifth and sixth copy permanently — and the same wizard is wanted by every scenario-to-<platform> flow.

RUNG 12
Second correction

Credentials already cross the wire

A complete, sealed, receipted credential-delivery path exists end to end. It has no operator entry point, which is why it reads as missing.

An earlier draft recommended adding a sealed_stdin field to the relay so secrets could reach a node. That was the wrong fix. Bridge already delivers credential values to nodes through a dedicated path that is better than anything a relay stdin field would give you.

RUNG 13
Status

Settled, and still open

Most of the target architecture is now understood well enough to plan against. What remains is mostly one real decision and a handful of design details that only matter once you commit to the proxy. They are listed in the order they block work.

Settled — verified in the tree

  • Who owns what across the four systems, and that Bridge's reach layer is finished and should not be rebuilt.
  • service.json and operator-state.json are a declaration layer and a selection layer. Keep both; the split is correct.
  • Operator-state is two changes from sufficiency: a missing environment field, and a missing target parameter.
  • nodeclient is legitimate but misplaced — relocate to api-core/nodereach and shrink, don't delete.
  • The discovery ladder's first two rungs are inert on a port-key mismatch; the fix is normalization plus a non-stubbed test.
  • The scope catalog already indexes {scenario, service, method} for 79% of governed commands, so per-method proxy admission is available.
  • vrooli-onboarding has no cli/manifest.json, and that alone blocks every relayed call to it.
  • Credentials already have a complete sealed transport; only the operator entry point is missing.
  • RCL's form runtime is built, its adapter layer is not (0 of 17), and GeneratedForm has zero consumers.
Open questionWhy it is openBlocks
Who owns desired state — the node or the control plane? Bridge's Machine already carries desired_profile_id, configuration_state, configuration_unmet and a ComputeDrift function, which implies the control plane wants to own desired state. The node's operator-state.json is the applied state. Once the document is addressable, one of them has to be authoritative — and that decides reconciliation semantics, what drift means, and what happens when someone edits the file on the node directly. This is a decision, not a discovery. Phases 1, 3, 4
Does the onboarding UI take a target, or become headless? Two different architectures, and the plan currently implies both. (a) Onboarding's own UI gains a machine picker — cheaper, proven by system-monitor, but a desktop-only Web Console user still has to open a second app. (b) Onboarding becomes a headless schema service and Web Console renders it — right for the deployed-desktop case, more work, and only avoids duplication if the schema is genuinely the contract. Probably both in that order, but it is a product call. Phases 3, 5
What identity does a proxied request carry? Web Console deliberately never lets browser credentials reach a node. When Bridge forwards a request to a scenario's local port on the node, what principal does that scenario see, and who signs the inner request? Unresolved, and it is the security-relevant part of the proxy design. Phase 2
Unary only, or streaming too? The channel already carries bidirectional PTY session frames, so streaming is mechanically possible. Whether the scenario proxy supports server-streaming RPCs — and what happens to a scenario whose surface needs them — is unspecified. Phase 2
Can the agent resolve local scenario ports at all? The proxy needs the agent to find vrooli-onboarding's port on the node. That is the same cliutil ladder — so it inherits the Rung 04 bug — and it also requires the agent to run as a user with access to ~/.vrooli/peers/. Not yet verified either way. Phase 2
What happens when the node's credential store is locked? The push writes into the node's own durable sink, which on macOS is the Keychain and has its own unlock story. A push to a node whose store is sealed needs defined behaviour — queue, reject, or hold ephemeral. Not traced. Phase 3
What vocabulary does ValidationAdapter speak? GeneratedForm's when and compute are functions, so a wire schema needs either a constrained predicate vocabulary or an evaluator. Separately, operatorinput.Request has no conditional or dependency fields at all today — so either the adapter needs less than feared, or the schema needs more. Undecided. Phase 6
RESOLVED — environment is a preset, not a field Investigated rather than assumed. Its only mechanism is filtering host requirements by their environments list; no resource manifest uses it and nothing reads it after setup. Repo-wide there are two distinct sets — development (17, all build toolchain) and development,production,minimal (8, a no-op) — so it carries one bit, and production and minimal are identical today. Operator-state's per-tool opt-ins already say it better. closed
Keep rung 2 of the lookup ladder? It shells sqlite3 to avoid a CGO driver in every CLI consumer. Once rung 1 works it fires only when a scenario runs without a live peer record. Small, but a real fork-versus-simplicity call. Phase 2 — minor
Shortest path to a plan: settle desired-versus-observed ownership first. Phases 1, 3 and 4 all change shape depending on the answer, and everything else is either verified or a detail that resolves once the proxy is being built rather than argued about beforehand.
RUNG 14
Why now

The same seam is the cloud prerequisite

When a person buys compute — a VPS they own, or one you provision for them — what they get is an SSH endpoint and a password. Everything in this document is on the critical path for that: reach a raw host from a UI, decide what it should be, collect the answers only a person can give, apply, observe, and re-apply later when the answer changes.

The cloud case adds no new architecture. It adds volume — many machines, non-technical owners, no terminal — which is exactly the pressure that makes "you must be present at the machine" fail. Building the seam now for one Mac mini on your LAN costs the same as building it later for a fleet, and you get to debug it against a machine you can walk over to.

The test to hold this work against: a person who has only ever seen the Web Console desktop app, holding nothing but an address and a password, can bring a machine from bare OS to fully configured and watch it happen — and can come back a week later, change one answer, and re-apply.
