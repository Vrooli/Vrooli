Reaching minimouse

What has to be built, generalized and deleted so that web-console can open a shell on minimouse and system-monitor can read its vitals — with the code left more portable than it was, and evidence that settles it.

The two outcomes

What finished looks like

Everything below exists to make these two sentences true, on this hardware, without configuration.

Outcome A

A shell on minimouse, from web-console

Start web-console with no Bridge environment variables set. minimouse appears in Machines within two seconds. Open a session; get an interactive darwin shell that resizes, survives a reconnect, and closes cleanly. No credential reaches the browser.

Outcome B

minimouse’s vitals, in system-monitor

Switch the machine control to minimouse. CPU, memory, disk and the device graph are the Mac’s, sourced from its darwin collectors. The identity strip says whose numbers these are. Disconnect freezes the view with a stamped age and reconnects itself.

Measured today, on the live fleet

One probe changed the plan

Outcome B looked like UI work. It is not: the transport that would carry it is broken for every scenario-owned verb, on every node, and nothing in the repository exercises that path.

a root verb, relayed to minimouse — works
$ vrooli scenario status minimouse/system-monitor --json
{ "success": true, "scenario": { "name": "system-monitor",
  "status": "stopped", "processes": 0, ... } }        ← the Mac's real answer
a scenario-owned verb, same node, same second — fails
$ vrooli-bridge relay call --node-id 25c7e426… \
    --scenario system-monitor --command "system-monitor metrics current"

{ "outcome": "RELAY_CALL_OUTCOME_FAILED",
  "reason": "exec: \"system-monitor\": executable file not found in $PATH",
  "exit_code": 127 }

The mechanism is exact. BuildArgv has a branch for scenario-owned verbs that sets argv[0] to the scenario name and discards the operator-configured binary path entirely, so the CLI is resolved from whatever PATH the agent inherited from its service manager. The runner does build a better PATH — commandEnvironment adds ~/.vrooli/bin and the toolchain directories — but it assigns it to cmd.Env after exec.Command has already resolved the binary against the parent’s environment. The constructed PATH never participates in the lookup that fails.

All 38 of system-monitor’s CLI commands are run_eligible with declared effects, so they are already in the derived dispatch vocabulary, and minimouse already holds *:read. Admission passes. Execution is what fails. Outcome B is one correctly-placed resolution away from working, and no test in the repository covers a scenario-owned verb on a real node — the unit test asserts the argv shape and stops there.

The work

Seven workstreams

Each names what to add, what to delete, and what has to be true about portability — then states a done condition that can be checked rather than judged. The first three are prerequisites; the last four can run in parallel once they land.

W1

Make the node CLI resolvable, not guessable

Unblocks Outcome B. Smallest workstream, largest consequence.

Add

  • Split cliinstall in two and promote the resolution half to packages/: finding an installed scenario CLI needs only a home directory; installing one needs a repository. Today both live behind NewManager(root, home) in internal/, which a node cannot use and a desktop install cannot satisfy.
  • Resolve every scenario verb to an absolute path before exec, from the same directory the node’s vrooli binary lives in.
  • A live-node test that dispatches a scenario-owned verb and asserts a real payload — not an argv shape.

Delete / fix

  • The argv[0] = verbTokens[0] branch in BuildArgv. argv[0] becomes operator-resolved on both branches, which also restores the metacharacter invariant its own comment claims.
  • The dead commandEnvironment PATH work, or make it actually participate in resolution. Right now it is careful code that cannot affect the outcome.

Portability

  • Absolute-path exec behaves identically on darwin, linux and Windows. PATH-based resolution does not — service managers give minimal environments, and launchd, systemd and the Windows SCM each give a different one.
  • The resolution seam must not require a repository checkout, or nodes installed from a desktop package can never run a scenario verb.

Done when

vrooli-bridge relay call --scenario system-monitor --command "system-monitor metrics current" against minimouse returns a JSON payload with darwin values and exit code 0 — and the same holds for a verb whose CLI was not yet built on the node.

W2

One node client, six wirings deleted

The package every consumer uses instead of inventing its own reach.

Add

  • packages/nodeclient with four verbs: list(), call(), dispatch(), open(). Typed []string arguments end to end, in-process Connect rather than subprocess forks, and a timeout that is owned rather than defaulted.
  • Bridge located by slug through ResolveScenarioURLDefault, per request, with the env var as an override only. The pattern already exists in scenario-to-ios.
  • open() promoted into the typed contract, so streaming stops being a literal WebSocket path that only web-console knows.

Delete

  • discovery/default_remote.go’s rival relay encoder — seed the client from vroolicli/remote.go, the only correct one.
  • Both copies of bridgeNodeList / bridgeRelayEnvelope; the dead TimeoutSeconds and MaxResponseBytes fields; the PortKey-carries-a-verb abuse.
  • Several historical environment namespaces and web-console’s private registry client; current fleet consumers use packages/nodeclient, with program-runtime’s private sidecar variables retained.
  • web-console’s remoteTerminalTarget, in favour of targetmodel.Target.

Portability

  • Dropping subprocess forks removes the assumption that a CLI is on PATH in the calling process — the same class of bug as W1, one layer up.
  • Move the delivery-ramp device vocabulary (android-emulator, cdp, screen-recording) out of targetmodel so the shared node model stops encoding one consumer’s platform assumptions.

Done when

A repository search for the legacy untyped Bridge endpoint variable returns no production hits; every consumer reaches nodes through the shared client; and CSV argument flattening no longer exists on any path, verified by relaying an argument containing a comma.

W3

Make reachability tell the truth

Every surface inherits these answers; wrong here is wrong everywhere.

Add

  • One typed readiness vocabulary in targetmodel: a check identity, a label, a pass state and a recovery action, resolved from the identity.
  • A staleness rule that is computed, not reported: a node with no heartbeat age is not fresh.

Delete / fix

  • The three parallel readiness enumerations in web-console and the string-keyed switch that couples them.
  • The empty bridge-node: placeholder row, and every recovery action that cannot work — starting with “Start Bridge” while Bridge is running.
  • The presence ordering defect. Live today: swarminator reports online: true, heartbeat_fresh: true with a last_seen_at of seven days ago and no age field at all.

Portability

  • Recovery actions must not assume a shell or a terminal. The desktop deployment has neither, so each action names an in-app destination.

Done when

A node last seen seven days ago renders as not-responding in every surface, with the age shown; and no recovery action in the product names a step the user cannot take from inside the app.

W4

Linking a machine without a shell

The day-one flow. Verified on a scratch node, never by re-linking minimouse.

Add

  • An mDNS responder on the control plane advertising _vrooli-bridge._tcp.local — the record the agent already browses for and nothing publishes.
  • A node-side client for RequestPairing, and the follow-through that turns an approval into credentials. The RPCs and four CLI verbs already exist with no caller.
  • A verification phrase derived from both keys, shown on each machine, matched by the person.
  • Permission presets over ApprovePairingRequest.scopes, replacing wildcard defaults with a narrow one that is also the easy one.
  • The agent binary shipped by the installer, not built on arrival.

Delete

  • The agent’s hand-rolled 395-line DNS-SD browser — its query encoder, message parser, name decompressor and TXT reader — in favour of packages/mdns-go, which device-control already imports.
  • The assumption that joining implies git clone and make setup. Keep that path for developer nodes; it must stop being the only one.

Portability

  • mdns-go already splits its listener across listen_linux and listen_other; the responder needs the same treatment plus a documented Windows firewall prompt.
  • Bundling means one agent per platform in the installer. The cross-builder covers linux and darwin on amd64 and arm64 — Windows is out of scope for the node agent and should be stated rather than discovered.
  • Autostart differs per platform (launchd, systemd, SCM). The bootstrap already handles the first two; the bundled path needs the same coverage.

Done when

A scratch machine with only the installed app joins the fleet from the UI in under a minute: it appears by itself on the LAN, shows matching words on both screens, is granted a preset narrower than *:write, and reaches ONLINE — with no terminal, no repository and no code typed by hand.

W5

web-console: machines, and a shell on one

Outcome A. Screens 01–04 of the mockups.

Add

  • A Machines surface: linked machines, honest reachability, the grant in a sentence, and a working Add flow.
  • Session open / resize / close against a selected machine, with the identity of that machine visible for the life of the session.
  • Reconnect behaviour that states what it is doing and what it will do next.

Delete

  • bridge_pty.go’s private WebSocket framing, once open() exists in the node client.
  • remote_targets.go’s credential resolution, registry client, and the uncancellable context.Background() health probe on every catalog read.

Portability

  • The remote shell already degrades correctly: a real PTY where one exists, a bounded pipe fallback elsewhere, and resize rejected rather than faked. Keep that honesty visible in the UI rather than hiding it.
  • Credentials stay server-side. A node must never receive browser credentials, and the browser must never receive Bridge’s.

Done when

From a cold start with no Bridge environment variables, minimouse is listed within two seconds; a session opens; uname -a returns Darwin; resize takes effect; the session survives a control-plane restart or says plainly that it did not; and no Bridge token appears in any browser-visible payload.

W6

system-monitor: the machine as app state

Outcome B. Screens 05–07. Greenfield — zero bridge references today.

Add

  • A machine context that scopes every query, plus a machine-keyed cache so switching back does not refetch and two machines’ series never merge.
  • The header switcher, including Add a machine… so the flow is reachable without opening vrooli-bridge.
  • The identity strip, and a frozen-with-timestamp degraded state on disconnect.
  • Actions gated by the machine’s grant, disabled with the reason rather than failing after the click.

Decide first

  • Relay the CLI verbs (works the moment W1 lands, no new Bridge surface, one round trip per sample) or proxy the typed API (better for live streams, a real new surface with real auth questions).
  • Recommendation: relay now — it reaches Outcome B and proves the path — and design the proxy separately rather than letting it block this.

Portability

  • system-monitor is already cross-platform: sampler, memory, paging and network all split across darwin, linux and windows, and the device graph has a real collect_darwin alongside its sysfs path. This is not a porting project.
  • Panels must render a platform’s absent metrics as absent rather than zero — a Mac has no sysfs fragmentation figure, and a zero there is a lie.

Done when

Switching to minimouse renders CPU, memory, disk and the device graph from darwin collectors; the strip names the machine throughout; unavailable-on-darwin panels say so; pulling the network freezes the view with one shared timestamp and it recovers unattended.

W7

Evidence that settles it

Produced as the work lands, not reconstructed afterwards.

Add

  • An evidence record under docs/reference/cross-platform-effort/evidence/, following the phase-C2 precedent: dated, with commands, correlation ids and verbatim outputs.
  • Screen capture of both outcomes, showing the machine identity in frame at the same time as the remote data.
  • A regression test that dispatches a scenario-owned verb to a real node, so W1 cannot silently return.

Rules

  • Every claim carries the command that produced it. A screenshot alone proves a render, not a round trip.
  • Negative evidence counts: capture the degraded and denied paths, not only the green one.
  • Record what was not covered. Silence reads as coverage.

Portability

  • Evidence is a two-machine claim: linux control plane, darwin node. Note the pair explicitly, because a single-host run would pass while proving nothing.

Done when

Someone who was not present can read the record, re-run the commands against the same fleet, and get the same answers — including the failures.

Standing constraint

minimouse stays linked

The one thing that would break it

Nothing in W1, W2, W3, W5 or W6 touches the pairing — they change how we reach a node, not how it is enrolled. W4 is the exception: it changes the join path, and the tempting way to test a join path is to re-join a machine you already have.

So W4 is verified on a scratch node — a VM or a spare box — and minimouse is never re-onboarded, never re-provisioned, and never used to test pairing. Its enrollment is treated as production data for the duration.

Two related cautions. minimouse is a working-tree node at revision 3e5bccc5cd…+dirty with no fetchable commit, so fleet rolls and provision sync exclude it by design — do not "fix" that by reprovisioning. And its grants are currently *:read and *:write; when W4 introduces presets, narrow minimouse deliberately and separately, after both outcomes are proven, so a permission change never gets confused with a transport failure.

Deliverables

What exists at the end that does not exist now

A shared node client package

packages/nodeclient — four verbs, typed arguments, owned timeouts, Bridge located by slug. Six private wirings and four environment namespaces removed in the same change, so the deletion is part of the deliverable rather than a follow-up.

A portable CLI-resolution seam

The resolution half of cliinstall promoted out of internal/, usable by a node with no repository checkout, so a scenario verb dispatched to any machine resolves to a real binary on every supported platform.

One readiness vocabulary

Check identity, label, state and recovery action defined once in targetmodel and consumed everywhere — replacing three parallel lists coupled by string matching, and carrying a staleness rule that cannot report a week-old node as fresh.

A join path for people without terminals

LAN advertisement, a node-side join request, key-derived verification words, permission presets, and an agent the installer already placed on disk. The developer path stays; it stops being the only one.

Machines as a product surface in two apps

web-console gains machines and remote sessions; system-monitor gains a machine axis through its whole UI. Both consume the same client and the same vocabulary, so the third app costs a fraction of the second.

A reproducible evidence record

Dated, command-level, two-machine, including the degraded and denied paths and an explicit statement of what was not covered — plus a regression test that keeps the scenario-verb path from silently breaking again.

Documentation that matches the code

vrooli-bridge’s README and discovery documentation now describe the implemented Bridge responder and shared agent browser. The manual URL remains the documented cross-network fallback.

Sequence

Order, and what each step unblocks

StepWorkRiskWhy here
1W1 — node CLI resolutionLowSmall, isolated, and Outcome B is impossible without it. Proves the fleet can run scenario verbs before anything is built on that assumption.
2W2 — the node clientMediumEverything after this consumes it. Doing it later means writing the UI twice. The risk is breadth, not depth — it touches seven consumers.
3W3 — readiness truthLowCheap once W2 centralises the model, and every screen in W5 and W6 renders its output.
4W5 — web-consoleMediumOutcome A. First proof that the client carries a real product surface, and the streaming verb gets exercised by its hardest consumer first.
5W6 — system-monitorLowOutcome B. Deliberately second: it is the test of whether the second app was cheap. If it is not, W2 is not finished.
6W4 — linkingHighLast, because it is the only workstream that can disturb an existing link, and because doing it earlier would mean designing the UI before the client exists.
—W7 — evidenceLowContinuous. Each step lands with its own record; the final document assembles them rather than reconstructing them.

One honest note on scope. Steps 1 through 5 are bounded and mostly deletion — the designs are already right and the code is already mostly written. Step 6 is a different size: bundling an agent, advertising on a LAN, and getting a trust handshake right are product work, not cleanup. It is placed last so that if it has to wait, both outcomes are already true and demonstrable without it.
