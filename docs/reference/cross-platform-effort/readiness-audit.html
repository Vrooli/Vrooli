Thread 1 · the requirements model

Two layers exist. One is switched off.

This is the full picture of how something becomes "required," across all four kinds.

.vrooli/service.jsonproject layer
committed
Declares hostTools and hostSafeguards, each with required, environments (development / production / minimal) and when (setup / develop / test). All 19 hostTools are required: true.
.vrooli/operator-state.jsonpersonal layer
gitignored · 0600
Schema supports host_tools.<name>.opted_in, resources.<id>.enabled, scenarios.<name> and active_profile. Only host_safeguards is populated today — 9 opt-ins on this machine.
bootstrapAwareRequirementscode override
hardcoded
Forces git and Go required-and-first regardless of declaration, and silently drops docker from the global set even though the project manifest marks it required in all three environments.

The one line that disables the personal layer

The schema for host_tools says it plainly: "Required tools (per the manifest's required: true) bypass this and are always installed." Since every one of the 19 project hostTools is required: true, the opt-in map can never apply to any of them. The layer you want already exists — it is just structurally unreachable.

What is actually being forced on a new developer

development those eight plus go, node, pnpm, python, java, quint, buf, protoc, protoc-gen-go, protoc-gen-connect-go, protoc-gen-es 11 more, all mandatory

rasdaemon, mcelog and kdump-tools are Linux RAS and crash-dump tooling with no macOS or Windows equivalent — and they are required in the minimal profile. A minimal setup on a Mac mini will try to install kernel crash-dump tooling before it does anything else.

Answering your instinct directly

You said you personally want a lot installed but should not impose that on other developers. That is exactly the split the two layers were designed for, and your preferences are on the wrong side of it. java, quint, python and the four protoc plugins are your working set, declared in the committed manifest as mandatory for everyone. Move them to required: false in service.json and record opted_in: true in your own operator-state.json, and nothing about your machine changes while a new developer stops inheriting your toolbox.

Two supporting signals that this is the intended discipline: scenario-level hostTools already do it — 23 declared required: false against 11 true — and active_profile is reserved in the schema with docs/configuration/profiles.md explaining that profiles are deliberately deferred until a second concrete profile exists. A second developer is that second profile.

The six external-cli pairs are not wired to each other — the driver probes the external command directly and each resource ships its own resource-<name> CLI wrapper. They are parallel declarations of the same third-party binary, not a designed pairing. internal/tools/tools.go embeds */tool.json, so a directory existing is enough to register a tool — nothing had to opt these in.

Recommendation

Delete internal/tools/vault/. It is the stray, and it contradicts the resource that already handles vault correctly. Then decide the general rule for the other six: either the resource registry is the authority for third-party binaries a resource wraps and the tool entries go, or the tool registry stays and the resources reference it — but not two independent declarations that can drift, which is precisely how vault ended up saying two different things.

This also corrects my rev-3 advice. The bespoke 336-LOC stager in cmd/vrooli-dist/vault_server.go is a separate question and still worth a look — but the resource archetype already implements install-if-missing / use-if-present, so the stager is solving a problem the resource layer solved.

Thread 3 · remote provisioning

Prebuilt bundles for a Pi — my read

Your idea is good and I would reframe the unit of work. The thing that is slow on a Pi is not "downloading things," it is compiling 275 modules. So the artifact worth shipping is a build result, not a bundle format.

Frame it as a portable build cache

Go already gives you the primitive. A build result is fully determined by {GOOS, GOARCH, toolchain version, module graph, build flags} — and packages/api-core/staleness/checker.go already hashes exactly that set (GOOS, GOARCH, CGO_ENABLED, GOFLAGS, GOEXPERIMENT, GOAMD64, GOARM). Cross-compiling for linux/arm64 on your workstation and shipping the binaries plus a warmed cache keyed by that digest gets the Pi to a running system without inventing a new distribution format — and my sweep already proved linux/arm64 builds clean with zero arch-specific breaks.

The transport already exists in two halves

  • The index and staging half: resource-artifacts-v1.txt plus the installer's verify-and-place loop already ship checksummed per-os/arch binaries into ~/.vrooli/artifacts/. Generalising that to scenario binaries is an extension of a working mechanism.
  • The delivery half: Bridge dispatches typed {scenario, verb, args} jobs to a node of any OS and never touches a shell. Pushing a payload before running setup fits its existing model.

The asymmetry to plan around

This works for the Pi and does not work for macOS credentials. internal/resources/securestore/store_darwin.go uses cgo for the Keychain, so a darwin binary cross-compiled from Linux has no credential backend — the code even names the escape hatch AllowMissingDarwinKeychain and says a release must never set it. So: Pi can be provisioned from your workstation; a Mac must build its own credential path locally. Worth knowing before the plan assumes one mechanism covers both.

Publish, or keep it Bridge-controlled?

Your instinct is right, and the repo already argues for it. The config space is 48 tools × 25 resources × 135 scenarios × per-operator opt-ins — publishing pre-baked bundles across that is not a product, it is a combinatorial explosion. Bridge-controlled per-node provisioning targets exactly one config: the one you chose for that node.

There is one future case for publishing, and it is already scoped: docs/configuration/profiles.md defines a profile as "a named bundle of scenario + resource selections," gives three worked examples, and defers the feature until a second concrete profile exists. Publishing makes sense per named profile and only then — the number of artifacts becomes the number of profiles, not the size of the config space. Until profiles ship, Bridge-controlled is the correct and only sane scope.

Thread 4 · testkit adoption

One field forbids it, and the schema already knows the answer

// packages/testkit-go/.vrooli/package.json
"adoption": {
  "scenario_adoptable": false,          ← the only false in the repo
  "allowed_consumers": ["internal_platform"],
  "adoption_modes": []
}

Every other package declares scenario_adoptable: true. And the schema already models the distinction you described between your UI component library and a normal Go dependency:

Adoption modeMeaningPackages using it
go_module_replaceImport — one shared version, updates flow api-core, cli-core, freshness-go, maturity-go, repo-contract-go
file_dependencyCopy with attribution — the UI model you built api-base, audio-capture-browser, iframe-bridge, vitest-requirement-reporter
generated_artifactEmitted, not authoredproto

allowed_consumers is equally specific and already includes scenario_test as a first-class class — declared today by api-core, freshness-go, maturity-go, proto and vitest-requirement-reporter. The consumer class for exactly this use case exists and testkit-go does not claim it.

The change

"adoption": {
  "scenario_adoptable": true,
  "allowed_consumers": ["internal_platform", "scenario_test", "template_api", "template_cli"],
  "adoption_modes": ["go_module_replace"]
}

Plus a go.mod, and keeping the four internal/-dependent fixtures (scenariofixture, processfixture, packagefixture, resourcefixture) out of the scenario-facing surface. The root package is already dependency-clean and its doc.go already says that is deliberate.

Enforcement without hardcoding — your constraint, and it is satisfiable

You are right to refuse a rule that hardcodes "look for a hand-rolled clock." The substrate to avoid that already exists: 113 of 135 scenarios carry a .vrooli/testing.json with a unit.policy_profile.policy_classes.<class> structure, and unit-health already projects data-declared rules into checks (projection_report.go) rather than hardcoding them — testutil.production_import_ban is a JSON field, not a Go literal.

The derivation should run in this direction:

1. testkit-go's .vrooli/package.json declares what it provides
     → needs one new schema field, e.g. provides: [{concern, import_path}]
2. unit-health reads every packages/*/.vrooli/package.json where
     allowed_consumers includes "scenario_test"
3. for each declared concern, it checks whether the scenario hand-rolls it
     → finding, with the ladder rung driven by adoption %
4. testkit adds a concern → the rule extends automatically
     nothing in unit-health changes, nothing drifts

The only new construct is the provides field on the package manifest. Everything else — the manifest layer, the consumer classes, the per-scenario policy file, unit-health's projection machinery, the maturity ladder — is already built. And because the rule reads the manifest rather than a list, it stays correct when testkit grows, which is exactly the property you asked for.

Where four revisions landed

The estimate of remaining work went down every round, and the reason is consistent: this project keeps having built the mechanism and left it unwired. The personal config layer exists and no tool can reach it. The adoption-mode vocabulary exists and one package opts out. The artifact index exists and carries one entry. Bridge allowlists the exact verb the Mac mini needs. The genuinely new engineering is one platform package, one provides field, one compatibility schema, and a go.mod. Most of the rest is deciding to turn on what is already there.
