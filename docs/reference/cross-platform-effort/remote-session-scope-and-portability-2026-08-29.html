Reproduction

What actually failed

Three symptoms, one root cause and two independent UI defects that hid it.

You selected minimouse in the machine picker, chose Empty Shell, and got [internal] PTY spawn failed: node client transport node="25c7e426…" websocket: bad handshake — rendered behind the New Terminal sheet, greyed out by its own scrim.

That message carries almost no information, so I queried the live control plane directly. The node is healthy on every dimension Bridge measures, and is missing exactly one thing:

scenarios/vrooli-bridge/api/handlers/channel/session_ws.go:63 reads the node's grants from the registry and hands them to session.Manager.Open, which returns ErrScopeDenied unless the list contains vrooli-bridge:session (internal/session/types.go:171). The handler answers 403 before the WebSocket upgrade. Gorilla reports any non-101 response as websocket: bad handshake — and the client throws away the response that would have said why.

Root cause

Supply and demand never met

The scope the handler enforces is not a value the grant model can produce.

Node grants come from pairing presets. Presets are derived from the CLI scope catalog, and the catalog mints exactly one shape of value: Value: scenario + ":" + string(effect) (packages/api-core/scopecatalog/catalog.go:368). Effect is one of read, write, destructive. There is no path from a CLI manifest to the string vrooli-bridge:session, so full-control is as powerless here as read-only.

The convention already existed — on the other transport

This is the part that changes the fix. Bridge's relay path solved this exact problem, and solved it well. discovery.ResolveScenario admits a remote command like this: 

packages/api-core/discovery/transport.go:113-121

  required, ok := r.commandScope(command)              // what the verb costs
  if !scopecatalog.Resolve(target.Scopes, required) { … }
  _, effect, concrete := strings.Cut(required, ":")
  transportScope := "vrooli-bridge:" + effect          // transport authority
  if !scopecatalog.Resolve(target.Scopes, transportScope) { … }

scenarios/vrooli-bridge/api/internal/dispatch/allowlist.go

  // A node must hold both the namespace-and-effect grant and Bridge's
  // transport-level effect capability.

So the fleet already has a working rule for “may this node be reached over this transport”: reuse the effect namespace. vrooli-bridge:read and vrooli-bridge:write are values the catalog produces, the presets grant, and your node already holds. The relay path works today because it followed that rule.

The session channel didn't. It introduced vrooli-bridge:session — a fourth effect, outside the catalog's vocabulary, with no producer. The root cause is not that nobody considered transport authority; it is that two transports on the same control plane chose two different conventions, and only one of them is grantable.

What I now recommend

  • Make the session channel require vrooli-bridge:write, exactly as the relay path derives its transport scope
  • Zero new machinery: operate and full-control already grant it, and minimouse already holds it
  • One convention across both transports, so the next one cannot diverge

The one decision this needs

  • An interactive shell is unbounded authority — a case exists for vrooli-bridge:destructive as the floor instead
  • write matches the preset labels and operator expectation: “operate” should mean you can get a shell
  • Either way it is a one-line change to the same mechanism — but the plan must state which, and why

This supersedes the capability-register idea in an earlier draft of this page. A register would have been new machinery to admit a value that never needed to exist.

Corroboration that this shipped unseen. scenarios/vrooli-bridge/requirements/04-job-dispatch/module.json:17 still states that vrooli-bridge:session “is reserved for a future interactive protocol and is not implemented here.” The protocol shipped; the requirement never moved, so nothing ever pulled the scope into the grant model.

The governance rule that should have caught it — and why it couldn't

This is not a case of nobody checking. structure-health runs a repo-wide rule, PROJECT_SCOPE_VOCABULARY, whose entire job is to fail any relying party that enforces a concrete scope the catalog does not know. It missed this on two independent axes, either of which alone would have caught it:

Axis 1 — its grammar

  • The matcher is \b[a-z0-9][a-z0-9-]*:(?:read|write|destructive)\b
  • vrooli-bridge:session cannot match it
  • The comment is explicit: “Wildcard grants and transport capabilities are deliberately outside this concrete-scope rule”

Axis 2 — its reach

  • It walks four hardcoded directories, not the repo
  • api-core/discovery, agent-manager/…/phases, vrooli-bridge/…/dispatch, vrooli-bridge/…/registry
  • vrooli-bridge/api/internal/session — where the scope is actually declared and enforced — is not in the list

That reframes the fix. It is not “remember to add a preset”; it is make transport capabilities first-class members of the vocabulary so the rule that already exists can see them, and replace the hardcoded directory list with a repo-wide walk so the next enforcement site is not invisible by omission.

Correction

What discovery actually does

An earlier revision of this page said discovery forks the CLI and cannot address another machine. Both claims were wrong. Here is the accurate picture, and the real defect underneath it.

Two corrections, stated plainly. (1) The default port lookup does not fork — it reads a peer record in-process, and the CLI fork is the third fallback. (2) The node/scenario@variant address grammar exists, is implemented, and works live against minimouse right now. The fork-storm and remote-addressing work you remember is real and in the tree.

The port lookup is a three-tier ladder, and tier one is a file read

DefaultResolver() constructs with an empty config, which sets sharedLookup: cfg.CommandRunner == nil && cfg.VrooliPath == "" — true. That routes every default call through cliutil.LookupScenarioPort, which tries three sources in order:

packages/cli-core/cliutil/port_detector.go:145-151
TierSourceCostWhen it runs
1lookupPeerRecord — os.ReadFile on ~/.vrooli/peers/<target>.jsonin-processalways first
2lookupRuntimeRegistry — sqlite3, kept behind a subprocess to avoid a CGO dependency for every CLI consumersubprocesspeer-record miss
3runScenarioPortCommand — vrooli scenario portforklast resort

On top of that sit a per-key mutex that collapses concurrent lookups onto one resolution, and positive and negative TTL caches at both the cliutil and resolver layers — the negative cache specifically documented as suppressing “a fork stampede against a stopped scenario.” I described tier three as though it were tier one. The anti-fork-storm work is in place and working as you remembered.

The node axis exists, and it answers

cliutil.SplitAddress parses node/scenario@variant exactly as you described: bare slug is local and live, @variant selects a shadow or other instance, and a node/ prefix selects a machine. discovery.ResolveScenario then resolves the target, rejects revoked or offline nodes, derives the required scope from the catalog, checks both the command scope and the transport scope, and relays. Machine-agnostic operation

Portability: compiles everywhere, proven nowhere

The cross-compilation half of this is genuinely solid. Everything above that rung is either undeclared, unmeasured, or inexpressible in the schema.

What is already good — say it plainly

vrooli capability conformance probes 1,638 targets (code root × OS × arch) and returns 80 findings across 14 code roots. web-console, vrooli-bridge, nodeclient and session-core contribute zero of them — all four build and vet cleanly for linux, macOS and Windows on both amd64 and arm64. The node agent goes further: its Makefile pins a six-platform matrix built CGO_ENABLED=0, with per-OS service managers, per-OS privilege separation and a documented pipe fallback where ConPTY cannot give a real terminal. Node→Bridge is dial-out, so a node never needs an inbound port or a public address.

One caveat on that number. The conformance gate exits 0 with 80 findings — it reports rather than enforces. A cross-compile regression in any of these four components would be visible but not blocking.

Gap 1 — the proof ladder stops one rung short, everywhere

The repo has a genuinely good vocabulary for this. internal/deployability defines eight platform statuses, and it is honest about what each means: build-verified is documented as “code that cross-compiles and passes fixtures but has never run on real hardware of that platform.” Above it sits supported, which maps to QualificationQualified.

Gap 4 — the remaining portability defects

P1

The Bridge address is not a web-console setting

Config

main.go:342 sets bridgeURL := "" with the comment “Bridge endpoint selection belongs to packages/nodeclient,” and nodeclient resolves the hub by slug through discovery. That part is correct and is the same pattern the file uses ten lines away for audio-tools.

What was wrong was the old untyped endpoint variable sitting above it. Nothing in the repository sets it — not a script, a manifest, or a test — yet endpoint() reads it at request time and returns it before consulting the explicitly configured BridgeURL field that four callers already pass. So an ambient global outranks explicit configuration, on a client that web-console constructs once per PTY spawn, meaning two clients can never address two Bridges.

Delete the os.Getenv. Precedence becomes typed field → slug discovery, both caller-controlled, and nothing breaks. Then give web-console a real setting whose default means “resolve locally,” so the field carries intent rather than emptiness. Note what this does not do: discovery locates a hub on this machine, so removing the variable removes the only — undocumented, config-beating — way to run the console off-host. That capability should return through the shape the agent already uses (an explicit control-plane URL plus mDNS), not an env var.

P3

A node's architecture is reported by the binary, not the machine

Self-perpetuating

The agent joins with Facts{OS: runtime.GOOS, Arch: runtime.GOARCH} — the arch it was compiled for. An amd64 build installed on an arm64 machine under emulation reports amd64, and every subsequent artifact Bridge cross-compiles for that node is amd64 forever. Your one node reports darwin/amd64.

The SSH onboarding path does it correctly — it probes the host and normalises aarch64 → arm64. So two sources of truth for the same fact disagree by construction, and the wrong one is the one the fleet stores.

scenarios/vrooli-bridge/agent/main.go:168 · api/internal/onboard/sshdriver.go:255-263
P4

The interactive shell is plaintext by design once it leaves the host

Boundary

Discovery yields http://…; websocketScheme maps that to ws://. The mDNS adapter states the assumption outright: “Bridge commonly serves plain HTTP on a trusted LAN.” On loopback that is fine. The moment an operator sets the old untyped endpoint variable to another machine — the only way to use the console remotely — the Authorization header and a live root-capable shell travel the LAN in the clear.

This is a posture, not a bug, but it is currently incidental rather than stated. A machine-agnostic console needs the boundary made explicit: which deployments may use ws://, and what refuses to start without wss://.

packages/nodeclient/client.go:607 · agent/internal/discovery/mdns_adapter.go:54-61
P5

The advertised address is one interface's guess

Multi-homed hosts

outboundIP() asks the kernel which source address it would use for a TEST-NET destination and advertises that. On a host with a VPN, a container bridge, or both wifi and ethernet, that can be an address no node can route to; with no default route it falls back to 127.0.0.1 and advertises loopback to the LAN. The comment is honest about the fallback; the failure is silent.

P6

A complete SSH backend is wired to nothing

Unreached transport

packages/session-core ships NewSSHBackend, SSHSession and a full sshPTY implementing the same contract as the local and node-agent backends. No caller constructs it. SSH is the portability answer for machines that cannot or should not run a resident agent: locked-down servers, appliances, a box you do not own. The implementation exists; the last wire does not.

F16

The highest-privilege operation in the fleet is the one that checks least

Security

Opening an interactive shell on a remote machine authorizes on two things: the node's grant, and the presence of an owner re-authentication proof. The owner's own scope ceiling — minted into the token, validated by ContainsAll, and carried on auth.Identity.Scopes — is never read by this handler. An operator enrolled with a read-only ceiling can open a full shell on any node that holds the session grant.

Your enrolled ceiling today is ["agent-manager:read", "agent-manager:write", "vrooli-bridge:read", "vrooli-bridge:write"] — and it is irrelevant to whether the session opens.

Where the code belongs

Not a new package — a package that was never finished

Your instinct about api-core was right, and the answer is smaller than a new package.

packages/api-core is a forty-subpackage utility belt — preflight, database, discovery, retry, metrics. Adding an authorization domain concept as a new sibling there would grow the belt, and you were right to push on it. But the domain already has an owner one level down, and its package comment already claims the job: 

packages/api-core/scopecatalog/catalog.go:1

  // Package scopecatalog derives the authorization vocabulary from CLI
  // governance metadata. It deliberately has no dependency on the
  // authenticator or on any scenario package.

It already has fifteen importers — nodeclient, vrooli-bridge (four packages), structure-health, agent-manager. It owns deriving the vocabulary. What leaked out is interpreting it. So the recommendation changes: do not create scopegrammar. Complete scopecatalog.

One line splits cleanly along vocabulary versus policy:

scopecatalog owns — vocabulary

  • Parsing <namespace>:<effect> and wildcards, once
  • TransportScope(required) — the "vrooli-bridge:" + effect derivation that transport.go and allowlist.go each perform inline today, so every transport asks the same question the same way
  • Classification and human summary, so every surface describes a grant identically

vrooli-bridge keeps — policy

  • Which effect each transport requires as its floor
  • What a grant means for admission
  • The owner ceiling and re-authentication rules
Note the scope of the change this implies. With the session channel moved onto the existing convention, the vocabulary work is no longer load-bearing for the fix — it becomes debt reduction that also prevents the next divergence. That is a better position to be in: the unblocking change is one line, and the consolidation can be judged on its own merits rather than smuggled in as a prerequisite.

session-core is the counter-example worth copying: a shared, transport-neutral contract, adopted by web-console through a thin alias file and by scenario-to-cloud directly. The scope vocabulary deserves the same treatment, and scopecatalog is already 80% of the way there.

  • NewSSHBackend and sshPTY in session-core — a complete transport, constructed by nothing
  • LaunchCommand / ExecuteLaunchCommand on session-core.LaunchSpec — set at three seams, read at none, and inherited by scenario-to-cloud because the dead field lives in the shared contract
  • scopes= query parameter sent by nodeclient — ignored whenever a registry exists
  • launcher-target-unavailable warning — reachable only in states the picker already prevents

Rules to adopt

  • A vocabulary constant with no producer is a defect, not a placeholder — emit it or delete it
  • A struct field carried across a process boundary and never read is a claim about completeness that is not true; in a shared package it is that claim made to every consumer
  • Conformance test: every Readiness* identity has at least one emitter
  • Conformance test: every capability the control plane enforces is reachable from at least one preset
  • Conformance test: no exported backend in session-core is unconstructed

The second conformance test is the general form of the root cause. It would have failed the day the session channel shipped, and it will catch the next capability enforced before it is grantable.

Seams to introduce

CanHostSession(node) (bool, reason)

One predicate, three consumers

“Can this node host an interactive session?” is answered independently by targetFromRegistryNode, by the Create preflight, and by nodes doctor — and all three are wrong the same way. One predicate, surfaced as a readiness fact, corrects every surface and makes the next divergence impossible.

dialSession — classify the handshake, don't discard it

Diagnosability

One helper in nodeclient that dials, keeps the *http.Response, and maps 401 → ErrMissingReauth, 403 → ErrMissingScope, 404 → ErrNodeNotFound, 503 → ErrNodeUnavailable, carrying Bridge's reason string. Also the right moment to replace websocket.DefaultDialer — the mutable package global whose 45 s handshake timeout silently exceeds the 30 s call context.

A durable session status channel, not a one-shot ready gate

Diagnosability

Replace readyCh's single-read handshake with a stored terminal status the PTY can report after Read returns io.EOF. Every close reason the protocol already carries then reaches the operator instead of a silently vanishing pane.

One error-mapping seam for local and remote

Simplification

mapCreateError exists and is good; the remote branch simply returns before reaching it. Move mapping to the single point where Create returns, so one place decides what an operator sees and no branch can bypass it by construction. Fix %v → %w in the same pass.

Target-aware launch resolution

Correctness by construction

ResolveWorkingDir() and ResolveShell() are host functions used as session functions. Make resolution take the target: for a remote node the answer is “let the node decide” unless the operator set something explicitly for that machine. The whole off-diagonal column of the portability matrix stops being a bug rather than being patched.

Resumption on the third leg

Reliability

Bridge already keeps the session and the node PTY alive across a transport detach and replays bounded scrollback. Give nodeclient the reconnect its own adapter comment already claims it has: re-dial with the same session id under the same backoff shape the agent uses. This is the difference between a console that works on a laptop and one that works on a laptop that moves.

Presentation strings out of the transport

Payload + tightness

grantDetailForScopes builds a 3,480-character sentence server-side by joining every scope, ships it per node on every catalog refresh, and the picker renders it into a fixed-width chip. The readiness detail should carry the summary; the scope list belongs in the machines drawer, fetched when opened.

Smaller tightenings

  • matchPreset is an exact-set comparison, so a node holding operate plus a capability grant matches no preset and the drawer shows nothing selected. Match on the preset's semantic content instead.
  • Bridge's default session id is a formatted timestamp (session_ws.go:76) — an identity that can collide. Use a UUID like every other id in the system.
  • createInFlight drops a rapid second launch with no feedback at all (useSessionManager.ts:309).
  • Auto-dismiss should apply to informational notices only; an error carrying a recovery action must persist until dismissed or resolved.
  • nodes update --scopes help text describes the grammar as <namespace>:<effect>, which cannot express the one value an operator currently needs to type by hand.
  • vrooli capability conformance exits 0 with 80 findings. Decide whether it is a gate or a report, and make the exit code say so.
