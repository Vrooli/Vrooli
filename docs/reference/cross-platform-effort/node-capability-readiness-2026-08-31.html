01

What actually happened

Not a hypothesis. Every number below was read from the live control plane and the live node while writing this.

The Bridge registry says minimouse is perfect. All five readiness facts pass, the node holds a live channel, its heartbeat is one second old, and it carries *:write. Web Console reads exactly those facts, finds nothing wrong, and offers you the full launcher.

Meanwhile, on the node itself, three of the five coding agents Vrooli manages are not installed — and two of the three are offered by name in the launcher.

Bridge has run onboarding against minimouse.local 159 times (plus one against swarminator and one against loopback). That number is itself a finding.

The two step traces that explain everything

The most recent SUCCEEDED op and the most recent FAILED op run the same 50-odd steps. Both contain:

20 setup          SKIPPED  --skip-setup (node cannot run jobs until setup is run later)
27 setup-finalize  SKIPPED  --skip-setup (native setup deferred)

They diverge only at the end. The SUCCEEDED op has no apply-selection step at all — it simply stops after verify-online-confirm and reports success. The FAILED op attempts apply-selection and dies on five blockers, none of which is about a coding agent.

So a "successful" onboarding on this machine means the agent dialled home. It does not mean the machine was configured, and nothing distinguishes the two.

02

Where the truth is lost

The fact "grok is not installed on minimouse" is knowable at layer 1 and is never carried past it. Eight layers each have a place to put it, and none of them does.

03

Root causes

Eighteen defects, grouped by the thing they break. Severity is about how much of the failure each one explains, not how hard it is to fix.

A · Coding agents are never actually installed

RC-01

The installer is unreachable on every real node

critical

runInstallCommand checks for a source build before it reads install.platforms, and returns. Every coding-agent resource declares cli.source_build: go_module, and every Bridge-onboarded node is a source checkout — the bootstrap ships the working tree. So the branch that would run resource-claude-code install-direct is dead code on exactly the machines that need it. What gets installed instead is Vrooli's own wrapper CLI, which is why every agent reports cli_installed: true while three of them have no binary to wrap.

internal/resources/drivers_cli.go:468-486 — early return runSourceBuild(...) precedes manifest.Install.Platforms[CurrentPlatform()]. Reached from resource install and resource start/restart alike (lines 148, 167, 383).
RC-02

Three upstream download URLs 404 on every platform

critical

Even reached, install-direct would fail for the three agents that are missing. The URL templates interpolate Go's GOOS/GOARCH with no per-vendor naming map. OpenCode publishes opencode-darwin-x64.zip; the template asks for opencode-darwin-amd64.tar.gz — wrong architecture token and wrong archive format. All six URL/platform combinations I checked return HTTP 404. The two agents that are present on minimouse are the two installed through npm, which needs no URL at all.

opencode 1.17.9 darwin/amd64 → 404  ·  linux/amd64 → 404
grok 0.2.72 darwin/amd64 → 404  ·  linux/amd64 → 404
antigravity 1.0.13 darwin/amd64 → 404  ·  linux/amd64 → 404
Real sst/opencode assets today: opencode-darwin-x64.zip, opencode-darwin-arm64.zip; latest tag v1.18.25 vs pinned 1.17.9.
RC-03

vrooli setup is designed never to install a coding agent

major

All five host-tool manifests are manual: true, bundling: host-required, with platform_status: unqualified on all three platforms. Every installer in hostreqkit short-circuits a manual requirement to SupportManualOnly / ExecutionManualActionRequired and returns. This is a deliberate posture, and it may be the right one — but it is currently unstated at every operator surface, so "I ran setup" and "I have a coding agent" have no relationship that anyone is told about.

internal/tools/{claude,codex,opencode,grok,agy}/tool.json · internal/hostreqkit/installers.go:40, 305, 455
RC-04

Web Console does not declare that it needs a coding agent

major

The scenario whose entire purpose is launching coding agents declares exactly one host tool — tmux — and no coding-agent resource dependency at all. Nothing in its closure asks for an ai-cli, so no resolver, no setup run and no readiness report has any reason to notice one is absent.

scenarios/web-console/.vrooli/service.json — hostTools: [tmux]; dependencies.resources lists ollama and openrouter only.

B · Nothing carries per-node capability state

RC-05

The shared readiness vocabulary has no capability rung

critical

Seven readiness identities exist and all seven are transport and trust: registry record, heartbeat, channel, protocol, dispatchable, bridge scope, session support. A node passes all seven while having nothing installed on it. A conformance test asserts every identity has an emitter; nothing asserts the set covers what a session actually needs.

packages/api-core/targetmodel/model.go:59-66 · emitted at scenarios/web-console/api/target_catalog.go:99-116
RC-06

The local target asserts readiness instead of measuring it

major

localTerminalTarget() hardcodes a single fact — "Web Console process, passed: true" — so the machine Web Console runs on is exempt from readiness entirely. If claude vanished from this host, the launcher would look identical.

scenarios/web-console/api/target_catalog.go:85-97
RC-07

The node record has nowhere to put an inventory

major

The registry Node message carries identity, platform, revision, scopes, status and six readiness overlays. It has no field for installed tools, applied configuration, or setup outcome. capabilities is a self-reported verb-namespace list that explicitly grants nothing — and in practice is empty on both registered nodes, as is revision.

packages/proto/schemas/vrooli-bridge/v1/registry/registry.proto:100-166
Live: both nodes report revision=null capabilities=null.
RC-08

The heartbeat already carries a probe channel that nothing reads

major

HealthSnapshot ships on every beat with toolchain_present, disk headroom, container runtime and a free-form details map. The agent's sampler fills it with exec.LookPath probes — precisely the mechanism a coding-agent inventory needs. Bridge stores the latest snapshot per node in Hub.health. Hub.Health() has no callers anywhere in the API.

packages/proto/…/shared/shared.proto:27-33 · agent/internal/health/health.go:57-82 · api/internal/presence/hub.go:31, 356-368

C · "Operator config" is two different things, neither per-node

RC-09

The applied config comes from the control plane's own host

critical

When Bridge asks vrooli-onboarding what to apply to a node, onboarding answers from its own operator state: the scenarios enabled here, the optional resources in this host's closure, the tools and safeguards opted into here. The node's identity is passed in and never used to shape the answer. There is no per-node desired configuration anywhere in the system — every node is asked to become a copy of the control plane.

scenarios/vrooli-onboarding/api/v2_handoff.go:99-124 — the returned Selection is derived from state + closure, both local; HandoffRequest.NodeID is unread.
RC-10

The per-machine profile that does exist carries none of this

major

Bridge machines have a desired_profile_id and version, versioned snapshots, and an audit trail — real machinery. It resolves to one of six hardcoded profiles carrying only a setup environment, suggested scopes, and privileged-op capabilities. No scenarios, no resources, no coding agents. And the profile's setup_environment is never threaded into onboarding's StartInput, so even that one field is decorative.

scenarios/vrooli-bridge/api/internal/machines/policy.go:30-39 — six built-ins · no caller passes snapshot.SetupEnvironment to onboard.StartInput.
RC-11

Desired-vs-applied drift is structurally unrepresentable

major

There is a desired_profile_version and no applied_profile_version; a desired selection and no record of what was actually applied. When the control plane's config changes, no node can be described as behind — the question has no field to be answered in.

machines.proto:41-53 — Machine holds desired state only. orchestrator.go:352 — the readiness report returned by a successful apply is dropped, never persisted.
RC-12

A whole-fleet setup profile silently applies nothing

major

FromSetupProfile filters the tokens all, none and enabled out of the resource and scenario lists. Pass --setup-resources enabled — the natural way to say "everything this install has turned on" — and the Selection comes back empty, requested comes back false, apply-selection never runs, and the op reports SUCCEEDED.

scenarios/vrooli-bridge/api/internal/onboarding/client.go:118-137 — splitNames drops those three tokens; requested = len(Scenarios) > 0 || len(OptionalResources) > 0.

D · Failures are miscategorised, then hidden

RC-13

"Not applicable on this platform" is treated as failure

critical

The completion gate collapses missing and unsupported into one bucket, and any required item in that bucket is a hard blocker. A TPM device grant and a Linux user-namespace sandbox on a Mac are therefore blockers — permanently, since both are required: true in the root manifest with no platform gate, so they cannot be deselected either. Both safeguards' own manifests already say not_applicable for macOS. Nothing reads that.

scenarios/vrooli-onboarding/api/completion.go:67-82 — if host.Status != "missing" && host.Status != "unsupported" { continue }
.vrooli/service.json — workspace_sandbox_userns and tpm_credential_access are required: true, unconditionally.
RC-14

The not-applicable evidence is copy-pasted and wrong

major

Both safeguards' macOS platform_status entries carry the evidence string "Windows does not expose the Linux host interface used by…". The macOS slot is justified by a sentence about Windows. A reviewer reading it would conclude macOS was never assessed — which, given the behaviour above, is the correct conclusion.

internal/safeguards/workspace-sandbox-userns/safeguard.json · internal/safeguards/tpm-credential-access/safeguard.json — platform_status.macos.evidence
RC-15

A backend outage is reported as a missing credential

major

"the credential backend could not answer for this address" maps to unsupported, which maps to a blocker whose remediation is "provide this credential on the credentials step". The operator is told to type in a value when the actual fault is that the store is locked. Two of the five blockers on minimouse are this.

scenarios/vrooli-onboarding/api/v2_readiness.go:270-285 — a status-probe error becomes unsupported with detail "native credential authority unavailable".
RC-16

Onboarding failure lives on the op and never reaches the node

major

Sixteen typed failure reasons exist, with full step histories, diagnostics and durable retry lineage — genuinely good machinery. None of it is projected onto the node. minimouse's four most recent onboarding attempts all failed; the node record shows ONLINE, dispatchable, fully scoped, with no trace. Web Console reads the node record.

api/internal/onboard/types.go:188-236 — 16 FailureReasons, none for "a declared capability is absent". The Node message has no failure or last-configured field.
RC-17

Launching a missing binary is not an error anywhere

major

A remote launch opens a shell on the node and pastes the command into it as text. A missing binary produces command not found in scrollback. The create call returns success, SessionCreated is emitted with the agent type, the metrics counter increments, and the pane is titled after an agent that never started. vrooli agent launch adds no preflight of its own — it execs the binary and lets exec fail.

api/handlers/sessions/adapter.go:188-193 and api/session/session_manager.go:501-505 — paste is best-effort by design, "a convenience the user can retype".
internal/cli/vroolicli/agent.go:66-77 — no LookPath, no install hint; supports 4 runners, not agy.

E · The launcher's agent list is fiction

RC-18

Nine hardcoded shell strings, independent of everything

critical

The agent grid is built from a static TypeScript array folded into five cards. It is not derived from the resource catalog, from operator state, from the selected target, or from anything installed. Antigravity has a resource, a host tool, a runner codec and is installed on this host — and does not appear, because nobody added a string. Grok and OpenCode do appear, on a machine where neither exists.

scenarios/web-console/ui/src/consts/shortcuts.ts:21-79 — DEFAULT_SHORTCUTS, 9 entries. components/launcher/agentGrid.ts folds the "(attributed)" duplicates into 4 agent cards + 1 sign-in.
Two adjacent defects worth filing separately

The --node flag is advertised in every scenario CLI and implemented nowhere. cliapp.GlobalOptions.Node is parsed, documented as "Target a connected node", and read by no code in the repository. agent-manager --node no-such-node runner list returns this host's runners and exits 0 — a CLI that claims to answer about a remote machine and silently answers about the local one.

Relayed human-format output truncates. vrooli-bridge relay call … "resource status" without --json returned 299 bytes on one call and a different prefix on another; the same command with --json returned a stable 34,463 bytes every time. Only the JSON path is currently trustworthy over the relay.

05

Target state

One rule, applied at four seams: a machine's capabilities are observed on the machine, carried as typed facts, and rendered at the moment of choice.

The current model has two states for a target — dispatchable or not — and both are about the wire. The target model needs a second axis: can this machine do the work, expressed in the same ReadinessCheck shape the transport axis already uses, so the existing UI picks it up without new concepts.

Four states, not two. A capability is ready (probed, present), missing (probed, absent, installable here), not applicable (this platform has no route — a permanent, non-blocking fact), or unknown (not probed since the last heartbeat). The fourth state is what stops a stale answer from reading as a good one, and the third is what stops a Mac from failing on a TPM.

The contracts this implies

  • A node's configuration is a per-machine document, not the control plane's mirror. The machine profile grows to carry scenarios, resources and required capabilities, and it is what onboarding applies. Today it carries a setup environment that nothing reads.
  • Applied state is recorded next to desired state. applied_profile_version, applied_at, and the readiness report that a successful apply already returns and currently throws away. Drift becomes a computable difference instead of a question with no field.
  • Onboarding reports a disposition per item, not one exit code. Applied / already-present / not-applicable / blocked / skipped, each with its own reason. "Exit 2 with five blockers in one string" is not a result an operator can act on, and three of the five were not real.
  • Not-applicable never blocks. A required item whose platform declaration says not_applicable is satisfied by that declaration. If the declaration is wrong, fix the declaration — do not make every Mac fail forever.
  • Success means configured. An onboarding op that skipped setup and applied nothing reports paired, not succeeded. Those are different outcomes and the fleet needs to see which one it got.
  • A launch that cannot succeed is refused before the PTY opens. Same refusal shape the target catalog already uses for scope and protocol failures: failed_precondition with a named missing capability and a recovery action.

07

Sequencing

Ordered so each phase is independently useful and none of them is blocked on the one before it landing perfectly. The first two phases are small and stop the bleeding.

  1. Make the truth reachable — RC-01, RC-02

    Move the install.platforms branch ahead of the source-build return, or make source-build build the wrapper and continue. Replace the GOOS/GOARCH URL templates with per-vendor artifact maps and add a platform-gate test that resolves every declared route against the real release index. Right now three of five agents cannot be installed on any platform, and no test says so.

  2. Stop reporting an unconfigured node as green — RC-13, RC-14, RC-16, and the success semantics

    Not-applicable stops being a blocker; the two mislabelled safeguard evidence strings get rewritten; a credential-backend outage gets its own category with its own remediation. An op that skipped setup and applied nothing reports paired, not succeeded. Cheap, and it turns the last four minimouse failures from five blockers into two real ones.

  3. Probe and carry — RC-08, RC-07

    Extend the agent's existing sampler to LookPath the declared ai-cli set, ship it in HealthSnapshot.details, persist it on the node record with a probed_at, and give Hub.Health() its first caller. No new transport, no new schema risk.

  4. Add the capability rung to readiness — RC-05, RC-06

    New identities in targetmodel for capability readiness with the four-state vocabulary. Emit them for bridge nodes from the persisted inventory and for the local target from a live probe. The machine picker starts telling the truth with no UI change at all.

  5. Derive the launcher — RC-18, RC-04, RC-17

    Build the agent grid from the target's capability facts instead of DEFAULT_SHORTCUTS; declare the ai-cli dependency in web-console's manifest so the closure knows it exists; refuse a launch whose agent is missing with failed_precondition and a named capability, the way scope and protocol failures are already refused.

  6. Make configuration per-machine — RC-09, RC-10, RC-11, RC-12

    The largest piece and the one worth designing before building. The machine profile becomes the desired configuration document — scenarios, resources, required capabilities — and is what onboarding applies. Applied state is recorded beside desired state so drift is computable. enabled/all stop being silently dropped.

  7. Install from the console — the new surface

    Only worth building once phases 1 and 3 are real: a governed remote install for one named capability on one named machine, reusing the relay path that already carries vrooli resource status. Until then, mockup 3's honest "here is why the automatic route will not work" is the whole feature.

Loose ends worth filing separately

The dead --node flag across every scenario CLI, and the relay's truncation of human-format output. Neither belongs to this arc, both silently produce wrong answers, and the first one will actively mislead anyone debugging this problem from a terminal.
