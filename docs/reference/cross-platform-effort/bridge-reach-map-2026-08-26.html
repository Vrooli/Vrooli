The mechanism

  • the historical web-console adapter performed a bare Bridge URL read once at boot, with no fallback. The current adapter resolves the control plane through packages/nodeclient and the scenario capability resolver.
  • Nothing sets that variable. It is not in web-console’s .vrooli/service.json; it exists only as a row in a reference doc.
  • Bridge’s API port is fixed at 18767 by its own service manifest (“fixed Bridge control-plane port for LAN admission”). The env var is solving a problem that does not exist.
  • Ten lines below the broken read, the same file registers capabilities.ScenarioChecker{Slug: "audio-tools"} — the resolve-a-sibling-by-slug pattern already exists in this file and Bridge alone doesn’t use it.
  • The recovery action is worse than useless: it tells you to start a service that is healthy, so following the advice confirms nothing and teaches you the feature is broken.
The suspicion, tested

Does Bridge know what a system-monitor is?

No — and this is the strongest part of the design. Bridge carries no scenario-specific logic anywhere in its production code.

The reason is worth understanding, because it is the pattern the rest of this system should copy. Bridge’s typed-verb allowlist — dispatch.manifest.json, the file you would expect to hold the hand-maintained list — is six lines long and contains no verbs at all. It holds two default grant effects and one artifact-output binding. The actual dispatch vocabulary is derived at load time from scopecatalog.BuildResilient(repoRoot), which walks the project CLI manifest and every scenario’s cli/manifest.json. A scenario-owned scope renders as <scenario> <command>; a root one renders bare.

api/internal/dispatch/allowlist.go — the design intent, in its own words
// A node must hold both the namespace-and-effect grant and Bridge's
// transport-level effect capability. The namespace grant follows the
// derived catalog, so adding a command needs no per-node verb edit
// while still granting nothing in an unconceded scenario or effect.

So a new scenario becomes dispatchable across the fleet by declaring governance metadata in its own CLI manifest. Bridge needs no edit, no rebuild, and no redeploy. That is exactly the property you asked for, and it already holds.

The genericity fails one layer up, in two specific places. First, the consumers are not generic: there is no shared client for them to build on, so each one hand-rolls a private wiring — which is why system-monitor would be real work despite Bridge being ready for it. Second, one leak runs the other direction: api-core/targetmodel, documented as the “provider-neutral” node model, carries a device-farm vocabulary — android-sdk, android-emulator, android-webview, cdp, screen-recording — plus three per-platform “authorized” reason strings for Android, iOS and desktop. The shared spine has absorbed one consumer’s vocabulary. Bridge kept its boundary; the model below it did not.

Question 1 — what are the different ways?

Five transports, four shapes of conversation

These are genuinely distinct capabilities, not alternatives. The problem is not that there are five — it is that each one was adopted by exactly one caller, who wired it privately.

Correctness

Arguments cross the CLI hop as one comma-joined string, then get split and trimmed. Any argument containing a comma — a JSON payload, a tag list, a commit message — is silently torn in half, and empty arguments vanish. The proto carries repeated string correctly; only this hop flattens it.

Getting there

The order I would fix these in

Sequenced so that each step makes the next one cheaper, and so you get a working fleet view before any of the larger architecture lands.

Delete the Bridge env vars; resolve by slug

Replace private Bridge URL reads with the shared node client and the same slug-based scenario resolution already used for sibling capabilities; resolve per request rather than once at boot. This alone should make minimouse appear in web-console, and it removes the “Start Bridge” advice that currently fires while Bridge is healthy. Smallest change with the largest visible effect.

Make unreachability explain itself

Every failure the catalog reports should name which rung broke — Bridge not running, no nodes paired, node offline, scope refused — and offer the action that actually repairs that rung. Drop the empty bridge-node: placeholder row entirely. Wrong recovery advice is what turned this feature into something you gave up on. The readiness facts already exist in the proto; they just aren't reaching the surface.

Publish one node client and delete the other five

Promote discovery’s node axis into a real package with list / call / dispatch, an in-process Connect transport instead of subprocess forks, and typed []string args end to end. Seed it from internal/cli/vroolicli/remote.go, which is the only correct relay encoder in the tree — it already mirrors the caller’s timeout onto the transport — and delete default_remote.go’s rival encoding rather than trying to reconcile the two. Then migrate the root CLI, web-console, delivery-ramp-go, notification-hub, scenario-to-ios and the cross-OS gate onto it and remove their private wirings. Fixes the encoding disagreement, the CSV corruption, the unowned timeout and the fork cost in one move, retires four environment namespaces, and is what makes rung L1 a five-line call instead of a copy-paste job.

Add open() — streaming as a first-class verb

Lift web-console’s session framing into the shared client as a typed stream over the declared contract, so PTY, log tail and live metrics are three uses of one primitive rather than three private WebSockets. This is the prerequisite for a remote system-monitor that updates, as opposed to one that renders a single stale snapshot.

Make node identity a UI primitive

A shared node context and picker: node in the route, a per-node API base, a node-scoped query cache, and a persistent indicator so it is never ambiguous which machine you are looking at. Ship it in system-monitor first as the reference implementation. This is the actual answer to “switch the whole UI to another node,” and it belongs in the shared component library so the second scenario costs nothing.

Fix the two trust signals before you rely on them

Give presence a monotonic ordering so a seven-day-old heartbeat can never report fresh, and replace hand-granted scopes with capability-derived grant bundles chosen at onboarding. Until presence is trustworthy you cannot alarm on a node going away; until grants are ergonomic, every operator will keep reaching for *:write and the allowlist stays decorative.

Build the console down to the CLI

Fill Sessions, Rollouts, Trust and Setup from their existing typed APIs, or remove the routes until they are real. An empty page behind a nav item costs more credibility than a missing nav item. The APIs are already there — this is projection work, not new capability.

Your system-monitor idea

It’s the right instinct, and it’s the harder half

System-monitor is a good choice for this — the value is obvious, the data is read-only, and Bridge already carries system-monitor metrics devices in its derived vocabulary. But it needs rung L3, and today it sits below rung L1: the scenario contains no reference to nodes, remotes or Bridge anywhere in its API or UI.

What it specifically needs that does not exist yet:

  • A node context — node in the route, resolved once, threaded to every fetch.
  • A per-node API base — today the UI assumes its own API is local and same-origin.
  • Node-scoped caching — otherwise switching nodes shows the previous machine’s numbers until refetch.
  • Streaming per node — a monitor that cannot update is a screenshot; that is open().
  • A visible node indicator — reading one machine’s disk pressure while believing it is another’s is a genuinely dangerous failure.
  • A read grant that survives onboarding — the C2 log shows the device graph refused for a missing system-monitor:read.

My recommendation: do steps 1 and 2 first and confirm you can see minimouse in web-console. That proves the fleet is real and gives you back the confidence this feature has cost you. Then build the node context in system-monitor as the reference implementation for every scenario that follows — it is a better first case than web-console, because read-only metrics let you get the identity and switching model right before a remote shell raises the stakes.
