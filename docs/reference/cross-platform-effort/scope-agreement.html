Goals

What we are actually trying to achieve

Four goals, ordered. Each later one depends on the ones above it, which is why the sequence at the end is not arbitrary.

G1
Be able to prove a platform claim
Today no verdict in the system records which OS produced it, so "it works on macOS" is unfalsifiable. Everything else is unmeasurable until this is true. The Mac mini is the instrument, not the milestone.
G2
One seam per platform concern, enforced
Not "make it work on macOS" — make it structurally impossible to write non-portable code without declaring it. Eight process implementations become one; the rule that keeps it one lives in a validation scenario, not in review discipline.
G3
Every declaration has one authority
Platform support, requirement level, package adoption, test architecture — each currently has multiple sources that can disagree, and in several cases already do. One vocabulary per concern, and a contract check that fails when a claim outruns its evidence.
G4
A new developer inherits a floor, not a toolbox
The project is being prepared for other developers. The committed manifest should express what the project needs; the operator's own file should express what the operator wants. Both layers exist; today everything is in the wrong one.

The through-line

Three of these four goals are consolidation goals that happen to be prerequisites for portability. That is the shape of this effort: the cross-platform target is what makes the duplication expensive enough to justify removing. Eight process seams were survivable while there was one OS. They are not survivable at four.

Approach

Why this order

The sequence is load-bearing in two places and flexible everywhere else.

PhaseWorkstreamsWhy here
0 · GrantWS-J1–J5 Prerequisite. Encrypted store initialized, scoped sudo granted, SSH key on the Mac mini, secrets provisioned by reference. Four operator steps, done once, before any autonomous work begins. Nothing downstream runs unattended without this.
1 · MeasureWS-A, WS-G1–G2, WS-J6 Load-bearing. Fix what is broken, stand up the Mac mini, make verdicts record their platform, extend the blocked-requirement contract so nothing halts. Until a run can say which OS produced it, every subsequent claim is unfalsifiable.
2 · UnblockWS-C Triage the required set before the Mac mini tries to install kdump-tools. Cheap, and it is the difference between a clean macOS setup and a confusing failure.
3 · SeamWS-B Load-bearing. The largest refactor, and the ban rules must land with it — a consolidation without enforcement re-drifts. Everything downstream is easier once syscall lives in one package.
4 · DeclareWS-D, WS-E, WS-F Independent of each other, all dependent on phase 3's precedent for "one authority, enforced by a health scenario." Can run in parallel.
5 · ProveWS-G3–G4, WS-I Record the evidence, promote the claims, tidy. The matrix becomes honest without being pessimistic.
6 · OptimizeWS-H Prebuilt artifacts pushed over Bridge. An optimization now that the Pi is a full developer machine — nothing else depends on it.
7 · RevokeWS-J7 Not optional. Every grant from phase 0 enumerated and removed, with the revocation verified. The effort is not done while the access it needed still exists.

The one rule I would hold to

No consolidation ships without its enforcement rule in the same change. Merging eight process implementations into one is a week of work that a single well-meaning exec.Command("bash", …) undoes. Every WS-B, WS-D and WS-E item has a named owning health scenario for exactly this reason — the rule is the deliverable, the refactor is how you make the rule passable.

Credential protocol

How the agent works unattended for the duration of this effort

An effort-scoped credential store, created at the start and destroyed at the end, so that a half-provisioned host never turns into a stop-and-ask. It is deliberately temporary scaffolding — the permanent architecture does not change, and one of the store's jobs is to measure whether that architecture holds.

The architecture stays; this is execution scaffolding

One-time elevation is a real feature and this must not erode it. The design principle — you grant elevated permission once to vrooli setup and it provisions everything so it is never needed again — stays exactly as it is. Same for Bridge's one-password-then-keys onboarding and the keyring's self-repair. Nothing below changes the product.

What this section covers is different: during this effort we cannot assume any of that is already provisioned correctly on either machine. New code will add things that need a fresh elevated setup run. The Bridge link may not exist yet, or may not have persisted. The credential store may need repair. Each of those is a stop-and-ask today, and there will be many.

The mechanism, per credential

One store, three entries, two different techniques — because the local sudo case has a strictly better answer than storing a password at all.

NeedTechniqueWhy
Root on this machine
re-run setup after adding privileged code		 NOPASSWD sudoers drop-in, not a stored password No secret material at rest at all. Every invocation is logged by sudo to the system auth log, so the whole run is auditable afterwards. Cannot be used from another machine. Revoked by deleting one file.
Mac mini account
first-touch SSH, re-pairing, node sudo		 askpass helper reading a 0600 value file A password genuinely is required for first-touch. The helper prints it to the consuming process; I pass the helper's path, never its output.
Credential store passphrase
unlock, repair, rewrap		 askpass helper piped to stdin credentials store unlock and keyring repair read from stdin and never print. helper | vrooli credentials store unlock keeps the value out of argv and out of my context.

Where it lives

~/.vrooli-xplat-effort/            0700 — outside the repo, outside .vrooli
  MANIFEST.json                    entry names + purpose + expiry. Safe for me to read.
  askpass-macmini.sh               0700 — prints one value to stdout
  askpass-store.sh                 0700
  .values/                         0700
    macmini                        0600 — I never read these
    store                          0600

Not /tmp or the scratchpad — a verification baseline written there previously was gone three days later, and this effort spans reboots (LaunchAgent persistence and supervisor restart are both on the acceptance list). It has to survive a restart and it has to not be in the repo.

The rules I hold to

  • Never cat, grep, echo or otherwise read anything under .values/, and never capture a helper's stdout into my own context.
  • Only ever indirection: SUDO_ASKPASS=<helper> sudo -A …, SSH_ASKPASS=<helper>, or <helper> | <command reading stdin>.
  • Never a secret in argv — it is visible in the host process list to every local user.
  • Redirect stderr on password-consuming commands, since some echo the value back on failure.
  • If a task cannot be done without me reading a value, I stop and say so rather than reading it.

The store doubles as a measurement instrument

Here is the part worth keeping even after teardown: every time I need the sudo grant for something that is not vrooli setup, that is evidence the one-time-elevation design has a hole. Those uses get logged and become findings — a privileged operation that setup should have provisioned but did not, or a broker registry entry that should exist.

So the scaffolding measures the very principle you want protected. If the count is zero by the end, the architecture held. If it is not, the list is exactly the backlog for making it hold.

What I would ask you to do once, up front

  • Install the sudoers drop-in I generate — one file, your user, removed at teardown.
  • Create the effort store and write the two values into .values/ yourself. I will generate the directory, the helpers and the manifest; you supply only the values.
  • Tell me the Mac mini's hostname and account name — those are not secrets and I need them to reference the entries.

That is it. Everything after — running vrooli setup with elevation, establishing or re-establishing the Bridge link, repairing the credential store, provisioning the Mac mini — I do autonomously.

A concrete gotcha, learned the hard way

Every value provisioned into the credential store must be single-line. A multi-line PEM previously made the entire GNOME login keyring unloadable, taking down remote desktop and every other secret with it. Base64-encode anything with newlines before it goes in.

What "never blocked" can honestly mean

Not "I will never need you" — "I will never stop." That distinction matters because there is at least one failure mode the project itself says is not automatable: the credentials keyring repair help text ends by telling the operator "what only a person can do when it did not" work. Promising zero human involvement would be promising something the tooling explicitly disclaims.

What is achievable: the run never halts. Anything needing a human is recorded as a typed blocked requirement with a stage, a retryable flag and a remediation string, the run continues with everything that does not depend on it, and you get one consolidated list at the end instead of being interrupted N times. The --result-file contract that does this already exists; J6 extends it beyond setup to the whole effort.

Worth saying plainly

An agent with reusable root on your dev machine and SSH into a second machine is a real blast radius, and scoping it is not just hygiene — scoped grants are what make the autonomy work. A broker registry entry and a specific sudoers line survive reboots, need no re-approval, and can be audited afterwards. A password in a file has to be trusted, cannot be scoped, and leaves you with nothing to inspect when the run is over.

All operating systems get the full lifecycle. The proof tier is what you asked for. The quality tier is what makes it worth doing. The durability tier is what stops it decaying back.

The agreement in one paragraph

We are doing a consolidation effort with a portability acceptance test. Fifty-nine items across ten workstreams: fifteen things that are broken, twenty-two duplications collapsed to a single authority, twenty-two new capabilities — most of which are enforcement rules that keep the consolidation from re-drifting. Every operating system gets the full setup + develop lifecycle. The Mac mini is the instrument that makes it measurable and the proof that it worked. If we did only the portability work, we would get a Mac mini running and a codebase with nine process implementations instead of eight. That is the outcome this scope exists to prevent.
