Correction & addendum

The Bridge permission model is not hardcoded — it is mis-keyed

An earlier reading of Wall 2 pointed at the nodes.capabilities column and concluded the command allowlist was a hand-maintained list. That was wrong in a way that changes the fix, so it is corrected here rather than quietly amended above.

What is already right

Bridge holds no hardcoded command vocabulary. dispatch/allowlist.go calls scopecatalog.Build(repoRoot) at init, which walks the root cli/manifest.json plus all 119 scenario manifests and derives 1,813 verbs with their governance.effect. Its checked-in artifact, dispatch.manifest.json, is six lines long and names no verbs.

The profile layer exists too: trustposture.DefaultsFor() maps a per-install stance (personal / shared / hosted) onto default node execution scopes. And scopecatalog already implements the hierarchical grammar — scenario:effect with *, scenario:* and *:effect.

What is wrong

The second grant axis is a literal verb-name prefix glob rather than the scenario namespace the catalog already emits on every scope. That is the per-command maintenance burden, and it is why both live nodes now reject everything.

The safety property behind the dual requirement is real and worth keeping — the code says it plainly: pairing the requirements "prevents adding a new catalog command from widening every existing node that only has the broad effect grant." The unit is the defect, not the idea.

The shape of the fix

Resolve the second axis with scopecatalog.Resolve instead of targetmodel.ScopeAllows, so a node grant reads web-console:read or *:read rather than "scenario status*". A new command in an already-conceded (scenario, effect) pair is covered automatically; a new scenario grants nothing anywhere; write never implies destructive. Same guarantee, no per-command work — and it retires a unit test that currently hardcodes one machine's verb list.

One constraint worth writing down before planning remote federation

packages/api-core/discovery/transport.go already implements the node axis, but a remote resolution deliberately carries no URL: "nodes dial out, so inventing an inbound endpoint would violate the bridge contract." Remote scenario interaction is therefore typed command relay — bounded, single-shot RelayRequest/RelayResponse — not Connect-RPC to a remote scenario. That is precisely why the CLI manifest is the right authorization surface: the CLI verb genuinely is the remote API.

Interactive and streaming work rides a second, separate transport: the binary WebSocket channel gated on vrooli-bridge:session. Two transports by design. A remote scenario status and a remote agent PTY are not the same mechanism, and a plan that assumes they are will mis-scope.

The iOS question

Reachable — with one correction to the premise

You asked whether Claude Code's iOS simulation, being Mac-native, could be proven through a Bridge-dispatched agent. The answer is yes for the capability that matters, and no for the specific feature you were thinking of.

What Anthropic's docs actually say

The iOS simulator pane is a Claude Code Desktop feature on macOS. Per the documentation: it "is available in local sessions only; in cloud and SSH sessions, Claude runs on a machine that can't reach the simulators on your Mac." It also requires Xcode 26.x specifically — the pane does not yet work with Xcode 27, which replaced the Simulator app with Device Hub.

inferred A Bridge-dispatched agent is, architecturally, a remote session. So streaming that GUI pane into Web Console is not the path.

What is the path — and it is better

xcrun simctl is a plain CLI. A headless agent on the Mac can boot a runtime, install an app, launch it, and capture io … screenshot and recordVideo artifacts. That produces durable evidence — files Bridge already knows how to return via produced_artifacts — rather than pixels in a pane.

And the vocabulary already exists: packages/delivery-ramp-go/validationmatrix/host_capabilities.go defines xcodebuild, simctl and ios-simulator as probed capabilities, and refuses to classify a darwin host as iOS-capable until it can genuinely build and boot a simulator.

Two hardware facts to price in now

minimouse is Intel (darwin/amd64). The code already anticipates this — its simulator-runtime hint says "on Intel hosts fetch the universal architecture variant." Intel Macs will run Xcode and simulators for now, but macOS 26 is the last release supporting them, so an Intel Mac mini is a proving ground with a known expiry, not the long-term iOS host.

Also: scenario-to-ios is not the stale relic you remember. The mobile-delivery-ramps plan has eight of nine phases done as of 2026-08-17; the scenario has ~5,950 lines of Go across nine handler domains, all touched this month, and its spine adapters and readiness ladder are implemented. A from-scratch regeneration would destroy recent work. Recommend you inspect before deciding.

Deliverable 3
The real cost
Port Redis first — it is nearly free — then decide Postgres deliberately

The portable pattern is already proven three times over. minio, qdrant and searxng carry the identical driver: managed-service + bundling: vendorable as Postgres and Redis. The only difference is that they declare managed_service.acquisition.targets[] — per-target {when:{os,arch}, url, sha256, archive, layout} — and Postgres declares install: null, binary: null, no targets, with its CLI still shelling out to docker exec.

  • Redis — do it now. 7 real dependents, 12 declarations already disabled. Prune the aspirational ones, then compose a tree the way SearXNG was composed. Note the upstream fact: Redis publishes no official macOS/Windows binaries, and Valkey — the Linux Foundation BSD fork, the natural target — distributes mainly through Homebrew, source and containers rather than plain archives. So this is a compose job, not a URL fetch.
  • Postgres — decide, do not drift. 34 real dependents makes SQLite-first a migration rather than a shortcut. The credible archive source is zonkyio/embedded-postgres-binaries, which repackages official EDB distributions for Darwin and Windows across amd64/arm64 into standardized archives — that maps straight onto the existing acquisition contract and packages/binaryfetch. Verify one thing first: their arm64 macOS artifacts are reportedly fat binaries and less current than x86-64, which the Intel Mac mini will not expose.
  • Docker on macOS remains the cheap answer that contradicts the premise. If you take it, take it explicitly and write the reason down.

Whatever you choose, collapse the three disagreeing platform axes into one authority in the same change, or the next audit will find four.
