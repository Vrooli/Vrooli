Part I

The system as built

What exists today, how it fits together, and what is verifiably true on this machine. An executing agent should read Part I before changing anything — several decisions in Part II only make sense against it.

§ 01

The model, in one page

Four moving parts. A credential is declared in a manifest, held by the authority, stored by whichever backend this host has, and reached either by injection into a foreign process or by direct resolution from Vrooli-authored code.

1. Declaration — internal/credentialspec

A resource manifest or a scenario's service.json declares a descriptor: a logical_id like vrooli/openrouter, a field like api-key, and optionally an env name. The logical ID and field are the durable, backend-neutral address. Nothing else is.

A credential nothing declares is a credential no backup captures. recovery export --all walks declarations, not the store. This is why the package serves both resources and scenarios — before it existed, tunnel-manager's Cloudflare token had no declaration and was invisible to every diagnostic and every bundle.

2. Authority — internal/credentialauthority.Authority

The only durable local credential writer. Owns identity parsing, the three-condition taxonomy, Put/Resolve/Inject/Status/Delete, and the recovery bundle format. Scenarios reach it through packages/credential-authority-go, a thin re-export so a scenario cannot pick its own backend.

3. Storage seam — internal/resources/securestore

Three methods, three error conditions, no fourth. Four implementations: libsecret, macOS Keychain, Windows Credential Manager, and an encrypted file store for hosts with no desktop session. All four pass one shared conformance suite that CI refuses to let you edit silently.

4. Reach — injection or direct resolution

Declaring env is a decision. It puts the value in the target process's environment, readable at /proc/<pid>/environ and inherited by every subprocess. Correct for a Postgres container or a third-party CLI; wrong for code Vrooli writes, which should resolve per-operation through the authority binding — which also means a rotated token takes effect with no restart.

§ 02

How a value moves

The single-line guard is scar tissue

GNOME Keyring stores a passwordless keyring in GKeyFile's textual format, one line per value. Handed a multi-line PEM it wrote the newlines verbatim, produced a file it could no longer parse, then rejected the entire keyring — every unrelated secret in it, including credentials other applications had stored years earlier.

values.go now base64-encodes any value containing a newline, carriage return, or NUL behind a versioned marker vrooli-b64:v1:. Single-line values pass through untouched, so no migration was needed. Tab is deliberately excluded because GKeyFile escapes it losslessly.

§ 03

Three conditions, never two

The most load-bearing idea in the design. Before it, an unreachable session bus was reported as "credential is not configured", so an operator with a perfectly provisioned key was told to provision it again — and a scenario start aborted over a host fault.

ConditionSentinelMeaningOperator action
UnavailableErrProviderUnavailableBackend exists, unreachable now — locked keychain, stopped service, broken session bus.Repair the session.
AbsentErrProviderAbsentNo native store here, or the encrypted store was never initialized.Install a backend, or store init.
UnconfiguredErrUnconfiguredStore answered cleanly, holds no value. A normal answer, never a fault.credentials provision

Enforced structurally, not by convention: Status carries ProviderState alongside Configured, so a caller cannot read "not configured" without also learning whether the store was reachable.

Degradation contract: a missing credential never blocks a scenario start. The variable is omitted rather than injected empty, so a consumer checking presence never sees configured-but-blank. Write paths — recovery export and restore — stay fail-closed, because a bundle written from an unreadable store would look like a backup and not be one.

§ 05

The encrypted file store

  • AAD binding everywhere — entry AAD covers format version, service, and key, length-prefixed. An attacker with write access cannot relocate a low-value token into a privileged slot.
  • tpm2-absent deliberately excluded — systemd-creds accepts it and encrypts under a null key, which would pass every structural check while protecting nothing.
  • Availability is a round-trip proof — the host-bound provider encrypts and decrypts a canary before claiming it works.
  • Honest strength reporting — tpm2 vs host-key are reported separately, because on a Pi possession of the SD card defeats the second.
  • Atomic writes, fsync before rename.
  • Only the passphrase unlock is session-cached, into tmpfs, keyed by a fingerprint of the wrap ciphertexts.

§ 07

The desktop supervisor — current state

This section is the one that changes the plan. The supervisor is a well-structured ~7,000-line Go runtime with clean dependency injection and a screaming-architecture layout — and it has never been built for macOS or Windows, contains zero platform-specific code, and does not currently compile at all.

What is good about it

  • Every external dependency is an injected interface — clock, filesystem, dialer, process runner, command runner, GPU detector, env reader, port allocator, secret store, health checker. This is what makes the cross-platform work tractable rather than a rewrite.
  • The secret store fails closed — NewUnavailableManager preserves the error; no plaintext, app-data, or environment fallback exists.
  • Startup ordering is explicit and correct — paths, secrets, migrations, auth+ports, telemetry, GPU, control API, then services. Services do not start while a required secret is missing; the API stays up so one can be supplied.
  • The IPC port is written to disk after binding, so a port collision falls back to :0 and clients still find it.
  • Bundle secrets already resolve through the shared authority with cross-tier identities — the hard part of Tier 2 credential work is done.

The runtime does not compile — on any platform

resources/vault_bootstrap.go:99 calls vaultbootstrap.Load(store, instanceID) with two arguments. The shared package's signature is Load(store, keys UnsealKeyStore, instanceID) — three. This is uncommitted in-flight work: packages/vaultbootstrap-go/ is untracked and both vault_bootstrap.go files are modified. The desktop copy was not updated when the shared package gained its parameter.

Nothing else in this plan can be verified until this is fixed. It is Phase 0, step 1.

Cross-platform reality

The runtime is a separate Go module (scenarios/scenario-to-desktop/runtime/go.mod). make cross-compile builds ./internal/... ./cmd/... in the root module only, so it never touches the runtime. CI runs go test ./... in that directory on ubuntu-latest alone. The result:

And the runtime contains zero //go:build files. There is no platform-specific code anywhere in it. "Cross-platform" is currently an aspiration that has never been compiled.

§ 10

Whose secret is it?

Two different things are called "secrets", they need different storage, and the fastest way to build something dangerous is to treat them as one.

Operator credentialsEnd-user auth data
ExamplesOpenRouter key, Postgres password, Vault unseal key, SESSION_SECRET, LPBS_API_KEY_ENCRYPTION_KEY, Stripe secret keyA customer's login session, subscription token, API keys they saved in your product
Belongs toWhoever runs the install — you, or your customer on their desktopEach individual user of a running install
How manyTens. One set per install.Thousands. One set per user.
Lives inThe credential authorityThe application's own database, encrypted at rest
Backed up bycredentials recovery exportNormal database backup

They meet at exactly one point: the operator credential is the key that protects the user data. LPBS seals customer API keys with securevalue.Encrypt under LPBS_API_KEY_ENCRYPTION_KEY. Lose that one key and every user's stored token becomes unreadable ciphertext, even though the database backup restored perfectly.

Non-goal for this plan: the per-user layer. It is a separate, correct system. This plan only guarantees that the operator key protecting it survives.

§ 11

Decision: library stays, surface moves

The proposal under discussion was to move project-level secrets code into the secrets-manager scenario, so it benefits from test-genie validation and so bundled apps can reach it through the supervisor's inter-scenario communication. The direction is right. The amendment is what moves.

The precedent: storage-manager

storage-manager did not move the implementation. packages/api-core/storage stayed at project level and is still the authority — every storage-manager file imports it. What moved was the entire operator surface: there is no vrooli storage top-level command at all.

Why secrets cannot move the same way, entirely

Storage had no bootstrap constraint. Credentials do, and it is hard:

  • internal/resources/env/credentials.go:132,209 — DefaultAuthority() runs on every scenario start, from internal/lifecycle. If secrets-manager owned the authority, starting secrets-manager would require secrets-manager.
  • internal/resources/user_host.go:77 and vault_bootstrap.go:114 — securestore.ProbeWritable gates whether a managed Vault is publishable at all. Resource layer, pre-scenario.
  • recovery restore must work on a machine where everything is gone — which is exactly the machine where no scenario is running.

The bootstrap floor, stated precisely

vrooli credentials retains exactly these subcommands, and gains no others: provision, status, doctor, store init, store unlock, store lock, store rewrap, store change-passphrase, recovery export, recovery verify, recovery restore. Everything else moves. The test that decides membership: "must this work on a fresh machine, or on a machine where everything is gone?"

Part III

The plan

Eight phases, ordered by dependency and by what stops a loss. Each names its deliverables as files, its acceptance as commands, and an explicit gate. A phase is complete only when every acceptance line passes.

§ 12

Rules for the executing agent

  • Never print, log, or echo a credential value — not in a test failure, not in a debug line, not in telemetry. Tests assert on presence and identity, never on value.
  • Do not use git for state management. No stash, no checkout, no snapshot commits, no worktrees. This repo has lost uncommitted work to exactly that.
  • Run suites with vrooli scenario test <name>, block once with test-genie runs wait, never poll. See docs/TESTING.md.
  • Test the desired behavior, not the current implementation. Several acceptance criteria below describe behavior that does not exist yet; that is intentional.
  • Phases 0 and A are strictly sequential and come first. Everything after Phase B may be reordered if a dependency allows, but the gates must still pass.
  • File a bug rather than widening scope — prompt-manager skill read report-bug, file to scenario-qa.
  • Log completed non-trivial work — vrooli-memory note --kind work-record with trigger, approach, evidence, outcome.

Phase A

Stop the bleeding — no code changes

Eleven configured credentials, including an irreplaceable Vault unseal key, exist in exactly one place. Five real secrets sit in a plaintext file that no descriptor declares, so no bundle could capture them even if one were made.

Deliverables

  • Export a bundle, then verify it from a different working directory — proving the passphrase actually typed is the one that opens it. Store bundle and passphrase apart, and off this machine.
  • Triage all 17 plaintext keys against §08's table. Confirm each already-declared key with credentials status before deleting anything.
  • Write descriptors for the five undeclared secrets — VAULT_TOKEN, MAILINABOX_ADMIN_PASSWORD, N8N_API_KEY, N8N_PASSWORD, TEST_API_KEY. Place each in the owning resource or scenario manifest. Until a descriptor exists, no bundle can capture them.
  • Move the seven config values (POSTGRES_HOST, POSTGRES_PORT, …) to runtime.env. They are not secrets and must not enter the credential store.
  • Re-export once the new descriptors are provisioned.

Phase B

The credential client — one contract, three transports

The keystone. Ten call sites currently shell out to vrooli credentials and each parses the reply into its own anonymous struct. Inside a desktop bundle every one of them fails, because runtimectl has no credentials command and the shim passes unknown verbs straight through.

Deliverables

  • New package packages/credentialclient-go exposing a single Client interface: Provision, Status, List, Doctor, KeyringInspect, KeyringRepair, RecoveryExport, RecoveryVerify, StoreStatus. Every response is a named exported struct — no anonymous structs anywhere downstream.
  • Transport: in-process. Calls internal/credentialauthority directly. No exec. This is the Tier 1 default and must be selected automatically when the process can reach the authority.
  • Transport: IPC. Speaks to the desktop supervisor's control API over loopback with the bearer token. Implemented in Phase D; in Phase B it exists as the interface plus a stub that returns a typed "transport not available" error.
  • Transport: SSH. Wraps the existing remote invocation for Tier 4. Values on stdin, never in a command string.
  • Add recovery to the doctor JSON payload — whether a receipt exists, its timestamp, entry count, and the list of configured credentials it does not cover. Mirrors what writeRecoveryStatus already prints in text.
  • Replace all ten exec sites: vrooli-onboarding/api/v2_credentials.go:19,23,33 and v2_readiness.go:53; secrets-manager/api/credential_diagnostics.go:13,17, vault_handlers.go:307, vault_status.go:81; vrooli-autoheal/api/internal/checks/infra/rdp.go:388,1279; scenario-to-cloud/api/secrets/writer.go.

Acceptance

grep -rn 'exec.Command.*"credentials"' scenarios/ resources/ internal/ # returns nothing vrooli credentials doctor --format json | jq -e '.recovery.receipt_exists != null' vrooli credentials doctor --format json | jq -e '.recovery.uncovered | type == "array"' go test ./packages/credentialclient-go/... -count=1
  • No exec.Command invocation of the credentials CLI remains anywhere in the repo.
  • doctor --format json carries a recovery object; a host with no receipt reports receipt_exists: false and a non-empty uncovered list.
  • A contract test asserts the JSON shape, so a CLI field rename fails the build instead of silently degrading a consumer.
  • The in-process transport performs zero subprocess spawns — assert this in a test.
Gate: Phases D and E both consume this package. Do not start either until its interface is committed and its in-process transport is green.
Phase C

Supervisor cross-platform hardening

The supervisor has zero platform-specific code and has never been built for macOS or Windows. Before credentials ride on its IPC channel, the channel and the process model must actually work on all three.

Deliverables

  • Replace the bash shim with a Go binary. Delete vrooliShimTemplate from api/bundle/staging.go. Build a small cmd/vrooli-shim in the runtime module, cross-compiled per target and staged as bin/vrooli (bin/vrooli.exe on Windows). This removes the bash and python3 runtime dependencies and gives Windows a shim for the first time.
  • One app-name sanitizer. Make config.SanitizeAppName the single authority. Have secrets.desktopIdentity and the new shim both call it. Add a table test covering My App 2.0, Acme Ltd., Café Tools, and app_v1, asserting all three consumers agree.
  • Platform-correct app-data resolution in the shim. The shim must call os.UserConfigDir() — the same function the supervisor uses — rather than assuming $XDG_CONFIG_HOME. This is what currently breaks macOS, where the supervisor writes to ~/Library/Application Support and the shim reads ~/.config.
  • Platform-correct graceful shutdown. Introduce infra/process_unix.go and infra/process_windows.go behind build tags. Unix keeps SIGTERM-then-SIGKILL. Windows cannot receive os.Interrupt via Process.Signal, so implement a real graceful path — a console control event, or an explicit shutdown request to the service — before falling back to Kill.
  • Process-group containment. Unix: SysProcAttr{Setpgid: true} and signal the group. Windows: assign each service to a Job Object with kill-on-close. Today a service that spawns children leaks them on every platform, because Kill() reaps only the direct child.
  • Enforce loopback on the control API. manifest.Validate currently only checks that IPC.Host is non-empty. Reject any host that is not a loopback address. The control API is about to carry credential operations.
  • Bundle-side platform matrix in CI — extend the Phase 0 job to also run the shim's tests and a smoke test that stages a bundle and resolves the token and port path on each OS.

Acceptance

cd scenarios/scenario-to-desktop/runtime go test ./config/... ./infra/... ./secrets/... -count=1 grep -rn "python3\|#!/usr/bin/env bash" ../api/bundle/ # returns nothing grep -rln '^//go:build' ./infra/ # at least process_unix, process_windows GOOS=windows GOARCH=amd64 go build ./cmd/vrooli-shim # exits 0
  • No bash or python3 appears anywhere in the staged bundle.
  • A Windows bundle contains bin/vrooli.exe.
  • The sanitizer table test passes for all four adversarial app names, across all three consumers.
  • A manifest declaring IPC.Host: "0.0.0.0" fails validation with a named error.
  • A test proves a service's child processes are reaped when the parent is stopped, on the host platform.
  • Windows shutdown does not fall through to Kill for a service that exits cleanly on request.
Gate: the loopback constraint and the Go shim must both land before Phase D exposes credentials over IPC.
Phase D

Credentials over the supervisor's IPC

This is what makes a bundled scenario able to reach the credential authority — and therefore what makes the secrets-manager move viable rather than a relocation of the same breakage.

Deliverables

  • Extend api.Runtime with a credential accessor, and register a /credentials route group on the control API mux: status, provision, list, doctor. Bearer-token guarded like every other authenticated route.
  • Scope the surface deliberately. A bundled app may read and write credentials it declares. It must not be able to enumerate or read credentials belonging to other apps or to a Tier 1 install. Enforce this against the manifest's declared secret set, server-side, and add a test that a request for an undeclared identity is refused.
  • Add credentials to runtimectl so the Go shim can forward vrooli credentials … rather than hitting the default: case.
  • Implement the IPC transport in packages/credentialclient-go, replacing the Phase B stub. Transport selection: in-process when the authority is reachable; IPC when a bundle IPC port and token file are present; SSH when explicitly configured.
  • Never log a value on any of these paths, and confirm the existing telemetry recorder cannot capture one — secrets_updated currently records a count, which is correct; keep it that way.

Acceptance

cd scenarios/scenario-to-desktop/runtime && go test ./api/... -count=1 # in a staged bundle, on each OS: ./bin/vrooli credentials status --identity vrooli/openrouter --field api-key --format json ./bin/vrooli credentials doctor --format json | jq -e '.provider.condition'
  • Both commands succeed inside a staged bundle on Linux, macOS, and Windows.
  • A request for an identity the bundle does not declare returns a refusal, not a value — asserted by test.
  • An unauthenticated request to /credentials is rejected.
  • Telemetry emitted during a provision contains no value and no identity-value pair.
Phase E

secrets-manager becomes the surface

secrets-manager is already a pure surface layer — 11.8k LOC of API, 9.4k of tests, ten CLI domains, and zero imports of securestore or internal/credentialauthority. It shells out for everything. Phase B removed the shelling out; this phase gives it ownership of the experience.

Deliverables

  • Refactor the existing domains first. Bring cli/domains/ up to the current CLI conventions before adding to it. Existing domains: admin, campaigns, deployment, overrides, overview, resources, scenarios, security, vault.
  • Add domains for the moving surface: credential inventory and diagnosis, keyring inspect/repair, backup and recovery orchestration, descriptor authoring and validation, and a tier-aware view of which credentials exist on which host, bundle, and VPS.
  • Move — not copy — vrooli credentials list and vrooli credentials keyring into secrets-manager. Delete them from internal/cli/vroolicli. Two surfaces that must agree forever is the failure this whole plan is correcting.
  • Keep the bootstrap floor intact per §11: provision, status, doctor, store *, recovery * stay in vrooli. Add a test that asserts the retained set exactly, so a later refactor cannot quietly move one of them.
  • Backup orchestration is the headline feature. Staleness tracking, scheduled export reminders, and a one-command "make me a verified bundle" flow. This is the capability whose absence produced F-02.
  • Declare secrets-manager's own credentials as descriptors if it gains any, so it is not exempt from the rule it enforces.

Phase G

The Tier 2 recovery story

A desktop customer has no vrooli install, no repo checkout, and therefore no way to back up or recover what they entered. Survivable for a re-enterable API key; not survivable for a per_install_generated secret, whose value nobody knows — including them.

Deliverables

  • Finish task #21 — the bundle manifest generator must populate logical_id and field from the scenario's declaration for every secret. The bundle-private namespace fallback should become a warning, not a silent second value.
  • Pick and implement one answer for customer recovery. Two credible shapes:
    (a) expose export and restore on the control API so a customer can make their own passphrase-protected bundle from within the app;
    (b) refuse to mint per_install_generated secrets that nothing can recover, deriving them from a customer-held value instead.
    Do not ship the current state — generating unrecoverable secrets with no export path.
  • Test a bundle against a host with no native credential store — a bare Linux VM, no desktop session. That path routes to the encrypted file store, which needs a passphrase or TPM the bundle currently has no way to request. This is the most likely field failure and it is untested.
  • Write down the "may a bundle carry a value" decision. Today it structurally cannot: manifest.Secret has no value field. Record that as a deliberate "no" with its reasoning, so the question is not reopened under deadline.

Acceptance

  • Every generated bundle manifest carries logical_id for every secret sourced from a scenario declaration.
  • A bundle on a store-less host reaches a working state through a documented, tested path — or fails with a named, actionable error. Not a hang.
  • A customer-facing recovery path exists, or generation of unrecoverable secrets is refused. One or the other, tested.
  • The no-values-in-bundles decision is recorded in scenarios/scenario-to-desktop/docs/.
Phase H

Harden and tidy

Nothing here is urgent. All of it is cheap once the above is done, and each item closes a way the system could silently regress.

Deliverables

  • Add a Linux-native CI job. Install libsecret-tools, run gnome-keyring-daemon headless, then run the existing conformance suite with no backend override. libsecret is the most bespoke adapter — 15s timeouts, a gdbus collection probe, session repair, a three-signal not-found heuristic — and the only one CI never exercises.
  • Version the recovery bundle's KDF. recoveryEnvelope records salt and nonce but not the iteration count, and recoveryKey hard-codes 600_000 on read. Add kdf and iterations, read them from the envelope, bump to version: 2, keep reading version 1 at 600k. The store's passphrase wrap already does this correctly — copy its shape.
  • Share the KDF policy constant between internal/credentialauthority/recovery.go and securestore/keyprovider.go. The comment at keyprovider.go:46 claims one policy; today they are two literals in two packages.
  • Add a multi-line round-trip case to the shared conformance suite — assert a PEM survives storage and retrieval on every backend. The guard is tested at the seam; the property every adapter must satisfy is not.
  • Periodic staleness check in autoheal or a scheduled task, so an operator who never runs doctor still learns their bundle has fallen behind.

Acceptance

  • The conformance suite runs against a real libsecret backend in CI and does not skip.
  • A bundle written at version 1 still opens after the KDF policy is raised — asserted by test with a committed fixture.
  • A PEM round-trips byte-identically on every adapter in the conformance suite.

§ 17

Against the four goals

Never lose secrets again

Mechanism built, correct, drilled in CI. Never run here. An unmigrated plaintext file is the sole home of at least four real secrets, and the signal that would say so is invisible to every UI.

Manage through onboarding

Provisioning, diagnosis, and keyring repair are wired. Backup is absent from the wizard; scenario-declared credentials never appear in readiness.

Tier 1 on any OS

Four adapters, one conformance suite, real backends on three runners, no value in argv anywhere. The gap is Linux-native coverage.

Tier 2 — desktop bundles

The storage model is right and the supervisor is well structured. But it does not compile, has never been built for macOS or Windows, has no platform-specific code, and its shim is broken on two of three OSes.

Tier 4 — cloud / SaaS

Deploy path genuinely fixed. The management API beside it still writes remote plaintext through the command line.

§ 18

What this design got right

Worth stating plainly, because the register is long and the underlying work is better than it implies. These are choices that are easy to get wrong and were not:

  • The three-condition taxonomy is carried structurally, not by convention, from an adapter's exit code to the operator's screen.
  • No fallback on ErrUnavailable — the hardest decision in the chain, correctly made, with the reasoning recorded at the decision site.
  • No credential value in argv on any platform — which is why macOS is cgo rather than security -w, and Windows is CREDENTIALW rather than cmdkey.
  • The single-line guard sits at the composition root, so the stored form is backend-independent and a future adapter cannot lose the guarantee.
  • Back up the unseal key, not the root token — a correct, non-obvious blast-radius call.
  • doctor is read-only by default — recognizing that a diagnostic which writes is the wrong tool for a store that is already misbehaving.
  • CI asserts drills ran rather than trusting a green summary a skip would also produce, and refuses a commit that edits the shared conformance suite alongside an adapter.
  • The desktop supervisor's dependency injection is real and complete — ten injected interfaces with a 909-line mock package. It is why Phase C is additive work rather than a rewrite.
  • The comments explain why, with the incident attached. This codebase is unusually readable at the seams that matter; protect that as the migration finishes.
