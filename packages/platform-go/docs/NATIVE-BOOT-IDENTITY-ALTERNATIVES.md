# Native boot identity alternatives

Research checkpoint, 2026-11-11. The parent approved actual-operator native boot and the source migration is active. The final trust baseline is the pinned vendor under the actual operator, as on Linux; stronger owner-home sandbox isolation is not required. This historical alternatives note does not qualify native runtime behavior. The current Darwin design and proof limits are in [Darwin operator jobs](../darwin_owned_backend.md).

## macOS

A root-owned boot LaunchDaemon can run the existing supervisor as the actual operator. `UserName` and `GroupName` select its credentials in the system launchd domain; a user login agent is unnecessary. Root setup can publish that one job and its executable, then leave ordinary supervision, private state and scenario lifecycle under the operator. [Apple launchd.plist source](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5).

The backend must remain canonically owned. Sharing the operator UID removes the dedicated-account boundary, so UID-wide inventory/kill is invalid. A process group alone is also insufficient: launchd cleans the job's surviving group, whereas a non-session-leader can change groups. XNU rejects group changes by a session leader and rejects another setsid by a group leader. [Apple process/session implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_prot.c).

The smallest candidate is a **single-process native child** with explicit kernel denial of future fork/spawn, same-PID image handoff, an isolated session where needed, and an inherited kernel fork/spawn denial for the maintained final body. XNU applies its MAC fork check before both fork and spawn creation. Existing project confinement currently denies only the unsafe IOKit transport; it does not yet provide this process/state boundary. A closed profile and real OpenRGB qualification are required; this cannot be claimed merely by adding a PGID. [Apple process creation implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_fork.c), [Apple MAC process checks](https://github.com/apple-oss-distributions/xnu/blob/main/security/mac_process.c).

Selected recovery design: exact launchd user-domain role-label bootout, with stable unique-birth extinction proof, replaces UID-wide cleanup. Native ServiceManagement typed queries replace non-API print diagnostics. The API/SDK/before-login native qualification is still open.

An earlier alternative considered exact root signaling after the supervisor loses its child handle. Apple's current libproc header and implementation contain `proc_signal_with_audittoken` and `proc_terminate_with_audittoken`; the kernel routes audit-token signaling separately from PID termination. This is a candidate for atomic incarnation-bound signaling instead of inspect-then-kill. The header warns that its interfaces may change and provides no availability annotation on these methods. Shipped SDK/export, supported OS floor, same-user permissions, and execution-version behavior are not yet proven. A pre-exec token must not be assumed to identify the post-exec payload; stable birth identity and the current kernel execution version must be bound correctly. [Apple libproc header](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h), [wrapper](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.c), [kernel dispatch](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c).

If those finite requirements qualify, a permanent privileged Vrooli control plane and dedicated OpenRGB UID are unnecessary for this lane. This would be a maintained native OwnedService backend within the existing supervisor, with persisted predispatch intent, exact birth/image proof, uncertain-submit lookup and retirement. It must not become an unowned exec fallback. General native services that require descendants are a separate capability; a no-child backend must state its contract explicitly.

## Windows

SCM supports an ordinary existing user account, but its service registration needs that account's password unless the account is genuinely passwordless. Managed and virtual service accounts have different native password handling and may have a different principal. The installer must not describe them as the operator identity. [Microsoft CreateService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-createservicew), [service accounts](https://learn.microsoft.com/en-us/windows/win32/ad/about-service-logon-accounts).

Therefore the smallest **SCM** option is the existing operator account with an explicitly supported service-logon credential path, an actual service dispatcher and the maintained owned Job child model. Credential lifecycle and a privileged operator's effective token still need explicit handling. A startup-only SYSTEM process cannot be assumed to transfer its SCM registration to another process: the SCM-launched service process owns the dispatcher connection. [Microsoft service entry point](https://learn.microsoft.com/en-us/windows/win32/services/service-entry-point).

If passwordless boot under the existing operator is required, the existing OS **Task Scheduler** offers another native owner: a boot trigger, S4U logon, and least-privilege run level. Boot-trigger registration is administrative setup; the task runs without an interactive desktop or stored password. Microsoft documents S4U restrictions on network/encrypted-file access, which must be assessed against the actual application rather than hidden. [BootTrigger](https://learn.microsoft.com/en-us/windows/win32/taskschd/boottrigger), [TASK_LOGON_S4U](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/ne-taskschd-task_logon_type), [least-privilege RunLevel](https://learn.microsoft.com/en-us/windows/win32/taskschd/principal-runlevel).

The project already has task rendering/install scaffolding, but its current task adapter does not establish the required exact native instance/action PID, incarnation, uncertainty and retirement contract. It must be matured through that owner, not represented as working by a registration success. The operator supervisor can own the backend's existing atomic Job admission, birth image locks and suspended-child durable claim without a permanent Vrooli SYSTEM broker. Task identity/lifetime proof is a remaining design gate.

An ordinary operator token plus Job provides process containment, not protection of that operator's private ledger. The vendor still needs an independently enforced file/device authority boundary, such as a suitable restricted-token capability with narrow runtime/code/HID ACLs. Same account must not silently mean vendor access to all owner state. This can require explicit setup and qualification; it does not establish a need for a permanent privileged broker.

## Decision recommendation

Prefer the actual-operator boot supervisor and reuse its ordinary state/lifecycle composition. Select the smallest native owner that preserves the real account and boot requirements: LaunchDaemon on macOS; credentialed SCM or qualified S4U Task Scheduler on Windows. Keep native process ownership, immutable image proof and durable admission intact. Prove the finite process-confinement, post-crash signaling, token/state isolation and native manager-instance gates before deleting the prior path. No architecture option has native boot/device qualification yet.
