# Flows — Client Workflow Rehearsal

## First rehearsal: import → simulate → repair → review → handoff

1. The operator submits a synthetic workflow document and title. The importer normalizes supported n8n graph nodes and connections, classifies trigger entry points, strips credentials and secret-shaped values, validates topology and rejects unsupported executable nodes. Set currently permits static literal assignments and simple `$json` path projections; arbitrary expressions are rejected.
2. The service passes only a normalized credential-free graph to its typed engine adapter. Multiple entry points require an explicit trigger selection.
3. The local engine walks connected nodes, follows If/Switch outputs, invokes description-driven synthetic HTTP operations and profile-backed service bindings, and executes included subworkflow or error-workflow graphs with recursion/depth guards. The graph validator rejects output ports outside the selected node adapter's declared output set. Polling triggers receive a small generic synthetic row sample. Static Wait delays are capped at 30 days and represented by a virtual resume trace; the engine never sleeps or persists a deferred execution. Legacy LangChain OpenAI chat and Slack message operations use allowlisted node-type adapters that require synthetic profile entries. Declared `continueErrorOutput` links pass import validation, but failed-operation routing through those ports is not yet simulated. No workflow-provided URL is opened and native service code is never invoked.
4. The engine returns an ordered trace. The service evaluates the seeded fault rule, stores failed assertions, and records repaired results as separate evidence events.
5. The record enters `needs_review`. The operator can inspect provenance, credential replacement counts, simulated calls, fault/repair evidence, and a handoff preview.
6. A human explicitly approves or requests changes. The choice, reviewer note, and timestamp are durable. Successful execution never implies approval.

The graph engine, synthetic OpenAPI/recorded-exchange catalog, and HTTP handler are local contract implementations. Eight sanitized public exports (8258, 16081, 22567, 2713, 5889, 21013, 6920 and 21098) have in-process import/run tests, including public subworkflow and error-handler exports invoked by synthetic parent graphs; this is local simulator evidence, not native n8n import or execution. Workflow 21098 also proves the bounded safe Code parser/evaluator on its unchanged sanitized topology and a generic single-condition Filter. The public 8995 export is retained only as sanitized evidence and fails closed at import: pinned n8n 2.48.0 source declares one OpenAI main output, but the public graph connects three. Component tests cover its bounded Wait and generic profile-backed node adapters, but 8995 receives no workflow run credit. The generic native-operation profile also has a synthetic Gmail/Sheets/HubSpot contract test. No task-runtime routing, TLS/host-alias behavior, external DNS denial, or built-in Gmail/Sheets/CRM behavior inside n8n has been verified. See `docs/internal/SEAMS.md` for the constrained bridge hypothesis and gates.

## State model

`imported → running → needs_review → approved | changes_requested`

A run can instead enter `failed` with a typed reason and retained trace. `approved` and `changes_requested` are operator decisions, never inferred from a successful run. Re-import creates a new immutable workflow revision; it does not overwrite evidence for an earlier run.

## Remaining charter work

Twenty-three distinct retained public community workflows currently count toward the 30-workflow simulator target. Coverage includes webhook, manual, scheduled, polling and subworkflow entry families, configured synthetic error-workflow routing, static profile-driven native services, generic HTTP descriptions, read-only Postgres response mapping, branching, fan-out, Aggregate, bounded safe Code, a generic single-predicate Filter, Set and Split Out data shaping. Polling input and Wait/resume remain virtual simulator semantics only; 8995 is excluded because pinned n8n 2.48.0 OpenAI v1.8 declares one main output but its public graph connects ports 1 and 2. Community-node, large-payload and more complex batch/loop coverage remain gaps. Synthetic error-handler routing is proven, but n8n runtime Error Trigger behavior remains unverified. Ten seeded repair packets and one synthetic Gmail/Sheets/CRM handoff are retained. No public export has run in a task-owned n8n runtime. Remaining: seven more unlike community workflows, native trigger/fault/recovery proof, operator-authorized named-tool replays, fresh scenario gates and operator review. Large payload coverage also requires a separately designed bounded storage/replay path.


## Exporting a synthetic profile to Workspace Sandbox

`DescriptionSimulator.ExportHTTPMockProfile` maps explicitly bound OpenAPI native-operation selectors to the same schema-v1 static HTTP profile accepted by Workspace Sandbox. It emits only exact routes on one `*.synthetic.invalid` host per service, syntheticized JSON response bodies and unique selectors/routes. It fails closed on real hosts, parameterized paths, variable query parameters, duplicate mappings, missing successful JSON fixtures or credential-shaped response fields. It never opens an API-description URL. The opt-in `task_scoped` request path generates a logical task ID in Client Rehearsal; Workspace Sandbox creates the task directory under its configured server-owned root and supplies owner attribution. The service declares/starts the profile, routes matched native operations to the exact companion aliases, reads route-hit evidence, persists it in the handoff, and stops/deletes the Sandbox. The end-to-end service test uses a local fake alias transport and proves the receipt flow. Actual alias resolution from the deployed API process, native n8n traffic, no-egress isolation, and live teardown remain unverified.
