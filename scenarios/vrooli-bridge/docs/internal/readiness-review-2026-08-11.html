Fleet control plane · readiness review

Vrooli Bridge:
what's built, what's broken,
and what "near-perfect" costs

The control plane is architecturally sound and about 80% built. Its reliability problem is not a bug — it is a missing contract. Nothing in the wire protocol ever confirms that a job arrived.

Reviewed 2026-08-11 Branch agi Code 55,308 Go LOC · 426 files · 3 modules Evidence live vrooli-bridge.db (read-only copy) + suite run 20260810-145547

The short version. Bridge has 17 API domains, a signed bidirectional-auth channel, durable runs, provisioning, cross-OS gates, and a real cross-compiled node agent. That is a lot of correct work. But three things are structurally missing, and each one is currently costing you real time:

1. Delivery is never acknowledged. A dispatched job is reported delivered when it is placed in an in-process Go channel. One third of every real job ever run on this bridge never produced a single event and had to be killed by hand.

2. Machine identity is not idempotent. One Mac has minted 17 distinct machine records, and two nodes are each claimed as current by two machines at once.

3. Interactive sessions don't exist. There is no PTY, no stdin, no session frame anywhere in Bridge — while two other scenarios each implement their own rival version of the same thing.

Mechanism · why jobs disappear

The delivery path has no receipt at any hop

Dispatch does eight things in order, and every one of them is individually correct. The failure is in what the sequence reports. Three separate layers each return "delivered" for something weaker than delivery, and no layer ever hears back from the node.

The agent's diagnosis was right, and it under-called one thing. The report you were given identified the queue and the check-then-push race correctly. It framed the fix as making the queue durable. That is necessary but not sufficient — a durable queue still cannot tell whether a frame reached the node, because the acknowledgement does not exist in the protocol. The protocol change is the load-bearing one; the durable queue is what makes the acknowledgement actionable.

Mechanism · why re-pairing keeps failing

One host, seventeen identities

The machines domain is well designed. It has a proper read-time projection that joins machine, trust, policy, registry and presence facts without copying live state into durable storage, and a readiness evaluator that names each missing fact separately. That design is right and worth keeping.

What is missing is an invariant. Nothing in the schema or the service prevents the same physical host from being enrolled twice, and the data shows exactly that happening — repeatedly, because each failed enrollment attempt encourages another one.

Absence · the remote terminal you asked for

Three teams solved the same problem; none of them connected

You want a web-console terminal that runs remotely through Bridge and feels local. Today there is no path at all — and the reason is more interesting than "not built yet."

web-console has a complete local terminal: a PTY package, a WebSocket handler, a CLI domain, and four requirement modules covering pane layout, fidelity, launcher and mobile toolbar. scenario-to-cloud has an independent WebSocket-over-SSH terminal with resize handling. Both work. Bridge has nothing — no PTY, no stdin, no session frame. Its own work ladder explicitly reserves vrooli-bridge:session for "a later Mode-B protocol" and rules PTY out of scope.

Underneath that, the same duplication exists one layer down: Bridge carries 3,754 lines of SSH connection and trust code, scenario-to-cloud carries about 4,000 more, and two files share a filename and a purpose while having diverged by 237 lines.

Coverage · reach vs. requirement

What Bridge can actually talk to

Your requirement for Bridge is that it connects to local machines, VPSes, and testing devices, and drives onboarding on anything that can run Vrooli. Bridge currently models exactly one kind of target: a host that has successfully installed the Vrooli node agent and dials out. Everything else is either unsupported or lives in another scenario.

The program

Nine tracks to a Bridge you'd bet a launch on

Ordered by dependency, not by size. Tracks 1–3 are what make Bridge trustworthy; 4–6 are what make it capable enough for the deployment program you described; 7–9 are what make it professional.

TRACK 1

Delivery becomes a contract

blocking

Add the acknowledgement the protocol never had, then make every layer report the fact it actually knows.

  • Add DeliveryAck to the NodeFrame oneof: the agent confirms each JobPush, ProvisionCommand and AbortJob by id. Bump CHANNEL_PROTOCOL_VERSION to 2 — the compatibility band classifier already exists to gate older agents, so this is a supported change, not a breaking one.
  • Split the run lifecycle into accepted → queued → pushed → acked → running → terminal. Today QUEUED conflates four of those.
  • Add queued_since, delivery_attempts, last_delivery_error and delivery_lease_expires_at to the runs table.
  • Persist the queue, or rebuild it at boot from durable runs. Make the in-memory scheduler a projection of durable state rather than the state itself.
  • Reconcile on startup: sweep every non-terminal run, re-drive it if the node is dispatchable, otherwise terminate it with a typed reason.
  • Run a delivery watchdog. Past the lease with no ack and no RUNNING: requeue up to N times, then terminate node_channel_lost.
  • Enforce timeout_seconds server-side. It is currently enforced only by the agent, which is the one party that may not have received the job.
  • Redeliver on reconnect: a presence-online event promotes that node's undelivered runs.
Done when A soak test kills the agent at each of the seven pipeline stages and, in every case, the run reaches a terminal state with a correct typed reason inside its deadline plus grace. No run is ever non-terminal past that bound — that single invariant is the definition of "reliable" here, and it is currently unmeasured.
TRACK 2

One machine, one identity, forever

blocking
  • Add a partial unique index enforcing a node is current for at most one machine. This is violated twice right now, so ship the migration with a reconciliation step.
  • Fix the identity resolution order: machine UUID, then node UUID, then SSH host-key fingerprint, then hostname. Hostname must be the last resort and must never mint a new machine when a host key already matches.
  • Add machines repair <id>: reuse the existing UUID and Bridge-managed key, revalidate host-key trust, restart the agent, reconnect. Idempotent, and structurally incapable of creating a second machine.
  • Add machines merge for the duplicates that already exist, fully audited.
  • Make machines list, get, trust and onboarding all read the same projection function. Three readers disagreeing is what produced the incident you were told about.
  • Classify enrollment failures. 28 failures with free-text diagnostics should become five named causes with five named remediations.
Done when Onboarding the same host ten times consecutively — including mid-run network drops and an agent restart — yields exactly one machine, one current node, and ten attempt records. And list, get, trust and onboard never disagree under a fuzz test.
TRACK 3

Readiness that cannot lie

blocking

"Online" currently means one thing — a live SSE connection — and operators reasonably read it as "will run my job." Those are different claims and both were true-then-false in the incident.

  • Report five independent facts, never collapsed: durable registry record, heartbeat age, live channel, protocol compatibility, and dispatchable.
  • Expire presence on heartbeat staleness, not only on socket close. A half-open TCP connection currently reads as online until the kernel gives up.
  • Add nodes doctor <id>: walk the ladder, stop at the first failing rung, print the remediation. This is the single highest-value operator command you can add.
Done when A node whose machine is suspended, whose laptop lid is shut, or whose agent is a version behind each render as a visibly different state in the UI, the CLI and the API — and dispatch refuses each with the matching typed error.
TRACK 4

Interactive sessions — the remote terminal

largest net-new

The biggest piece of new work, and the one with the most existing material to reuse.

  • Upgrade the channel to bidirectional. SSE cannot carry stdin. Add a WebSocket channel alongside it (gorilla/websocket is already in the repo) and keep SSE as the constrained-network fallback for jobs. Version negotiation already exists to make this safe.
  • Define one session contract in a new v1/session proto: Open, Data, Resize, Close, with backpressure and a sequence number. Bridge is a relay — it multiplexes console to node, it does not interpret the stream.
  • Extract web-console's PTY into a shared package and have three backends implement the same contract: local PTY, node-agent PTY, and SSH. This is what makes "terminal on a VPS" and "terminal on a paired Mac" the same feature.
  • Give web-console a target selector on its existing launcher. The pane, scrollback, resize and mobile toolbar work is already done and should not be rebuilt.
  • Treat sessions as the highest-privilege verb Bridge has. Its own scope (vrooli-bridge:session, already reserved), owner re-authentication, idle timeout, full recording into the audit sink, and a visible kill switch. An allowlist is meaningless once someone has a shell, so the compensating control has to be recording plus revocation.
  • Fix CheckOrigin: return true in scenario-to-cloud's terminal before any of that code is reused — it accepts WebSocket upgrades from any origin.
Done when A recorded journey opens a terminal on a remote node from web-console, runs an interactive program, resizes the window, survives a 30-second network drop with scrollback intact, and is killed from the Bridge UI — with the full session retrievable from the audit trail afterwards.
TRACK 5

Reach beyond agent-capable hosts

unblocks VPS + devices
  • Introduce a typed NodeKind: agent (dial-out, full capability), ssh (agentless, Bridge-initiated, sessions and commands only), and attached (a device hanging off a host node).
  • Rebuild the attached domain to the shape every other domain uses — repository seam, schema.sql, proto-free service, adapter. Then it can actually carry test-device support.
  • Consolidate the SSH stacks. One package. Bridge owns connection, trust and session; scenario-to-cloud owns provider lifecycle and provisioning recipes. That matches the split you already lean toward, and it retires roughly 4,000 duplicated lines.
  • Fix macOS: the launchd install fails over SSH because a GUI domain isn't available. Either use a LaunchDaemon, or detect the SSH-only session and report a typed, actionable failure instead of raw exit status 125.
  • Give Windows a first real run. The agent cross-compiles for it and has never executed on it.
Done when A fresh VPS goes from bare IP to enrolled, provisioned, dispatchable and terminal-accessible in one command, and a device with no agent appears in the fleet with correctly reduced capabilities rather than as an error.
TRACK 6

Wire Bridge to vrooli-onboarding

integration

There is currently zero code referencing vrooli-onboarding from Bridge, or Bridge from vrooli-onboarding, in either direction. The two scenarios are strangers.

  • Bridge onboarding should hand off to vrooli-onboarding once a host is reachable, rather than running a fixed twelve-step script.
  • Selection of which scenarios and resources to run — and which are "important" versus "core" for vrooli-autoheal — belongs to vrooli-onboarding, with Bridge supplying the transport and the machine identity.
  • The subset computation you described — the union of every scenario, resource, tool and safeguard needed by the selection — should be one function with one owner, callable from CLI, API and UI. Deciding where it lives is a real design question worth settling before either scenario builds it.
Done when Onboarding a new machine through Bridge presents the same configuration experience as onboarding locally, and the resulting node runs exactly the selected set — verified by comparing the requested union against what autoheal actually supervises.
TRACK 7

The surface people actually touch

UX

Seventeen API domains, fourteen CLI groups, three product UI features. The UI is a dashboard with a fleet panel, a run list, and settings.

  • An information architecture that matches the domains: Fleet (machines and nodes with the five-fact readiness), Sessions (terminals), Work (dispatch, runs, queue), Rollouts (provisioning, fleet roll, gates), Trust (pairing, credentials, audit), Setup (the onboarding wizard).
  • The onboarding wizard is the highest-leverage UI you can build. Today a failure surfaces as a raw log tail ending in a Homebrew banner and a launchctl error. It should be a resumable wizard with per-step status, a plain-language cause, and a repair button wired to Track 2's repair verb.
  • Mirror it exactly in the CLI — same step names, same states, same remediation strings — so an agent driving Bridge headlessly sees what a human sees.
  • Live run output, queue depth per node, and the delivery state from Track 1 all need to be visible. An operator should never have to open SQLite to learn that a job is stuck; that is how the current incident was diagnosed.
Done when Every domain with an operator verb has a surface, and a new user can enroll a machine and run their first job without reading documentation.
TRACK 8

Security to a payments-grade bar

hardening
  • Close G8. The two-principal privilege separation is proven structurally in-process by an AST import-graph test, and the service renderer supports --service-user, but the live install path installs only the single unprivileged runner. Provisioning currently runs in the user agent's context — the designed second principal does not exist at runtime.
  • Triage the 6 gitleaks findings and 4 gosec G101 hits to zero-or-annotated. Carrying secret-scanner hits forward is exactly the habit you cannot have when Stripe keys enter the picture.
  • Route the audit sink to the tamper-evident substrate. The seam exists and is proven swappable; only the implementation is missing.
  • Session recording, owner re-auth and revocation for Track 4 — treated as part of that track's definition of done, not as follow-up.
Done when The security phase is green with no suppressions that lack a written justification, and a privileged provisioning action is demonstrably running as a different OS principal than the job runner.
TRACK 9

Proof: green suite, real journeys, continuous soak

validation
  • Clear the six red phases. Five are hours-to-days; the proto v1/shared move is the one-day keystone that has blocked green since June and is what makes all 22 requirement records truthful.
  • Write the regression suite this incident earned: disconnect between the online check and the push; queued job followed by reconnect; control-plane restart with in-flight runs; missing RUNNING event; lease expiry; list/get/trust/onboard consistency; agent restart followed by successful dispatch.
  • Build the BAS journeys. There are zero product journeys today. Enroll, repair, dispatch, follow, abort, open a session, roll the fleet — each recorded as video evidence, which is also what feeds deployment-manager's review.
  • Run a continuous multi-node soak with injected disconnects, asserting the one invariant from Track 1. Reliability that isn't measured continuously regresses silently.
Done when 20/20 phases green, all 22 requirements complete, and a 24-hour soak across Linux and macOS nodes with random agent kills produces zero non-terminal runs past deadline.

Sequencing

What I'd do first

Track 1, then Track 9's regression tests, in the same pass. The acknowledgement frame is a small protocol change with a large blast radius of benefit, and it is the prerequisite for trusting anything else you build on Bridge. Writing the seven regression tests alongside it — rather than after — is what keeps the fix honest.

Track 2 immediately after, because every hour spent re-onboarding is an hour of duplicate machines, and because Track 4 needs a stable machine identity to attach sessions to.

Then the proto v1/shared move — out of order relative to its track, because it is one day of work that unblocks a green suite, and a green suite is what turns 22 in_progress records into evidence you can point at.

Track 4 is the largest and most interesting piece, but it should follow 1–3. Building an interactive session layer on top of a channel that cannot confirm delivery and a registry that duplicates identities would inherit both problems at a much higher cost to fix.

Decisions I need from you

Four questions worth settling before code

  1. SSH ownership. You lean toward scenario-to-cloud owning VPS lifecycle with Bridge owning connection and onboarding. I agree — with one amendment: the SSH transport and host-key trust should be a shared package that both consume, not owned by either. Provider lifecycle stays in scenario-to-cloud; connection, trust, identity and session go to Bridge.
  2. Channel transport. Adding WebSocket alongside SSE is the conservative path and keeps the constrained-network fallback. Replacing SSE entirely is simpler to reason about but loses that fallback. I'd add alongside.
  3. Where the "union of everything needed" computation lives. Bridge, vrooli-onboarding, or the control plane. It affects both Track 5 and Track 6 and should not be decided by whichever gets built first.
  4. Session recording retention. Full-fidelity terminal recording is the compensating control that makes remote shells acceptable, but it captures whatever is typed — including secrets. Retention window and redaction policy should be decided before the feature ships, not after.

Honest framing

What this is and isn't

Everything above is drawn from reading the code, the requirement records, the last recorded suite run (2026-08-10), and a read-only copy of the live database taken today. I did not run the suite or start the scenario — so the suite state is as-of that run, not as-of this minute.

The overall picture is better than the incident report implies. Bridge is not a shaky prototype: the security model is genuinely well-built, the domain boundaries are consistent, and the failure modes are narrow and nameable rather than diffuse. What it lacks is the last mile of every distributed system — acknowledgement, idempotency, and reconciliation — plus the surface area that makes it pleasant to operate. Those are known problems with known shapes, which is the best kind to have three tracks before a launch.
