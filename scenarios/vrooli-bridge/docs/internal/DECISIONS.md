# Decisions — Vrooli Bridge

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

| 2026-07-14 | **Managed first touch: owner-supplied `{host, user, password}` for a specific host is an accepted, bounded first touch — distinct from the still-rejected pre-trusting of arbitrary SSH.** The bridge api owns an SSH first-touch capability (`api/internal/onboard/ssh`, a deliberate duplicate of scenario-to-cloud's proven ssh package) that, given a transient owner password for one reachable host, establishes working passwordless key-based SSH: generate keypair if absent → test passwordless → copy key using the password → retest. Rejected: extracting a shared ssh package with scenario-to-cloud (duplicate-before-extract — the two callers have different state-path/lifecycle needs). Rejected: persisting the owner password anywhere (even encrypted) — the key install is the whole point, after which the password is worthless. | The onboarding flow needs a bootstrap execution channel on a fresh node; a bounded, credential-minimizing managed first touch is the professional shape (it is how ssh-copy-id / cloud bootstrappers work), and the risk is contained to a single owner-named host. | Bridge gains a dependency on `golang.org/x/crypto/ssh` (already approved, used by scenario-to-cloud) and on the local `ssh`/`scp`/`ssh-keygen` binaries for the system-ssh test/exec path. | 2026-06-18 | **Mutual-auth mechanism = per-node Ed25519 keypair pinned both directions at pairing.** At pairing the node generates an Ed25519 keypair and sends its public key; the control plane stores it (hashed/encoded) in `node_credentials`. The control plane has its own long-lived keypair, and the node pins the control-plane public key at bootstrap (delivered out-of-band with the pairing code). Every channel exchange is authenticated both directions over TLS: the node signs its requests (Connect-RPC calls carry a signed credential / the SSE token is bound to the node key), and the control plane's responses are verifiable against the pinned key. Rejected: full PKI / mTLS-CA (an X.509 CA, cert issuance, CRL/OCSP) — heavier than a single owner controlling their own machines needs, and a CA is a second thing to secure. Rejected: bearer-token-only (no control-plane proof) — leaves nodes vulnerable to a rogue coordinator. Pinned-key signed-both-ways is the NAT-proof, single-owner-appropriate professional choice (the Tailscale/WireGuard-style pinned-key model, not the web-PKI model). | Resolves the HIGH `SECURITY.md` gap "Mutual-auth mechanism not yet chosen (mTLS vs signed tokens)". Remote code execution is the highest-stakes surface; both impersonation directions must be closed before any node runs a job. | Ed25519 chosen for small keys, fast verify, no parameter choices, and CGO-free `crypto/ed25519`. Pairing transports the public key (node→CP) and the pinned CP key (CP→node, out-of-band). Credentials hashed at rest, destroyed on revoke. Heavier than a shared secret, but a shared secret cannot prove the control plane's identity to the node. | If multi-owner/multi-instance arrives (then a real CA may be justified), or if a hardware-token / TPM-backed key store becomes available. |
| 2026-06-18 | **Runner sandboxing = dedicated non-privileged service user + a structurally separate privileged provisioning helper.** The node-agent installs as a dedicated **non-privileged service user** (e.g. `vrooli-agent`, no sudo, no login shell). The job **runner** executes allowlisted manifest verbs as that user and has no code path to elevate. A **separate privileged provisioning helper** — a distinct binary/process installed at bootstrap as root/admin (via the platform service manager) — performs only a whitelisted set of provisioning ops (git fetch@R, `vrooli setup`, version report, rollback), is invoked explicitly over a local IPC the runner cannot forge, and audits every call. The two tiers are different OS principals, not a boolean flag or a convention. Rejected: a single agent process with an `isPrivileged` flag (one bug = full escalation); rejected: running everything as root (the everyday runner would hold standing privilege). | Resolves the HIGH `SECURITY.md` gap "Runner OS-level sandboxing/least-privilege user not yet specified". The helper's whitelist is itself an allowlist — adding a provisioning capability is a deliberate, audited change, never a shell escape. | If provisioning is ever delegated to an external orchestrator (then the helper shrinks to a thin adapter), or if an OS-level sandbox primitive (e.g. systemd `DynamicUser`, Windows AppContainer) supersedes the dedicated-user model. |

| 2026-09-15 | **Bridge generates and escrows each node's credential-store passphrase.** At the operator's direction — connecting a machine must set it up completely with nothing done at the machine — onboarding's `credential-store` step (after online confirmation, before apply-selection) creates the node's encrypted store over the verified key-only SSH connection with a 32-byte random passphrase that rides SSH stdin only. | 2026-09-15 | **Every Bridge-managed node store carries an escrowed recovery passphrase, and the control plane can rotate it crash-safely.** (a) A store `vrooli setup` created behind an unattended wrap alone (TPM/host key/Keychain) gains a Bridge-generated passphrase wrap beside it (`vrooli credentials store add-passphrase`, stdin), escrowed before the node sees it; the unattended wrap is never replaced. The step also converges: an escrowed value missing on the node is added, one present is proved with `verify-passphrase` (which consults only the passphrase wrap, so a working TPM cannot make a stale escrow look right), and a mismatch is reported without pushing a grant. (b) `vrooli-bridge machines rotate-store <machine>` (`MachineService.RotateMachineCredentialStore`) swaps the passphrase in this order: reconcile any pending value → prove the escrow opens the node → write the new value to a second escrow field `passphrase-next` → `change-passphrase` on the node (one atomic wrap replacement) → prove the new value → promote it to `passphrase` → clear pending → re-push the unlock grant → prove a fresh node shell opens the store. Before the node change the escrow opens it, between change and promotion the pending field does, after promotion the escrow does; a re-run (or the next onboarding connect) finishes an interrupted rotation. No grant names `passphrase-next`, so it is never pushed. (c) Windows nodes keep the skip, now with an operator-visible reason: setup's DPAPI store is bound to the node user, and Bridge's node-CLI path is a POSIX shell command over SSH. (d) Escrow lives in the control-plane store file (`~/.vrooli/secrets.enc.json`), so the encrypted root copy covers it; manifest-driven `recovery export --all` does not (per-machine `--entry vrooli-bridge/node-credential-store/<machineID>:passphrase` does). | Before this, a TPM host's node store had no copy of its key anywhere but the TPM, and the only way to change a node's passphrase was at the node. A rotation that updated escrow before the node, or the node before escrow, could strand a node's credentials on one interruption. Rejected: rotating by re-initializing (destroys values); rejected: overwriting an operator-chosen passphrase through the unattended wrap (silently takes custody). | Nodes need a control plane with the two new CLI verbs; an older node answers "Unknown subcommand" and the step/rotation reports `node_cli_outdated` instead of claiming a recovery path. Rotation codes: `not_escrowed`, `escrow_mismatch`, `node_cli_outdated`, `unsupported_platform`, `store_absent` (FailedPrecondition); `node_unreachable` (Unavailable); `escrow_unavailable`, `node_command_failed` (Aborted, re-run reconciles); `X-Vrooli-Error-Code` carries the code. | When Windows nodes get a PowerShell node-CLI path, or when the control plane's own store backup is operator-configured (then the backup gap note retires). |
