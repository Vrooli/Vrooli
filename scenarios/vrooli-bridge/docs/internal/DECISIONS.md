# Decisions — Vrooli Bridge

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| Date | Decision | Context | Consequences | Revisit Trigger |
|---|---|---|---|---|
| 2026-06-18 | Use the generated `react-vite` scenario documentation contract. | Scenario scaffold was generated from the template. | Docs start with stubs and maturity metadata in `docs/manifest.json`. | Revisit when scenario adopts a different template or doc contract. |
| 2026-06-18 | **Dial-out connection direction.** Node-agents dial OUT to the control plane and hold a persistent channel; the control plane never dials in. | Nodes are the owner's machines, often behind NAT/firewalls or in another location. | No inbound ports on nodes; firewall/NAT-proof; reuses device-sync-hub's presence model; off-LAN reach via tunnel-manager. This is the industry-standard agent pattern (Tailscale, GitHub Actions runners, Buildkite). | If a future model requires the control plane to initiate (e.g. push to a fully passive node), reconsider — but expect to keep dial-out as the default. |
| 2026-06-18 | **Two trust tiers.** A privileged *provisioning* path is structurally separated from a non-privileged *job runner*. | Remote code execution and remote provisioning are different risk classes. | The everyday runner can never escalate privilege; provisioning is explicit, consented, and audited. More code than one path, but safe by construction. | If provisioning is ever delegated to an external orchestrator. |
| 2026-06-18 | **Allowlist = typed, manifest-declared CLI verbs — never raw shell.** A job is `{scenario, verb, args}` validated against the scenario-CLI manifest plus per-node scopes. | The "run commands on devices" capability is the dangerous part; arbitrary shell would be a standing RCE. | Remote execution is constrained to declared operations; leans on the existing scenario-CLI-manifest work as the allowlist surface. | If a use case genuinely needs an un-declared operation, add it to the manifest — do not add a shell escape hatch. |
| 2026-06-18 | **Node-agent is bridge-owned, not baked into the root `vrooli` CLI.** | Convenience argued for a `vrooli node join` primitive, but that puts one scenario's fleet protocol into the shared platform CLI. | Root CLI stays scenario-agnostic; bridge owns the control-plane↔node protocol end to end; the node side stays thin (hold channel, validate job, call local `vrooli`). | If the platform later defines a generic node-agent the root CLI could host. |
| 2026-06-18 | **A node is a versioned build/test environment, not a dumb runner.** Provisioning brings it to revision R; it builds/tests natively per OS. | You cannot cross-compile a macOS app on Linux and call it "validated on macOS" — codesigning, native deps, and real OS behavior only exist on the OS itself. | Source reaches a node via `git@R`; non-git artifacts via device-sync-hub; nodes need the toolchain (`vrooli setup`). Provisioning is heavier than a thin runner would be. | If a lighter pre-built-artifact smoke path proves sufficient for some gates. |
| 2026-06-18 | **Compose, don't reinvent.** Delegate byte transport (device-sync-hub), durable runs (test-genie), off-LAN reach (tunnel-manager), secrets (secrets-manager), owner auth (scenario-authenticator), audit (workspace-sandbox). | Each concern already has an owner scenario; re-implementing them would create drift and risk. | Bridge is an orchestrator, not a re-implementation; tighter coupling to those scenarios, accepted. | If a dependency proves unfit for bridge's needs, revisit that single seam — not the principle. |
| 2026-06-18 | **One-touch bootstrap; reject pre-trusting arbitrary SSH.** Exactly one manual touch (the installer) on a fresh machine; everything after is remote. | You cannot fully provision a machine with no pre-existing execution channel; standing SSH/WinRM into personal machines is unconstrained by default. | The first touch is unavoidable but bounded; all subsequent provisioning/updates are control-plane-driven and audited. | If a fleet operates in an environment with managed pre-provisioning (cloud-init), an automated first touch could be added. |
| 2026-06-18 | **Single-owner fleet in v1; control-plane-on-Mac/Windows is gated P2.** | Bridge controls the owner's own machines; multi-tenant adds large surface. Control-plane portability depends on Vrooli-the-platform running on Mac/Win. | v1 is single-owner; bridge is written cross-platform from day one so it is never the blocker, but full Mac/Win control plane waits on a separate platform-level track. | When multi-owner demand is real, or when the platform becomes installable on Mac/Win. |
| 2026-06-18 | **SQLite (`api-core/storage`) + proto-versioned node protocol.** Control-plane metadata in SQLite (Postgres-compatible schema); the node↔control-plane wire protocol is proto-versioned with a back-compat policy. | Single-owner fleet does not need a server DB; nodes may run older agents. | Embedded simplicity now, forward-compatible later; a node on an old protocol either interoperates or is flagged needs-update. | If the fleet outgrows single-owner/single-instance. |
| 2026-06-18 | **Mutual-auth mechanism = per-node Ed25519 keypair pinned both directions at pairing.** At pairing the node generates an Ed25519 keypair and sends its public key; the control plane stores it (hashed/encoded) in `node_credentials`. The control plane has its own long-lived keypair, and the node pins the control-plane public key at bootstrap (delivered out-of-band with the pairing code). Every channel exchange is authenticated both directions over TLS: the node signs its requests (Connect-RPC calls carry a signed credential / the SSE token is bound to the node key), and the control plane's responses are verifiable against the pinned key. Rejected: full PKI / mTLS-CA (an X.509 CA, cert issuance, CRL/OCSP) — heavier than a single owner controlling their own machines needs, and a CA is a second thing to secure. Rejected: bearer-token-only (no control-plane proof) — leaves nodes vulnerable to a rogue coordinator. Pinned-key signed-both-ways is the NAT-proof, single-owner-appropriate professional choice (the Tailscale/WireGuard-style pinned-key model, not the web-PKI model). | Resolves the HIGH `SECURITY.md` gap "Mutual-auth mechanism not yet chosen (mTLS vs signed tokens)". Remote code execution is the highest-stakes surface; both impersonation directions must be closed before any node runs a job. | Ed25519 chosen for small keys, fast verify, no parameter choices, and CGO-free `crypto/ed25519`. Pairing transports the public key (node→CP) and the pinned CP key (CP→node, out-of-band). Credentials hashed at rest, destroyed on revoke. Heavier than a shared secret, but a shared secret cannot prove the control plane's identity to the node. | If multi-owner/multi-instance arrives (then a real CA may be justified), or if a hardware-token / TPM-backed key store becomes available. |
| 2026-06-18 | **Runner sandboxing = dedicated non-privileged service user + a structurally separate privileged provisioning helper.** The node-agent installs as a dedicated **non-privileged service user** (e.g. `vrooli-agent`, no sudo, no login shell). The job **runner** executes allowlisted manifest verbs as that user and has no code path to elevate. A **separate privileged provisioning helper** — a distinct binary/process installed at bootstrap as root/admin (via the platform service manager) — performs only a whitelisted set of provisioning ops (git fetch@R, `vrooli setup`, version report, rollback), is invoked explicitly over a local IPC the runner cannot forge, and audits every call. The two tiers are different OS principals, not a boolean flag or a convention. Rejected: a single agent process with an `isPrivileged` flag (one bug = full escalation); rejected: running everything as root (the everyday runner would hold standing privilege). | Resolves the HIGH `SECURITY.md` gap "Runner OS-level sandboxing/least-privilege user not yet specified". Privilege escalation via the runner is one of the two highest risks (the other is arbitrary RCE, closed by the typed-verb allowlist). | More install complexity (two principals, an IPC boundary, per-OS service definitions for both). A test must prove the runner has no provisioning path (privilege-separation proof, Phase 4). The helper's whitelist is itself an allowlist — adding a provisioning capability is a deliberate, audited change, never a shell escape. | If provisioning is ever delegated to an external orchestrator (then the helper shrinks to a thin adapter), or if an OS-level sandbox primitive (e.g. systemd `DynamicUser`, Windows AppContainer) supersedes the dedicated-user model. |

| 2026-06-18 | **Cross-OS gate is a durable, re-attachable fan-out that DELEGATES every per-OS validation to dispatch + runs — it never reimplements them.** `GateService` exposes `RunGate` (select one eligible node per target OS, dispatch a validation run to each, persist a durable `Gate` + per-OS ledger, return immediately) / `GetGate` (live-recompute verdict) / `WaitGate` (block-once for the terminal verdict, no polling) / `ListGates`. The gate's `Runner` seam is bound to the SHARED dispatch service (`dispatch.Module` was split into `NewService`+`Module` so one instance backs both the dispatch handler and the gate runner) and the runs service. Aggregation: PASSED only when every OS is green; ANY failing OS — non-zero/aborted run OR a target OS with no eligible node — fails the gate (fail-fast), with the offending run id surfaced. Rejected: a blocking synchronous `RunGate` that holds the connection until all OS runs finish (breaks the durable-run philosophy bridge uses everywhere). Rejected: a gate-local re-implementation of dispatch/run management (would create a second, un-audited execution path). | OT-P1-002, the headline capability. The cross-OS validation must reuse the exact allowlist + scopes + audit + durable-run machinery as any other job, so there is no second RCE surface. | Each per-OS run is a normal durable run (re-attachable, audited); the gate is the fan-out + verdict-aggregation ledger on top. The verdict is recomputed live from the per-OS runs on read, so a gate row is never a stale snapshot. | If a lighter pre-built-artifact smoke gate proves sufficient for some checks (a second gate mode), or if the fan-out needs a Quint-modeled partial-failure state machine at scale. |
| 2026-06-18 | **Bridge supplies the cross-OS gate capability; the consumer owns the verdict. P2 consumer integrations are exposed as seams, not built here.** deployment-manager consumes `GateService` over the Connect/JSON wire contract via its own `crossosgate` package (no proto-module dependency on the consumer; additive + inert until `VROOLI_BRIDGE_URL` is set) and maps the aggregate gate verdict to its own production-readiness decision. The remote-desktop (OT-P2-002), cloud-runner/ephemeral-node (OT-P2-003), self-healing (OT-P2-004), and Mac/Win control-plane (OT-P2-001) consumers are RECORDED as future seams (PROBLEMS.md + SEAMS.md) but deliberately NOT built — they are separate initiatives reusing bridge's `registry`/`dispatch`/`runs`/`gate` contracts. | Scope discipline: bridge ships reusable, drift-gated control-plane contracts; downstream integrations belong to their own initiatives. | Bridge's obligation is to keep the consumed contracts stable + documented; consumers evolve independently behind the proto contract. The deployment-manager wiring proves the pattern (a thin Connect/JSON client + an owned verdict type). | When a consumer initiative starts, it builds against these seams; if a contract proves unfit, revisit that single seam. |
