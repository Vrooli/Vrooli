## 🎯 Overview

Purpose: Vrooli Bridge is the **fleet control plane** for an owner's trusted Vrooli installations. It adds one permanent capability the rest of the system lacks today: the ability to register other machines that run Vrooli ("nodes"), keep them provisioned and version-compatible, and run a constrained, allowlisted set of project/scenario CLI operations on them — collecting durable results back at the control plane. Bridge is the missing primitive behind cross-platform deployment validation: build a scenario's desktop app, bring an Ubuntu, macOS, and Windows node to the same project revision, run the validation suite natively on each, and aggregate a single verdict. Bridge orchestrates; it does not reinvent byte transport, durable test runs, secure tunnels, or secrets — it composes the scenarios that already own those concerns.

Primary users/verticals: The Vrooli operator validating that a scenario is production-ready on every target OS before it ships; release/deployment automation (deployment-manager, scenario-to-desktop) that needs a cross-OS gate; and agents that need to run a known, safe operation on a specific machine in the owner's fleet. Bridge is infrastructure for a single owner controlling their own machines — not a multi-tenant SaaS and not a general remote-shell.

Deployment surfaces: Go API server with Connect-RPC (proto-owned wire contracts) plus a dial-out event channel (SSE) for node presence and job push; a Go CLI with full headless parity for registering nodes, dispatching jobs, provisioning, and reading results; a cross-compiled **node-agent** binary (linux/darwin/windows) that runs on each node, dials out to the control plane, and executes allowlisted work through the node's own `vrooli` CLI; and a React + Vite + TypeScript + Tailwind fleet dashboard (nodes, versions, health, run history).

Value proposition: Today an owner who wants to know "does this scenario actually work on macOS and Windows?" must hand-carry builds to each machine and run tests by hand — there is no fleet, no remote provisioning, and no safe remote execution anywhere in Vrooli. Bridge makes that a one-command, repeatable, audited operation, and does it without inbound ports on the nodes (agents dial out, like Tailscale / GitHub Actions runners / Buildkite agents). Every node is brought to a known project revision and kept compatible, so cross-OS validation tests the same build everywhere. Because remote execution is constrained to typed, manifest-declared CLI verbs with per-node permission scopes — never arbitrary shell — the dangerous capability is safe by construction. This is the foundation that lets "production-ready" mean "validated on every OS we ship to," and it is the identity/reach layer a future remote-desktop scenario composes on top of.

## 🎯 Operational Targets

Operational targets are measurable outcomes; checkboxes may auto-update based on validation.

### 🔴 P0 – Must ship for viability
- [ ] OT-P0-001 | Node Registry & Durable Identity | An owner can register, list, inspect, and revoke trusted Vrooli nodes; each node carries a durable, long-lived identity with OS, architecture, Vrooli revision, reachable endpoint, and self-reported capabilities — distinct from device-sync-hub's ephemeral sync-peer grants because nodes are persistent infrastructure, not one-off pairings.
- [ ] OT-P0-002 | One-Touch Bootstrap & Mutual Auth | A single per-OS bootstrap command run once on a new machine installs Vrooli, runs setup, installs the node-agent as an OS service, and pairs it to the control plane out-of-band (pairing code/token); the node and control plane mutually authenticate on every exchange, and revoking a node atomically kills both its job and provisioning rights.
- [ ] OT-P0-003 | Dial-Out Presence & Health | Each node-agent maintains a persistent **outbound** channel to the control plane (no inbound ports on the node, NAT/firewall-proof); the control plane tracks online/offline presence and the node's self-reported readiness (toolchain present, disk headroom, container runtime up) so dispatch only targets nodes that can actually do the work.
- [ ] OT-P0-004 | Allowlisted Typed-Job Dispatch | The control plane dispatches **typed jobs** — `{scenario, verb, args}` validated against the scenario-CLI manifest — never raw shell strings; each node grants which verb-namespaces it will accept (e.g. `scenario test*` yes, `secrets*` / `scenario deploy*` no), so remote execution is constrained to declared operations with per-node permission scopes.
- [ ] OT-P0-005 | Durable Remote Execution & Result Collection | A dispatched job runs as a server-owned durable run on the node (reusing the test-genie run-lifecycle philosophy): it survives client and agent disconnect, is re-attachable by id with a block-once wait verb (no polling), and streams exit status, logs, and result artifacts back to the control plane for aggregation.
- [ ] OT-P0-006 | Privileged Provisioning Tier | A distinct, privileged provisioning path brings a node to a target project **revision R** (fetch source at R + idempotent `vrooli setup`) and reports the resulting version; provisioning is separated from the non-privileged job runner so everyday remote execution can never escalate privilege, and re-running provisioning is always safe (idempotent).
- [ ] OT-P0-007 | Cross-Platform Node-Agent | One node-agent codebase is cross-compiled for Linux, macOS, and Windows and installs itself as the platform-native background service (systemd / launchd / Windows Service or Scheduled Task); the agent uses platform path/process abstractions only, with no Linux-only assumptions, so a node can run any supported OS from day one.
- [ ] OT-P0-008 | Immutable Audit Trail | Every job dispatch and every provisioning operation — who, which node, what verb/args, outcome — is recorded to an append-only audit trail (workspace-sandbox as the accountability substrate), because remote code execution and remote provisioning must be fully traceable after the fact.

### 🟠 P1 – Should have post-launch
- [ ] OT-P1-001 | Remote Update, Version-Pin & Rollback | The control plane can roll one node or the whole fleet to a target revision, gate on node↔control-plane protocol compatibility before dispatching incompatible work, and automatically roll a node back to its prior revision if setup fails — so the fleet stays coherent without per-machine hand-maintenance.
- [ ] OT-P1-002 | Cross-OS Deployment Gate | deployment-manager can call bridge to run a cross-OS validation gate: distribute the built scenario, native-build/test it on each target OS node, aggregate per-OS verdicts, and return a single "production-ready on Ubuntu + macOS + Windows" result that gates promotion; bridge supplies the capability, deployment-manager owns the verdict.
- [ ] OT-P1-003 | Build-Artifact Distribution via device-sync-hub | When a job needs a non-git artifact on a node (a built desktop installer, a large fixture), bridge ships it through device-sync-hub's directed delivery rather than reinventing file transport — "bridge orchestrates, device-sync-hub moves the bytes."
- [ ] OT-P1-004 | Per-Node Job Queue & Scheduling | Each node runs at most one job at a time (or a small bounded concurrency), with queued jobs scheduled fairly and surfaced in the control plane, mirroring test-genie's one-run-per-scenario discipline so a gate run never thrashes a node.
- [ ] OT-P1-005 | Fleet Control-Plane UI | A React dashboard shows the fleet at a glance — nodes with OS/arch/version/health, pairing and revocation, live job status, and run history with drill-into logs/artifacts — so the owner can operate the fleet without the CLI.
- [ ] OT-P1-006 | LAN Auto-Discovery | On a trusted LAN, the bootstrap can discover the control plane automatically (mDNS) so pairing is "run the installer" rather than "find and type the control-plane URL," while the manual URL+code path remains the cross-network default.

### 🟢 P2 – Future / expansion
- [ ] OT-P2-001 | Control Plane on macOS / Windows | The control plane itself runs on a macOS or Windows host, not only Linux; Bridge is written cross-platform from day one so it is never the blocker, but full support is gated on Vrooli-the-platform becoming installable/runnable on those OSes (a separate project-level track outside this scenario's scope).
- [ ] OT-P2-002 | remote-desktop Integration | A future remote-desktop scenario (real-time screen/input control via WebRTC/RDP/VNC) reuses bridge's node identity, trust, and reach layer rather than reimplementing it, while owning its own streaming; bridge exposes the identity/reach seam it needs.
- [ ] OT-P2-003 | Ephemeral & Cloud-Runner Nodes | A node can be a VM or a cloud macOS/Windows runner provisioned on demand, not only a physical machine; bridge treats a node as "any reachable Vrooli install," so ephemeral capacity composes without special-casing.
- [ ] OT-P2-004 | Self-Healing Re-Provisioning | The control plane detects drifted or unhealthy nodes (wrong revision, missing toolchain, repeatedly failing health) and re-provisions them automatically toward their target revision, keeping the fleet validation-ready without manual intervention.

## 🧱 Tech Direction Snapshot

Preferred stacks / frameworks: Go API server with Connect-RPC for all control-plane↔CLI and control-plane↔node wire contracts (proto-owned, drift-checked, versioned), plus an SSE dial-out edge for node presence and job push (EventSource-compatible, since agents and browsers both consume it). One Go **node-agent** binary cross-compiled for linux/darwin/windows, installed as a platform-native service. React + Vite + TypeScript + Tailwind (vrooli-default kit) for the fleet dashboard. Go CLI with full headless parity. The node-side executor is intentionally thin: it holds the outbound channel, validates an incoming typed job against the manifest, and shells to the node's own root `vrooli` CLI — the root CLI stays scenario-agnostic; bridge owns the fleet protocol end to end.

Data + storage expectations: SQLite via `api-core/storage` for control-plane metadata (Machines, immutable enrollment attempts, paired Nodes, pairings, capability snapshots, jobs, dispatch/provisioning audit, version history), with a Postgres-compatible schema for forward scale. A **Machine** is durable operator intent and can exist before contact; an **EnrollmentAttempt** is immutable recovery history; a **Node** is paired Registry identity; and **Presence** is live agent observation. These facts are composed rather than copied. No large binaries live in bridge's own store — build artifacts move through device-sync-hub's blobstore-backed transport; job logs/artifacts stream back and are retained per a configurable policy. The node↔control-plane wire protocol is proto-versioned with an explicit backward-compatibility policy (DiscardUnknown) so a node on an older agent either still interoperates or is flagged "needs update."

Integration strategy: Compose, don't reinvent. device-sync-hub is the **byte transport** for non-git artifacts; test-genie's durable server-owned run-lifecycle is the model (and, where a job is a scenario test, the actual mechanism) for remote execution that survives disconnect; tunnel-manager is the **reach** for off-LAN nodes (the agent dials the control plane's tunnel URL); scenario-authenticator provides owner identity for control-plane access; the scenario-CLI **manifest** is the allowlist surface (typed verbs, not strings); secrets-manager is the path for any node-bound secret (never ship secrets ad hoc); workspace-sandbox is the audit substrate; deployment-manager and scenario-to-desktop are the consumers of the cross-OS gate. Connection direction is **dial-out only** — the professional, NAT-proof pattern used by Tailscale, GitHub Actions runners, and Buildkite agents.

Non-goals / guardrails: No arbitrary remote shell — execution is restricted to typed, manifest-declared CLI verbs with per-node scopes, full stop. No multi-tenant / multi-owner fleet in v1 (single owner controlling their own machines). No reinvention of file transport (device-sync-hub), durable runs (test-genie), tunnels (tunnel-manager), secrets (secrets-manager), or owner auth (scenario-authenticator). No control of third-party IoT/smart-home hardware — that is home-automation's domain via Home Assistant, a deliberately separate track. Bridge does not itself make Vrooli installable on macOS/Windows; it is written so it will not be the blocker when the platform gets there. The everyday job runner never holds elevated privilege; privilege exists only in the explicit, consented, audited provisioning tier.

## 🤝 Dependencies & Launch Plan

Required resources: SQLite via `api-core/storage` (control-plane metadata). scenario-authenticator for owner identity on control-plane access (fail-closed, consistent with device-sync-hub). No third-party runtime resource is required for the core control plane.

Scenario dependencies: device-sync-hub (build-artifact transport — directed delivery of non-git binaries to a node, P1); test-genie (durable-run lifecycle reused for remote execution; the dispatch target when a job is a scenario test); tunnel-manager (off-LAN node reach via the control plane's tunnel URL); deployment-manager + scenario-to-desktop (consumers of the cross-OS validation gate, P1); secrets-manager (node-bound secrets when needed, P2); workspace-sandbox (audit substrate). The node side depends on the target machine having (or being bootstrapped into) a full Vrooli install with the root `vrooli` CLI, since a node is a real build/test environment, not a thin runner.

Operational risks: Remote code execution is inherently high-stakes — mitigated by the typed-verb allowlist, per-node scopes, mutual auth, atomic revocation, and immutable audit; this is the single most important thing to get right. The bootstrap chicken-and-egg (you cannot fully provision a machine that has no execution channel) is mitigated by accepting exactly one manual touch — the bootstrap installer — and making everything after it remote; pre-trusting arbitrary SSH would be worse, not better. Privilege separation (provisioning vs runner) must be enforced structurally, not by convention. Version drift across the fleet is mitigated by the proto-versioned protocol, compatibility gating, and "sync to revision R" as a first-class op. Cross-platform correctness (especially Windows: no default SSH, different service model and paths) is a real cost paid up front by writing the agent portable from day one. The control-plane-on-Mac/Windows goal depends on platform-level work bridge cannot do alone — scoped explicitly as P2 and gated.

Launch sequencing: (1) Proto-first node↔control-plane contract + node registry + durable identity + dial-out presence/health — the spine (OT-P0-001/003). (2) One-touch bootstrap + mutual auth + atomic revocation — getting a real node attached safely (OT-P0-002). (3) Allowlisted typed-job dispatch + durable remote execution + result collection + audit — the first real remote operation (`vrooli scenario test X` on a node), reusing test-genie semantics (OT-P0-004/005/008). (4) Privileged provisioning tier (sync to revision R) + cross-platform agent service install (OT-P0-006/007) — the fleet becomes self-provisioning and truly cross-OS. (5) Remote update/version-pin/rollback + per-node queue + fleet UI + artifact distribution via device-sync-hub + mDNS (P1). (6) Cross-OS deployment gate wired into deployment-manager, then the P2 expansions (control plane on Mac/Win, remote-desktop seam, cloud-runner nodes, self-healing).

## 🎨 UX & Branding

Look & feel: An operational fleet-console aesthetic using the vrooli-default kit — calm, dense, status-first, equally usable on desktop and mobile. The dashboard's center of gravity is the node list: each node a card/row showing OS/arch, Vrooli revision, online/health status (green/amber/red status-color semantics), and its current or last job. Drill-in surfaces a node's capabilities, permission scopes, version history, and run log with live-streaming job output and downloadable artifacts. Pairing presents a copyable code/QR and a clear "run this on the new machine" instruction; revocation is a confirmed, irreversible-feeling action. Long-running jobs always show progress with cancel and ETA, never a frozen spinner — mirroring the no-polling, durable-run discipline underneath.

Accessibility: WCAG AA across all surfaces. Full keyboard navigation for every control (pair, revoke, dispatch, provision, drill-in). Status is never conveyed by color alone — every status dot has text/iconography. All template a11y primitives are preserved: `role`, `aria-*`, and `data-testid` selectors. i18n wiring is maintained throughout so localization needs no structural change.

Voice & messaging: Precise, operator-grade, and honest about risk. The product never pretends remote execution is casual — dispatch and especially provisioning surfaces state plainly what will run, on which machine, with what privilege. Messaging favors "this node will run `scenario test web-search`; it cannot run deploy or secrets commands" over vague reassurance. Empty and error states are actionable (how to pair a first node, why a node is unreachable, what a failed provision left behind).

Branding hooks: The PWA install surface is kept valid — `ui/public/site.webmanifest`, `apple-icon-180.png`, `favicon-196.png`, and the maskable manifest icons remain present and valid; generic placeholder icons are replaced when final Vrooli brand assets exist. Light and dark themes via the vrooli-default theming primitives. Iconography leans on the fleet/network metaphor (nodes, links, reach) without implying third-party device control, which belongs to home-automation.
