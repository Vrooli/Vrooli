# Decisions — Content Desk

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| ID | Date | Decision | Context | Consequences | Revisit Trigger |
|---|---|---|---|---|---|
| D-001 | 2026-07-28 | Use the generated `react-vite` scenario documentation contract. | Scenario scaffold was generated from the template. | Docs start with stubs and maturity metadata in `docs/manifest.json`. | Revisit when scenario adopts a different template or doc contract. |
| D-002 | 2026-07-28 | **Replace `campaign-content-studio` rather than migrate it.** | The fleet's in-place-modernization precedent (`landing-page-business-suite`) was chosen to protect ~29.5k lines of real product. The prior scenario held ~3.2k lines of generic campaign CRUD plus RAG generation, no consumers outside its own skill, and a domain model that changes completely — `campaigns/documents/generate` becomes `campaigns/artifacts/claims/posttypes/review/ledger`. That is a rewrite, not a migration. | Fresh generation on a new slug. The old tree was moved out of the repo rather than deleted; its obsolete skill, cross-references, and resource capability listings were retired or corrected. | If a capability in the retired scenario is discovered to have been load-bearing. Nothing found so far suggests it was. |
| D-003 | 2026-07-28 | **The scenario owns the ledger and the gates; it does not generate copy.** | Generation prompts live in the paired `x-<type>` skills, where the doc-plus-skill discipline puts executable procedure. Absorbing them would freeze prompt iteration behind a deploy and collapse the separation between strategic reasoning and procedure. | The desk consumes drafts; it never authors them. Skills stay mutable and independently reviewable. | If skill-authored drafts prove impossible to constrain to the required field set, which would argue for a stricter authoring surface — not for absorbing the prompts. |
| D-004 | 2026-07-28 | **`claims` answers "is it true"; `review` answers "is it allowed".** | Some assertions are unfalsifiable by design — persona traits and lifestyle implication are permitted marketing embellishment under existing canon. Routing them into a truth gate would make it fail constantly on statements no evidence can settle, and a gate that fails constantly gets disabled. | Two domains with two different mechanisms. Policy rules — credential claims, real-person likeness, fabricated testimonials, missing disclosure — score as review failure modes, never as unverified claims. | Never expected. Merging them is the most likely way this scenario decays. |
| D-005 | 2026-07-28 | **Claims are a shared library cited by many drafts, not per-draft annotations.** | The same fact is asserted across many posts. Hanging claims off a single draft would mean verifying the same thing repeatedly and would make it impossible to ask which published posts depend on a fact that has since changed. | A many-to-many citation join. Verify once, cite many, re-check on a schedule. This is what enables the contamination report (`CONTENTD-P1-002`). | If claim reuse turns out to be rare in practice, the join is still harmless — but the contamination capability would lose most of its value. |
| D-006 | 2026-07-28 | **Evidence has two strengths, and re-runnable checks are required where they are cheap.** | A citation proves someone looked; it does not prove the claim is true, and it rots silently because the link still resolves after the fact behind it changed. A stored command with an expected result can be re-run before publish and after. | Quantitative, existence, and status claims require a check. Capability claims accept a named test. Novelty claims require a dated prior-art record and expire. | If check authoring proves burdensome enough that authors avoid the claim kinds that require them, which would show up as claim-kind skew. |
| D-007 | 2026-07-28 | **Approval is operator-only and is never automated.** | It is the last human check before a public assertion. Every other gate in the scenario is mechanical precisely so that this one stays cheap enough to be real. | The API refuses approval from a non-operator actor. The workbench is designed so approving takes seconds, because operator attention — not agent capacity — becomes the binding constraint once agents are freer. | Never for the approval itself. The *speed* of approval is a UI problem and is expected to need iteration. |
| D-008 | 2026-07-28 | **Campaign artifact slots are a hard cap, not a target.** | Campaign sprawl is already a named marketing risk, and the existing canon carries "outstanding artifact slots" as decorative checkboxes an operator ticks by hand. As an enforced constraint the same field bounds both sprawl and operator review load. | A draft beyond budget is refused rather than queued. The budget is the only mechanism bounding review load. | If operators routinely hit the cap on work that all genuinely belongs, which would mean the budget is set below real need. |
| D-009 | 2026-07-28 | **Import idempotency is by content-addressed key, never by offset or watermark.** | Every import source is a file a human or an agent rewrites and reorders. Positional keys break on the first reflow and re-import an entire file as new; watermarks desynchronise on any out-of-order edit. | Re-import is a no-op for unchanged items — that is the diff, with no cursor or state file. **Accepted consequence:** an item edited in place hashes differently and imports as a new record rather than updating the old one, which is correct under an append-oriented ledger. | If edit churn produces visible duplicate pairs that reviewers cannot reconcile. |
| D-010 | 2026-07-28 | **No credential, in any table, in any form.** | Marketing canon already routes account handles and credentials away from editorial surfaces, and Channel Manager owns identity with vault references. | Account eligibility is a single question answered elsewhere: *is this account eligible for this lane*, plus a reason. A schema change introducing a token column is a defect, not a feature. | Never. |
| D-011 | 2026-07-28 | **The team restructure this scenario enables is explicitly out of scope.** | The scenario makes a smaller marketing roster possible by externalising pipeline state into gates. Rewriting the operating model against a scenario that does not yet run would repeat the error of designing a workbench against an empty publish log. | No member, topic, or operating-model change ships with this scenario. The restructure is a separate, decision-gated change that should follow observed behaviour. | Once the P0 loop has produced published posts and the real handoffs are visible. |
| D-012 | 2026-07-28 | **Imported publish records carry no draft reference.** | The ledger and its import land before `artifacts` exists, and every historical publish predates the scenario entirely. Requiring a draft would either block the import or force synthetic drafts that never went through a gate — which would make the approval history lie. | The publish record's draft reference is nullable **by design**. A record with no draft is imported history; a record with one went through the gates. Reporting distinguishes the two rather than hiding it. A later change making the column required is a defect, not a tightening. | If synthesising retrospective drafts for historical posts ever becomes worth the false approval trail. It is not today. |
| D-013 | 2026-07-28 | **Character, scene, and product definitions stay in operator-curated canon; a rendering scenario is deferred.** | `docs/marketing/catalogs/rich-media/` already holds characters, scenes, products, and model-compatible prompt templates as structured JSON. What is missing is validation, composition, render orchestration, and provenance — a different clock and a different failure mode from editorial work, being visual drift and generation spend rather than a false claim. Every image and video post type is currently inactive, and no persona account exists. | No media domain here. A draft references a rendered asset by identifier once a producing scenario exists (`CONTENTD-P2-003`); until then it references nothing. Building the pipeline first would be building a factory before knowing what it makes. | When a persona account is activated and at least one image or video post type reaches active state. Not before both. |
| D-014 | 2026-07-28 | **This scenario is a direct-product candidate, not internal-only infrastructure.** | *Reversal.* The prior verdict rested on three claims. "No external buyer" confused seed data with engine — the post-type registry is a table a buyer fills with their own types, while the claim gate, evidence model, and ledger carry no marketing doctrine whatsoever. "Gates nothing a self-hoster could run" argues against feature-gating, not against monetization, and `vrooli-memory` D-014 already settled that shape. "Touches no bundle" describes the current packaging map, not the existence of a buyer. Stripped of marketing vocabulary the capability is claim substantiation with an audit trail, and that is a category with established enterprise willingness to pay. | `MONETIZATION.md` and `GO-TO-MARKET.md` carry a real hypothesis with named segments, comparables, five preconditions, and a kill signal. The tool is never feature-gated; revenue is indirect through ai-gateway inference fall-through, and **agent invocation from the UI is what makes that volume non-trivial** — claim extraction alone is bursty and small. No P0 work depends on any of this. | If internal dogfooding shows the gate is routinely bypassed, or catches only trivial claims, the product case collapses regardless of market interest. That is the kill signal and it is internal. |
| D-015 | 2026-07-28 | **Approval records the acting identity and its kind (human or agent); multi-user roles are a later expansion, not a P0 requirement.** | *Corrected the same day it was written.* The original claim — that an editorial gate needs two humans, making multi-user critical-path — was wrong. It conflated **role separation** with **multi-user**. The separation that matters is producer versus approver, and that is already satisfied by an agent drafting and a human approving. A solo operator is a complete user, not a degraded one. Where the human also writes the draft, the mechanical claim checks still run and still bind, because a re-runnable check does not care who authored the assertion. | Approval attribution stores the actor and its kind, which `CONTENTD-P0-007` needs for the audit trail regardless. That shape happens not to foreclose multiple human approvers later, which is a free side effect rather than the reason. **No roles table, no permissions model, no tenancy is built.** | If collaboration is ever actually built. It is a P2 monetization expansion, not a correctness gap. |
| D-016 | 2026-07-28 | **Evidence-check execution lives behind a seam, and the execution model is recorded as an open fork rather than discovered later.** | A re-runnable check is the strongest evidence tier and the reason the gate is worth anything. Locally it is a stored shell command, which is correct and cheap. In any hosted or multi-tenant deployment the same design is **arbitrary remote code execution**, and sandboxing it is not a hardening pass — it is a different product with different infrastructure. This is the equivalent of `vrooli-memory` D-020: the item that is cheapest to decide now and most expensive to retrofit. | Check execution goes through a seam from the first implementation, with the local shell runner as the only implementation built. No hosted execution, no sandbox, no remote runner is built or designed. The fork is named so a future hosted move is a new implementation behind an existing seam rather than a rewrite of the claims domain. | When hosted deployment is actually proposed. Not before — building a sandbox now would be speculative infrastructure for a product that does not exist. |

| D-017 | 2026-07-28 | **Tier 2 desktop is the external delivery target, not hosted SaaS.** | The buyer runs this on their own machine, exactly as they run their coding agents. `scenario-to-desktop` already exists as the Electron Tier 2 ramp, so packaging is an existing capability rather than new infrastructure. Local-first also resolves the awkward parts of the product by construction: no tenancy, no hosted credential surface, and evidence checks that execute locally are ordinary tool use rather than remote code execution. | Desktop packaging becomes the external path, and hosting stays unbuilt. **This substantially defuses D-016** — the sandboxed-execution branch is only reached if hosted delivery is ever chosen, which is now explicitly not the plan. Distribution and updates would ride the existing landing-page download-hosting machinery rather than anything built here. | If demand appears specifically for a hosted collaborative product, which would reopen D-016 and the multi-user question together. |
| D-018 | 2026-07-28 | **Single images are produced through `image-tools`; identity-consistent and video media stay deferred.** | These are two different problems that share the word "media". A blog banner or an inline figure is one image with no continuity requirement, and `image-tools` already provides `ai` generation, `ops` for deterministic resize and crop, and `looks` for reusable style recipes. Character-consistent multi-frame media is the hard problem — identity blocks, drift across frames, generation spend — and it needs persona accounts that do not exist and post types that are all inactive. | A draft may attach images produced through `image-tools`, including a banner at a declared aspect ratio and inline figures with alt text and position. **This scenario stores references and metadata, never bytes** — the desk holds state, not assets. The deferred asset-production scenario (D-013) keeps the identity-consistent and video scope; this decision narrows it rather than replacing it. | If blog imagery starts requiring cross-post visual continuity, which would make it the deferred scenario's problem rather than a call into `image-tools`. |

| D-019 | 2026-07-28 | **From the MLR-review category, take the object model and leave the workflow.** | Veeva Vault PromoMats is the established comparable: claims management, claim-to-reference linking, MLR review, DAM, modular content reuse, and publish-and-withdraw. Its object model is the durable idea; its **shape** is enterprise, regulated, multi-role, and configurable, which is precisely why a gap exists for a solo-operator version. Copying the workflow would aim this scenario at a market it cannot serve with a build it cannot finish. | **Taken:** citation-to-span anchoring (`CONTENTD-P0-004`, P0 because it cannot be backfilled), claim coverage over the body (`CONTENTD-P1-012`), remediation of contaminated posts (`CONTENTD-P1-013`), and re-running the gate at handoff (`CONTENTD-P1-006`). **Rejected:** multi-role parallel review with electronic signatures (needs the multi-user model D-015 declined), regulatory submission packaging, the asset portal (image-tools and the deferred asset scenario own it), and the distribution engine (Channel Manager owns it). | If a regulated buyer segment is ever pursued deliberately, at which point the rejected half becomes the requirement rather than the bloat. |
| D-020 | 2026-07-28 | **Record modular reusable approved content as an idea; build nothing.** | *Recorded idea, not design.* A passage whose cited claims are all verified could be reused across drafts with its citations intact — the same architecture as the claim library, one level up, and the reuse headline of the comparable product. It fits the model cleanly, which is exactly why it is tempting to build early. | Nothing is built and no requirement depends on it. Written down so the seam is deliberate rather than rediscovered. The precondition is ordinary: something has to have shipped, and claim reuse across real drafts has to be observed rather than assumed. | Once the claim library holds real reuse — the same evidence D-005's value rests on — and a second draft genuinely wants a passage from the first. |

**Note on D-003.** In-UI agent invocation (`MONETIZATION.md` § Mechanism) does
not contradict D-003. That decision keeps generation *prompts* in the paired
skills; invoking an agent that runs such a skill is an invocation surface, not
ownership of the prompt. If a future change moves prompt content into this
scenario, that is the contradiction — not the button that triggers it.
