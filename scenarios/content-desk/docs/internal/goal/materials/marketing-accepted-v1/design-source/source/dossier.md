### A return session starts from what changed

Today has three modes: a new workspace offers Write a post, Bring in existing work and Plan an app campaign; an active workspace resumes the last meaningful edit and shows urgent decisions; a quiet workspace says there is no required action and offers optional capture. A blank day is a legitimate state. The page must not invent a task to justify its presence. First-use setup remains private and lightweight; choosing a platform does not start account connection.

The primary suggestion is selected from a bounded attention queue. A release uncertainty or expiring permission outranks optional adaptation because delay can cause a duplicate or missed external commitment. A saved typing session is offered as Resume, even when another suggested action ranks higher. A blocked item never masquerades as the best actionable next step: it names the blocker, responsible actor and useful resolving action. Waiting on a friend appears under Waiting, without nagging them or estimating their consent. Separate items in the side column are not numbered as though the article review depends on the LinkedIn adaptation.

Why this next? exposes three short layers: the objective and source revision; the actual dependency or rule; and any AI interpretation. For the Aster fixture, the supported structural change and an existing draft justify an adaptation. No relevant performance data establishes an optimal time or likely reach. Dismiss lets the owner choose Not useful, Later, Already handled or a free explanation; Later saves an explicit revisit condition rather than silently recurring. A changed source may bring an item back only with the new reason visible.

The suggestion's picture changes with its real object. An article can show its permitted cover or a readable text extract; a demonstration can show the selected frame; a revision can show a small actual changed passage; a community-setup task can use curated contextual artwork. The picture always links to that object or an inspectable provenance label. A decorative poster is never relabeled as a product screenshot. When no suitable permitted asset exists, strong type and a short excerpt carry the suggestion. Image failure does not remove the action.

The earlier solo-maker market hypothesis remains historical and potentially reusable, but broad productization, pricing and hosting choices are deferred until a separate commercial purpose is established. ### Relationships that stay intelligible as work grows

A single post is one native draft with optional subject/project and optional campaign. A content family is an optional relationship among a source article and adapted drafts, held by Content Desk if its existing relationships cannot express the need. It does not require a root article before writing a short post. Every variant points to the exact source revision from which it was derived and may carry deliberate local differences. A publication intention points to one exact variant plus one destination identity; several destinations create several intentions, never an ambiguous account array. A batch can group those intentions for review, but each retains its own admission and outcome.

Native draft/revision IDs remain authoritative. Proposed new relationships use owner-qualified references and explicit relation kinds such as derived-from, adapted-for, corrects, replaces or part-of-series. A copied text fragment is not automatically a live dependency. On source change, the user sees which supported claims or variants are affected and may update, keep an intentional historical version, or sever an incorrect derivation with explanation. A core change cannot silently mutate an already approved descendant.

A materialized ReviewPackage freezes body, media order/version/crop, links, accessibility text, author/attribution, method/source basis and the declared review scope. This proposed relationship must be reconciled with the native human-only ApproveDraft and review/type gates; destination-free wording assessment must not be mislabeled as that existing operational approval. An editorial package can lack a destination; it then records destination-unbound and cannot satisfy destination-specific release validation. A PublicationPackage adds account, audience, route, allowed time window, consent and release authority and therefore has its own immutable identity. In the connected fixture, RP2 derives from editorial package P2; the manual fixture uses MP2. Neither reuses P2’s digest for changed fields. Any package identifier must be content-addressed or version-bound under the owner contract. These are proposed domain contracts, not existing fields asserted by the pictures.

### Independent states instead of one green status

The UI keeps at least six dimensions separate: persistence (local, saving, confirmed, conflict or unknown); editorial work (idea, draft, awaiting review, changes requested, editorially accepted or archived); evidence readiness (unchecked, supported, needs evidence, changed or inaccessible); media (candidate, under review, released, rejected or missing); release (no intention, proposed, authorized, admitted, dispatching, uncertain, partial, published or cancelled); and observation coverage (none, reported, verified, stale or incomplete). Compact rows show the two dimensions relevant to the user's current task and disclose the rest on inspection. A green source check cannot stand for approval, and a published receipt cannot stand for a successful marketing outcome.

Every transition names its actor, preconditions, exact base revision, admitted result and failure return. Save advances persistence and a draft revision. Apply suggestion changes content, never review acceptance. Request review freezes a package and creates a decision request. Accept wording records an editorial decision for that package. Authorize release names the destination/action/time scope. Admit release returns an actual local/provider state. Reconcile records observed external truth. Learn proposes a hypothesis change. Denials preserve the prior admitted state; uncertain writes retain operation identity and await reconciliation.

### Cardinalities, slots and explicit relationship changes

Recommended initial rule: each draft has one owning project or explicit Unassigned and at most one native campaign, consistent with the current campaign_id contract. Its private working title belongs to the draft. It can appear in multiple saved collections, which are projections and consume no slots; it has at most one primary content-family membership in that same project. A family does not own campaign membership or grant source access. Multiple causal source/derivation references are allowed with exact pins and permitted access, including an authorized cross-project reference, but never automatic membership or copying. The campaign slot is charged once to its actual admitted draft/channel/format under native rules; a second collection or source link does not consume another slot.

A family is an optional Content Desk grouping with a stable identity and same-project membership. Detaching a draft removes that membership without deleting its source, siblings, history or receipts. Archiving a family hides the grouping, not every member. Moving a draft previews project, family, campaign and restricted references separately; a family in project A cannot remain the primary family of a draft moved to B. Cross-project citations may remain only where both permissions and method allow them. An active release remains bound to its historical package/scope; the move is blocked or explicitly deferred until that constraint can be safely resolved. No hidden cascade reschedules siblings. Supporting the same artifact in two campaigns is a later explicit native cardinality change, not achieved by duplicating its ID or charging it twice.

Concrete trace: source S1 in Founder writing supports family F1 with drafts D1 and D2; a permitted pinned reference from app campaign C2 supports independent draft D3 in project Aster. D1 and D2 may each belong to one campaign or none. A collection called Launch examples can display all three without owning them. Moving D2 to Aster preserves D2/revisions, requires explicit F1 detach and campaign remap, verifies S1 access and leaves D1's active release unchanged. If D2 itself has an admitted release that cannot tolerate the move, the preview refuses it until resolved. These are proposed relationship rules to reconcile in source application.

### An operation key binds one exact intended effect

Every mutating owner command stores a canonical request fingerprint with its operation key: actor/owning scope, action, native target and expected base revision, exact package, destination and timing when applicable. Same key with the same fingerprint returns the prior admitted result. Same key with a changed fingerprint returns Operation conflict and exposes the original permitted result; it cannot report success for the new request. Lookup is authorization-checked and retained at least through the operation/recovery lifetime defined by the native owner; eviction must not silently make an uncertain request safe to repeat.

A parent plan operation groups stable child command keys and individual receipts, not one reusable key for every mutation. An intentional second import/copy carries a new explicit import-intent identity or nonce chosen as Create separate copy in the preview. A retry reuses the prior identity. Changing r2 to r3 or account A to B after a lost response requires reconciliation of the old action first, then a separate authorized intent if still wanted. The captured ReleaseWithOptions returns a prior key result without comparing the changed payload, while Enqueue does not itself establish deduplication; both need compatible owner changes. Existing body/update/approval/suggestion DTOs also lack the proposed revision guards. The UI must not imply that adding a correlation field alone solves these contracts.

The proposed reservation closes that observed source gap. It is not a new public reuse permission, and reimporting identical bytes remains an invalid workaround. Legitimate cross-identity reuse still requires a separate policy decision with rights, transparency and platform evidence.

### A package, not a green global status

An exact review package comprises content revision, variant/format, media versions/order/crops, captions/alt text, links, audience, account/destination, applicable source/offer/method basis, contributor identity and consent/final-wording revision when present, permitted reuse/destinations/time window, and material exceptions. A reviewer can approve wording, request changes or decline. The release permission names the consequential action and scope separately. Moving a card to a date is a publication intention until the supported owner contract admits it under actual authority.

A simple reflection receives a light exact preview. A material announcement requires the relevant source, offer, asset and destination checks. A post type named in the native registry must be active under its doc-plus-paired-skill discipline before operational approval. An externally authored article cannot be relabeled as an active type merely to bypass a v0 gate. A general one-off route may be valid under a supported native contract; if no compatible route exists, retain the draft and propose the narrow type/adapter activation separately. “Keep simple posts simple” is a UX goal, not permission to remove existing safety/activation gates silently.

Roles are bounded capabilities: author can edit; reviewer can inspect/assess; operator can accept a plan or approve an exact package; publisher can execute the permitted release; contributor controls their own contribution; moderator controls authorized community actions. A link does not grant these roles. A friend’s approval of their own contribution does not authorize unrelated brand publication. Contributor consent is checked at execution and any later withdrawal enters the cancellation/reconciliation path described below. Revocation takes effect on future attempts and visible access, preserving the appropriate audit history.

### Contributor consent travels with the exact package

A contributor package records contributor identity, actual relationship/disclosure basis, approved wording/media revision, permitted uses/accounts/destinations, allowed time window and a versioned consent disposition. The contribution can be accepted as an editorial input without granting publication. A change to text, destination, attribution, media or use beyond that scope invalidates the corresponding contributor approval. The exact release validation checks the latest consent revision in addition to the owner’s release authority; account ownership does not override withdrawn content consent.

Withdrawal before publication immediately blocks new local dispatch and invalidates the queued package. If a provider schedule already exists, show Cancellation requested and attempt the supported cancellation only under the authorized cancellation policy; otherwise escalate promptly to the accountable owner for the required action. A provider may be executing or the cancellation response may be lost, so do not promise that withdrawal instantly removes an external schedule. Preserve the schedule/attempt identity, reconcile the actual result and surface any unavoidable race. If already published, create a separately authorized correction/removal task and retain the historical event. Acceptance includes withdrawal while locally queued, provider-scheduled, dispatching and after publication, with a visible responsible actor at each branch.

### Three release routes, chosen by evidence

Manual handoff remains universally useful where permitted: copy/export the reviewed package, open the supported destination independently, then record what happened. Copying is not publication. Store the exact copied package and later actual text if the user changed it externally. A manually entered URL/time is labeled owner-reported unless separately verified through an authorized read. If the owner does not complete posting, retain Ready for manual handoff or Mark not published.

Provider-native scheduling can be used where the owner has the correct account role and a supported native feature. The system records the actual provider schedule identity, accepted time and revision basis when available. If the user performs the native step manually, the evidence remains owner-reported until verified. The design does not assume it can inspect or control every native scheduled item.

Connected dispatch is a supported future route through Channel Manager only after its adapter, account grants, format limits, authority and recovery behavior qualify. It is not postponed by a universal “manual first” product decision, and not promised just because code exists. Per destination, show Available, Manual only, Not connected, Unsupported or Unverified. Offer the legitimate route appropriate to that state. X remains manual/link-only under the current restriction. LinkedIn requires a permitted integration or human native action, not prohibited automation.

### A truthful control contract for every release route

Each release record distinguishes desired time, observed scheduled time, evidence source and control capability. A connected provider may support status/read, edit/reschedule, cancel, or none of those after handoff; record the actual qualified capabilities and last verification. A local queue remains under Channel Manager’s execution gate. A provider-owned schedule is controlled only through supported provider commands. A manually created schedule can be owner-reported but may have no authorized programmatic control at all.

When evidence, offer, consent or permissions change, block new local dispatch immediately. For an existing external schedule, create an urgent responsible-operator action, show the affected package and desired correction, and request or perform only the cancellation/amendment already authorized and supported. Keep Cancellation requested until confirmed, and Outcome unknown where the provider cannot establish the result. Do not advertise a universal execution-time recheck or automatic hold for native/manual schedules. If no reliable read/control route exists, a time-sensitive or revocable package should not be pre-scheduled far ahead under a promise of automatic protection; choose a later manual confirmation or an explicitly accepted risk/operating procedure.

The unified view shows Provider held/restricted when observed, rather than continuing to label the item simply scheduled. A missed publication may require rescheduling after the restriction is resolved, and the old authorization may have expired. After the target passes without a receipt, show Due for verification or Outcome unknown, never infer success. Acceptance A5/A7 includes a manually created provider schedule with no read/cancel API, a provider-held video, and a changed offer after provider acceptance. The test expects a truthful operator action and reconciliation, not a fake cancellation guarantee.

### Proposed release state machine

Draft → In review → Editorially approved describes content readiness. Revision changes can return the affected package to Needs review. Separately, Target proposed → Release requested → Accepted locally (shown as Queued locally) / Scheduled with provider → Dispatching → Published verified / Published owner-reported / Partial / Failed / Outcome unknown / Cancellation requested / Cancelled describes release. A local accepted job is not a provider schedule, and a provider schedule is not a published post. A terminal failure can still have a partial external result that needs reconciliation.

A provider-owned schedule or manual external action may run independently and cannot be guaranteed to honor a later local hold. The route-specific control contract above governs those cases. If the package changes after scheduling, pause or propose amendment through the provider’s supported route rather than assuming the stored schedule updates automatically.

### Observation identity survives correction and reconciliation

An immutable observation identifies native release/item and exact package, metric definition/version or qualitative question, collection route, observation time, covered interval, unit/denominator when meaningful and evidence basis. ### Start with the audience question

The useful question may be whether a reader understands what an app does, whether a demonstration is reproducible, what confuses a prospective user, or whether a founder explanation creates substantive questions. ### Make the next proposal better

### Evaluate effort and quality honestly
