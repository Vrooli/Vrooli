## Twelve substantive changes

### J01 · Preserve C’s distinct page forms and complete their cross-page task contracts

**Priority: critical to the full redesign. Current C disposition: the geometry problem is materially addressed in the chosen direction.** Historical M04–M08 used tall shared framing; task-led-v2 has an actual Plan grid and intention editor, a Create canvas, a Review queue/diff and a Learn ledger. Keep these. The remaining design obligation is to give each route a precise entry, mutation/decision, exit and return contract so the attractive screens describe one coherent product. Visual consistency should come from controls, type, spacing, navigation and state meaning; composition should continue to follow the task.

**Before scenario.** Today opens the LinkedIn draft; Create applies a new opening; Review accepts wording; Plan still identifies revision 1; Learn can import a receipt. The individual screens are now purposeful, but the user cannot yet tell which record/revision each handoff selects, what Review has accepted after Apply, or whether importing a receipt changes release state. “Create” also needs a defined browse/capture/import entry as well as its selected-editor state.

**Recommended after.** Establish explicit page contracts:

| View | Question it answers | Dominant working object | Appropriate form | Successful exit |
|---|---|---|---|---|
| Today | What deserves my attention now, and where was I? | A resumable task or a decision that needs this actor | Compact attention queue plus one resume point; purposeful preview only when it helps identify the work | Resume exact context, resolve urgent issue, or capture a new thought |
| Plan | What useful work fits, and what changes if I choose it? | Versioned content proposal and its dependencies/capacity | Proposal comparison, ordered production list and time projection; calendar is one mode | Accept a bounded plan or revise/defer an explicit subset |
| Create | What am I making, and what does the reader receive? | The selected artifact in its actual format | Format-shaped editing canvas, narrow content navigation and inspectable evidence | Durable revision, compare suggestion, preview or request review |
| Review | What decision can I make on this exact package? | Review request, complete package and material change | Decision inbox, reader preview and issue/decision rail | Approve this scope, request a specific change, or hold |
| Learn | What happened, what might it mean, and what should change? | A question and attributed observations | Inquiry notebook/ledger with comparable outcomes and proposed next step | Record observation, close a question or propose an experiment |

The shared five-route shell can remain a candidate; this does not settle CQ01/CQ12/CQ15. Add route-level entry/list and selected-record states where necessary rather than a new dashboard for every subtask. Account readiness and settings are supporting tasks opened in context and retrievable independently, not compulsory stages in every draft.

**Test.** First retain the C working-form distinction: unlabeled main-area crops should still identify the task. More importantly, trace one native draft across Today → Create → Review → Plan → release/outcome → Learn, writing its identity, current revision, review basis and next actor at every edge. Repeat with a one-off that skips campaign planning. No screen may invent a second current revision, convert target to release or treat source content as an outcome. This is a proposed test, not an executed success claim.

### J08 · Separate the review inbox, reader review and release preflight

**Priority: high. Current C disposition: Review now has a true queue, Content/Publication/Outcomes separation, comparison, evidence and an explicit wording-only footer. Preserve those advances over historical M06.** Its remaining high-impact ambiguity is whether r2 has already been applied in Create or is merely an unapplied editing suggestion: “Current wording r1 / Proposed wording r2” with “Accept wording / Keep current” can imply a second adoption operation. Clarify the revision/review transition before scaling the flow.

**Before scenario.** In Create the owner applies the opening and receives draft r2. Review then calls r1 “current” and offers to accept r2. The user cannot tell whether accepting changes the text again, approves the already saved revision or both; “Keep current” could accidentally appear to erase r2. A return review of a long article also needs full final content and actual images, not just the diff.

**Recommended after.** Review begins with an actionable inbox: ready for this actor's decision, changes requested, waiting, and release/recovery attention. A selected editorial review presents complete reader-facing content, actual rendered images and alt text/links, plus a concise issue rail. A return review highlights material differences from the last reviewed basis and affected checks, while preserving access to the whole package. Do not waive required full-context review merely because a diff is small.

Use one explicit chain: Create’s Apply creates unapproved current draft r2; Review compares “Last reviewed r1” (or another precisely identified comparison basis) with “Draft r2”; editorial acceptance approves the exact r2 package under its allowed scope. Returning to r1 is a deliberate recoverable revision/revert operation, not silently making the old revision current or deleting r2. If the product instead permits pre-adoption review, label that separate mode as an edit proposal and keep adoption distinct from editorial approval. Editorial decisions have precise labels and scope, such as “Approve wording r4” or “Request changes.” Release preflight is a subsequent explicit surface for account, exact package, route, timing bounds and action authority. If the native type gate prevents operational editorial approval, the UI says why and offers a permitted draft assessment/preparation path without inventing an approval. Show what can be decided now and what remains blocked.

**Test.** First trace Create Apply r1→r2 → Review accept / request changes / return to earlier wording, with saved, unsaved and concurrent-edit branches. Verify exactly one adoption and the intended editorial disposition, with no revision erased or applied twice. Then put an ordinary reflection, a long illustrated article, an inactive-type package, a contributor-dependent package and a small revision in the inbox. The owner must choose a useful next review, see all consequential content, make the allowed decision and explain what it did not authorize. Reopen after a changed image/account/offer and verify scoped invalidation. Preserve CQ09, native gates and separate release permission.

## Acceptance and boundary record

The revised candidate should show that a reader can answer, from the actual relevant surface: What am I looking at? What is mine to do? What happens if I act? What remains unverified? Where can I return later? Page headings and disclaimers alone do not establish that contract.

J01–J12 are recommendations for the full-app redesign. Their resolution should cite changed sections and exact new screen/state versions, with a short counterexample retest. A reviewer may accept an alternative with a reason and evidence. Agreement on the design does not settle the pending CQs, amend native sources, establish a working integration, authorize paid work or publication, or pass actual accessibility/device/runtime gates.

Do not add a universal wizard, mandatory core-story aggregate, second workspace/calendar/metrics database, universal all-green status, repeated regeneration, or a new generic dashboard to “solve” these findings. The strong native ownership and truthful-state model should remain underneath a much more direct creative and decision-making experience.
