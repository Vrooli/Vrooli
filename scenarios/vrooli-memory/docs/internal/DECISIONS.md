# Decisions — Vrooli Memory

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

D-000 through D-021 come from a completed design workshop on 2026-07-27; D-022
came from the contract review that followed it, and D-023 from live imported-
corpus validation. Five
of them **reversed an earlier position** (D-001, D-002, D-003, D-013, D-015),
and nine earlier positions were withdrawn in total — see § Superseded Decisions.
The evidence that moved each one is recorded with the decision, because the
evidence is the durable part. If you are about to relitigate one of these, check
whether the evidence still holds first.

Rows are ordered by ID. Ordering carries no priority — D-020 and D-021 are the
two most expensive to retrofit.

| D-006 | 2026-07-27 | **Unscoped `wake` is acceptable; do not build task-relevance scoping.** | Raised twice as a context-budget concern and settled: harnesses already work this way, and compaction does the relevance work by proxy — settled material of any domain is already compressed to a line. | D-007 | 2026-07-27 | **Pressure-driven compaction, scored by cohesion × slots freed — not a fixed cohesion threshold.** | A threshold needs a magic constant, drifts as the corpus grows, and strands orphans that never cluster, so the frontier grows unbounded anyway. Orphans compact last and survive verbatim, which is correct — a memory with no relatives is distinctive. Guards: recency floor, pinned exclusion, episode-facet gate. | The scoring shape is **unvalidated**; expect it to change once real clustering output exists. |
| D-008 | 2026-07-27 | **Frontier target size and wake budget are independent settings.** | Conflating them would force the frontier down to ~the wake line budget, making every frontier node summarize an enormous span and forcing constant over-compaction to serve a rendering constraint. | Frontier target is generous (thousands); `wake` runs `cover()` selection over it. Frontier size is structural, wake budget is presentational. | Never expected — this is a correctness property of the budget model. |
| D-009 | 2026-07-27 | **Summaries are embedded and searchable — required, not optional.** | The frontier contains summaries alongside leaves. If summaries had no vectors they could not participate in clustering, and nothing above depth 1 could ever form. | Retrieval returns the best-scoring node at any depth and collapses descendants of returned nodes, rather than a parents-only rule that would suppress an exactly-matching leaf in favour of a vaguer ancestor. | Never — the tree depends on it. |
| D-010 | 2026-07-27 | **One journal plus a pin flag; not a separate resolved-state store.** | An earlier design proposed two derived structures — a key/value "standing" store for preferences and facts, beside the episodic tree — justified by contradiction resolution. That justification did not survive: near-identical contradictions co-cluster on the frontier even when one is already inside a summary, because summaries are frontier nodes too. The argument that *did* survive is narrower — guaranteed inclusion in `wake`, which ranking cannot promise. | Far smaller design: one storage, one tree, a pin flag, and a facet policy table. | If pinning proves insufficient to guarantee a standing rule reaches context. |
| D-011 | 2026-07-27 | **`MEMORY.md` is a generated one-directional projection, never hand-edited or read back.** | Bidirectional sync between an editable file and a database is a conflict problem with no clean answer. As a pure projection it also gives something better than interception: a harness with no hook API still receives memory, because it reads its memory file natively at session start. | Projection covers reads uniformly across every harness. The write half of this decision was superseded by D-015 — the prompt block no longer teaches a write verb, and capture (D-015, `VMEM-P1-008`) replaced hooks-as-hardening. | D-012 | 2026-07-27 | **Defer re-summarization drift monitoring to P2.** | Summaries are lossy by design, so dropped facts are intended compression rather than defect. | Ships without drift instrumentation. | D-013 | 2026-07-27 | **This scenario is a direct-product candidate, not internal-only infrastructure.** | *Reversal.* An earlier revision marked monetization and go-to-market `not-applicable` on the grounds that this is a substrate other scenarios depend on. That reasoning ignored the design's own property: the harness integration is a prompt block plus a CLI plus a generated file projection, none of which require Vrooli. That is the kill signal, and it is internal. |
| D-014 | 2026-07-27 | **The tool is free; revenue is indirect, via ai-gateway inference fall-through. Team/shared memory is speculative expansion, not the revenue case.** | An earlier revision put the revenue case on a paid team tier, which forced reopening D-005 and pointed the product at a materially harder build. The actual mechanism already exists: ai-gateway routes local models → BYOK → hosted, so a user who can run neither local inference nor their own key falls through to a paid option. Memory is an unusually good demand driver because compaction is *recurring background* inference proportional to retained corpus, not per-user-action. | The memory capability is never feature-gated. This scenario builds no billing, entitlements, or tenancy — it just routes through ai-gateway. **D-005 stays closed.** A standalone build must *package* ai-gateway rather than bypass it, or the revenue surface disappears. Team sharing is documented as P2-at-most and must not shape architecture or justify P0/P1 work. | Two dependencies, both outside this scenario: the Vrooli hosted-inference tier does not exist yet (ai-gateway's own `MONETIZATION.md` records the revenue line as deferred), and fall-through rate is unmeasured. If fall-through is negligible, the inference path is a rounding error and monetization returns to an open question. |
| D-015 | 2026-07-27 | **The prompt block describes _what_ to remember; it never instructs the agent to call a memory command. Native writes are captured, not redirected.** | *Reversal of the write half of D-011.* Telling an agent to use a foreign write verb is an instruction-compliance problem with three outcomes — comply, ignore, or write to both stores and fork memory silently — and the third is the worst because it looks like success. Describing what to remember lets the agent use its built-in memory tool, which it uses reliably because that is its native behaviour. This converts a soft adoption failure into a hard, testable capture problem. | `VMEM-P1-007` is rewritten and gains a test asserting the rendered block contains no memory-command imperative. Capture becomes `VMEM-P1-008` at P1: hook where the runtime exposes one, store diff as the universal floor. Hooks are **load-bearing, not hardening** — the single-blob harnesses (Codex, opencode) cannot be diffed reliably into discrete memories. The old `VMEM-P2-002` "write-path enforcement hooks" is retired; its id now carries Cursor support. | If a harness's native memory tool proves uncapturable by both channels, that runtime falls back to instructing the CLI directly — accepting the compliance risk for that runtime only. |
| D-016 | 2026-07-27 | **Import idempotency is by content-addressed key `hash(harness_id, source_path, normalized_content)`, never by offset or watermark.** | Every import source is a file a human or an agent may rewrite out of order. Positional keys break on the first reflow and re-import an entire file as new; watermarks desynchronise on any out-of-order edit. A content hash with a unique index needs no cursor and no state file. | Re-import is a no-op for unchanged items — that is the diff. **Accepted consequence:** a source memory edited in place hashes differently and imports as a *new* entry rather than updating the old one. Correct under an append-only journal with facet supersession — the edit is a new assertion. The alternative, fuzzy-matching edits onto existing entries, is a harder system whose failure mode is silent false merges. | If operators report edit-churn producing visible duplicate pairs that supersession fails to resolve. |
| D-017 | 2026-07-27 | **The projection is bounded by each harness's documented size cap, and pinned entries are emitted first.** | Codex documents a **32 KiB** default cap on `AGENTS.md`; the other installed runtimes expose no stable numeric cap. Phase 8 measured the scenario-owned guard across all six targets and proved pinned overflow fails before a file write. | `wake` budget is capped per harness rather than globally. Ordering is pin-first, and the 32,768-byte scenario guard prevents a pinned rule from being silently dropped by this system. Native oversized files are not written merely to probe undocumented runtime behavior. | If a harness publishes a larger stable cap or changes its injection semantics. |
| D-018 | 2026-07-27 | **The pinned set is bounded by operator curation — consolidation proposals, renew-or-lapse, and a pin budget — never by compaction or automatic eviction.** | Pinning shipped with a signal and no response: `wake` reports overflow (`VMEM-P0-006`) and `OBSERVABILITY.md` tracks pinned-set size, but nothing ever *removes* a pin, so the set grows monotonically. Agents cannot pin — promotion is operator-confirmed (`DATA.md` § Import does not auto-pin) — so the failure mode is not a flood but slow accretion. The binding constraint is **attention, not tokens**: a wake view with fifteen standing rules is read, one with three hundred is skimmed, so the guarantee that makes pinning valuable decays long before the token budget overflows. The redundancy is already observable — the hand-curated `MEMORY.md` this scenario replaces carries six git entries of which three ("NEVER stash/restore/checkout--", "no mutations", "no stash") are one rule stated three times. | `VMEM-P1-010`. Consolidation reuses the forest's cohesion scoring with a *proposal* as the terminal action instead of a collapse — same machinery, different ending. Lapsed pins are unpinned, never deleted, so they remain searchable standing-rule memories and the mechanism fails safe. The budget is the forcing function; without it review is optional and therefore skipped, exactly as measured on `--backlog-ref` in D-001. Automatic merge was rejected: a rule the system must display unconditionally cannot be silently rewritten. | The budget value and review interval are unvalidated. Revisit if operators hit the trade-off prompt routinely on pins that all genuinely belong, which would mean the cap is set below real need rather than above it. |
| D-019 | 2026-07-27 | **The facet vocabulary and its policy table are seeded data, not Go constants.** | *Cheap insurance, taken deliberately.* The facet set stays **closed** — D-019 does not weaken the `DOMAINS.md` invariant, because "closed" means every write is validated against a known set, not that the set is fixed at compile time. Holding definitions and facet→policy mappings in `facets` tables seeded at boot costs essentially nothing now, and it is the one change that would let a second vocabulary exist later without touching every domain that reads policy. | Validation loads the set from the table; an unrecognised facet is still a hard error at write. **Honest residual cost:** the wire representation stays a closed proto enum for stability, so a genuinely new vocabulary would still need a proto change — probably a string facet id rather than an enum. This decision removes the storage and policy-plumbing half of that cost, not all of it. | Never expected. This is strictly cheaper than the alternative even if no second vocabulary is ever built. |
| D-020 | 2026-07-27 | **A journal entry is bounded prose plus its derived facet texts. It never references a blob.** | The entry shape is the actual fork between "memory" and "ledger", and it is the one item here that is expensive to retrofit. Agent memories are short prose; a source ledger holds papers, datasets, Lean files. Chunking a long artifact into entries would not merely flood the frontier — it would **distort compaction**, because cluster scoring counts nodes rather than information, so one chunked paper outbids genuinely cohesive clusters. | No BlobStore seam in `journal`, unlike the template's `notes` example. A memory that needs to point at a large artifact stores the reference *as text* — a path or URL — which costs nothing and keeps frontier accounting honest. | If the source-ledger direction is actually taken (`ARCHITECTURE.md` § Deliberately Not Built). This is precisely the decision that direction would need to reopen, which is why it is recorded rather than left implicit. |
| D-021 | 2026-07-27 | **Record the generalizable core as a seam; build no generalization now.** | The engine under this scenario — append-only journal, provenance, multi-vector index, frontier compaction, `cover()` budget, content-addressed import — is not memory-specific, and several applications want it (fact-checking, mathematical research, scientific research, personal health protocols). But the design is unvalidated in exactly the places generalizing would multiply: only `health` exists in code, D-007 records the compaction scoring shape as unvalidated, D-018 records the pin budget as unvalidated, and the facet taxonomy has never met a real corpus. Across one store a wrong facet model is a correction; across several it is a migration. | The idea, the two candidate shapes (package extraction — preferred — versus multi-store in one scenario), and the two non-obvious traps (belief state is not summarization; entry shape is the real fork) are written up in `ARCHITECTURE.md` § Deliberately Not Built. **No `store_id`, no multi-store API, no package extraction, no requirement depends on it.** The only cost paid forward is D-019 and D-020. | When the unified store holds a real corpus and the facet model has survived contact with it — or when a second ledger becomes actual scheduled work rather than an idea. Not before both. |
| D-022 | 2026-07-27 | **Promote harness memory import from P1 to P0 (`VMEM-P0-011`).** | As originally scoped, **P0 shipped a system with no writers.** D-015 removed the "instruct the agent to call the CLI" path, capture was `VMEM-P1-008`, and import was `VMEM-P1-009` — so at P0 the journal filled only if a human typed `memory note`. Four consequences, all at the milestone meant to prove the design: compaction (`VMEM-P0-007`) and the wake budget (`VMEM-P0-008`) cannot be exercised without corpus volume; federated registration (`VMEM-P0-009`) publishes a corpus that cannot certify, since search-hub requires at least one reviewed positive and one junk negative or it returns `SEARCH_EVAL_CORPUS_INADEQUATE`; D-013's kill signal — "recall quality is not clearly better than a harness's built-in memory" — is unevaluable; and D-021's own caveat that the facet taxonomy "has never met a real corpus" would still hold at the end of P0. Import is the cheapest fix because the corpus already exists on this machine: 392 Claude Code memory files plus the `MEMORY.md` index. | P0 gains one requirement (11 total). Import moves ahead of compaction *and* ahead of projection in the transition sequence — ahead of projection is a **correctness** constraint, not a preference: a projection overwrites the harness memory file and `MEMORY.md` is itself an import source, so projecting first would destroy the corpus before reading it. Turns D-007 (scoring shape), D-018 (pin budget), and D-019/D-021 (facet taxonomy) from paper assumptions into day-one measurements. Id `VMEM-P1-009` is retired, not reused; `VMEM-P1-010` was deliberately not renumbered. | If import proves to yield a corpus too small or too homogeneous to exercise compaction, the gap is real and the next candidate is promoting capture (`VMEM-P1-008`) as well — accepting a larger P0. |
| D-023 | 2026-07-28 | **Bound embedding requests at 4,000 Unicode code points, preserving head and tail, before adding the provider task prefix.** | Live replay of the imported corpus left one entry retrying indefinitely: the local embedding route accepted an exact 5,000-character payload but rejected the previous 6,000-character envelope with `input length exceeds the context length`. | D-024 | 2026-07-29 | **Keep the six-facet taxonomy; do not trust the current zero-shot classifier for unattended broad classification.** | A 50-entry stratified imported-corpus review found 17 correct assignments (34%) and 33 corrections. | D-025 | 2026-07-29 | **Keep pressure-driven compaction scored as mean pairwise cohesion × slots freed; use frontier target 16.** | The initial 412-entry, single-harness corpus had 28 episode topic-vector candidates and 378 pairwise cosine comparisons (`min 0.5752`, `mean 0.7343`, `max 0.9391`). The distribution has no defensible universal cutoff. A ranking score lets high-cohesion clusters free space first and leaves distinctive material intact. A target of 16 provides a compact working frontier without conflating it with the independent 40-line wake budget. | Phase 11 must implement this score shape and default target, with no fixed cohesion threshold. | D-036 | 2026-08-07 | **Schedule compaction as a bounded pass inside the maintenance loop, after import and projection.** | D-031 correctly made rebuild provider-independent, but nothing then called the explicit compaction pass. The forest sat empty for a day at 2,628 eligible nodes against a target of 16 while every probe stayed green, so the "infinite journal, bounded view" guarantee held only for storage. Compaction is the one maintenance step whose cost scales with the backlog rather than with the number of runtimes, so it cannot share the per-runtime timeout. | `forest.Service.RunBounded` stops cleanly at a cluster budget even above target; the loop calls it with `VROOLI_MEMORY_MAINTENANCE_COMPACT_LIMIT` (default 200) under a 30-minute bound, records the outcome on `maintenance_runs`, and never fails the run on a compaction error. Ambient memory must never be blocked on the backlog; the canopy a pass grows is picked up by the next tick. Each cluster is still an atomic write, so a bounded pass is durable progress and the next pass resumes from a smaller frontier. | Revisit when compaction becomes a separately queued, resumable job with its own progress and cancellation semantics. |
| D-037 | 2026-08-07 | **Report the compaction backlog as a non-critical health signal, never as unhealthy.** | The empty forest was invisible because no surface compared the eligible frontier against its target. A large frontier degrades ambient recall quality but does not stop recall, and handing a quality signal to a liveness remediator invites restart loops. | The `canopy` health check is Optional and reports the frontier size **the compaction engine recorded on its last pass**, flagging `status=lagging` above ten times target and surfacing a failed pass directly. It deliberately does not recompute eligibility: the first implementation did, in SQL, and reported 273 against the engine's 16 because it omitted the recency floor, the pin guard, and the vector-presence guard — the same surface-drifts-from-engine defect this scenario already fixed once on the frontier RPC. Reading the recorded value also keeps a thirty-second probe from loading every candidate. `vrooli-autoheal`'s loop restarts only itself and explicitly treats a self-reported degraded dependency as unfixable by restart, so the signal is safe. | Revisit if a remediator begins acting on scenario-reported degraded status. |
| D-038 | 2026-08-07 | **A harness store that holds only this service's own managed block is a completed import that saw nothing, not a failure.** | After the one-directional projection fix, four runtimes (codex, gemini, grok, opencode) whose entire store is the projection reported `non-empty harness store yielded zero importable items` on every maintenance tick. Four permanent reds on the operator surface is how a real failure later gets missed. | `extractPath` drops sources that are empty once the managed block is removed and reports that it did; `discover` returns that as a healthy zero. A store with content that genuinely fails to parse still errors. | Revisit if a runtime legitimately needs an alert when its native store stops receiving writes. |
| D-039 | 2026-08-07 | **One journal database, at the storage-resolver path, merged by union when forks exist.** | The service ran for two days against a committed `SQLITE_PATH` override pointing into `/tmp` while the registered backup target pointed at a different, diverging copy in the repository tree. The two files were forks, not stale-and-fresh: 351 entries existed only in the runtime copy and 3 only in the repository copy. | Corpus divergence is repaired by union — never by copying one file over the other, which would delete permanent journal rows and break the append-only boundary. The override is removed, the resolver path is the single authority, and the backup target follows the file the API actually opens. | Revisit only if a deployment genuinely needs a non-default database location, in which case the backup target must be derived from the same resolution. |
