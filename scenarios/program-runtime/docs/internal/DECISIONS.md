# Decisions — Program Runtime

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| Date | Decision | Context | Consequences | Revisit Trigger |
|---|---|---|---|---|
| 2026-08-06 | Use the generated `react-vite` scenario documentation contract. | Scenario scaffold was generated from the template. | Docs start with stubs and maturity metadata in `docs/manifest.json`. | Revisit when scenario adopts a different template or doc contract. |
| 2026-08-06 | Implement the programmatic-tool-calling techniques natively rather than adopt Prime Intellect's Prime Agent as a runner. | Prime Agent (MIT) demonstrated the RLM programming model and a Continual Harness. Wrapping it as an agent-manager runner was the cheaper path and was evaluated first. | Vrooli owns the governed version. Prime Agent may still be wrapped later as a low-priority open-weights runner; that is a separate, unrelated decision. | A future harness offers a governance boundary Vrooli cannot express through `cli-manifest` governance. |
| 2026-08-06 | Generate bindings from `cli/manifest.json` + the proto descriptor image, **not** from prompt-manager actions. | Actions were the obvious source — they are already curated and agent-facing — but an action wraps `argv`: subprocess in, untyped stdout out. | Zero per-scenario integration; typed pre-flight validation; governance (`effect`, `run_eligible`, `permissions`) is inherited rather than redeclared. Bound by manifest coverage: 58 of 128 scenarios today. Actions remain the curation layer above bindings. | Manifest coverage stalls, or a binding need arises that no proto method can express. |
| 2026-08-06 | Python for the kernel, rejecting Go, TypeScript, and Starlark/Lua. | The scenario's value depends on a model writing a correct program on the first attempt. Go was the consistency-preserving choice. | Model competence at Python-in-a-REPL is materially higher; IPython supplies session persistence, async, and rich reprs (the handle mechanism) with no new code. Costs a non-Go toolchain in CI and forfeits automatic Go-side identity propagation (see Problem: identity). | Measured first-attempt correctness converges across languages, or the toolchain cost exceeds the capability gain. |
| 2026-08-06 | Ship the kernel as a sidecar under `kernel/`, not as a shared `packages/` entry. | Follows `browser-automation-studio/playwright-driver`. A shared package was the initial proposal. | Exactly one consumer, so nothing is shared. Bindings/handles and kernel-host stay separate modules **inside** the sidecar so a later promotion to `packages/` is a move, not a refactor. | A second scenario needs the binding layer. |
| 2026-08-06 | Handles with bounded default representation are the default return type; full materialization is explicit. | The obvious implementation returns decoded responses directly. | This is the entire token thesis. Bindings without bounded materialization produce the same context cost with different syntax, so *context bytes per query* is an acceptance signal, not a nice-to-have. | Never — if this is relaxed the scenario has no reason to exist. |
| 2026-08-06 | Kernel variable state is process memory and is deliberately **not** persisted. | Durable handles look attractive for long investigations. | A handle is a live reference. Promoting it to durable storage recreates the materialization cost this scenario removes. Named durable sessions (`OT-P2-003`) reuse a live kernel; they do not serialize handles. | A concrete use case requires handle survival across a kernel restart. |
| 2026-08-06 | Typed inference (classify/extract/judge) resolves through **ai-gateway**; `structuredresult` is promoted out of agent-manager rather than generalized inside it. | Generalizing agent-manager's run-attached pipeline and exposing it via its CLI was proposed first. | One inference front door. agent-manager becomes a consumer of the same surface, so runs and programs get identical guarantees — notably that provider extraction is advisory and local JSON Schema validation is the only authority. Creates a dependency on that promotion landing. | ai-gateway cannot express a shape a program needs. |
| 2026-08-06 | Bounded typed inference and delegated agent runs are **separate** bindings. | Prime Agent conflates them: every `rlm()` is a full sub-agent. | A program picks the cheap path for cheap work. `vrooli.ai.*` is bounded latency and cost; `vrooli.agent(...)` is an agent-manager run. Keeping them distinct is why the token argument survives contact with real workloads. | Never expected; merging them reintroduces the cost profile this rejects. |
| 2026-08-06 | Program telemetry emits through the shared `api-core/eventbus`; no scenario-local analysis stack. | A local statistics surface was tempting because program failures are unusually good evidence. | agent-manager's existing friction analysis consumes program events (it must subscribe); meta-optimization-manager surfaces them via `gaps`/`focus`. Program telemetry does **not** depend on the run-attribution fix — a syntax error is a fact regardless of who caused it. | The shared bus cannot carry a program-specific event shape. |
| 2026-08-06 | Program friction feeds `gaps`/`focus next`; it is **not** a coverage projection. Act coverage is the projection. | Both are meta-optimization inputs and were initially conflated. | Act measures *effect supply* (is the operation invocable). Friction is observed behavior and belongs in the ranking layer. Agents read the synthesized board rather than being told to consult new data sources, so new signals never require editing an agent prompt. | The projection model in `COVERAGE-MODEL.md` changes shape. |
| 2026-08-06 | The operator console is designed as an **IDE for programs an agent wrote**, with a real code editor as its anchor. | The primary user is an agent that never opens the UI, so the console is forensic rather than task-oriented. A formatted code block was the cheaper option. | Monaco (already governed in the fleet via react-component-library) supplies gutter markers, the markers API, hover providers, inline decorations, and a diff editor. Five surfaces become panels around one center. Monaco is lazy-loaded; `shiki` renders read-only snippets so list views do not pay for it. | The editor stops carrying scenario-specific meaning (hover signatures, per-line materialization) and degenerates into syntax highlighting. |
| 2026-08-06 | The editor's squiggles are produced by the **same** pre-flight validator the API uses to refuse a call — never a reimplementation. | An editor-side validator would be faster to build and could drift. | The editor cannot lie about what will be accepted. Stated as a design invariant rather than an implementation preference. | Never. A divergence here makes the editor actively misleading. |
| 2026-08-06 | No friction-analysis surface in this scenario's UI. The statistics surface renders **declared measures** instead. | A "Problems panel" aggregating recurring failure shapes was proposed and rejected — it would have been exactly the scenario-local analysis stack already ruled out. | Friction analysis stays in agent-manager, fed by emitted events; program detail links out to the owning run's investigation rather than reimplementing it. Measures are typed, parameterized, search-hub-matchable queries, so the thesis metric (context bytes avoided) becomes answerable in natural language without opening the UI. | agent-manager stops consuming program events, leaving the evidence unread. |
| 2026-08-06 | **Unbound** and **refused** are distinct concepts with distinct surfaces. | Both are "a thing an agent could not call" and were initially conflated. | *Unbound* is static registry state — a fleet capability with no typed binding (no manifest, `binding.kind: "local"`, an `omitted` RPC, external-tool-only). It renders in the binding registry and is the Act numerator. *Refused* is a runtime denial of an existing binding (`run_eligible: false`, destructive without a grant). It renders inline on the offending program line. Act cell vocabulary (`COVERED`/`PARTIAL`/`MISSING`) belongs to operation classes and is never reused for individual bindings. | The governance vocabulary in `cli-manifest.schema.json` changes shape. |
| 2026-08-06 | Operators may author and submit programs from the console, not only replay and fork. | Owner decision. The raised concern was that a second submission path carries operator identity rather than agent identity, and would pollute the corpus that feeds meta-optimization. | Accepted with a mitigation that is now `OT-P1-008`: provenance is recorded on every submission and operator-submitted programs are excluded from corpus mining by default. The corpus keeps measuring what agents attempt. | Corpus mining begins reporting shapes traceable to operator experimentation. |
| 2026-08-06 | The binding registry surface is promoted from `OT-P2-001` to `OT-P1-007`. | The whole operator UI sat at P2 (MAY). | It is the only operator surface that carries information before any program has run, and it renders the same registry state the P0 Act numerator computes — so the data exists regardless. The rest of the operator UI stays at P2. | The Act numerator ships with an adequate consumer elsewhere and this surface earns no additional use. |
| 2026-08-06 | `refine` is **not** a domain of this scenario. | Session-local harness refinement is a real capability and was considered here. | Its evidence is the run trajectory, which agent-manager owns; its durable write targets are prompt-manager and vrooli-memory. Tier-1 refine belongs with the working agent (taught by a prompt-manager skill); durable promotion follows CLAUDE.md rule 6. Recorded so `DOMAINS.md`'s "not a domain" row resolves here. | A refinement need appears whose evidence is the program corpus rather than the run trajectory. |
| 2026-08-06 | Requirement modules are grouped by **owning domain**, but requirement **IDs stay priority-based** (`PRT-P<priority>-<n>`). | The generator emitted priority-bucket modules (`01-must-ship`/`02-post-launch`/`03-future`), which is the current template default. Mature scenarios (meta-optimization-manager, prompt-manager) use per-capability modules with domain-encoded IDs. | Domain grouping gives a per-domain progress view that matches the build order in `DOMAINS.md`; priority-based IDs stay stable because they are cited from outside this scenario — `meta-optimization-manager/docs/concepts/COVERAGE-MODEL.md` and `docs/spaces/act-space.md` both name `PRT-P0-007` and `PRT-P0-008`. Taking both changes at once would have broken those references for no gain. | A requirement's priority changes, making its ID misleading — then rename deliberately and update every external citation in the same change. |
| 2026-08-06 | The Act projection is built **before** the kernel, not after it. | The original launch sequencing put Act at step 5, after handles and telemetry. | `actspace` reads `bindings` only, so the numerator is a pure read over the binding registry with no Python involved. `meta-optimization-manager` is already waiting on it with a placeholder branch in `numeratorclient.go`. Steps 1–2 become a coherent shippable slice — a governed binding registry plus a live Act projection — that converts manifest coverage from an anecdote into a tracked board number before any program has run. | The binding registry cannot resolve enough cells for a numerator to be meaningful. |
| 2026-08-06 | The thesis metric asserts **non-scaling**, not an absolute byte budget. | The requirement originally pinned context bytes for one large-result query. | A budget proves handle discipline but cannot falsify the PRD's actual claim — that context cost stops scaling with inspected volume. The replacement runs the same query across result sets differing by four orders of magnitude and asserts a constant band. It also avoids needing a tool-call baseline harness, which would have to be maintained and would rot. | The claim in the PRD changes from a scaling claim to an absolute one. |
| 2026-08-06 | Delegation uses a private session-gated bridge to agent-manager's typed workflow routes. | Manifest-bound Connect calls correctly exclude agent-manager's write/run-ineligible workflow-start command, but Phase 11 still requires a program to launch a governed workflow and collect its result. | `vrooli.agent.run(owner, workflow_key, input)` cannot reach the network directly; Go validates the live program session, supplies a replay-safe idempotency key, waits for terminal state, and returns only the explicit result projection as a handle. An unavailable or missing workflow is surfaced as a typed program failure. | Agent-manager publishes a dedicated run/delegation binding with an equivalent governance contract. |
| 2026-08-07 | Delegated examples use a terminal validator workflow and a synchronous `Handle`. | The runtime submits delegation synchronously and returns a bounded result handle; an approval-gated investigation workflow cannot provide deterministic example completion. | `delegated-run.py` exercises the governed Agent Manager bridge with `development-toolchain-validator/skill-experiment-audit`, records its structured evidence, and avoids direct network or shell access. The bridge wait request includes the execution ID required by Agent Manager's typed route. | Agent Manager publishes a stable dedicated delegation contract, at which point the example may move off the validator workflow. |
| 2026-08-06 | Typed inference is shipped through ai-gateway; Phase 10 meters its typed Usage per session while delegated-run spend remains explicitly unmeasured. | The original plan deferred PRT-P1-002 to ai-gateway structured-extract promotion. That promotion and the governed classify/extract/judge facade are now live. ai-gateway publishes typed Usage, while agent-manager's delegated workflow result still has no per-run charge receipt. | Programs fail closed when ai-gateway is unavailable, local JSON Schema validation remains authoritative, inference usage and ceilings are durable, and delegation responses carry an explicit unmeasured note rather than a fabricated zero-cost claim. | agent-manager publishes a stable per-execution charge receipt with currency and metering basis; then complete PRT-P1-011. |
| 2026-08-06 | Use a dedicated generated capabilities message for the operational REST probe. | proto-health rejected an untyped `google.protobuf.Struct` declaration because the descriptor image only accepts scenario-owned full message names for REST payload declarations. | The capability registry output is decoded into `capabilities.DescribeResponse` and re-encoded through protojson; the endpoint remains lifecycle-friendly while its wire contract is typed and discoverable. | The capability probe becomes a Connect method with a stable service contract. |
| 2026-08-06 | Keep optional event-bus reachability in both lifecycle dependencies and the capability registry. | Scenario Dependency Analyzer requires a recovery-aware registry entry for every declared scenario dependency. | `vrooli-events` uses `try_start`, has a checker/operator action, and degrades to local persistence when unavailable; the dependency graph and runtime capability surface tell the same story. | Telemetry becomes a mandatory dependency rather than an optional enhancement. |
| 2026-08-11 | Use a local supervisor boundary instead of container isolation for the first production runtime. | Program Runtime executes trusted-local agent programs and needs a portable development path. The shipped boundary now allowlists environment, pins a mode-0700 work directory, applies Linux resource limits, and kills process groups on deadline. | The runtime is materially safer and cross-platform lifecycle-compatible, but a Python program can still import `subprocess` and reach host resources. | Untrusted or multi-tenant execution enters scope; revisit with workspace-sandbox plus container/VM isolation and a deployment contract. |
