## Tools focus: Agent Manager

Use Agent Manager when work must run as a governed agent run: a task the current session should not do itself, a multi-step workflow with typed hand-offs, or a diagnosis of runs that already happened. This skill holds the judgment `--help` does not: which shape to start, how to wait, and how to read a finished run. Command flags are in the CLI (`agent-manager <group> <command> --help`); several subcommands print only a usage line, so read flag names here or in `cli/cmd_*.go`.

Required reading, once per task context (use `skill show` once for metadata, never as a progress check; re-read only when the source changed or the guidance is missing): `prompt-manager skill read vrooli-memory investigating-agent-runs program-runtime --output=skills --format=markdown` (the learning spine; how to read a run report, cited not restated; when a program's `agent.start` and `agent.collect` is the layer instead of this CLI). If Prompt Manager or Search Hub is unavailable, do not repeat the failed lookup or stop unrelated work: read the canonical source from `scenarios/<owner>/skills/` or `scenarios/prompt-manager/store/skills/packs/`, record that registry usage was unavailable, and if the source is absent keep the unknown and continue independent work.

### 1. Scope

In scope: starting one run or one workflow execution; result specs; waiting; reading one run or a cohort; discovering retained conversations from incomplete clues; bounded context and provenance; parking and waking; caller-neutral finite investigations and findings; bounded learning retry; what to journal. Out of scope: authoring workflow JSON (`path:scenarios/agent-manager/docs/guides/workflow-adoption.md`), profile and runner policy, regulating Agent Manager itself (`agent-manager-improve`), starting a scenario (`vrooli scenario start`).

### 2. Before acting

1. `vrooli-memory recall wake --scope agent-manager-usage` for the ambient set; when the task names a workflow or profile, `vrooli-memory recall recall "<workflow key or profile>" --scope agent-manager-usage --limit 5`.
2. Record advice IDs applied or rejected and the decision each changed. Advice is evidence, not authority. Keep task and attempt IDs, an ordinal, comparable context and observed start timestamps before orientation.

For a plan-family cohort, read `agent-manager-plan-family-supervision` before creating a watch. For large efforts use `agent-manager effort board` (or `--effort-ref` for an exact effort) and the Efforts view, with `large-effort-supervision` for judgment and `scenarios/agent-manager/docs/reference/effort-supervision.md` for typed enrollment, withdrawal and the delivery commands (`run continue`, `run park`, `run wake --key`, `run report --children`, `effort epoch-check`). Discovery permits observation only; missing metrics stay unknown; steer a delivery goal through its goal home files, not the board. `--local-owner` serves explicit local operators on supported owner mutations without persisting tokens. `effort signals <ref> --after <seq>` and `effort board` are snapshots, not waits or progress signals: read the exact effort when its reference is known, read signals at a real review event, and wait through the owner route instead of polling an unchanged board.

For a bounded diagnosis of an existing run set, use the typed investigation operation or `agent-manager.investigate`. Operation status is independent of diagnostic condition: a completed result may be `inconclusive`, and missing coverage is never an observed zero. Use one stable request key, wait once through the owner, and reattach with get or wait after a disconnect. If `learning.captureState` is `pending`, retry with `POST /api/v1/investigations/{id}/learning-retry`, which does not rerun diagnosis.

### 3. Choosing the shape

One prompt with one answer is a **bare run**; two or more agent steps with typed hand-offs, or a wait between them, is a **declared workflow**; work inside a program-runtime program with arity over many units uses `agent.start(**req)` and `agent.collect(h, wait_seconds<=300)`, not this CLI; reading runs that already happened is §4 (a known run id is inspected directly, an unknown run id is found with `agent-manager conversation search` and `conversation context`, `references/extended-operations.md` §4.1).

**Bare run.** `agent-manager task create --title "<t>" --scope-path <path>` if no task exists; pick the profile by role, not model (`profile list`); choose the result shape: a fixed set of answers `--classify a,b,c`, fields the caller reads `--result-schema-file <schema.json>`, prose only neither (read `run result <id>`). Exactly one of `--classify`, `--result-schema`, `--result-schema-file` (the CLI refuses two). Start: `agent-manager run create --task-id <task> --profile-id <profile> --prompt "<p>" [--classify ...|--result-schema-file ...] --workload-key <stable-key> --workload-kind adhoc --idempotency-key <k>`. `--workload-key` is what `measures get workload-breakdown` and `workload-efficiency` group on: reuse it for the same recurring job and put no timestamp in it. `--idempotency-key` makes a retried create return the same run. A run that needs another producer's result parks itself (`run park <id> --producer <scenario> --key <k>`); the producer's owner wakes it with `run wake <id> --result "<text>"` and the run reads it with `run await-result <id>`.

**Declared workflow.** `workflow list --owner <scenario>`; dry plan with `workflow simulate --owner <o> --key <k> --input-file in.json`; start with `workflow start --owner <o> --key <k> --input-file in.json --idempotency-key <k>`; wait once with `workflow execution-wait <execution-id> --timeout-seconds 1800` (server-side: it returns on the terminal transition or at the bound, `0` blocks until terminal; never wrap it in a loop); read with `workflow execution-get` and `workflow trace`; payloads with `workflow execution-result <execution-id> --explicitly-authorized`.

**Waiting on a bare run.** There is no server-side wait verb, so do not poll `run get` or `run list`; use `program-runtime library run agent-manager.run-inventory` for one bounded `{id,label,status,phase,execution_mode,progress_percent,source,updated_at}` snapshot; imported-session ids and run content stay private; continue by offset while `offset + count < total`. Never treat it as a progress signal. Choose the shape before starting when you can: a one-node workflow around the prompt gives `workflow execution-wait`. Already started and interactive: `run events <id> --follow` streams to a terminal (a live socket that ends with the session, using the resolved API base including `--api-base` and the saved token; a terminal status is an observation). Already started and headless: record the run id in your journal entry and stop; the next session reads `run get <id>` once. Another scenario produces what the run needs: park it. `run quiesce --scenario <name> --timeout <duration>` waits once for planned maintenance; its filters identify affected runs and are no global admission barrier, so recheck other active runs before restarting Agent Manager and never infer global idleness from a scenario-scoped drain; without `--force` a timeout leaves live work untouched.

**Program contracts.** Declared owner programs (`agent-manager.conversation-recall`, `friction-digest`, `investigate`, `investigation-evidence`, `setpoint-read`, `supervision-case-read`, `supervision-evaluate`, `supervision-experiment-read`, `run-inventory`) run as `program-runtime library run <name> --input key=value` (inputs are JSON-decoded: `--input 'window="7"'`; the runner owns session, wait and cleanup: branch on the declared envelope, never rebuild joins from database reads). Inputs and `conversation-recall` degradation rules: `references/extended-operations.md` ("Program contracts").

### 4. Reading runs

- **One run:** `run get <id>` for status, phase and exit code. FAILED or NEEDS_REVIEW: `run report <id>` then `investigating-agent-runs`. Result missing or abstained: `run result <id>`. Succeeded but slow or costly: `run report <id>` then `reviewing-agent-run-efficiency`. What the agent said hurt: `run report <id> --json` (`selfReportSpans`). Which commands ran: `run report <id> --facts`.
- **Many runs:** by tag `measures cohort-report --filter-json '{"tag_prefix":"<p>"}' --limit 50`; by ids `measures cohort-report --run-ids a,b,c`; one owning scenario `run agent-manager.friction-digest` (inputs `scenario`, `window_days`).
- **Recurring friction:** `usage friction [--status open] [--owner <scenario>]`. What to change (quota, tools, programs, corrections): `usage recommendations [--run ID]`, one ranked list in which each action names its owner, effect, evidence and verify command. Fleet rate: `measures get run-success-rate --window last_7d` (other measures: `measures list`, then `measures get <id> [--param name=value]`).

Reading the friction-digest envelope: `ok` means `signals.top_fingerprints` are the fingerprints to act on, with `signals.inferred_annotations` stating the gated label coverage (a null inferred rate is an unproven gate: the label is evidence, never a rate); `partial` means act on what is present and `errors[0].class` names the gap; `scenario_unreachable` means agent-manager is down (journal, stop); `no_runs_in_window` means widen `window_days` once or accept the empty reading; `invalid_input` means nothing was read.

`run report` reads status and cost first, then result provenance, then failure counts; its `Next:` lines are the drill-down and it excludes transcript bodies. `selfReportSpans` ("blocked", "cannot find") cue a read of the run and are no verdict. Command friction comes from `measures get tool-profiles` and `usage friction`; `--owner <scenario>` scopes findings and profile totals while the coverage line stays window-wide and counts commands read by an older parser (outcomes there may be missing).

For Test Genie run summaries, catalogs, and findings, run `program-runtime library run test-genie.run-evidence` with `--input view=<view> --input scenario=<scenario> --input run_id=<run-id>`, choosing `show`, `artifacts`, or `findings`. Copy an opaque artifact ID from the catalog before transfer, then call the same program with `--input view=download --input scenario=<scenario> --input run_id=<run-id> --input artifact_id=<catalog-id> --input path=<relative-path>` in the admitted Program Runtime workspace. The program validates identity and stream capability, preserves existing files unless `--input overwrite=true`, and returns a metadata-only receipt. If the receipt is uncertain, reconcile before retrying; never guess IDs or construct private URLs.

**Annotations and label-filtered search.** Deterministic lenses first; read the inferred layer only for causes rules cannot see, and say which gate it passed: `usage annotations --window last_7d` (per label proven, partial or unproven; model; calibrated or raw), `annotations coverage|series|show <run-id>|run <run-id>|evaluate --since <RFC3339> --limit 10|scheduler`, and `conversation search "..." --mode semantic` or `--tags label:work.blocked_by_tool`. A proof is per model, an unproven label is evidence not a rate, an empty window is unknown not zero friction, and mood labels (`operator.dissatisfied`, `pleased`, `impatient`) read human-written messages only. `friction-analysis` is the four-lens method; read `annotation-tuning` before changing a label.

### 5. Investigating

One or more failed runs: `investigation start --file request.json` (subject `run_ids`), then `investigation wait|get|list`; a reusable program caller uses `program-runtime library run agent-manager.investigate` with a stable request key and bounded inputs. A historical legacy result with an explicit operator decision uses `run apply-investigation` (old approval and apply records only). A fingerprint that keeps returning: `usage friction` (plain description, owner, cost), then `usage friction-report <fingerprint>` files it with scenario-qa.

New diagnosis uses the typed investigation contract and the bounded `agent-manager-process-investigation` method behind the owner workflow. Never start the retired `agent-manager/investigate` workflow or paste either investigation skill into a bare run; the apply skill is a separate authorized repair path for retained legacy records, and a typed diagnosis never grants repair authority. Unknown-run recovery, debug order, safety details, in-use settings, troubleshooting, joined supervision reads and caller-identity refusals are in `references/extended-operations.md`.

### 6. After acting, always

Use `vrooli-memory learning record --scope agent-manager-usage --attempt '<Attempt JSON>'` once per selected operation (the shared Memory skill has the contract). Retain task identity across retries, one attempt identity and ordinal per actual attempt, observed timestamps, comparison context, operation and owner evidence; record applied and rejected advice IDs and assessed or unknown verdicts; capture observed first-action time and tool round trips, omitting unknown values; mark fixtures test. Only evidenced outcomes are verified_success; failed, unavailable and unknown stay distinct, and a completed run is not proof that supervision helped it. Append no ordinary journal run-record or workflow-note as well, and keep work-records for implementation changes. On capture failure retain the unchanged payload and retry its ID; the operation outcome does not change. Supersede contradicted advice through the shared curation path; supervision policy changes follow the owner replay and promotion process, never remembered prose.
