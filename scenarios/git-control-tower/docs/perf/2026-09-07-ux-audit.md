# Git Control Tower UX performance audit

## Outcome

The primary performance problem was the Changes surface during interaction.
The current targeted capture reports 27.0 ms average FileList commit time,
323.0 ms maximum FileList commit time, 70% dropped frames, 336.9 ms of Layout,
and 446.9 ms of UpdateLayoutTree work. App commits are similarly expensive at
27.6 ms average and 327.7 ms maximum.

The history list is currently healthy after virtualization. The earlier
comparison measured a 64% reduction in GitHistory average commit cost. Markdown
deferral remains inconclusive for CPU reduction. Panel resize was improved by
imperative DOM updates, but the App-level query/state cascade remains.

## Findings

### P0 — FileList materializes all expanded rows and reruns parent work during scroll

Locations: `ui/src/components/FileSection.tsx:66-88,120-135`,
`ui/src/components/FileList.tsx:500-536`, and
`ui/src/components/FileList.tsx:743-1274`.

Every expanded section maps every file into a `FileRow`. `FileRow` is memoized,
but `FileSection` is not, so the parent still rebuilds entry data and evaluates
the complete section tree on each upstream commit. Grouped mode also performs
repeated `groupedSections.filter(...).reduce(...)` work inside the render loop
at `FileList.tsx:770`.

Evidence: the targeted capture measured 27.0 ms average and 323.0 ms maximum
FileList commits, with a 70% dropped-frame rate and hundreds of milliseconds of
layout work.

Recommended action: flatten the visible file model into section headers and
rows, virtualize that single list with the existing `@tanstack/react-virtual`
dependency, and precompute grouped-band summaries once with `useMemo`. Preserve
section collapse and selection semantics in the flattened model. Add a targeted
before/after capture and budget the journey after the change.

### P0 — App owns too many live subscriptions and broadcasts polling churn

Locations: `ui/src/App.tsx:478-557` and query definitions in
`ui/src/lib/hooks-core.ts`, `ui/src/lib/hooks-settings.ts`,
`ui/src/lib/hooks-agent.ts`, and `ui/src/lib/hooks-visual.ts`.

The root component owns repository status, history, sync, approved changes,
provenance, authority, health, branches, settings-health, grouping, and many
mutation subscriptions. Several queries poll at 5–30 second intervals. Query
fetch-state changes and new response objects therefore invalidate the root
render path and make FileList, GitHistory, and DiffViewer participate in work
that belongs to another panel.

Evidence: App and FileList both remain above the 8 ms component budget during
the targeted scroll capture. The prior comparison explicitly attributed
residual App commit cardinality to polling-query cascade after resize state was
removed.

Recommended action: move query ownership down to the panel that consumes each
query, starting with settings-health, provenance/approved changes, and review
surfaces. Keep only shared repository identity and the minimum status/diff
selection state at App scope. Use stable panel props and `React.memo` after the
subscription boundaries are moved; memoization alone will not stop a child
whose parent owns all changing query state.

### P1 — Grouped FileList render has avoidable superlinear bookkeeping

Location: `ui/src/components/FileList.tsx:743-770`.

For each group, the render computes the same band group count and file count by
scanning `groupedSections` again. With many groups this becomes O(groups²),
before row rendering. The grouped model also allocates four category arrays per
group.

Recommended action: derive `bandSummaries` once while constructing
`groupedSections`, attach the summary to each group, and avoid `Object.values`
and repeated filters in JSX. This is a low-risk improvement that should remain
after virtualization.

### P1 — Syntax-highlighting and editing dependencies are reachable from the initial app chunk

Locations: `ui/src/components/DiffViewer.tsx:3,11`,
`ui/src/lib/highlighter.ts:1,120-139`, and `ui/vite.config.ts:43-50`.

`DiffViewer` statically imports the Monaco React wrapper and Markdown preview.
The highlighter module statically imports Shiki and declares a broad language
set. Mermaid is manually split, but Monaco and Shiki are not given equivalent
route/feature boundaries. The current entry JavaScript is 1,587,853 bytes
(about 430 KB gzip), and the emitted asset set is 13.53 MB because many
language modules are produced.

Recommended action: lazy-load Monaco only when edit mode opens; keep preview
rendering behind a feature boundary; split Shiki core and load the selected
language on demand, with a small plaintext fallback. Verify that the initial
HTML requests only the workspace shell and core UI. Do not remove syntax
highlighting or editor functionality to reduce the score.

### P1 — Markdown deferral improves scheduling semantics but not measured CPU

Location: `ui/src/components/MarkdownPreview.tsx:250-259`.

The previous comparison reduced commit count but left cumulative Markdown work
essentially unchanged (41.5 ms → 40.1 ms), and average commit time rose because
work was concentrated into fewer commits. This is not a proven render-cost win.

Recommended action: retain `useDeferredValue` if typing/input interleaving is a
requirement, but validate it with a dedicated typing-latency flow. For large
documents, consider section-level progressive rendering or an explicit large
document mode only if a measured complaint justifies the added complexity.

### P2 — Resize path is improved but needs a dedicated current capture

Locations: `ui/src/App.tsx` resize effects around lines 2006-2160.

Imperative width/height/grid updates already removed the prior one-state-update-
per-mousemove pattern. The old comparison showed a 29% App total reduction.
However, the current targeted flow did not produce a usable resize trace, so the
present resize experience is not freshly certified.

Recommended action: add a literal-selector drag flow and capture resize alone
after the FileList and subscription work. Keep the current imperative update
until a dedicated trace disproves its value.

## Suggested implementation order

1. Add FileList flattening + virtualization and precomputed grouped summaries.
2. Move non-workspace query subscriptions out of App and stabilize panel props.
3. Lazy-load Monaco and reduce the initial Shiki surface; re-run build and Lighthouse.
4. Re-measure Changes scroll, Markdown preview typing, and panel resize separately.
5. Set tighten-only performance budgets for the three journeys once stable.

## Limitations

The fresh governed targeted capture successfully measured the Changes-list scroll
journey. The attempted combined Markdown-open/Preview flow did not produce a
usable trace, so Markdown conclusions use the prior comparison plus static
analysis. The current resize path likewise lacks a fresh targeted trace. The
trace analyzer reports an implausible wall-clock duration field, but its
component timings, frame counts, layout totals, and web-vitals are internally
usable for this audit; repeat measurements should use deltas and per-commit
averages rather than that duration field.

## Implementation pass — 2026-09-07

Flat Changes sections now share one virtualized list backed by the existing
`@tanstack/react-virtual` dependency. Grouped-band counts are precomputed once
instead of rescanned in JSX. In the same scroll journey, FileList improved
from 27.0 ms average / 323.0 ms maximum commit time to 2.0 ms average / 12.4
ms maximum. Layout improved from 336.9 ms total / 310 ms maximum to 13.7 ms
total / 4.3 ms maximum. The capture still reports 60% dropped frames, but no
longer reports the previous multi-hundred-millisecond component or layout work.

The health-count query was removed from App and moved to StatusHeader,
preserving the settings badge while preventing health polling from invalidating
the full workspace tree. The broader panel-by-panel query split remains
follow-up work.

Monaco, MarkdownPreview, and Shiki initialization are now deferred imports.
ContextPreviewPopover was updated so it does not pull MarkdownPreview back into
the initial graph. The initial entry fell from 1,587,853 bytes / 430,225 gzip
to 1,461,675 bytes / 399,910 gzip. Lighthouse improved from 0.38 to 0.65, but
remains below the 0.75 error threshold.

The focused Test Genie run remains red on existing gates: unit reports
`UNIT_POLICY_PROJECTION_DRIFT` (missing `test:coverage`) and a test execution
failure; performance reports Lighthouse below threshold. Focused package
validation passed: type-check, touched-file lint, and 12 StatusHeader/
GitHistory tests.

## Mutation latency follow-up — 2026-09-08

The reported multi-second staging/commit/push delays include repeated full
repository-status enrichment on the authorization path. Preview, confirmation,
and writer consumption each requested UI line statistics, untracked file content
counts and author settings, although their subject uses branch/index identity
and the staged diff. Fresh lightweight porcelain parsing now replaces that work;
no authorization cache or digest bypass was added. Push target resolution uses
the same lightweight read.

Read-only measurements on the live checkout (three iterations per variant):

| Status read used by authorization | Mean |
| --- | --- |
| Full presentation status | 3.191 seconds |
| Fresh authorization snapshot | 0.379 seconds |

This is an 88% reduction for this status-read component, not an end-to-end action
latency claim. Reproduce with `GCT_PERF_READONLY_REPO=/absolute/checkout go test ./
-run '^$' -bench '^BenchmarkMutationStatusSnapshot$' -benchtime=3x -count=1` from
`api`. Normal tests skip this opt-in benchmark and use disposable/fake repositories.
Concurrent edits and host load limit comparison precision.

Workspace mutations now serialize authorization and writes per repository while
projecting all queued requests immediately. A failed request is removed from the
projection without restoring an old snapshot over later clicks. The queue pauses
status polling, tracks every pending path, retains errors from earlier requests,
and reconciles once after draining. Server refusals are errors, not optimistic
success. Bulk staging also avoids quadratic staged-path membership checks.

Commit preview starts its pending state on the first click and suppresses duplicate
preview requests. The commit control distinguishes file updates, authorization
preparation, checks, and submission; message composition remains available during
staging. Confirmed commits immediately invalidate history instead of waiting for
its 30-second poll. Push no longer performs a full fetch between reviewed safety
inspection and the server's own live inspection. Server checks, normal Git push
rules, and post-transfer verification remain in force. Background safety queries
pause during active writes; their large revision key is memoized rather than
serialized on each unrelated App render.

Evidence: 77 focused UI tests passed; focused backend authorization/status/staging/
push tests passed with the race detector; TypeScript and scoped lint passed.
Test Genie unit run `20260908-072311-87086d30` remained failed on UI policy and
execution findings plus architecture findings. No clean full-scenario verdict or
live mutating browser measurement is claimed.


## Large-change follow-up — 2026-10-15

The flat-list repair had left grouped Changes eager. This pass replaces both
render paths with one measured list containing group/band headers, category
headers and file rows. Group summaries, stageable paths and run dots are derived
once per model; scrolling stays inside the list and uses stable measurement keys
and callbacks. More than 500 net lines of duplicate/unreachable rendering were
removed. Partially staged files now retain both appearances and action routes.
Collapsed destination sections open before navigation; mobile selection and
scroll restoration retain their existing semantics.

The live checkout initially exposed approximately 10,804 changed/untracked paths.
Narrow ignore rules for copied Secrets Manager Electron bundles, delivery media
and rendered exports reduced this to approximately 1,726 (84%). Native-host and
Electron source, delivery Markdown, verifier scripts and authored prototypes
remain visible. All files remain in place. Already tracked bundle files remain
tracked; the ignore rules do not rewrite the shared index or commit history.
