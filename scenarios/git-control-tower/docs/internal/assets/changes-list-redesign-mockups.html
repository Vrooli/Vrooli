What the code actually says

Each finding below was read out of the working tree on agi. The verdict chip says whether the fix has to be designed or merely adopted.

F1

Groups sort by label only — Kind is computed, then discardeddesign needed

The resolver already knows each group's target kind. It writes Kind: string(target.Kind) into every contract group, then sorts on sourceRank → order → Label. order is hard-coded 0 for every contract group, so the entire list collapses to one alphabetical run. Scenarios appear to come first only because agent-*, ai-*, algorithm-*, api-* happen to sort early; further down, resources and packages interleave with scenarios exactly as you saw.

The repo contract defines nine kinds — scenario, resource, tool, safeguard, team, package, control-plane, docs, project. That is a ready-made second level; nothing needs to be invented.

api/grouping_groups.go:64-72 kind written · :87-95 sort ignores it
ui/src/components/FileList.tsx:496 kind reaches the UI and is used only to decide whether one button renders
F2

Every group is a bordered card with a 16px guttercheap

Each group renders as mb-4 rounded-lg border bg-slate-950/40 with a two-line header: an uppercase label plus the full path. On mobile that is roughly 70px of vertical space per collapsed group carrying one number.

The second line is the redundant one. scenarios/agent-inbox/ is fully derivable from the kind band plus the group name — so adding hierarchy is what lets the path go, and the density improves rather than degrades.

ui/src/components/FileList.tsx:739 card shell · :757-765 two-line header

"Reveal in file tree" is one call away and not wiredalready built

ProjectTreeView already accepts scrollToFile, expands every ancestor directory, and scrolls the row into view. App.tsx already owns the scrollToFile state and a completion handler. The only missing piece is a menu item that sets view mode to tree and the path in the same tick.

F4

The toolbar buttons are hand-rolled; RCL ships the exact controlalready built

ViewModeCycleButton is a bare <button> at h-11 w-11 with a full circular border and per-mode border colours. IconButton.tsx in this scenario is 21 lines of p-2 rounded-md.

React Component Library IconButton@3.1.2 covers all of it: an xs rung at 32px, four surfaces where ghost needs no border, selected that sets aria-pressed, and morph that animates the glyph swap with no call-site work. Its own release notes describe fixing this control for web-console's view toggle — the same widget, one scenario over.

F5

Three different colours claim the top of the screenalready built

index.html hard-codes theme-color: #0f172a. The app shell paints bg-slate-950 (#020617). The header paints bg-slate-900/95 with backdrop-blur and carries pt-safe, so it also owns the notch strip — at 95% opacity over slate-950, which is a fourth value again. Nothing derives any of these from the others.

RCL's ChromeTheme service exists precisely for this: it resolves one value and writes both channels — the theme-color meta tag Android reads and the StatusBarFill strip iOS black-translucent paints — so they cannot drift. web-console adopted it. git-control-tower did not.

F6

The banner calls sandbox output "approved" — and the run data it hides is already serveddesign needed

You are right that auto-apply is not review. The banner reads "Approved changes ready · apply all" for files a sandbox wrote while you were not looking.

What makes this worth redesigning rather than deleting: the API already returns agentManagerRunId, sandboxOwner, changeType and appliedAt per file, and a second endpoint already groups pending changes by run. The UI throws all of it away and renders one aggregate count. The run view you half-remembered does exist — AIProvenanceTab — but it is buried inside the Review panel with no path to it from a file.

06

Why nothing caught it

You were right that a scenario is supposed to own this. The claim exists, is correctly worded, and is guarded by an assertion that cannot fail for the reason it was written.

git-control-tower ships a mobile regression oracle. Case GCT-MOBILE-002 is titled chrome-declaration-and-render-alignment and its claim reads, verbatim:

"Declared theme/status chrome metadata matches the rendered top safe-area surface."

It declares required_artifacts of screenshot_png and layout_json, and its status is repaired_and_guarded. It is the right claim. It degraded across three hand-offs:

LayerWhat it should assertWhat it actually asserts
The guard
MobileShellContract.test.ts:10		 The declared colour equals the rendered top surface. expect(indexHTML).toContain('name="theme-color"')
— presence of the tag. Green for any value, including a wrong one. It never reads the header's colour at all.
The spec
experience/pages/workspace.json		 A machine-tier claim about chrome colour agreement. Cases 002 and 006 were merged into one claim, gct-mobile-002-006-chrome-pinned, whose statement is purely geometric — "stay inside the viewport… without overlapping". The colour half has no representative in the spec.
The validator
experience-manager		 Flag an oracle case with no corresponding spec claim. Its registry holds four checks — BAS reference integrity, state coverage, attestation freshness, evidence reconcile. The spec parser never reads experience/fixtures/ at all, so the oracle is an unreferenced document. Nothing can notice a case that lost its claim.
The proper fix is the third row. Repairing the guard fixes one colour. Adding a fixture.claim_coverage check to experience-manager — parse experience/fixtures/*.json, require every case id to be named by at least one spec claim, and fail when a case declares screenshot_png evidence that no machine-tier claim consumes — makes the whole class of silent degradation visible, in this scenario and in every other one that ships an oracle. That check is what would have caught this, and it is the one that does not exist.
