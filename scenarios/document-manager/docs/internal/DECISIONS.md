# Decisions — Document Manager

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

| 2026-08-17 | **Retain `unstructured-io` as an optional, measured Docker fallback; remove it from every P0 required chain.** | `docker manifest inspect` of the pinned image returned only `linux/amd64`; a warm `hi_res` scan parse took 6.12 seconds and observed 1.373 GiB resident memory, while the Docker image occupies ~9.81 GB. | 2026-08-17 | **Select `doc-ocr` as the tier-2 local OCR handler and keep `unstructured-io` as its optional alternative.** | The selected native Go resource has a checksum-verified MIT model, `network: none`, conditional amd64/arm64 desktop pairs, CPU-mode readiness, and positioned runs with confidence. | 2026-08-17 | **Select one WASI Rust module executed in-process by Wazero for the first production `doc-parse` path; retain native artifacts as the fallback.** | A 42-fixture corpus covering DOCX, ODT, EPUB, PDF, RTF, CSV, XLSX, PPTX, malformed PDF, scanned PDF, and password-protected DOCX was run through the native shim and the same code compiled to WASI under Wazero. | 2026-08-05 | **Collapse three scenarios into one.** `document-manager` (repo documentation quality), `secure-document-processing` (encryption/compliance shell), and `data-structurer` (schema extraction) are all retired; this scenario reclaims the `document-manager` name. | ~14,400 lines of Go across three scenarios that all predated AI Gateway, carried none of the current template surface, overlapped each other more than they served the actual need, and had no dependents outside prose mentions in two READMEs. | One coherent charter instead of three partial ones. The old trees must be removed, not left to confuse discovery. | If a retired capability turns out to have had a real consumer. |
| 2026-08-06 | **This scenario owns retrieval over its own corpus, and owns no recall over the ledger's.** | Supersedes the 08-05 "no search or index endpoint" decision, which forbade a capability the scenario needs. The real failure mode is not "two vector stores exist" — it is *the same content indexed twice with no defined authority*. Documents and findings are different content classes with different lifecycles, so two stores with exclusive authority over each is correct architecture. Nine scenarios in this repo already declare embedding tables in their own schema (`calendar.event_embeddings`, `task-planner.embedding_metadata`, `text-tools`, `audio-tools`, `vrooli-memory`, …); scenario-owned vectors are an established pattern, not an exception. (An earlier draft of this row said "roughly thirty" — that was the count of scenarios *touching* embeddings anywhere in Go, not the count owning tables. Nine is the load-bearing number.) | A `retrieval` domain exists and is P0. Unification across corpora is `search-hub`'s job, achieved by both registering as providers — never by co-locating stores. The standing obligation is narrower but still real: **never index ledger content here, and never expose recall over another scenario's corpus.** | If `search-hub` federation proves insufficient for cross-corpus queries — in which case the fix is in `search-hub`, not here. |
| 2026-08-06 | **Documents never enter the ledger. The ledger's compaction is wrong for them.** | The ledger folds old entries into summaries so its frontier stays bounded, because its output is injected into every session. Documents have no frontier: page 7 of a 2024 paper is either relevant to a query or not, and that never changes. Storing documents in the ledger would pay the full cost of the compaction forest for a corpus with no use for it, and a PDF page must never reach an agent's ambient session context. | This scenario stores documents, units and their embeddings itself, permanently and without compaction. What may be published to a ledger scope is a *finding* — a small entry citing an anchor — and that is a consumer's decision, not this scenario's. | Never. Reversing it means the ledger is no longer a bounded-attention system. |
| 2026-08-06 | **This scenario and the ledger engine are siblings — neither depends on the other.** | The ledger must stay generic: it accepts text + facet + scope + provenance, where provenance is an opaque URI it never dereferences. It cannot be allowed to learn what a PDF is. This scenario ingests, parses, anchors and retrieves with no ledger present. The coupling belongs to a *consumer* (a research or investigation scenario) that reads sources here and writes findings there. | Ledger handoff moved from P0 to P1 (`DOC-P1-020`, `DOC-P1-023`); `search-hub` provider registration moved from P1 to P0 (`DOC-P0-018`). P0 no longer waits on `vrooli-memory` scope CRUD. The extracted ledger-engine scenario is off this scenario's critical path entirely. | If a consumer needs a coupling neither sibling can express — which would be an argument for a third scenario, not for a dependency edge. |
| 2026-08-06 | **`enrichment` owns embeddings, and their purpose is stated rather than assumed.** | An embedding table with no declared reader is how a second corpus gets built by accident. Two readers exist and both are real: the `retrieval` domain queries units semantically, and `intake` uses near-duplicate detection to catch what content hashing cannot — two copies of the same paper from different sources are not byte-identical. | Embeddings stay in this scenario's SQLite with full role/model/dimension/content-version/retarget metadata. A finding published to a ledger scope is embedded *again* by the ledger, in its own space. That duplication is correct and cheap; do not "optimise" it by passing precomputed vectors across the boundary. | If the ledger ever accepts precomputed vectors — which would require the two embedding spaces to be compatible, and they are not guaranteed to be. |
| 2026-08-06 | **Two anchor kinds, not one: `geometric` and `logical`.** | `DOC-P0-009` promises a v1 anchor still resolves after v2. A single character-range anchor cannot deliver that: a better parser changes whitespace, reading order and table handling, so the same offsets mean different things across versions. Meanwhile parse outputs are `regenerable: true` and prunable, so resolution cannot depend on a prior version's parse output still being on disk. | `geometric` anchors bind to source geometry (page + bbox in the original document's coordinate space) and are durable across every derivation, because the original bytes are `regenerable: false`. They are only available where the tier supplies geometry — PDF and image sources. `logical` anchors bind to a structural path plus offset, cover every format, and require an alignment map computed at re-derivation time. **`DOC-P0-009`'s guarantee applies unconditionally to `geometric` anchors and to `logical` anchors only through a recorded alignment.** Anchor kind is stored per anchor from the first migration. | If a format-independent durable coordinate system is found. Adding a third kind is additive per the anchor-format rule in `DATA.md`. |
| 2026-08-06 | **A collection carries a default privacy class that its documents inherit.** | Privacy class was per-document only. A legal matter or a patient file is confidential wholesale — classifying document by document invites the one mistake that breaks the product's central claim. | `collections.default_privacy_class` is set at creation and inherited on intake. A document may be classified *more* restrictively than its collection but never less. The collection becomes the boundary a user actually reasons about, which matches how the Corpus surface presents it. | If per-document classification alone proves sufficient in practice — unlikely, and the failure is silent, so the default stays. |
| 2026-08-06 | **Every outbound AI Gateway request is constructed at one choke point.** | The fail-closed residency guarantee is a property of the *profile*, not the privacy class: `PROFILE_LOCAL_FIRST` is documented to fall back to a permitted remote provider, so a confidential document sent with the wrong profile routes remote and the gateway is behaving correctly. The guarantee therefore lives entirely in this scenario's class→profile mapping, and delegating "enforcement" upstream misreads where the safety property sits. | `internal/gatewayreq` is the only construction site for a `GatewayRequest`. It applies the mapping and refuses to emit a profile weaker than the document's class. Registered in `SEAMS.md` as load-bearing, with an AST check asserting no other construction site exists — the same pattern `storage-manager` already enforces for the routed database seam. | Never while the residency claim is the product. |
| 2026-08-06 | **`DOC-P0-023` hybrid retrieval is FTS5 for lexical, in-process cosine over SQLite-resident vectors for semantic, fused by reciprocal rank.** | The requirement said "hybrid semantic and lexical" without naming a mechanism, which left a P0 with no implementation path. Three mechanisms were available and the choice is constrained by the deferred-`qdrant` decision: vectors must live in SQLite. | **Lexical:** an FTS5 virtual table over unit text — four scenarios already do this on the same `modernc.org/sqlite` driver (`signal-inbox/internal/retrieval/schema.sql` is the closest precedent, plus `agent-inbox`, `portal`, `knowledge-observatory`). **Semantic:** decode the `float32` blobs and score cosine in-process, following `vrooli-memory/internal/vector`. **Filter before scoring**, never after — collection membership and privacy class narrow the candidate set first, so `DOC-P0-024` is a precondition of the query rather than a post-filter. **Fusion:** reciprocal rank fusion, chosen because it is rank-based and needs no score normalisation across two incomparable scales. **Reranking** via `resource-reranker` is an inference step and therefore goes through the `gatewayreq` choke point under the document's privacy class — it is an escalation, not a default. | When linear scan latency becomes unacceptable, migrate the semantic half to `ai-go/search`'s `VectorStore` (the abstraction `signal-inbox` uses against Qdrant). That is the same trigger already recorded in the `qdrant` deferral row of `INTEGRATIONS.md`, and it changes no ownership rule. |
| 2026-08-06 | **A declarative handler registry is the source of truth for format support; no parser is load-bearing by default.** | The first `anydoc` decision treated a library as the architecture — it named `anydoc` "the tier-1 and tier-2 parse path" and retired `unstructured-io` on that basis. That was wrong twice over: it made a two-day-old dependency structural, and it assumed capability overlap that does not exist. The correct unit of routing is not "format X uses parser Y" but a chain of handlers selected by **capability** (`content`, `geometry`, `tables`, `elements`, `ocr`), because a single format routinely needs more than one — a text-native PDF needs `anydoc` for content and `pdf-inspector` for the geometry `anydoc` discards. | `api/internal/derivation/registry.json` is the source of truth; [`../reference/format-matrix.md`](../reference/format-matrix.md) is its projection, with a test asserting they agree so a format cannot be supported by accident. Formats declare *required* and *desirable* capabilities; the router picks the cheapest chain satisfying the required set within what the sensitivity gate permits. Adding a handler is registry data, never routing logic — if a new handler requires a code change in the router, the router has drifted and that is the defect. Tier becomes a **cost class** (1 = instant local, 2 = heavy local, 3 = metered inference) rather than a sequence. | If capability-based selection proves insufficient to express a real routing need — which would be an argument for a richer capability vocabulary, not for hard-coding a parser. |
| 2026-08-06 | **`unstructured-io` is retained. It is not superseded by `anydoc`; they fail in opposite directions.** | Correcting the same over-claim. Measured against the two libraries' actual surfaces: `anydoc` gives ~4.4 ms, zero setup, no Python or ML weights, 14 document formats, and one normalized model — but **no position metadata at all**, no OCR, no element typing, and no HTML, XML, email or image support. `unstructured-io` gives 24+ formats including all of those, page numbers and coordinates, typed element hierarchy, `text_as_html` tables, and Tesseract OCR in 100+ languages — but needs Docker and takes seconds. Six matrix rows depend on it, including every HTML, email and image row. | Both are declared handlers. `anydoc` wins the common path, which is most documents most of the time and is why the free tier stays fast; `unstructured-io` wins the long tail and **owns position** for non-PDF sources. Its docker-service migration still needs verifying and that risk does not dissolve. Its absence degrades named formats in named ways rather than being invisible. | If `unstructured-io` is abandoned upstream, or if a single handler ever provides both breadth and speed. |
| 2026-08-06 | **Tesseract OCR is tier 2, not tier 3 — so confidential scanned documents have a working local path.** | Tesseract runs inside `unstructured-io` as a resource-owned local runtime. It is not a provider call, costs nothing, and routes nowhere, so classifying it as inference was a category error inherited from treating "OCR" as synonymous with "vision model". | Scanned documents get a **free local** parse path. Tier 3 narrows to what Tesseract genuinely cannot do — handwriting, complex layout, figures. This closes a hole that would otherwise have been permanent: under an all-OCR-is-tier-3 model, a confidential scanned PDF is refused by the sensitivity gate and is **never processable at all**. More of the corpus also stays in the free tier, which strengthens the monetization posture rather than weakening it. | If Tesseract quality proves unusable for a class of documents that matters, in which case tier 3 becomes the desirable handler for that class — a registry change, not an architecture change. |
| 2026-08-06 | **Unsupported is a terminal state on a stored document, never a rejected upload.** | A document that cannot be parsed still has evidentiary value: the fact that it was received, and that a decision was made about it, is part of the custody trail. Rejecting the upload destroys that. Five different conditions also need five different remedies, and a shared "parse failed" message makes a one-command fix indistinguishable from a roadmap item. | Bytes are retained, a custody record is written, and the document surfaces in the Corpus carrying one of `no_handler_for_format`, `handler_unavailable`, `handler_failed`, `blocked_by_policy` or `unsupported_variant`. Each states its own reason and remedy. Partial success is also first-class: a chain that produced content but not geometry is recorded as such, and the receipt names what was skipped. | Never while custody is the product. |
| 2026-08-06 | **Anchor kind is a property of the handler chain that ran, not of the format.** | The format matrix states the *best available* kind, but a PDF parsed without its geometry handler cannot honestly claim a `geometric` anchor. Treating kind as fixed per format would let a degraded parse mint anchors it cannot resolve. | Each unit records the kind its chain could actually prove, and each derivation records the chain and handler versions that produced it. Degradation is visible per unit rather than global. This also makes `DOC-P1-003` mechanical: re-derivation is the query "find every derivation produced by chain A and re-run under chain B" instead of a heuristic. | Never — the alternative is anchors that lie. |
| 2026-08-06 | **`anydoc` supplies content; `pdf-inspector` is called directly for PDF geometry.** | `anydoc` preserves no page numbers, no character offsets and no bounding boxes — its output is Markdown, with an intermediate document model available before serialization. That collides directly with `DOC-P0-008`, which requires geometric anchors where the source has geometry. The library that solves the breadth problem destroys the coordinate system the product's citations depend on. | Two libraries, one nested inside the other, for two different reasons: **`anydoc` for content and normalization across every format**, feeding `logical` and `tabular` anchors from its document model; **`pdf-inspector` called directly as a parallel geometry pass on PDFs**, feeding `geometric` anchors. Do not assume that because `anydoc` embeds `pdf-inspector`, geometry is available through `anydoc` — it is not surfaced. `pdf-inspector`'s per-page classification is also finer-grained than `anydoc`'s binary supported/unsupported verdict, which `DOC-P0-002` wants. | If `anydoc` exposes source geometry in its document model, at which point the second call is redundant for PDFs. |
| 2026-08-06 | **A third anchor kind: `tabular`.** | Adopting `anydoc` makes spreadsheets and delimited text first-class P0 formats, and `page + character range` cannot describe a cell. A character offset into a serialized sheet is meaningless to cite and unstable under any reserialization, including changes that alter nothing semantically. The two-kind model was designed before spreadsheets were in scope. | `tabular` anchors bind to sheet or table identity plus a cell range (`sheet:2!B4:D9`). Because cell coordinates are intrinsic to the source rather than produced by the parser, `tabular` is durable **without** an alignment map — it sits on the `geometric` side of the durability split despite looking structural. **`DOC-P0-009`'s guarantee therefore applies unconditionally to `geometric` and `tabular`, and to `logical` only through a recorded alignment.** Anchor kind remains stored per anchor from the first migration; this is now a three-value enum, which is cheap today and a migration later. `DOC-P0-019`'s resolver dispatches on three kinds. | If a format-independent durable coordinate system is found. Adding a fourth kind stays additive per the anchor-format rule in [`../concepts/DATA.md`](../concepts/DATA.md) — a transcript's time anchor (`DOC-P2-003`) is the likely fourth. |
| 2026-08-05 | **Sensitivity resolves before tier selection, not after.** | A confidential document must never be *eligible* for the remote tier, rather than being blocked from it once selected. | The residency guarantee is structural instead of advisory, so there is no fallback path that can get it wrong. Constrains the pipeline ordering permanently. | Never. Reversing this invalidates the product's central claim. |
| 2026-08-05 | **Re-derivation mints a new version; it never overwrites.** | Parsers and models improve, and a citation minted last year must still resolve. | `derivation_versions` is append-only, storage grows with each re-derivation, and anchor resolution must be version-aware. Accepted cost. | If storage growth becomes untenable — but prune parse outputs (`regenerable: true`) before considering version collapse. |
| 2026-08-05 | **The custody journal is append-only and outlives the document.** | Chain-of-custody evidence that can be edited or deleted is not evidence. | No repository method issues UPDATE or DELETE on `custody_records`. Document deletion writes a tombstone. Retention horizon for the journal itself is still undecided. | When a legal retention limit requires journal expiry — which is a policy decision, not an engineering one. |
| 2026-08-05 | **Security is repositioned from encryption to provable processing locality.** | `secure-document-processing` treated AES-256 and a compliance-framework badge wall as the product. Encryption at rest is table stakes; the defensible claim is a per-document record of where each step executed. | Vault and MinIO are deferred rather than adopted. Marketing must not claim certification we do not hold. The claim depends on AI Gateway route evidence, which creates an upstream dependency on a gap that is not yet closed. | If a buyer requires managed key custody beyond OS-level disk encryption. |
| 2026-08-05 | **Nothing is gated; the paid tier is metered only.** | Canon forbids gating what a self-hoster could run with their own keys, and BYOK must stay valid. | Free tiers must be genuinely good, because they compete with Paperless-ngx rather than with a crippled trial. Revenue depends entirely on real marginal-cost operations. | If a gated feature is ever proposed, treat it as a signal the framing drifted rather than as a pricing question. |
| 2026-08-05 | Keep the template's unused `fileRootPath` seam with a `//nolint:unused` directive rather than deleting it. | `react-vite` v1.6.5 ships this documented-as-mandatory routed-storage seam unreferenced, so the template's own `golangci-lint --fix` post-hook fails on every fresh generation. | Generation completes cleanly here; the seam is preserved for the artifact store, which is its first real caller. The underlying template defect is upstream and unfixed. | Remove the directive when the corpus artifact store calls it. |
| 2026-08-07 | **Federated exposure is per-collection opt-in, because search-hub cannot express caller identity.** | `DOC-P0-018` (federate) and `DOC-P0-024` (filter by caller authorization) are in direct tension: `routing.QueryRequest` carries no principal field, and the provider descriptor's `body_template` interpolates only `{{query}}` and `{{limit}}`. A federated query therefore arrives anonymous, and a per-caller filter has nothing to filter on. `control_token` is not a substitute — it proves provider ownership, not caller identity. | A collection carries a `federated` flag, default off, set deliberately by an operator. On top of it sits a hard ceiling that no flag overrides: **confidential and secret units never federate.** Direct Connect callers are unaffected and still see everything they are authorized for. This is a policy substitute for an identity the contract cannot express, and it is deliberately conservative — the cost is that federation cannot serve the restricted corpus, which is the half the product exists for. | When search-hub's query contract carries a caller principal. Filed as an upstream gap; until then this stands. |
| 2026-08-07 | **The semantic half of retrieval sits behind `ai-go/search`'s `VectorStore` from the first commit, not at migration time.** | `DOC-P0-023` ships an in-process linear scan whose only precedent is `vrooli-memory` at 8,181 vectors. This scenario's premise is document corpora — 10k documents at ~200 units each is ~2M vectors, roughly 250× that. The migration trigger was recorded qualitatively ("when latency becomes unacceptable") with no number attached, which is how a P0 acquires a silent cliff. | The linear scan is an *implementation* of the interface rather than the interface itself, so swapping to Qdrant is configuration rather than surgery. A vector-count and p95 threshold is stated in `PERFORMANCE.md` and is the trigger, not a judgement call. Costs one indirection today. | When the stated threshold is crossed — at which point the swap is already mechanical. |
| 2026-08-07 | **An AST check asserts no ledger client is reachable from indexing or retrieval.** | The "never index ledger content here" obligation is the boundary that already drifted once — the superseded no-search-endpoint row was an over-correction *of this same boundary*. Every other load-bearing rule in this scenario (the `gatewayreq` choke point, the routed file-store seam) is enforced structurally; this one was prose. | Same enforcement pattern as `DOC-P0-026`. Registered in `SEAMS.md`. Cheap, and it makes the rule survive an agent who has not read this file. | Never while sources and findings are separate corpora. |
| 2026-08-07 | **Both tier-1 parsers are packaged as CLI-shaped resources; per-document subprocess cost is accepted for v1.** | `anydoc` and `pdf-inspector` are Rust with Node, Python, browser and CLI bindings — **no Go binding**. The API is Go, so "in-process Rust" is true of the library and false of our call path: a text-native PDF costs two subprocess spawns, and the published ~4.4–4.7 ms median is measured in-process, not across a spawn and a serialization boundary. | Both are packaged as resources and governed through `scenario-dependency-analyzer` before use. The packaging work carries an explicit spawn-cost measurement rather than inheriting the published figure. The first slice is tier-2-only, so this work runs parallel to it and blocks nothing. **`format-matrix.md`'s "In-process Rust via CLI/bindings" wording is wrong and is corrected to name the invocation model.** | If measured spawn cost threatens the free tier's latency claim, promote a long-lived handler process — a resource-shape change, not an architecture change. |
| 2026-08-07 | **`handoff` stays documented but unscaffolded until P1.** | It is the only one of the nine domains with zero P0 requirements. `PROBLEMS.md` already records that P0 is over-scoped for a first milestone; scaffolding proto, schema, repository, service, handler, mocks and tests for a domain nothing in P0 touches adds surface without adding proof. | The domain map, data ownership and flows keep their `handoff` rows so the boundary stays designed. No code is generated for it until `DOC-P1-020` is scheduled. | When ledger handoff is scheduled. |
| 2026-08-07 | **Document generation belongs in this scenario, as a renderer and not an author.** | Generation was unowned across the whole repo: `chart-generator` owns charts, `graph-studio` diagrams, `asset-studio` media, `content-desk` marketing copy, `brand-manager` tokens — and nothing turns a slot-filled brief into a `.pptx`, `.docx`, `.xlsx` or PDF. A search for a render toolchain (pandoc, typst, gotenberg, unioffice, python-pptx, weasyprint, marp) found none anywhere in the tree. Meanwhile this scenario already owns the two assets generation needs: the normalized document model, and a registry that routes by declared capability rather than by format. | A **write spine** is added at P2 (`OT-P2-010`…`OT-P2-027`) as three domains — `templates`, `composition`, `render` — reusing `corpus`, `custody`, `anchors` and `intake` rather than duplicating them. It renders; it never authors. Generation prompts live in skills, exactly as `content-desk` decided when it rejected a `generation` domain, because a domain freezes prompt iteration behind a deploy. Non-text assets stay with their existing owners and arrive as *references in a spec*. | If the spec/authoring surface grows its own designer UI, template-authoring workflow and multi-user editing, it is a different product and should split into a sibling scenario — the same line `DOC-P2-009` already sits behind. |
| 2026-08-07 | **The spec is the authority; rendered bytes are a derivation of it.** | The read spine is: bytes are `regenerable: false` authority → derivations are `regenerable: true` versioned readings → re-derive when parsers improve. Modelling generation as "we also write files" would have created a second, unrelated architecture. Modelling it as the same machine mirrored costs nothing and buys the whole verb set. | **Spec is `regenerable: false`; rendered bytes are `regenerable: true` render versions**, append-only exactly like `derivation_versions`. Re-render-on-template-change and re-derive-on-parser-upgrade become the same verb shape, the same version table, the same diff report, and `DOC-P2-007` document diff works across deck revisions for free. A generated document is content-addressed and ingested back, so it is an ordinary corpus document with no special class. Storage grows per render version; parse and render outputs are both the safe eviction target. | Never while re-rendering must be reproducible. Reversing it makes the artifact the authority, at which point a template switch is a rewrite rather than a re-render. |
| 2026-08-07 | **Renderers declare fidelity, not formats — the write-side twin of the handler registry.** | The read side's load-bearing rule is that handlers declare capabilities (`content`, `geometry`, `tables`, `elements`, `ocr`) and a format declares what it requires, so adding a handler is registry data rather than routing logic. Naming target formats directly on the write side would reintroduce exactly the coupling that rule exists to prevent. | A renderer declares the **fidelity** it can honor — `paged-geometry`, `cell-structure`, `speaker-notes`, `vector-embed`, `styled-text` — and a spec declares the fidelity it requires. `api/internal/render/registry.json` is the source of truth, projected into [`../reference/render-matrix.md`](../reference/render-matrix.md) with a test asserting they agree, mirroring the format matrix. Adding a render target is registry data; if it requires router changes, the router has drifted and that is the defect. | If fidelity-based selection cannot express a real routing need — which argues for a richer fidelity vocabulary, not for hard-coding a renderer. |
| 2026-08-07 | **Authoring persists as three layers: sources, spec, bindings — and `refresh` is a different verb from `render`.** | "Store what the caller provided" is the obvious answer and it is not enough. Template switching, figure refresh and citation each need a different layer, and collapsing them means every template change re-asks for content and every figure update re-authors the document. | **Sources** are re-runnable bindings (a command-center query, a corpus anchor, a chart-generator render id) whose resolutions are snapshotted with timestamps so a rendered document stays reproducible. **Spec** is template-agnostic content and intent. **Bindings** are how this spec resolved against *this* template, and are the only layer discarded on a switch. Two verbs follow and must not be merged: `refresh` re-runs source bindings into a **new spec version**; `render` re-renders a **fixed spec**. Because a spec block may cite a corpus anchor as its source, a generated research report carries citations back to the papers it was built from. | If a fourth layer appears — most likely per-audience variants — decide fold-in versus split at that point rather than overloading `spec`. |
| 2026-08-07 | **A spec block may have no source, and unsourced content is marked rather than forbidden.** | A pitch deck is mostly operator voice and judgement; `docs/narrative/PITCH_DECK.md` explicitly declares slide content operator-authored and refuses to delegate it. A global "every claim must cite" rule would make the flagship use case impossible. A global absence of the rule would make a research report indefensible. | Each block carries `provenance: sourced | authored`. "Every claim cited" becomes a **per-template policy** (`require_sources: true`), so a research-report template enforces it and a deck template does not. Unsourced blocks are always visible as such in the Composer — allowed, never invisible. | If a regulated generation use case needs corpus-wide enforcement, add a collection-level policy above the template one; do not make the template rule global. |
| 2026-08-07 | **Templates are corpus documents; their presentation half references brand tokens and never redefines them.** | Templates need versioning, custody, export, diff and access control — all of which this scenario already provides for documents, and all of which a bespoke registry would reimplement. Separately, a template that hardcodes a hex value or a font name drifts from brand permanently and silently. | A template is stored as a corpus document under a distinguished kind, so it inherits the whole spine and is excluded from `retrieval` by kind rather than by a parallel store. A template declares a **slot contract** (what a document of this type must supply) plus **presentation** that references `brand-manager` tokens; a literal color or font fails validation (`OT-P2-013`). A rebrand therefore re-renders the corpus without editing a single template. | Storing templates as documents is the deliberately clever choice here. If template kinds start needing document fields that make no sense (privacy class, OCR confidence, page geometry), that is the signal to split them into their own store — recorded in `PROBLEMS.md` as a watched risk rather than a settled comfort. |
| 2026-08-07 | **Template switching works only for template-agnostic specs, and the failure is named per element.** | A spec that says "slide 3: two-column, image right" has already chosen a template. A spec that says "slide 3 conveys X, these three points, this chart" has not. Only the second is portable, and the difference is authoring discipline rather than a mechanism anyone can add later. | The rule is stated as a contract: **the spec declares content and intent; the template decides presentation.** Switching to a template that cannot express something the spec requires produces `unrepresentable_element` *per element* (`OT-P2-014`, `OT-P2-016`), never a silent drop, for the same reason the read side has five terminal states instead of one "parse failed". | Never. A silent drop on a template switch is the write-side equivalent of an anchor that lies. |
| 2026-08-07 | **Per-document overrides apply directly; template edits are proposals a human confirms.** | These two operations feel identical in a chat window — "make this heading bigger" — and have wildly different blast radii: one document versus every document using that template. Conflating them is how one person's tweak silently restyles a corpus. | Three distinct verbs with three confirmation levels: **override** (this document only, immediate, reversible by spec version), **fork** (new template, immediate, affects nothing existing), **template edit** (proposal → human confirmation → new template version), mirroring the redaction-review pattern already in this scenario. Overrides are explicit and **enumerable** — "this deck deviates in 4 ways" — and are surfaced at switch time with which of them the target cannot honor, because every override is a bet against future template changes (`OT-P2-015`, `OT-P2-024`). | If proposal friction proves to block real work, lower the confirmation for templates with exactly one consuming document — never for shared ones. |
| 2026-08-07 | **The in-UI agent chat is a client of the public verbs, not a feature with privileged access.** | The requirement is parity: an agent spawned outside this scenario, loading the same skill, must be able to do everything the chat panel can. Stated as prose that decays; stated structurally it holds. | Every chat action is a public proto verb with CLI parity, which `DOC-P0-020` already mandates for every domain verb — so a chat interaction that cannot be expressed as a sequence of public verbs is a **missing verb, not a chat capability**. Asserted by an AST check that the chat surface constructs only generated clients (`OT-P2-021`), the same enforcement pattern as `gatewayreq` and the corpus-authority boundary. Three consequences follow: edit verbs are **spec-level, never byte-level** (editing rendered bytes diverges the artifact from its authority and voids everything downstream); **undo is free**, because spec versions are append-only and revert-to-version *is* undo; and every edit is a **custody event** recording actor, verb, before/after version and whether inference was involved (`OT-P2-022`). There is no `chat` domain. | Never while parity is the requirement. |
| 2026-08-07 | **Chat inherits the sensitivity gate, and the agent is document-scoped by default.** | The chat panel is an inference caller like any other. Left unconsidered it would be the one path that reaches a confidential document without passing the class→profile mapping — precisely the second construction site `DOC-P0-026` exists to forbid. | A chat-driven edit builds its request at the same `internal/gatewayreq` choke point under the document's privacy class and fails closed identically (`OT-P2-023`). This is not overhead: it produces a claim no hosted competitor can make — *you can talk to your privileged documents and nothing leaves the machine.* Separately, the agent is scoped to **one document** by default; a corpus-scoped action such as "restyle every deck in this collection" requires an explicit, separately authorized scope binding rather than inheriting document access (`OT-P2-025`), because blast radius and authorization must move together. | Never for the gate. The scope default may loosen only alongside per-collection access control (`DOC-P1-014`). |
| 2026-08-07 | **The renderer emits its alignment map, so generated documents get durable logical anchors for free.** | `PROBLEMS.md` and the anchor-kinds decision both name logical-anchor durability as the deepest technical risk: `logical` anchors need alignment maps "that no handler chain produces for free". That is true of *parsing*, where the mapping must be recovered. It is false of *rendering*, where the renderer placed every element and already knows the mapping. | A renderer emits its spec-block → output-region mapping as a byproduct of rendering (`OT-P2-017`). Generated documents therefore carry `logical` anchors that are durable **without** a computed alignment, sitting on the durable side of the split alongside `geometric` and `tabular`. This is not a new anchor kind — it is the existing kind with an author-minted stable identity — so no migration and no fourth resolver branch. The hardest unsolved problem on the read side is solved by construction on the write side. | If a renderer cannot emit alignment for some target, that target's generated anchors degrade to ordinary `logical` and say so per unit — the same honesty rule as a PDF parsed without its geometry handler. |
| 2026-08-07 | **A template pins a target family, not a single format; and the write spine is a second milestone with nothing scaffolded.** | One deck template rendering to both `.pptx` and PDF is genuinely useful and materially harder than either alone, so it must be a declared property rather than an accident. Separately, `PROBLEMS.md` already records P0 as "a program, not a first milestone", two parse resources are unpackaged, and `vision.default` does not exist — adding an equally large second spine to the same milestone would guarantee neither ships. | A template declares one or more render targets **and its fidelity for each**; an undeclared target is `no_renderer_for_target` rather than a best-effort attempt. And the entire generation spine is P2: the boundary, domains, data ownership, flows and requirements are all recorded now, and **no proto, schema, repository, service, handler, mocks or tests are generated** until the read spine ships — exactly the treatment `handoff` received on the same date, for the same reason. | Open the spine at launch-sequencing step 8, not before. The round-trip fidelity gate, the anchor reuse and the custody spine all require the read side to exist, so building generation earlier means building it twice. |

| 2026-08-07 | **The anchor URI is specified, and it pins the derivation version it was minted against — always.** | The URI was named in three documents as "provenance" and defined in none, which left the entire contract between this scenario and the ledger to be improvised by whoever implemented first. Reading the actual ledger proto corrected two assumptions: provenance is not one opaque string but `ImportProvenance{runtime, source_locator, content_hash}`, and the dedupe key is `runtime + ":" + source_locator + ":" + content_hash` unique on `(scope, import_key)`. | Grammar, canonical form, resolution outcomes and the field mapping are specified in [`../reference/anchor-uri.md`](../reference/anchor-uri.md), funded by `DOC-P0-028`. The version is **mandatory** rather than optional: for `logical` anchors it is forced, since offsets are version-relative and an unpinned one silently means something different after re-derivation; for `geometric` and `tabular` it costs one integer and makes a citation a claim about a specific *reading*, which stays checkable after a later version disagrees. `content_hash` carries the **finding body**, not the document — the document is already in the URI, and hashing it there would collapse every finding about a document into one entry. | If a consumer needs to cite "the current reading" rather than a fixed one — which is a different verb (resolve-latest), not a different URI. |
| 2026-08-07 | **Canonical form is a correctness requirement, because the ledger's dedupe key is a byte-exact string join.** | Canonicalization reads like tidiness until you notice nothing ever parses `import_key` back apart. Two URIs differing by a trailing zero, a percent-escape case or an attribute order are *different citations* to the ledger. | Ten canonicalization rules, and **equality is byte equality of the canonical form** — no semantic comparison, no read-time normalization, no coordinate tolerance. A minting implementation that emits non-canonical output is a defect even when every URI it produces resolves correctly, because the damage lands downstream in a system with no way to detect it: `DOC-P1-023`'s idempotency stops working and republishing produces duplicates that read as new findings. | Never while the ledger dedupes on string equality. |
| 2026-08-07 | **A URI carries content-addressed and intrinsic values only — no database identifiers, no corpus identity, no content-derived tokens.** | Three separate temptations, one shared failure. A unit id makes the URI a foreign key wearing a citation's clothes, meaningless once exported. A corpus id is exactly the lock-in `DOC-P0-017` forbids, and leaks deployment topology into a compliance artifact. A sheet name or element path leaks *content* into a ledger whose access control may differ from the corpus's — `Q3 Layoffs` as a sheet name is the worked example. | Sheets and structural paths are addressed by **index**, never by name. Geometric coordinates are normalized to the page box with a pinned top-left origin, because raw units are parser-dependent and an anchor that changes meaning with the parser defeats the design. Logical offsets are Unicode scalar offsets over NFC-normalized text. Attributes exist but are **never load-bearing** — resolution uses the path alone, so a URI arriving from outside cannot steer resolution through a crafted attribute. Accepted and documented rather than solved: a content address permits confirmation of possession, and the HMAC mitigation would defeat the portability `DOC-P0-017` requires. | If a regulated buyer requires unlinkability across corpora, at which point per-corpus HMAC becomes a deployment profile — not a change to the default scheme. |
| 2026-08-07 | **A published anchor URI is never rewritten; degradation truncates at a marked stable prefix.** | `DOC-P1-020` gives `handoff` "re-derivation propagation", whose tempting reading is to update old entries to point at the new version. That is wrong twice: the journal is append-only, and the citation was a true statement about what that version said. Separately, the documented behavior that "an unaligned anchor into slide 7 still resolves *to slide 7*" had no mechanism. | Propagation appends a **new** entry noting the newer reading and leaves the old one standing. And a `logical` anchor marks the end of its intrinsically stable prefix with `!` (`7!2/1@120-260`), so degradation is mechanical: truncate at the marker and return `resolved-degraded`; with no marker, return `unresolved`. Six resolution outcomes, and no seventh — in particular no best guess, because a plausible wrong region is the failure the whole anchor design exists to prevent. | Never. Rewriting a published citation makes the ledger's history unfaithful. |

Absorbed rather than discarded. |
| 2026-08-06 | **This scenario exposes no search or index endpoint**, because a second vector store would compete with the ledger and break unified cross-scope recall. | This scenario owns retrieval over its own corpus; unification is `search-hub`'s job. | The fear was real but misdiagnosed. Duplication is *the same content indexed twice with no defined authority*, not *two stores existing*. Sources and findings are different content classes with different lifecycles and different retention rules; each needs a store that fits it. The original wording forbade the `retrieval` domain, which is now P0. |
| 2026-08-06 | **`anydoc` is the tier-1 and tier-2 parse path, replacing both planned resources.** `unstructured-io` no longer needs verification because it is no longer relied on. | A declarative handler registry selects chains by capability; `anydoc` and `unstructured-io` are both retained as handlers. | Held for a few hours on 2026-08-06. It also mis-tiered OCR as inference, which would have left confidential scanned documents with no processable path at all. Recorded rather than deleted because the reasoning error — mistaking a good library for the architecture — is the one most likely to recur. |

What belongs in a ledger is a small entry citing an anchor. This also removed P0's dependency on ledger scope CRUD, which does not exist yet. |
