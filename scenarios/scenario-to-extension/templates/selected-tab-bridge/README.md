# Selected-tab bridge prototype

This Manifest V3 prototype shares exactly the active tab after a person clicks the extension action and enters a one-time Vrooli pairing code. It does not attach to Chrome's user-data directory, read cookies, inspect other tabs, export history, or execute arbitrary JavaScript from the broker. The extension metadata inventory is read-only and reports declared extension permissions and host permissions.

The extension uses an explicitly selected tab grant plus `activeTab`; it scopes every observe/action/navigation message against the permission profile returned by the bridge. The supported prototype actions are `navigate`, `click` by selector, and `type` into a form control. DOM-injected events are not trusted input and some sites will reject them. There is no stealth, fingerprint spoofing, or claim that bot-detection challenges are bypassed.

## Pair and wire contract

The BAS agentaccess owner provides `POST /api/v1/browser/bridge/pair` on the configured Vrooli origin and `GET /api/v1/browser/bridge/socket` for the one-time ticket. The extension sends a one-time pairing code and the currently selected tab's id/url/title only after the person clicks the extension action. The broker consumes the code, binds caller+tab+session+lease+permission profile, asks the existing Agent Manager consent owner for a tab receipt, verifies it through the permission owner, and returns only a same-origin WebSocket URL, session id, opaque lease receipt, expiry and a minimal effective permission profile. BAS also revokes that owner receipt on extension revoke or trusted session close. Pairing fails closed unless issue, verification and revocation owner adapters are configured. The pair route requires the exact configured extension origin; the socket route accepts its ticket only under the configured origin and protocol. The browser receives no raw node URL or credential. Only after the profile grants extension access does the extension send its installed extension metadata over the authenticated socket.

WebSocket subprotocol: `vrooli-browser-bridge-v1`; the first frame must present the opaque lease receipt and the broker must answer `lease_accepted` before the extension reports inventory or accepts commands. The extension attempts bounded reconnects with the same unexpired receipt while its worker and browser remain alive; restarting Chrome requires a fresh user pairing. Supported messages: `observe`, `act` (`navigate`, `click`, `type`), `extension_inventory` (only when granted), `heartbeat`, `handoff`, `revoke`, and completion/denial receipts. A handoff switches the extension to observe-only; the agent cannot regain control through the same receipt. Reacquiring control requires a new open/attachment grant and socket. The broker authorizes every operation and revokes on receipt expiry, explicit revocation, scope violation, or close. Temporary socket disconnects may reconnect within the ticket expiry; reconnect after expiry requires a fresh pairing. Concurrent operations on one tab must be serialized. The extension refuses a second simultaneous share and disconnects if its selected tab leaves the granted URL scope.

## Permission disclosures

`activeTab` grants the chosen tab only after an explicit extension click. The existing `management.getAll()` owner returns Chrome's active API and explicit host permission sets; the popup labels those as Chrome-reported active permissions. The bridge sends them only for IDs explicitly allowlisted by the admitted profile, marks their source as `chrome.management.getAll`, and does not include the bridge extension itself. It never reads another extension's local storage or internal pages. These values are the browser-reported active permission set at inventory time; they do not claim a digest for third-party extensions or every transient tab-specific access state. The bridge host permission is requested at runtime for the entered origin. For a remote host, the extension must be built with an explicit optional origin and the operator must authorize that host. A `debugger` permission is deliberately not requested.

The managed Playwright path uses Chromium `Extensions.getExtensions`, which reports extension identity/state/path but no effective permission set. BAS therefore returns `permission_evidence: {status: "unavailable", source: "chromium.Extensions.getExtensions", scope: "unavailable", per_tab_site_access: "not_measured"}` and keeps digest-verified manifest declarations in the separate `declared_permissions` fields. The selected-tab bridge returns `permission_evidence: {status: "effective", source: "chrome.management.getAll", scope: "grant_set_only", per_tab_site_access: "not_measured"}` alongside `effective_permissions` and `effective_host_permissions`. This describes only the extension's granted permission set. In particular, an `activeTab` permission or matching host pattern does not prove that the extension currently has access to the selected page. BAS continues to enforce the session URL profile independently. The browser API is the existing owner; no additional extension privilege or permission prompt is introduced by BAS.

Agent Manager's existing browser-permission owner now issues and verifies the short-lived selected-tab receipt after the bridge consumes its one-time pairing code. The receipt binds the run grant, profile, BAS session and lease, selected tab, allowed origin and pairing nonce; the run principal cannot call these service-only routes directly. BAS holds the opaque receipt only for the active session and fails closed if the dedicated service credential or Agent Manager owner is unavailable. Agent Manager restart drops outstanding receipts, so an attached lease must pair again.

The bridge template is still not installed in a user browser; extension loading and tab selection require a person. Dedicated service-credential provisioning, live backend qualification receipt, Web Console frame stream receipt, real reconnect/revocation and real-tab qualification remain unverified.
