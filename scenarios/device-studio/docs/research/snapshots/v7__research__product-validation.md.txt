## Product shape recommendation

Use the same saved shot for UI, CLI and agent invocation. A shot is a versioned declarative request, not a collection of browser state. It binds sources, device/plate instances, presentation profiles, placement, device/camera motion, renderer strategy and delivery settings. Rendering resolves a frozen dependency set and records an attempt. Editing creates a new recipe revision; old jobs remain replayable against their pinned inputs.

The normal UI is a shot builder: choose/create/import assets, attach captures, configure the presentation, select compatible scene and motion, preview, render, compare and export. An advanced workspace exposes screen calibration, transform/joint tracks, material/light controls and reference review. The initial product should not require a general mesh editor, arbitrary shader graph or non-linear film editor. Import/export of native files and AI-assisted edits can serve advanced modeling without rebuilding Blender in the browser.

Separate four concepts in every interface: a rough interactive preview; a final-render frame; a motion sample; and a released shot. The first must not silently stand in for the other three. The existing operator artifact viewer is a delivery surface, not the proposed editor. Direct PNG/MP4/model download remains required regardless of embedded preview success.

AI-assisted creation is a target capability, not a footnote. Its initial workflow should accept a desired device/scene, references and constraints, search/import or build candidates, render comparisons, revise a bounded set of parameters, and retain a resumable candidate. It should be useful with review between candidates before claiming autonomous qualification. Human-review defaults, catalog breadth and cost policy are operator choices; the data model and execution safety are engineering choices.

## Validation structure

Validate behavior at the boundary that owns it; do not use one generic green suite as a visual verdict.

| Boundary | Evidence required |
|---|---|
| Definition and compatibility | Positive and negative fixtures for units, part hierarchy, joint limits, display masks, screen handoff, mounts, host openings, slot bounds and scene placement. Reject unsupported requests rather than silently changing the shot. |
| Media composition | Known patterns at all display edges and cutouts; contain/crop behavior; no leakage into reserved OS regions; per-surface clocks; frame order/timestamps; source hashes; alpha/premultiplication and color tests. |
| Physical motion | Tested articulation endpoints and intermediate poses, swept clearances, contact, stable mapped screens and explicit occlusion. A rotation of a flattened photograph cannot satisfy a 3D motion requirement. |
| Appearance | Final-profile still and continuous short clip against a named reference board. Inspect silhouette, small anatomy, materials, lighting, shadows, reflections, projected text readability and temporal stability. Reviewer verdict remains distinct from geometry/codec checks. |
| Jobs | Idempotent submission, durable states, restart recovery, cancellation of owned children, timeout/resource limit handling, partial-output visibility, cache invalidation and retained failed attempts. |
| Import and AI execution | Dependency closure, external path policy, no automatic imported scripts, bounded isolated execution, credential exclusion, immutable candidates and auditable edits. Actual isolation must be demonstrated. |
| UI and agent surfaces | Same recipe/result through UI and CLI; accessible controls and numeric alternatives to dragging; mobile review; progress/error/empty states; save/reopen and reproducible export; discoverable tools. |
| Consumer handoff | A real launch-video workflow consumes the produced shot and retains media timing, dimensions, provenance and attribution. Do not require copying transient local paths into another scenario. |

Use focused unit/contract tests during implementation, representative renderer integration runs for changed geometry/material behavior, and scoped `vrooli scenario test device-studio --phases ...` according to the actual interfaces affected. The available phases and server-owned wait command must come from Test Genie at execution time (`docs/TESTING.md:1`, `:68`). Final scenario acceptance includes all agreed product journeys and quality gates; early photographic success alone cannot close a promised 3D-motion scope.

Reproducibility has levels. Replay of pinned 2D inputs can target deterministic composites in a pinned environment. Path-traced renders across GPU/CPU or version changes need declared numeric/visual tolerance, not a false universal byte-identity promise. Image generation preserves its actual returned bytes and invocation metadata; a prompt alone is not a reproducible asset.

## Color and screen presentation

Keep source color metadata and the output encoding explicit. Blender's current manual describes scene-linear compositing, image input conversion and view transforms; AgX deliberately changes highly exposed colors. This makes a physically lit emissive display and a color-faithful app demonstration different rendering choices, even when both use genuine captures. Recommended default: preserve app readability/color through a separately controlled display pass, with an optional physically integrated screen treatment whose reflections and tone mapping are reviewed. This is an engineering proposal, not yet a tested moving-device compositor. See [Blender color management](https://docs.blender.org/manual/en/4.5/render/color_management.html). The installed 4.0 feature set must be inspected rather than assuming all features of the 4.5 manual exist.

Video range/transfer conversion must be explicit and distinct from simply labeling the file. Variable-rate input timing, final frame rate, pixel aspect and dimension padding need dedicated fixtures. See [FFmpeg colorspace filter](https://ffmpeg.org/ffmpeg-filters.html#colorspace). Defaults can be SDR sRGB stills and BT.709 video; HDR and wide gamut should be a separately qualified target if requested.

Blender's documentation states that embedded Python can execute without general restrictions and distinguishes automatic from manual execution. Disable imported automatic scripts and restrict generated/imported execution through a separate isolation boundary; the flag alone is not a sandbox. See [Blender scripting security](https://docs.blender.org/manual/id/dev/advanced/scripting/security.html). Version-specific 4.0 manual retrieval failed through the web tool; these general findings are cross-checked against the current manual and must not be read as a runtime isolation test.
