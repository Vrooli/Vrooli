# Device Studio: desktop packaging and render workers

Investigation dated 2026-10-19. Applies the accepted [v8 decisions](decisions.json), [brief](brief.md) and [v7 rendering assessment](../../v7/research/rendering.md). The current Vrooli host is the first runtime qualification target. Windows, macOS and Linux architecture and downloadable personal desktop use are required from the start; this does not mean all native releases are already certified.

**Recommendation:** use one portable shot/job/artifact contract, a browser editing stage, and an independently owned local render worker. Package a private desktop runtime through scenario-to-desktop rather than requiring an end user to install the monorepo or fleet. The photographic compositor is the demonstrated first appearance workflow; native Blender supplies genuine geometry/motion after its toolchain and look are qualified. A desktop can optionally connect to a host worker, but must not silently require one for its advertised local features.

Evidence labels: **code-verified** means the cited code implements the stated shape; **runtime-observed** means a retained bounded command returned the result; **documented** means a source claims it; **proposed** means recommended work, not an implemented capability. No builds, renders, GPU kernels, installs, configuration changes, shared lifecycle operations, credentials or paid calls were performed. Only read-only metadata/device enumeration was executed.

## 3. Proposed minimal personal bundle

This is a concrete target architecture, **not a claim that a Device Studio bundle exists**.

| Component | Local package role | Optional remote dependency |
|---|---|---|
| Electron shell and static UI | Project/shot builder, imports/exports, review, native file selection and progress; no Vite development server | Browser access to an explicitly selected host can use the same API contract |
| Device Studio Go API plus worker entry point | Domain-owned SQLite state, content-addressed project artifacts, deterministic shot compilation, durable job/cancellation/recovery and local API | A remote worker is a separate authenticated target with explicit transfer and cost/privacy policy |
| Deterministic raster/composition capability | Photographic-plane warp/masks/contain, presentation profiles and frame evaluation | Reuse/expose Image Tools' supported primitives; a small local deterministic profile or owner-shared library must be deliberately packaged and qualified. Do not require every AI backend just to transform pixels. This packaging profile is proposed, not currently verified. |
| Qualified FFmpeg **and FFprobe** | Decode/source inspection, video encoding, color/range conversion and final verification | None for advertised local export |
| Optional renderer pack | A pinned Blender distribution, its Python/runtime libraries, scripts, import/export extensions and required kernels; engine-specific native profile | A user may choose an explicitly configured host renderer instead; no automatic paid or remote fallback |
| Curated device/scene/profile content | Small initial library with rights, hashes, units, screen bindings, masks/rigs and strategy eligibility | Additional free model/library downloads are explicit cached content imports; no account-gated asset is silently assumed |
| Account/credits, providers, agent creation and shared publication | Adapters with explicit initiating disclosure; project controls remain local | Existing account/credit/AI/provider/Asset Studio owners, addressed by the sibling research; no copied credentials or full fleet in the bundle |

Core local project reopening and an eligible imported-plate render should not spawn BAS, Agent Manager, Ollama, PostgreSQL, Redis, a Docker daemon or a second app server fleet. BAS remains an optional capture provider; importing existing screenshots/video is a complete alternative. Model/scene AI creation remains first-class but optional execution, with the accepted budget/review and clear AI/agent-launch disclosure before initiation. This follows the accepted decisions rather than suggesting a subscription credential or paid budget exists.

Tool acquisition should follow the **tool/dependency and desktop artifact owners**, not a Device Studio shell script that invokes package managers or downloads executables on demand. The full Vrooli host can use the governed host-tool/SDA path. A standalone product needs the same verified artifact/provisioning contract through a small packaged helper or a signed renderer-pack installer; it must not require a development checkout or installation of all Vrooli services. That slim standalone provisioning surface and Blender owner manifest still require implementation.

In the inspected tool tree, no `internal/tools/blender/tool.json` exists. Existing FFmpeg and Python declarations say `host-required` and list all three OS statuses as unqualified; the FFmpeg declaration names `ffmpeg`, not a qualification of the complete FFmpeg/FFprobe pair. [ffmpeg/tool.json:9](/home/matthalloran8/Vrooli/internal/tools/ffmpeg/tool.json:9), [ffmpeg/tool.json:21](/home/matthalloran8/Vrooli/internal/tools/ffmpeg/tool.json:21), [python/tool.json:23](/home/matthalloran8/Vrooli/internal/tools/python/tool.json:23). An installed binary on this host is not an eligible distributable renderer package. Govern the declaration/artifact/profile work before marking a self-contained bundle ready.

For 3D scripts prefer Blender's pinned included Python rather than ambient user Python. The experiments needed a process-local clean environment; those Linux paths must not be copied into Windows/macOS launch recipes. A renderer package resolves its own Python/module/script paths. Similarly, photographic compositing cannot silently depend on whichever `python3`, Pillow, OpenCV, fonts or system codecs happen to be installed.

## 4. GPU discovery: current host diagnosis

**Runtime-observed in a 1.123-second owned scope:** Blender 4.0.2 has compiled CUDA/HIP flags, but OptiX/Metal/oneAPI flags are false. CPU, CUDA and OptiX enumeration return only the Ryzen CPU. In the **same Blender process**, loading `libcuda.so.1`, `cuInit(0)` and `cuDeviceGetCount` succeed; one RTX 4070 Ti SUPER is visible. CUDA/NVIDIA visibility and loader override variables were unset. No context was created and no kernel/render/allocation benchmark was requested. [Probe source](desktop-rendering-evidence/probe_gpu.py), [result](desktop-rendering-evidence/gpu-probe.json), [owned receipt](desktop-rendering-evidence/gpu-run/receipt.json).

The debug log identifies the missing boundary: CUEW initialization succeeds, then Blender reports **“Neither precompiled kernels nor CUDA compiler was found”** and disables CUDA. [Exact log](desktop-rendering-evidence/gpu-run/output.log). Upstream Blender **v4.0.2** source has precisely this condition: after loading the CUDA wrapper, it requires either packaged kernels or a compiler before returning a usable CUDA backend. [Official source, device_cuda_init](https://github.com/blender/blender/blob/v4.0.2/intern/cycles/device/cuda/device.cpp#L17).

A second 0.319-second owned metadata probe identifies Ubuntu's `blender`/`blender-data` **4.0.2+dfsg-1ubuntu8**, finds no `nvcc` on PATH and no `.cubin`/`.ptx`/`.fatbin` under the inspected `/usr/share/blender` tree. It retains the executable hash, driver name/version/VRAM and FFmpeg build configuration. This corroborates the emitted packaging diagnosis; it is not a claim that every path on the machine was searched. [Toolchain result](desktop-rendering-evidence/toolchain-probe.json), [receipt](desktop-rendering-evidence/toolchain-run/receipt.json).

**Conclusion:** the observed NVIDIA driver/device exposure is functional. This installed Blender's CUDA kernel/compiler packaging gate suppresses its Cycles GPU enumeration; OptiX is also compiled out. Do not describe this as “no GPU,” a missing NVIDIA driver, or a shared-GPU permission failure. Do not install a CUDA toolkit merely because it could satisfy one branch. First qualify an owner-managed Blender distribution that includes the intended backend/kernel payload. Nothing was changed here, and no GPU throughput or available capacity is established.

## 5. Cross-platform renderer policy

The renderer contract must separate **physical hardware detected → backend compiled → runtime enumerated → capacity admitted → representative render qualified**. Host inventory/System Monitor can supply hardware/utilization observations, but only the actual worker process can establish its available Cycles devices. Browser WebGL and Cycles capabilities are also separate.

| Target | Backend candidates to probe, not promises | CPU/packaging behavior | Required native evidence |
|---|---|---|---|
| Linux x64 | CUDA/OptiX for eligible NVIDIA; HIP for eligible AMD; oneAPI where supported by the selected distribution | Pinned distribution with libraries/kernels, actual driver compatibility, headless engine initialization; CPU remains explicit fallback | This host's renderer package, approved-look frame, short phone/lid motion sample, media decode/color, cancellation and descendant cleanup |
| Windows x64 | CUDA/OptiX/HIP/oneAPI according to exact GPU, driver and Blender build | `blender.exe`, FFmpeg/FFprobe `.exe`, DLL closure and argv-safe paths; no bash or `/usr/bin` assumptions | Installed signed package, clean-user launch, per-device probe/render, worker termination, Windows path/Unicode tests and update/relaunch |
| macOS Apple Silicon | Metal when supported by the exact OS/device/build | Native arm64 package and included libraries, signed helper executables, CPU fallback if the chosen scene/profile qualifies | Notarized app/renderer, Gatekeeper first launch, Metal probe/render, app permissions, shutdown and upgrade |
| macOS Intel / Linux arm64 / Windows arm64 | Separate supported-version/artifact decisions; no architecture inferred from an OS label | Preserve capability refusal or explicitly qualified alternate renderer/version; do not reuse an x64 manifest entry | Target-native evidence for each architecture actually offered |

The official manual describes CUDA/OptiX, HIP, oneAPI and Metal as distinct OS/device-dependent routes. Treat it as backend-family guidance, not qualification of the Ubuntu binary or an arbitrary future bundle. [Blender GPU rendering manual](https://docs.blender.org/manual/en/4.1/render/cycles/gpu_rendering.html). Current Blender release downloads also vary by OS/architecture; select/pin a supported release with its own compatibility matrix rather than freezing every desktop to this old experiment build. [Official Blender releases](https://www.blender.org/releases/5-2/). No download or version migration was performed; retained 4.0.2 scenes/receipts remain immutable.

**Proposed selection:** `auto` means select only a render-qualified local profile meeting the shot's requirements and admitted capacity. A specifically requested unavailable GPU returns an actionable refusal or an explicit offer of CPU fallback. CPU fallback preserves scene/profile semantics where supported; it does not silently reduce quality, reset timing, change material features or use cloud. Record selected backend/device, renderer/driver/build hashes, samples/color settings and fallback reason. A qualified GPU failure can offer a checkpointed CPU retry, with new receipt and estimate, rather than silently call the failed attempt successful. Same seed across CPU/GPU is not a guarantee of byte-identical pixels.

No latency promise follows from GPU inventory. The v7 CPU timings remain constrained still-render observations; native 1080p/24–30fps rotation/lid movies and the accepted photographic-quality 3D look still require their own samples. Denoiser support must be probed separately; a CUDA-capable build does not imply the requested denoiser exists or preserves UI text over time.

## 6. Portable assets, jobs and process ownership

**Proposed persistent representation:** a saved shot contains logical artifact IDs/digests, relative package dependencies, units/axes, exact renderer profile, source frame clock, presentation profile, physical or photographic display mapping, and tracks. Resolve host paths only at the worker boundary. Put projects/output/native packages in `data`, job checkpoints in `state`, previews/decoded frames in bounded `cache`, and logs in `logs`; retain their domain-owned schemas/repositories. Keep imported user source references distinct from a deliberately copied immutable project snapshot. Do not put mutable SQLite/media/caches beside the executable or within a signed `.app`/ASAR tree.

Packed `.blend` files are valuable but not automatically self-contained: inspect external images, linked libraries, fonts, scripts, color configuration, video and importer/extension dependencies. Native files, GLBs, photographic plates and portable screen rasters have different supported behavior. Asset license/attribution and redistribution permission travel with the package; user output rights are not inferred from Blender's software license.

**Worker responsibilities, proposed:** a durable job survives UI disconnect, evaluates an immutable source clock, writes outputs atomically, binds progress to attempts, and retains failure/cancellation/cleanup receipts. Resume deterministic frame batches from verified artifacts; do not replay an external paid generation after an uncertain acknowledgement. A desktop update or app close drains/checkpoints/cancels its own work according to a declared policy. A remote worker uses the same job/asset semantics with authenticated upload/download, not the host's absolute file paths or an unauthenticated localhost endpoint.

The desktop supervisor owns service lifetime, not the full render-job domain. Use platform-go's operation-owned containment for render children with explicit wall/memory/task limits and a bounded working set. Its source describes Linux cgroup evidence, Windows Job Objects and macOS per-process rlimit/process-group semantics; Windows/macOS have narrower fixture/compile evidence. [containment.go:16](/home/matthalloran8/Vrooli/packages/platform-go/containment.go:16), [containment_windows.go:15](/home/matthalloran8/Vrooli/packages/platform-go/containment_windows.go:15), [containment_darwin.go:16](/home/matthalloran8/Vrooli/packages/platform-go/containment_darwin.go:16). macOS limits are not aggregate cgroup equivalents, and its shim requires the host helper to route the `rlimit-exec` subcommand. Do not copy Linux systemd arguments into other OS adapters.

Generated scene Python remains untrusted executable input. Disabling Blender autoexec, using a clean environment and resource ceilings are useful but do not establish full filesystem/network isolation. The packaging/worker owner must implement and validate that boundary separately. The scratch experiment runner is retained evidence, not a standing cross-platform service.

**Recommendation:** use the existing deployment/release owners for artifact channels, promotion and download/signature metadata. This is a redistribution inventory requirement, not a blanket legal conclusion about the surrounding application or codec patents. No final commercial distribution/legal clearance is claimed.

## 8. Acceptance matrix and remaining evidence

Architectural readiness means these contracts can represent the required OSes and degradation. Runtime certification needs immutable target evidence:

| Gate | Evidence required before a support claim |
|---|---|
| Bundle closure | Exact app/tool/content manifests and hashes; no repo paths, ambient Python or implicit fleet dependencies; all required binaries/libraries/extensions/licenses present |
| Clean installation | Real target user without a checkout; download verification, installer/uninstaller, spaces/Unicode/long paths, permissions and disk-full/partial-download recovery |
| Local core | Open/save/reopen/import/project snapshot, private offline imported-plate composition, high-resolution PNG and selected 1080p landscape/portrait SDR video, full decode and source-fit checks |
| Native renderer | Actual worker package enumeration, one approved final-look frame and temporal sample, CPU fallback, missing driver/backend/denoiser behavior, legitimate capacity admission, no UI-blocking full render |
| Job/process lifetime | UI disconnect, app close, cancel, process crash, worker restart and OS reboot leave truthful durable jobs, no orphan descendants, no output falsely marked complete |
| Updates/trust | Signed target package/helpers, macOS notarization/Gatekeeper where required, verified predecessor→successor update, project retention and health/recovery receipt; no active-job renderer replacement |
| Optional remote/AI | Explicit connection and initiating disclosure, privacy opt-in, authentication/credit availability, budget policy, source transfer, unavailable/reconnect and no automatic paid fallback |
| Native platform certification | Separate Linux x64, Windows x64 and macOS arm64 cells first; any additional architecture gets its own artifact and native evidence. Build/fixture tests stay distinct from target runtime results. |

The existing desktop validation contract already models one immutable artifact/target/BAS journey/environment cell and explicit unavailable/refused/not-run outcomes. Reuse that structure for the user journey; add renderer-specific evidence rather than replace it with a successful CLI smoke. [OVERVIEW.md:79](/home/matthalloran8/Vrooli/scenarios/scenario-to-desktop/docs/OVERVIEW.md:79). Linux live-desktop/Xvfb evidence does not certify native Windows/macOS installers, updates, helper signing or GPU backends.

**Changed understanding:** the physical-NVIDIA/Cycles disagreement now has a specific kernel/compiler packaging explanation. Cross-platform design can use existing portable storage/bundle/lifecycle seams without bundling a development checkout, but standalone renderer/tool acquisition still needs a governed implementation.

**Verified in this pass:** production source boundaries and references; native-adapter/typed-degradation patterns; concrete private bundle paths/environment/assets/process/update/signing code; Ubuntu Blender/FFmpeg metadata; same-process CUDA driver success and exact Cycles gate; two successful terminal owned read-only receipts. **Remaining/unverified:** a provisioned supported renderer package, its GPU render/profile/performance qualification, Device Studio itself, a minimal deterministic Image Tools bundle/profile, production worker isolation, target-native Windows/macOS application/tool-chain validation, release signatures/credentials, artifact download/update/install results and complete redistribution review.
