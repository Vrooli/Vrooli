# Device Studio rendering and animation research

Investigation, 2026-10-19. This report recommends a rendering strategy. It does not implement a scenario or certify the existing assets for production. The [research brief](brief.md) and [device-domain design](../../v2/device-domain.md) govern the scope. Reproduction inputs, source hashes, host observations and retained timings are in [rendering/evidence.json](rendering/evidence.json).

## Recommendation

Use a **browser proxy for shot editing**, **Blender for controlled 3D output**, and the **photographic plate compositor for eligible stationary shots**. Keep one backend-neutral device/part/joint/display/content/timeline definition. Compile that definition into each renderer; do not make a `.blend` or GLB file the public domain contract.

The photographic path is the best demonstrated route to the operator's selected appearance. A generated plate can contain convincing device and environment photography with authentic screen pixels inserted afterward. It supports a changing screen and editorial crop, but its device is approximate. The controlled 3D path is needed for exact geometry, device motion, lid movement and true camera parallax. Its current scene appearance has **not** met the operator's benchmark. Preserve that gate rather than describing v5 as a proxy that only needed more samples. The [v6 parent review](../../v6/parent-review.json:3) explicitly records the earlier deficiency and the distinction between technical and operator acceptance.

For 3D, retain a packed native scene and deterministic recipe for authoritative output. Deliver a separately qualified GLB for portable inspection where possible. Render a final-look still and a short temporal sample from the actual output engine before accepting a longer clip. GPU rendering may become an optional execution profile after qualification; no GPU performance or allocation is established by this investigation.

**Controlled motion remains required for the agreed delivery.** The photographic workflow can be an earlier useful milestone. It does not complete the requested phone rotation and laptop lid closure. Current static asset qualification identifies the repair and acceptance frontier; it does not justify omitting those motions or calling the overall goal finished.

### Why the current browser stage is not the animation backend

The current code is deliberately a bounded file preview. It removes `animations` while parsing, rejects skins and morph targets, and admits a limited extension set. Its `rotate` option is an OrbitControls camera behavior, not lid or device-joint playback. See [prepareModel.ts:72](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/prepareModel.ts:72), [prepareModel.ts:108](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/prepareModel.ts:108), [prepareModel.ts:146](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/prepareModel.ts:146) and [modelStage.ts:88](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/modelStage.ts:88). These are source observations, supported by earlier static viewer receipts; this report did not claim a new browser motion runtime test.

The stage also normalizes the entire scene to a bounding sphere, supplies its own RoomEnvironment and lights, and uses ACES filmic tone mapping at exposure 1.1. That is useful inspection lighting, but it replaces the native scene's intended look. A large exported wall can make a device tiny, and normalization can expose small screen-layer depth separations. See [modelStage.ts:46](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/modelStage.ts:46), [modelStage.ts:70](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/modelStage.ts:70) and [modelStage.ts:75](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/modelStage.ts:75).

Reuse its admission principles, resource disposal, camera fitting and actual renderer tests. Device Studio needs a separate shot stage that evaluates the canonical tracks, uses a declared camera/environment profile and seeks screen media deterministically. Do not broaden a generic file preview merely to make an animation demonstration look supported.

The current target budgets are 20 MiB, 600,000 vertices and 200,000 triangles; image admission limits each axis to 4096, each image to 8 Mi pixels and aggregate image/texture allocation to 16 Mi pixels, with 32 texture records and 256 draws. These are this viewer's limits, not glTF's or proposed universal Device Studio limits. See [modelData.ts:1](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/modelData.ts:1) and [prepareModel.ts:175](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/prepareModel.ts:175). Native render packages may require a higher texture budget and a distinct admission profile.

The successful run took 1.871 seconds; it did no rendering or source mutation. The laptop's `Object_10`, `Object_20` and `Object_22` each have raw topology components across the low base and raised display envelope. The probe retains their bounds and component data. These are material-group objects, not clean base/lid mechanical parts. Raw disconnected components are also split by imported normals/UV seams; automatic “separate loose parts” is not a qualified mechanical segmentation. The height heuristic additionally identifies the screen itself near the hinge; it is a diagnostic, not a hinge classifier. The prior normalization explicitly says closed-state validation is unavailable because the source is a static open assembly with mixed joined parts. See [studio.py:53](../../v3/imported-laptop/studio.py:53) and [normalization.json](../../v3/imported-laptop/normalization.json).

For the slab phone, parent every hardware and display component under one declared instance frame; test transformed geometry and screen orientation. For the laptop, first assign every triangle/component to base, lid or fixed hinge detail; define a measured or explicitly estimated pivot/axis and permitted angle range; retain the original open pose as a regression; then inspect intermediate and closed states for seams, collision and envelope. The published closed dimensions are separate evidence from the width-normalized open envelope. Missing armatures alone would not block a rigid hinge—the missing qualified part assignment and pivot do.

No acquired foldable, flexible display, watch strap or multi-joint asset is motion-qualified here. Their catalog entries and design graph are requirements coverage, not animation proof. Rigid part tracks can fit core glTF animation, but flexible surfaces need a separately qualified deformation representation and portable target. Core glTF stores node transform/morph tracks and image resources; it does not establish media playback, UI reflow, mechanical limits or the application's timeline policy. [Khronos glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#animations).

The first probe failed because the ambient user Python environment supplied NumPy with a missing `_contextvars` dependency. A process-local `PYTHONHOME=/usr`, `PYTHONPATH=/usr/lib/python3/dist-packages`, `PYTHONNOUSERSITE=1` retry succeeded. Both receipts/logs are retained; no host package was changed. Use a pinned renderer environment and capability preflight. This is ordinary diagnosable environment friction, not a missing operator decision. [Failed receipt](rendering/probe-run/receipt.json), [successful receipt](rendering/probe-fixed-run/receipt.json).

## Screen motion, topology and color

The v4 profiles already separate the real app viewport, simulated status/home or desktop/browser chrome, active display boundary and physical occlusions. Whole capture containment and independent source/simulated clocks are useful reusable behavior. See [phone compose.py:18](../../v4/phone/compose.py:18), [laptop manifest](../../v4/laptop/manifest.json) and the [v4 content-profile design](../../v2/device-domain.md:215).

For a 3D render, compile each output frame to an explicit capture timestamp/frame, display surface, presentation-profile revision and evaluated device/camera pose. Decode source media once into a pinned sequence or use a tested deterministic decoder. Declare frame-rate conversion, holds and transitions; do not drive the UI clock from render wall time. The v2 phone proves the simpler version: its script updates the screen image for every evaluated frame, holds the initial source during reveal, plays the retained four seconds, then holds the final source. [scene.py:95](../../v2/phone/scene.py:95), [recipe.json](../../v2/phone/recipe.json).

The direct GLBs currently contain static representative PNGs. Embedding an MP4 by renaming a resource will not turn them into portable recording assets. A browser shot player needs its own timed texture adapter and seek/readiness checks; a native job needs its own pinned frame binding. The portable model and the complete shot package are separate delivery artifacts. Core glTF image resources are JPEG/PNG; material base color is sRGB, while roughness/metalness data are linear. Preserve those meanings and do not mark a captured color image as non-color data. [Khronos specification, images and materials](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#images).

Keep the existing corrected active aperture around the Dynamic Island. Clone only the relevant material; keep the physical pill black. The v4 unlit materials and light-background diagnostic exposed a coverage problem that a dark UI hid. An unlit material bypasses lighting response, but a renderer's display/tone transform can still affect the displayed color. Khronos specifies unlit behavior and a PBR fallback; combining competing shading models is undefined. [KHR_materials_unlit](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_unlit/README.md). The actual target rejects unlit combined with its lighting extensions, including zero factors. [prepareModel.ts:31](/home/matthalloran8/Vrooli/scenarios/web-console/ui/src/components/file-preview/prepareModel.ts:31).

Adopt explicit color modes rather than promising exact UI pixels in every photograph:

- **Color-preserving presentation:** preserve the captured raster/profile before projection and encoding; composite into a reviewed display mask after the scene look where appropriate. This is demonstrated by v6 stationary plates. For moving 3D, an accurate UV/coverage/occlusion pass and a separate reflection treatment would be needed; that compositor is not yet demonstrated.
- **Photographic screen:** render an emissive/unlit screen through the declared scene transform with controlled glass/reflections. The v5 AgX native still is this class. It changes screen appearance and does not inherit pixel parity. Inspect critical UI colors, contrast and readability at final resolution.

Blender documents Standard as a display conversion suitable for already-baked video looks, while AgX compresses a wider scene range with highlight/color changes. This explains why the v5 ceramic highlight correction also changed UI appearance; it does not prove that Standard or AgX is universally preferable. Pin the OCIO configuration, view/look, exposure and output encoding. [Official Blender displays/views documentation](https://docs.blender.org/manual/en/5.0/render/color_management/displays_views.html).

Begin with direct surface rendering for 3D instead of an untested screen-isolation compositor. A planar four-corner homography is appropriate for a stationary planar plate. Curved/folding displays require evaluated UV/geometry and occlusion, not one screen quadrilateral. Calibrate orientation with a numbered grid, border/corner marks and a color chart. Check every surface, including hidden/cover displays and physical gaps. A GLB material export does not transfer arbitrary Blender shader math: the existing laptop instead bakes the presentation raster and derives screen UVs from evaluated geometry. [embed_screen.py:18](../../v4/laptop/embed_screen.py:18).

The v5 larger portable scene exposed screen-layer depth fighting after the standalone phone had passed. Its accepted adaptation offsets only the portable screen and pill by 200/300 μm, preserving native geometry/contact; those numbers are a documented asset-specific correction, not a universal fix. Validate the intended scene scale and grazing angles after export. [portable.py:11](../../v5/table/portable.py:11), [target-viewer validation](../../v5/target-viewer-table-fixed/validation.json).

## Environment, lighting and realism

Use authored, licensed scene assets and physically scaled surface textures before expanding the environment library. The retained CC0 Poly Haven wood maps and studio HDR have pinned URLs and hashes. Poly Haven explicitly permits commercial use of its CC0 assets; still preserve asset-level provenance and separate model attribution when combining them with CC BY phones/laptops. [Poly Haven license](https://polyhaven.com/license), [retained source closure](../../v5/assets/sources.json).

Start qualification in a controlled studio: large area softboxes/reflection cards, a restrained fill, negative fill for edge definition, a continuous backdrop and a single consistent ground/support. A metal chassis needs shaped reflections; merely raising ambient intensity makes it flat. Then approve one carefully sourced lifestyle scene with the same camera and hardware. HDR lighting, visible photographic background, geometry and shadow-receiving support are distinct assets. A studio HDR does not create a detailed room, and a room photograph does not specify the light field.

V5 is instructive but not a finished visual preset. Its numerical contact and dependency checks passed, and native/portable images were reviewed, yet the operator rejected the overall finish. I reinspected the table still and v6 phone hero: v5 has simplified ceramic/prop surfaces, restrained but comparatively flat illumination and a less convincing material/environment combination; v6's light, surface variation and contact read much more photographically. This is qualitative craft judgment, not a calibrated image score. It should drive a scene/reference improvement, not another blind increase from 256 to 1024 samples.

Texture scale is measurable. The native table uses a 1.5 m wood tile. A 2048px map gives about 205 texels across 150 mm; 8192px gives about 819. That explains the close-up blur even before material tuning. The retained final uses 8K diffuse plus weaker 2K normal/roughness; the portable version intentionally uses 1K maps and simpler shaders. These are different quality profiles. An 8K map exceeds the current browser per-axis limit. [scene-final.py:75](../../v5/table/scene-final.py:75), [table manifest](../../v5/table/manifest.json).

Physical support is part of appearance and motion. The face-up phone's camera protrusions make a flat-body placement wrong; v5 solves a supporting facet and records clearance under an assumed mass-center projection. That is a rigid mesh/contact assumption, not measured mechanical stability. A moving shot needs support/contact evaluation over its whole sweep and coherent shadows/reflections, not just an initial zero-height placement. [support evidence](../../v5/table/final/support.json).

The host reports an AMD Ryzen 9 7950X with 32 logical CPUs, but the experiments were bounded to **200% CPU quota, two render threads, 3 GiB memory and declared wall time**. The timings below describe that constrained execution, not unrestricted machine speed. See [evidence.json](rendering/evidence.json). At the retained snapshot approximately7.1 GiB was used and three GPU processes existed; those transient figures do not reserve capacity or establish exclusivity. Only nonsecret CPU/GPU/tool fields were retained in [host-inventory.json](rendering/host-inventory.json).

The inventory reports successful NVIDIA/device-access probes. A second tiny owned, read-only Blender capability probe then checked compiled backend flags and enumerated device types without rendering or saving preferences. **Installed Blender4.0.2 reports CUDA support=true and OptiX support=false, but CUDA and OPTIX enumeration both return only the Ryzen CPU.** The CPU enumeration also returns that CPU. No GPU render, configuration write or capacity reservation was performed. The physical RTX card is a promising qualification path, but it cannot yet support a latency promise for this installed process. Diagnose the enumeration boundary before requesting any new renderer dependency or treating CPU as the only possible host capability. Blender documents backend/device-specific requirements. They establish useful cost ranges and failure cases, not a Cycles/Eevee speed multiplier or visual-quality ranking. A naïve 144-frame extrapolation of the retained Cycles still times gives about 6.3–22.2 hours. That is an estimate, not a promised throughput or reason to render the full sequence without a cost gate.

[Actual error log:73](../../v3/imported/runs/studio-preview2/output.log:73). The new probe confirms Cycles and OpenColorIO build flags but does not itself certify an available denoiser. More samples and denoising can reduce noise; they cannot repair the wrong flash shape, flat props, lost geometry or unsuitable lighting. A future denoiser must also pass a temporal test for text loss and flicker.

Recommended operating contract: responsive browser layout preview; queued native preview; an approved final-look still; then bounded frame batches with an estimated total budget, progress, cancellation and restart from immutable frame receipts. Keep `--python-exit-code 1`, source/hash assertions and full output decode checks. A zero Blender exit code without that option previously concealed Python failures. Resource-limited scopes are useful containment of compute but are not the complete execution security boundary for generated code.

Do not promise interactive Cycles or realtime software-Eevee movie export on this host. A CPU fallback is viable for stills and carefully bounded clips. Faster local GPU or external rendering is a later operator/execution decision with its own rights, cost, isolation and performance evidence. This investigation authorizes none of those changes.

### Output and latency choices

Recommend **1920×1080 at 24fps for the first accepted motion presets**, with explicit 1080×1920 reframing for portrait output. Keep lower-resolution proxy playback for editing, and inspect final-resolution crops before a full render. This is a target profile: the current generic phone movie proves only 1280×720 animation, and the 1920px lifestyle evidence is still imagery at other aspect ratios. A 16:9 camera needs an actual reframe that retains the device and story content; do not silently crop the existing stills.

| Output choice | User-visible tradeoff | Evidence and qualification |
|---|---|---|
| 1080p/24, queued final render | Recommended quality baseline for launch-video inserts; useful detail with a more manageable pixel budget | Native near-1080p stills measured at roughly 2.6–9.2 minutes in these different scenes. A final 1080p moving preset still needs the motion/craft gate and a measured estimate. |
| 720p draft or motion proof | Faster feedback and articulation review; insufficient alone to approve fine text, chamfers or final temporal edges | Actual generic-phone 720p software-Eevee clip took 21.7 minutes for six seconds. Different assets/settings need a new estimate. |
| Native 4K UHD/24 (3840×2160) | More final detail and reframing headroom; exposes anatomy/texture shortcomings and requires higher source density | No local 4K scene or animation benchmark exists. UHD has **4× the pixels of 1080p**; this is arithmetic, not a measured 4× time claim. Ray work and image buffers can increase substantially, while fixed setup, adaptive sampling, memory pressure and export costs change the actual ratio. |
| Upscaled 4K from a smaller render/plate | A 4K container with interpolated detail | Can be offered only with an explicit upscale label; it is not evidence of native 4K appearance or text quality. |

The current phone recording is 430×880. Its 1206×2622 presentation raster contains resized app pixels plus simulated regions; it does not create additional captured detail. The v6 photographic plate is only 1536×1024. A native 4K photographic shot therefore needs a higher-resolution approved plate and sufficient capture density for the projected screen, or an explicitly accepted upscaled result. Rendering a large mesh does not repair a low-resolution UI source. The same footprint test applies to small laptop text and procedural/photographed environment textures.

Operator latency choices should be **quality-first asynchronous CPU**, **a qualified accelerated profile**, or **a separately specified faster/lower-detail output profile**. Recommend asynchronous CPU as the honest fallback and 1080p/24 as the initial acceptance target. Do not promise a fixed maximum final latency until opening, midpoint and hold frames plus a continuous sample have been measured for the chosen scene and hardware. A job ceiling should stop with a usable checkpoint and unmet criteria, rather than silently drop resolution, frames, physical motion or realism.

## Hybrid constraints

A fixed-camera photographic room with a genuinely rendered moving device can avoid modeling the entire room. It still needs camera matching, a support/receiver proxy, light/reflection inputs consistent with the photo, foreground occluders and correct alpha/color composition. The environment image is static; device shadows and reflections must change with motion. A plate already containing a phone and its baked shadow is not automatically an empty backdrop.

No retained v6 result is this hybrid: image generation supplied the visible hardware as well as the room. Supplying a GLB render as a generation reference may guide composition, but generated pixels can change hardware geometry and cannot inherit exact-fit qualification.

Keep hybrid optional. Its acceptance experiment should compare the **same qualified device and fixed-camera motion** against a simple native scene and a photographic backdrop, holding framing/output constant. Review contact, reflections, occlusion, temporal consistency, setup time and render time. Reject a visually attractive hybrid that leaves a frozen contact shadow during device motion. Camera movement increases reconstruction requirements and should remain outside that first gate.

## Proposed minimum visual and motion acceptance

These are recommended production budgets for the decision round, not measured manufacturer tolerances or existing passing results.

1. **Final-look approval:** review a 1920px-or-wider frame from the actual final renderer/recipe at normal viewing size and 100% detail. The device silhouette has breathing room unless the shot explicitly requests a detail crop. Reject obvious toy props, incorrect hardware anatomy, flat or blown metal/ceramic, visible backdrop seams, floating contact and screen glare that hides the decisive content. Bind acceptance to the exact asset, scene, camera, color and recipe hashes.
2. **Readable interval:** a six-to-eight-second study at 24fps includes at least two seconds with stable device/camera framing and the decisive real app state visible. As a starting budget, the smallest text the story requires should project to at least 12px glyph height at delivery size; review actual glyphs instead of accepting the number alone. Do not require every incidental UI label to be legible.
3. **Screen proof:** retain source/frame clocks, full-capture fit and presentation config. Test a bright aperture around the physical black pill, corner/border/grid orientation, masked hardware, native/portable light changes and the largest intended scene bounds. Preencode source identity claims are scoped to the unresampled capture rectangle or original texture; final perspective/grade/video is qualified separately. No app pixels enter physical hinge gaps, bezels or simulated system regions.
4. **Rigid phone motion:** render a short front-three-quarter-to-readable hold with the current accepted phone asset, not the older generic v2 phone. Inspect continuous playback and first/mid/last frames for silhouette crawling, screen instability, reflected-light flicker and text aliasing. Approve all intended visible hardware angles against retained references.
5. **Laptop articulation:** after part/pivot repair, exercise the intended open/closed endpoints and intermediate angles with contact and swept-clearance diagnostics. Include a readable open interval and a closing interval in the continuous clip. Verify that screen, bezel, lid hardware and reflections move together while the base remains seated. A static front view cannot pass this gate.
6. **Deterministic evaluation and portable limits:** browser/native evaluators must agree on named joint values, source timestamps, camera transforms and surface orientation at selected frames. Identical lighting pixels are not required between unlike renderers. Reimport the direct GLB and test its declared capabilities; static export is acceptable only when explicitly labeled. Deliver direct PNG/MP4 plus packed native/recipe, hashes, rights and full decode proof.
7. **Budget gate:** measure at least representative opening/middle/hold frames and a continuous final-profile sample before the full job. The total estimate and ceiling must be visible. Treat visual failure, timeout, missing renderer feature and unsupported motion as distinct outcomes; samples and successful execution alone cannot set `accepted`.

This gate can begin with a controlled studio rather than waiting for a whole-room asset library. Its result decides whether the first supported 3D preset can be released; it does not certify all device families.

## Product decisions for the parent decision packet

The browser proxy/native renderer split and color implementation are engineering recommendations above. They do not require the operator to choose an engine or solve color management. Preserve both photographic and controlled3D routes in the agreed scope. Ask product preferences about quality, waiting time and acceptance; then benchmark the implementation that meets them.

| Decision | Options | Recommendation and effect |
|---|---|---|
| Milestone order and complete delivery | A. Photographic milestone first, then qualified 3D motion before the agreed delivery is complete; B. Show the first milestone only after both paths pass; C. 3D-only | **A.** Delivers useful evidence early while preserving controlled phone motion and lid closure as required completion gates. B changes when the operator first receives a usable workflow, not whether motion is required. |
| Waiting time versus finish | A. Quality first, asynchronous jobs and explicit estimates; B. Prefer faster output with an explicitly lower-detail preset; C. Strict latency ceiling to be specified | **A initially**, with the discovered GPU as an engineering qualification opportunity and CPU fallback. If C is chosen, establish the ceiling before promising quality or selecting hardware. No external provider spend is presumed. |
| Initial final output | A. Native1080p/24 with reviewed portrait reframe; B. Native4K/24 with larger budget and source-density gate; C. 720p final | **A.** Balances launch-video detail and observed compute cost. B remains a supported design target pending actual measurements; C is better retained for drafts unless the operator explicitly selects it. |
| Hybrid priority | A. Defer until base 3D motion passes; B. Include one fixed-camera A/B experiment now; C. Make hybrid mandatory | **A.** B is reasonable only if reducing room modeling effort is a first-release requirement. Existing evidence does not support C. |

The operator chooses product scope, quality acceptance and spending/latency tolerance. Engineers can resolve process-local Python configuration, part segmentation, source-frame mapping, shader adaptation and renderer preflight without asking permission for routine reversible fixes. Unavailable hardware/credentials or provider authority would be actual external gates; no such missing authority blocks this report.
