# CLI Commands — Device Studio

## Availability and planned product commands

Health/configuration and Notes below are the generated reference surface. Product commands are not implemented. The target command groups mirror projects, devices, scenes, presentations, motions, shots, jobs, creations and reviews. Use the generated manifest as the executable authority; do not advertise these future groups as available.

Planned CLI operations must support noninteractive structured input and bounded JSON output, exact revision references and durable receipt/job IDs. Preview/compile are deterministic unless an explicit AI operation is requested. AI/agent submission must show provider/funding, data disclosure, maximum scope/spend and the authorized project policy before dispatch; CLI automation supplies the same explicit accepted envelope as the UI. No implicit remote fallback, raw secrets in output or hidden child agents. Cancellation returns execution and settlement state separately.

The scenario CLI is a thin Go wrapper over the API. Every command
calls a single API endpoint and renders the result; there is no
business logic in the CLI. If a command needs to make a decision the
API doesn't expose, the correct fix is to add the API endpoint —
**not** to compute it locally.

The CLI binary is built from `cli/`, installed by `make setup` to
`~/.vrooli/bin/device-studio`, and rebuilt automatically when its
sources change (cli-core's stale-detection rebuilds before any command
that touches the API).

## Source of truth: `cli/manifest.json`

The CLI's command surface (groups, commands, positionals, flags,
RPC bindings, governance metadata) is declared in
[`cli/manifest.json`](../../cli/manifest.json) and validated against the
project CLI-manifest schema (`path:.vrooli/schemas/cli-manifest.schema.json`)
(schema id `cli-manifest/v1`). The manifest is loaded at startup by
`cliapp.LoadFromManifestPrimitives`, which:

- builds each domain's `SubcommandGroup` from its manifest group
- wires each command's `binding.method` (e.g.
  `<Domain>Service.List<Entity>`) to a cli-core **primitive** registered in the
  domain's `register.go` bindings map (`cliapp.ProtoList` / `ProtoMutation` /
  `ProtoOperational`, each a `<name>Call` + `<name>Report` pair). The
  `<name>Call`/`<name>Report` funcs take a narrow `cliapp.OperationContext` — no
  `JSON()`, no renderers — so an operation *cannot* branch on the output format;
  renderer separation is enforced by the callback signature, not convention
- attaches the primitive's observed evidence to each command and **fails loudly
  if it disagrees with the manifest's `architecture.primitive` declaration** —
  this supports verification of the declared primitive rather than accepting a declaration alone
- fails loudly on missing handlers, dead handlers, or unknown groups

Declaring `architecture.primitive` in the manifest is intent; building the
handler with the matching primitive here is the proof. The intended evidence mechanism is
a committed **static** artifact: `.vrooli/generated/cli-primitive-evidence.json`
(schema `cli-primitive-evidence/v1`), generated from the assembled command tree
(no command is executed) and regenerated by the golden test in
[`cli/evidence_test.go`](../../cli/evidence_test.go) (`UPDATE_CLI_EVIDENCE=1`
rewrites it; scaffolding writes it once via a template postHook). CLI Health reads
that committed file **statically** to verify each declared primitive — it never
runs your commands. A declaration with no matching evidence is advisory
not-yet-verified debt, a mismatch is a gating error, and a stale/missing artifact
keeps declared primitives unverified. See the CLI architecture maturity
reference (`path:scenarios/cli-health/docs/reference/cli-architecture-maturity.md`).

Current scaffold observation: `.vrooli/generated/cli-primitive-evidence.json` is absent. The mechanism described above is not a claim that this artifact exists or that CLI L4 has been earned. Generate and validate it through the owning test/CLI Health workflow during implementation; do not synthesize a success receipt.

Per-domain tests use `cliapp.RequireProtoServiceCoverage` to assert
that every RPC on the bound proto service either has a manifest command
binding or appears in the manifest's `omitted[]` list with a reason —
adding a new RPC without exposing it as a CLI command (or explicitly
omitting it) fails the test.

The manifest's `governance` block (`effect`, `run_eligible`,
`permissions`, `requires_confirmation`) is consumed by prompt-manager
to derive action certainty automatically; scenarios that adopt the
manifest don't need hand-classified action-safety lists.

`binding.kind` is currently `connect-rpc` only. REST-exception
commands (for example, a multipart file-upload command whose request
body carries opaque bytes) are appended to the loaded group outside the
manifest path in the domain's `register.go` and documented in the
manifest's `exceptions[]` array (command, class and reason). RPC coverage omissions remain in `omitted[]`.

For environment-variable precedence and CLI config-file shape, see
[`configuration.md`](configuration.md).

## Global flags (provided by cli-core)

Every command supports the following flags. **Do not reimplement them
in scenario commands.**

| Flag | Purpose |
|---|---|
| `--api-base <url>` | Override the API endpoint for this invocation |
| `--auto-start` | Run `vrooli scenario start device-studio` if the API is unreachable |
| `--json` | Emit machine-readable JSON instead of the human report |
| `--no-color` | Disable ANSI color (also respects the `NO_COLOR` env var) |
| `--color` | Force-enable color (overrides terminal detection) |
| `--help`, `-h` | Show command help |
| `--version`, `-v` | Show the CLI version |

## Built-in commands (auto-provided by `cli-core`)

### `device-studio status`

Health check. Calls `GET /health` and renders status + dependency
details. The output uses the **operational contract**:
`Status → Triage → Next Steps`.

```bash
device-studio status
device-studio status --json
```

### `device-studio configure <key> <value>`

Persist a setting to the per-user CLI config file (location resolved
per [`configuration.md`](configuration.md#cli-config-file)).

```bash
device-studio configure api_base http://localhost:15001/api/v1
device-studio configure token "<token>"
```

Read values back without an argument:

```bash
device-studio configure api_base
```

### Example domain — `notes` (removed by `template-manager detemplate`)

The `notes` domain is the canonical worked example. Copy its layout
when adding the first non-trivial domain to your scenario, then remove
it.

#### `device-studio notes list`

List notes, newest-first. Calls the generated Connect-RPC
`NotesService/ListNotes` method. Uses the
**data-retrieval contract**: `Summary → Results → Retrieval Hints`.

```bash
device-studio notes list
device-studio notes list --json
```

#### `device-studio notes create --title <title> [--body <body>]`

Create a note. Calls the generated Connect-RPC `NotesService/CreateNote` method. Uses the **mutation
contract**: `Result → What Changed → Next Command`.

```bash
device-studio notes create --title "First note" --body "Hello world"
```

`--title` is required. `--body` is optional. Validation lives in the
API service, so an empty title surfaces as an `invalid_argument`
Connect error rather than a CLI-side check.

#### `device-studio notes get <id>`

Fetch a note by id. Calls the generated Connect-RPC `NotesService/GetNote` method.

```bash
device-studio notes get abc123
```

A non-existent id surfaces as `not_found`; the CLI translates the
typed Connect code to an actionable error message.

#### `device-studio notes attach <id> --file <path>`

Attach a file to a note. This is the documented REST multipart
exception because the request body contains opaque bytes. The response
is proto-typed attachment metadata.

```bash
device-studio notes attach abc123 --file ./example.png
```

## Output contracts

Every scenario command should render through one of three human
contracts. Proto-backed commands should use `cliapp.RenderProtoList`
or `cliapp.RenderProtoMutation`: human consumers see the report, while
`--json` consumers receive the proto JSON response shape.

| Contract | Used by | Structure |
|---|---|---|
| **Operational** | `status`, `health`, `audit`, `validate`, `doctor` | Status → Triage → Next Steps |
| **Data Retrieval** | `list`, `get`, `view`, `search` | Summary → Results → Retrieval Hints |
| **Mutation** | `create`, `update`, `delete`, `start`, `stop` | Result → What Changed → Next Command |

For commands that aggregate multiple API calls or produce a
non-proto report, use the `RunContext` render helpers directly
(`ctx.RenderList`, `ctx.RenderMutation`, or the operational report
helpers).

**`--json` is an output contract, never an operation selector.** Declare each
command's `architecture.primitive` in the manifest (`proto_list` /
`proto_mutation` / `operational` / `action`) and either bind the matching
cli-core primitive builder (`cliapp.ProtoList` / `ProtoMutation` /
`ProtoOperational`) or render inline with `RenderProtoList` /
`RenderProtoMutation` / `RenderProtoOperational`. Both keep the operation outside
any `if ctx.JSON()` branch — the top rung of CLI Health's command-architecture
maturity capability. Legitimate special cases (streaming, upload, passthrough,
external delegation, durable runs) go in the manifest's top-level `exceptions[]`.

## Adding a new command

For a new domain, copy the worked CRUD command group in the fenced
example above first, then replace it once your real domain is green.

For a command inside an existing domain:

1. If the command needs a new API endpoint (RPC), add it first per
   [`api-endpoints.md`](api-endpoints.md#adding-a-new-endpoint). The
   manifest's coverage test will fail otherwise on the next CLI build.
2. Add a command entry to the matching group in
   [`cli/manifest.json`](../../cli/manifest.json): `name`, optional
   `description`, `positionals` / `flags`, the `binding` (service +
   method), the `governance` block (`effect`, `run_eligible`,
   `permissions`, optional `requires_confirmation`), and an
   `architecture` block (`{ "primitive": "proto_list" | "proto_mutation"
   | "operational" | "action" }`) matching the command's renderer. The
   schema in `.vrooli/schemas/cli-manifest.schema.json` is authoritative.
3. Implement the typed call/report functions in the domain's focused handler
   files. Use the matching cli-core primitive and its narrow
   `cliapp.OperationContext`; keep output rendering out of the call function.
4. Register that primitive under its exact `"<Service>.<Method>"` binding in
   `cli/domains/<domain>/register.go` through
   `cliapp.LoadFromManifestPrimitives`. Missing or dead bindings must fail.
5. Use generated Connect clients and typed responses. Choose the appropriate
   list/mutation/operational primitive and its report contract. Multipart REST
   exceptions use the owner upload primitive, are appended to the group, and
   are declared in `exceptions[]`; RPC omissions alone belong in `omitted[]`.
6. Add endpoint metadata in the API handler module and bind the method
   (or list it in `omitted[]`) in `cli/manifest.json`. Then run
   `make endpoints`; do not edit [`.vrooli/endpoints.json`](../../.vrooli/endpoints.json)
   by hand.
7. Add a row to this document.
8. Add a handler test in
   `cli/domains/<domain>/handlers_test.go` using `clitest.NewTestApp`
   + `clitest.NewAPIServer` + `clitest.CaptureStdout` (see
   [`../internal/TESTING.md`](../internal/TESTING.md)). Driving the
   handler via `cliapp.NewTestRunContextFromArgs` against the manifest's
   schema gives the closest parity with the dispatched path.

## Command structure principles

- **Subcommand groups** (`<domain> list`, `<domain> create`) over flat
  verbs (`list-<entity>`, `create-<entity>`). Discoverability via
  `--help` is the goal.
- **Positional for required, flags for optional.** `<domain> get <id>`
  not `<domain> get --id <id>`.
- **One command per API endpoint.** If you find yourself making two
  endpoint calls, the API is missing a use-case.
- **Error messages must be actionable.** "API unreachable" is bad;
  "API unreachable at http://localhost:15001 — try `--auto-start` or
  `vrooli scenario start device-studio`" is good.
