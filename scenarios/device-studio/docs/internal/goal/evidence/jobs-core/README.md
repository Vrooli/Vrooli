## Domain contract

- `Input` is a canonical immutable execution closure: project and shot revision, artifact role/ID/revision/SHA-256 bindings, source-clock digest, tool-profile digest, renderer version and output profile. Bindings sort by role; duplicate roles and non-lowercase/non-64-hex SHA-256 values reject. A SHA-256 fingerprint binds the canonical payload to the idempotency key. Reusing a key for different input returns `ErrIdempotencyConflict`.
- Before any `Running` state, the worker/process owner supplies a durable execution-claim reference, including the attempt ID/number selected for that launch. The service binds it to job, attempt, immutable input fingerprint, tool-profile/source-clock digests and owner-selected scope. A resumed attempt ID is supplied before Start so the owner receipt can bind that exact identity. A checkpoint transition additionally requires the owner’s digest-bound quiescence receipt for that exact claim. `SaveCheckpoint` is a quiescent pause after the checkpoint is durable, not a periodic checkpoint while rendering continues. Therefore `SaveCheckpoint` means a quiescent pause after the checkpoint is durable; it does not represent periodic checkpointing while frames continue to render. Checkpointed work cannot resume without both records. Resume uses caller-supplied, previously unused attempt and scope IDs for a new attempt linked to the prior immutable checkpoint; reused historical IDs/scopes reject, and stale receipts from the old attempt cannot complete or heartbeat the new one. For started work, cancel confirmation requires the same job/attempt/fingerprint/claim/owner/scope binding plus a durable proof artifact reference and digest. These are opaque owner assertions with durable, immutable identity bindings, not locally verified process facts: the job domain does not verify referenced bytes or prove the owner actually stopped an OS process tree. The later execution adapter must use a qualified lifecycle owner; existing API presence does not constitute that qualification.
- `Repository` is engine-neutral. `NewSQLiteRepository` implements it with domain-owned declarative schema, SQLite `BEGIN IMMEDIATE` serialized writes and versioned transitions. `Schema()` exports the schema for the future module owner to register. This task intentionally leaves the E1-owned central registry/wiring untouched.
- Submit persists a queued logical job and first queued attempt atomically. Start, heartbeat, checkpoint, completion, failure, cancellation intent/confirmation, and settlement are distinct versioned operations. Completion needs typed worker evidence with matching attempt/input fingerprint, a nonempty output receipt and validated-shaped output refs; this service has no byte/blob owner and cannot prove those hashes exist or match the bytes.
- Checkpoints bind attempt ID/number, execution claim ID, input fingerprint, tool profile, source clock and checkpoint artifact digest. A `checkpoint_resume_candidate` is returned only for a persisted checkpoint plus a matching owner quiescence proof. Recovery returns classifications only: queued dispatch eligible, live lease, checkpoint resume candidate, worker reconciliation required, cancellation quiescence required, or terminal. It never blindly resubmits a stale execution. If the owner proof is missing/altered, the job remains reconciliation-required and Start rejects dispatch.
- Success and cancellation intent race through one SQLite serialized transition. Whichever valid write commits first advances the version; stale writes fail. If cancellation intent wins, later success cannot promote the job. Running work remains `cancel_requested` until an owner-supplied quiescence proof bound to the saved execution claim is recorded. A checkpointed attempt already has such proof; cancelling it can use the persisted proof. A queued cancel records only that this job admitted no worker execution. These state tests do not prove a process tree stopped or that a supplied proof is truthful.
- Execution state and settlement are separate. `AccountingRequired` pins an accounting operation and starts `pending`; terminal execution leaves it pending until explicit settlement/reconciliation. Local no-accounting submissions start `not_required`.

## Verification

Command, from `scenarios/device-studio/api`:

```text
gofmt -w internal/jobs
go test ./internal/jobs -count=1 -v
```

Result: pass. Tests cover durable reopen, exact idempotent replay and changed-input conflict, success evidence validation and receipt persistence, concurrent success/cancel terminal precedence, checkpoint mismatch and owner-proof gating, recovery rejection after proof removal, fresh resume scope, stale prior-attempt completion rejection, stale-worker classification without retry, claim-bound cancellation proof, pre-dispatch cancellation, terminal transition rejection, and settlement independent from execution. The suite uses a temp SQLite file with two repository lifetimes and `busy_timeout=5000` for the concurrent writer case.

Not run by this bounded task: full API module suite, Test Genie, application startup/routes, schema registration, cross-process lifecycle probes, actual worker/process cleanup, blob byte/digest verification, checkpoint restore execution, disk-full/tool-failure injection, cross-platform package qualification, or E2 acceptance. No test claims physical process cleanup. Parent source review additionally notes that current StopScopeContext evidence is Linux agent/test-only and the desktop runner root Kill is not descendant proof; no production worker lifecycle is qualified by this package.
