# Visual and release acceptance

## Evidence levels

This is a planned manual review protocol, not a pass receipt. Separate structure, semantic review, executed correctness, visual craft and distributable release. Historical experiments establish only their named scope. The user rejected v5 scene quality and accepted v6 photographic direction; those judgments are preserved.

## Cross-cutting review matrix

| Review | Given / When / Then | Required retained evidence |
|---|---|---|
| Device fidelity | Given fixed measured dimensions and held-out references, when the candidate is compared, then silhouette/details/material differences are explicit | Calibrated views, measurement uncertainty, deviations and reviewer |
| Phone chrome | Given a bright app edge, when the phone is shown front/angled, then status background surrounds the opaque pill and app video excludes simulated bars | Still/crop, profile and source hashes |
| Browser presentation | Given app-only recording, when browser/desktop mode is used, then real content retains fit and simulated chrome is independently controllable | UI configuration, rendered frame and source mapping |
| Physical motion | Given a qualified spin/hinge track, when played continuously, then contact, joints, masks and reflections stay coherent | Full short MP4 plus sampled frames/rig recipe |
| Screen entry | Given a camera move into the screen, when transition completes, then the active app surface fills the intended frame at continuous source time | Final transition footage and timing/crop receipt |
| Photographic replay | Given a pinned plate/mask, when the saved shot rerenders, then unchanged physical regions remain fixed before encode | Plate/mask/frames/recipe/tool hashes |
| Craft | Given the actual final output footprint, when reviewed against the chosen photographic benchmark, then scale, contact, materials, illumination and composition appear credible | Independent human findings and exact input revision |
| Broad library | Given eight promised groups, when their released recipes are inspected, then real assets/outputs and supported motion envelopes exist | Per-group package, references, rights and reviews |
| Credits/privacy | Given a selected route and project consent, when work/retries/children execute, then data/funds remain within that scope | Owner receipts, admission/cancel/reconciliation and upload evidence |
| Desktop | Given a clean target install, when used offline and updated, then local projects persist and only qualified capabilities are advertised | Target/installer/tool digests and actual journey receipt |

## Review procedure

1. Pin the candidate, renderer/output profile and intended use/view envelope.
2. Declare source-dependent tolerances and required readable UI regions before judging output.
3. Review dimensions/materials separately from art direction; inspect held-out views and continuous playback.
4. Record every material issue with artifact/time/view and repair owner.
5. After edits, invalidate affected prior checks and rerun the relevant evidence.
6. Record the human verdict and remaining limits; approve only that revision/scope.

No universal numeric aesthetics score overrides an operator rejection. The library reviewer and upstream human release decision remain separate. Two empty documentation review passes establish this foundation's consistency, not future rendering excellence.

### Accepted execution choices

- Full delivery with staged demonstrations; an initial slice does not complete the release.
- Operator approves initial representative looks. Orchestrator applies that approved standard to subsequent assets; an operator rejection cannot be overridden by automated tests or reviewers.
- No paid provider calls initially. Request one concrete bounded allowance when live paid tests are ready. Development Luna delegation is explicitly authorized; it is distinct from product-provider spending.
- Measure the first real rendering slice, then agree numerical performance targets before library expansion. Do not invent a performance pass threshold retrospectively.
- Architecture remains compatible with Windows/macOS/Linux. Only this machine is a required runtime validation target for this effort; unavailable other-OS execution/signing/certification does not block delivery. Do not advertise unexecuted native validation.
- Preserve original research and selected reference bytes. Existing accepted v6 images establish direction, not blanket approval of new actual-renderer outputs.

### Approval and evidence standing

Initial representative-look approval, later live-spend allowance and measured performance targets are pending inputs. Continue independent local implementation while those are pending. Missing credentials or upstream interfaces remain explicit unverified obligations, never simulated success. No automatic purchase, paid fallback, public deployment or commit is authorized by this agreement.
