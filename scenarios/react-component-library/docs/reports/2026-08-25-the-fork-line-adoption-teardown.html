01

The two loops, and where each one leaks

Everything here is one bidirectional cycle. Code is harvested from scenarios into the library, proved by a five-stage test pipeline, then adopted back out. The leaks are all at the two boundaries, not in the middle.

The pipeline in the middle is the part that works. Five stages run per component version: closure_integrity walks the dependency closure, source_integrity hashes the file, contract_validation checks story.json against the schema, declared_behavior drives each story's interactions and assertions in a real browser via BAS, and experience_evidence confirms the artifact bundle came back complete.

The two boundaries are where your concerns live, and they're symmetric: harvest has an origin-parity gate that blocks behavior loss; adopt has nothing equivalent. Nothing checks that a copy still does what the library version did.

It was — it was the v3 form that v4's composition block replaced, and all three spellings coexisted. It is now zero occurrences across all 237 story files, and every file is schemaVersion: 4. Your read of "something fishy in the schema" was exactly right, and it has been collapsed.

Confirmed, and the migration made a subset of them actively wrong. $node was the element form ({"$node":"button", children:[…]}); $text is a literal string. In 20 files, 45 stories had their $node collapsed into $text carrying the tag name — so Card/1.1.0's metric-card story now renders the literal word "div" twice, and its screenshot is silently wrong.

The diagnostic that would have caught this (legacy_raw_node) was deleted with the compatibility layer rather than surviving to police the result.

Confirmed

There is no declared ideal to push toward. The schema permits five ways to express one story — composition.specimen, composition.harness, composition.frame, composition.fixture, or nothing at all plus raw args — and validation is indifferent between them. The node mini-DSL isn't even schema'd: $text, $node, $icon, $handler, $rowKey, $columns, $filters exist only as an allow-list inside a prototype-pollution safety check.

Confirmed

Half right, then worse than you thought. Both gates now exist — ValidateI18n and ValidateSelectorCoverage — and both check only the library end. On the adopter end, both seams are inert: see the ledger in §04.

Needs reframing

Every copied component needs its own test file

The rule isn't 1:1 test files — unit-health enforces a per-file coverage threshold plus a workspace aggregate. But the practical effect is what you described: 582 vendored files sit in adopters' coverage denominators, and money-ledger really does carry button.test.tsx, dialog.test.tsx, data-table.test.tsx and four more for components it did not write. An imported package would leave that denominator entirely.

03

Why adoption copies — and why the reason no longer holds

This is the part of your update that matters most, so here is the chain in full.

The story-contract-v4 plan measured a 97% modification rate and made Decision 1: "Forking is the real adoption model; build for it." It explicitly considered and rejected package imports:

From the plan, verbatim

"Rejected: ship components as real package imports instead of copies. This is a defensible long-term design and it is out of scope here… Revisit when the fork classification data shows what proportion of forks are behavioral rather than cosmetic."

"Revisit trigger: if fork classification shows most divergence is cosmetic (styling only), reconsider the package-import model, because a cosmetic-only fork rate means the extension points were the missing piece rather than the copy model."

That is a well-formed decision with an explicit escape hatch. Three things have happened to it since.

The classification was never produced

Phase 9 built fork_status with three values — declared-fork, unintended-drift, mechanical-translation. In the live database, all 394 records have fork_status = ''. The classifier has never run against the corpus, so the revisit trigger has no input and cannot fire.

The classifier can only see a third of the corpus

reconverge.go:33 skips any adoption that is not behind. Only 145 of 394 records are behind. The 249 records that are current and modified — the majority — are structurally unreachable by the classification the decision depends on.

And "cosmetic" is defined so narrowly it can never be found

classifyModified calls a fork translation_only only when the on-disk bytes exactly equal the library body after design-token substitution and import rewriting. A component restyled from CSS custom properties to Tailwind classes can never match that, and won't pass the containsEverySourceLine fallback either. It lands in local_fork — "behavioral" — by construction.

The revisit trigger is rigged shut. It asks a question that is never run, over a third of the data, using a definition of "cosmetic" that the most common kind of cosmetic change cannot satisfy.

So I ran the measurement the trigger wanted

The right proxy for "behavioral vs cosmetic" is the exported API surface: same exported symbols and same prop members means the contract held and only the rendering changed. Across all 379 modified adoptions (376 resolvable to a library source):

What the forks actually are

The dominant fork is a styling-system rewrite. The library renders through CSS custom properties, injected <style> blocks and data-rcl-* attributes — 55 library files use inline style={{}}, exactly one uses twMerge. Adopters are Tailwind apps. 35 copies visibly switch systems on the way across. Here is the canonical case:

Is importing actually possible here?

Yes, and more of the machinery exists than you'd expect. The obstacles are real but named, and none of them is the one usually cited.

99
scenarios already import a shared TS package via file:
4
governed TS packages under packages/
0
build, barrel, or package.json in library/
263
live component versions to expose as entry points

The sanctioned mechanism already exists and is load-bearing. packages/api-base/.vrooli/package.json declares exactly the shape an importable library would need:

packages/api-base/.vrooli/package.json

"adoption": {
  "scenario_adoptable": true,
  "allowed_consumers": ["scenario_ui", "template_ui"],
  "adoption_modes": ["file_dependency"]
}

Ninety-nine scenario UIs consume it as "@vrooli/api-base": "file:../../../packages/api-base". Scenario UIs are deliberately kept out of the root pnpm workspace — that boundary is enforced and commented in pnpm-workspace.yaml — but file: deps are provisioned by scenario setup before UI install, so isolation and standalone deployability survive. The usual objection to a shared UI package in this repo does not apply.

What genuinely stands in the way

ObstacleWhy it's realShape of the answer
Multi-version coexistence 263 live versions; adopters pin different ones (Button@1.2.0 while latest is 2.2.0). One npm package = one version for all consumers. Subpath exports keyed by version: @vrooli/rcl/Button/1.2.0. The tree already has this exact shape on disk, and the library's own internal imports are already version-pinned relative paths.
Styling-system impedance The real driver of forking. Library = CSS custom properties + injected style blocks. Adopters = Tailwind. Importing a component you can't restyle is worse than copying one you can. The token bridge already exists (tokens.go derivation + design-tokens.css). What's missing is a className/slot pass-through contract on every component so an adopter restyles from outside — which is also what Decision 1's "extension points" wanted, delivered without a copy.
No build for library/ No package.json, no barrel, no emit. It is raw source that RCL's own UI reaches with ../../../../library/… paths. Smallest real work item, and it also fixes RCL importing itself. Source-only distribution (no emit, bundler-resolved) matches how packages/proto/gen/typescript is already consumed.
Local-edit affordance Copying's genuine virtue: an adopter can change anything, immediately. Importing removes that. Keep ApplyAdoption as an explicit eject — with the fork declared, not the default. 1.3% genuinely need it.
06

Two models, side by side

Copy — today

  • 582 files vendored across 35 scenarios; each one enters that scenario's coverage denominator and needs tests it didn't write.
  • 96% modified, 37% behind. A library fix reaches adopters for 6 records out of 394 — the plan itself calls that capability "already theoretical".
  • 115 versions are retirable only because forks don't re-read their source; version retention is bounded by provenance, not by use.
  • Local edit is instant and unpoliced — the genuine upside, and the reason 1.3% of adoptions exist.
  • i18n and selector obligations must be re-satisfied by hand in every adopter. Nobody has.

Import — if the styling contract lands first

  • Zero vendored files in the coverage denominator. Component tests live once, in the library, where the 5-stage pipeline already runs them.
  • A fix propagates by changing a version pin, for the 78% whose contract never diverged.
  • i18n keys and selector ids ship with the module instead of needing a merge step — the bridge and the ids already exist.
  • Version pinning survives via subpath exports; RCL stops reaching into itself with ../../../../.
  • Requires the className/slot pass-through contract first. Without it this fails exactly where copying failed, and you have added a package for nothing.

The sequencing matters more than the choice. Importing is not an alternative to the extension-point work — it is what the extension-point work unlocks. Ship the restyle contract, then the package, and 78% of the fleet can stop being a fork. Ship the package first and you will re-derive the same 96% divergence rate through a different mechanism.

The cheapest next move

Before any of this, run the measurement the existing decision is already waiting on, and fix the classifier so its answer means something:

  • Widen reconverge.go:33 past behind so the 249 current-and-modified records are classifiable at all.
  • Add an API-surface comparison to classifyModified as a fourth disposition — contract_preserved — sitting between translation_only and local_fork. Exact-bytes-after-translation is too narrow to ever describe a restyle.
  • Then populate fork_status across all 394 records and let Decision 1's own revisit trigger fire on real data.

That is a small change to one file plus one run, and it converts an architectural argument into a measurement. My proxy says the answer will be roughly 78/21/1 — but the system should be able to say it itself.

And independently of all of it

  • Repair the 45 broken stories in 20 files where $node was flattened to a tag-name $text. Their screenshots are currently green and wrong.
  • Pick one story authoring shape and enforce it. 441 stories use a real story.tsx specimen; 267 use raw args with no composition. Make specimen the required form for anything with children, schema the node DSL or delete it, and let the diagnostic gradient name the better form instead of silently accepting both.
  • Point the i18n and selector gates at the adopter. A gate that only reads library source will stay green forever while both seams are inert in all 35 consumers.
