Setup architecture review/ react-component-library/ 2026-08-31

The Reconciliation Tax

The component library is not hard to work in because the components are hard. It is hard because one fact about one asset is stored in six places, no single component owns making them agree, and twenty commands exist to repair them after they drift. That friction is why a library with 992 released versions reaches only 3.1% of the ecosystem's UI files. Sections 4–9 measure the faults. Sections 10–13 specify what replaces them, file by file.

01

What this is for

This scenario exists so that a designed, validated, accessible React component is authored once and then reused across every scenario in the ecosystem — and so that building a good UI stops being a per-scenario act of craft.

That is a mature product goal, and the machinery in this repo is proportionate to it: a catalog of declared intent, per-asset capability contracts, immutable releases, a version ledger, adoption tracking, and a validation matrix. None of that is over-engineering. A library that other teams pin against needs releases that cannot change under them, and a library that claims accessibility needs evidence rather than assertion.

So the question in this document is never whether this machinery should exist. It is whether the machinery is currently shaped so that using it is cheap. Today it is not, and there is one number that shows exactly what that costs.

The library has reached 36 scenarios but only 3.1% of the files in them. That is breadth without depth: most adopting scenarios import between five and thirteen components and hand-roll the rest. And 61 scenarios that have a UI import nothing at all — including agent-inbox (263 UI files), architecture-cartographer (237), agent-manager (168), app-monitor (168) and flow-verifier (167).

Those are not scenarios that decided against the library. They are scenarios where reaching for it was more expensive than writing a div. 3.1% is the friction, measured. Every fault in this document is worth exactly what it subtracts from that number.

What "done" means, in one sentence

An engineer or agent building any scenario UI reaches for a library asset by default, because finding it, adopting it, and improving it are each cheaper than writing the equivalent by hand — and improving it is safe, because the release they depend on cannot change under them.

02

The verdict

Every architectural problem in this scenario is the same problem wearing a different hat: a fact about an asset has no single owner.

“Button version 2.2.4 exists, and it depends on Icon” is written into the catalog declaration, the component manifest, the per-version dependency lock, the TypeScript import statement, the published package export map, and three SQLite tables. Six authorities. None of them derives from the others. When they disagree — and they disagree constantly, because they are written by different tools at different moments — the answer is not a rebuild. It is a repair command, chosen by hand, from a menu of twenty.

That is the reconciliation tax, and everything else follows from it. Gates exist to detect the drift. Repair commands exist to fix it. Allowlists exist to excuse the parts that cannot be fixed. Invariants exist to prove the allowlists are working. And an agent walking into this scenario has to learn all four layers before it can change one line of one component.

The good news is real and worth saying plainly: the pass that just landed fixed the two faults that were actively destroying value, and the residual faults are mostly too many copies rather than wrong logic. The work below is subtraction, not redesign.

04

Fault A — six authorities, one fact

A

Nothing derives. Everything is written independently, then reconciled by hand.

20 repair commands · 5 reconcile gates · 0 single source of truth

Take one sentence: Button 2.2.4 exists, and it depends on Icon. Here is every place that sentence is independently recorded.

How this reaches an agent

An agent changes one prop on one component. To land that change it must, in order: begin a draft (a new prerelease version directory), edit the TSX, regenerate the lock, republish, let the export map regenerate, let the hash ledger record the new bytes, let the DB mirror ingest them, and confirm the catalog declaration still matches. If any step is skipped or done out of order, a gate fires — but the gate reports the symptom (“graph not reconciled”) rather than the missing step. The agent then has twenty repair commands and no rule for picking one.

That is the loop where agents get lost, and it is why they reach for scripts. Faced with “the export map disagrees with the tree”, writing a small .mjs that walks the tree and rewrites the map is a shorter path than learning which of the twenty commands owns that edge. The scripts are a rational response to a missing derivation.

What it costs you Every asset edit is an eight-step distributed transaction with no transaction manager. The twenty repair commands are not tools — they are the manual rollback log for a commit that has no atomic form.

And the .mjs sprawl is not agents misbehaving — it is agents filling a hole the design left open.

Fault F — the front door still points at the scaffold

F

The first three documents an agent reads describe a freshly generated template with a notes demo, not a 163-component library.

Cheapest fault to fix. Possibly the most expensive one you are paying.

This one is not architecture, but it shapes every agent session, so it belongs in the same list. Here is what an agent actually encounters, in order.

README.md gives the real instruction — begin with components draft-begin, work only in the draft, never edit a released version directory — in one blockquote at the top. Then it spends the next 90 lines on template scaffolding: a section titled Placeholders vs. Durable Scaffolding, nine numbered “Working Rules” that must be satisfied before feature work, and a closing pointer to another scenario to see the same template shape taken to completion.

It names docs/START-HERE.md as the place to start. That document opens: “This is the first document to read after generating the scenario from the react-vite template. … do not start product implementation until the charter and requirements gates are complete.” It then instructs the reader to replace the notes domain, which has not existed in this scenario for months.

And docs/guides/asset-update-flow.md — the one document the README links for the actual editing loop, the single most important procedure in the scenario — is fifteen lines long and describes gate cache invalidation. It never mentions draft-begin, draft-publish, or the eight steps a change has to pass through.

Even .vrooli/testing.json still carries "description": "Sample testing configuration for React + Vite template", last updated 2026-05-03.

So an agent's first ten minutes are spent on orientation gates, a charter, a requirements registry, and a demo domain that does not exist — and it never receives a clear statement of the loop it is actually there to run. When it then hits an authority mismatch, it has no mental model to place the error in. It writes a script.

What it costs you Every agent session starts by learning the wrong thing. This is a two-hour fix that changes the baseline behaviour of every future session in the scenario.

The target, stated once

Two files per asset are written by a human. Every other file that mentions that asset is generated from those two, and can be deleted and rebuilt byte-identically.

That is the whole target. Everything in the next three sections is that rule applied to a specific file. If a future change cannot be justified by it, it is the messiness coming back.

The two authored surfaces are intent and implementation:

  • catalog/assets/<domain>/<asset>.json — what the asset is for, what it must be able to do, what it may depend on and why, the variant matrix it must offer, its signature moment. This file is already the best-designed artifact in the scenario. It does not need changing; it needs to become the only place those facts live.
  • The version directory — the TSX, its stylesheet, its strings, its stories. The implementation, and nothing else.

Everything else — the component manifest, the dependency lock, the story contract, the export map, the release-hash ledger, the provenance file, the SQLite rows and the byte mirror — becomes a projection with exactly one generator and no hand-editing.

The rule that tells an agent when a second copy is allowed

Not every duplicate is debt, and an agent needs to know the difference or it will delete something load-bearing. A second copy of a fact is legitimate only when the two copies mean different things — one is a requirement, the other is an observation — and a gate compares them.

The catalog saying Button must offer variants primary, secondary, ghost, danger and Button.tsx exporting BUTTON_VARIANTS is a contract: two different statements, with a gate asserting they agree. Keep it. The catalog and component.json both carrying a description field is duplication: the same statement twice, with nothing comparing them. Delete one.

11.1  Styling — author CSS in a file, ship it as a string

You were right to be suspicious, and also right that some assets genuinely need CSS. Here is what is actually in the tree today — four mechanisms, all live at once:

MechanismIn useCan express :hover, @media, ::beforeConsumer needs a CSS bundlerStatus
useLibraryStyleSheet(key, css)25 filesyesnothe documented target
import "./Asset.css"15 filesyesyesundocumented, mostly primitives
style={{ … }}1,961 sites / 71 filesnonothe actual debt
<style> in render output9 filesyesnobanned by gate

Decision — the .css file stays as the authoring format; the build inlines it into the module

Author Button.css as a real CSS file next to the component. At build time it is inlined into the emitted module as a useLibraryStyleSheet call keyed by asset and version. Nothing named .css ships in dist, and no consumer bundler needs to understand CSS.

Why this and not the two obvious alternatives
  • Not “keep importing .css” — the package is built with plain tsc, and a .css import is not a JavaScript module. Today that is papered over by a declare module "*.css" shim in library/css.d.ts, which silences the type error without making the import resolvable anywhere except a bundler that happens to handle CSS. That is a hidden requirement placed on every future consumer.
  • Not “write the CSS as a template literal in the TSX” — which is what useLibraryStyleSheet callers do today. It works at runtime, but it throws away syntax highlighting, Prettier, stylelint, and the ability to grep for a selector. That is precisely the kind of local convenience that makes a codebase feel hostile to work in six months later.
  • Inlining at build time gets both — real CSS authoring, and a published artifact with no bundler requirement. It also deletes css.d.ts, deletes the .css copy step in build.mjs, and lets one gate own the whole styling question.
The rule for inline styles

style={{ }} is for values genuinely computed at runtime — a measured width, a gesture-driven transform, a CSS custom property set from a prop. It is never for static appearance. Nearly all of today's 1,961 sites are static, and each one is a rule that a consumer cannot override and a theme cannot reach.

Unchanged from today

BaseStyles remains the single owner of the reset, focus ring, reduced-motion and forced-colors policy, and control sizing. Library-owned utility classes stay banned — and that allowlist is already empty, which is the one styling gate in this scenario that is fully enforced with zero exemptions. className and its siblings stay pass-through seams that the component never concatenates onto.

11.2  Stories — one authored module, one generated contract

Today story.json is a hand-authored contract that names export symbols inside a hand-authored story.tsx. Two files, both authored, referring to each other by string. 115 versions have the contract and no module; 27 have neither. Nothing type-checks the reference.

Decision — the story module is the only authored story artifact

Each story becomes a typed export that carries its own metadata beside its render: the args, the expectations, the role, the mode. story.json stays — roughly fifteen Go call sites and the preview iframe consume it as a runtime contract — but it becomes a build output, not a source file.

Why
  • The story's args must type-check against the component's props. A JSON file cannot do that, so today an args field can name a prop that no longer exists and nothing notices until a preview renders wrong.
  • It is one file to write instead of two kept in sync by hand, which is the same derive-don't-duplicate rule applied at asset scale.
  • It is the shape every mature React component library converged on, for exactly this reason. Choosing it also means a future contributor recognises the format instead of learning a house one.
The migration this replaces

The story.tsx rollout is sitting at 51% and has been for a while. This is the same migration with a defined finish line: when every version has a story module, story.json stops being writable and the ambiguity is gone.

The house rules, for the plan and for every agent that follows it

Short enough to paste into a prompt, and specific enough to catch the actual failure modes observed in this scenario.

Always

  • Change intent in the catalog declaration; change behaviour in the TSX. Those are the only two files you write.
  • Regenerate derived files with the one generator, and commit its output unread if it is deterministic.
  • Work inside a draft version directory. A released version's bytes are frozen.
  • Put a new fact in exactly one file, and let a gate compare it to anything that must match.
  • Make a failing number visible. An honest red is worth more than a manufactured green.

Never

  • Write a script to reconcile two files. If they can disagree, one of them should not be authored — fix that instead.
  • Add an allowlist, exemption list, or baseline file that lowers a count. Annotate the count; do not reduce it.
  • Pin a gate's floor to the value it currently measures. That is not a floor.
  • Add a per-asset special case to gate code. If one asset does not fit the shape, the asset is wrong, not the shape.
  • Create a .mjs outside the one declared home, or leave a probe script in docs/.
  • Hardcode a measurement, or read one from a committed file.

The path from here

Ordered by friction removed per unit of work. The first three are the ones that make the library feel different to work in.

Each carries a one-line acceptance test, because the failure mode of this scenario has always been work that is declared done and reconciled by hand afterwards. The what for each of these lives in Sections 10–13; this is only the order.

Make five of the six authorities derived

Section 10 is the shape. The catalog declaration and the TSX are the only files anyone writes; the lock, the story contract, the manifest, the export map, the ledgers and the DB rows all become projections regenerated by one idempotent command. This is the change that deletes the reconciliation layer — the twenty repair commands exist only because nothing regenerates. Start by making the generator total and provably idempotent, then delete the repair commands it makes unnecessary, one at a time.

TEST  Delete every dependencies.json, the export map, and the DB rows. Run one command. The tree is byte-identical to before.

Declare one asset shape and migrate the corpus to it

Section 11 is the canonical directory, including the styling and story decisions with their reasoning. Land the shape first as a gate over new work, so nothing can be added outside it while the backlog is migrated. Then finish the migration that stalled at 51% — convert the 115 json-only stories, author the 27 missing ones, converge the four styling mechanisms on the one in Section 11, and move the preview harnesses out of the asset tree. This is what actually removes the special cases, and it removes them from the corpus rather than from the gate code.

TEST  ls any two version directories and the file sets match. A shape-census gate holds it at one shape.

Rewrite the front door before anything else lands

README and START-HERE.md should open with the asset loop and nothing else. asset-update-flow.md becomes the real eight steps, with the failure mode and the exact recovery for each. Delete the template prose, the notes references, and the orientation-gate ceremony — this scenario is years past generation. Cheapest item on this list, largest effect on agent behaviour.

TEST  An agent given only the README edits a component and publishes it without reading another file.

One specifier parser, one tree walker

Collapse the seven Go regexes and the JS classifier into one Go function and one JS function that share a declared grammar. Replace the sixty-seven ad-hoc walk sites with one library.Walk() that owns the exclusion list. Mechanical, low-risk, and it retires a whole category of “one gate sees it, another doesn't”.

TEST  Grepping api/internal for the package name returns exactly one regex.

Give the JavaScript tooling one home, and batch the process spawns

Declare a single directory for node tooling; leave only Vite plugins under ui/scripts/; delete the two abandoned probes in docs/reports/. Then stop spawning one node process per file for AST facts — the --facts-root batch mode already exists. And no blocking gate should ever invoke vite build.

TEST  A cold full matrix spawns a bounded, countable number of subprocesses that does not scale with asset count.

Make the instrument falsifiable

Delete or implement I12, I13, I16 and I20. Compute the timings live instead of reading a committed file. Retire population-decisions.json and let I19 report the true 224, with a target you are actually driving down — an honest failing number is worth more than a manufactured zero. Same for self-hosting-policy.json: a floor pinned to the current value is not a floor.

TEST  Introduce a known defect of each invariant's kind and confirm the report goes red for that invariant and no other.

Prove it by adoption, not by a green matrix

The whole point of the six moves above is the number in Section 1: 3.1% of ecosystem UI files. So the last move is to measure the thing the work is for. Pick the three largest scenarios with zero adoption — agent-inbox (263 UI files), architecture-cartographer (237), agent-manager (168) — and adopt the library into each, keeping a log of every moment the loop was harder than writing a div. That log is the next backlog, and it is worth more than any gate reading green.

Add an adoption-depth invariant to the corpus report — library imports as a share of ecosystem UI files — and put it at the top of the report. It is the only number in the instrument that measures whether the library is doing its job.

TEST  A scenario team adopts a component without asking anyone how, and the friction log from the three pilots is empty by the end.

One last signal

There are 44 plans in the plan store whose slug begins with react-component-library or rcl-. Each was a real attempt at a real fault, and the most recent ones genuinely landed. But forty-four plans against one scenario is itself the measurement: the faults keep coming back because each pass fixed a projection rather than the thing being projected. Move 1 on this list is the first one that changes that.
