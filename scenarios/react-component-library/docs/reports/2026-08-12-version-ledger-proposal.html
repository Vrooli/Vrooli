A version history that has no history

Every one of the catalog's 264 versions is stamped with the same three-second window — the moment of the last reindex. The evidence that would show progression across versions is either overwritten on every run or piled into a 57 MB table that nothing can read. This is what's broken, and what the repaired system looks like.

0 versions with a real creation date, of 264
32,059 test reports stored; newest 30 per asset are readable
57MB of an 84 MB database, in one unpruned table
65 versions retirable today — no adopter, no dep pin
0 CLI verbs that retire, archive, or delete a version

Root cause

The reindex destroys the timeline

Git holds the versions; SQLite is a projection rebuilt by components index. The rebuild is a delete-and-reinsert, so every row is restamped with the clock at rebuild time. There is no column that survives it.

Measured, not inferred

MIN(indexed_at) = 2026-08-12T15:54:48.189Z, MAX(indexed_at) = 2026-08-12T15:54:51.279Z across all 264 rows — a 3.09-second spread. released_at is empty on every one. Because the list sorts by indexed_at DESC, id ASC and the timestamps tie, markdown-renderer's 17 versions return in UUID order: 0.2.2-draft.1, 0.2.0-draft.1, 0.2.2, 0.3.2, 0.1.0… The UI labels that list “newest first.”

Second failure

Five signals per version, four dead ends

Each version already generates real quality evidence. None of it accumulates into something you can plot. Gate verdicts are overwritten in place; test reports pile up faster than they can be read; adoption is stamped per version but never grouped by it.

What is actually growing

Not the versions — the evidence about them

The entire library/ tree — 192 manifests and 275 version folders — totals 8.1 MB, and their indexed content is 2 MB of the database. The instinct that the scenario grows because we keep adding versions is understandable but wrong. Growth comes from ValidateScenario, which runs all ~180 assets on every test-genie component-tests phase and persists one report row each.

Retirement pressure — 264 indexed versions

181 pinned as latest 18 older, still referenced 65 retirable — no adopter, no dep pin, no provenance

That 65 is computable today in one query. What's missing is any command that runs it and anything that would let you retire the result safely. There is no versions delete, prune, or archive verb; deprecatedVersions[] is honoured by the indexer but sits empty in all 192 manifests; and .vrooli/service.json declares data/ as regenerable: false with a rationale that explicitly forbids automatic deletion — so storage-manager's cleanup is locked out by design and nothing replaced it.

Target end state

Versions become deletable because the record doesn't live in them

The goal isn't to keep every version forever — it's to make retiring one cost nothing. A ledger row keyed on library_id + version holds the measurements; the folder holds the code. Delete the folder, keep the data point. 

-- The one new table. Everything else in the plan feeds or reads it.
CREATE TABLE version_ledger (
  library_id        TEXT    NOT NULL,   -- survives component_id reassignment
  version           TEXT    NOT NULL,
  created_at        TEXT    NOT NULL,   -- backfilled from git, never restamped
  released_at       TEXT    NOT NULL DEFAULT '',
  retired_at        TEXT    NOT NULL DEFAULT '',   -- set when the folder is reclaimed
  lifecycle         TEXT    NOT NULL,   -- draft|released|superseded|deprecated|archived|retired
  gate_pass         INTEGER NOT NULL DEFAULT 0,
  gate_fail         INTEGER NOT NULL DEFAULT 0,
  test_runs         INTEGER NOT NULL DEFAULT 0,
  test_pass_rate    REAL    NOT NULL DEFAULT 0,
  adoption_peak     INTEGER NOT NULL DEFAULT 0,
  adoption_current  INTEGER NOT NULL DEFAULT 0,
  file_count        INTEGER NOT NULL DEFAULT 0,
  loc               INTEGER NOT NULL DEFAULT 0,
  dep_count         INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (library_id, version)
);

On “Tests” vs “Stats”

In addition to, not instead of. The Tests tab is a run-and-inspect workflow with real product value — the measures-adoption skill is explicit that you don't gut an operator surface to clear a maturity rung. What's missing is a sibling view that reads the ledger and plots change across versions, including versions whose code no longer exists.

Execution

Six phases, one hard dependency

Numbered because the order is real, not decorative: nothing downstream of phase 1 can be validated without a truthful timeline. Phases 2 and 3 then run in parallel. Each phase carries the check that proves it landed.

1

Version identity and time

blocks 2–6

Give versions a creation date that survives the reindex, and an order that means something.

  • Add created_at; replace the DELETE+reinsert at components/sqlite.go:100 with ON CONFLICT DO UPDATE preserving it
  • Populate released_at when a version becomes latest
  • Add a semver comparator; order lists by it instead of indexed_at DESC, id ASC
  • One-shot backfill of all 264 rows from git history
  • Decide the second-writer question: versions.Record plain-INSERTs into a table with UNIQUE(component_id, version), so a content edit without a @version bump throws and is swallowed

Proves it: 264 rows with distinct, git-correct created_at; markdown-renderer's 17 versions return in semver order; a reindex leaves both unchanged.

2

Version-scoped gate evidence

after 1 · parallel with 3

Stop overwriting the only signal that answers “are issues increasing or decreasing?”

  • Re-key catalog_gate_evidence to (asset_id, target, gate, version); append instead of upsert
  • Retain generously — 955 rows per sweep across 12 gates is cheap
  • Keep source_revision so a re-run at the same version is distinguishable from a new one

Proves it: two gate sweeps at different versions leave two rows, not one; the earlier verdict is still queryable.

3

Test-report retention and rollup

after 1 · parallel with 2

Convert 57 MB of unreadable blobs into a bounded table plus a durable summary.

  • Retain newest N per (component_id, root_version), plus the first pass and first failure per version
  • Roll evicted rows into per-version counters before deleting them — no verdict is lost, only its payload
  • Add a version filter to ListComponentTestReportsRequest so the Tests tab stops mixing versions in one history list
  • Add both tables to docs/concepts/DATA.md; neither is in the ownership map today

Proves it: table stays bounded across ten validation runs; pass/fail totals computed pre- and post-eviction match exactly.

4

The version ledger

after 2 + 3

One durable row per version that outlives both the reindex and the folder.

  • Create version_ledger keyed on library_id + version
  • Project into it from gate evidence, test rollups, adoption, parity, and the manifest
  • Make projection replayable so the ledger can be rebuilt from retained facts

Proves it: delete a version folder, reindex, and every ledger field for that version still reads back — the acceptance test for cleanup-without-loss.

5

Adoption rollup and retirement verbs

after 4

Make the 65 visible, then make them safe to act on.

  • GROUP BY adopted_version on AssetMetrics; expose per-version adoption on the wire
  • versions retire-candidates — ship the orphan query as a command
  • Lifecycle verbs: deprecate, archive, retire; wire the unreachable VersionStatusArchived rung
  • Revisit the regenerable: false declaration in .vrooli/service.json now that eviction is safe

Proves it: the command surfaces 65 candidates; retiring one reclaims the folder, sets retired_at, and leaves the chart intact.

6

Measures and the Progression surface

after 4 + 5

Only now is there a substrate worth declaring measures over.

  • Declare catalog.version_count, catalog.retirable_versions, adoption.by_version, quality.gate_pass_rate — questions the scenario already owns
  • Clear the four measures.undeclared-substrate warnings; cli/manifest.json has zero measure blocks today
  • Ship the Progression tab reading the ledger, retired versions included
  • Consider the v1/domain/ move that retires the measures.domains[] fallback advisory

Proves it: measures-health validate scenario react-component-library reports provider maturity unblocked with no new waivers.

Before phase 1

Four calls I'd like you to make

Each changes the shape of the work rather than its size. My recommendation is on each card; none of them blocks starting phase 1.

Backfill source for created_at

Git history gives true dates but costs a walk over 275 folders. File mtime is instant and wrong.

Recommend: git, once, offline. It's a one-shot cost for a column read forever.

Retention depth N

Keeping 10 reports per version puts the table near 2,600 rows. Keeping 3 puts it near 800.

Recommend: 5, plus first-pass and first-failure pinned. Bounded, and keeps enough to spot flake.

Who owns retirement

An RCL-local verb, or a policy registered with storage-manager whose cleanup is currently locked out by regenerable: false.

Recommend: RCL-local. It needs catalog semantics — adopters and dep pins — that a generic file sweeper can't see.

Retire the 65 now or after phase 4

They're safe to delete today, but doing it before the ledger exists throws away their history permanently.

Recommend: wait for phase 4. The whole point is that retiring stops being lossy.
