The Bypass Deadlock

The lock-driven setup plan did real work — five of its seven mechanisms are materially closed. The one that isn't produces everything you have been experiencing, and this morning it took the scenario down.

Live state at time of writing

react-component-library is stopped and cannot start. vrooli scenario start fails at build component ui after 64 seconds with 63 lint errors across four files. All four belong to three assets created on disk between 01:00 and 01:26 this morning. None of the three has a publish record. Because the gate CLI requires a running API, no gate report can be produced to diagnose it.

What this review is

The plan landed. The loop did not close.

Yesterday's pass authored a sixteen-phase plan against seven named mechanisms and marked fifteen phases done. I re-measured every claim in its own end-state table against the tree as it stands today rather than trusting the phase markers.

Most of it is honest. .build-source is gone. The three per-component build patches are gone. The 36 bespoke composition cases — 569 KB — are gone, and no BAS case names a component or a version. 19 MB of committed generated artifacts is untracked. 483 per-version dependency locks exist where none did. The package no longer reaches into scenarios/**. The new Node tooling is genuinely well built, with explicit guards against vacuous green results.

What did not close is the third mechanism: the draft lifecycle exists and is bypassed. Phase 6 was marked done. In practice the flow has never been used — 459 of 462 provenance records are backfills, and there are three real publishes in the entire corpus. Everything below follows from that.

The mechanism

A cycle, not a bug

Each step is individually reasonable. Together they form a loop that converts one unvalidated file into a dead scenario and a blind agent.

Step one · free A version is created by writing to the filesystem mkdir versions/1.0.0 — unguarded.
Immutability is enforced in api/internal/components/service.go, which only sees API writes.
Step two · skipped Publish validation never runs PublishComponentVersion calls CheckComponentVersion and refuses on failure. The filesystem calls nothing. Both produce a latest.
Step three · frozen The unvalidated version becomes immutable IconGeometry@1.0.0 is latest in its manifest, has no provenance row and no released-version hash — yet is treated as released source.
Step four · blast radius Corpus lint runs inside the app build build → type-check → catalog:check → lint:catalog → eslint over every version of every asset.
Step five · dead The app build runs inside scenario start vrooli scenario start → setup → build component ui → exit 1. One bad asset, no scenario.
Step six · blind Every gate command needs the API that will not start "react-component-library is stopped, so its local API is unavailable." 45 gates unreadable at the exact moment they are needed.
Step seven · flail With no diagnostic surface, config becomes the only lever Edit eslint config, add a disable, write a script to find out what broke — the observed behaviour, and the locally rational move.
Step eight · reset The repair is written to the filesystem too The draft flow is still the expensive path and still needs the API. The loop re-enters at step one.
↺ Step eight returns to step one. Nothing in the cycle is load-bearing on a person noticing.

What remains

Five structural problems

The first three are the loop. The last two are why the setup stays expensive even when nothing is broken.

One

The correct path validates. The free path does not. Both produce a release.

This is the deepest defect and it is a one-line asymmetry. Publishing runs a check and refuses on failure. Creating a directory runs nothing. The manifest's latest field does not care which route produced it, so an unvalidated version is indistinguishable from a released one the moment it lands.

The plan's Phase 6 answer was a blocking gate. A gate is a report, and it arrives after the fact, through an API that is down precisely when a bad release has been made. Prevention has to sit at the write, not at the read.

Two

Corpus conformance lint sits on the critical path of process start.

build runs type-check, which runs catalog:check, which lints every version of every asset under strictTypeChecked. That build is a setup step of vrooli scenario start. The consequence is that a lint error in any one of 493 version directories is not a red gate — it is a scenario that will not run, a UI you cannot open, and 45 gates you cannot read.

A conformance failure and an inability to boot should not be the same event. The scenario should start with a red gate and tell you which asset is red.

vrooli scenario start
  → setup → build component ui
    → pnpm build → pnpm type-check → catalog:check
      → lint:catalog → eslint over library/**
✗ 77 problems (63 errors, 14 warnings) → exit 1 → scenario stopped

Three

Immutable source is judged by a mutable, type-aware ruleset.

eslint.catalog.config.js applies tseslint.configs.strictTypeChecked to all 493 versions, released ones included. Those rules are type-aware: no-non-null-assertion, no-unnecessary-condition and no-deprecated resolve against the current TypeScript, the current @types/react, and the current dependency graph.

So a frozen version's verdict is not frozen. Bump a type dependency and green releases turn red with no source change — and they cannot be repaired, because they are immutable. Today's failure is the mild version of this; the severe version arrives on a toolchain upgrade and hits dozens of assets at once. An immutable artifact should carry an immutable verdict, recorded when it was published.

rules firing today: no-non-null-assertion 57 · no-unnecessary-condition 3 · no-deprecated 3
all three are type-aware and none can be evaluated from the source bytes alone

Four

root has no single meaning, and a wrong root reads as clean.

resolveScenarioRoot accepts three different things — a library/ directory, a scenario root, or the repository root — and guesses which by probing the filesystem. Meanwhile 59 call sites hardcode filepath.Join(root, "scenarios", "react-component-library", …) against only 16 that use the resolver.

The residue is on disk: a self-nested scenarios/react-component-library/scenarios/react-component-library/tmp/ proves the two conventions have already collided. The dangerous version is quieter — 24 gate globs discard their error, so a wrong root yields Inspected: 0, no findings, and a pass. That includes ValidateDependencyRank, the plan's own new gate for the Doctrine 3 rank rule.

59 × filepath.Join(root, "scenarios", "react-component-library", …)
16 × resolveScenarioRoot(root)
24 × filepath.Glob with a discarded error → empty result → Result{Inspected: 0} → clean

Five

Validation logic has five homes and no rule for choosing one.

Roughly 16,600 lines of validation machinery serve 158 components, spread across Go gates, Go coverage, Go one-off commands, two separate scripts/ directories of .mjs, custom ESLint rules and BAS JSON. Nothing states which home a new check belongs in.

That is the direct answer to the .mjs proliferation you have been watching. An agent needing a new check finds two plausible script directories and a Go package it would have to rebuild and restart to exercise. Writing a fresh .mjs is the cheapest move that looks correct — and it is, locally. Twenty-five of them now exist.

Sequence

What to do, cheapest first

The order matters here: the first three turn the loop off, the last three stop it forming again. Nothing below changes a component.

Turn the loop off
Minutes · unblocks everything else

Republish the three assets through the flow that would have caught them

IconGeometry, MorphingIcon and IconButton are latest with no publish record. Re-entering them via components draft-begin and draft-publish runs CheckComponentVersion, fixes the lint, and produces the corpus's fourth, fifth and sixth genuine publishes — which is also the first real exercise the flow has ever had.

Small · removes the blast radius

Take corpus conformance lint off the scenario-start path

Move catalog:check out of build and into check and the test suite. A conformance failure should make a gate red and leave the scenario running, so the gate report stays readable exactly when someone needs to read it.

Small · closes the bypass

Make the filesystem route refuse, not just report

A version directory that appears without a provenance row should fail at the write or at the earliest read that owns it — not only inside a gate that needs a running API. The asymmetry between the two creation routes is the single defect that generates the rest.

Stop it forming again
Medium · one design decision

Freeze the verdict with the bytes

Record each released version's conformance result at publish time and stop re-linting frozen source under a moving ruleset. Re-lint drafts, and assets whose lock changed. This also removes most of the corpus lint cost, and it removes the class of failure where a dependency bump breaks assets nobody can edit.

Medium · mechanical

Give root one meaning and make empty scans fail

Resolve the root once at the process boundary and pass a single named type onward, retiring both conventions. Then make a gate that inspected zero items report unavailable rather than clean — the vacuous-green guard the Node tooling already has, which the Go gates do not.

Larger · the remaining speed win

Teach the other 43 validators to accept a scope

The per-asset staleness index already computes the right answer; only ValidateTypesForAssets consumes it. Until the rest take a scope, editing one component still runs 44 gates at full corpus cost, and the feedback loop stays flat no matter how small the change.
