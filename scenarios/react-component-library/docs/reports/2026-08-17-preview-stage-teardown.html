React Component Library Preview pane teardown measured 2026-08-17

The preview pane gives your component 648 pixels — on every monitor.

At a 1600×1000 browser window, the component preview iframe occupies a quarter of the screen, and the component inside it renders into a box 648 px wide. Widen the browser to 2560 px and that box is still 648 px wide; the extra 960 pixels become empty gradient. This is not a spacing bug that a few Tailwind classes fix. Six independent layers each take a cut of the same space, and the last one hard-caps what survives.

Vertical budget

Nine stacked bands, one of which is the thing you came to look at

Every piece of chrome in the preview is a sibling of the preview, laid out in the same vertical flow. The workspace header, the asset tabs, the preview toolbar, the readiness line, the specimen card header, and the tools panel all claim their height first. The iframe gets the remainder. Horizontal budget

The width waterfall ends at the same number no matter where it starts

The vertical squeeze is annoying. The horizontal one is the part that makes the whole feature not work, and it happens on the API side where the UI's viewport controls cannot reach it. api/handlers/preview/static.go wraps every standalone component in a .rcl-preview-well whose width is min(100%, 760px), with clamp(24px, 5vw, 56px) of padding, inside a .rcl-preview-specimen with clamp(24px, 6vw, 80px) more.

That is a hard ceiling. Nothing in the toolbar — not the viewport preset, not the zoom, not Framed, not Stage — can raise it.

Diagnosis

Seven causes, none of which is "the padding is too big"

These are grouped by what kind of mistake they are, because the fix differs by class. Anything tagged LAYOUT or HARNESS is structural — a redesign has to change it. The rest are defects that a redesign would inherit if it were built on top of the current code unchanged.

Layout

The preview is a paragraph in a document, not a stage with a frame around it

Header, tabs, toolbar, status, card header, preview, tools, and mobile actions are all siblings in one column. The preview's size is defined as subtraction: whatever the other eight leave behind. There is no layer in the tree where the preview surface owns the box and the controls composite on top of it. Every future control anyone adds will come out of the preview's height, forever.

ComponentEditorController.tsx — the toolbar <div> and <ComponentEditorStage> are consecutive children of the same flex column.

Layout

Chrome scales with the component; the preview doesn't

The story picker is a flex-wrap nav sharing a row with eight other controls. Button declares 16 stories, so the chips take a second row and the preview shrinks by ~52 px. The size of the preview is a function of how many stories the author wrote. That coupling should not exist at all — a story switcher is navigation, and navigation belongs in a menu or a palette, not in the layout flow.

Measured: DashboardPage (8 stories) → 332 px iframe. Button (16 stories) → ~304 px.

Harness

The API decides how wide your component may be, and the UI can't argue

wrapStandalone puts every component-kind story inside .rcl-preview-specimen → .rcl-preview-well. The well is width: min(100%, 760px). That cap is a reasonable default for a Badge and actively wrong for a DashboardPage, a CommandCenterShell, or a CollectionPage — and the harness applies it to 118 of 129 components, because only 11 declare a frame that routes around wrapStandalone.

api/handlers/preview/static.go lines 232–257 and 796–807; frame declarations counted across library/components/**/story.json.

Sizing

Fixed constants stand in for measuring the pane

aspectRatio: "16 / 9" on the iframe. 760px for the well. 1280×720 at zoom 1 for the Desktop stage. 280 for the tools panel. clamp(…, 80px) for specimen padding. Each is a guess made without knowing the component or the container, and 16 / 9 is the worst of them: it makes iframe height a function of pane width, so narrowing the window shortens the letterbox instead of reflowing the content.

fitToPane is the one measurement that exists, and it is capped Math.min(1, …) — it can only shrink, never enlarge, so a 390×844 mobile preview can never grow to fill a big pane.

Scroll

Three nested scroll containers, and the status text scrolls with the content

EmulatorViewport's frame is overflow-auto, the gallery div inside it is overflow-auto, and the resizable Panel wraps both. Nobody owns the scroll. In Stage mode you get vertical and horizontal bars at once, and because the readiness line and the card header are children of the inner scroll box, they slide out from under the toolbar and float over the specimen instead of pinning.

Visible in the AppShell capture above: "1 of 2 stories ready" sitting at mid-stage; "Workspace" clipped at the top edge.

Modes

Four modes, each half-implementing the thing its name promises

Gallery filters down to exactly one specimen and then renders it into grid-cols-[repeat(auto-fit,minmax(20rem,1fr))] — a multi-column gallery grid that only ever holds one card. Stage opens a device box larger than the pane. Framed is a visible primary-styled toggle that does nothing for 91% of the catalog. Full screen targets previewCanvasRef, which is only attached when stageMode && isActive; the fullscreenchange handler then reads state back from that same null ref, so entering full screen from Gallery resolves the flag to false while the element is genuinely fullscreen.

Same class of bug in Stage's auto-collapse: the effect calls previewToolsPanelRef.current?.collapse(), but the Panel only mounts once activeSpecimen is set — on first paint the ref is null, so the state says collapsed while the panel is open, and the first click on the chevron does the wrong thing.

Axis

Space is spent on the axis that's scarce and hoarded on the axis that's free

The tools — props, inspector, events — are a full-width band costing 300 px of height, which is exactly what a page-shaped component needs most. Meanwhile the library rail keeps 340 px of width mounted on the Preview tab, where you are looking at one component and not browsing. Widescreen monitors have width to spare and never enough height; this layout has it backwards on both counts.

None of the preview's own state survives a reload either — stageMode, frameEnabled, previewKit, and tools-collapsed are all unpersisted, while split layout and the asset tab are saved.

Prerequisite

Three fixes every option below depends on

These are geometry-independent. Ship the most beautiful shell you can imagine and the component still renders at 648 px until they land.

  1. Make the harness wrapper conditional. wrapStandalone's well is a presentation choice for small components. It should be requested by the host (a query param or a per-archetype default), not applied unconditionally to everything that isn't frame-declared. Unwrapped, the component fills the iframe and the iframe fills the stage.
  2. Delete aspectRatio: "16 / 9". The iframe should be height: 100% of a stage that is itself sized by the pane. Height must stop being derived from width.
  3. Give one element the scroll. The stage scrolls; the toolbar, readiness state, and card header live outside it. That alone fixes the clipped header, the drifting status line, and the double scrollbars.
Second problem

The specimen isn't alive, and that's a different bug from the space

Space was the question I was asked to look at. But "I can press the Button, yet most components don't actually do anything" is a separate failure with its own causes — and giving the preview the whole viewport does nothing for it. Worth treating as a parallel workstream.

The core of it: the library is built from controlled components, and the preview has no state owner. VoiceInputButton takes state as a prop (idle / preparing / recording / …) and emits onStart, onStop, onPrepare. It does not own a microphone; there is nothing in it to "use". Clicking it fires the callback into postPreviewEvent, which appends a line to the Events log. Nothing writes back to props, so the visual state cannot change. That is a correctly-built component meeting a harness that treats every story as a static snapshot.

Your own caveat is the design key here. You said a loading-state story shouldn't have its state auto-advance away — exactly right, and it means the answer is not "make everything live". It means pinned versus live should be a declared property of the story, not an accident of whether someone happened to write a story.tsx. A pinned story freezes props and logs callbacks, which is what the expect checks need to run against a deterministic snapshot. A live story owns state and closes the loop. Both are legitimate; today the distinction is implicit and invisible.

On terminology, since you asked: the words this system actually uses are story (a named specimen with declared args) and story contract (the story.json that holds them). "Variant" isn't a term here.

What this workstream actually is

  1. Declare pinned vs live per story. Make the distinction explicit in the contract instead of implicit in whether a story.tsx exists. Pinned keeps deterministic expectations; live closes the loop.
  2. Extend fixture injection to component stories. The contract grammar and the server-owned adapter allowlist are the right design — they just stop at hooks. Components need the same injection, delivered as props or context.
  3. Grow the adapter registry past one. voice-input is the only adapter. Audio, file/image attach, clipboard, geolocation, and network are the obvious next ones, and each is a sandboxed mock, not a real device.
  4. Backfill args.fields. 116 contracts declare none, which is why the props panel is empty more often than not. Teach the panel structured and array too, or stop declaring kinds it will drop.
  5. Decide separately whether real device access is ever wanted. If yes, that's an allow attribute plus an origin decision — a different conversation from mocking, and worth not conflating.
Redesign options

Four independent decisions, not four competing plans

Read these as layers, not as a menu. Each one answers a different question, so they compose rather than compete — you can take all four, and the recommended sequence at the end of this page does exactly that.

There is one real dependency: Fit Canvas contains Overlay Stage. A pan-and-zoom canvas with 316 px of stacked bands above it defeats its own purpose — the zoom pill and icon rail are overlay chrome by another name. So Overlay Stage is not an alternative to Fit Canvas; it is the first half of it.

And one fork — now settled. The question was whether the terminal state is a single-specimen stage or a multi-specimen canvas. The answer is both are views we support: single-specimen focus as the default (and the right default on mobile), multi-specimen when you want to see variants or sizes together.

That answer is cheaper than it sounds, and it flips my earlier recommendation. If both are views, do not build two systems — a single-specimen stage is a canvas with one item and fit locked. Build the canvas substrate once and make focus view a preset of it. Building Overlay Stage as a standalone geometry first would mean writing the sizing logic twice.

Overlay Stage

Axis: chrome Load-bearing — do this one properly, once Medium build

The preview surface becomes the layout root of the pane — position: absolute; inset: 0 — and every control becomes something that floats over it. Nothing is a sibling any more, so nothing subtracts.

  • One floating dock, bottom-centre, holding viewport, zoom, theme, and mode. It dims after a few seconds of idle and wakes on pointer or focus. H hides it outright.
  • The story switcher leaves the layout entirely — a command-palette-style picker (⌘K, or a dropdown in the dock) that lists stories with descriptions. Sixteen stories no longer cost the preview a single pixel.
  • Props and inspector become a right slide-over, resizable, dismissible, remembered. They take width (plentiful) instead of height (scarce), and they're closed by default.
  • Full screen stops being a mode. It's the same layout with the app shell hidden — one boolean on the shell, no second rendering path, no ref to get wrong. The bug in the current implementation cannot recur because there is nothing to re-implement.

Fit Canvas

Axis: geometry Settled — build this as the substrate Focus view is a preset of it

Stop trying to make the device box fit the pane; make the canvas scale to the box. The stage becomes a pan-and-zoom surface — the Figma model — where specimens render at true CSS pixels inside real device frames and the view auto-fits on mount and on every resize.

  • Fit scales up as well as down. Removing the Math.min(1, …) cap in fitToPane is the whole unlock: a 390×844 phone preview can fill a 27-inch monitor at 180%, which today is impossible.
  • Multi-specimen becomes spatial. All 16 Button stories tile on the canvas at once — the gallery the code already claims to render but never does. Version comparison stops being a special two-up mode and is just two frames side by side.
  • Multi-viewport in one glance. Mobile, tablet, and desktop frames of the same story, laid out together, is the strongest possible answer to "does this component respond".
  • Chrome is a thin icon rail plus a floating zoom pill; the canvas keeps the rest.

Own Route

Axis: host Fastest win Small build

The preview stops being a tab inside a detail page inside an app shell. Give it /assets/:id/preview — a chromeless full-window surface with no rail, no workspace header, no asset tabs — plus a pop-out that opens it in its own window.

  • Removes 340 px of width and ~106 px of height by construction, before any layout work at all.
  • The Preview tab keeps a compact live thumbnail and an Open preview action, so the detail page stays a detail page.
  • You get a shareable preview URL for free — linkable from bug reports, embeddable in other scenarios, usable as a second-monitor workflow while you edit source in the first.
  • Composes with Overlay Stage rather than competing with it: the route needs a chrome model, and Overlay Stage is it.

Archetype Stages

Axis: policy Lands independently, in any order Medium build

The catalog already knows what kind of thing each asset is — slot (ui-primitive, ui-pattern), assetKind, and whether a frame is declared. Stop applying one geometry to all 129 components and let the archetype pick the stage. This is what replaces the fixed constants with something defensible.

  • Primitive → small centred well, and every story tiled at once. A Button page should show all 16 variants; that is the useful view, and it happens to be the one the current grid was written for.
  • Pattern / composite → wide fluid stage. No well, no width cap, no forced centring.
  • Page / shell / frame → edge-to-edge device stage, fit-to-pane by default, tools collapsed on entry.
  • Overlay / dialog → a viewport-sized stage so position: fixed behaves the way it will in production.
  • Kills the incoherent Framed toggle: framing becomes a property of the archetype and its declared frame, not an always-visible button that is inert for 91% of the catalog.

Recommendation

What I'd actually do, in order

Revised against four settled decisions: both stage and canvas are supported views (focus is the default), fully interactive, archetype-resolved wrapper with a per-story override, and commit straight through the shell rather than staging the validation. Two of those move work earlier and one removes a whole build step.

First

The floor, now including archetype resolution. Delete the 16 / 9 aspect ratio, give one element the scroll, and make the specimen wrapper an archetype-resolved default with a per-story override. Choosing archetype resolution over a host query param is what pulls Archetype Stages forward out of step four — it is no longer a later refinement, it is how the wrapper decision gets made at all.

Then

Canvas substrate with overlay chrome — one push. Because both views are wanted, these stop being two steps. The canvas owns sizing; focus view is the canvas with one item and fit locked; the dock, story palette, and slide-over are the chrome for both. Build the sizing logic once. Full screen falls out for free, since overlay chrome makes it a shell-visibility boolean rather than a second rendering path.

Then

Own Route. Now purely a host for the surface you already built — the cheapest step rather than the risky one, and it can't be mistaken for the fix because the fix already landed. Brings the shareable preview URL and the second-monitor workflow.

Parallel

The fidelity workstream. Pinned-vs-live declaration, fixture injection for component stories, an adapter registry past one entry, and backfilled args.fields. This shares no code with the geometry work and answers a complaint the geometry work cannot touch — it can run alongside from day one.

One consequence of combining fully interactive with canvas that's worth designing for up front: at any zoom other than 100%, wheel and drag are ambiguous. Scrolling could mean zoom the canvas or scroll inside the specimen; dragging could mean pan or interact. Figma resolves this with an explicit mode; the equivalent here is an enter specimen affordance — click to focus a frame, wheel and pointer go to the component, Esc returns to canvas navigation. Decide this before the canvas exists, because retrofitting it means re-plumbing every pointer handler.
