The Cold Version Tier

Two-thirds of the tracked library tree is superseded history that nothing reads. The bytes to fix it already exist somewhere untracked — what's missing is a verb between “relabel” and “delete”.

measured 2026-08-26 606 versions · 151 components 395 adoptions · 35 scenarios

Across every consecutive version pair in the library, ~91% of the bytes in a new version folder are a verbatim copy of the folder before it. The tree stores full snapshots of every release, inside a repository whose entire job is storing full snapshots of every release. You are paying for history twice, and only the second copy is diffable.

The cold band is 246 version folders, 875 files, 65,710 lines across 136 components — 188 already labelled deprecated, 58 still labelled released. This is not an estimate: it is exactly what react-component-library versions retire-candidates returns today, after the reference graph clears adopter pins, adoption files, manifest dependency pins, and source imports. They are in the working tree because publishing put them there and nothing has ever taken them out.

Why it accretes — the missing verb
CommandWhat it does todayBytes in the treeReversible
version-publish Writes a complete new folder, copying the previous version forward +1 full snapshot — works
versions deprecate Sets status='deprecated'. Nothing else. unchanged yes works
versions archive Sets status='archived'. Nothing else. The folder does not move. unchanged yes name lies
versions retire os.RemoveAll on the folder, row marked retired −1 snapshot no nobody runs it

There are three lifecycle states and only two behaviors: relabel and destroy. An agent facing an irreversible delete with a --confirm gate correctly declines every time, so the only reachable state is “relabel”, and the tree grows monotonically. This is not an agent discipline problem — it's a missing verb.

The finding that changes the design

The cold tier's data store already exists. Every version's complete file set is already mirrored, byte-for-byte with per-file SHA-256, in the untracked SQLite database.

component_version_files2,128 files / 610 versions5.4 MB, full source + content_sha256~/.vrooli/data/vrooli/react-component-library/react-component-library.db

So the proposal isn't “build a cold store”. It's “stop projecting the cold store into the working tree”. Eviction becomes a projection change, not a data migration — and rehydration is verifiable, because the hash of every file is already recorded.

Applied across the catalog this removes 875 files and 65,710 lines from the tracked tree while changing nothing an adopter can observe. A version that later gains a pin materializes back automatically — which is exactly the behavior you described.

What has to change — five edits, one of them blocking

  1. Stop treating “absent from disk” as “deleted”

    api/internal/components/sqlite.go:193

    Reindex currently runs DELETE FROM component_versions WHERE component_id = ? AND version NOT IN (…on-disk versions…). Evict a folder today and the next components index destroys its row and its file mirror. Add a presence column (materialized / evicted) and prune only rows that are materialized-and-missing. Nothing else in this list is safe until this lands, and it can land on its own with zero behavior change.

  2. Make archive the eviction verb

    Verify the DB mirror matches the folder by SHA, remove the folder, set presence='evicted'. Reversible, so an agent can actually run it. retire stays as the irreversible tier-3 delete; deprecate stays a pure label.

  3. Rehydrate on demand, not on request

    Four call sites must materialize transparently: adoptions link, components show-version, preview bundle, and the package build's .build-source copy. Each already has the version ID; each gains one “if evicted, write files from the mirror and checksum them” step.

  4. Make sync-exports read the ledger, not the disk walk

    If exports are generated by walking library/, evicting a folder silently deletes a published subpath and breaks any pin on it. Exports must come from component_versions, which knows about evicted versions.

  5. Bound the database before it becomes load-bearing

    The DB is 308 MB, and 262 MB of that is component_test_reports. Retention exists and works — newest 5 per version plus 2 pinned — but it counts rows, and each results_json averages 110 KB and peaks at 3.1 MB, because a report enumerates every asset in the closure against every stage. A count cap cannot bound that. The DB is also host-local and untracked. Before it becomes the only home of library history it needs a byte budget and an export/restore path.

The honest tradeoff: today, cold version bodies survive in two places — the tree and the DB. After eviction they survive in one, and it's the untracked one. That is fine if step 5 lands first, and not fine if it doesn't. Sequence 5 before 2.
Adjacent win — the other file that churns on every publish

packages/react-component-library/package.json is 160 KB and 3,334 lines, because it enumerates 827 export keys — one per version, plus one default alias per component. Every single publish rewrites a tracked 160 KB file.

Node subpath patterns match across path separators, so if the build emits a thin alias layer at dist/exports/<Name>/<Version>.js (plus dist/exports/<Name>.js for the latest alias), the entire block collapses:
