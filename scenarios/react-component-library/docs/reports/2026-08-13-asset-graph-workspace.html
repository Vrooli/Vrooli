The ladder is enforced, not aspirational

rank() maps every asset kind to one of six rungs, and an asset may not require anything above its own rung. That check runs today and fails the catalog gate. Everything below is a read of this data — no new model, no migration.

Obligations travel up; claims do not travel down. Re-proving Button's contrast inside DataTable inside a page template is combinatorial and tests the same pixels repeatedly. What genuinely composes upward is the unmet port — a host dependency an asset cannot satisfy alone. Every surface below reads the graph in that direction.

Reconcile the two graphs

There are two dependency graphs and nothing compares them. catalog/assets/** declares the desired state — 848 edges across 410 assets. library/**/component.json declares what the implementation actually pins — 143 edges, on 72 of 193 version manifests. This is the honest version of screaming architecture: the filesystem only screams if something enforces the scream.

05

Unmet ports — what actually stacks

The capability registry already splits every capability into promises (59) and port (23), and 23 assets declare satisfies. A port is a host obligation an asset cannot fulfil alone. Union the port-facet capabilities over an asset's closure, subtract what the closure provides, and the remainder is exactly the contract a consuming scenario must honor. That number is computable today and appears nowhere.

One correctness note before any of this ships

rank() in catalogvalidate/validate.go:259 is a bare map lookup with no default. An asset whose kind is misspelled or newly added ranks 0 — foundation — and silently passes every downward check. Every surface above inherits that hole. Guard the lookup and fail on an unknown kind before you build things that trust the ladder.
