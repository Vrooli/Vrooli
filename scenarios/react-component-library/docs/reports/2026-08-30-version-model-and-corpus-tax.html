01

Three faults, one shape

Each one takes something that belongs to a single asset and makes it belong to the whole corpus.

The setup-maturity plan closed fifteen of sixteen phases and most of it is genuinely delivered. What it did not reach is a single recurring shape, and every friction you have described is one of its three expressions.

  1. Failure is now attributable. The matrix records runner faults as unmeasured and preserves runner messages; the refreshed matrix has 0 failing cells without findings.
  2. Retention is operational. retire-candidates, plan-cleanup, and reconcile-presence all return, unreadable mirrors are typed, and the reachability closure is shared by the destructive paths.
  3. Cost is bounded. The current corpus has 320 version directories, 23% superseded compiled source, a warm matrix around 1 second, and a single-asset validation cycle under 10 seconds.

Your versioning question turns out to be the load-bearing one, so it goes first.

02

The version model

Your reading is correct, and the fix is already built — it was just never applied to the library's own source.

You noticed that consuming scenarios import a major line while the library pins exact versions of itself. That is exactly what the tree says, and the asymmetry is close to total.

What exact pinning costs, measured

I computed the true reachability closure over all 487 generated locks, rooting at every asset's latest plus every exact version any scenario pins. Then I recomputed it with each intra-library edge resolved to the highest active release in the same major line — which is what major-line imports would produce.

And the thing you described about updates propagating

You said it looked like scenarios get component updates automatically within a major line, and that the library does not. That is right, and the cost of not having it is severe because dependency depth multiplies it.

Under exact pinning, publishing a patch to a shared leaf means every dependent must be republished to see it — and each republish mints a new permanent version, which is itself a new thing to gate, compile and eventually reap. On today's live graph:

The recommendation, and the one thing it forces you to give up

Intra-library imports should be major-line, never exact and never bare. Major-line is the right point on the scale for the same reason it is right for consumers: minor and patch improvements propagate for free, and a major bump remains an explicit, visible barrier. A bare specifier would silently carry a breaking change into a released component, which is worse than pinning.

There is a genuine trade, and it should be stated plainly rather than assumed away. A released version's bytes stay frozen, but its behaviour stops being frozen. Button@2.2.1 compiled today and compiled next month would render differently if Icon shipped a patch in between. That is precisely the deal your 35 consuming scenarios already accepted 426 times, and it is the deal every package ecosystem makes — but it is a deal, not a free win.

The reason it is safe here is that the reproducibility record already exists and is separate from the specifier. Phase 2 built versions/<v>/dependencies.json, which records the exact resolution. The whole point of that lock was to stop the import string from being the dependency record — the machinery landed, and the source was simply never migrated to take advantage of it.

One contradiction has to be resolved first. dependencies.json is currently both a regenerated derived artifact and a byte protected by the immutability ledger — 265 lock files are hashed in released-version-hashes.json, and one has already drifted. Under floating imports every dependency publish would regenerate downstream locks and turn that gate red. Pick one: the lock is derived and leaves the immutability ledger, or the lock is frozen and retention resolves floats itself. Take it out of the ledger. Immutability should cover authored source; provenance for a historical build already lives in release-provenance.json.

The alternative — keep exact pins and make republish-dependents run automatically on every publish — is coherent and I would not take it. Figure 3 is why: it converts one leaf fix into 157 permanent versions, which is the accretion you are trying to stop, industrialised.

At the baseline, nothing enforced this. The delivered state has a blocking specifier-shape gate and publish-time normalization; the consumer-pin gate remains the separate external-consumer check. The baseline description is retained here to explain why the gate and migration exist.

03

Retention is offline, and has been

You asked whether there are flaws in the reaping logic. There are three, and one of them means it does not run at all.

Before any of the version-model work matters, the thing that removes versions has to work. Right now it does not. All three retention entry points fail identically:

observed 2026-08-30$ react-component-library versions retire-candidates --json
$ react-component-library versions plan-cleanup --json
$ react-component-library versions reconcile-presence --json

Error: build source reference graph: evicted version
react-component-library:inline-code@0.3.2 has no file mirror rows

A previous eviction left two versions with an empty file mirror. sourceReferences treats a mirror-less evicted version as a hard refusal — correctly, since it cannot prove what that version imports and retention is a deletion boundary. The consequence is that the tool which would clean up the residue of a cleanup is disabled by the residue of a cleanup. The same two rows also break pnpm run exports:check, and through it the types gate for all 243 assets.

versions doctor knows about it and reports it as two ordinary “issues”. Nothing escalates it, so the library has silently been unable to reap.

On your cascade question specifically — whether a dead version importing another dead version keeps both alive — you are right that nothing iterates to a fixpoint, but the effect is smaller than the other two problems. Of the 129 currently-unreachable versions, 119 are referenced by nothing at all and would be freed by a single pass. Only 10 are shielded solely by other dead versions and would need a second. Worth fixing with a proper closure, not worth leading with.

The third flaw is a blind spot rather than a bug. Locks are generated by walking outward from a version's entry module, so story.tsx is never traversed — nothing imports a story. Story imports are also package specifiers, so the source scanner misses them too. Today that leaves 3 versions pinned only by a story and recorded in no lock, deletable without warning. The 10 preview-harnesses assets have no locks at all, because the lock generator's rank table does not list that directory.

05

The other baseline faults

The findings below preserve the independently verified baseline rationale; the current measurements and repaired outcomes are recorded in the table above and the closing note.

F1

Unattributed runner faults are broadcast as per-asset failures

api/cmd/gate-matrix/main.go:107 reads if len(cell.FindingCodes) > 0 || len(result.RunnerError) > 0, so a gate that fails for a reason belonging to no asset marks every applicable asset failed with no findings attached. The two mirror errors above become 210 red assets under types. Corpus-wide, 506 of 956 failing cells (53%) carry zero findings — under types (210), i18n (125), released-version-immutable (118) and lifecycle (42). This is the mechanism that sends an agent into the machinery.

fix a third verdict — unmeasured: runner fault — carrying the runner's own message. The types gate already has codes of exactly this shape (catalog.types_runner_unavailable, catalog.types_timeout); it just does not emit one when the subprocess crashes.

F2

The catalog app does not compile, from a hand-copied proto type

At the baseline, ui/src/api/componentTests.ts:14 hand-declared ComponentTestResult without the rule_source and rule_declared_in fields added to component_tests.proto:34, producing five TS2339 errors. That catalog type drift is repaired: the current catalog check and UI build pass. Repository-wide make lint and make check still report inherited UI lint debt, which remains separate from the repaired catalog application build.

fix generate ui/src/api/*.ts from the proto, or add a freshness check that fails when a declared field is absent from the client.

F3

Three write paths reach a released version; one is checked

draft-begin → draft-publish runs CheckComponentVersion and refuses to promote a failing draft. version-create --release reaches CreateComponentVersion(Intent: release) directly and skips it. Writing the directory by hand is free. 0 of 243 assets have an active draft, and SettingsList minted 0.1.0 through 0.1.5 — six permanent releases — in one day. The governed path is also the most expensive one.

fix retire version-create --release or route it through the same check; add a gate that fails when a released version directory exists with no provenance record.

F4

The release-hash ledger is a third fiction

2,857 entries; 1,885 match disk, 40 are mutated in place, 932 point at files that exist nowhere — not in .retired/ — across 89 assets. The ledger is append-only and nothing reaps it when a version is removed. released-version-immutable is blocking at rung verified and fails 188 assets on that basis, so those assets cannot reach verified no matter what is done to the components themselves.

fix reconcile once; make removal of a version remove its ledger rows in the same operation; drop derived files (dependencies.json) from the hashed set.

F5

Attribution is declared and not implemented

All 49 gates declare the identical determinism input ["catalog/config.json", "library/**"] at registry.go:91. registeredDefinition and scopedDefinition are byte-for-byte identical functions, so the “scoped” label carries no behaviour. Only 4 of 49 runners read scope.Assets. assetCacheFingerprint hashes every asset into one string against one cached report while its own comment claims the opposite; the honest comment is at evidence.go:1136 — “the runners themselves are whole-corpus by construction, so the saving is the runner's entire cost or nothing.” Separately, readiness.go:125 counts attribution from a field that does not exist in the config file, so readiness reports 0 attributable and 0 corpus gates.

fix convert the ten most expensive runners to per-asset functions with real determinism inputs before doing any further caching work.

F6

Everything is blocking, so nothing is prioritised

46 of 49 gates block. Five of those — unit, interaction, accessibility, responsive, visual — are registered as declaration-only and delegate to browser capture and test-genie phases, so they are permanently unmeasured in the deterministic matrix: 1,127 cells that can never turn green from that surface. When every gate is mandatory the only exit is an allowlist, and vacuous-allowlist.json holds 218 entries.

fix block only gates that have an in-process runner, can attribute a finding to an asset, and are green for most of the corpus.

F7

Gates still judge TypeScript by regular expression

Phase 13's AST fact extractor works and is wired into two checks. gates.go is 3,665 lines carrying 50 MustCompile calls matching patterns against source text. The extractor is also Go shelling out to node resolve-imports.mjs --facts per file — a process spawn inside a gate loop.

source internal/gates/ast_facts.go · callers at gates.go:993 and gates.go:1231

F8

Duplicate experience authorities, one of them degraded

41 canonical specs under experience/components/, every storyRef resolving. 350 copies pushed into version directories, of which 310 carry no storyRef at all and 37 carry one that does not resolve — the relative paths were copied verbatim from five levels away. Three resolve. Manual-review claims outnumber machine claims 452 to 378, up from 319 to 240 at the plan's baseline.

fix keep the 41; reference them from versions rather than copying.

F9

Residue: the baseline, the design record, and the .mjs habit

tmp/ holds 55 MB, 43 MB of it the Phase 1 before-state captured on 27 Aug and never reaped. The architecture review that Phase 16 step 14 requires to be refreshed was last written 28 Aug 02:46, before phases 6–15 closed. And the .mjs habit you have been watching is conformance, not deviation: 25 .mjs files totalling 3,977 lines are the library toolchain. Adding a library dependency genuinely requires editing one — packageDependencyPaths at build.mjs:30 is a hardcoded twelve-entry map.

fix derive the compiler paths from package.json dependencies; reap tmp/; refresh or retire the review.

The one-sentence version

The baseline pass fixed how a component was written but left untouched how it was judged and retired. The delivered implementation repairs the retention and attribution machinery, migrates new intra-library imports to major lines, and keeps the remaining historical closure explicit. Restore the floor, make failure name a defect, then let the library import itself the way its own consumers already do.
