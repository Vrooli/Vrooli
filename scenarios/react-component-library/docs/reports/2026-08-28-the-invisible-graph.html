The Invisible Graph

The pruner that deleted IconButton is not slightly wrong. Every one of its three protections is blind to the way library components actually reference each other — and the tool meant to propagate updates is blind for the same reason.

Fixed and verified — 2026-08-28

When this was written, versions cleanup marked 13 versions eligible for deletion that other versions' locks required — IconButton 2.0.1 among them, needed by 28. Retention now reads the generated locks, including those mirrored in cold storage, and resolves the package specifiers the workbench uses. That count is now 0, and the repair carries regression tests.

plan-cleanup: eligible-but-required 13 → 0 · index 138 → 224 of 236 · republish-dependents 0 → 4
Still open

13 released directories were created by the filesystem bypass and still carry no publish record. The release-provenance gate reports them correctly and its test fails on purpose. Clearing them is asset work — IconGeometry@1.0.0 alone carries 63 lint errors — and it is the one item below that code could not close.

The defect

Three guards, three ways of missing the same edge

All three are now closed. The diagnosis below is kept as written; what changed is recorded at the end of each panel.

A version survives cleanup if it is latest, a draft, already retired, externally adopted, or shown to be referenced. The last one is where composition inside the library is supposed to be caught. It is caught by three independent mechanisms, and all three fail on the same import.

This is the import that broke:

library/components/VoiceInputButton/versions/4.3.1/VoiceInputButton.tsx:10

The authoritative answer already exists and is not consulted. Every version carries dependencies.json — a generated, per-version lock naming exactly what it imports. 483 of them exist. Retention reads none of them; the only code that reads a lock is the dependency-rank gate. Cross-checking the cleanup plan against those locks is how the thirteen unsafe deletions above were found, in one pass.

The same blindness, the other direction

The propagation tool reports success by finding nothing

You asked whether a component could follow IconButton's latest release instead of pinning 2.0.1. The command for that already exists — components republish-dependents — and it reads component.Dependencies, which is the same empty table as guard two.

So republish-dependents IconButton 3.1.1 finds zero dependents and reports a clean dry run. Not an error, not a warning: a confident nothing. Fixing the pruner and fixing propagation are the same fix.

The cost of pinning

Every hook release mints three component releases

Exact pins mean a dependency bump is a source change, and a source change to an immutable version means a new version. The overlay family shows this cleanly: useOverlaySurface has nine versions, and its three consumers have twelve each. They move in lockstep.

The decision you raised

Should a component follow the latest release instead?

Worth doing, but not as stated — "follow latest" is what just broke. IconButton 3.1.1 became latest, 2.0.1 stopped being latest, and the pruner treated not-latest as not-needed. Moving that same idea into resolution would make a released version's behaviour change without its bytes changing, which is the one property the whole immutability design buys you.

The useful version of your instinct separates three things that are currently one thing: what an author writes, what a release records, and what a consumer resolves.

Keep exact pins everywhere

status quo

Reproducible and safe, and it is why the equivalence proof in the last plan worked. But it makes every dependency bump a version, which is the ladder above, and it makes retention a permanent liability because no old version can ever be released.

Cost: the version explosion, and the cascade tax on every foundation edit.

Resolve dependencies at build from the latest release

not recommended

Updates propagate for free, and no version is minted to carry a bump. But a frozen version stops being frozen: its rendered output depends on when it was built. released-version-hashes.json, the immutability gate and the equivalence proof all stop meaning anything, and a regression in a foundation silently reaches every consumer at once with no record of which pairing was tested.

Cost: reproducibility, which is the property the library sells to 35 consuming scenarios.

Record a range beside the resolved pin

recommended

The lock already stores { libraryId, version, rank } per dependency. Add what the author actually meant — "compatible": "^2" — beside the exact "version": "2.0.1" the build resolved. The exact pin still governs the build, so nothing about reproducibility moves.

What changes is that a machine can now answer two questions it cannot answer today: is this dependent still compatible with the new release? and which versions are actually reachable? republish-dependents becomes a real sweep that bumps everything whose range still admits the new version, in dependency-rank order, in one command — the propagation you described, without surrendering the frozen bytes.

Cost: one field in the lock schema and a generator change. The authoring experience is unchanged, because drafts are already meant to be written unpinned.

Protect by reachability, not by latest

recommended

Independent of the above, and the direct fix for the incident. A version is needed if anything reachable still names it — computed as the transitive closure over the 483 locks, not as a property of a single manifest field. latest is a pointer for consumers; it was never a statement about what is safe to delete.

The concept is already half-built: versions reconcile-presence describes itself as the "reachability-based materialized/evicted tier". Retention should share that graph rather than keeping a second, weaker opinion.

Cost: low. The graph exists in the locks; retention just has to read it.

Sequence

What I would do about it

Now · prevents a repeat

Stop cleanup from running until its reference scan reads locks

Thirteen unsafe deletions are queued behind one confirmation hash. The incident recurs the next time anyone runs it, and it will take more than IconButton with it.

Small · the actual fix

Make dependencies.json the reference graph

Build reverse edges from the 483 locks on disk and use them for both retention and republish-dependents. This retires the relative-import filter and the dead component_asset_dependencies read at the same time, and it does not depend on the index being fresh — which is what made all three guards fail together.

Small · closes the third guard

Make an incomplete index refuse to authorise deletion

Eight assets on disk are absent from the index and nothing noticed. A retention plan computed from an index that disagrees with the filesystem should report unavailable, not eligible. Deletion is the one operation where a missing row must never read as an absent reference.

Medium · your propagation idea

Add compatible to the lock and make the sweep real

Record the author's range beside the resolved pin, then let republish-dependents bump every dependent whose range still admits the new release, in rank order. Updating a foundation becomes one command instead of a hand-walked cascade — and the frozen bytes stay frozen.
