Finding 09 · new, and it outranks everything else

Half the work surface serves nobody

You asked why progress is slow. This is the answer, and nothing else on this page competes with it. The library is 231 components — but the unit of work is the version, and there are 559 of those. Every version directory carries its own story contract, experience contract, and source; every one is indexed, gated, story-tested, and screenshot-captured on each pass.

Of those 559, exactly 268 are live — 231 latest-of-each plus 37 older versions still pinned by an adopter. The remaining 291 are dead: not the newest, and not imported by anything in the repo. The package still exports 541 pinned-version subpaths; adopters reference 59. An agent grinding through the catalog overnight is spending about half its passes on versions no one can reach.

Finding 01 · the root cause

The coverage rule writes the bad stories

You guessed the validation wasn't pushing configs toward the ideal. It's stronger than that: the one rule that governs story sets has a shape that can only be satisfied by adding near-duplicate stories.

The rule StoryCoverageGaps requires every declared enum option to appear in some story's args.
The cheapest fix Add one story per option. The agent has no reason to do anything else.
The result Text declares an 8-option style enum, so Text has 8 stories. Icon declares 9 names, so Icon has 9.
What you see Every story renders the same specimen. One line of copy changes. The sheet teaches you nothing.

TypographyShowcase paints a fixed heading, an overline, a muted paragraph, and a three-chip footer in all eight. Roughly 90% of each captured frame is pixel-identical to its siblings.

The same component, two ways

A list of values vs. a matrix of variation

This is the answer to "how do we decide what the stories should be." Coverage should be a property of what is rendered, not of what appears in args. One story that paints all eight styles side by side covers the enum completely — and frees the other slots for the conditions that actually break typography.

Four frames, each answering a different question: what is the scale, what are the tones, where does it break, how does it set. Enum coverage is satisfied by frame one.

The three story kinds worth naming

  • Anatomy — one frame, default props, no chrome. Answers "what is this thing."
  • Axis matrix — one frame per axis, not per value. All sizes together, all tones together, all icons together. This is where enum coverage should be discharged.
  • Boundary — one frame per credible failure condition: empty, overflowing, truncated, loading, error, disabled, RTL, forced-colors.

Under that model Icon becomes three frames (default grid, tone grid, size grid) instead of nine copies of the same grid, and the 299 single-story contracts get exposed for what they are: components whose variation has never been rendered at all.

F2

The i18n bridge has no producer

Hollow

Correction. My first pass said no component emits a key. That was wrong — I grepped for the bridge's name rather than the helper's. A producer exists: hooks/useLocale exports translate(key, fallback), and 82 sources import it. The finding is not absence. It is quality and delivery.

82 of 534 sources (15%) call translate across 380 call sites, for 282 distinct keys. But 199 of those 282 keys are positionally numbered — ai.approval-prompt.text.3, …label.8 — which is meaningless to a translator and re-numbers whenever the markup shifts. Most of the remainder are slugified English, so the key changes whenever the copy does.

And none of it is delivered: zero adopter catalogs contain a derived key. The gate still passes everywhere, because ValidateI18nAdopted only checks that the adopter's file contains the marker comment. It verifies plumbing, not flow.

F4

The code moved to the library; the tests didn't

Open

The orphans are real — 138 .test.tsx files whose sibling source was deleted during the import migration, 131 of them importing @vrooli/react-component-library and asserting library behaviour from inside a scenario that no longer owns the code. F10

The styling contract is documented, then violated

New

Your recollection is right, and the library already knows the correct answer. foundations/ClassMerge describes itself as "the single class composition primitive used by library assets; Tailwind conflicts resolve in favor of the consumer override," and 148 sources use it.

But 187 sources (35%) accept className and then set an inline style object on the same element. An inline style beats every stylesheet rule short of !important, so the consumer's class is applied and silently loses. That is precisely the "hard to customize" symptom: the override appears to be supported, type-checks, renders, and does nothing.

Two related gaps make adopted components awkward for anything beyond static display. On React 18, ref forwarding is opt-in — and only 36 of 534 sources (7%) forward one, so focus management, popover positioning, form libraries and animation libraries cannot attach to the vast majority of the catalog. And Text overloads the standard DOM style prop to mean either a token name or a CSS object, which is a trap for anyone who has written React before.

The shape: one spec, not 221

  1. Export the runner. Turn the 22 substituted top-level constants into one function parameter and export it. The Go template collapses to a shim that calls the same function with the same values — one evaluator, two callers, nothing to drift.
  2. Give the library a denominator. A library/ vitest project with coverage include: ["library/**/versions/**/*.tsx"]. This is the step that turns the census from unmeasured into measured.
  3. Walk every contract once. A single generated spec renders all 1,209 stories in jsdom, runs their interactions, and asserts everything except layout. Per-file coverage lands on Component.tsx and story.tsx in the same pass.

Which settles the story.tsx question. Rendering a story is what executes its specimen, so story.tsx never needs a test file — it is a specimen, not logic. What it deserves instead is two checks that fall out of the same walk for free: every exported specimen is referenced by at least one story, and every specimen renders. A per-component Icon.test.tsx only earns its place if you want per-component reporting granularity, and then it should be three generated lines delegating to the runner — never hand-authored.

What to do next

One plan, ordered so nothing is done twice

Progress felt slow because most of this is a treadmill until the thing upstream of it is fixed. Two orderings matter more than the rest: retire dead versions before touching contracts, and stand up the runner before changing what contracts must contain.

  1. Retire the dead version surface. 291 of 559 versions have no consumer. Every later phase gets roughly half as large the moment this lands, and the 805 cross-version imports stop being a reason not to delete anything.
  2. Stop the fork factory. Convert the react-vite template to the linked adoption, then migrate the 80 residual forks. Until this lands, every new scenario re-creates the problem two passes already cleared.
  3. Export the story runner and give the library a denominator. Converts the surviving contracts into a real unit suite with no assertions authored, and makes every later phase measurable rather than argued.
  4. Move test ownership. Promote the 60 distinct bodies, delete all 138 orphans.
  5. Re-aim the coverage rule, then migrate the contracts. Ship the covers/role/axis extension and the four gates first, so the migration is verified as it happens instead of reviewed afterwards.
  6. Fix the styling contract. Codemod the 187 inline-style overrides, forward refs, retire the overloaded prop. This is what makes adopted components genuinely customizable.
  7. Give the obligations real producers. The typed strings provider and the suffix-derived selector naming, each with a gate that counts usage rather than markers.
  8. Trim the schema, then build the viewer. Both are mechanical by this point, and the viewer makes every audit after this one faster.
