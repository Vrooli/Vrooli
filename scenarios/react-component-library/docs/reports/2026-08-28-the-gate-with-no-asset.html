The Gate With No Asset

Your library already describes, in data, exactly the architecture you intuited: universal rules, per-kind rules, and per-asset rules. The code that runs the rules reads none of it. It loops the other way round — gate on the outside, assets on the inside — and every symptom you've been living with follows from that one inversion.

01

The words, defined

Six nouns. Everything else in this report is built from them. Your reading was right on the first one and understandably tangled on the rest, because three of these live in different files with different naming.

You asked whether gates have to do with the evidence contract. They are related but different layers: a gate is a rule, and evidence is one of several things a rule may look at. Some gates read source code, some read recorded browser observations, some read declaration files. Here is the whole vocabulary.

Any publishable unit in the library — not just visual ones. You were right to hesitate at "component": that is one kind of asset, not the category. An asset has a folder under library/, one or more immutable versions, and a declaration under catalog/.

Finding what a gate emits

One defect. Carries the asset it belongs to, a file and line, a message, and a remediation. A gate that produces no findings after inspecting zero inputs is treated as broken, not passing — that part of the design is genuinely good.

A finding's AssetID is how a result gets attached to a component. Hold onto that; it becomes the crux in §3.

Recordings taken by actually rendering an asset in a browser. Evidence is input, not a rule. The accessibility gate reads the recorded accessibility tree; the types gate reads none of it and runs a compiler instead.

Evidence is produced from story.json, which declares specimens to render and what to expect of each one.

02

How a run works today

You guessed it exactly: "for each gate, we run the whole library against the gate." That is precisely what happens, and it is the wrong way round.

The same thing, in the code

Nearly every gate funnels through one shared helper. Here is its core, lightly trimmed:

A worked example: the tokens gate

This one shows the whole problem in a single runner. tokens declares "appliesTo": ["foundation"] — it is a rule about the nine foundation assets that publish design ramps. What its runner actually does:

  1. Globs templates/design/*/…/tokens.css — files outside this scenario entirely — and checks each design kit declares the shared token vocabulary.
  2. Then loads every active library source file and scans all of them for hardcoded pixel dimensions.
  3. Emits every finding from step 1 with AssetID: "" — no asset attached at all.

So a gate declared to cover 9 assets reads several hundred files, and throws away the attribution on half its findings. That is why it is labelled corpus — not because the rule is genuinely corpus-wide, but because the runner discarded the information needed to attribute it.

What "corpus" actually means today

24 of the 45 gates are marked corpus, which the system reads as "this verdict does not belong to any one asset, so it can never be cached per asset." Nothing verifies that claim. It is a field an author types, and typing it is the easy way to make a whole-corpus runner acceptable. During the pass that was meant to make validation cacheable, four gates were added — all four were marked corpus, and the attributable count did not move.

Your model is already declared. Nothing reads it.

This is the finding that reframes everything. You described three layers of rule ownership. All three exist in the data today.

You said rules should be defined at whichever layer covers the most, so you stop re-declaring them per component. That design is not missing from your library. It is written down in three places, validated for correctness, used for scoring — and ignored by every gate runner.

The consequence is that applicability is described twice and the two descriptions can disagree. The declaration says tokens applies to foundations. The runner's hardcoded list says otherwise. Nothing compares them, so neither is wrong in a way anyone finds out about.

The vocabularies don't even line up. Assets declare their kind as hook and service; gates declare runtime-hook and runtime-service; the Go list hardcodes a third set. And 40 assets declare no kind at all, so no kind-scoped rule can find them.

04

Your model, drawn

Asset on the outside, rules on the inside, resolved from three layers. This is right, and it is closer than it looks.

Two details worth confirming, because you raised both and both are right:

The skip key needs two halves, not one

You said "if they haven't changed or the set of gates haven't changed since the last run." That second half matters and is missing today. A stored verdict is only valid if the asset's content is unchanged and the rules applied to it are unchanged. Key the cache on both and a gate edit correctly invalidates every asset it touches, while a component edit invalidates only that component and its dependents.

Some rules genuinely are corpus-level

A few gates ask questions about the whole graph, not about one asset: "does any released version import a deleted one", "is the dependency rank ordering intact". Those should stay corpus-scoped — but as a small, justified handful, proven by the runner returning no per-asset findings, rather than 24 gates that opted into it because it was easier.

06

The UI gap you predicted

You guessed the test panel shows results but not where the rule came from. That is exactly what it does.

ComponentTestPanel.tsx is 1,103 lines and renders six evidence kinds well — story sheet, screenshot, accessibility tree, computed styles, layout box, console, performance — plus a per-stage verdict with a message and a recommended next step.

What it never renders is provenance: for any given check, whether it applies because it is universal, because of this asset's kind, or because this asset declared it. There is no field for it in the panel, and there is no field for it in the finding either — a Finding carries a code, an asset, a file, a line, a message and a remediation, but nothing about which layer imposed the rule.

This is not a cosmetic gap. It is the reason a failing gate reads as "this component is wrong" rather than "this component is being held to a rule that comes from here, and here is where to change it if the rule is wrong." Without it, the only visible repair is to change the component or add an exemption — which is precisely the behaviour you keep seeing.

This falls out of the restructure for free

Once the runner resolves a rule set per asset from three declared layers, it necessarily knows which layer each rule came from. Carrying that on the finding is one extra field. The panel then shows, per check: the rule, the verdict, the evidence, and the layer that imposed it — with a link to the file where it is declared.

07

The change, in order

One structural move, then three that get much cheaper once it lands.

01

Turn the loop inside out

Give the gate runner the asset it is judging: Validate(root string, scope []AssetID) (Result, error), with an empty scope meaning the whole corpus so nothing breaks on day one. Then delete each runner's private glob and hand it the assets from the outer loop.

At the same time, replace the hand-written dispatch — a 271-line function with 19 if needed("…") blocks — with a registry where each gate registers its id, its runner and its applicability once, next to its implementation.

unlocks → per-asset skip for all 45 gates, keyed on asset revision + rule set · attributable stops being a field an author asserts and becomes something the runner demonstrates · adding a gate drops from five files to two
02

Make the declarations authoritative

Have the runner resolve applicability from appliesTo and requiredCapabilities instead of hardcoded kind lists. Then reconcile the three kind vocabularies into one (hook vs runtime-hook), and backfill the 40 assets that declare no kind and the 22 that carry no catalog identity.

This is what makes your "define it at the layer that covers the most" rule enforceable rather than aspirational — right now a broad rule and a per-asset rule are equally easy to write, so per-asset wins.

unlocks → 17 of 19 per-asset stamp exemptions become deletable · one applicability definition instead of two that can disagree · gates stop silently missing assets they cannot name
03

Put provenance on the finding, then show it

Add the layer and the declaring file to Finding, and render both in the component test panel next to each check. A reader should be able to see, without leaving the page, that status-announced is being checked because alert.json asked for it, and open that file.

unlocks → a failing gate becomes actionable in two directions — fix the component, or fix the rule · exemptions stop being the only visible repair
04

Declare one home per rule class, then close the others

Write it down: cross-asset and structural policy lives in Go gates; single-file source syntax lives in ESLint; nothing lives in a standalone .mjs script. Then fold the 13 existing scripts into whichever surface owns them.

This only holds after move 01. Agents reach for .mjs because it is the cheapest surface available; the fix is to make a real gate cheaper than a script, not to forbid the script.

unlocks → the token rule stops existing twice in two languages · the 218-entry vacuous allowlist can finally drain
The short version

Your library's data model already describes the architecture you want. Assets declare their kind and their required capabilities; gates declare which kinds they apply to; contracts declare per-asset claims. The scoring layer reads all of it and reports honestly.

The execution layer reads none of it. It loops gate-first, each runner re-deriving its own scope by globbing the filesystem and filtering on a hardcoded list. Turning that loop inside out is not a redesign — it is making the code obey the declarations the rest of the system already believes.
