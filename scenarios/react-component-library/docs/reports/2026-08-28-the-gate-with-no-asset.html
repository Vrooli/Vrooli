That last row is where this report starts. The freshness machinery was built correctly. It cannot deliver what you asked it for, and the reason is one line above it in the call stack.

02

The root cause is a type signature

You asked for validation that skips components that haven't changed. For 44 of 45 gates that is not slow — it is impossible.

The consequence is written into the code by whoever built the skip layer, in a comment on recomputeEvidenceWithSkip:

From api/internal/catalogcoverage/evidence.go

"When stale is present a runner is skipped only if no applicable asset needs it; the runners themselves are whole-corpus by construction, so the saving is the runner's entire cost or nothing."

So the freshness index knows precisely which components changed, computes the dependent closure correctly, and then hands that knowledge to 44 functions that cannot accept it. Touch one component and every gate that applies to it re-runs across all 243 assets. The skip is per-gate, not per-asset — and a gate only skips when every asset it covers is already fresh, which after any edit is almost never true.

ValidateTypesForAssets is the proof that fixing this works. It is the one runner that was given a scope parameter, and it went from 24.6 s to 1.0 s for 147 of 238 assets. That result is available for the other 43 runners and nothing about them makes it harder — they simply were never asked for it.

03

Adding one gate costs five files

There is no gate registry. Each of the 45 gates is hand-wired at every layer it passes through, and the wiring has already come apart.

The drift, precisely

catalog/config.json declares 45 gates. The determinism map in .vrooli/test-genie.json covers 32. Fourteen catalog gates — including self-hosting, dependency-rank, release-provenance and consumer-pin — have no entry, so they inherit the file's declared default of observational: not file-determined, therefore never skippable by digest. Meanwhile the map carries one entry, adopter-contracts, for a gate that no longer exists in the catalog at all.

04

Every asset has two names, and 22 have only one

The single most mechanical source of friction, and the one with the cleanest fix.

This is the clearest example in the codebase of the pattern you described — a special case for a specific component that isn't really about that component at all. Backfilling 22 catalogId values deletes 17 exemption entries as a side effect, with no gate changes.

The same file also shows the tax in miniature: its 42 entries are written in three different ID formats (foundations.tokens, monetization.auth-section, react-component-library:AssetDetailShell), 41 of the 42 name a specific asset rather than a kind, and 15 are self-labelled backlog rather than permanent.

05

Why agents write .mjs files

Because thirteen of them already exist, and because a rule can legitimately live in six different places.

The duplication this produces is not hypothetical, and one of the rules documents it in its own header. ui/eslint-rules/no-raw-dimensions.js opens by explaining that the Go tokens gate globs library/** only, so ui/src drifted to 382 raw dimensions across 36 files while the library stayed clean — and that rather than add a third scope definition in Go, the rule was written again in JavaScript. One design policy, two implementations, two languages, and four config files (token-map.json, tailwind.theme.json, design-token-exceptions.json, utility-class-allowlist.json).

That was a reasonable local call. It is also exactly how a setup accretes a second enforcement stack.

The gates still read TypeScript as text

Phase 13 promised parsing instead of matching. A parse seam exists — ast_facts.go shells out to resolve-imports.mjs --facts — but it currently answers one predicate (does this element carry an overlay role). gates.go still contains 39 regexp uses and 27 strings.Contains calls against JSX source. While that holds, gates keep producing both false failures and false passes, and an allowlist entry stays the cheapest available repair. The vacuous-allowlist.json is still 218 entries, all carrying the same deferral reason, and it drains only when an asset is next touched.

06

The authoring path has three front doors

The plan promised a four-step loop. The documented loop is ten steps, and step one has three spellings.

Both families are live, both are documented, and docs/guides/asset-update-flow.md uses the first in its numbered steps and the second in its bulk-migration example — so an agent reading one section and an agent reading another learn different commands for the same operation. The CLI carries 82 commands across 8 groups; components alone offers init, ingest, draft-begin and version-create as four ways in.

And the guide itself is the gap between promise and reality. The plan's stated outcome was four steps: open a draft, edit, validate, publish. The guide documents ten numbered steps plus five follow-on sections — index, catalog vocabulary gates, ramp-completeness gates, component tests, the full scenario suite, per-target adoption preflight, token sync, adoption refresh, classification, reapply, batch apply, and an evidence record.

The instruction agents actually receive is one line in AGENTS.md pointing at components draft-begin. That line is duplicated on consecutive lines, and the whole file is duplicated below itself, so it appears four times — a small thing, but it is the entire briefing an agent gets before touching this library.

08

Four moves, in order

The first one is load-bearing. The other three get much cheaper once it lands.

01

Give the gate interface an asset parameter

Change the runner contract to accept the scope it is meant to judge — Validate(root string, scope []AssetID) (Result, error), with an empty scope meaning "the whole corpus" so the cold path is unchanged. Then replace the 271-line hand-wired dispatch with a registry: each gate registers its id, its runner, and its applicability once, next to its implementation.

This is the move that stops the setup manufacturing special cases, because it makes the per-asset runner the default shape rather than the one exception someone had to fight for.

unlocks → per-asset caching for all 45 gates · deletes the if needed(…) chain · makes attributable a property the runner proves instead of a field an author asserts · collapses five registration points to two
02

Collapse the dual identity to one asset ID

Backfill the 22 assets carrying catalogId: null, then pick one identity as canonical and derive the other. Delete get-by-library-id once get resolves either spelling.

unlocks → 17 of 19 per-asset stamp exemptions become deletable · one ID format in exemption and allowlist files instead of three · gates stop silently missing assets they cannot name
03

One front door for authoring, and a four-step guide behind it

Keep components draft-begin / draft-publish, retire catalog draft * and versions cleanup-draft as public surfaces, and rewrite docs/guides/asset-update-flow.md to the four steps the plan promised — pushing index, gates, preflight, refresh and reapply behind a single publish command that runs them. Fix the duplicated AGENTS.md line while you are there.

unlocks → the agent-facing loop finally matches the designed loop · no more choosing between two documented spellings of step one
04

Declare one enforcement home per rule class, then close the others

Write down the rule: structural and cross-asset policy lives in Go gates; single-file source syntax lives in ESLint; nothing lives in a standalone .mjs script. Then audit the 13 existing scripts against it and fold each into the surface that owns it.

This only holds if move 01 landed first. Agents write .mjs files because that is the cheapest surface to reach; the way to stop it is to make adding a real gate cheaper than writing a script, not to forbid the script.

unlocks → the token rule stops existing twice · the vacuous allowlist can drain because parsed gates stop producing false failures
The thing to keep in view

The lock-driven plan was good work and most of it held. What it treated were the symptoms that had already appeared: the build patches, the bespoke BAS cases, the committed artifacts, the version sprawl. All of those are genuinely gone.

What it did not change is the shape that produces them. A gate runner that cannot name an asset must scan everything; a gate that must be registered in five places will drift; and a policy with no declared home will land in whichever file is easiest to open. Until the runner contract changes, the next pass will add gates the same way this one did — four more, all whole-corpus — and you will be asked to drive down the debt again.
