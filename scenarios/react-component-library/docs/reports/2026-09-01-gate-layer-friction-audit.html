React Component Library · Architecture Review

Why the library fights back

The refactor you planned already shipped — the corpus is canonical, metadata has one owner, the generator is idempotent. What still makes agents flail isn't the library. It's the feedback channel: after any edit, the only whole-library check returns 4,863 messages, and 2,650 of them come from a quarantine folder two gates forgot to skip.

branch agi measured 2026-08-31 live corpus, no fixtures

You asked why every pass needs another debt-reduction round. Here's the honest read: the structural work is done and it worked. The plan's 15 phases were executed — the phase reports are dated today — even though the plan file still reports draft because no phase was ever marked started.

What remains is not architectural debt. It's four leaks in the validation layer, each small, each independently fixable, and together they produce essentially all of the friction you've been feeling. Three of the four are the same root cause: every gate hand-rolls its own file walker.

01

What actually landed

Verified against the live tree today, not read from the plan. These are the things you no longer need to worry about.

  • One asset shape, not 37

    All 283 live version directories resolve to the canonical shape ± the two documented optionals (.css, .strings.ts). Every one has a story. The old "37 shapes" figure counted literal filenames, so useHover.ts read as a different shape from Button.tsx — it overstated the problem roughly ninefold.

  • Metadata has one owner

    component.json now carries 7 pointer fields and nothing else — no description, displayName, slot, requires, or entry. The drift the plan measured (147 of 210 assets disagreeing) is structurally impossible now. Duplication invariant reads 0.

  • The generator is total and idempotent

    catalog build --check reports zero authored-derived drift. Delete the derived artifacts, run one command, get the tree back.

  • No special cases left

    Both allowlists are empty (entries: []). Across 72k lines of Go, only 4 string literals name a specific asset. The thing you explicitly asked not to have — per-component exceptions — is genuinely gone.

  • The exemption file is deleted

    population-decisions.json — 225 identical reason strings existing only to zero an invariant — is gone, and the gap it hid now reports honestly as 225. That's a real number replacing a fake zero.

  • Structural rules read syntax, not text

    A shared ast-grep facts index owns JSX elements, attributes, imports, exports, and calls. The 10 surviving regexes are documented, and each one validates literal text contracts rather than substituting for tree traversal.

  • The front door is real

    README.md now opens with the four-command asset loop and an always/never list. The scaffolding text about a notes demo domain is gone.

03

Where the friction actually is

Ranked by how much each one costs an agent trying to change one component. Every number here was measured today by running the scenario's own instruments.

F1

The quarantine folder leaks into every gate run

2,650 of 2,680 runner errors — 98.9% 674 retired trees 19 MB

library/.retired/ holds retired component trees. Their imports point at versions that no longer exist — which is correct, that's what retired means. But version-liveness and provenance-stamp walk it anyway and report every one of those imports as an error.

The mechanism is precise: both gates skip node_modules and dist but not .retired, while internal_helpers.go and version_shape.go do skip it. The exclusion set was copy-pasted, and two copies are missing a line.

This is the single largest source of noise in the system, and it's a two-line fix. Remove it and the error channel drops from 2,680 to 30 — at which point the remaining errors are real and worth reading.

F2

There is no way to validate one asset

--all + --asset-id → rejected 29.6 s 26,416 files 2,183 findings

The operation an agent needs after editing Button — run every gate against Button — cannot be expressed. The CLI refuses it outright:

invalid_argument: asset_id cannot be combined with all=true

So the choices are: run one named gate scoped to the asset, or run the whole matrix over the whole corpus. The README's advice to "use the narrowest applicable gate first" is not guidance — it's a workaround for a missing capability, and it requires the agent to already know which of 57 gates its edit could have broken.

This is the answer to why agents wander. They edit one file, get 4,863 messages about 247 other assets, and start looking for a way to narrow the signal — which is exactly when they begin writing scripts.

F3

Asset scope is a convention, not a contract

silently ignored by 3 of 7 tested no error emitted

Even where scoping is allowed, gates honor it only if their author remembered to. There's no enforcement and no warning — the gate simply scans everything and reports as if it had scoped.

F4

Eleven walkers, three different exclusion policies

11 WalkDir sites 35 Glob sites 1 shared helper, used by 2

F1 and F3 are symptoms of this. There is no single library walker. Each gate opens the tree itself, and the exclusion sets fall into three groups: skips .retired (2 sites), skips node_modules/dist but not .retired (2 sites), skips nothing at all (6 sites, including conformance, self-hosting, and provenance-stamp).

This is the one genuinely architectural item left, and it's the plan's Phase 2, which was never executed. One walker that takes a scope and returns the files — every gate calls it — makes F1 and F3 unrepresentable rather than merely fixed.

F5

The rule against big gate files created a 2,121-line dumping ground

internal_helpers.go — 2,121 lines, 75 functions largest policed file: 310

gate_structure_test.go fails any file over 400 lines — but only files containing func Validate. Every such file complies. internal_helpers.go contains zero func Validate declarations and is therefore exempt by construction.

So the rule didn't reduce complexity, it relocated it into the one file nothing polices. This is worth calling out because it's the pattern you noticed from the outside: a gate that looks like it enforces tidiness while creating the mess.

There's a naming split on top of it. A gate may own field-ownership.go or field_ownership.go — the test accepts either, and some own both. On ValidateFieldOwnership, the doc comment sits in one file and the function in the other.

documentation (marked red) costs 12.5 seconds to emit 648 non-blocking findings — a third of everything an agent has to read, none of which can fail the run. Moving it out of the default path is close to free.

types stays around 11.7 s even when scoped down to two files, so its cost is TypeScript startup, not corpus size. Scoping cannot fix it; a persistent or incremental checker can. This is why the single-asset cycle sits at 12–13 s against a 10 s target.

F7

Adoption is blocked in the consumer, not in the library

39 of 109 scenarios import it 3.44% of UI files median adopter: 8 files best: 19%

Breadth is actually decent — a third of scenarios with a UI already import the library. Depth is the problem: even the best adopter uses it in 19% of its files, and the median uses it in eight.

The Phase 14 report explains why. Adopting Button in one scenario required four separate workarounds: the Scenario Dependency Analyzer's apply path emits pnpm add without the file: source and hits the public npm registry (404, because the package is private); then each consumer needs a Vite source resolver, consumer-local aliases for clsx, tailwind-merge and lucide-react, and a restored package link so tsc resolves before Vite runs.

Nobody pays that four times, which is exactly the shape of the data — people import a few components and stop. The library isn't under-adopted because it's unfinished. It's under-adopted because the second import costs as much as the first.

F8

Three soft spots left in the instrument

I16 cannot fail I13 = I24 33.5% of cells unmeasured

The plan's audit of fake invariants was mostly carried out — I12 and I13 are real computations now, and the 225-entry exemption list is gone. Three items survive:

I16 is a tautology. Value and target are the same variable (float64(blocking), float64(blocking)), so "blocking gates" reports 44/44 forever and can never fail. I20 is saturated — it returns 1 if any .json file exists in a directory, against a target of 1. I13 and I24 are the same measurement: both call liveBuildFailures(), reported under two IDs with two different labels, so the report shows 26 invariants but takes 25 readings.

Separately, 1,701 of 5,079 matrix cells (33.5%) are unmeasured against a 10% target. That's already filed as debt, and it's the honest number — worth keeping visible rather than resolving by narrowing the matrix.

F9

Enough entry points that writing a new script is the cheap option

88 CLI commands / 8 groups 35 .mjs across 2 homes 19 Go cmd tools 26 pnpm scripts

You noticed agents writing .mjs files. This is why: codegen lives in two places (packages/…/tooling/ and ui/scripts/), there are 19 more tools in Go under api/cmd/, and 88 CLI commands. Finding the right existing tool costs more than writing a new one.

Two smaller traps in the same area. pnpm type-check doesn't run tsc — it runs a bespoke conformance script plus lint plus an exports check, so an agent that runs tsc directly gets different answers than the gate. And catalog gates with no gate name doesn't error; it silently runs story-grammar. The help text lists 17 valid gate names while the registry holds 57.

04

What to do, in order

Ranked by friction removed per unit of work. The first three are small and change the day-to-day feel immediately; the fourth is the one real piece of architecture left.
