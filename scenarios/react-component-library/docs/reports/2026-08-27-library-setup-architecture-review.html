The Component Library Fights Back

The library building itself is the point, and nothing here argues against it. If the catalog app cannot be built from the catalog, the catalog is not finished — that test is the whole reason to have a self-hosting library, and it should get stricter, not looser.

What is broken is narrower and more fixable: an intra-library composition edge is spelled as an external package import, which routes a dependency that should stay inside the source graph through a build artifact. That is a module-resolution defect, not a dogfooding one. The design around it is coherent and mostly already declared — the implementation has drifted away from its own doctrine in five measurable places.

This review separates three things I collapsed in the first pass: the self-use principle (correct, keep, strengthen), the declared architecture (coherent, largely already written down in catalog/config.json and the asset schema), and the implementation (which was drifted at investigation time). The dated counts and red diagrams below preserve that investigation. The verified post-implementation state is recorded here so this remains a truthful design record.

Current state · verified 2026-08-28 · acceptance still open

The lock-driven architecture is implemented in the source: governed catalog versions carry generated per-version dependency locks, the package owns its compiler without a disposable source-copy tree, graph reconciliation and dependency rank are blocking, and cache attribution uses content fingerprints with dependent selection.

The generic evidence seam is present: component-specific BAS cases and their generator are absent, the reserved generated artifact roots are empty, and the self-hosting/experience evaluators are registered. The current corpus contains 472 governed version locks plus ten source-bearing preview-harness fixtures intentionally outside the catalog-release lock inventory; zero catalog manifests retain the removed authored dependencies field, and the vacuous allowlist is 218 entries.

Package boundary tests, the API component package, and the CLI suite pass. The catalog lint gate currently fails on inherited released-source findings (63 errors), the comprehensive scenario run remains red on performance, unit, experience, and component-test/provider findings, and the authoring rehearsal has not completed because the scenario cannot start through its catalog build. Phase 16 therefore remains open; these results are recorded here so the design record does not present implementation progress as acceptance.

The intended architecture

Most of this is already written down, and it is good. I am restating it because the implementation gaps below only make sense against it — and because a coherent statement of the target is what you asked for.

Four documents describe every asset

The separation is clean and unusually well thought out: intent, reality, claims and evidence are four different documents with four different owners, and no document is allowed to assert another's content.

Dependencies point one way

catalog-asset.schema.json · doctrine 3

"DEPENDENCIES POINT ONE WAY, AND ONLY requires IS COPIED. kind carries a dependency rank: foundation < runtime-hook = runtime-service = adapter < primitive < component < pattern < page-template. An asset may requires only assets of equal or lower rank; a Button must never know about a form."

This is the rule that makes self-use safe. If it holds, the asset graph is a DAG by construction and the library can compose itself to any depth without ever forming a cycle. It is stated clearly, it is correct, and — as far as I can find — nothing enforces it. There is no rank check in any of the 41 gates.

Versions have a lifecycle, and drafts are mutable

This is the finding that most changes my first-pass recommendation. I said you needed a working state below "released." You already have one, fully implemented, and it is used by one component out of 155.

component.json carries a draft pointer. BeginComponentVersion opens a mutable draft; PublishComponentVersion freezes it into an immutable release. Only one draft may be open at a time, and writing to a released version is refused outright — "released component versions are immutable; begin a draft before writing content."

The reason agents bypass it is mundane: the draft flow is reachable only through the service and CLI, while creating library/components/AlertDialog/versions/2.0.1/ is something a filesystem lets you do for free. The immutability gate protects existing releases from being edited; nothing stops a brand-new release appearing without ever having been a draft. So the cheap path and the correct path point in opposite directions.

Gates already declare their own cache granularity

The second finding that improves on my first pass. Every one of the 41 gates in catalog/config.json carries an attribution field with exactly two values: attributable (the verdict belongs to one asset) or corpus (the verdict is only meaningful library-wide). The split is 21 attributable, 20 corpus.

That is precisely the per-component skip you asked for, already designed and already declared per gate. The cache simply does not read it — report_cache.go collapses all three source trees into one (file count, newest mtime) key and recomputes everything on any change.

The one snag is that types is declared attributable but implemented as a single whole-corpus pnpm run catalog:check, and its per-asset result is never persisted. So it is the gate that both costs the most (13.5s of an ~18s recompute, by the code's own measurement) and is furthest from honouring its own declaration.

Where implementation diverges from the design

Reframed against the doctrine above. Every one of these is the implementation failing its own declared intent — which is the good kind of problem, because the target is not in dispute.

Root

Composition edges are routed through the build artifact

515 files under library/ reach their siblings through @vrooli/react-component-library/<Name>/<version>. Doctrine 3 already says these edges live inside the asset graph. Spelling them as package imports moves them outside it, creating the cycle — and the build erases the spelling anyway, so no consumer-path evidence is gained.

The consequence is that every tool answers the same question differently: build.mjs rewrites to relative, Vite resolves through ui/node_modules to the last built dist, and the UI's tsc sees whatever dist held at the time. An agent that fixes one breaks another.

library/components/Alert/versions/1.0.2/Alert.tsx import { Stack } from "@vrooli/react-component-library/Stack/1.0.0"; ^ an intra-library edge, spelled as an external one build.mjs — transformBuildSource() rewrites it to: import { Stack } from "../../../Stack/versions/1.0.0/Stack"; ^ so the package path is never exercised from inside
What it costsThe "stuck, then start editing configs" loop. There is no single authority on what an import means, so an agent alternates between three answers.
Root

The draft lifecycle exists and is bypassed

Not a missing capability — an unrouted one. BeginComponentVersion / PublishComponentVersion implement exactly the mutable-draft-then-freeze model that iteration needs, and component.json already carries the draft pointer. One component of 155 has an active draft.

The immutability gate guards existing releases against edits. It does not guard against a new release directory simply appearing, which is the cheapest thing an agent can do. So a polish pass mints a permanent version per attempt: AlertDialog 2.0.0 through 2.0.4 are untracked in your tree right now, and AlertDialog carries nine versions in total.

The three dependency views have drifted to 94%

Three views per edge is deliberate and good: it is how drift becomes visible. But graph-reconciled is non-blocking by design, and it depends on an external typescript-code-graph scenario being indexed — when that is unavailable, every asset reports "unmeasured" rather than failing. The result is that the reconciliation has never had to hold.

I compared each component's component.json pins against the imports its latest source actually makes. 144 of 153 disagree. Nine agree. The very first component alphabetically — Alert, a P0 asset targeted at production-ready — pins Icon@1.0.0 while importing Icon@1.1.0, and imports StyleSheet and ClassMerge, which appear in neither the catalog nor the manifest.

Major

The cache ignores the attribution field it is handed

21 gates declare themselves attributable. The cache keys all 41 on one corpus fingerprint of (file count, newest mtime) across catalog/, library/ and ui/src — roughly 2,500 files. Any change recomputes everything. There is no per-asset skip anywhere in the layer.

The blocker is narrower than it looks: types is declared attributable but implemented as one whole-corpus pnpm run catalog:check whose per-asset result is never persisted. Fix that one gate's storage and the other 20 attributable gates can be keyed per asset immediately.

Major

The dogfooding claim is not measured, so it cannot be defended

Your stated test — if the library cannot build its own catalog app, the library is not complete — is the right one, and it is currently unmeasured and ungated. The catalog app uses 49 of 155 assets across 43 of its 152 files. The other 109 files are hand-rolled markup that is not proving anything about the library.

Some of that is legitimate: an editor shell and a Monaco integration are not component-library work. But a great deal of it is exactly the surface the library should be covering, and today nothing tells you which is which. The external consumers are, ironically, dogfooding harder: 35 scenarios, 358 import sites.

Major

Go gates judge TypeScript by regex, so the escape hatch is an allowlist

The 6,520-line gate package cannot parse TSX, so it matches patterns against source text — role\s*=\s*["'](?:dialog|alertdialog|menu)["'] for overlay semantics, and similar elsewhere. Regex over JSX is approximate in both directions, so correct components fail.

When that happens, the cheapest repair is a suppression entry rather than a fix. vacuous-allowlist.json is now 56 KB and 229 entries. That is your "agents mess with config files," and the setup rewards it.

What it costsSuppression is faster than repair, so quality drifts down while every gate stays green. A plausible mechanism for the regressions you keep seeing.
Contributing

The package owns no toolchain, and .mjs is the only extension point

packages/react-component-library/ has no dependencies, no node_modules, and no TypeScript. It borrows twelve type resolutions and the tsc binary from the scenario's UI app by relative path — so the consumer supplies the compiler that produces what it consumes, and a UI dependency bump silently changes what the library compiles against.

Alongside that, twenty .mjs scripts do codegen, conformance, census and two Vite plugins, plus five single-dependency pnpm projects under tools/preview-runtime-* that pin their version in the directory name. Agents writing more .mjs files are imitating the house pattern correctly; there is nowhere else to put library tooling.

tsconfig.build.json — 12 entries of this shape: "react": ["../../scenarios/react-component-library/ui/node_modules/@types/react"] build.mjs:227 const tsc = join(packageRoot,"..","..","scenarios", "react-component-library","ui","node_modules",".bin","tsc");
What it costsThe package cannot be built, validated or published independently, and there is no typed, tested place to add tooling.

How the build survived the cycle in the investigation snapshot

Worth seeing once, because it is what the lock-driven implementation removes. In the investigation snapshot, build.mjs copied library/ into a disposable .build-source tree and ran six find-and-replace passes over it. Three of those passes were per-component special cases — including one that injected five TypeScript interface declarations into MonetizationAccount.tsx at build time.

Those patches exist because an evicted version is still imported by an older released version. Since released versions are immutable, the import cannot be edited; since the evicted version is gone, it cannot resolve. The only remaining move is to rewrite the text during the build. There are 227 evicted-or-deprecated version references, 7 of whose directories are still on disk — and the list can only grow.

The version-resolution question

You caught a real hole in my last proposal. Relative paths bake the version into the path — ../../../Stack/versions/1.0.0/Stack — which makes the cascade you described worse, not better. And you are right that consumers outside the library want the unpinned form, especially greenfield.

Working through it turned up a structural defect that explains the cascade, and once that is named the design falls out cleanly.

The lock is at the wrong granularity

Immutability is a property of a version. The dependency lock is stored on the component. Alert has two released versions, 1.0.0 and 1.0.2, and one shared dependencies[] array between them:

library/components/Alert/component.json "dependencies": [ Text@1.0.0, Stack@1.0.0, Icon@1.0.0 ] ← one array library/components/Alert/versions/1.0.0/ ← governed by it library/components/Alert/versions/1.0.2/ ← also governed by it There is no per-version dependency record anywhere in the tree.

A single array cannot be true for two immutable versions whose imports differ, so the field is unfalsifiable and has drifted to 94%. This is also why exact pins in source feel mandatory today: the source string is the only per-version dependency record that exists. Put a real per-version lock in place and the source no longer has to carry the version at all.

Three ways to spell it

Recommended — resolve at publish

Drafts are unpinned; publishing freezes the resolution into the source

draft/     import { Stack } from "@vrooli/react-component-library/Stack"
           ↓  publish resolves against latest non-draft
1.0.2/     import { Stack } from "@vrooli/react-component-library/Stack/1.0.0"
           + versions/1.0.2/dependencies.json  (the per-version lock)

Authors and agents never type a version. The publish step resolves every unpinned specifier once, writes the exact form into the frozen version, and records the same resolution as a per-version lock. A released version is then fully self-describing: its imports say exactly what it was built against, and the hash ledger covers precisely what ships.

Updating Stack touches nothing. Alert@1.0.2 stays locked to Stack@1.0.0 forever, which is what immutability means. Dependents pick up the new Stack the next time they are published — a deliberate act, not an edit cascade. An explicit pin written by hand in a draft is carried through verbatim, so deliberate pinning stays available for the rare case that needs it.

This is how every lockfile-based ecosystem resolves the same tension, and it makes the 94% drift structurally impossible: the lock is generated, never authored.

Alternative — resolve at build

Released source stays unpinned; a per-version lock drives resolution

1.0.2/     import { Stack } from "@vrooli/react-component-library/Stack"
1.0.2/dependencies.json   { "Stack": "1.0.0" }
           ↓  build resolves from the lock, not from dist

Keeps authored source ergonomic forever and the resolution honest — it reads a declared lock in the source tree, never a build artifact, so there is no bootstrap cycle. The cost is that a text-transform step survives, and tsc, Vite and Vitest must all be taught the same resolver or the three-way divergence returns.

Pick this only if writing back into a released version is unpalatable. It is strictly more machinery for the same guarantees.

Status quo — pin in source, no lock

Every import carries its version, forever

1.0.2/     import { Stack } from "@vrooli/react-component-library/Stack/1.0.0"
           (no lock; the string is the only record)

This is today. It is why bumping a foundation requires minting new versions of everything above it, why build.mjs accumulates version-pin patches when a pinned version is evicted, and why the manifest pins are unfalsifiable.

One detail worth stating explicitly, because it is what makes the recommended option safe: the resolver reads the source tree, never dist. "Latest non-draft version of Stack" is answered by looking at library/components/Stack/versions/ and component.json. No build artifact participates, so there is no bootstrap cycle — which is the whole difference between this and what exists today.

The BAS cases went component-specific

Your recollection is right, and the doctrine you described is written into the one case that still follows it. bas/flows/capture-story-evidence.json describes itself as:

Alongside it there are now 36 composition cases totalling 569 KB, one per component × consumer × viewport, plus three component-specific interaction cases and one component-specific calibration case. Every version bump orphans four of these files, which is the same cascade as the import problem in a different costume.

Why it happened

Not carelessness — a gap. The experience contract is meant to carry component-specific validation, but 319 of its claims are manual-review against roughly 240 machine claims across 317 contracts. When a claim cannot be machine-proved, the only way to get evidence is to hand-write a workflow that measures it. The 36 cases are that pressure finding an outlet.

Which means the fix is not to delete them and hope. It is to give their measurements a generic home first, then delete them.

Target state and sequence

Six phases, ordered so each makes the next cheaper. The sequence below records the design rationale; the lock-driven implementation has now delivered the seams it describes. Every change remains governed by doctrine already written into the schema — none required a new architectural idea.

Add the five missing machine probe types — accessible-name, focus-containment, token-resolution, dark-parity, portal-boundary — so every measurement the 36 composition cases perform has a generic home selected by requiredCapabilities. In the same pass, move the TSX-shaped gates from regex to an AST pass in the Node layer feeding structured findings to Go. Correct components stop failing, so the allowlists can shrink instead of grow and suppression stops being the cheapest repair.

The design here is better than the implementation, which is the good way round. A declared catalog, ranked dependencies forming a DAG, immutable releases with mutable drafts, capability-driven evidence, and 41 gates that compute maturity rather than asserting it — that is a strong architecture for a self-hosting component library, and the self-use principle is exactly what makes it worth building. Nearly everything painful traces to generic mechanisms that were never built, so specific ones got written in their place: three patches in the build, thirty-six bespoke test cases, and a version string in every import doing a lockfile's job. None of the six phases requires a new idea — only finishing the ones already written down.
