Correction to the first version of this page

My first pass said the library defines no token values. That was wrong, and the architecture is better than I gave it credit for: design kits under templates/design/<style>/adapters/react-vite-tailwind/tokens.css define the ramp, and template-manager copies the selected kit's file into each new scenario as ui/src/design-tokens.css at generation time. web-console's ramp isn't bespoke — it is vrooli-default, and its spacing and radius values match the kit exactly, step for step.

The visual symptom I measured is still real. Its cause is different, and Finding 01 below now says what it actually is.

The short answer

You're right, and it isn't one thing

You said it doesn't look professional but couldn't point at a single cause. There are eight, and they compound. Five are token-layer problems — not missing infrastructure, but gaps and duplications inside infrastructure that already exists. Two are layout defects. One is a component that was never built.

The important part: none of them is a web-console problem. Every one reproduces in any scenario that builds a settings screen, which is exactly the "solve it every time" trap you described. Fixing them in the shared layer fixes them once.

01

Components are authored against fallbacks the ramp overrules

Live

Every library component writes its styles as var(--space-md, 1rem). The fallback is the only value an author can see while working — the kit's tokens.css lives four directories outside the library and isn't loaded in the file they're editing. So the fallback becomes the de-facto design decision, and it is systematically wrong:

The ramp wins, everywhere. So FormSection — drawn by someone reading 1.5rem — ships with 32px padding and an 8px radius instead of the 24px and 14px it was composed with. That is the over-padded, slightly-off look, and it's uniform across the library rather than local to any screen, which is exactly why it reads as "unpolished" without resolving to a single culprit.

02

55 tokens are referenced and defined by nobody

Blocker

Library components reference 215 distinct custom properties. vrooli-default defines 119, BaseStyles adds 19 more. That leaves 55 that no kit and no foundation defines anywhere — permanently on their fallback, in every scenario, by construction.

They aren't obscure. They're the vocabulary a component reaches for when the published ramp doesn't have the concept it needs:

FamilyUndefined propertiesWhat it means
Semantic color depth --color-field · --color-scrim · --color-overlay · --color-on-primary · --color-primary-hover · --color-border-subtle · --color-surface-sunken · --color-danger-subtle … The ramp publishes one flat value per role. Components need hover, subtle, sunken, and on-color variants and invent them.
Typography --text-subtitle · --text-body-sm · --text-heading-sm · --text-heading-lg · --text-xs · --tracking-caps · --tracking-tight · --weight-medium FormSection's own title uses --text-subtitle. It has never resolved.
Focus & borders --focus-ring-width · --focus-ring-color · --focus-ring-offset · --border-thin · --border-medium · --border-focus The ramp has --focus-ring and --border-hairline; components wanted them decomposed.
Overlay geometry --overlay-dialog-sm/md/lg · --overlay-grabber-block · --overlay-grabber-inline · --overlay-drawer-top-gap · --radius-overlay Every overlay dimension you and I have been tuning for weeks is unpublished and unthemeable.
Ramp ends --space-4xs · --space-4xl Components needed a step below 4px and above 48px. The ramp stops at both ends.

Two of the 55 are outright defects rather than gaps: --wc-kb-height — a web-console-private token — is referenced inside FullPageDrawer, BottomSheet, and DrawerShell, so the library depends on a name only one scenario publishes. (BaseStyles 1.2.0 introduced --rcl-keyboard-inset as the correct seam; those versions never migrated.) And one call site emits a malformed var(--elev-) from a template string.

03

The parity gate certifies 8% of the vocabulary

Reads green

There is a kit-parity gate — ValidateTokens in gates.go — and its remediation text states the contract exactly right: every kit must publish the full shared vocabulary, because a component authored against one kit is expected to render in all of them.

Then it checks seventeen token names. Components use 215. So the gate passes while vrooli-command-display is missing 50 of the tokens vrooli-default publishes — the entire --text-* composite set, every --radius-* step, --control-*, --focus-ring, --font-sans, --font-mono:

vrooli-conversion-landing11918 missing0

vrooli-command-display also introduces 27 --display-* properties that no library component references. Combined with the 50 it doesn't publish, it isn't a design style the shared components can render in — it's a private theme wearing the kit interface. Switching to it in the preview doesn't restyle the library; it drops half the library's declarations to their fallbacks.

A second, unrelated parity mechanism exists in themes/kit_parity_test.go, checking a different vocabulary (tailwind.theme.json sections) plus one negative assertion. Two parity checks, two vocabularies, neither of them the 215 names components actually use.

04

The same vocabulary exists in four shapes, and the SSOT holds the rejected one

Duplication

DESIGN.md opens with "DESIGN.md is the source of truth for scenario UI decisions". Its front-matter carries a tokens: block in camelCase YAML. But its spacing: section declares unit: 0.25rem — a multiplier model — while tokens.css declares an explicit eight-step ramp, and kit_parity_test.go actively asserts that --spacing-unit must never appear in any tokens.css.

Two incompatible spacing models coexist, and the file that calls itself the source of truth holds the one the tests forbid. Nothing generates tokens.css from DESIGN.md — the CSS is hand-maintained, and the drift between them is invisible.

The kit list is duplicated the same way. The Go loader enumerates templates/design/* correctly; then ThemeSwitcher.tsx hardcodes the three ids, build-preview-kits.mjs hardcodes them again in a const kits = [...], and ui-health keeps its own per-kit regex map. A fourth kit added to the registry appears in the API and in nothing else.

And the preview build reads tailwind.theme.json only — it never reads tokens.css. The kit's actual custom properties reach the preview through a separate path in preview/static.go. So your instinct that the style selector might not be grabbing the real design style is half right: it grabs the real file, but through a second pipe that nothing checks against the first.

05

Generation copies the ramp, so scenarios drift silently

Structural

template-manager copies the chosen kit's tokens.css into the new scenario as ui/src/design-tokens.css. That's a real, working mechanism, and it's why web-console's ramp matches vrooli-default exactly. But a copy is a fork the moment it's edited, and nothing compares them afterwards.

web-console's copy has since dropped 22 tokens the kit publishes. Ten of those drops are properties library components actively use, so those declarations resolve to nothing in your app right now:

Dropped tokenLibrary referencesConsequence in web-console
--sidebar-width4Sidebar sizing falls to per-component fallbacks — the surface we've spent this week on.
--touch-target4Tap-target floors unset wherever a component uses this name rather than --tap-target-min.
--layer-tooltip2Tooltip stacking order unset; z-order becomes DOM-order luck.

This is the answer to your question about how far to go migrating web-console. You don't need to migrate it — it's already on the standard ramp, because it was generated from it. What it needs is the opposite: a check that its copy still publishes everything the kit does, so the ten broken references surface and the next twenty don't happen. Its genuinely custom --wc-* palette can stay exactly where it is and shrink on its own schedule.

06

The library has a form stack. Settings aren't forms.

Missing component

There's a genuinely good data-entry stack in there: Form, FormField, FormSection, ArrayField, ObjectField, ConditionalField, ValidationSummary, even a schema-driven GeneratedForm. All of it assumes the form's shape: a draft you edit, validate, and submit.

A settings screen is the opposite. Every change commits immediately. There's no submit, no dirty state, no validation summary. The label isn't above the control, it's beside it. The description isn't help text for filling something in, it's an explanation of what a switch does. Reaching for FormField here gets you an "Optional" badge next to "Voice input" and a stacked label — both wrong.

web-console noticed and quietly built the right thing anyway: settings/primitives.tsx — SettingsSectionIntro, SettingsCard, SettingsRow, plus context-wired SettingsToggle and SettingsSlider. It's used 138 times across 14 files. That's not a local helper, that's an unpromoted library component with one consumer.

Nine library imports against 138 local-primitive uses. The controls came from the library; the layout — the part you're unhappy with — is entirely hand-rolled, and every future scenario will hand-roll it again.

07

The row stacks on mobile, even for a 44px switch

Visible in your screenshot

SettingsRow is flex-col until Tailwind's sm: breakpoint, then flex-row. On your phone it never reaches sm:, so every setting spends two lines: label, then the control alone on the next line, left-aligned.

The comment in the source explains the reasoning honestly — the control is shrink-0, so in a row the label had nowhere to go and wrapped to one word per line. But that's only true for wide controls. A switch is 44px. There was always room. The fix was applied to every row because the row has no way to know what kind of control it's holding.

The cost is bigger than a wasted line. Trailing-edge alignment is what makes a settings list scannable: you read down the left for names and down the right for states. Stacked rows destroy both columns, which is most of why the screen reads as a pile rather than a list.

08

Card-always, and keyed to the viewport instead of the container

Design decision

Your instinct is right and it's the standard call: inset cards when there's room, full-bleed grouped lists when there isn't. iOS has shipped exactly that split for a decade; Android's preference screens do the same. On a 390px screen a bordered card costs 2px of border, 32px of horizontal padding, and a radius that visually eats the corners — inside a drawer that already has its own gutter. Nested containers, no information added.

Worse, the one responsive step FormSection does have is @media (max-width: 30rem) — a viewport query. Your desktop settings content pane is roughly 700px inside a 1400px viewport, so it never fires. A component that can appear in a drawer, a pane, and a dialog cannot key off the viewport and be right in all three.

The library already knows this: DescriptionList, DataTable, and ResourceCollection all use container-type: inline-size. The pattern is established. It just hasn't reached the form layer.

The proposal

What I'd add to the library

One component family, named for what it is rather than where it first appeared, so it reads correctly in a scenario that has no "settings" screen: 

// @vrooli/react-component-library/SettingsList

<SettingsList
  // "auto" is the whole point — grouping affordance is a
  // function of available width, resolved by container query.
  variant="auto" | "card" | "flush"
  density="comfortable" | "compact"
>
  <SettingsList.Intro eyebrow title description />

  <SettingsList.Group label="Capture">
    <SettingsList.Row
      label="Voice input"
      hint="Enable speech-to-text controls throughout the workspace."
      // declares the control's appetite for width, not a breakpoint.
      // "compact" never stacks; "wide" stacks only while cramped.
      control="compact"
    >
      <Switch />   // takes its accessible name from the row
    </SettingsList.Row>
  </SettingsList.Group>
</SettingsList>

Sequencing

What to do, in what order

Almost none of this is new infrastructure. The registry, the generation-time copy, the preview pipe, and a parity gate all exist and work. The task is closing the vocabulary, widening the gate until it actually covers that vocabulary, and collapsing the hand-maintained duplicates — then the component.

Steps 1–2 are the gate. Publish SettingsList before them and you'll tune it against fallbacks the ramp overrules, shipping the same authored-vs-rendered mismatch that produced Finding 01.

follow-up
Decisions

Settled, with what they cost

1 · tokens.css is the authority

DESIGN.md keeps its prose and loses its token blocks; tailwind.theme.json and Tokens.tsx get generated. The reason is not preference — DESIGN.md holds two token blocks that disagree with each other, names the error role error where the nested block says danger, has already drifted from the CSS (rounded.lg: 1rem vs --radius-lg: 0.75rem), and contains no spacing ramp at all.

One wrinkle to settle while implementing: there are two CSS ramps, not one. rampfile.go reads values from react-component-library/ui/src/design-tokens.css, not from the design kit — plus a hardcoded 29-property fallback list. That RCL ramp is the de-facto authority already. Make it the declared one, and let kits express overrides against it rather than each redeclaring all 119 properties.

2 · Kit compatibility is derived, not declared

Replace hand-written designStyles[] affinity with a computation: a component's required tokens are already derived at index time by ExtractRequiredTokens; intersect that set against each kit's published vocabulary and the answer falls out. Four verdicts, and the middle two are the ones that don't exist today:

VerdictConditionTodayMeaning
universal Every kit satisfies it51 Adoptable anywhere.
restricted Some kits satisfy it51 Valid, but only in the named kits. Search and adoption must respect it.
unsatisfiable Every token exists in some kit; no single kit has all 0 A composition error — renderable only in a kit that doesn't exist.
undefined‑vocabulary A token no kit defines59 A vocabulary error. Different owner, different fix.

0 unsatisfiable is the good news: the case worth worrying about is real in principle and empty in practice, so it needs a slot in the model but blocks nothing. 59 undefined-vocabulary — 37% of the library — is the same 55-token gap from Finding 02 seen per component, driven by --color-border-strong (22 components), --text-body-sm (16), and --text-subtitle (12).

Of the 51 restricted: 45 are satisfied by vrooli-default and vrooli-conversion-landing but not vrooli-command-display, 5 by default alone, and one — BoundedMeter — by conversion-landing alone, because it needs --color-border-subtle, which only that kit publishes. Its manifest declares vrooli-default as its native style. Its native style is the one kit that cannot render it.

That is the argument for deriving rather than declaring, and it generalizes: 16 components overclaim their affinity — asserting compatibility their tokens contradict — against 85 that are consistent. Nothing today can catch that, because the metadata is advisory prose and the token contract is computed somewhere else that never compares them.

Keep one hand-declared field, narrowed to what humans actually know and machines can't derive: aesthetic fit. A dense data table can be perfectly token-satisfiable on a TV kit and still be the wrong component at four meters. The rule that ties them together is one line — declared affinity may never be broader than derived compatibility — and it fails on exactly those 16 today.

Kit inheritance and this model compose rather than compete. If kits inherit a base vocabulary and override, restricted collapses toward universal on its own, unsatisfiable becomes nearly impossible to construct, and vrooli-command-display's 50 gaps close without anyone inventing 50 values for a screen nobody is building yet.

3 · The threshold stays at 34rem

The two real surfaces are 390px and ~924px, so every value between 26rem and 44rem produces identical output today. 34rem sits in the middle of that dead zone, which makes it the most robust choice if a mid-width surface ever appears, and it puts a 768px tablet in card mode — matching the platform convention on both iOS and Android. Pinned by a story at 544px so the boundary is visible if it ever moves.

Ahead of all of it

The sync can't see how the library is used

components tokens-sync exists and is well-built: it derives each version's token requirements from source, resolves a closure, and writes the union into a managed rcl:tokens region in the scenario's design-tokens.css. 37 scenarios have that region. Two recorded decisions from 2026-08-13 govern it, and both are sound.

Neither anticipated consumption without adoption. Sync collects requirements by walking the adoption ledger, and the library is now consumed mostly by package import — which creates no ledger row.

The 17 unrecorded components include SidebarShell, Switch, Slider, Input, Checkbox, Textarea, NumberField — essentially every control on the settings screen this page is about.

The existing import scanner in versionledger can't be reused as-is. It was built for retention, so it deliberately ignores unpinned specifiers: a bare import says nothing about any particular version and must not pin one against retirement. Correct for retention, inverted for tokens — a bare import tells you the component is used, which is all sync needs.

Until this is fixed, do not run tokens-prune. It removes any managed token the ledger does not require, so on web-console it would strip tokens that 17 imported components genuinely need.

Decision 4

Two changes, and they do different jobs

These are easy to conflate. One makes sync accurate; the other makes the system fail-safe when sync has not run at all.

A

Sync keys off what the scenario uses, not what the ledger says

Walk the scenario's ui/src for library import specifiers, resolve bare and partial pins the way the export map resolves them, and union the closure's requirements. Declarations outside the managed region stay untouched — that is already guaranteed by the delimited-region design and does not change. This also makes tokens-prune safe, because prune and sync finally agree on what "used" means.

Cheaper than it sounds: RuntimeWrittenTokens already walks ui/src for a neighbouring purpose, and a shared walkScenarioSources helper already feeds two other classifiers. This is one more matcher on a walk that already happens.

fixes the
reported problem
D

The library publishes its own defaults in a cascade layer

BaseStyles emits the full ramp inside @layer rcl.tokens { :root { … } }. This changes no value a scenario has set. It supplies a value only where the scenario has none — and "none" today does not mean unstyled, it means the component falls back to whatever its author typed in var(--space-md, 1rem). So it replaces the author's private guess with the canonical value as the floor. A change of default, not a change of values.

The mechanism is the elegant part: unlayered styles always beat layered ones, regardless of source order. A scenario's existing design-tokens.css is unlayered, so it wins automatically — no ordering discipline, no specificity war, no !important. The library uses no cascade layers today, so there is nothing to collide with.

removes the
failure class

D lands on decision #2's own stated revisit trigger — a future scenario template exposes a typed theme service that can satisfy the same contract without source files. A cascade layer is that contract, delivered in CSS instead of a service. A stays within decision #1's spirit, extending "derive from source" from the library's source to the consumer's.

One sequencing risk: D makes scenarios that were coasting on a fallback shift to the ramp value. That is Finding 01's drift being corrected, and it should land deliberately — before an adoption sweep, not during one.

Decision 5

Not every token should be a scenario's to change

A scenario experimenting with its palette is the system working. A scenario lowering the tap-target floor is a defect wearing a preference's clothes. Three tiers, and the strictest one already exists in embryo.

TierCoversScenario overrideWhy
Expression Colors, surfaces, fonts, elevation, motion durations, radii Free This is what a design style is.
Rhythm The spacing ramp, control sizes Warns Not independent values — every component's internal proportions are built on their ratios, so moving one step desynchronizes that component from itself. A scenario wanting denser UI should derive a kit, not poke --space-md.
Contract --tap-target-min · --layer-* · --rcl-safe-* · --rcl-keyboard-inset · --color-focus · --opacity-disabled Never A wrong value here is a defect, not a preference: an accessibility floor, a relative stacking order, or a runtime-computed viewport value.

The Contract tier is not a new idea — tokens-sync already removes runtime-written tokens from the managed region, reasoning that it prevents a stale default racing the runtime writer. Tier 3 generalizes that from "the app computes this" to "this is not yours to set."

The tier belongs on the token, declared once alongside the vocabulary in tokens.css — the authority Decision 1 settles on. Then each surface behaves differently per tier: Expression syncs and is left alone, Rhythm raises a gate finding when a scenario overrides it, Contract never enters the managed region at all.

An honest limit: Contract cannot be locked. A scenario can write CSS anywhere, so this is a gate finding rather than a mechanism — except for the runtime tokens, which sync already removes outright.
