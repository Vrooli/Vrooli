React Component Library · Adoption Path Review

Why a Button doesn't survive the trip

The governed adoption path is better than it looks: 36 of 39 scenarios went through adoptions link and got locale keys, a strings provider and a selector registry wired automatically. But the path is blocked at step zero for every asset in every scenario by a misspelled config key — and link never syncs design tokens, so components render against variables nothing defines.

branch agi measured 2026-08-31 39 adopting scenarios swept

You suspected the adoption setup was buggy. It is — but the machinery is mostly built, and the failures are a chain rather than a scatter. One typo makes preflight refuse every adoption, so its blocking signal is noise everyone routes around. adoptions link never runs tokens-sync, so even correctly linked scenarios render components against undefined CSS variables. That is the regression you keep seeing.

Measured across the 36 scenarios where preflight runs: 36 of 36 report blocking: true, and only one has every token it needs. The median adopter is missing 10 of 92 required custom properties; the worst is missing 73.

The library is red right now. Two unused React imports in released versions of PinInput and ValidationAdapter fail noUnusedLocals, so vrooli scenario start fails at the UI build and the whole API — preflight, tokens-sync, gates — is unreachable.

01

What adoption actually requires

Seven steps from "I want a Button" to "it renders correctly." Green means it works today, amber means it works but costs manual effort, red means it's broken.

0

Read the contract broken

react-component-library adoptions preflight controls.button web-console

This command is exactly right in concept — it returns required tokens, satisfied tokens, dependency verdict, i18n and selector verdicts, and a maturity rung. It's the best-designed thing in the adoption surface.

It fails outright on 3 scenarios (generation.template.id not declared) — two of which are the Phase 14 pilots. And on the 36 where it runs, it returns blocking: true every single time, for reasons covered in B1 below.

1

Install the package broken

The Scenario Dependency Analyzer approves the local package, then its apply path emits pnpm add --workspace-root @vrooli/react-component-library without the file: source. The package is private, so this hits the public npm registry and returns 404.

Every consumer must instead hand-write file:../../../packages/react-component-library into their manifest. The Phase 14 report flagged this as the one action it left open; it's still open.

2

Make the package resolve manual

The library's compiled modules import themselves by package name — @vrooli/react-component-library/Pressable/1 appears inside Button.js. That's a legitimate pattern, but it means a consumer aliasing the package to source must alias the self-references too.

In practice each consumer adds a Vite source resolver, local aliases for clsx, tailwind-merge and lucide-react, and a restored package link so tsc resolves before Vite runs. Four pieces of config per scenario, none generated.

3

Import the component works well

import { Button } from "@vrooli/react-component-library/Button/2";

This part is well designed. 493 export subpaths give you ./Button (latest) and ./Button/2 (major line, currently resolving to 2.2.4). Pinning to a major line means a consumer picks up patches without breaking changes.

One caveat: importing from the package root pulls a 248-module barrel that references mermaid and shiki. Always use the subpath.

4

Supply the design tokens the regression

react-component-library adoptions tokens-sync <scenario>

A Button requires 92 CSS custom properties — colors, control sizes, durations, easings, elevations, layers, radii, spacing, text ramps. The package ships no CSS at all; the consumer's own theme must define them.

There is a command that does this, and it works. 33 of 39 adopting scenarios have never run it — 287 missing declarations in total. The two Phase 14 pilots don't even have a design-tokens.css file.

This is why components look right in the library and wrong everywhere else. The library's own preview app defines every token in ui/src/design-tokens.css (411 lines) — 20 of which exist nowhere else in the library. Components are developed against a theme that never ships.

5

Text and translation works via link

Zero-config default: useStrings(key, fallback) resolves to the literal fallback when no provider is mounted, so a freshly imported component renders correct English with no setup.

Localization is wired by adoptions link, not by importing the strings module. Link reads the asset's .strings.ts, derives the key/value pairs, merges them into the consumer's ui/src/i18n/locales/en.json, and mounts LibraryStringsProvider into main.tsx between managed markers. 36 of 39 adopters have all of it.

Two real limits. The derivation runs a regex over source text rather than reading a structured export, so a strings file written in an unexpected shape silently yields no keys. And link reads the library source tree, not the published package — the 85 compiled .strings.js modules in dist are exported by nothing, so this mechanism only works inside the monorepo. An external consumer of the published package has no localization path at all.

6

Selectors for tests works via link

Components stamp data-testid derived from their catalog id — a Button renders data-testid="controls.button" with data-control-slot="icon" and "label" on its parts.

adoptions link generates ui/src/consts/selectors.library.ts in the consumer and composes it into the scenario's own selectors.ts registry. 36 of 39 adopters have it.

Two rough edges: 26 assets have interactive elements with no derived testid (the selector-coverage gate reports them), and the findings stream mixes two identifier vocabularies — overlays.alert-dialog next to react-component-library:SelectionControl.

7

Styles arrive on their own works well

No CSS import, no bundler plugin, no stylesheet ordering problem. Authored CSS is inlined into the emitted module and injected at runtime by useLibraryStyleSheet, which mounts one <style data-rcl-sheet> node per key at the start of <head> so consumer styles win equal-specificity ties. This is a genuinely nice piece of design.

One gap for later: the injector early-returns when document is undefined, so there is no SSR story — a server-rendered consumer gets unstyled markup on first paint.

03

Five concrete bugs

Each verified in source today. B1 is the one that gates everything else.

B1

A misspelled config key blocks every adoption in the system

catalog/config.json declares: "adoptionMaturityFloor": "scaffolded" handlers/catalog/readiness.go reads: `json:"adoptionMaturityFloor"` → "scaffolded" ✓ internal/adoptions/maturity.go reads: `json:"x-adoptionMaturityFloor"` → "" → defaults to "verified"

The adoption path reads a key that does not exist, gets an empty string, and silently falls back to verified. Achieved rungs are computed from gate evidence and currently sit at scaffolded for every asset, so the comparison is rank 1 < rank 3 — blocking for every asset, in every scenario, permanently.

Meanwhile catalog readiness reads the correct key and correctly reports gap: 0. Two subsystems, one config file, opposite conclusions.

This is why --override-validation exists on apply, eject, batch-apply and reapply: the escape hatch was added because the gate always fires. A blocking signal that is always on teaches everyone to bypass it — which is exactly what the Phase 14 pilot did.

B2

A shipped module imports a subpath the package doesn't export

dist/support/VoiceInputButtonGlyph/4.3.1.js import { withClassName } from "@vrooli/react-component-library/ClassMerge/1.0.2"; package.json exports: "./ClassMerge" · "./ClassMerge/1" ← no 1.0.2 entry

An exact-version subpath that the exports map does not declare. Any consumer whose bundler reaches this module fails to resolve it.

The specifier-shape gate does catch this class of defect — it reported three exact pins in VoiceInputButton. It missed this one because the asset lives in library/support/, a sixth asset kind whose layout doesn't match the others: files sit at support/<Asset>/<version>.tsx with no versions/ segment. The shape census only counts directories under a versions/ segment, so the entire support/ kind is invisible to the "one canonical shape" invariant.

B3

An undeclared external dependency

dist/hooks/useVoiceInput/versions/3.0.0/useVoiceInput.js import { useVoiceCore } from "@vrooli/audio-capture-browser"; package.json: not in dependencies, not in peerDependencies → unresolvable

Any consumer importing useVoiceInput gets a resolution failure. Nothing catches it: no gate validates that a bare external import is declared in the package manifest. That's a missing check, not a broken one.

Only three assets need the heavy four — code-block, markdown-renderer, and mermaid-diagram. Making them optional peers behind their own subpaths would cut the install cost of adoption dramatically without changing a line of component code.

B5

"Not measured" quietly counts as "fine"

Preflight's i18n_verdict and selector_verdict come from stored gate evidence, and return not-measured when no evidence row matches. But the blocking rule only blocks on fail — so an asset with no i18n or selector evidence passes adoption silently.

The library states the opposite principle elsewhere and enforces it well: a gate that inspects zero inputs raises "treat this as a runner fault, never as a pass." The adoption seam is the one place that rule isn't applied. Given 33.5% of the gate matrix is currently unmeasured, that's a wide gap.

05

How to make adoption reliable

In order. The first two are small and unblock everything downstream; the rest turn a manual procedure into a governed one.

1
Fix the floor key in maturity.go
One lineunblocks all
Read adoptionMaturityFloor, not x-adoptionMaturityFloor. Then delete the empty-string fallback — a missing floor should be an error, not a silent promotion to verified. Add a test asserting readiness and preflight report the same floor.
2
Run tokens-sync for all 33 scenarios
Mechanicalfixes the regressions
287 missing declarations, one command each. This alone should visibly fix component rendering across the ecosystem — and it's the thing that has been silently undoing your component-quality work.
3
Make tokens-sync part of adoption, not a follow-up
Smallprevents recurrence
Have adoptions link and apply sync tokens as their last step. A component that can be adopted without its tokens will keep being adopted without its tokens.
4
Repair the analyzer's local-file apply
Mediumcloses step 1
Emit the file: source instead of a bare pnpm add. Until then every new consumer starts by debugging a 404 on a package that was never on npm.
5
Harden locale derivation; export strings for external consumers
Smallcompletes i18n
Link derives locale keys with a regex over source text — a strings file in an unexpected shape yields no keys, silently. Read the structured export instead. Then add a ./<Asset>/strings subpath so a consumer outside the monorepo has a localization path at all.
6
Gate the package manifest against dist imports
Mediumcatches B2/B3
One check: every bare import in dist resolves to a declared dependency, and every intra-library subpath exists in the exports map. That's both broken imports caught, plus the whole class.
7
Bring library/support/ into the canonical shape
Mediumcloses the blind spot
17 files in a sixth layout that the shape census cannot see, which is why the "one canonical shape" invariant reads clean while a broken import sits inside it.
8
Make heavy dependencies optional
Mediumcuts install cost
Move mermaid, shiki, react-markdown and remark-gfm to optional peers used by three assets. Move react-dom to peers and the @types packages to dev.
9
Treat not-measured as blocking in preflight
Smallafter 1–2 land
Apply the library's own rule — unmeasured is never a pass — to the adoption seam. Do this after the floor fix, so the first honest blocking signal isn't immediately drowned by a second always-on one.

Numbers came from sweeping adoptions preflight across all 39 adopting scenarios, the full gate matrix, and static analysis of the published dist and exports map. The scenario API stopped partway through the sweep; the per-scenario preflight results were captured while it was up, and the source-level findings (B1–B4) are static and independent of it.
