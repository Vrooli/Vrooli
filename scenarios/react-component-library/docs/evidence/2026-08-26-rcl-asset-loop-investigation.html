Pipeline 1 of 2

How an asset gets proved

Everything hangs off one immutable version directory. The contract declares what to render; the specimen renders it; the browser proves it; the gates read the proof. Nothing in this chain re-derives an earlier step — which is why a mutation at the left end invalidates everything to its right.

01 · DECLARE
Asset manifest
Catalog id, category, slot, latest version, dependency edges.
component.json
02 · IMPLEMENT
Version directory
Frozen once released. Adopters pin it by content hash.
versions/1.3.6/ · BottomNav.tsx · styles.ts · *.strings.ts
03 · SPECIFY
Story contract
Declarative. Args, fixtures, composition, and one entry per story with a role.
story.json
04 · COMPOSE
Specimen module
Real React. The contract points at named exports here rather than describing a DOM tree in JSON.
story.tsx
05 · SERVE
Preview harness
Vite kit renders one story per route, or up to four tiled on a sheet route.
?stories=a,b,c,d
06 · CAPTURE
BAS execution
Drives interactions, asserts expectations, returns screenshots plus an accessibility bundle.
bas-screenshotbas-story-sheet
07 · RECORD
Evidence rows
One row per asset × version × gate × target, hash-stamped to the source it proved.
sqlite: evidence
08 · JUDGE
36 gates
Go, in the scenario API. Each has calibration fixtures so the gate itself is tested.
internal/gates/
authored by hand or agent machine-produced judgment

Two properties of this chain matter for everything below. First, evidence is bound to a content hash, not to a version number — so editing a released file doesn't just risk breaking adopters, it detaches every screenshot and every gate verdict already recorded against it. Second, the gates read declarations, not implementations. They ask the contract what it claims to cover and check the claim. They don't ask the TypeScript what it could cover.

Root cause

Why validation doesn't push toward the ideal

The story grammar you wanted exists. The gate that enforces it can be satisfied by declaring nothing.

Schema v5 introduced exactly the vocabulary you described in the second update — stories stopped being a flat list and became three kinds of question:

role: "anatomy"
What is this thing?

Exactly one per contract. The canonical rendering, free of matrix or boundary-only variation.

Text → "Default anatomy"
role: "axis"
How does it vary?

One story per dimension, rendering every option at once. covers records which values actually appeared. This is your "matrix, not a list".

Text → axis: "textStyle"
covers: 8 styles in one frame
role: "boundary"
Where does it break?

Drawn from a closed vocabulary: empty, truncate, overflow, loading, error, disabled, rtl, forced-colors.

Text → states: empty, truncate,
overflow, forced-colors

Text/1.1.0 is now exactly the shape you asked for: four stories — one anatomy, an eight-value style matrix, a four-value tone matrix, and a boundary frame. That's the exemplar. The problem is that it's an exemplar and not the norm.

143/302
contracts with exactly one story
59/728
stories that declare an axis
214/302
contracts declaring zero arg fields
443/728
stories rendering a single specimen

Here is the mechanism, in the gate's own logic. It walks contract.Args.Fields, and for each field of kind enum it demands a matching axis story:

api/internal/gates/gates.go — ValidateStoryGrammarline 884
// the obligation is derived from what the contract declares…
for _, field := range contract.Args.Fields {
    if field.Kind == components.StoryFieldEnum && !axes[field.Path] {
        // …"enum axis %q has no axis frame"
    }
}
// …so a contract that declares no fields owes no axes.

Now look at Alert. The component exports a four-value union:

Alert/versions/1.0.1/Alert.tsxthe implementation
export type AlertTone = "info" | "success" | "warning" | "danger";
Alert/versions/1.0.1/story.jsonthe declaration
{
  "args": { "fields": [] },        ← declares nothing, so owes nothing
  "stories": [
    { "id": "default", "role": "anatomy" }   ← one story. gate passes.
  ]
}

Alert 1.0.0 had four stories. Alert 1.0.1 has one. Coverage went down, the gate stayed green, and nothing in the pipeline noticed — because the only thing that could have noticed reads the same file that shrank.

This generalizes past stories. Every gate in the system judges a declaration against itself. That's a coherent design when a human authors the declaration and the gate catches drift. It inverts when an agent authors both sides: the cheapest way to pass is to declare less, and 214 contracts have found that path.

The fix is a direction change, not a new gate

Derive the obligation from the implementation, not the contract. The prop types are right there — a union type on a prop is an axis whether or not the contract admits it. Parse Alert.tsx, find AlertTone, require an axis frame covering all four values. The same inversion applies to i18n (a JSX string literal is an unkeyed string, regardless of whether a .strings.ts exists) and to selectors (an interactive element without a data-testid is uncovered, regardless of what the manifest lists).

That single change turns 214 silently-compliant contracts into 214 actionable findings, and it makes "declare less" stop working as a strategy.

Fault 1 · The bundler has no CSS loader

The story bundler configures esbuild with Bundle: true, Write: false, and an explicit loader map covering .js, .jsx, .ts, and .tsx. There is no .css entry and no Outdir. The moment a component does import "./Text.css", esbuild has a CSS file it must emit somewhere and nowhere to put it:

api/internal/preview/bundler.goline 50
Loader: map[string]esbuild.Loader{
    ".js":  esbuild.LoaderJS,
    ".jsx": esbuild.LoaderJSX,
    ".ts":  esbuild.LoaderTS,
    ".tsx": esbuild.LoaderTSX,
    // no ".css" — and Write:false with no Outdir
},

That produces the exact string you saw. Live, just now:

GET /preview/react-component-library:MorphingIcon/harness.html?version=2.0.9HTTP 400
bundle failed: primitives/MorphingIcon/versions/2.0.9/story.tsx

Cannot import "../library/primitives/MorphingIcon/versions/2.0.9/MorphingIcon.css"
into a JavaScript file without an output path configured

Exactly 15 library files import a sibling stylesheet, and all 15 fail. The set explains why the tab feels universally broken — these are the typographic and layout primitives you look at most:

Text · Icon · MorphingIcon · Stack · Inline · Container · Surface · Badge · Link · Separator · Skeleton · Spinner · ScrollArea · EdgeFade · SearchInput

One caution for whoever fixes it: adding a .css loader is necessary but not sufficient. With CSS in the graph esbuild emits two output files, and the code returns result.OutputFiles[0].Contents unconditionally — it would start serving a stylesheet as the ES module. The cleanest fix is an OnLoad plugin that turns a .css import into a module which injects a <style> tag, since the harness already injects design-system CSS the same way; that keeps the output single-file and preserves the component's styling in the preview.

Fault 2 · Every authoring error reports as a server fault

The harness error writer classifies exactly three typed errors — component not found, path escape, bundle failure — and sends everything else to a default branch that logs and returns preview: internal error. Meanwhile resolveStory produces six distinct failure causes, and every one of them is an untyped fmt.Errorf. Reproduced:

BottomNav 1.3.6 — real story ids vs. an unknown onelive
?version=1.3.6&story=mobile-primary   HTTP 200
?version=1.3.6&story=disabled-item    HTTP 200
?version=1.3.6&story=long-labels      HTTP 200
?version=1.3.6&story=anatomy          HTTP 500  preview: internal error
?version=1.3.6&story=bogus-story-id   HTTP 500  preview: internal error

A story id that doesn't exist in the contract is an authoring mistake with an obvious message — "story x not found; this contract declares mobile-primary, disabled-item, long-labels". Instead it surfaces as an opaque 500. The same branch swallows an unparseable contract and a missing contract. Give those causes typed errors and map them to 404 and 422 with the resolver's own text, and a whole class of "the preview is just broken" turns into a fixable sentence.

This also matters for how you read the tab: a 400 means the component's code is wrong, a 500 currently means almost anything.

Fault 3 · Pinch zooms the page because preventDefault is a no-op

The canvas does try to stop it. The handler is a React onWheel prop that calls event.preventDefault() — but React 18 (this project is on 18.3.1) attaches wheel, touchstart, and touchmove at the root as passive listeners. A passive listener cannot cancel the event; the call does nothing and the browser logs a warning. The gesture falls through to the browser and zooms the page.

There's a second bug hiding behind the first: the handler never checks ctrlKey. A trackpad pinch is wheel with ctrlKey: true; ordinary two-finger scrolling is the same event with ctrlKey: false. Both are currently treated as zoom, so the canvas can't be scrolled at all.

The fix is one useEffect: attach the listener natively to the canvas ref with { passive: false }, then branch — ctrlKey zooms, everything else pans. The existing touch-none class handles touch devices already; it has no effect on trackpad wheel events, which is why the class being present didn't help.

Fault 4 · Drag-and-drop is disabled by the element it's attached to

I checked the obvious suspects first and they're all fine. The draggable attribute and both drag handlers pass cleanly down IconButton → Pressable → ControlBase → <button>; every hop spreads its props. updateCanvasDropTarget calls preventDefault and sets dropEffect, which is what makes a drop zone accept a drop. The pan handler's setPointerCapture correctly bails out when the pointer starts inside a specimen card, so it isn't stealing the gesture. And the drop math uses getBoundingClientRect, which reports post-transform coordinates, so it stays correct at any zoom level.

What's left is the handle itself. The grip is an IconButton, which renders a real <button>, and Chromium and WebKit do not reliably start a native HTML5 drag from a form control — the control's own activation behavior consumes the gesture. This is the long-standing reason drag handles are conventionally a div or span rather than a button.

Two ways out. The small one: render the grip as a <span role="button" tabindex="0"> so it keeps its keyboard affordance and its accessible name while becoming genuinely draggable. The better one: drop HTML5 drag entirely and reorder with the pointer events the canvas already handles — that fixes touch reordering at the same time, which native drag will never give you. The keyboard path via moveCaseByKeyboard already works and should stay either way.

The absence of squiggles isn't a styling problem or a marker that failed to render. There are no markers. Ecosystem fit

Where this system sits, and where it doesn't

I had this substantially wrong in the first pass. The corrected version is more interesting than what I originally wrote, and it changes the recommendation.

Correction to the first draft

I wrote that the catalog's gates are invisible to everything outside the scenario, and prescribed surfacing them to the control plane. The first half overstated the isolation and the second half pointed at the wrong home.

What's true: nothing in internal/ knows what a story contract is — verified. What's false: that nothing outside consumes the catalog. ui-health already integrates with react-component-library through a typed, proto-governed seam, and the control plane is not where UI conformance belongs anyway.

The seam that already exists

There are twelve *-health scenarios, and one of them owns exactly this territory. ui-health defines an InventoryService proto and react-component-library implements it — the catalog is a registered provider to the health scenario, called over Connect with URL re-resolution and transport-failure retry. That is a properly built ecosystem seam, not an absence of one.

ui-health also carries 44 of its own UI checks, and several are the adopter-side counterparts of the catalog's gates:

The two real defects

First: the seam carries inventory, not conformance. ScanScenarioResponse returns provenance, widget declarations, and surface records. There is no field for a gate verdict. ui-health can tell you that a scenario vendors BottomNav 1.2.0 while the catalog's latest is 1.3.6; it cannot tell you that 1.3.6 currently fails released_version_immutable. The pipe exists and the conformance signal isn't in it.

Second — and I got this wrong twice before landing on it. There is no Makefile target, CI workflow, or internal/ caller that runs the health scenarios, which is what I first reported. But that was looking in the wrong place: test-genie runs them as phases. The last full run has a ui-health phase that passed with 30 findings. So cadence exists.

The real failure is one layer in, and it's covered in full in the next section: the phase that validates the library itself hit its deadline, reported zero blockers, and disappeared from the verdict set. The run went red for docs, security, and tidiness — and stayed completely blind to 207 immutability errors.

The draft lane exists and has never been used

Every manifest carries a draft field. Across 221 assets it is empty 221 times.

This is a structural cause of the immutability break, not just a curiosity. An agent performing a mechanical migration — rewriting import specifiers, hoisting i18n hook calls, adding selectors — has three options: bump every touched asset to a new version, land the change in a released directory, or do nothing. The first is absurd at 293 files. The third fails the task. So it took the second, and the gate lit up 207 times.

Give mechanical work a draft lane to land in, and the pressure that produced the breach goes away. That is a better fix than any amount of reminding an agent not to edit released files.

So the version work is three things, none of which is reaping:

  • Use the draft lane. Mechanical migrations land in draft, get reviewed once, and release once — instead of either N bumps or an in-place rewrite.
  • Declare retirement instead of performing it. Populate deprecatedVersions when a version is dropped, so evidence and tests attached to it become findable orphans rather than silent ones.
  • Attach evidence to a version range, not a directory. The reason a retired version strands its tests is that the test lives inside the directory. This is the deeper fix and the largest of the three.

Why it can't finish, and what makes skipping possible

Three compounding reasons, each fixable:

  • It runs serially. The descriptor sets "concurrency": {"mode": "provider-serial"}. Every asset waits for the one before it.
  • It validates history. There are 328 version directories against 221 asset manifests — 107 of them, a third of the surface, are neither latest nor draft. Nothing imports most of them. Your instinct to scope runs to draft plus current would cut the work by a third immediately, and it would eliminate a large share of the evidence_freshness noise by construction, since much of that noise is stale evidence on abandoned versions.
  • It deliberately opts out of caching. The descriptor sets "determinism": "observational", with a stated reason: catalog releases and recorded evidence change outside the target scenario's files, so test-genie's file-digest cache would give wrong answers. That reasoning is correct — but the consequence is that every run is a full run, forever.

That last one is the interesting one, because the skip primitive already exists — just not where test-genie can see it. The catalog records a content hash per asset version; that's how released_version_immutable can say "recorded 0b46a905, current 555a86e5". Evidence rows are keyed by asset × version × gate × target. So the provider can already answer "which assets have a source hash that differs from the hash their last verdict was recorded against" — which is precisely the skip decision.

The fix isn't to flip determinism to deterministic and let test-genie cache on file digests; that would reintroduce exactly the wrongness the descriptor is guarding against. It's to keep the phase observational at the test-genie layer and make the provider incremental internally: it enumerates draft plus latest, diffs each against its recorded evidence hash, validates only the drift, and reports the skipped set explicitly so a run can never look complete when it wasn't.

One small thing to fix along the way: the report digest at runner.go:334 mixes report.CreatedAt into its hash, so two identical runs produce different digests. Nothing downstream can ever treat a report as unchanged while that's true.

The throughline: five enumerations of the catalog, all different

This keeps surfacing, and it's the reason "the whole library passes" is currently unachievable even in principle. Five places decide which assets exist, and no two agree:

package.json exports — all kinds, canonical enumeration shared with the indexer and health adapters
catalog/config.json appliesTo — 11 kinds, the most complete declaration
indexer.go registryAssetPath — components, primitives, foundations, hooks; services missing, foundations rejected downstream anyway (205 rows / 221 manifests)
test-genie.json applicability — library/components/* and library/hooks/* only, so changing a primitive doesn't even trigger the gating phase
ui-health standard_component_version_staleness — library/components only

Pick one as canonical. catalog/config.json is the obvious candidate — it is the most complete, it already expresses kinds rather than paths, and it is the file the ratchet lives in. Everything else should derive from it rather than restate it.

Yes, and it's four changes rather than a redesign.

Make the timeout a blocker

Honor the descriptor's own "unavailable": "fail". A phase that dies must not report blockers=0 and must not vanish from the verdict set. This is the one change that makes "can't be green unless the library passes" true, and it's independent of everything else — though expect it to turn the run red immediately, which is the correct outcome.

Q1, the hard part

Component granularity without hardcoding the catalog

You asked how per-component invocation and version skipping can work when ui-health, experience-health, and workflow-health all validate a scenario as a whole — without teaching those scenarios what react-component-library is. There are three separable problems and the tree already answers two of them.

First: there is no sub-scenario subject in the target model

test-genie's phase descriptor schema constrains targets.kinds to a closed enum:

scenarios/test-genie/schemas/test-genie-phase-descriptor.schema.jsontargets.kinds
"enum": ["scenario", "resource", "tool", "safeguard", "team",
         "package", "control-plane", "docs", "project"]
// nothing smaller than a whole scenario

That is the structural reason "validate just this component" cannot be expressed. The fix is generic and precedented: add an asset kind. Any scenario that owns a versioned catalog can then enumerate sub-targets — the catalog is not special, it's just the first one with a reason to. The enum has already been widened before; 28 phases target scenario and another 25 target the eight other kinds, so extending it is a proven move rather than a new mechanism.

With that in place, test-genie enumerates the subjects and each health scenario validates what it is handed. None of them learns what a component is.

Second: the skipping lever already exists — I was wrong about needing to build it

I previously recommended making the provider incremental internally, because determinism: "observational" appeared to be an all-or-nothing opt-out of caching. It isn't. The schema supports declared inputs and per-capability overrides:

the same schema — determinism17 phases already use file-determined
"default":  "file-determined" | "observational"
"inputs":   [ … ]        ← required when file-determined; scopes the digest
"capabilities": {        ← per-capability override of the above
   "<name>": { "mode": …, "inputs": [ … ], "reason": … }
}

So the catalog does not need hand-rolled skip logic. It needs a correct descriptor: declare the static capabilities — contract parsing, story grammar, immutability, token vocabulary — as file-determined with inputs scoped to the asset's own version directory, and keep only the genuinely observational ones (BAS capture, screenshot evidence) as observational. Today the phase declares one blanket observational for everything, with a reason that is true of the screenshot capabilities and false of the static ones. That single over-broad declaration is why every run is a full run.

This is the highest-leverage speed fix on the page, and it is a config change rather than an implementation.

Third: make the scan contract take subjects, not a scenario name

ui-health's contract is ScanScenario(scenario) — scenario in, findings out. That shape is what forces whole-scenario granularity on every consumer, and it is the same shape workflow-health uses (applicability.default: "applies", provider-serial, observational, gating — identical problem, identical cause).

The generic change is to accept a subject list: (kind, id, version, fingerprint). The catalog passes assets; an ordinary scenario passes itself; the health scenario validates whatever it is given and returns findings keyed by subject. No health scenario acquires catalog knowledge, and the same change fixes experience-health and workflow-health at the same time — which answers your worry about solving this three times.

Note this is one change, not three: it is the same subject model that targets.kinds: ["asset"] introduces. Do them together or the target kind has nothing to talk to.

Q1, the composition part

Selectors work the way you described. i18n was redesigned, then never connected.

You asked whether selector and string tables are stored with the component, composed across imports, and isolated from the catalog's own. For selectors: yes, exactly that, already built. For i18n I initially reported that a codemod broke it — that was wrong, and the truth is both better and worse.

Selectors · working

A component emits a data-testid derived from its catalog id. Adoption generates a per-adopter selectors.library.ts between // vrooli:library-selectors markers, keyed by catalog id.

Q3 · the trigger

You're right, and there's more built than I found

The retirement machinery is close to complete: RetireCandidates and RetireVersion in the version ledger, a CleanupVersions RPC that takes a plan_hash and a confirm flag, a CLI surface under versions, and a ledger row carrying lifecycle_state, retired_at, adoption_current, and adoption_peak. There is even a test asserting that draft versions are excluded from candidacy. That is a full plan-and-apply retirement system with only the automatic trigger missing, exactly as you said.

Recommendation: don't make the trigger a timer — make it a gate. CleanupVersions is already hash-addressed with a separate confirm step, which is the same shape as every other gate here: compute a plan, report it, apply under policy. So compute the retirement plan on every run, emit the candidate count as a finding, and let the ratchet decide whether it applies automatically, warns, or blocks. A cron would be a second scheduling authority for something the run already visits; this reuses the gating you're building anyway and keeps the deprecation window auditable in the same evidence stream as everything else.

Q4 · my call

Generalize the seams, not the topology

You asked for the cleanest professional long-term answer rather than a menu. Here it is, with the reasoning, because the reasoning is the part you should push back on if you disagree.

Don't build a generic cross-scenario verdict contract. The cleanest long-term system has fewer authorities, not more, and a generic contract standing beside twelve *-health scenarios is a thirteenth. The version of it I'd endorse — building it as a consolidation of the health family — is a far larger project than anything else on this page and shouldn't be started while the catalog's own gating phase can't finish.

Instead, make the two Q1 changes generic, and the need for a generic contract mostly evaporates. An asset target kind plus a subject-list scan contract give every health scenario sub-scenario granularity and give every catalog-owning scenario a way to be validated per-asset. That is the generality people actually want from a verdict contract, delivered by widening two seams that already exist rather than by introducing a new layer above them.

What this defers, honestly: there is still no cross-cutting place to ask "is anything in the repo red right now", and resources, tools, and safeguards still have thin validation. Those are real. But they are better answered later from a subject model that already exists than solved now by inventing one. If a second scenario turns up needing catalog-style per-asset verdicts, you will already have the model, and the contract becomes a small addition rather than a rewrite.

The test for whether this call was right: in six months, either the subject model got reused by something that isn't the component library — in which case generalizing the seams was correct — or it didn't, in which case a generic contract would have been over-engineering and this was still correct.

The freshness pile has a cheaper fix: 87 of 270 sit on non-latest versions — 32%, matching the 33% of version directories that are historical. Scoping routine runs to draft plus latest deletes them mechanically rather than by fixing anything.

And 29 documentation warnings demand a TSDoc block on Default — the story specimen export. Story exports aren't public API and shouldn't be in that gate's scope.

Speed

Why the phase can't finish, exactly

I said earlier this was serial execution plus no caching. That was incomplete. Two gates shell out to full pnpm workflows with their own inner deadlines.

api/internal/gates — two subprocess gatesinner timeouts
gates.go:1268          exec("pnpm", "run", "catalog:check")   timeout 3m
                       └─ catalog-conformance type-check + lint, whole catalog

story_evidence.go:71   exec("pnpm", "run", "build")           timeout 5m
                       └─ full production vite build

Eight minutes of inner timeouts inside a twenty-minute outer deadline, before a single browser capture runs. Add serial BAS execution across every story of every version and the 1200s ceiling is not close.

Neither of those two can be made per-asset. You cannot typecheck one component through pnpm run catalog:check, and you cannot build one component through pnpm run build. They are corpus operations.

The gate config already knows which is which

Every gate carries an attribution field, and it splits exactly along the line the incremental design needs: 21 attributable (per-asset) and 10 corpus (whole-library). That maps almost one-to-one onto the descriptor's determinism.capabilities override map.

So the design writes itself: the 21 attributable gates become file-determined with inputs scoped to each asset's version directory and skip when unchanged; the corpus gates run once, file-determined against the whole library tree, and skip entirely when nothing in the library moved. A no-change run should cost near zero instead of 1200 seconds.

The ui-health ownership split removes i18n-adopted, selectors-adopted, and adopter-hygiene from the catalog. Moving them out drops the un-incrementalizable set from 13 to 10.

Decided

Of 247 calls, ~204 sit in JSX attributes where a hook has always been legal — the stated hook-ordering justification simply doesn't apply to them. The remaining ~43 are destructuring defaults, fixed by moving the default out of the signature into the body: const t = useStrings(); const title = props.title ?? t(key, fallback). Decided

Scenario calls go through api-core/discovery; everything else is a subprocess

This is already the scenario's own pattern — the catalog imports api-core/discovery in three places (experience/reader.go, capabilities/registry.go, workflows/agent_manager.go). So graphreconcile exec'ing typescript-code-graph isn't a missing capability, it's an inconsistency with established local practice — and that scenario runs a Go API on a discoverable port, exactly what the resolver is for. Fixing it deletes 199 findings.

Decided

Declared-but-unbuilt stays a finding, at info, non-blocking

Keeps the 230 rows visible per-asset while removing them from the warning count and from the gating denominator. "The whole library passes" then means the 221 implemented assets pass.

Decided

Retention: N recent runs plus anything a baseline references

Prune on run start, reference-aware so a baseline diff never loses the run it compares against. Bounded by count, so worst-case disk stays predictable on a host that has filled up before.

One caveat on the subprocess half

Four bare-name exec calls remain after the discovery fix — pnpm twice, prettier, and vrooli — and exec.LookPath appears nowhere in the scenario. Go resolves bare names through PATHEXT on Windows, so pnpm finding pnpm.cmd is not the real risk. The risk is that a missing tool surfaces as an error in the middle of a gate rather than as a clean unavailable-dependency verdict up front — which is exactly how one absent binary became 199 warnings. A LookPath preflight per subprocess gate, reported once as blocked, is the whole fix.

Ratchet config

The gate config is sound. Five things would make it airtight.

Good news first: it validates clean against its schema — zero errors — all 34 gates carry all seven core fields, and rung and attribution are real enums. The gaps are at the edges, and one of them is the ratchet knob itself.

GapDetailFix
The floor was untyped adoptionMaturityFloor: "scaffolded" is now a first-class catalog-config property with the four-rung enum. Schema validation rejects a typo such as "verifed"; the live catalog declares the measured scaffolded floor.
blocking isn't required The gate item's required list is id, description, appliesTo, rung, attribution. blocking and runner are optional. All 34 gates set them by convention only. Make both required. Undefined gating behavior is the one thing a ratchet cannot tolerate, and the schema currently permits it.
Four unvalidated extensions x-evidence-kinds (5 gates), x-experience-claim-types (3), x-experience-min-viewports (1), x-experience-requires-capture (1). These carry real semantics — what evidence a gate needs, what it captures — in a namespace with no shape. Promote the two that recur into the schema; the two single-gate ones read as leakage from one feature and should move into that gate's runner or go.
Two orphan calibrations catalog/calibration/integration and .../stress exist as directories with no matching gate in the config — and both contain zero fixtures. Delete, or define the gates they were meant to calibrate. Right now they are the only two of 36 calibration dirs with no owner.
Kind vocabulary drift The gate config's appliesTo says runtime-hook and runtime-service; preview-harnesses/manifest.json says hook. Two registries, two spellings for one concept. Settle on the config's vocabulary as canonical — it is already the most complete of the five enumerations, which is why it should own this too.

Worth stating plainly because it cuts against the rest of this report: the ^x- escape hatch is a deliberate, schema-blessed extension mechanism, not a hack. The problem is only that load-bearing fields moved into it and never moved back out.

One command

You already built most of it

Your memory is right — catalog health exists, backed by GetHealthOverview, and it already carries coverage, score history, per-asset health, promote lanes, quarantined gates, and kind mismatches. Roughly 85% of the readiness report is sitting in that response today. Three things are missing and one is wrong.

What the data already gives you

CoverageRow per asset carries rung, target, achieved, asset_score, weight, passed_gates, failed_gates, nearest_blocking_gate, newest_evidence, and blocks_downstream. MaturitySummary carries by_rung, catalog_completion, mandatory_gate_coverage, production_ready_coverage, pass/fail/unmeasured_evidence, and per-gate score breakdowns. HealthNode carries staleness_days and visual_current.

nearest_blocking_gate is the single most valuable field on this page and it already exists per asset. That is literally "what is stopping this asset from climbing one rung."

What's missing

  • Run identity and staleness at the report level. There's staleness_days per node and newest_evidence per row, but nothing says which run produced this, when it ran, and whether it completed. That gap is exactly how the timed-out component-tests phase stays invisible: the report happily renders against evidence from a run that never finished.
  • Config strictness. Nothing surfaces the current floor, how many gates are blocking versus advisory, or the delta between the declared floor (verified) and where the library actually sits (16 of 34 gates at implemented). Without that, "how do I get to strict green" has no denominator.
  • Unification. Coverage, health, and next-work are three commands. An agent has to know all three exist and how they relate.

What's wrong: the output contract

cli-core defines three canonical shapes — ListReport (Summary → Results → Hints) for data retrieval, MutationReport (Result → Changes → Next Command) for writes, and OperationalReport (Status → Triage → Next Steps) for diagnostics. catalog health is a diagnostic rendered through ListReport, and it shows: an eleven-number run-on Summary string, then a flat list of every asset as id health score stale, unprioritized and untruncated.

No react-component-library command uses OperationalReport at all. That's the whole "not following the output guidelines" finding — the right contract exists and this command family never adopted it.

Three properties make this worth building as one command rather than three.

It refuses to look green when it isn't measured. The status block leads with run identity and completion, so a report built on a timed-out run says so in its first three lines instead of rendering a confident score over stale evidence. That single property would have surfaced last night's break immediately.

Triage is ordered by blast radius, not alphabetically. blocks_downstream and weight already exist per row and nothing currently sorts by them. An agent should see the gate that unblocks 24 assets before the one that unblocks one.

It states the ratchet as a distance. "Declared verified, sitting at implemented, gap one rung" turns the maturity ladder from a config value into a number that goes down. Add a --floor flag and the same command previews what tightening would cost before you tighten it.

Implementation is mostly assembly: extend GetHealthOverview with a run block and a config block, sort the existing rows by blocks_downstream × weight, and render through RenderOperationalReport instead of RenderProtoList. The expensive parts — coverage computation, evidence joins, score breakdowns — are already written.
