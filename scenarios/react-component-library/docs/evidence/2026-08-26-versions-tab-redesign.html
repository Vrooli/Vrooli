Proposal

One tab: the version is the row, health is the colour

Progression, Tests and Adoptions collapse into columns of the thing they were always describing. Eight tabs become six. Comparing two versions stops being a four-tab errand.

Anatomy

Every column answers a question someone actually has

Thumbnail → “is this the thing I mean?”

The capture corpus already exists on disk (coverage/preview-composition/, plus per-story visual baselines). A light/dark split thumb makes an asset list scannable and — this is the useful part — a missing thumbnail is itself a signal: 3.0.0 has no capture because nothing renders it any more.

Health → “can I trust this version?”

test_pass_rate as a bar, test_runs as the confidence behind it. 94% over 17 runs and 94% over 1 run are not the same claim, so both are shown. A version with no runs reads grey, not green — absence of evidence never renders as a pass.

Gates → “what's actually broken?”

gate_pass_count / gate_fail_count, with the failure count red and clickable straight to the failing claims. This is where content-not-clipped would have surfaced the microphone bug months ago.

Adoption → “can I change this?”

adoption_current with a sparkline against adoption_peak. The direction matters more than the number: 3 and rising means coordinate; 1 and falling means it's already being abandoned; 0 with a peak of 5 means it's dead and retirable.

Size & tokens → “what does it cost me?”

Files, lines and dependency count from the ledger — plus required_tokens, the CSS custom properties the version needs but doesn't define. That amber warning is a portability defect surfaced at the moment of choosing, which is the only moment it's cheap to act on.

The retire banner → “what should I delete?”

ListRetireCandidates and PlanCleanup already exist and already compute blockers. Surfacing them at the top of the tab is what turns 827 published exports from a number nobody owns into a queue somebody can drain.

Why this is the right next piece of work

Yes — and it's a sharper test than a checklist

You asked whether building this through the library is a way to find the library's gaps. It is, and this exercise already produced four, before a line of it was written:

  • Nobody reaches for the components. The library's own front-end hand-rolled a <ul>, a diff viewer and two card shells while DataTable, DiffViewer, Card and StatusBadge sat adopted in the same tree. If the maintainers don't reach for them, discoverability is the product defect — not the components.
  • The sizing bug is visible in the library's own UI. Every button in VersionsCard carries a hand-tuned height class — h-control-tight, h-control-compact — because size doesn't set size. The library is working around its own primitive, in its own product.
  • Data models outrun surfaces. Sixteen modelled fields, four rendered — the same shape as 35 evaluators with 20 unused, and 282 contracts with 230 vacuous. Third instance of one failure mode: built, then not adopted.
  • Provenance is unverified. Two files claim data-display.data-table and contain no table. A stamp nothing checks is documentation that rots silently.
Build the tab as a conformance exercise, not a feature. Require it to use only library assets; every time that's impossible, you've found a real gap and the fix belongs in the library, not the page. That constraint is what converts a redesign into a maturity instrument — and it is exactly the discipline the 230 vacuous contracts show is currently missing.

The consistency debt underneath all of it

Scanning the latest version of every asset for cross-cutting concerns that a foundation layer should own once:

Local class composer instead of cn12—bypasses ClassMerge

A design system with 32 different focus rings — 20 of them written for exactly one asset, and three variants using different hardcoded widths including a literal #2563eb fallback — is not a design system yet. Reduced-motion and forced-colors are worse: every single implementation is unique, which means none of them were shared and all of them can drift independently.

This is the same fix as before, arriving from a different direction. A single foundation sheet — reset, focus ring, reduced-motion, forced-colors, visually-hidden — injected once, removes 67 + 47 + 58 independent implementations and makes the per-instance <style> problem disappear as a side effect. One file. It is the highest-leverage refactor available in this codebase.

Method. Field names, RPCs and enums are read directly from packages/proto/schemas/react-component-library/v1/. Component usage, the false provenance stamps and the 187-vs-70 line counts are read from the RCL ui/src tree. The concern-duplication table is an exact parse of the latest version of every asset under library/, counting normalised rule bodies — so "67 distinct" means 67 textually different implementations after whitespace normalisation, some of which may be semantically equivalent. Health, adoption and run-count values inside the mockup are illustrative placeholders.
