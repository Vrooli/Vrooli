Third in the series · disposition and hardening

The Overlay Ledger

I was wrong about one thing in the last document. I proposed inventing an Overlay component with a presentation prop. That component is already specified — it is overlays.responsive-dialog, a P0 asset with a written contract and fifteen required capabilities, sitting in the catalog with no implementation. The work is not to design the API. It is to build what the catalog already says should exist, and to retire the eight things built around the hole.

01

The catalog already answered your architecture question

catalog/assets/overlays/ holds 18 asset specifications. Nine have an implementation in library/components/. Nine do not. And the missing nine include every name that matters here.

catalog/assets/overlays/responsive-dialog.json
{
  "asset": {
    "id": "overlays.responsive-dialog",  "name": "ResponsiveDialog",
    "description": "The adaptive overlay presenting as a centered dialog on pointer-first
       desktops and as a sheet or full-height drawer on constrained or touch-first viewports,
       without losing open state across the change.",
    "target": { "priority": "P0", "maturity": "production-ready" }

So: not one god component with a mode switch, and not fifteen siblings. A small composition graph, with one ergonomic front door that most callers use. That is a better design than what I proposed, and it has the advantage of already being blessed.

overlays.responsive-dialogThe front door — 80% of call sites

Composes dialog and bottom-sheet, selects between them with useMediaQuery, and — the part the spec singles out — keeps open state, focus and scroll position across the switch. A device rotation must not close the surface or lose the form.

No implementationP0
overlays.dialogDesktop half

Centered modal card. Exists as Dialog/1.2.2 but is not modal-safe: no focus trap, no scroll lock, escape via a bare window listener with no layer stack.

Exists, unsound1 consumer (RCL gallery)
overlays.bottom-sheetMobile half

Bottom-anchored sheet with a grab handle, swipe-to-dismiss and safe-area padding. The geometry exists inside DrawerShell size="compact"'s stylesheet but is not extractable — it is a media query, not a component.

No implementation
overlays.full-page-drawerThe other responsive transformation

Full-height sheet on mobile, inset card on desktop. This is precisely what DrawerShell size="full" does today — off-catalog, under a different name, in ten web-console call sites.

No implementationSquatted by DrawerShell
overlays.context-menuThe action-sheet gap

Anchored menu on desktop, action sheet on mobile. Nothing implements the responsive half anywhere in the repo — web-console's local ContextMenuBase renders the same 140px popover on a phone.

No implementation
navigation.sidebarThe rail — already correct

SidebarShell/2.0.0. Properly catalogued, responsive by prop rather than by stylesheet, takes utility classes from the consumer. This is the model. 29 imports across 28 scenarios — the most-used overlay in the ecosystem by a wide margin.

Keep & promote25 scenarios a major behind

Why nobody found any of this

DrawerShell and FocusTrapPanel carry catalogId: "react-component-library:DrawerShell" — self-referential IDs, meaning they are not registered against any catalog asset — plus an x-supplementalJustification that explicitly demotes them: "the public catalog overlay is the adopted asset."

So the component that ten real call sites depend on is off-catalog and marked supplemental, while the catalog asset it should be registered against (overlays.full-page-drawer) has no implementation at all. The catalog and the library are two disconnected maps of the same territory, and the gates only read one of them.

03

Generation A: the proper fix, and the gate that lets it happen

First, the scale is larger than web-console. The Tailwind-in-library components are pinned across the ecosystem:

Generation-A componentPinned versionScenariosEffect
BottomNav1.2.027Mobile navigation styled by whatever classes the consumer happens to use elsewhere
DataTable1.2.01810 className literals in library source, none emitted by any consumer's Tailwind build
markdown-renderer0.3.213CodeBlock chrome purged
DrawerShell1.0.0118 of 21 layout classes purged — the case in the first document

Three fixes, and only one of them is the real one

A

Add the package to every Tailwind content glob

Restores the missing utilities immediately. But it keeps the coupling: the library's appearance depends on each consumer having Tailwind, configured compatibly, with matching theme extensions. A scenario without Tailwind cannot use the library at all. This is a bridge, not a fix — take it in week one, and give it an expiry date tied to fix B.

B

Rewrite Generation A as Generation B — the actual fix

A published component owns its own appearance: data-rcl-* attributes, a module-level stylesheet mounted through StyleSheet, every value from a published token. No build-tool coupling, works in any consumer, survives any bundler. 198 versions already do this; 12 do not. The library has already proven the pattern — DrawerShell 1.0.0 → 1.1.2 is exactly this migration, done once and never rolled out to the rest.

C

Invert class ownership for consumer-specific styling

Some styling genuinely belongs to the app — where the sidebar sits in its shell, which z tier its overlay occupies. SidebarShell already handles this correctly with className, panelClassName, contentClassName, backdropClassName: web-console passes "fixed inset-0 z-wc-drawer bg-black/55" from its own src/, Tailwind sees it, it survives.

That is the whole reason the sidebar didn't break when the drawers did, and it is the rule worth writing down: intrinsic appearance is the library's, placement in the host is the consumer's, and utility classes only ever appear in files the consumer's scanner reads.

Prevention — and here is the good news

You already have the gates. api/internal/gates/gates.go ships ValidateForeignTokenClasses, ValidateStyleInjection, ValidateSharedStyleOwnership and ValidateReleasedVersionImmutable. They didn't fire for three specific, small reasons.

gates.go:827 — why wc-* classes sailed through
foreignPaletteClassRE = regexp.MustCompile(
  `(?:^|[\s"'` + "`" + `])(?:border|bg|text|from|to|via)-app-[A-Za-z0-9_-]+`)

This matches only the app-* palette family, and only 6 utility prefixes.
  bg-wc-backdrop      ✗ wrong family      z-wc-drawer      ✗ wrong family and prefix
  md:inset-x-8        ✗ not a palette class at all         touch-target  ✗ not a class pattern
The gate's own comment says so: "The app-* family is intentionally seeded first;
adding a new forbidden family should be a reviewed change to this gate."
That review never happened, and the general utility problem was never in scope.
1

Widen the class gate from "foreign palette" to "any utility class"

The correct rule is not "don't use another app's palette" — it is "a published component emits no utility classes at all." A library component's className should only ever be the value a consumer passed in. That is a stricter, simpler and far more checkable rule than an ever-growing family blocklist, and it makes the whole class of failure impossible rather than enumerating instances of it.

Land it with a dated allowlist for the 12 Generation-A versions, and delete entries as fix B rewrites them. An allowlist that only shrinks is a ratchet; one that can grow is the vacuous-allowlist.json problem again.

2

Make the gates inspect the versions consumers actually import

validateActiveSources resolves each asset's latest plus draft and inspects only those. Web-console imports DrawerShell/1.0.0; latest is 1.1.2. The gates have never looked at the file that is running in production. The same is true of BottomNav/1.2.0 in 27 scenarios and SidebarShell/1.2.0 in 25.

Add a second scope derived from real imports — walk every scenario's ui/src, collect the pinned specifiers, and run the same gates over that set. It is the same gate functions with a different file list, and it converts "the catalog is clean" into "what ships is clean."

3

Give the immutability gate something to read

ValidateReleasedVersionImmutable queries SELECT … FROM component_versions WHERE status = 'released'. The database has zero tables, so it inspects zero rows and passes. That is why Alert/1.0.0 could be edited in place. Either backfill the index from the filesystem at gate time, or make an empty index a hard failure — a gate that passes because it found nothing is worse than no gate.

4

Close the ingest path that produced Generation A's worst case

api/internal/components/ingest.go lifts a component out of a scenario and writes a provenance header. It has been used exactly once — it produced DrawerShell/1.0.0, complete with z-wc-drawer, touch-target and web-console's safe-area variables. Its only styling check flags hard-coded colors; it does not translate or reject utility classes.

Either make ingest run the widened class gate and refuse, or retire the command. Ingestion without contract translation is how an app's private CSS becomes 35 scenarios' shared dependency.

04

What else stands between this and production-ready

Nine things I found this round that none of the earlier documents covered. The first is the most serious.

01

No overlay portals. Not one, anywhere.

createPortal does not appear in any of RCL's 486 component versions. Every overlay renders inline in the React tree, which means position: fixed silently resolves against the nearest ancestor with transform, filter, backdrop-filter, perspective, contain or will-change — not the viewport. An ancestor's overflow: hidden clips it, and its z-index is trapped in that ancestor's stacking context regardless of --layer-modal.

web-console is full of transforms — drag, resize, pane animation — and has already hit this: it portals its own overlays (AudioPlayerBar, MessageJumpList, KeyComboPicker) with createPortal, but cannot portal DrawerShell because the library gives it no seam. A comment in Workspace.tsx calls the composer "a portaled DrawerShell overlay" — it is not portaled; it is hoisted, which is not the same thing.

This is the highest-severity item in this document and it belongs in the shared core, not in each component.

02

Nothing makes the background inert

No component sets inert or aria-hidden on the content behind an open modal. A focus trap stops Tab; it does not stop a screen reader's virtual cursor, browser find-in-page, or a click that lands through a gap. focus-containment — a declared capability on every modal asset — is not satisfied by a trap alone.

03

Duplicate data-testid within a single component

Dialog puts data-testid="overlays.dialog" on both the backdrop and the close button. ResponsivePanel puts overlays.responsive-panel on three elements; AlertDialog on two. getByTestId throws on multiple matches, so these components cannot be driven by their own testid convention. The testid is being used as a component identifier where it needs to be an element identifier.

04

Hardcoded English in the localized library

The library has a strings system — useStrings, resolveStrings, 91 files use it — and DrawerShell/1.1.2 bypasses it: closeAriaLabel = "Close drawer", title = "Drawer", and aria-label="Dismiss drawer backdrop" as a bare literal with no prop to override it. ResponsivePanel does the same. There is a ValidateI18n gate; these are its subjects.

05

Version skew is the ecosystem's largest latent break

SidebarShell: 25 scenarios on 1.2.0, one on 1.3.1, three on 2.0.0 — a major-version split across 28 consumers of the most-used overlay. Button: 117 on 1.2.0, 13 across 2.x. BottomNav: 27 on 1.2.0. Every one of those pins is a version the gates do not inspect (§03.2), and a fix landing on latest reaches none of them.

06

No breakpoint token

@media (min-width: 768px) in seven overlay stylesheets, 48rem in three, useMediaQuery("(max-width: 767px)") in web-console's JS. Identical at a 16px root, divergent the moment a user scales text — so at 20px root some overlays flip to desktop and others don't, mid-layout. Publish --breakpoint-md and drive all three from it.

07

Overlays cannot animate out

Every one does if (!open) return null, so React unmounts on the frame the state flips and an exit transition is impossible by construction. Presence already solves this and four non-modal components use it. This is also what no-layout-animation and reduced-motion in the capability list are about.

08

Two dependency dialects inside the library

Button/1.2.0 imports "../../../Pressable/versions/1.0.0/Pressable" — a deep relative path. Button/2.2.1 imports "@vrooli/react-component-library/Pressable/1.0.0". Both compile. Only the second is visible to the dependency graph the manifests and gates reason over, so relative-path dependencies are invisible to closure analysis and token verdicts.

09

Where the app is ahead of the library — three times now

ConfirmDialog is more correct than either catalog alert component. ContextMenuBase is the only context menu in the repo. web-console portals its own overlays because the library cannot. That is a pattern, not three coincidences: real usage is finding the requirements and there is no path back. The ingest command was supposed to be that path; it has been used once, badly. Fixing the flow matters as much as fixing the components.

05

Definition of done — also already written

You asked what "fully professional, production-ready" means here. The catalog answers that too, and more precisely than I would have.

Every overlay asset carries a requiredCapabilities list — 14 to 15 entries each — drawn from a governed vocabulary in scenarios/experience-manager/capabilities/. The definitions are good. Here is focus-containment, verbatim:

{
  "id": "focus-containment",
  "title": "Modal surfaces contain focus",
  "description": "While a modal surface is open, keyboard focus cannot escape to the inert
     content behind it, including through nested overlays.",
  "proves": { "evidence": ["ax-tree"], "claimTypes": ["focus-contained"] },
  "tierCeiling": "machine",
  "rationale": "The library already ships useFocusTrap and FocusTrapPanel, so the behavior
     exists in code with nothing asserting it holds. Nested scopes are the case that
     breaks in practice."
}

The acceptance criteria are free; the evidence producer is the missing piece

The capabilities are declared tierCeiling: "machine" — checkable by machine — and they name the evidence type (ax-tree) and the claim (focus-contained). What does not exist is anything that produces that evidence. So Dialog declares focus-containment and has no focus trap, and nothing anywhere notices.

This dovetails exactly with the composition gate from the first document. One browser harness — render each asset inside each consuming scenario's real CSS — can emit ax-tree evidence for focus-containment, focus-restoration, accessible-naming and status-announced; computed-style evidence for contrast-floor, tap-target-size, focus-visible-indicator and dark-parity; and viewport evidence for responsive-transformation. That is one harness satisfying most of a bar that is already specified for every asset.

Do not write a new definition of done. Point the harness at the one in the repo.
