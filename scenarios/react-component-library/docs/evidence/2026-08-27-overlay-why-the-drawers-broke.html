web-console × react-component-library

Why the Drawers Broke

Nothing regressed inside web-console. Its overlays broke because the component library moved its styling contract out from under them — twice — and no gate on either side is watching the seam where the two meet. The same seam is open in 34 other scenarios.

18 / 21 DrawerShell layout classes stripped from web-console's compiled CSS by Tailwind purge
1 / 35 Scenarios that mount BaseStyles, the library's mandatory foundation sheet
−117 Component versions that lost their :focus-visible rule to a gate that assumed BaseStyles was present
0 Rows in the adoption registry — every Go-side governance gate is dormant
01

There are two component libraries in the repo, wearing one name

RCL's catalog holds 486 component versions across 152 components, 27 primitives and 32 hooks. They are not one design system — they are two, built on incompatible assumptions about who owns the pixels. A consumer's experience depends entirely on which generation the version it pinned belongs to, and nothing in the import specifier tells you which.

Generation A — ingested Tailwind

12 versions · styling lives in the consumer

  • Created by lifting a component out of a scenario and dropping it into the catalog verbatim. DrawerShell/1.0.0's header still reads @originScenario web-console.
  • Ships raw Tailwind class strings — including web-console's private ones: z-wc-drawer, bg-wc-backdrop, touch-target.
  • Renders correctly only if the consumer's Tailwind build scans the package. None do.
  • The lift carried no contract translation. touch-target was never defined in web-console's Tailwind config at all.

Generation B — token-bound StyleSheet

198 versions · styling lives in the library

  • Zero class names. Renders data-rcl-* attributes and injects its own CSS via useInsertionEffect into <head>.
  • Immune to Tailwind purge. Entirely dependent on ~120 CSS custom properties the consumer must declare.
  • Delegates focus rings, reduced-motion, forced-colors, control sizing and the box reset to a separate BaseStyles sheet the consumer must mount by hand.
  • An undeclared token doesn't error. It silently computes to the CSS initial value.

What web-console actually pins

24 import sites, 11 distinct pinned versions. The one that matters is at the top — DrawerShell is the shell behind Settings, Appearance, Archive, the terminal launcher, group management, message export, the file viewer, the Mermaid viewer and the full-screen composer.

02

What a drawer is supposed to look like, and what it renders as today

Every class in DrawerShell/1.0.0 that positions the panel on a desktop viewport is a md: variant. Tailwind emits a utility only if it finds the literal string in a scanned file. web-console scans ./src/**/*.{ts,tsx} — and DrawerShell.tsx no longer lives there. It lives in node_modules.

As designed

Inset card, 2rem from each edge, 16px corner radius, elevated over the scrim.

Settings ×
  • ✓md:inset-x-8 md:top-8 md:bottom-8 — the inset
  • ✓md:rounded-2xl md:border — card edge
  • ✓touch-target — 44px close button

As it renders now

Full-bleed, square-cornered, flush to every edge. The scrim is invisible because the panel covers it.

Settings ×
  • ✗All 14 md: utilities absent from the CSS bundle
  • ✗rounded-t-[20px], top-[max(1rem,…)] absent
  • ✗touch-target absent — close button collapses to its padding
  • ✗bottom-[var(--wc-kb-height)] absent — mobile keyboard avoidance is dead in the composer

Two classes survive, and that is the tell

z-wc-drawer and bg-wc-backdrop still work — not because anything protects them, but because seven other files under src/ happen to use the same strings. The drawer's appearance is currently a side effect of unrelated code. Delete the last src/ reference to bg-wc-backdrop and the scrim disappears, with no error anywhere.

That is the mechanism behind "it worked perfectly the other day." The breakage isn't a change to the drawer. It's a change to what else in src/ happens to mention the drawer's classes.

03

Four independent breaks between the library and the screen

A component's appearance passes through six stages before a pixel is painted. Four of them can drop styling silently, and there is no check at any boundary.

Authored

scenarios/react-component-library/library/<Component>/versions/<v>/ — a .tsx, a styles.ts, a story, sometimes an experience contract.

Break 1 Released versions are edited in place. Alert/1.0.0's compiled bytes differ between two installs of the same version — one uses a raw <style> tag, the other StyleSheet. A pinned version is not a stable artifact.
Package build

packages/react-component-library/scripts/build.mjs overlays the authored tree onto a ledger projection, then compiles to dist/.

Break 2 The build script's own comment: builds "used to resolve that disagreement by accident — provisioning runs before the API is up, so it took the authored tree, while a build against a healthy API took ledger content and produced a different package from the same commit."
Install

"@vrooli/react-component-library": "file:../../../packages/react-component-library" — pnpm materializes a hard copy into the store, not a live link.

Break 3 566 dist files currently differ between packages/…/dist and web-console's installed copy. Rebuilding the library does not reach the app until someone reinstalls, and nothing reports the skew.
Tailwind

Each scenario's tailwind.config.ts declares which files to scan for class names.

Break 4 Zero of 95 scenario Tailwind configs include the RCL package in content. Every Generation-A component is styled by luck in every consumer that uses one.
Tokens

Generation-B CSS resolves against --color-*, --space-*, --text-* declared by the consuming app.

Break 5 web-console declares 121 fewer custom properties than the canonical ramp. Today's import graph mostly survives that — but four typography tokens inside the library-managed region are dead, because the sync wrote them without their transitive dependencies. Detail in §05.
Foundation

BaseStyles — the sheet that owns the [data-rcl-control] box reset, the icon scale (--control-icon-size-*), the focus ring, the reduced-motion policy, the forced-colors policy and the visually-hidden utility.

Break 6 Nothing imports it. No component depends on it. web-console never mounts it, and neither do the other 33 consumers. Walking the real runtime import graph — 34 modules from web-console's 11 entry points — BaseStyles is simply not in it, so none of those six policies apply to a single RCL control in the app. Only RCL's own gallery mounts it, which is exactly why components look correct in the library preview and degrade in the apps.
04

The library removed accessibility rules on a promise it never collected

This is the most consequential finding, and it is a library-side decision, not a web-console one.

gates.ValidateSharedStyleOwnership in the RCL API rejects any component that declares its own :focus-visible, @media (prefers-reduced-motion), @media (forced-colors: active) or visually-hidden rule. The stated reason is correct: BaseStyles owns those. Components were duly rewritten to comply — you can watch it happen version by version:

library/components/Dialog/versions/  1.2.1 → 1.2.2   (1.2.1 now marked deprecated)

- [data-rcl-dialog] :focus-visible { outline: 3px solid …; outline-offset: 2px; }
- @media (prefers-reduced-motion: reduce) { [data-rcl-dialog] * { transition-duration: .01ms; } }
- @media (forced-colors: active) { [data-rcl-dialog] .rcl-dialog__surface { border-color: CanvasText; … } }

Across the whole catalog, comparing web-console's installed build against the current one:

Rule centralized into BaseStylesFiles beforeFiles afterNetDelivered to consumers
:focus-visible19780−1171 of 35 apps
@media (prefers-reduced-motion)20283−1191 of 35 apps

The gate was right about the design and wrong about the world

Centralizing shared policy into one foundation sheet is the correct architecture. But the gate enforced the removal half of the migration on the library side while nothing enforced the mounting half on the consumer side. The result is a net accessibility regression across 34 applications: keyboard focus rings, reduced-motion honoring and high-contrast support all quietly stopped shipping.

The structural fix is small and permanent: make the foundation a dependency, not a convention. Have ControlBase, Pressable and every StyleSheet-based component call useLibraryBaseStyles(). The sheet already dedupes by key — mounting it a hundred times costs one <style> node. Once it is imported rather than remembered, the failure becomes impossible instead of merely documented.

05

Tokens: the sync tool ran, and made one thing worse

Credit where it's due: web-console does carry the managed region the contract describes — /* rcl:tokens:begin */ … /* rcl:tokens:end */ in src/design-tokens.css, 36 declarations — and it mostly works. Resolving the 90 custom properties its real import graph requires against the 130 it declares leaves only one genuinely unsatisfied, --control-icon-size, and that one is missing because BaseStyles is missing, not because the sync failed. The token bridge is in better shape than the raw 121-token headline suggests.

Two problems remain, and the second is a regression the sync itself introduced.

The synced tokens reference seven tokens that were not synced

Custom properties that reference an undeclared property are invalid at computed-value time — they don't fall back, they poison the declaration that uses them. Four of the six typography tokens in the managed region are dead on arrival:

src/design-tokens.css — inside the managed region

--text-display: 700 var(--text-display-size) / var(--text-display-line) var(--font-sans);
--text-title:   700 var(--text-title-size)   / var(--text-title-line)   var(--font-sans);
--text-caption: 600 var(--text-caption-size) / var(--text-caption-line) var(--font-sans);
--focus-ring:   0 0 0 3px color-mix(in srgb, var(--focus-ring-color) 35%, transparent);

↑ every marked name is undeclared anywhere in web-console.
  Any component doing `font: var(--text-title)` gets the browser default face.

The sync overwrote a variable the app sets at runtime

--wc-kb-height is written imperatively by useAppViewport from visualViewport, and is 0px when no on-screen keyboard is present. tokens-sync added a static --wc-kb-height: 2.5rem to the managed region. The collision detector only inspects declarations that already exist in CSS, so an app-owned variable that lives in JavaScript is invisible to it — and every consumer of var(--wc-kb-height, 0px) now falls back to 40px instead of zero whenever the hook hasn't written a value yet.

One piece of good news, and it is the cheapest fix in this document

DrawerShell/1.1.2 — the Generation-B rewrite — requires zero custom properties web-console does not already declare. Moving the 10 import sites from 1.0.0 to 1.1.2 removes the entire Tailwind-purge failure mode for the drawers, with no token work at all. It is a one-line change per file.

06

Why every gate stayed green through all of this

RCL has a serious governance apparatus — adoption records, token verdicts, drift reporters, staleness scans, composition contracts, calibration, a visual bar. None of it fired, for four separate reasons.

MechanismWhat it should catchWhy it didn't
Adoption token verdict
adoptions/tokens_verdict.go		 "scenario X cannot satisfy this closure's required properties" Fires only at adoption time. The registry DB has zero tables; web-console's 24 imports are plain ESM specifiers that never entered the system. The gate has no subject.
Experience contracts
library/vacuous-allowlist.json		 A machine-checkable claim per component version 290 of 486 versions have no contract. Of the 298 that exist, 229 (76%) are allow-listed as vacuous — "retained until this asset is next changed." Real coverage is ~14%.
Visual bar
coverage/visual/verdicts.json		 Rendered appearance across 8 viewport/theme combinations Covers 17 of 486 versions, all marked pass. Verdicts are authored prose, not a computed diff. DrawerShell — the most-used component in the ecosystem — is not among them.
web-console unit tests
ui/src/__tests__/*.test.tsx		 Drawer and dialog behavior jsdom applies no stylesheet. Escape-to-close, focus trap and aria-modal all pass exactly as before. Every symptom in this document is invisible to a green suite.

The common shape: each gate validates the library in isolation or the app in isolation. Nothing validates the composition — the only place these failures exist.

07

The path forward

Ordered so each step is independently shippable and the early ones stop the bleeding without waiting on the structural work. Steps 1–2 fix web-console; 3–6 make the class of failure impossible.

1

Add the package to every Tailwind content glob

One line per scenario. It restores the 16 purged utilities immediately and un-breaks Generation-A components everywhere, including the 34 other consumers. Do this even though step 2 makes it unnecessary for the drawers — other Generation-A components are still in use.

content: [..., "./node_modules/@vrooli/react-component-library/dist/**/*.js"]

95 configsReversibleNo behavior change
2

Move web-console's drawers to DrawerShell/1.1.2

Verified: 1.1.2 requires no token web-console lacks, and its props are source-compatible with 1.0.0. Ten import lines. This retires web-console's dependency on Tailwind purge for its most important surface, and picks up the mobile-safe sizing and the entry animation the current pin predates.

Do the same audit for ColorPicker/1.0.0 → 1.0.3, which is three versions behind.

10 filesToken-clean
3

Make BaseStyles a dependency instead of a convention

The single highest-leverage change in this list. Have ControlBase, Pressable, StyleSheet-based overlays and anything reading --control-* call useLibraryBaseStyles() internally. The keyed sheet already dedupes, so the cost is one <style> node regardless of call count.

This retroactively repairs the −117 / −119 / −87 accessibility regression in all 34 consumers without touching any of them, and it means the style-ownership gate's premise finally holds.

Fixes a11y regressionNo consumer change
4

Make released versions immutable, and add a build-freshness check

A pinned version must be a stable artifact. Hash each released version directory at publish; reject in-place edits to a released version and require a bump. Separately, have vrooli scenario start compare the installed package's content hash against packages/…/dist and fail loudly on skew rather than serving a 566-file-stale copy.

Also settle the build's authored-tree-vs-ledger ambiguity in one direction. A build whose output depends on whether an API happened to be up is not a build.

StructuralCloses breaks 1–3
5

Add a composition gate: the only test that would have caught this

For each scenario × each RCL component it imports, render the component inside that scenario's compiled CSS and token set, in a real browser, and assert that no declaration resolved to an initial value and no referenced utility is absent from the bundle. This is a small extension of the existing BAS harness and the visual bar — the infrastructure exists, it is just pointed at the library in isolation.

Cheap first approximation, worth landing on its own: a static check that every var(--x) reachable from a scenario's import closure is declared by that scenario, run in CI. That alone catches breaks 5 and the seven transitive token gaps.

Highest coverage valueExtends BAS
6

Make imports real adoptions, or retire the adoption machinery

Right now there are two parallel consumption models: the documented, governed one (adoption records, token verdicts, drift reports, reapply) and the one everybody actually uses (a deep ESM import). The governed one has zero rows in its database, so all the Go-side gates are elaborate dead code.

Pick one. Either have a step register each import specifier as an adoption so the verdicts have a subject, or accept plain imports as the model and move the token/foundation checks into the composition gate from step 5, where they can run without a registry. The current split is what let all of this land silently.

Decision neededRemoves dead governance

Two cleanups worth folding in

Retire Generation A. Twelve versions still ship consumer-private Tailwind classes. Once step 2's pattern is applied to DataTable/1.2.0, BottomNav/1.2.0, the markdown and mermaid renderers and the rest, step 1 becomes belt-and-braces rather than load-bearing, and the library has one styling contract.

Fix the corrupted CSS in the deprecated drawer versions. DrawerShell/1.1.0 and 1.1.1 contain transform: resolveStrings(-50%, -50%) — an i18n codemod that ran over a CSS string literal. Already repaired in 1.1.2, but it is direct evidence that codemods are being applied to styles.ts without a CSS-validity check. Add one; it is a few lines and it would have caught this before publish.
