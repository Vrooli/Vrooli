Companion to “Why the Drawers Broke”

The Overlay Contract

web-console has five distinct overlay behaviors and no name for any of them. RCL has fifteen overlay components that each implement a different subset of the same six concerns. This is the missing spec: what each surface should do at each breakpoint, which component should own it, and what the API should look like.

01

The single most useful thing in this document

DrawerShell size="compact" already is the responsive dialog you described — bottom sheet on mobile, centered 32rem card at ≥48rem. It has been sitting there the whole time under a name that says "drawer" and a prop that says "compact". Four web-console surfaces already use it correctly by accident. The fix for discoverability is naming, not new code.

Drawer is a 58-line stub and it is the one the catalog advertises

It declares side="left"|"right"|"top"|"bottom" and presentation="modal"|"non-modal" and uses neither — it emits them as data attributes onto an unpositioned <section> with inline padding. No backdrop, no positioning, no focus management, no escape.

Meanwhile DrawerShell — the one that actually works — carries x-supplementalJustification: "Pre-catalog overlay shell retained as a supplemental implementation seam; the public catalog overlay is the adopted asset." The catalog metadata says the stub is the public asset and the working one is supplemental. It is exactly backwards, and it is the single best explanation for why nobody found the right component.

Dialog and AlertDialog cannot be used as modals

Dialog/1.2.2 has no focus trap: Tab walks straight out of the open dialog into the page behind it. It has no scroll lock, so the page scrolls under it on touch. Its Escape handler is a bare window.addEventListener("keydown", …) rather than the shared hook and it does not consult a layer stack — so with two dialogs open, one Escape closes both. AlertDialog/1.0.6 has none of the three.

web-console's local ConfirmDialog — 111 lines — does all of it correctly: useFocusTrap, useEscapeKey, role="alertdialog", safe-action autofocus, its own z tier above the drawer tier. It is strictly better than both catalog components, and it never went back into the library.

Gestures do not exist

useSwipe is twenty lines. It records a pointer-down position and, on pointer-up, fires a direction — with no distance threshold, no velocity, and no time bound, so an ordinary tap fires a swipe. There is no drag-follow, so a sheet cannot track the finger. Nothing in the library imports it, and web-console has no swipe handling on any overlay. Swipe-to-dismiss is not "partly built"; it is absent, and the existing hook is not a foundation to build on.

Nothing animates out

Every overlay does if (!open) return null. React unmounts the node, so exit transitions are impossible by construction — the surface vanishes on the frame the state flips. DrawerShell and ResponsivePanel animate in via a CSS keyframe and pop out. Dialog, AlertDialog and Menu have no animation in either direction. RCL already ships a Presence primitive that solves exactly this, and Popover, Toast, Tooltip and UndoBanner use it — none of the modal surfaces do.

Two breakpoint dialects

Overlay stylesheets use @media (min-width: 768px) seven times and @media (min-width: 48rem) three times. Those are the same on a default root font and diverge the moment a user scales text — so at 20px root, some overlays switch to desktop and others do not, mid-layout. web-console adds a third dialect in JS: useMediaQuery("(max-width: 767px)"). There is no breakpoint token in the canonical ramp.

04

The proposed API

One component, one prop that selects a presentation, and everything else an override on the defaults that presentation implies. Modeled on SidebarShell's shape, which is the one API in the family that already got this right.

// One import. Presentation carries the entire responsive contract.
import { Overlay } from "@vrooli/react-component-library/Overlay";

<Overlay
  /* — what kind of surface this is — */
  presentation="dialog"        // page | dialog | alert | rail | menu
  size="md"                    // sm 24rem | md 32rem | lg 48rem | full   (desktop only)

  /* — state: controlled, uncontrolled, or both — */
  open={open}
  defaultOpen={false}
  onOpenChange={setOpen}
  onClose={handleClose}          // fires only on dismissal, not on programmatic close

  /* — chrome — */
  title="Appearance"
  description="Theme, accent, and text size."
  headerActions={<Button …/>}
  footer={<FormActions …/>}
  closeLabel="Close appearance settings"

  /* — behavior: every one defaulted from `presentation` — */
  dismiss={{ escape: true, backdrop: true, swipe: true, outside: false }}
  scrollLock                     // default true when the presentation is modal
  avoidKeyboard                  // lift above the on-screen keyboard
  initialFocusRef={inputRef}
  returnFocusRef={triggerRef}

  /* — anchoring, for presentation="menu" only — */
  anchorRef={buttonRef}
  placement="bottom-start"

  /* — escape hatches: consumer-authored classes, so Tailwind sees them — */
  className panelClassName contentClassName backdropClassName
  testId="appearance"
/>

Three properties of this shape matter more than the exact names:

The responsive behavior is a value, not a stylesheet. Today a consumer cannot know that size="compact" means "bottom sheet on mobile" without reading the library's CSS. presentation="dialog" says it.

Classes come from the consumer, never the library. SidebarShell already does this — web-console passes backdropClassName="fixed inset-0 z-wc-drawer bg-black/55" from its own src/, so Tailwind sees it and it survives. That is precisely why the sidebar did not break when the drawers did. Structure and behavior live in the library; utility classes live where the scanner can see them.

One breakpoint, one token. Publish --breakpoint-md: 48rem in the canonical ramp, drive every overlay stylesheet from it, and have useMediaQuery read it rather than accepting a hand-written string.

Do not build this as a fifteenth overlay

The failure mode here is obvious and the repo already demonstrates it: Drawer, DrawerShell, Dialog, AlertDialog, ResponsivePanel, FocusTrapPanel, InspectorPanel and OverlayCanvas are all somebody's attempt at this component. Overlay is only worth building if the same change deprecates the ones it subsumes and rewrites the survivors as thin presets over it — Dialog = Overlay presentation="dialog", AlertDialog = presentation="alert", DrawerShell = presentation="page", SidebarShell = presentation="rail". Otherwise you have made the problem 7% worse.

05

Versionless imports: yes, they work — and no, don't default to them yet

You remembered right. packages/react-component-library emits a bare subpath alongside every pinned one, and it resolves to the newest version:

dist/exports/DrawerShell.js
export * from "../components/DrawerShell/versions/1.1.2/DrawerShell.js";

dist/exports/DrawerShell/1.0.0.js
export * from "../../components/DrawerShell/versions/1.0.0/DrawerShell.js";

So import { DrawerShell } from "@vrooli/react-component-library/DrawerShell" works today and gives you 1.1.2. Both forms are live for all 227 assets.

How "newest" is actually computed

scripts/sync-exports.mjs lists the versions/ directory and sorts the folder names with localeCompare(numeric). It never opens component.json. That means the bare export ignores three things the manifest declares:

Manifest fieldHonored by bare export?Measured today
latest — the declared current versionNo1 asset disagrees: ControlBase declares latest: 1.0.1, bare resolves to 1.1.0
deprecatedVersions[]No0 assets affected right now — but only by luck; nothing prevents it
draftNo0 assets affected right now — same caveat
Major-version boundaryNo5 assets already span majors: Button 1→2, SidebarShell 1→2, VoiceInputButton 3→4, useElementRect 1→2, useVoiceInput 1→3

That last row is the real hazard. A bare import silently follows a major bump. The next time someone publishes SidebarShell 3.0.0 with a different prop shape, every bare consumer picks it up at their next install, with no diff, no warning and — because released versions are still mutable — possibly without any version number changing at all.

On keying the default off scenario maturity

The field exists: .vrooli/service.json → maturity: greenfield | pilot | production | sunset, defaulting to greenfield, currently consumed only by storage-manager to gate migration findings. But I'd push back on using it for this, for two reasons.

It would be a no-op. 115 of 120 scenarios don't declare it at all. web-console — the most heavily used UI in the repo — reads as greenfield. You'd be shipping a policy that applies to two scenarios.

It's the wrong variable. Maturity describes the consumer's deploy risk. What determines whether floating is safe is whether the library guarantees that "newest" is non-breaking — an upstream property. A greenfield scenario that floats onto a breaking major is just as broken as a production one; it merely matters less. Tying pin policy to consumer maturity encodes "we tolerate breakage in immature apps" rather than "breakage shouldn't reach anyone."

What I'd do instead

Float within a major, pin across one. Have sync-exports emit three subpaths per asset: ./DrawerShell/1.1.2 (exact, for reproduction), ./DrawerShell/1 (newest within major 1 — the recommended default), and ./DrawerShell (newest overall, resolved from component.json.latest and skipping deprecated and draft, which it currently does not).

Then make ./Component/<major> the house style. You get the consistency you're after — a component upgrade is a library publish, not 35 pull requests — without the class of failure where a major bump lands silently. And it's a change to one build script, not to any consumer.

The prerequisite is the immutability work from the first document. Floating onto a moving latest is only safe once a published version's bytes cannot change; right now the same version number can mean two different components, which makes any import — bare or pinned — non-reproducible.

06

Revised plan

Steps 1–3 are unchanged from the first document and remain the priority; everything below folds this investigation into the rest. Ordered by dependency, not by size.

A

Write the contract down before touching code

The five presentations, the per-breakpoint geometry, the dismissal matrix and the ARIA roles from §01 and §04, as a reference doc in RCL. Every subsequent step is a claim against it, and today there is no document in the repo that says what any of these surfaces is supposed to do — which is why nothing could be validated as correct.

Pair it with a breakpoint token (--breakpoint-md: 48rem) and retire the 768px/48rem/767px split.

Unblocks everythingDoc only
B

Fix the catalog's signposting immediately

Cheap and high-value: Drawer, InspectorPanel, FocusTrapPanel and OverlayCanvas are stubs presenting as finished components. Mark them draft or deprecated, and remove the x-supplementalJustification that demotes DrawerShell beneath the stub that replaced it. Fill in the empty description fields on the overlay manifests.

Nobody can pick the right component from the current catalog. That is a metadata bug, and it is a one-session fix.

One sessionNo code
C

Harden the shared behavior layer, then wire it into what exists

Before any new component. Give useScrollLock a nesting counter and an iOS-safe implementation; rewrite useSwipe with distance, velocity and drag-follow, or delete it; extend LayerManager to assign a z value rather than only tracking order, and to own background inert. Then wire focus trap + escape + layer + scroll lock into Dialog and AlertDialog, which are shipped as modals and are not modal-safe.

Adopt Presence in the modal surfaces so they can animate out instead of vanishing.

CorrectnessBenefits all 35 consumers
D

Contribute ConfirmDialog back as presentation="alert"

web-console's local implementation is more correct than both catalog alert components. Promote it rather than reimplementing it — and note that the library's version of this component being worse than the app's is the second time that pattern shows up here. The first was DrawerShell being ingested from web-console and then diverging.

Net deletion
E

Build Overlay, and deprecate what it subsumes in the same change

Only after A–D. Rewrite Dialog, AlertDialog, DrawerShell, SidebarShell and ResponsivePanel as thin presets over it so no consumer has to migrate on day one, and mark Drawer, InspectorPanel, FocusTrapPanel and OverlayCanvas deprecated with a pointer to the preset that replaces them.

Give presentation="menu" a real mobile action sheet — that is the one behavior in the matrix that exists nowhere today, and it affects three web-console surfaces plus every context menu in every other scenario.

Largest stepGated on A–D
F

Emit the three-subpath export map and adopt ./Component/<major>

Change sync-exports.mjs to read component.json, honor latest/deprecatedVersions/draft, and emit the major-scoped subpath. Then move consumers onto it as the house style. Do this after the immutability work from the first document, not before — floating onto a mutable latest is worse than pinning to one.

Leave maturity out of it. If you want the field to earn its keep, the better use is what it already does for storage-manager: gate the strictness of checks, not the shape of imports.
