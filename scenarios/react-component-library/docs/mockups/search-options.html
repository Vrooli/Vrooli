Search should know what a landing page is.

Today the library has four search boxes and no shared idea of what can be found. “Landing page” returns zero results on the components page, and the command palette only finds a scenario name. The fix is not a bigger text field. It is a searchable model of intent, composition, source and evidence — plus an omnibox that makes the model feel obvious.

Recommendation. Build one search system with three states, not three products: Atlas is the browse-first front door (empty query), Spotlight is the same engine summoned with ⌘K, and Ask is an explicit AI mode inside it. Underneath, index one typed result model over workspaces, pages, displays, states, page types, assets and commands. Merge the template shelf into designs; keep the catalog page-template as the intent blueprint.

Follow-up: the workspace → page → display → state model and the rest of the matured workbench are in workbench-maturation.html.

01 / TODAY

Four searches, none of them a search system.

Each box is useful in isolation. Together they disagree about what exists. The captured screens below are the running workbench at 1440×900 on 2026-11-19.

01
Four surfaces, four answers.

The home form navigates to Components with ?q=. Components filters the 275 published assets it loaded in the browser. ⌘K filters two more lists. The design studio has a template dropdown. The API has a fifth, unused search.

02
The server index is already there — and unused.

CatalogService.SearchAssets indexes 478 authored catalog assets with kind, domain, regions and availability. searchDesignAssets() is defined in the UI and called nowhere.

03
“landing page” is an intent, not a substring.

Token search returns LandingPage first, then every other page archetype because they all contain “page”. There is no IDF, phrase boost, AND semantics or type prior.

04
Templates and designs are invisible to search.

Two designs, eight templates and nineteen page archetypes exist. None appears in ⌘K. The only path is Design studio → a dropdown of eight names.

05
Actions have no registry.

RCL already ships CommandRegistry, CommandPalette and GlobalCommandSystem. The workbench hand-builds a palette and registers no commands.

06
Two stores for one composition.

studio_templates stores a single-frame TemplateNode tree with no revision, binding or assets. studio_designs stores multi-frame, revisioned, conflict-safe compositions. They are the same idea, split.

The deeper gap. RCL is organised asset-first, but people ask outcome-first: “landing page”, “onboarding flow”, “pricing page”. There is no first-class searchable object for a page or flow that composes assets. Templates were an attempt to create one, but they live beside the design model instead of inside it.

Yes: template and workspace should be one entity.

A template is a curated workspace snapshot, not a second document. A workspace holds pages; each page holds displays (desktop, tablet, phone); each display holds states (default, filled, error, loading). Give the workspace provenance (authored · curated · imported), tags, summary and preview.

“Use template” forks the curated workspace into your own copy and keeps the origin link. That removes the separate studio_templates store.

No: a page type is not a template.

The catalog page type remains the requirement/blueprint: regions, states, capabilities, required assets. It is not a rendered page. A workspace page declares realizes; the page type exposes the pages and workspaces that realize it.

An onboarding flow is one workspace with four pages. A page is one screen; a display is one device frame; a state is a named variant of that display. The canvas may show state copies side by side; the stored object is one display with N states.

The search consequence. “Landing page” should match the page type (intent), the workspaces tagged or bound to it (composition), the assets those workspaces compose (source), and the commands that act on the result (new page, compare, adopt). One query, four kinds of answer, ordered by what the person is trying to do.

05 / RECOMMENDATION

One system, three states, one model.

Do not choose between Atlas, Spotlight and Concierge. They are the empty, invoked and AI-assisted states of the same omnibox. The order matters: index first, commands second, AI third.

LayerWhat it isWhy this order
AtlasThe Home front door and the empty query state. Categories, recent designs, curated templates, commands.Answers “what exists?” without a query and teaches the vocabulary the search engine uses.
SpotlightThe ⌘K overlay on every surface. Same index, same groups, plus a preview pane on desktop.Makes search one gesture away; the preview turns results into decisions.
AskAn explicit mode inside the omnibox. Natural language in, a cited shortlist and next action out.Handles the “I don’t know the name” case without making every query pay for a model.
CommandsA declarative registry of actions with labels, shortcuts, scopes, availability and handlers.Turns the palette into a real command surface and makes shortcuts discoverable.

What ships first (no migration)

0.1
One typed result model.

Design, template, page archetype, asset, page, command, evidence. Common fields: id, kind, title, subtitle, score, highlights, relations, preview, badges, route.

week 1
0.2
One index, one endpoint.

Index the component registry, catalog assets, workspaces, pages, displays, states, experience pages and a command registry. Replace the capped client filters and the unused searchDesignAssets.

week 1–2
0.3
Atlas + Spotlight.

Use the library’s own SearchFilterResults, SearchResults, SearchInput and CommandPalette assets. Add URL state, abort, loading/stale/no-match/index-empty/error.

week 2–3

What fixes the model (after search works)

1
Merge the template shelf into designs.

Add provenance, tags, summary, preview, realizes. Migrate existing rows into single-frame designs. Curated templates are immutable; “use” forks.

phase 2
2
Add flow semantics.

Introduce a Workspace (ordered designs) or frame.role = screen. A template can then be a flow snapshot, not just one page.

phase 3
3
Link intent to composition.

Designs declare realizes; archetypes project designs[]. Search can then answer “show me every landing page and what it composes” honestly.

phase 3

Acceptance evidence

“landing page” returns LandingPage first, then workspaces tagged or bound to it, then composed assets — never every page type.
The empty state shows categories with counts derived from the catalog; every category opens a real filtered result set.
Commands are searchable, show their shortcuts and context, and execute from the palette.
Search survives a 478-asset corpus and a 390 px phone; no capped client list, no hidden overflow.
Loading, stale, index-empty, no-match, partial and request-error are distinct states with recovery.
Every AI answer cites an indexed design, archetype or asset; unanswerable queries fall back to lexical results.
The workbench consumes its own search and command assets; no fifth hand-rolled search implementation remains.
“Use template” forks a design; the curated shelf cannot be edited in place; provenance survives the fork.

Open questions for you

1. Is a template a page or a flow?

If onboarding flows are in scope, we need a workspace/screen model. If templates stay single-page, we can merge them into designs without that work. I recommend supporting both, but shipping the single-page merge first.

2. Should curated templates be immutable?

Fork-on-use preserves a trustworthy shelf and the studio’s current copy behaviour. Direct editing is faster but lets a showcase drift. I recommend immutable + fork.

3. What is the default ranking?

Outcome-first (page/flow, then design/template, then asset) or asset-first with types as filters? I recommend outcome-first for plain queries and asset-first for explicit asset queries.

4. How local must Ask be?

The experience-engineering programme bans paid vision APIs; the same constraint should apply here. I recommend a local model through AI Gateway, with a lexical fallback when it is unavailable.
