# Product Requirements Document (PRD)

## 🎯 Overview
Purpose: Performance Health is Vrooli's single authority for software-performance **judgment**. It owns three performance axes that today are scattered across test-genie and structure-health (plus a hacky audit skill): ① **build-time** (go build + UI build timing), ② **startup/runtime** (time-to-healthy + per-surface reachability + a resource envelope via `api-core/metrics`), and ③ **UI browser perf** (Lighthouse scores + React component-commit profiling). It detects which capture **tier** a scenario can reach, autofixes scenarios toward the higher tier, orchestrates capture (delegating the raw browser trace mechanism to Browser Automation Studio's perf-capture), interprets traces into deterministic findings, sets and enforces budgets, stores trends, and aggregates fleet-wide performance intelligence. It continues Vrooli's test-genie phase-externalization program (siblings: unit-health, quality-health, security-health, structure-health, cli-health, ui-health, proto-health).

Primary users/verticals: Vrooli agents and Test Genie (as the delegated provider for the build-time and UI-browser performance axes over `scenario-validation/v1`), the Ecosystem Manager / meta-optimization maturity loops (trend + fleet intelligence as durable optimization inputs), scenario maintainers tuning a specific scenario's render/build/startup cost, and operators inspecting fleet performance. The primary vertical is Vrooli's engineering-quality loop, where performance regressions are caught and attributed deterministically rather than discovered by hand.

Deployment surfaces: Go API (native `performance-health/v1` per-domain services — readiness, audit/capture-orchestration, lighthouse, benchmark, analysis, budgets, trends, fleet, startup — PLUS the shared `scenario-validation/v1 ScenarioValidationService` so Test Genie can delegate axes ①/③), Go CLI (`performance-health readiness|audit|lighthouse|benchmark|budget|trend|fleet|startup`), and a React/Vite UI performance console (audit workbench, trend charts, fleet dashboard, readiness + one-click autofix, budgets, trace viewer link-out). The API and CLI are the canonical programmatic surfaces; the UI is an inspection and operator console.

Value promise: Performance stops being three fragmented, hand-rolled efforts and becomes one discoverable, tiered, deterministic capability. Agents get `performance-health audit scenario <name>` (full capture pipeline → located, quantified findings), `performance-health readiness scenario <name>` (tier detection + one-command autofix toward Tier 1), and `performance-health trend|fleet` (durable regressions + offenders). BAS becomes a dumb capture mechanism; performance-health owns all the meaning. Test Genie stops carrying a native perf phase; structure-health stops carrying a perf domain; budgets gate regressions through the test-genie Performance phase and therefore the suite run.

## 🎯 Operational Targets

Operational targets are measurable outcomes; checkboxes may auto-update based on validation.

### 🔴 P0 – Must ship for viability
- [ ] OT-P0-001 | Code-Facts-Gated Tier Detection | `performance-health readiness scenario <name>` derives surfaces and UI framework from Code Facts (Connect client with a filesystem fallback that records a degraded reason when Code Facts is unavailable) and decides the reachable capture tier deterministically: no UI → skip browser perf; UI but non-React → Tier 0 only; React → Tier 0 + Tier 1; React-but-divergent infra → flagged. The scenario NEVER assumes React from the filesystem.
- [ ] OT-P0-002 | Readiness Validation & Format-Preserving Autofix | Readiness detects the four Tier-1 perf-build infra pieces (vite profile-mode `react-dom/profiling` alias + `keepNames:true`, a profile-mode build script, `lib/profiler.ts` `onProfilerRender`, a top-level `<React.Profiler>` boundary), emits findings + `autofixable_count` through the shared maturity response, and `--apply` writes the missing infra via the shared `packages/maturity-go/autofix` helper using format-preserving edits (dry-run default; apply-twice is a single change).
- [ ] OT-P0-003 | Capture Orchestration over BAS perf-capture | `performance-health audit scenario <name>` conducts the capture pipeline: profile-mode restart → verify the served bundle is the profile bundle → call BAS perf-capture (CDP trace + web-vitals; ⚛ component marks ride along when present) → restore the default build. Capture NEVER fails for lack of instrumentation — absent ⚛ marks are a Tier 0 result, not an error. The pipeline skips cleanly (mirroring Lighthouse's silent-skip) when there is no UI / no browser / headless.
- [ ] OT-P0-004 | Deterministic Trace Analysis with Located Findings | The analysis engine parses the perf trace into a per-component count/avg/max table (pairing `⚛` `blink.user_timing` begin/end by `id2.local`) plus long-task and paint/LCP signals, and emits **deterministic** findings (NO AI hypotheses) where each finding maps a component name to its source definition (file plus line, via symbol lookup) and carries quantified evidence (count/avg/max, budget delta). Findings flow through the maturity finding pipeline with stable codes mapped in `.vrooli/maturity.json`.
- [ ] OT-P0-005 | Test Genie Performance Provider | Performance Health implements the shared `scenario-validation/v1 ScenarioValidationService`; Test Genie's `Performance` phase is served by performance-health for the build-time (axis ①) and UI-browser (axis ③ Lighthouse) signals; the native test-genie perf runner is deleted (not shimmed) and the default phase profile is byte-identical; the provider-contract scan recognizes the provider.

### 🟠 P1 – Should have post-launch
- [ ] OT-P1-001 | Lighthouse Runner & Build Benchmarks | `performance-health lighthouse scenario <name>` wraps the Lighthouse CLI (its own Chrome, NOT via BAS) with per-page error/warn thresholds from `.vrooli/lighthouse.json` (Tier 0, any URL, silent-skip when the CLI is absent); `performance-health benchmark scenario <name>` times `go build ./...` and the UI build with thresholds from `.vrooli/testing.json`, preserving early-exit semantics. Both migrate their config shapes from test-genie.
- [ ] OT-P1-002 | Budgets & Suite-Run Gating | A declarative per-scenario and per-flow budget model (build time, bundle size, LCP, component-commit, frame-health, browser-work, long-task, and input-event budgets) with a ratchet; a perf regression vs. budget/trend fails through the test-genie Performance phase and therefore `vrooli scenario test` exits non-zero. `performance-health budget` views/edits budgets.
- [ ] OT-P1-003 | Trend Storage & Comparison | A SQLite trend seam (`schema.sql`, modeled on structure-health's perf store and test-genie self-health snapshots) persists per-run measurements additively (never destructive); `performance-health trend scenario <name>` reads newest-first and a before/after comparison primitive diffs two traces (per-component delta + long-task delta).
- [ ] OT-P1-004 | Fleet Performance Intelligence | `performance-health fleet` rolls up deterministic structured offender queries (scenarios with no perf budget, slowest builds, recent regressions, tier distribution) — NOT a search-hub semantic provider; the UI renders a fleet dashboard; the CLI verbs are discoverable through cli-health's command index.
- [ ] OT-P1-005 | CLI Discoverability & Human Default | CLI commands render useful human output by default with `--json` as the opt-in programmatic format; thin Connect-client wrappers carry no business logic; every verb is registered and discoverable through cli-health.

### 🟢 P2 – Future / expansion
- [ ] OT-P2-001 | Resource-Aware Startup Benchmark (migrated axis ②) | `performance-health startup scenario <name>` restarts a scenario behind a runner seam and persists per-surface time-to-healthy plus a `common.v1.ExecutionMetrics` resource envelope (CPU/mem/GPU/host-load) to the trend store; it refuses to measure performance-health itself (self-restart deadlock guard). This is the greenfield re-home of structure-health's `perf` domain — measurement substrate for deferred lifecycle-startup optimizations, never invoked by a Test Genie phase.
- [ ] OT-P2-002 | Expanded Tier-1 & New Axes | As stacks mature, performance-health gains non-React Tier-1 component-attribution adapters (Vue/Svelte) and new axes charted but out of v1 scope: API latency/throughput (Go pprof / load testing) and DB-query performance.

## 🧱 Tech Direction Snapshot
- Preferred stacks / frameworks: generated React/Vite UI, Go API, Go CLI, proto/Connect contracts. SQLite (`api-core/database`) backs only the trend store. CLI business logic stays thin over API behavior.
- Data + storage expectations: live readiness/audit/lighthouse/benchmark are stateless captures. The trend store persists per-run measurements + resource envelopes to scenario-local SQLite with deterministic retention. Fleet scans are computed on demand. Trace artifacts are produced by BAS (stored in MinIO + exported to a folder), referenced by performance-health, not re-stored.
- Integration strategy: Code Facts is the source of actual surface/framework discovery and tier gating; `service.json` is read only for declared intent (ports/lifecycle). BAS perf-capture is the raw capture mechanism consumed over Connect (BAS stays agnostic to tiers/build-modes/meaning). Test Genie consumes performance-health as its `Performance` phase provider over `scenario-validation/v1`. `packages/maturity-go` validates the maturity ladder and turns finding impacts into global signals; `packages/maturity-go/autofix` is the shared remediation substrate; `packages/api-core/metrics` supplies the ExecutionMetrics envelope. The Lighthouse runner uses its own Chrome (not BAS).
- Non-goals / guardrails: Do **not** generate AI hotspot hypotheses (findings are deterministic). Do **not** build Vue/Svelte Tier-1 in v1 (non-React = Tier 0). Do **not** implement API-latency/pprof/DB-query perf in v1 (charted as next axes). Do **not** make BAS learn about tiers/build-modes/meaning (it stays a dumb mechanism). Do **not** build a search-hub data provider for fleet (queries are deterministic/structured). Do **not** put business logic in the CLI. Do **not** keep legacy native test-genie perf or structure-health perf code after cutover (greenfield; default-profile verdict parity is required, not code backwards-compat). Do **not** wire monetization (route via ecosystem-fit; do not price).

## 🤝 Dependencies & Launch Plan
- Required resources: none for live readiness/audit. SQLite is used only for the trend store. Browserless/Chrome are reached indirectly (BAS perf-capture for traces; the Lighthouse runner's own Chrome) and the pipeline skips cleanly when unavailable.
- Scenario dependencies: Code Facts (surface/framework discovery + tier gating), Browser Automation Studio (perf-capture mechanism consumer), Test Genie (phase orchestration + provider-contract scan), structure-health (relinquishes its `perf` domain — axis ② moves here), quality-health (sibling that co-adopts `maturity-go/autofix`), cli-health (registers CLI verbs into search-hub's command index). Maturity wiring uses `packages/maturity-go`; metrics use `packages/api-core/metrics`; CLI client uses `packages/vrooli-cli-go`.
- Operational risks: BAS is old and rotted with pre-existing reds (mitigated by a targeted, behavior-preserving capture-subsystem refactor + baseline-diff triage against known reds); capture flakiness / headless environments (mitigated by graceful silent-skip and tier-0-never-fails semantics); parity drift when delegating test-genie's perf phase (mitigated by a byte-identical default-phase-profile gate, delegate-then-delete, never dual-path); moving fresh structure-health perf code (mitigated by a parity gate + baseline diff; the domain is self-contained); rebrowser-playwright lacking a high-level tracing API (mitigated by a raw CDP session fallback).
- Launch sequencing: (P3, this gate) generate the scenario, apply ecosystem-fit, lock PRD/requirements/docs, verify the stubbed skeleton starts green. Then (P4) proto + domains + CLI scaffolding; (P5) readiness validate + autofix; (P6) capture orchestration + Lighthouse runner + build benchmarks; (P7) deterministic analysis engine; (P8) budgets + trends + suite-run gating + fleet; (P9) migrate structure-health axis ② and delegate+delete test-genie axes ①/③; (P10–P11) UI; (P12) end-to-end validation. BAS perf-capture (P1–P2) lands before P6 so audit has a real mechanism to call.

## 🎨 UX & Branding
- Look & feel: operational engineering console using the `vrooli-default` design kit. The first screens are the audit workbench (pick a scenario → see its tier → run → trace + located findings) and the perf-over-time trend view (build time, startup, LCP, component hotspots), with a separate fleet-performance dashboard — not a marketing landing page. Readiness + one-click autofix and a budgets editor are first-class surfaces.
- Accessibility: WCAG AA contrast, keyboard-operable filters/actions, ARIA labels for status controls, axe-clean navigation landmarks, stable `data-testid` selectors on all actionable and status-bearing elements.
- Voice & messaging: direct, diagnostic, agent-ready. Findings explain what is slow (component, build step, startup surface), quantify it (count/avg/max, budget delta), locate it (file plus line), and flag which readiness gaps are auto-fixable — never speculative.
- Branding hooks: `vrooli-default` design tokens; diagnostic iconography for pass/warn/error and tier-0/tier-1 states; no external logos.
