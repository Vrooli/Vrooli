# CLI Commands: Compute Manager

The scenario CLI is a thin Go wrapper over the API. Every command calls
a single API endpoint and renders the result. There is no business logic
in the CLI. If a command needs to make a decision the API does not
expose, the correct fix is to add the API endpoint, not to compute it
locally.

The CLI binary is built from `cli/`, installed by `make setup` to
`~/.vrooli/bin/compute-manager`, and rebuilt automatically when its
sources change, because cli-core's stale detection rebuilds before any
command that touches the API.

## Read this first: implementation status

**The Compute Manager CLI is partially implemented.** The instance and
reconciliation groups are manifest-declared and dispatchable through
generated Connect primitives. Intent/provider/meter and several operational
commands remain planned or intentionally omitted from the current headless
surface.

This document is split into two parts:

| Part | What it describes | Trust level |
|---|---|---|
| What exists today | Manifest-declared instance and reconciliation commands plus cli-core built-ins | Verified against `cli/manifest.json` and `cli/domains/domains.go` |
| Planned commands | Command groups and methods not yet exposed by the manifest | Proposal or deferred work; verify against the manifest before dispatch |

A planned command becomes real only when it is declared in
`cli/manifest.json`, bound to a handler, and moved into the first part of
this document.

## Source of truth: `cli/manifest.json`

The CLI's command surface, meaning groups, commands, positionals, flags,
RPC bindings and governance metadata, is declared in
[`cli/manifest.json`](../../cli/manifest.json) and validated against the
project CLI-manifest schema (`path:../../.vrooli/schemas/cli-manifest.schema.json`,
schema id `cli-manifest/v1`). The manifest is loaded at startup by
`cliapp.LoadFromManifestPrimitives`, which:

- builds each domain's `SubcommandGroup` from its manifest group
- wires each command's `binding.method` (for example
  `<Domain>Service.List<Entity>`) to a cli-core **primitive** registered
  in the domain's `register.go` bindings map (`cliapp.ProtoList`,
  `ProtoMutation` or `ProtoOperational`, each a `<name>Call` plus
  `<name>Report` pair). The `<name>Call` and `<name>Report` funcs take a
  narrow `cliapp.OperationContext`, with no `JSON()` and no renderers, so
  an operation cannot branch on the output format. Renderer separation is
  enforced by the callback signature, not by convention
- attaches the primitive's observed evidence to each command and fails
  loudly if it disagrees with the manifest's `architecture.primitive`
  declaration, which is what makes the declared L4 maturity verified
  rather than self-certified
- fails loudly on missing handlers, dead handlers, or unknown groups

**Manifest declaration is what makes a verb dispatchable through
vrooli-bridge.** A verb that exists only as Go code, with no manifest
entry, cannot be relayed to a remote node, cannot be governed by
`effect`, `run_eligible` and `permissions`, and cannot be discovered by
prompt-manager. For a scenario whose whole job is acquiring capacity on
other hosts, that matters more than usual: every planned Compute Manager
verb must be manifest-declared, including the ones an operator would only
ever run locally.

Declaring `architecture.primitive` in the manifest is intent; building
the handler with the matching primitive is the proof. That proof is
captured as a committed static artifact,
`.vrooli/generated/cli-primitive-evidence.json` (schema
`cli-primitive-evidence/v1`), generated from the assembled command tree
without executing any command, and regenerated by the golden test in
[`cli/evidence_test.go`](../../cli/evidence_test.go)
(`UPDATE_CLI_EVIDENCE=1` rewrites it). CLI Health reads that committed
file statically to verify each declared primitive and never runs your
commands. A declaration with no matching evidence is advisory
not-yet-verified debt, a mismatch is a gating error, and a stale or
missing artifact keeps declared primitives unverified. See the CLI
architecture maturity reference
(`path:../cli-health/docs/reference/cli-architecture-maturity.md`).

Per-domain tests use `cliapp.RequireProtoServiceCoverage` to assert that
every RPC on the bound proto service either has a manifest command
binding or appears in the manifest's `omitted[]` list with a reason.
Adding a new RPC without exposing it as a CLI command, or explicitly
omitting it, fails the test.

The manifest's `governance` block (`effect`, `run_eligible`,
`permissions`, `requires_confirmation`) is consumed by prompt-manager to
derive action certainty automatically, so scenarios that adopt the
manifest do not need hand-classified action-safety lists.

`binding.kind` is currently `connect-rpc` only. REST-exception commands,
for example a multipart file-upload command whose request body carries
opaque bytes, are appended to the loaded group outside the manifest path
in the domain's `register.go` and documented in the manifest's
`exceptions[]` array.

For environment-variable precedence and CLI config-file shape, see
[`configuration.md`](configuration.md).

## Part 1: What exists today

### Global flags (provided by cli-core)

Every command supports the following flags. **Do not reimplement them in
scenario commands.**

| Flag | Purpose |
|---|---|
| `--api-base <url>` | Override the API endpoint for this invocation |
| `--auto-start` | Run `vrooli scenario start compute-manager` if the API is unreachable |
| `--json` | Emit machine-readable JSON instead of the human report |
| `--no-color` | Disable ANSI color (also respects the `NO_COLOR` env var) |
| `--color` | Force-enable color (overrides terminal detection) |
| `--help`, `-h` | Show command help |
| `--version`, `-v` | Show the CLI version |

### Built-in commands (auto-provided by `cli-core`)

#### `compute-manager status`

Health check. Calls `GET /health` and renders status plus dependency
details. The output uses the **operational contract**: Status, then
Triage, then Next Steps.

```bash
compute-manager status
compute-manager status --json
```

Today this reports one dependency, the SQLite database. It does not
report the business suite, the bridge, or any provider, because none of
those is wired.

#### `compute-manager configure <key> <value>`

Persist a setting to the per-user CLI config file, with the location
resolved per [`configuration.md`](configuration.md#cli-config-file).

```bash
compute-manager configure api_base http://localhost:15001/api/v1
compute-manager configure token "<token>"
```

Read values back without an argument:

```bash
compute-manager configure api_base
```

This is not the place to put a provider API token. Provider credentials
resolve through the credential authority, never through this file. See
[`configuration.md`](configuration.md#environment-variables).

### Scenario commands

There are none. `cli/manifest.json` declares an empty `groups` array and
`cli/domains/domains.go` registers no group, so every dispatchable verb
today comes from cli-core. The template's `notes` CRUD example was
removed by `template-manager detemplate compute-manager`; the worked
example it demonstrated lives in `templates/scenarios/react-vite/`.

## Part 2: Planned commands (not yet implemented)

None of the groups below exists in
[`cli/manifest.json`](../../cli/manifest.json). There is no handler, no
binding and no dispatchable verb for any of them. Names here are a
working proposal derived from the PRD's operational targets and the
domains in [`../concepts/DOMAINS.md`](../concepts/DOMAINS.md), and they
are settled when the manifest entry is authored, not before.

The CLI is required to reach **full headless parity** with the API, so
an operator or an agent can request, inspect, extend and destroy capacity
without a browser. Every planned verb below is therefore expected to be
manifest-declared, with an `architecture.primitive` and a `governance`
block, so that it is dispatchable through vrooli-bridge and governable by
prompt-manager.

Command groups mirror the API domains one for one.

### `compute-manager instance ...`

The group an operator uses most. Mirrors the implemented `InstanceService`
commands currently declared in the manifest.

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `request` | mutation | write | Writes intent, reserves credit, then calls the provider. Carries an idempotency key so a retry is safe |
| `list` | data retrieval | read | Live inventory with elapsed cost and remaining lifetime |
| `get <id>` | data retrieval | read | One instance and its full state history |
| `extend <id> --until <time>` | mutation | write | Moves an expiry later. Refused for an instance already destroyed |
| `reclaim <finding-id> --intent <intent-id>` | mutation | write | Rebuilds the lost local record for an instance this scenario created, from a `provider-only` finding and its surviving intent. Opens a usage window from the provider's reported creation time and sets an expiry from that point, so the instance is metered and expiring again |
| `destroy <id>` | mutation | write | Terminates and settles. Expected to carry `requires_confirmation`, confirmed against the instance's own name rather than a generic prompt, because destruction is irreversible |

`reclaim` starts the meter and `enroll adopt` never does. They are
deliberately different verbs on different groups, because an instance the
reconciler found is capacity this scenario bought, while an adopted host
is a machine the operator already pays for elsewhere. Reclaim is refused
for a finding whose provider-side instance has no matching intent: with
no intent there is nothing proving the machine is ours, and metering
someone else's machine is the mirror image of losing track of our own.

### `compute-manager intent ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `list` | data retrieval | read | Intents, filterable by `--state` and by `--provider-id`. Includes abandoned ones, because an intent stuck in `creating` is the signature of a lost response |
| `get <key>` | data retrieval | read | Look up by id or idempotency key |

There is no `intent create`. Intent is written by `instance request`,
because the ordering guarantee is worthless if a caller can request an
instance without one.

### `compute-manager provider ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `list` | data retrieval | read | Registered adapters by identifier |
| `describe <id>` | data retrieval | read | The adapter's declared billing facts: rounding, minimum billable unit, whether a stopped instance bills, whether inbound traffic counts against the allowance |

No other command names a provider. Selection happens behind the adapter
interface, and a second adapter must change no caller.

### `compute-manager meter ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `usage` | data retrieval | read | Metered usage for an instance or a tenant, computed from transitions this scenario caused |
| `reservations` | data retrieval | read | Open and settled reservations. Identifiers only, since the business suite holds the wallet |
| `ceiling` | data retrieval | read | The tenant ceiling computed from our own meter |

A refusal states which ceiling was reached and what would raise it. It
never says only that usage is high.

### `compute-manager reconcile ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `run` | operational | write | Triggers a bidirectional sweep on demand. Emits findings and mutates no instance |
| `findings` | data retrieval | read | Divergences in both directions |
| `get <id>` | data retrieval | read | One finding with its evidence |
| `quarantine <id>` | mutation | write | Marks a finding as seen so it stops being re-reported on every sweep. Writes to the finding and to nothing else |
| `cost --day <date>` | operational | read | Compares metered usage against a provider statement for one day |

`quarantine` is the only reconcile verb that writes, and what it writes
is a finding's own state. It changes no instance, calls no provider, and
touches no meter. It exists because the findings queue is only readable
if an operator can mark what they have already looked at, and because
marking has to precede any decision about the thing that was found.

There is no `reconcile resolve` and no `reconcile destroy`. The
reconciler reports and never resolves, so a reconciler bug cannot delete
a paying customer's node. Destruction runs through
`instance destroy` after `instance reclaim` has proved the instance is
ours, or outside this scenario entirely when it is not. The operator
procedure is
[Quarantine An Unaccounted Instance](../operations/RUNBOOK.md#quarantine-an-unaccounted-instance).

### `compute-manager expiry ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `run` | operational | write | Triggers the expiry sweep on demand. The background loop runs the same work on an interval |
| `list` | data retrieval | read | Instances approaching their expiry |

The second enforcement point is not a command. It is a timer rendered
into the instance's own first-boot configuration, which powers the
instance off at its expiry with no control plane involved. Verify it with
[Verify The Instance-Side Drain](../operations/RUNBOOK.md#verify-the-instance-side-drain).

### `compute-manager enroll ...`

| Planned verb | Contract | Effect | Notes |
|---|---|---|---|
| `status <id>` | data retrieval | read | Whether an instance became a trusted node |
| `retry <id>` | mutation | write | Re-runs a queued enrollment after the bridge returns |
| `adopt <address>` | mutation | write | Enrolls a host the operator already owns. Records no instance, no intent and no reservation, so it is never metered and stays free forever |

Enrollment is delegation to `vrooli-bridge`. No enroll verb opens a
shell, and none ever will. Unattended enrollment is blocked upstream
until bridge publishes its onboarding public key.

There is no `enroll key-status`. Whether the bridge onboarding public key
is retrievable is a dependency fact, so it belongs in the dependency
block that `compute-manager status` already renders, beside business
suite and provider reachability. A second command that reports one
dependency's readiness would be a second place to look for the same
answer.

### Verbs that will never exist

`OT-P0-007` is a must-ship target, and this is the CLI half of it.

| Never | Why |
|---|---|
| `pause`, `stop`, `suspend`, `halt`, `shutdown`, on any group | A stopped instance still bills at the full rate on five of the seven providers surveyed. A pause button that maps to a provider power-off costs full price for zero value, so **destroy is the only stop.** `instance destroy` is the sole lifecycle terminator |

This is enforced twice, not documented once. A structural test asserts
that no exported method, handler or domain function named pause, stop,
suspend, halt or shutdown exists anywhere in the scenario, and a CLI test
asserts that `cli/manifest.json` declares no such verb. The requirement
stub for that CLI test currently names
`cli/domains/instances/verbs_test.go`; the exact path settles when the
group is created.

The same rule rules out any verb that would create a second `Machine`
object, manage a wallet or invoice, hand out a hostname, or deploy a
scenario onto a host. Those belong to `vrooli-bridge`,
`landing-page-business-suite`, `tunnel-manager`, and `scenario-to-cloud`
with `deployment-manager` respectively.

## Output contracts

Every scenario command should render through one of three human
contracts. Proto-backed commands should use `cliapp.RenderProtoList` or
`cliapp.RenderProtoMutation`, so human consumers see the report while
`--json` consumers receive the proto JSON response shape.

| Contract | Used by | Structure |
|---|---|---|
| **Operational** | `status`, `health`, `audit`, `validate`, `doctor` | Status, Triage, Next Steps |
| **Data Retrieval** | `list`, `get`, `view`, `search` | Summary, Results, Retrieval Hints |
| **Mutation** | `create`, `update`, `delete`, `request`, `destroy` | Result, What Changed, Next Command |

Note that the mutation row deliberately does not list `stop`, which the
generic template row does. This scenario has no such verb.

For commands that aggregate multiple API calls or produce a non-proto
report, use the `RunContext` render helpers directly (`ctx.RenderList`,
`ctx.RenderMutation`, or the operational report helpers).

**`--json` is an output contract, never an operation selector.** Declare
each command's `architecture.primitive` in the manifest (`proto_list`,
`proto_mutation`, `operational` or `action`) and either bind the matching
cli-core primitive builder (`cliapp.ProtoList`, `ProtoMutation` or
`ProtoOperational`) or render inline with `RenderProtoList`,
`RenderProtoMutation` or `RenderProtoOperational`. Both keep the
operation outside any `if ctx.JSON()` branch, which is the top rung of
CLI Health's command-architecture maturity capability. Legitimate special
cases such as streaming, upload, passthrough, external delegation and
durable runs go in the manifest's top-level `exceptions[]`.

Money and time deserve one extra rule. Any command that renders cost or
remaining lifetime must name the amount and the unit. "Usage is high" is
not an acceptable line, and neither is a bare number with no currency or
duration attached.

## Adding a new command

For a new domain, copy the worked CRUD command group in Part 1 first,
then replace it once your real domain is green.

For a command inside an existing domain:

1. If the command needs a new API endpoint, add it first per
   [`api-endpoints.md`](api-endpoints.md#adding-a-new-endpoint). The
   manifest's coverage test fails otherwise on the next CLI build.
2. Add a command entry to the matching group in
   [`cli/manifest.json`](../../cli/manifest.json): `name`, optional
   `description`, `positionals` and `flags`, the `binding` (service plus
   method), the `governance` block (`effect`, `run_eligible`,
   `permissions`, optional `requires_confirmation`), and an
   `architecture` block (`{ "primitive": "proto_list" | "proto_mutation"
   | "operational" | "action" }`) matching the command's renderer. The
   schema in `.vrooli/schemas/cli-manifest.schema.json` is authoritative.
   A verb that is not declared here is not dispatchable through
   vrooli-bridge.
3. Implement the handler in `cli/domains/<domain>/handlers.go`, or a
   focused sibling file, with signature
   `func(ctx cliapp.RunContext) error`. Read values with `ctx.Flag(...)`,
   `ctx.BoolFlag(...)`, `ctx.Positional(...)` and `ctx.JSON()`.
4. Add the handler to the bindings map in
   `cli/domains/<domain>/register.go` keyed by `"<Service>.<Method>"` so
   `cliapp.LoadFromManifest` can wire it. A missing handler and a dead
   handler both fail at startup.
5. Handler implementation should construct generated Connect clients with
   `cliapp.NewConnectHTTPClient(core)`, use `cliapp.UploadFile` only for
   documented multipart REST exceptions, and render proto-backed
   responses with `cliapp.RenderProtoList` or `cliapp.RenderProtoMutation`.
6. Run `make endpoints`. Do not edit
   [`.vrooli/endpoints.json`](../../.vrooli/endpoints.json) by hand.
7. Move the command's row out of Part 2 and into Part 1 of this document
   in the same change.
8. Add a handler test in `cli/domains/<domain>/handlers_test.go` using
   `clitest.NewTestApp`, `clitest.NewAPIServer` and
   `clitest.CaptureStdout` (see
   [`../internal/TESTING.md`](../internal/TESTING.md)). Driving the
   handler via `cliapp.NewTestRunContextFromArgs` against the manifest's
   schema gives the closest parity with the dispatched path.

## Command structure principles

- **Subcommand groups** (`instance list`, `instance destroy`) over flat
  verbs (`list-instances`, `destroy-instance`). Discoverability through
  `--help` is the goal.
- **Positional for required, flags for optional.** `instance get <id>`,
  not `instance get --id <id>`.
- **One command per API endpoint.** If you find yourself making two
  endpoint calls, the API is missing a use case.
- **Error messages must be actionable.** "API unreachable" is bad. "API
  unreachable at http://localhost:15001, try `--auto-start` or `vrooli
  scenario start compute-manager`" is good.
- **A refusal names its cause.** For this scenario that usually means a
  ceiling, a missing reservation, or an unavailable business suite. Say
  which one, and say what would lift it.
