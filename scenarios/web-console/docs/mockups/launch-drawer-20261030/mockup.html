Launch drawer review

The drawer's layout problems are fixable, but the launch data underneath isn't yet reliable enough to charge for. This covers what's wrong, a redesign you can click through, and the order I'd fix things in. Nothing has been changed.

The three things that matter most

Your Claude weekly reading is being hidden.

The card said "Weekly: Unavailable" while the newest sample showed 86%. Tonight it's 87%. That's the number you most need before launching.

An update button can't be added on top of today's data.

All five cards show an arrow. Only Claude and probably Codex could update today. Grok's arrow is false, and OpenCode's card reports the wrong copy.

Agent settings come before the choice they depend on.

You were right. Context limit sits above the choice of agent or shell, yet it only works for plain Claude and Codex launches. Its 1M and 150k values never look at the model.

What's wrong today

Sorted by harm. P0 gives you wrong information or blocks launch. P1 causes misclicks, confusion or dead ends. P2 is polish and upkeep.

Recommended order

Each step ships on its own. The first two fix wrong information, so they should go first whichever design you pick.

  1. Make the readings true. Use each window's newest reading, drop the 15-minute cutoff in favor of showing age, keep old values during refresh, and stop treating a reset moment as a missing window. Proof: a regression test where one window changes and the other doesn't, plus live comparison with the sample file.

  2. Fix the small launch bugs. Refresh the Claude model list, hide the chips where they do nothing, apply limits to the custom bar or say they don't apply, and accept Antigravity in vrooli agent launch. Fix Grok's version comparison.

  3. Add one harness descriptor. A typed block in resource.json covers identity, features and expected usage windows, with a test that fails when a hand-kept table disagrees. Move tables over one at a time. Proof: a fake sixth harness changes one file, and the "grok" count keeps falling.

  4. Add model context data. Capture context_window_size from Claude's status line, read Codex's model list, and return the resolved number with the launcher data.

  5. Rebuild the drawer. Move the rail into a shared component with snap, ship the new order, fixed card heights and a real Manage detail page. Split the two oversized components along the way, and verify on a real iPhone as well as headless.

  6. Add real updates. Add vrooli resource update and a status per harness with one action. Add eligibility checks, repairs for the shadowed and unlinked copies, and an Antigravity updater. The badge goes live here. Proof: a real update of each harness, including one remote node.

  7. Finish the cleanup. Send launches as structured requests, build a shared resource CLI shell, and give transcript parsing one owner. This last one has the highest risk, so it comes last.

Decisions for you

I've picked a default for each, so none of these block the work. Tell me if you'd go the other way.

Type first, or shell in the rail?

Recommended: A, type first.

A makes "agent or plain terminal?" the first decision, which is the flow you described, and gives Group a proper home. B is one less control, but shell is scrolled out of view at the end of a rail. Switching later costs about a day, since both use the same data. Try both with the Layout control above.

Should a stale model list block overrides?

Recommended: warn instead of blocking.

An out-of-date list doesn't make its models invalid, and a bad choice fails right at launch. The catch is that billing class comes from the same list, so a new, pricier model could be mislabeled. Metered models should keep a hard block. The refresh itself also has no governed command yet, so step 2 needs to add one.

Update with one tap, or qualify first?

Recommended: one tap, with rollback available.

The drift report says updates should be qualified with rollback kept. Installs are already versioned, so going back is just relinking, although a rollback command needs adding because the updater refuses downgrades. New versions could quietly change permission behavior, so the page should say when a version is newer than the one the permission policy was reviewed against.

Should Claude's 5-hour window be removed now?

Recommended: no. Let the data decide.

This account still reports it tonight, with a reset at 3:10 AM. I found no public confirmation of the removal, and reports on Codex's 5-hour window conflict. The redesign doesn't care: a window shows only while it's reported, and the descriptor's expected list gets updated when the change reaches you.

How far to trust this

I re-checked the weekly-usage bug, the 15-minute gap, the 5-hour samples, the Claude and Codex model data and the file sizes myself. One sub-agent reported that the live endpoint returned weekly usage, which was wrong, and I corrected it. The 14 samples missing 5-hour all fall on the 5-hour reset boundary, so they aren't a sign of the rollout. The harness table comes from read-only checks, and no update was run, so "works today" is a reading of the code and disk state. These are also unverified: what an update does to running sessions (the symlink swap suggests they continue), whether Codex or Claude clamp a 1M limit, and how the drawer renders on a real device. Line numbers in long files may be off by a few. Vendor limit reports came from third-party sources.
