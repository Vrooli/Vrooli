Part 01

How it actually works

There are four moving parts. They were each built well; they were never introduced to each other.

1 · Identity — what makes your phone "your phone"

Purely browser-local, and deliberately not a hardware claim. On first load, deviceIdentity() mints a crypto.randomUUID() and stores it in localStorage under wc.deviceId, alongside an operator-editable label under wc.deviceLabel.

The shape — phone, tablet, laptop, monitor, ultrawide — is computed fresh on every connect by deviceClassFromScreen(), from screen.width, screen.height and navigator.maxTouchPoints. Touch plus a short edge under 600px is a phone; touch under 1100px is a tablet; otherwise aspect ratio and long edge decide. The comments are explicit that this reads screen and not the terminal grid, because the grid shrinks when a virtual keyboard opens and a phone would reclassify itself as a laptop mid-sentence. That reasoning is sound and the code honours it.

All three values ride the WebSocket URL as query parameters and land in the session's per-connection ClientInfo. Every comment in both languages repeats the same disclaimer: display only, never an authorization signal.

2 · Authority — the size lease

One session, one PTY, one winsize. So exactly one connection holds the size lease and gets to resize the shared terminal. In api/session/session.go the lease owner is stored as leaseOwner chan []byte — a Go channel, which is the identity of one WebSocket connection. Not a device. Not a person.

It moves in four ways: first_client on the empty session, input when a follower types, explicit on a Take over tap, and leader_disconnect, which hands it to oldestClientLocked() — the longest-connected survivor.

3 · Presentation — the silhouette

Presence and size_info frames carry the leader's leaderDevice, deviceClass, kbOpen, holdsLease and viewerCount. A follower runs resolveArchetype() (declared class wins; grid geometry is the fallback), then fitFollowerPresentation() letterboxes the leader's grid inside a fixed-aspect enclosure from one geometry table, picking a full / hairline / strip chrome tier by how much pane surplus is left. This layer is genuinely good work — one table drives both the drawn bezel and the aperture the terminal is inset into, so they cannot drift.

4 · Takeover

takeLease() re-declares this client's last known grid, then sends {type:"take_lease"}. The server calls AcquireLease, applies the new owner's declared size to the PTY, and re-publishes presence to everyone.

One sentence explains four of your six symptoms: a device can be its own remote. Two sockets from one phone are two independent clients to the server, and the UI has no way to notice they are the same hardware.

Part 02

What is broken

Six defects, ordered by how much of the annoyance they account for. Every one is traced to a specific line; none required guessing.

D1 Blocker Confidence
High — mechanism read end to end

The phone becomes its own ghost leader

"Sometimes it thinks there's a remote device in control when it's really just the current device."

When a phone's socket dies without a close frame — backgrounded Safari, a Wi-Fi-to-cellular handoff, a tunnel — the server does not find out immediately. It learns via a read deadline of 2 × wsPingPeriod, which is 60 seconds by default. Meanwhile the client, which knew instantly, has already reconnected.

For up to a minute the session holds two ClientInfo records with the same DeviceID and the same DeviceLabel. The dead one still owns the lease. So viewerCount is 2, holdsLease is false, and the phone dutifully draws a phone-shaped silhouette captioned with its own name and offers to take control back from itself.

It self-heals when the deadline expires, which is exactly why it reads as intermittent and unreproducible.

Evidence api/terminal_ws.go:160 — read deadline = 2 × 30s api/session/session.go:787 — Subscribe registers a second client api/session/sizelease.go:146 — presence built from leaseOwner's ClientInfo useTerminalSession.ts:388 — applyLeaderPresentation drops msg.leader TerminalPane.tsx:199 — presentsFollowerDevice = frame && viewerCount > 1
FixTwo halves, both cheap. Client: read msg.leader — it is already typed in types/terminal.ts:89 — and suppress the follower presentation when it equals this device's id. Server: on Subscribe, when an existing connection carries the same non-empty DeviceID, treat the newcomer as that device reclaiming its seat: move the lease and evict the stale socket instead of waiting out the deadline. A device reconnecting to its own session should not have to ask itself for permission.
D2 Blocker Confidence
High — single-line cause, matches laptop/phone split exactly

Take over control cannot be tapped, only clicked

"The takeover button doesn't seem to work when I'm viewing it from my phone… it always works when viewed through my laptop."

The pane's touch layer attaches touchstart / touchend listeners on the pane container in the capture phase, so it sees every touch before any descendant. On a short tap it calls e.preventDefault() — deliberately, with a good comment: it suppresses the synthetic click the browser fires ~300 ms later, by which time the virtual keyboard has resized the pane and the click would land somewhere else.

The consequence is that no click event is ever dispatched inside the terminal pane on a touch device. The Take over button is a DOM descendant of that container, so its onClick never runs. A mouse produces no touch events at all, which is why the laptop is unaffected.

The tell is already in the file: onTouchStart carries a hand-written escape hatch — target.closest("[data-testid='terminal-context-menu'], [data-testid='ctx-backdrop']") — added the last time this exact bug bit. The device caption was never added to that list.

Evidence useTerminalTouch.ts:635,640 — capture-phase listeners on the pane container useTerminalTouch.ts:566 — e.preventDefault() on the tap path useTerminalTouch.ts:360 — the two-entry allowlist DeviceFrame.tsx:101 — <button onClick={onTakeOver}>
FixStop maintaining an allowlist of test ids. Invert it: bail out of the gesture machine whenever the touch target is interactive at all — target.closest("button, a, input, textarea, select, [role='button']") — so the terminal's gesture layer only ever claims touches that landed on the terminal. That fixes the take-over button and every future in-pane control in one edit.
D3 Friction Confidence
High — stacking rules are deterministic

The device frame paints over the messages view

"When I have the messages view open it shouldn't be showing the device frame, but it still does."

The messages view is not a replacement for the terminal — it is an absolute inset-0 sibling layered on top of a still-mounted TerminalPane. That sibling has no z-index, so it sits at z-index: auto.

Inside the terminal pane, the device caption carries z-wc-chrome-raised, which is z-index: 20, and the enclosure carries z-index: 1. The pane root is relative with no z-index, so it does not establish a stacking context — those two values escape into the parent's context and win against a later sibling at auto. DOM order says messages are on top; the z-scale says otherwise, and the z-scale wins.

Note the blast radius is wider than the device frame: the pane status toast, upload errors and input errors all use the same token and will also punch through the messages view.

Evidence WorkspacePaneShell.tsx:216 — MessagesPane in a bare absolute inset-0 DeviceFrame.tsx:82 — z-wc-chrome-raised on the caption useFollowerViewportLayout.ts:23 — FOLLOWER_ENCLOSURE_Z = 1 tailwind.config.ts:81 — wc-chrome-raised = 20 TerminalPane.tsx:312 — root is "relative", z-index auto
FixTwo independent corrections, and I'd do both. Containment: give the pane root an explicit isolation: isolate so its z-scale cannot leak past its own box — that is the general bug, and it protects the toasts too. Intent: a follower frame while the reader is in the messages view is meaningless chrome; pass the view mode down and stop rendering it, rather than relying on paint order to hide it.
D4 Friction Confidence
High — the pinch workaround is the proof

Nothing re-fits the terminal when the role changes

"When I take over or get back into the main full view, sometimes the terminal doesn't resize properly and I have to pinch to zoom in and out to get it to figure out that it needs to resize."

Your workaround is the diagnosis. There are exactly three things that fit the terminal and report a new size upstream: a ResizeObserver on the container, a change to paneFontSize, and first mount. A lease change is none of them.

Worse, it cannot be. isFollower reaches the lifecycle hook as isFollowerForLifecycle — a useCallback with an empty dependency array that reads a ref. Its identity never changes, so every effect that depends on it is frozen at mount and none of them re-run when you take control back.

What does run is useFollowerViewportLayout, which clears the follower styles and calls refit(). But refit is scrollAwareFit — it fits xterm to the box and never calls sendResize. So the local grid and the PTY's winsize can disagree, and the container has not changed size, so the observer stays quiet. Pinching changes paneFontSize, which is the one live dependency left, which fires the effect that finally calls maybeSendResize.

A second trap compounds it: maybeSendResize requires serverDiffers && dimensionsChanged. lastSentSizeRef is never reset — not on reconnect, not on a role change. If a fit lands on a grid this client already sent once, dimensionsChanged is false and the correct size is withheld precisely when it is needed most.

Evidence TerminalPane.tsx:114 — isFollowerForLifecycle: useCallback(…, []) useXtermLifecycle.ts:157,178,188 — three effects gated on that frozen identity useXtermLifecycle.ts:22 — maybeSendResize's double guard useFollowerViewportLayout.ts:95 — refit() with no upstream declaration
FixMake the role a real dependency instead of a ref smuggled through a stable callback, and make "I am now the leader" an explicit transition that re-fits and declares: fit to the host, then unconditionally sendResize(terminal.cols, terminal.rows). Reset lastSentSizeRef on every transport open and on every lease change — the guard exists to suppress chatter, not to withhold the truth after the ground moved.
D5 Friction Confidence
High — explicit branch in the code

A reconnect never re-declares the device's grid

Size declaration is guarded by if (t && !wasReconnect). A first connect declares its grid; a reconnect declares nothing. But the server built a brand-new ClientInfo for that socket with DeclaredCols = DeclaredRows = 0.

So if that connection later inherits the lease through leader_disconnect, applyDeclaredSizeLocked finds a zero and returns without touching the PTY. The new leader is left rendering the departed leader's grid on hardware that never agreed to it. Take over control still works — it re-sends declaredSizeRef explicitly — but that ref holds the size from before this device became a follower, so a rotation or a keyboard open while following is silently discarded.

This is the same class of bug as D4 and shares its symptom, but it is a distinct cause and needs its own fix.

Evidence useTerminalSession.ts:248 — if (t && !wasReconnect) api/session/session.go:836 — applyDeclaredSizeLocked on leader_disconnect api/session/sizelease.go:101 — zero declaration returns nil PTY
FixDeclare the grid on every open. A connection's declared size is per-connection server state; a reconnect is a new connection and must re-establish it. Keep declaredSizeRef current while following too — the device's own preferred grid is knowable at all times, whether or not it is currently allowed to apply it.
D6 Design smell Confidence
High as written; low as a live bug

Two different answers to "am I following?"

The pane computes presentsFollowerDevice = followerFrame !== null && viewerCount > 1 and uses it for the visual frame — but hands the raw isFollower to the xterm lifecycle and the touch layer. So a viewer who has lost the lease with viewerCount === 1 gets a terminal that refuses to re-fit and a pinch gesture that is disabled, with no frame and no Take over button to explain either.

The comment above that line says the two must agree, and then wires them to two different predicates. Today the reachable window is narrow because presence and lease travel in the same frame. It is still one concept with two implementations, which is how D4 stayed hidden.

Evidence TerminalPane.tsx:199 — presentsFollowerDevice TerminalPane.tsx:126,247 — raw isFollower to lifecycle and selection
FixDerive one followerMode value in the session hook and feed every consumer from it. If a state has no frame it should have no follower restrictions either.

The test topology is the real finding

84 unit tests pass across seven files covering this feature, and every symptom you reported survives them. That is not a coverage gap — it is a coverage shape problem. Everything tested is a pure function: geometry fitting, archetype resolution, silhouette rendering, wire-message reduction. Every defect above lives in a seam:

  • D1 — two connections, one device. Needs two clients against one session.
  • D2 — a capture-phase listener versus a descendant's click. Needs a real touch event, and jsdom will not produce one.
  • D3 — CSS stacking contexts. No unit test can observe paint order.
  • D4/D5 — effect dependency identity and reconnect branches. Needs a mounted pane across a role transition.

The scenario has three BAS suites — foundation, messages, snippets — and not one case touches the follower, lease or device-frame surface. The nearest neighbour, reconnect-offline-buffer-replay, is single-client. Nothing in the repo has ever exercised two viewers on one session end-to-end.

Part 04

Where I'd start

Ordered deliberately: the first item changes the model, and it makes two of the later ones smaller. The last one is what stops this list from being written again in three months.

  1. Make identity beat the socket

    Read msg.leader in the client and suppress follower presentation when the leader is this device. Then, on the server, let a reconnecting DeviceID reclaim its own lease and evict its stale socket. D1 disappears, and D5's blast radius shrinks with it. One-line client change, one modest server change.

  2. Let the pane's controls receive touches

    Replace the two-entry test-id allowlist in useTerminalTouch with an interactive-element check. Smallest change on this page, and it is the difference between the feature working on a phone and not.

  3. Contain the pane's z-scale, and gate the frame on view mode

    isolation: isolate on the pane root fixes the class of bug; passing view mode into TerminalPane fixes the intent. Both, not either.

  4. Give the role transition an owner

    One followerMode value, real effect dependencies rather than a frozen callback over a ref, an explicit re-fit-and-declare when the lease arrives, and a lastSentSizeRef reset on every open and every role change. This is the largest of the four and it retires D4, D5 and D6 together.

  5. Put a two-client test where the bugs live

    A Go test that subscribes two clients with the same DeviceID and asserts the newcomer is not made a follower of itself. A BAS case that opens one session in two viewports, taps Take over from the touch viewport, and asserts the frame clears and the PTY adopts the new grid. Two tests, and every defect above becomes detectable rather than reportable.

Worth saying plainly

The follower geometry layer is the strongest code in this area — one table driving both the drawn bezel and the terminal's aperture, keyboard plate sized from its own key metrics rather than leftovers, declared class deliberately preferred over the grid so a keyboard cannot morph a phone into a laptop. Those comments read like someone who had already been burned and fixed it properly. You said the frames look great, and the code explains why.

What's missing is not care. It is that "which device am I" and "who is in charge" were built as separate, well-documented systems that each state they are not the other — and then nobody wrote the line that reconciles them.
