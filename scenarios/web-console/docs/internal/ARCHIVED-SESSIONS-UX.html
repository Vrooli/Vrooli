Archived sessions

Closing a session should file it, not destroy it. Below: where the archive lives in the sidebar, what the deep search surface looks like, and how a filed session comes back.

Corrections to my last answer

Search is closer than I implied

It already searches message text, not session names

searchConversation(sessionId, query) drives the navigator panel in the messages view. Server-side it's SELECT … WHERE session_id = ? AND text LIKE ? with a 160-char excerpt builder. So the primitive you need exists and is proven — widening it to "all sessions" is dropping one predicate, not building a search engine.

ui/src/api/conversation.ts:149 · api/conversation_repository.go:243

But LIKE '%…%' won't survive the archive

There is no FTS5 table and no index on text. Scoped to one session that's fine — a few hundred rows. Scanned across every session you've ever closed, it's a full table scan that gets slower every week. Widening the scope and adding an FTS5 index are the same change; don't split them.

Semantic search is a real project, not a flag

web-console has one AI provider (Ollama, for generate/summarize) and no embeddings anywhere — no vector store, no embed calls, no backfill. Adding it means an embedding model, somewhere to put the vectors, a job to backfill years of messages, and re-embedding on every write. It's a genuinely good third rung. It should not block the first two, which deliver most of the value.

Reuse, don't rebuild

The right pane should be MessagesPane in a read-only mode, not a new viewer. You get markdown, mermaid, the file viewer, and the existing copy and export affordances for free — and they stay consistent with the live messages view forever.

The action that earns the feature

→ Send to composer is the literal job you described: pull a message out of an old conversation and into the one you're in now. It's cheaper to build than Reopen and I'd guess you reach for it ten times more often.

Wireframe 04 · the honest state

Not everything can come back

Recoverability() already refuses claude, opencode and grok sessions with no recorded agent session id, and a plain shell has nothing to resume at all. That distinction has to be visible on the row, before the click — the recovery drawer already does this well with a disabled button and a reason string. Same pattern, three states:

claude · trusted-receipt-signing archived 3 days ago · agent transcript on disk
● Reopenable Reopen Export
Agent id recorded and the agent's own history still on disk. Reopen pastes the resume command.
claude · early experiment archived 5 months ago · agent transcript pruned
● Read-only — agent history no longer on disk Reopen Export
Decayed. The conversation is intact and searchable forever; the live resume is gone.
terminal · scratch archived 3 weeks ago · no agent, no messages
● Nothing to restore Reopen Delete
A shell session carries no recoverable value. These are the ones retention should expire early.

That middle state is the one worth designing for deliberately. An archive naturally decays from reopenable to readable as the agent's own on-disk history gets cleaned up — those directories are far larger than the SQLite rows and are what retention will actually need to prune. Showing the decay is more honest than implying everything reopens forever.

Wireframe 05 · the cheapest win

Close → undo

Before any of the above ships, this one change converts the scariest action in the product into a safe one. Roughly twenty lines.

▤ Archived claude · agi Undo

Toast on close, ~8 seconds. Archive becomes the X button's meaning; Delete moves to the context menu behind a confirm. Today the default is destructive and silent — this inverts it.

The search ladder

Three rungs, in cost order

RungWhat it matchesWhat it needsCost
Name filter Session and group names in the shallow sidebar list Client-side string match over rows you already have Hours
Text search Literal substrings in every message of every session Drop the session_id predicate; add an FTS5 index — the existing LIKE won't scale past a few thousand rows Days
Semantic "that thing about signing receipts offline" with no shared words Embedding model, vector store, backfill job, re-embed on write, drift handling — none of which web-console has today Weeks

Design the UI for all three now — that's the Text / Semantic toggle in wireframe 03 — and ship rungs one and two. Semantic slots into an existing surface later instead of forcing a redesign. My honest read: literal search over your own messages covers most of what you described, because you tend to remember your own phrasing.

Before building

Four decisions I can't make for you

  1. Does reopening copy the transcript or re-point it? Recover() mints a new session id and copies the conversation rows. Archive → reopen → archive → reopen leaves three copies of one conversation cluttering the archive. Either re-point the rows or thread a lineage so the archive collapses a chain into one entry. This is the detail most likely to make the feature feel broken.
  2. What's the retention policy? There is none anywhere in web-console — I grepped. Today the delete cascade is the retention policy, and archiving removes it. This has to ship in the same change, not after.
  3. Archive everything, or only sessions with messages? I'd archive uniformly so there are no surprises, default the archive view to "has messages", and expire message-less shells fast.
  4. Does the archive subsume the recovery banner? I think it should — a crash orphan is just an involuntarily archived session. One surface, one mental model, and it deletes code.
