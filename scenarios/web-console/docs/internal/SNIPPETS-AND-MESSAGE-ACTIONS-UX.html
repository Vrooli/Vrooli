The Snippet Layer

Session groups gave the console a way to hand a plan from a planner to an implementer. What it did not give you is a reusable message that belongs to nobody — no group, no role, no handoff. That is the missing noun, and it is smaller than it looks.

What is actually there

Your memory of the template is right, and the design around it is better than you think

The default group template really does say almost nothing. In api/internal/grouptemplates/seed.go, the shipped “Plan → Implement” template is two roles: an eager Planner running Claude Code, and a waiting Implementer running codex --yolo whose entire prompt is Implement the plan at {{payload}}.

But the terseness is not laziness — it is a deliberate constraint, and it is worth knowing before you expand on it. The design record lists ten prohibitions, three of them enforced by greps in SEAMS.md, whose collective point is that nothing in the data model may know what a plan is. No plan_path field, no pair-shaped model, no parser in the template language. That is why the seed prompt is one line: a richer default would have smuggled one workflow into shipped content.

Prompts live
On the receiving role (workspace_roles.incoming_prompt), never on the sender. Decision D3. A running session and a waiting placeholder both supply their own framing, so handoffs compose.
Template language
Exactly one placeholder, {{payload}}, and three cases in renderHandoffPrompt: empty template → payload alone; no placeholder → template, blank line, payload; placeholder → substituted. Decision D4: no parser, no escaping, no error states.
Storage
Three tables already carry operator-authored text: group_templates, handoff_rules, shortcut_profiles. All three seed a deletable example through the same public write path the UI uses. No is_builtin column anywhere.
The blocker
targetsForSession() in ui/src/hooks/useHandoff.ts:151 opens with if (!groupId) return []. A session outside a group has zero handoff targets. That is your “I made a plan outside a group and now I can’t hand it off” — one line, one real design decision behind it.
Already built
useComposerDraft exposes appendAtCaret(text). The insert mechanic you need exists and is used by voice dictation today. HandoffComposer already does multi-select with per-target editable text. HEADER_COLORS is an 8-swatch palette shared by panes and groups.
The diagnosis

You don’t need a better role prompt. You need a text that belongs to the sender.

Every reusable string in the console today is addressed by who receives it. That is correct for handoffs and wrong for the thing you keep describing: the message you are about to type, again, for the fourth time this week, in the middle of an investigation. It has no receiver yet. It has no group. It may never be sent twice to the same agent.

So the new noun is a snippet: a named, colour-tagged body of text with no owner and no destination. Not a role. Not a template. Not a rule. And critically — as you spotted yourself — not a skill.

The distinction worth writing down

A skill is authored, reviewed, indexed, and read by agents through discovery. A snippet is jotted, reused, edited in place, and read by your thumbs. Forcing the second through the machinery of the first is exactly what kills it — the moment capturing a phrase costs a spec-conformant SKILL.md, you go back to your notes app.

TierLives inLifetimeGovernanceConsumer
Draft useComposerDraft + localStorage One session, one message None You, right now
Snippet web-console SQLite message_snippets Days to weeks — disposable by design None. Personal. Delete freely. You, across sessions
Skill prompt-manager registry (SKILL.md) Permanent capability Spec-conformant, indexed, publishable Agents, via discovery

One caveat I’d want checked rather than assumed: prompt-manager currently carries two different Skill structs. The live API store model (api/internal/store/models.go) is the SKILL.md registry. But cli/internal/types/types.go holds an older shape with Variables, UsageCount, IsFavorite, QuickAccessKey — which is almost exactly the snippet model described here. It looks like legacy, but if it is live, that is a naming collision worth resolving before you ship a second one.

Reach

Four surfaces compose text. Only one of them can reach a saved prompt.

Recommendations

Eight moves, ordered by how much they buy per line changed

S1

Add message_snippets as an ordinary row, copying the idioms already in the schema

Columns: id, name, body, color, pinned, use_count, last_used_at, sort_order, timestamps. That is group_templates plus handoff_rules with nothing invented — same use_count, same sort_order, same seed-into-empty-store-only pattern, same absence of an is_builtin marker.

No JSON child column. D10 chose JSON for templates because roles are a list; a snippet’s body is one string, so the reason doesn’t apply and a plain column keeps it searchable with LIKE.

S2

One <SnippetPicker>, one useSnippets(), mounted on every surface that composes text

Insert-at-caret is the only default action, and it already exists: draft.appendAtCaret(text). Replace is destructive against an uncontrolled textarea with no undo — make it a secondary action or leave it out of v1 entirely. Send-immediately is a third, deliberate control; do not let it share a tap target with insert.

Your instinct to put it in the full-screen composer overlay is right as the primary home. Just don’t make it the only one.

S3

Capture where the value is discovered — not in a settings form

This is the highest-leverage single affordance in the whole memo. Your real workflow is not “open settings and author a prompt.” It is “that one worked, I’ll want it again.” So put Save as snippet on a message you already sent in MessagesPane, and on the current composer draft.

The conversation store already holds your sent messages in conversation_events and the pane already renders them. Settings becomes the place you go to tidy up, not the place you go to create — same relationship the group picker now has with the manager drawer.

touches ui/src/components/MessagesPane.tsx · FullScreenComposer.tsx · a tenth settings tab beside templates and handoff-rules

S4

Generalize {{payload}} to named variables — without growing a grammar

Keep D4’s discipline and change only the noun. Scan for distinct {{token}} occurrences, render one text field per distinct token, substitute. Still no parser, no conditionals, no computation, no escaping rules. {{payload}} simply becomes one reserved variable name among several — which is what makes a role’s incoming_prompt and a snippet the same type.

Allow a closed set of auto-resolved names the console can fill without asking — {{cwd}}, {{session}}, {{selection}} — and nothing else. Everything unrecognised prompts you. Resist adding to that list later; an open resolver is a template language wearing a disguise.

One behaviour to change deliberately: renderHandoffPrompt today silently blanks an empty payload ("Review {{payload}} now" → "Review now", asserted in handoff.test.ts). For a named variable that is the wrong default — leave the token visible so a half-filled snippet fails loudly instead of shipping a sentence with a hole in it.

touches ui/src/lib/handoff.ts (which currently imports nothing — keep it that way) · handoff.test.ts

S5

Unify snippet and role prompt by copy, not reference

Inserting a snippet into a role’s incoming_prompt copies the text. It does not store a snippet id. Referencing would buy “edit once, every role updates” and cost “delete a snippet, a template silently breaks” — and it would put a foreign key into a table whose whole doctrine is that every row is an ordinary, freely deletable row.

group_templates already copies its roles into a group rather than referencing them. Follow that.

S6

Widen handoff targets past the group boundary

This is your “I planned outside a group” case, and it is separable from snippets entirely — ship it independently if you want a quick win. Replace if (!groupId) return [] with a two-section target list: this group first, then other sessions below it. The group stays the default scope; it stops being a hard gate.

The model barely resists: HandoffTarget’s kind: "session" variant carries no group at all. Only kind: "new-session" needs work, since it takes a groupId — make it nullable, or drop that option when there is no group.

touches ui/src/hooks/useHandoff.ts:151 · handoff/HandoffComposer.tsx (section headings in the target list)

S7

Colour, yes — but recency and filtering are what actually make it findable

Reuse HEADER_COLORS verbatim. A third palette in the same app is how design systems rot, and a snippet tinted the same teal as the session you use it in is a real association.

But colour stops scaling at eight and is useless for search. Order the picker by most-recently-used (last_used_at, with use_count as tiebreak), give it type-to-filter over name and body, and allow pinning. That combination handles fifty snippets; colour alone handles six.

S8

Build one one-way promotion path to a skill, and no sync

When a snippet earns permanence, offer Promote to skill — shell out to prompt-manager skill create with the body prefilled. Explicit, one direction, no ongoing coupling, and the snippet stays where it is afterwards.

That is the honest way to respect “skills are the official ones” without taxing the throwaway case. It also gives you a real signal for which snippets deserve promoting: use_count.

Worth noting this connects to something you’ve wanted before — skills that become part of a prompt rather than a tool call an agent may skip. Substitution exists; the resolver hook never got built. A snippet resolver in the console is the smallest honest first implementation of it.

Sequence

Build order, and where each step is independently useful

Genuinely ordered — each step is shippable on its own, and steps 1–3 already deliver the thing you asked for. S6 has no dependency on any of them and can go first if the handoff-outside-a-group friction is biting today.

  1. Store + thin settings CRUD — table, Go domain, proto, a settings tab that lists and edits. S1
  2. Picker in composer and toolbar — insert-at-caret only, MRU ordered, type-to-filter. S2 · S7
  3. Save-from-sent-message — the capture affordance that makes the store fill itself. S3
  4. Handoff targets past the group — independent; ship any time. S6
  5. Named variables — generalize the placeholder, keep the grammar closed. S4
  6. Picker in handoff and template panels — nearly free once the picker exists; this is where a snippet and a role prompt visibly become one thing. S2 · S5
  7. Promote to skill — last, driven by whichever snippets actually accumulated a use_count. S8
Restraint

What I’d actively not build

✕
A tag taxonomy. Everyone builds it, nobody maintains it. Colour plus MRU plus text filter covers the range a personal store ever reaches.
✕
Auto-suggesting snippets as you type. This is the capture-rule mistake in a new costume. D6 and D13 say suggestion is the part that can be wrong in a way that annoys daily, and it ships last. If you ever do it, route it through the existing handoff_rules message_text source rather than inventing a second matcher — and keep prohibition 4 intact: the send path must never be able to reach the matcher.
✕
A scope hierarchy in v1. shortcut_profiles has service → workspace → parent. Snippets don’t need it yet. Expect to be asked for it; don’t pre-build it.
✕
Routing snippets through prompt-manager. Different lifecycle, different consumer, different governance. web-console already owns four kinds of personal convenience state in its own DB; this is the fifth.
✕
Sending snippet insertion through the AI provider. AiSuggestBar exists and is a different feature. A snippet must be instant, offline, and exactly what you saved.
✕
Hanging snippets off the group template. Orthogonal. Coupling them re-creates the group dependency you are trying to escape.
Your call

Four decisions I’d rather you made than I assumed

Should a snippet be able to send itself, or only fill the box?
my lean Fill only, in v1. A one-tap send from a picker list is a mis-tap away from delivering the wrong prompt to a running agent, and you lose the chance to tweak the few words you always tweak.
Per-machine or shared across remote targets?
my lean Wherever the console’s DB lives, same as templates and rules. But you do drive remote targets, so if your snippets should follow you across machines that is a different — and much larger — feature.
A tenth settings tab, or folded into “Templates”?
my lean Its own tab. Folding a sender-owned text into a panel about role recipes muddies exactly the distinction this memo is drawing.
Does “replace the draft” earn its place?
my lean No, not at first. It is destructive with no undo path on an uncontrolled textarea. If you want it, it needs a real undo, which is more work than the whole picker.
