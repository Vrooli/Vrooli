How the input and output lanes actually work

A structural read of the web-console terminal stack — the round trip from a keypress to a PTY and back — and the five places the architecture, not the code, is what's failing.

01The map

Read it as a loop. Left column descends from keypress to kernel; right column climbs from kernel back to the screen. The two columns never touch: there is no point in the system where a keystroke and a mouse-wheel event, or a keystroke and the output it caused, are ordered against each other.

02What the design gets right

Worth saying plainly, because the problems below are all composition problems, not craft problems. The pieces are unusually well made.

  • The server emulator is the source of truth. terminal.Emulator parses the real ANSI stream and serializes a self-contained replay; xterm.js is a renderer with no authority. That is the correct choice and most browser-terminal projects get it wrong.
  • One input seam. Every source — typing, paste, image upload, voice, toolbar keys — reaches the PTY through inputGate.submit → Session.applyInput, and greenfield tests fail the build if anyone reaches around it.
  • The tmux delivery rules are hard-won and correctly documented. send-keys -l plus an explicit -X cancel, per-call paste buffers, bracketing keyed to semantics rather than transport — every one of those constants has a comment explaining the bug it fixes.
  • Failure has a vocabulary. stdin_ack carries typed reasons, and the paste UI genuinely waits on settlement instead of assuming success.

So the question isn't "is this code careful." It is: the pieces are individually sound and the system still misbehaves — where is the seam?

03The offset ledger has two owners

This is the one I'd fix first. It is not a bug in either half — each half is internally correct — it's that the two halves count in different units.

The reliable input lane is built on a cumulative byte offset. The client keeps a writeHead that starts at 0 when the hook mounts. The server keeps session.acceptedThrough, which starts at 0 when the PTY session is created and is documented as "monotonic for the lifetime of the PTY session."

Those two lifetimes are not the same lifetime. A session outlives a page load, a pane remount, and a browser tab — that persistence is the whole point of the tmux backend. So the moment a fresh client attaches to a session that has ever received input, the two counters disagree by exactly the number of bytes typed before.

session_ready carries accepted_through: 47. The client evaluates 47 > writeHead (0), latches unreconcilable = true, and from that instant every send() returns {sent:false, reason:"not-ready"}. The gate dutifully queues each keystroke. Nothing ever drains the queue, nothing surfaces an error, and unreconcilable is never cleared — not by resetForNewConnection, not by a reconnect, not by anything. The pane looks alive and silently accepts input forever.

Two paths reach the same dead end. If the server's count is ahead, the client latches unreconcilable and freezes. If a client's offset is behind — a second device on the same session — terminal_ws_input.go takes the msg.Offset < accepted branch and replies ok: true without writing the bytes to the PTY at all. Input vanishes and the UI is told it succeeded.

The second path matters because multi-viewer isn't hypothetical here — viewerCount, leaderDevice, the size lease and the "Take over" affordance exist precisely to support two devices on one session. Two viewers means two independent write heads advancing one shared server counter. There is no arrangement of two clients under which that counter is meaningful to both.

What makes this a maturity finding rather than just a bug: the behaviour is tested, and the test asserts it as correct.

// ui/src/hooks/terminal/useStdinStream.test.ts
it("rejects a server offset that is ahead of the local write head", () => {
  result.current.send("x", "typing");
  result.current.reconcile(2);
  expect(events).toEqual([[2, false, "unreconcilable"]]);
});

As a statement about useStdinStream in isolation, that assertion is right. As a statement about the system, it encodes the failure. Every test in the suite pins accepted_through: 0 — the composition where the counters can diverge is the one case nobody wrote down.

04The output path forks two processes per frame

The persistent backend pays a subprocess tax on both hot paths, and pays it while holding the mutex that everything else in the session needs.

After every PTY output frame, the WebSocket forwarder calls emitEchoState(). That calls Session.EchoState(), which takes s.mu and — still holding it — asks the tmux backend for the pane's echo bit. On tmuxPTY that means tmux display-message -p '#{pane_tty}' followed by stty -a -F <tty>. Two process spawns and two tmux-server round trips, per frame, per connected viewer.

The deduplication in emitEchoState compares the result — so it saves a WebSocket frame, and saves nothing at all on the cost that matters.

The arithmetic is the finding. PTYReadBuffer is 4096 bytes, so a program emitting 4 MB of output produces roughly 1,000 frames — about 2,000 process spawns and ~2.1 seconds of subprocess time, serialized under the session mutex, for one viewer. The standard backend does the identical job with one ioctl.

And tmuxCommandTimeout is 5 seconds. If the tmux server stalls, Session.EchoState() can hold s.mu for up to ten seconds — during which readLoop cannot broadcast, applyInput cannot write a keystroke, Resize cannot run, and Subscribe cannot attach a new viewer. A cosmetic feature has a hard lock on the terminal's critical section.

What echo_state is for is the client-side prediction overlay: don't draw a predicted character where the shell has echo off, because it might be a password. That is a good invariant, correctly fail-closed. It just doesn't need a per-frame probe — echo state changes when a program changes it, which is a rare event, and two of the four fields (InAltBuffer, CursorAtLineEnd) already come free from the emulator.

05The rest of the findings

Ranked by how much of the system each one moves. Severity chips are impact; the tags underneath name which of your five axes it lands on.

F3

One mutex owns parsing, replay, input, and presence

Critical
PerformanceReliability

s.mu guards the emulator feed, snapshot serialization, the client registry, the size lease, and the PTY pointer. broadcast() holds it across a full ANSI parse of every frame; Subscribe() holds it while serializing up to 2 MiB of scrollback. So output parsing blocks input delivery, a new viewer attaching stalls the read loop, and the lock is the reason F2's subprocess cost turns into a system-wide stall rather than just a slow probe.

This is the structural reason the terminal "feels stuck under load" and the reason a single slow tmux call takes the whole pane down with it.

api/session/session.go — EchoState() takes s.mu, then calls out to the backend
api/session/broadcast.go — broadcast() holds s.mu across emu.Feed(data)
F4

Two input lanes, no shared ordering

Structural
ReliabilityQuality

Typing goes stdin → send-keys (~3.2 ms, two forks, via the tmux server). Mouse and wheel go control → ptmx.Write (one syscall, immediate, straight to the attach client). Same session, same WebSocket, two transports with wildly different latency and no sequencer between them.

A control frame issued after a keystroke can and will reach the pane first. In a TUI that mixes mouse and keys — which is exactly what Claude Code, vim and fzf do — the pane observes events in an order the user never produced. The control lane is also deliberately unacknowledged and unreplayed, which is right for a wheel tick and wrong for anything that carries state.

The same split explains a subtler one: the ANSI responder answers DA1/DA3 queries through SendInput — the typing lane — so a capability reply can interleave into the middle of a line the user is typing.

api/pty_tmux.go — KindControl → ptmx.Write; KindKeystroke → tmux send-keys
api/session/ansi_responder.go — server replies share the keystroke lane
F5

PTY delivery runs inline on the WebSocket read loop

Structural
ReliabilityPerformance

The loop is ReadMessage() → dispatch → write to the PTY → write the ack → ReadMessage(). On the tmux backend the middle step is two process spawns, so each keystroke blocks reading the next one for ~3 ms. Type at 10 cps and a third of the loop's time is spent forked. Hit a 5-second tmux timeout and the connection stops reading anything at all — including take_lease, resize, and pong.

It couples the other way too: the ack write contends on writeMu with the output forwarder, whose wsWriteTimeout is 10 seconds. A client with a stalled TCP receive window therefore blocks its own input acknowledgements. Slow output stops input.

api/terminal_ws.go — wsWriteTimeout = 10s, one writeMu shared by both loops
api/pty_tmux.go — tmuxCommandTimeout = 5s ×2 per delivery
F6

Input is resumable; output is not

Structural
PerformanceQuality

The input lane got a real reliability protocol: cumulative offsets, acknowledgement, replay of the unaccepted suffix. The output lane got none of it. Every WebSocket open — including the visibility-triggered reconnect a phone does every time it wakes — runs terminal.reset(), terminal.clear(), and a full re-stream of up to 2 MiB of ANSI in 64 KiB JSON frames, which the client then re-parses from scratch.

The client already holds that state. There is no cursor, no "I have through byte N", no delta. On a flaky mobile link this is the dominant cost of the entire system, and it's the asymmetry — one lane got the treatment, the other didn't — that marks it as unfinished rather than intentional.

useTerminalSession.ts — onTransportOpen resets and clears unconditionally
api/terminal_ws.go — full sub.Snapshot re-stream per connection
F7

Every keystroke arbitrates the size lease

Design smell
QualityPerformance

dispatchInputMessage opens the stdin case with HoldsLease() and, if false, AcquireLease() — which resizes the PTY to that viewer's declared grid and publishes to every client. That's two more mutex round trips per keypress on the hot path, plus two more for AcceptedThrough and AdvanceAcceptedThrough: five acquisitions of the contended session mutex to deliver one character.

Semantically it also means typing one letter on a phone silently reflows the desktop's terminal. That may be the intent, but it is a policy decision buried in the byte-delivery path rather than expressed anywhere a reader would look for it.

F8

useTerminalSession is doing eight jobs

Maintainability
MaintainabilityQuality

596 lines holding: the protocol switch, the prediction overlay, a latency EMA, echo-state gating, the scroll controller, the size lease, mouse mode, conversation acks, the debug probe, and direct useWorkspaceStore.getState() reads. The transport and stdin layers below it were extracted cleanly — this one wasn't, and it's where the layering stops.

Two concrete consequences. useStdinStream returns a fresh object literal every render, so the message-subscriber effect tears down and re-subscribes on every pane re-render. And the gate is built as useRef(createInputGate({…stdin.send})) — which reconstructs and discards a gate on every render, and permanently captures the first render's send. It works today only because those callbacks happen to have stable identity; the day one gains a dependency, the gate holds a stale closure and input dies silently, with no test that would notice.

The protocol switch is already a pure state machine over (message, state) → state + effects. Lifting it out of React would make the reconnect and multi-viewer cases testable without a fake socket and a fake terminal.

F9

A truncated snapshot drops its own documented prologue

Maturity
QualityReliability

Emulator.Snapshot() opens with \x1b[?1049l \x1bc \x1b[3J \x1b[H \x1b[0m and documents each byte as a defensive invariant — exit a stuck alt-buffer, full reset, clear scrollback, park the cursor. When boundSnapshot() trims an oversized snapshot it re-prepends a bare \x1bc and drops the other four. So the truncation path — the one that runs when state is largest and most likely to be wrong — is the path that discards the guards.

It's harmless today because the client happens to call reset() + clear() first. That's a coincidence, not a contract, and the prologue is duplicated as a literal in two files rather than shared as one constant.

api/terminal/snapshot.go — prologue with per-byte rationale
api/terminal_ws.go — boundSnapshot() re-prepends only \x1bc
F10

The tests verify parts, and the failures live between them

Maturity
MaturityReliability

Coverage is genuinely good per unit — useStdinStream, useTerminalTransport, tmuxPTY payload sizing, a real measured ceiling test for send-keys, and greenfield assertions that fail CI if a forbidden shape reappears. That's a mature instinct.

But every finding above lives at a seam: client offset space vs. server offset space, echo probe vs. mutex, control lane vs. stdin lane, snapshot prologue vs. truncation. The suite has no test that runs two clients against one session, and none that reconnects with a non-zero accepted_through. Those two fixtures would have caught F1 outright.

06What I'd change, structurally

Ordered by leverage. Each of these deletes a class of bug rather than an instance — the first two together account for most of what's listed above.

LEVER 01

Give the offset space one owner: the connection

Stop treating acceptedThrough as a session fact. At Subscribe, snapshot it as that connection's base and hand the client a base of zero; the client's offsets are then connection-relative and correct by construction, for one viewer or five. Session-wide ordering is the session's job — it already has a serialization point — not the offset's.

Then make unreconcilable recoverable: clear it on reconnect, and surface it in the pane instead of silently queueing forever. A lane that can enter a permanent silent-failure state with no operator-visible signal is the actual defect; the offset mismatch is just what triggers it.

Closes F1 · unblocks multi-viewer

LEVER 02

One long-lived tmux control channel, not a fork per operation

Every tmux interaction in pty_tmux.go spawns a process. tmux -C (control mode) gives you a single persistent client you write commands into and read tagged responses out of — the same operations, without the spawn, and with a real place to serialize them.

That single change removes the per-keystroke fork pair, the per-frame probe pair, and the 5-second-timeout blast radius at once, and it turns "did the tmux command succeed" into a channel read instead of a process exit code.

Closes F2 · defuses F3, F5

LEVER 03

Take echo state off the output path entirely

Derive in_alt_buffer and cursor_at_line_end from the emulator, which already knows them for free. Sample the termios ECHO bit on its own cadence — or only while a client has prediction enabled — and push echo_state on change, not per frame.

Non-negotiable either way: never hold s.mu across a call that can exec, block, or time out.

Closes F2 at the design level

LEVER 04

Split the session mutex; make input asynchronous

Two locks, not one: emulator + snapshot cache under one, client registry + lease + presence under another. Neither is ever held across I/O. That alone stops a new viewer's snapshot from stalling the read loop.

Then give the session one ordered input queue that both stdin and control feed. The WS read loop enqueues and returns immediately; a single writer drains it and emits the ack. Input ordering becomes a property of the queue instead of an accident of two transports, and the read loop stops being hostage to backend latency.

Closes F3, F4, F5, F7

LEVER 05

Make output resumable, like input already is

Keep a monotonic byte cursor on the broadcast stream alongside a bounded ring. A reconnecting client sends the last cursor it rendered; if it's still in the ring, replay the delta and skip the reset entirely. Fall back to the full snapshot only when it isn't.

The reliability vocabulary for this already exists on the input side — this is applying it to the lane that carries a thousand times more bytes.

Closes F6 · biggest mobile win

LEVER 06

Lift the protocol out of React

The message switch in useTerminalSession is a pure reducer wearing a hook. Extract it as (state, message) → [state, effects], leave the hook to bind effects to xterm and the store, and move prediction, scroll, lease, mouse mode and speech into siblings.

The payoff is the test fixtures you can't write today: two clients on one session, a reconnect at a non-zero offset, an ack arriving after unmount — none of which need a DOM.

Closes F8 · makes F10 fixable

07Confidence, and what I didn't do

This is a static trace of the current working tree plus one measurement. To be precise about which is which:

  • Measured. The tmux and stty timings in §04 — 100 iterations each against a scratch tmux socket I created and killed. Idle host, no other load. Real-world numbers under a busy tmux server will be worse, not better.
  • Traced, not executed. F1's failure path. I followed acceptedThrough from session_ready through reconcile() to the unreconcilable latch and confirmed nothing clears it, but I did not reproduce it in a browser. Confirming it takes about thirty seconds: open a pane, type anything, reload the page, type again.
  • Not examined. bridge_pty.go and the remote-session path, session recovery after an API restart, and the conversation/TTS surfaces that share this WebSocket. Any of those could hold findings of their own.

One framing note, since you asked for structure over symptoms. Every finding here is the same shape: a correct component composed against a component with a different notion of scope. Client-mount scope against session scope. Frame cadence against process-spawn cost. Two transports against one ordering assumption. That's why the individual code reads so well and the system still misbehaves — and it's why the fixes above are all about relocating an authority rather than patching a call site.
