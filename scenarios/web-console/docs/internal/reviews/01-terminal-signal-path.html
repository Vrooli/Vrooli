MAP

Two lanes, three shared chokepoints

Output and input are separate pipelines with separate failure modes, but they meet at three places. Every compounding bug in this subsystem is a chokepoint problem: something slow in the output lane starves the input lane, and the input lane's recovery logic then does damage.

The compounding chain

A slow or backgrounded browser tab stops draining its WebSocket. ② writeMu is held by the output forwarder with no write deadline set anywhere in the server, so stdin_ack cannot be written. The client's 2 s ack timer fires, declares the keystroke lost, and re-queues it — even though the server already wrote those bytes to the shell. The re-queued payload then waits for the next reconnect before it is sent, because the queue's only drain trigger is session_ready. The user sees characters vanish, then a burst of duplicated, out-of-order input minutes later.

CORE

The queue with no scheduler

This is the single most consequential structure in the input path. Five conditions push payloads into the pending queue. One event drains it — session_ready, which only fires when a WebSocket connects. None of the five filling conditions causes a reconnect, so none of them causes a drain.

FINDINGS

What is structurally wrong

Ordered by how much downstream behaviour each one explains. Severity is about blast radius, not effort.

criticalcorrectness

At-least-once retry on a stream that is not idempotent

Each keystroke is treated as an independently retryable datagram: its own sequence number, its own 2 s timer, automatic re-send on timeout or close. Terminal input is an ordered byte stream where re-delivery means re-execution. A retried payload is also appended to the tail of the queue, so it arrives after everything typed since — retry corrupts order as well as content.

Their own docs say so“WebSocket stdin messages — PTY input is inherently non-idempotent (typing ls\n twice runs the command twice). No sequence tracking is implemented.” The reasoning in INVARIANTS.md is right; the code stopped matching it.

criticalreliability

No write deadline anywhere on the WebSocket

SetWriteDeadline appears in no non-test file in api/. Only the keepalive WriteControl ping carries a 5 s bound; every WriteJSON can block indefinitely while holding writeMu. One stalled peer wedges the output forwarder, the ack path, and therefore the input loop — the server has no mechanism to notice or shed it.

Why it matters hereThis is the mechanism that converts a slow client into duplicated shell commands, by starving stdin_ack past the client's 2 s budget.

criticalmaintainability

One client protocol, two independent server implementations

remote_terminal.go reimplements the browser-facing protocol for bridged targets and has already drifted: no control frames (mouse and touch scroll are dead), no take_lease (the client's in-flight flag latches on), no snapshot replay (it writes history_end immediately, so reconnect shows an empty screen despite a comment promising the scrollback contract), no intent, no keepalive ping, no read deadline, an unbounded pending map, and a "close" message type the TypeScript union cannot express.

criticalperformance

Two subprocess spawns per typed character

On the persistent backend, deliverTyping runs tmux display-message to probe #{pane_in_mode}, then tmux send-keys. Both are fresh exec.Command invocations with a full client handshake over the tmux socket. Steady typing at 10 cps is 20 process spawns per second per pane, each on the latency path of an acked round trip. Momentum scroll is worse: one WebSocket frame and one raw write per line, per animation frame, unbatched.

Why it was built this wayCorrect, and well argued — send-keys -l alone does not escape copy-mode. The mechanism is right; paying for it per character is the problem.

Local echo can predict but cannot retract

On a mismatch the controller drops its predictions and passes the server bytes through unchanged. The comment says it “trusts xterm.js to repaint from scrollback” — xterm.js does no such thing; nothing repaints. Characters echoed on a wrong prediction stay on screen.

Concrete caseAt a sudo or SSH password prompt the shell echoes nothing, so every typed character is predicted, drawn, and never withdrawn. The password renders in cleartext until the line scrolls away. There is no echo-state awareness (termios ECHO) and no visual marking of unconfirmed text.

The client sanitizer is stateless across read boundaries

A \x1b[?2026h that straddles two reads is not matched, reaches xterm.js v6, and kills that terminal's parser — the documented failure is a permanently blank pane. UTF-8 splitting is buffered across reads; escape sequences are not.

Available leverA correct stateful scanner already exists one line above: the emulator parses this same stream. The client-bound copy is the only consumer doing byte matching by hand.

majorperformance

Full scrollback replay blocks stdin on every connect

Every WebSocket open re-serializes up to 10 000 scrollback lines with SGR into one ANSI snapshot and streams it in 64 KiB frames — routinely megabytes. The forwarder takes writeMu once for the whole loop, and session_ready waits on that lock, so the user cannot type until the entire replay has flushed. With no write deadline and no cap on snapshot bytes, a mobile reconnect on a weak link can hang input for as long as the link takes.

Missing primitiveThere is no resume-from-offset. Reconnect is always a full replay, never a delta, even when the client already has the scrollback.

majorfidelity

UI status text is injected into the byte stream

[Reconnected], [Disconnected], [Session ended], the coalescing warning and error hints are written straight into xterm's buffer. The server's emulator — the declared source of truth — never sees those bytes. They corrupt alt-buffer TUIs mid-render, pollute selection and copy, shift the grid, and vanish on the next snapshot, so client and server disagree about screen contents by construction.

Cheapest structural fix on this pagePane chrome already exists for the pending-input pill and the input-rejected banner. Route status there and the in-band writes disappear entirely.

majorcorrectness

Unmount flattens the queue and loses intent

On unmount the pane concatenates every queued payload into a single string and stores it as a draft; on remount it is submitted as one bulk_text. Boundaries between payloads are gone, control bytes become pasted text, and the tmux paste path may bracket the result. Combined with the 64-entry cap dropping the oldest entries, the queue can silently reorder and mangle input it was built to protect.

MOVES

Structural changes, in dependency order

Each one removes a class of bug rather than an instance. The first two together retire most of what is listed above.

1

Make input a stream, not a queue of messages

Give the connection a single monotonic byte offset. The client appends to a send buffer and tracks what it has written; the server acknowledges a cumulative bytes-accepted offset, not per-payload sequence numbers. Retransmission happens once, on reconnect, from the acknowledged offset — never on a timer, never out of order. Delete the per-payload timers, the 64-entry cap, the tail re-enqueue, and the unmount flattening along with them.

retires: retry duplication · reordering · the stranded queue · intent loss on unmount · silent oldest-first truncation

2

Extract the wire protocol into one package with a conformance suite

Move TerminalMessage, the frame constants, and the reason codes out of package main into a versioned protocol package, and make both the local and bridged handlers satisfy one shared test suite: session_ready ordering, snapshot then history_end, control frames unacked, lease frames answered, unknown types ignored. Divergence becomes a failing test instead of a silently broken remote target.

retires: remote-target feature gaps · protocol/doc drift · unversioned contract

3

Put deadlines and bounds on every blocking edge

Write deadlines on all WriteJSON calls; a bound on snapshot bytes with the oldest scrollback dropped rather than an unbounded replay; timeouts on the tmux subprocess calls. A peer that cannot keep up should be disconnected with a typed reason, not allowed to wedge a shared mutex.

retires: half-open wedges · ack starvation · unbounded connect-time input block

4

Hold a persistent tmux control-mode client per session

Replace the per-keystroke display-message + send-keys spawn pair with one long-lived tmux -C connection, tracking pane mode from its event stream instead of probing for it. Coalesce onData in a short window client-side so a fast typist produces frames, not one frame per character, and batch wheel events into a single control payload.

retires: fork storm on typing · scroll frame flood · a large share of input latency

5

Decide what local echo is for, then commit

It is currently a half-implementation: it predicts but cannot retract, and it draws characters that may only have been queued. Either delete it — the round trip is sub-millisecond on a local socket and the queue-aware failure modes go with it — or implement it properly: track echo state, render predictions in a distinct style, and erase on mismatch. The password-prompt case makes the middle ground untenable.

retires: stuck phantom characters · cleartext at non-echoing prompts

6

Split the session lock and move status out of the stream

Separate the emulator/client-set mutex from the PTY handle so writes never wait on parsing. Move [Reconnected] and its siblings into pane chrome so the terminal buffer contains only bytes the server's emulator also saw. Both are small, self-contained, and restore an invariant the architecture already claims.

retires: typing stalls under heavy output · client/server screen divergence

NOTE

What is already right

Worth being explicit, because the findings list is long and the baseline is not weak. The server-authoritative emulator with snapshot replay is the correct architecture and most web terminals do not have it. The intent vocabulary, the mode-cancel reasoning behind send-keys -X cancel, the separation of the argv ceiling from paste semantics, the size-lease model for multi-viewer panes, the UTF-8 boundary buffering, the tmux re-attach backoff, and the decision to route synthetic control bytes outside the reliable lane are all things someone thought hard about and wrote down. The failures above are what happens when a well-reasoned design accumulates a second delivery mechanism, a second server implementation, and a recovery layer whose assumptions nothing re-checks.
