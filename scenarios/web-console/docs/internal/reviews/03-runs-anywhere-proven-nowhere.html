Runs Anywhere, Proven Nowhere

web-console cross-compiles cleanly for macOS and Windows today — I verified both this session. What it does not have is a single machine-readable statement of what actually works on those platforms, and the one place the answer is written down in prose is already out of date. The portability problem here is not missing code. It is missing declaration, and a handful of host assumptions that fail loudly on the machine you didn't test on.

GAP

The repo has a portability ladder. web-console is not on it.

internal/deployability defines a closed vocabulary for what a scenario claims per operating system, plus a qualification ranking over those claims. The point of the ladder is that “we think it works” and “we ran it” are different rungs and must not be written the same way.

supportedRuns, measured on real hardware.
build-verifiedCross-compiles and passes fixtures; never run on that platform. Where web-console honestly sits for macOS.
experimentalWired, behaviour unproven.
partialRuns with known functional limits.
unsupportedDeliberately out of scope. The honest answer for Windows today.
undeclaredNothing authored, so nothing proven — and the loader synthesizes unsupported. Where web-console is now.

The scenario's actual portability record is a single sentence inside a notes string on the tmux host-tool declaration — a field no resolver reads:

scenarios/web-console/.vrooli/service.json → hostTools[0].notes
"Platform support: Linux is supported (measured on the current host);
 macOS is reasoned from source and runs without live session
 working-directory inspection, so relative file preview reports an error;
 Windows is reasoned from source and unsupported because no PTY
 implementation exists."
And the highlighted clause is already wrong

packages/platform-go/process_darwin.go implements processWorkingDir via lsof -a -p <pid> -d cwd -Fn. macOS does have live working-directory inspection, and has for some time. On the tmux backend it was never needed anyway — CurrentDir asks tmux for #{pane_current_path}, which is portable. This is the failure mode of prose declarations in one line: the code moved, the sentence did not, and nothing could have caught it.

DEFECTS

Host assumptions that will bite on an untested machine

criticalall platforms

Config load panics on a machine-specific env var

resolveShellChecked is written correctly — it returns a typed ErrShellUnavailable. Its caller resolveShell() throws that away and panics, and it is invoked from the config-defaults constructor. Any host where $SHELL names a binary that is not on PATH kills the API at startup with a stack trace instead of a diagnosis.

The Windows case in particularGit Bash and MSYS set SHELL=/usr/bin/bash — a POSIX path exec.LookPath cannot resolve on Windows. So the carefully-written powershell.exe branch is reached only when SHELL is unset, which is precisely when Git Bash is not installed. On a developer Windows box the likely outcome is a panic, not a fallback.

criticallinux · macos

The tmux capability probe runs against the wrong tmux server

Every tmux operation in the scenario goes through tmuxCmd(), which prepends -L wc to pin the dedicated socket — the comment calls this mandatory. The availability probe does not use it. defaultCheckTmuxAvailable calls exec.Command(path, args...) directly, so it creates and kills a probe session on the user's default tmux server.

Three consequencesIt answers a question about a server the scenario never uses. It starts the user's tmux server as a side effect of web-console booting. And set-buffer -b vrooli-probe-buffer is never deleted — paste-buffer -p is called without -d — so it leaves a named buffer behind in the user's own tmux session.

criticalmacos

On macOS the tmux socket location depends on who started the process

tmux -L wc resolves the socket under the per-user temp directory. On Linux that is a stable /tmp/tmux-$UID. On macOS it is $TMPDIR, which differs between a login shell and a process started by launchd — the same user gets different, unrelated paths.

Failure modePersistent sessions survive the restart, and the API cannot see them. DiscoverTmuxSessions returns nothing, recovery finds nothing, and every pane the user left running is silently orphaned. TMPDIR is not pinned, and not in the serviceEnvVars filter list, so the socket path is inherited from whatever launched the API.

majorwindows

Zero available backends renders identically to one

The launcher computes showBackendSelector = backends.length > 1. On Windows the filtered list is empty, which takes the same branch as “exactly one backend, no choice needed”: the selector is hidden and the launcher looks normal. The user presses Launch and the failure surfaces from the API, without the reason string the backend registry already computed — "no PTY implementation for this platform".

The information existsEvery Descriptor carries Available and Reason, and the reason reaches the UI in session_backends. Nothing renders it. Honest degradation is a two-line change at the point where the list is empty.

majorall platforms

The terminal font stack contains no font that ships with any OS

'JetBrains Mono', 'Fira Code', 'Cascadia Code', monospace. None of the three named faces is present on a stock macOS, Windows or Linux install — they are developer installs. So most users land on the generic monospace keyword, which resolves to Courier on macOS and Consolas or Courier New on Windows.

Why this is a portability bug, not a taste issuexterm.js derives cell width from the resolved font. A different fallback per OS means a different cell size, which means a different computed grid for the same window dimensions — and the PTY is then sized differently on each machine. With the size-lease feature, two viewers on different operating systems disagree about the grid for the same session by construction.

majorlinux · macos

Every persistent session is born in mouse-tracking mode

applyTmuxOptions sets mouse on unconditionally on session creation. That is the exact condition that routes scrolling down the remote, round-trip-bound path documented in the previous review — so the network-dependent scroll velocity is not an edge case triggered by a TUI, it is the default state of every tmux-backed pane on every platform.

Cross-platform angletmux mouse behaviour and copy-mode entry differ across tmux builds, and macOS commonly runs a different tmux minor version than the Linux host this was tuned on. Making mouse mode a deliberate, surfaced setting removes both the performance coupling and a source of per-machine divergence.

Three scrollback depths for one scrollback

tmux keeps history-limit 50000, the server emulator keeps 10 000 lines, and xterm.js keeps 10 000. A user scrolling a tmux-backed pane can reach content the emulator no longer holds, so what survives a reconnect depends on which layer answered — and the reachable depth differs by backend.

hygieneall platforms

The probe forks tmux before it consults its own cache

defaultCheckTmuxAvailable keys its cache on the version string, which it obtains by running tmux -V — so the cache never avoids a fork, only the six probe commands. Minor on Linux; on a machine where process creation is expensive (Windows, constrained containers) the pattern is worth inverting.

MODEL

The patterns already here that should be generalized

This scenario has better portability instincts than most. Three of these are genuinely the right answer and should be named as the house pattern rather than left as local cleverness.

Capability probing, not version parsingThe tmux probe actually executes -e, resize-window -x -y, paste-buffer -p, send-keys -X cancel, #{pane_in_mode} and #{pane_dead_status}, and reports which one failed. That is strictly better than comparing a version string, and it is the single most portable thing in the codebase. Fix its socket and make it the template.
Gated privilege with a real fallbacksystemdRunUsable() checks GOOS and LookPath, logs the result once, and falls through to plain new-session. Linux gets cgroup isolation; nobody else pays for it or fails because of it.
Per-OS files with an explicit unsupportedplatform-go splits process_linux / process_darwin / process_windows and returns a typed ErrUnsupported rather than a zero value. Absence is a fact, not a failure — the comment says so, and the code means it.
Clipboard as a capability boundarylib/clipboard.ts declares one seam, tries the async Clipboard API, falls back to the gesture-bound execCommand path, and returns typed unsupported/denied/failed. Exactly the shape every browser-capability difference should take.
Windows-aware shell defaultsresolveShellChecked already branches on GOOS, uses LookPath, and absolutizes the result. The logic is right; only the panicking wrapper above it is wrong.
Optional host tools, declaredtmux is required: false with a stated reason and a documented fallback. The scenario boots without it.
MOVES

Getting to portable-and-provable

1

Author the platform_capabilities block and delete the prose

Use the matrix above as the starting content. One entry per capability, three OS keys each, with status, mechanism and evidence — following the shape system-monitor already uses. Then remove the platform sentence from the tmux notes field so there is exactly one record, and it is the one tooling reads. This is the change that converts every other item here from folklore into something CI can regress.

retires: stale prose · undeclared-means-unsupported · “does it work on a Mac?” being a conversation instead of a query

2

Probe the socket you will actually use

Route defaultCheckTmuxAvailable through tmuxCmd() so the probe targets -L wc, and add -d to the probe's paste-buffer so it leaves nothing behind. Then pin the socket explicitly with -S <scenario-state-dir>/tmux.sock instead of -L, which removes the $TMPDIR dependency and makes the macOS launchd-vs-login-shell divergence structurally impossible rather than merely unlikely.

retires: probing the wrong server · buffer leak into the user's tmux · silent session orphaning on macOS

3

Never panic on host state

Make resolveShell return its error to the caller and let config load report a typed startup failure — or degrade to a probed default. A host whose $SHELL is unusable is a supportable condition with a clear message, not a crash. Audit for the same shape elsewhere: any panic reachable from reading the environment, the filesystem, or PATH is a portability bug wearing a different hat.

retires: startup crashes on Git Bash, minimal containers, and service-manager environments

4

Make degradation legible from capability to pixel

The backend registry already computes Available and a human Reason, and ships both to the client. Render them: when the filtered backend list is empty, show the reason instead of a launcher that looks ready. Same rule for any capability the matrix marks unsupported — the user should learn it from the UI, not from a failed launch.

retires: Windows users discovering the platform matrix by trial

5

Give the font stack an OS ladder, then assert cell metrics

Append real system fallbacks — ui-monospace, SFMono-Regular, Menlo for macOS, Consolas for Windows, 'DejaVu Sans Mono', 'Liberation Mono' for Linux — so every platform lands on a designed monospace instead of Courier. Better still, ship one webfont with the app so cell geometry is identical everywhere, and add a test that asserts a known grid for a known pixel size.

retires: per-OS grid divergence · cross-platform size-lease disagreement

6

Climb the ladder with evidence, not edits

make check already runs cross-compile, which is what keeps build-verified honest. To reach supported on macOS you need something a cross-build cannot give: run the Go unit suites under darwin, then a scripted manual pass on real hardware covering session create, detach, restart, recover, resize, paste and scroll. Record the result as the evidence string on the capability entry. A status that changes without its evidence changing is the thing the ladder exists to prevent.

retires: status drift · “supported” meaning “nobody has complained yet”

SCOPE

One decision to make first

Windows is the fork in the road. Today it is honestly unsupported: no PTY, no tmux, no backend. Making it work means wiring ConPTY behind the hostSupportsPTY build tag and accepting that persistence has no tmux equivalent — a real project, not a fix. The alternative is to declare unsupported in the capability block and render that in the launcher, which is a day of work and leaves nobody confused. Both are defensible; drifting between them is not. Everything else in this review points the same way on all three platforms, so pick the Windows answer and the rest of the matrix stops being ambiguous.
