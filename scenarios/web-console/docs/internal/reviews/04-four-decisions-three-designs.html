Four Decisions, Three Designs

Four calls are now made. Three of them need a design before anyone writes code, and one of those — remote terminals — has a much better answer than the one I proposed, because the mechanism you were reaching for already exists in this scenario and is being used for exactly one thing. The three follow-up questions are closed too; two of them turned out to be answerable from the code rather than by judgement, and one of those answers retires a workaround.

DESIGN 1

Remote terminals

You were right that the integrations concept is the missing piece, and it is further along than you thought. packages/capability-registry-go already models everything this needs — and web-console's catalogue currently contains exactly one entry.

Two independent moves that happen to fit together Status and lifecycle belong in the capability registry. The transport belongs behind the PTY interface. Neither needs a bespoke mechanism.

Part A — vrooli-bridge becomes a declared capability

The Def struct already carries dependency kind and slug, an action kind, an action label, an operator command, a feature list, and a platform verdict. ScenarioChecker is generic. IntegrationsPanel already renders status, message and a start/restart button. The catalogue is one entry long:

That alone un-gates it. The remote target stops being conditional on WEB_CONSOLE_BRIDGE_URL being set: the target always exists, and its status comes from the registry the same way audio-tools' does. And it retires a whole parallel vocabulary: remoteTerminalTarget now projects the shared capability result rather than duplicating its status, reason, action and readiness strings. Implement ResultChecker for the bridge and those duplicate fields disappear.

Part B — the thesis

Do not build a second WebSocket handler that reaches parity with the first. Make the bridge a pty.PTY implementation. A bridged session already gives you every method on that interface: data frames are Read, stdin is WriteInput, resize is SetSize, close is Close, the ack stream gives ExitCode and ProbeReady. Register it as a third backend beside Standard and Persistent, and a remote session becomes an ordinary Session.

Everything remote is missing then arrives for free, because it was never remote-specific — it belonged to Session and the WS handler all along:

Snapshot replay on reconnect, from the same terminal.Emulator Control frames — so scroll and mouse work Size lease and multi-viewer presence Coalescing, trim and resync Keepalive pings and read deadlines Intent-aware delivery The byte-offset stdin protocol, once The GetScreen / WaitIdle RPCs for agents

And remote_terminal.go's 160-line WebSocket handler is deleted rather than fixed. The registry, catalogue and Bridge credential handling stay; the duplicated protocol goes.

1

Extract the protocol package first

Move TerminalMessage, the frame constants and the reason codes into a versioned package with one conformance suite. This is on the critical path for the byte-offset decision anyway, and it is what makes step 3 safe.

2

Declare the capability and wire the checker

One Def, one ScenarioChecker, and a ResultChecker that maps bridge readiness onto CheckResult. Remove the env-gate from target construction.

3

Implement bridgePTY and register it as a backend

The frame translation that lives in the WS handler today moves behind Read/WriteInput. Bridge sequence numbers stay internal to the PTY; they are no longer part of the browser protocol.

The bridge's own durable data sequence maps cleanly to the cumulative offset model — it is already an offset, which is why these two decisions compose rather than conflict.

4

Delete the parallel handler

The parallel remote terminal handler, the remote: prefix branch in handleTerminalWS, the pending map and the unreachable "close" message type all go.

One caveat, stated plainly. A remote session running through Session means web-console holds an emulator and 10 000 lines of scrollback per remote pane, in web-console's memory rather than the node's. That is the right trade — it is what makes replay identical everywhere — but it is a real memory cost per remote session and should be measured before you scale the node count.

DESIGN 2

Predictive echo, done properly

You chose the hard option, so here is what it actually requires. The current implementation has three defects and only one of them is the alt-buffer gate.

Four properties the rebuild must have Miss any one and it degrades back into the current behaviour under load.
1

Predictions render in an overlay, never into the buffer

The root defect is not the matching logic — it is that a prediction is a terminal.write(), which mutates authoritative state that only the server is supposed to own. Once written it cannot be retracted without emitting more bytes. Predictions must live in a layer that can be cleared without touching terminal state: xterm's decoration/marker API over the cursor cell, or an absolutely-positioned layer above the screen element.

This single change is what makes retraction possible and removes the client/server divergence.

2

The server tells the client when prediction is valid

The browser cannot read termios. The server can — it holds the fd for the standard backend, and tmux can report pane state for the persistent one. Add an echo-state signal to the wire protocol so prediction is enabled by an authoritative fact rather than inferred from buffer.active === buffer.alternate once, at connect time. Predict only when: echo is on, the pane is in the normal buffer, the cursor sits at the end of the line, and no resize is in flight.

This is also the honest fix for the password-prompt leak — at a non-echoing prompt the server says “do not predict”, and nothing is ever drawn.

3

Confirmation is keyed to the byte offset

Each prediction records the send offset that produced it. When the server confirms bytes through that offset and the emulator's cursor lands where predicted, the prediction retires. Anything else — mismatch, timeout, resize, reconnect — clears the whole overlay. This is why the byte-offset stream has to land first: it is the confirmation mechanism, and building echo on the current per-payload acks would just inherit their ambiguity.

4

Unconfirmed text looks unconfirmed

Render predictions underlined or dimmed, the way mosh does. It costs nothing, it makes a wrong prediction self-evident rather than mysterious, and it means the user is never misled about what the shell has actually received. Tie the styling to a threshold so it only appears once round-trip latency is high enough for prediction to be earning its keep — on a local socket predictions confirm within a frame and should be invisible.

Interim position

The rebuild depends on the offset protocol, which depends on the protocol package. That is a multi-week chain, and the corruption you are hitting in Claude Code is happening now. Ship the buffer.onBufferChange subscription and a hard-reset-on-mismatch as a stopgap in the meantime — hours of work, fixes the reported symptom, and every line of it is deleted when the real subsystem lands. Do not let the stopgap become the plan.

DESIGN 3

Windows, declared and rendered

RESOLVED

The three follow-ups, closed

Two were empirical and did not need a judgement call. The third was a genuine ownership question.

1 — The xterm.js crash the sanitizer guards against is not in the code you ship Verdict: restore synchronized output, then verify the mobile case.

I read requestMode in the installed v6.0.0 source and then in lib/xterm.js, the bundle that actually runs. Every identifier is declared, there is no stray r, and mode 2026 is handled explicitly — as are the DECSET/DECRST toggles:

src/common/InputHandler.ts:2303
if (p === 2026) return f(p, b2v(dm.synchronizedOutput));

lib/xterm.js — the shipped bundle, minified
2026===_?u(i.synchronizedOutput):0,o.triggerDataEvent(`${n.C0.ES…
2026:this._coreService.decPrivateModes.synchronizedOutput=!0}ret
2026:this._coreService.decPrivateModes.synchronizedOutput=!1,thi

So the primary rationale in sanitize.go is obsolete, and the server is currently telling every TUI that a capability the terminal genuinely has is “not recognized”. Two layers of workaround come out: the $p query strip, and the fake \x1b[?2026;0$y reply in ansiReplyFor.

The second rationale is untested, not disproven. The comment also cites mobile-browser timer throttling stranding a framed block until the next DECRST. That risk is about xterm's own sync implementation under throttling, and it only ever arose because the server stopped TUIs emitting toggles in the first place. Restore, then background a mobile tab mid-repaint and watch for a stuck frame. Re-add a mitigation only if it reproduces — and if it does, mitigate inside the renderer rather than by lying about the capability.

Retires one of the four causes of agent-TUI corruption identified in Scroll, Zoom, Redraw, and it is independent of every other phase.

2 — ollama and openrouter were always meant to be integrations Verdict: author the missing Defs. The UI test already assumes they exist.

The code does not say what was intended, but the test does. integrations-panel.test.tsx builds capability fixtures for audio-tools, ollama, openrouter and kokoro-tts, and asserts that cap-card-ollama and cap-card-openrouter render. It passes — because it feeds the panel its own fixtures rather than the real catalogue.

The same pattern as the font stepper

A green test proving the mechanism works, next to production wiring that never supplies it. The panel can render these integrations; capabilities.Known just never lists them. Add the Defs — ollama and openrouter already have working checkers registered in main.go. kokoro-tts appears in the fixture with neither a Def nor a checker, so decide whether it is real before adding it.

Then make the panel test read the real catalogue for at least one case, so “declared” and “renderable” stop being independently true.

3 — Node onboarding stays with vrooli-bridge Verdict: web-console consumes the registry only. Pairing remains a bridge CLI operation.

vrooli-bridge owns a full PairingService — issue and redeem pairing codes, request and approve pairing, register encryption keys — plus a ProvisionService for revision sync. It has api, cli, agent and bootstrap, and no ui directory, so the onboarding ceremony has no browser surface anywhere today.

Phase 3 therefore reads ListNodes and GetNodeReadiness to populate targets and status, and does not grow a pairing flow. Un-gating remote terminals never required one: a node that has been paired via the CLI shows up as a target with live status and a restart action, which is the whole of what was missing.

Deliberately deferred, not forgotten: a browser pairing surface belongs in vrooli-bridge alongside the protocol it implements. web-console should deep-link to it when it exists rather than absorb another scenario's domain.
