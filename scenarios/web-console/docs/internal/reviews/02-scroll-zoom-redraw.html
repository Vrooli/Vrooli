Scroll, Zoom, Redraw

Three reported symptoms, traced to source — plus a consolidation inventory for the terminal subsystem. All three turn out to be the same shape of bug: one user-facing behaviour implemented two or three times, in different layers, with no shared authority between them.

SCROLL

Scrolling is three implementations wearing one gesture

Reported“Scrolling velocity changes based on connection speed. Touch scrolling and trackpad/mouse scrolling are very different speeds and there is no way to adjust them.”

Both halves are accurate, and they have the same cause. Whether scrolling is a local operation or a network operation depends on whether the foreground program has mouse tracking on — and which of the two network paths you get depends on whether you used a finger or a wheel.

Any device · mouse tracking OFF
touch: scrollTerminal() · wheel: xterm native term.scrollLines(n) renders immediately
Local. Instant. Network-independent.
Touch · mouse tracking ON
sendControl() — one frame per line, per rAF tick WS control frame · unacked, best-effort ptmx.Write → tmux client app redraws → output → render
Remote. Round-trip bound. Dropped silently above 1 MiB buffered.
Wheel / trackpad · mouse tracking ON
xterm CoreMouseService → SGR report triggerDataEvent → onData submitInput(data, "typing") — the reliable acked lane seq + 2 s ack timer + retry-on-timeout tmux: display-message + send-keys -l
Remote, acked, retried, and delivered to the wrong recipient.

The wheel path lost its routing guard

xterm emits SGR mouse reports through onData, the same event as keystrokes. useTerminalSession forwards everything from onData as intent: "typing". Only useTerminalTouch was taught to use the control lane; the wheel path was never updated. On the tmux backend the mouse report is then handed to send-keys -l, which delivers it to the pane's program instead of the tmux client — precisely the failure the codebase used to guard against.

The guard's doc comment is still in the tree, describing a function that no longer exists: pty_tmux.go:151 — “Routing these via send-keys would deliver them to the pane's shell, which does not understand them, and mobile scroll would silently break.” The comment survived the refactor; the enforcement did not.

Momentum decays per frame, not per unit time

startMomentum multiplies velocity by TOUCH_SCROLL_DECEL = 0.95 once per requestAnimationFrame, and converts to lines with a fixed ×16 ms assumption in onTouchMove. On a 120 Hz phone the loop runs twice as often, so one flick travels roughly twice as far and takes half as long to stop as the same flick on a 60 Hz display. Nothing in the loop reads elapsed time.

useTerminalTouch.ts — startMomentum, onTouchMove velocity calc · consts/config.ts:152

Velocity is generated open-loop while rendering is closed-loop

In mouse-tracking mode the momentum animation keeps emitting wheel events at frame rate regardless of whether any of them have been rendered yet. The visible scroll only advances when the app processes the event and its redraw comes back. On a fast link the two rates roughly match; on a slow one the client races ahead, the frames pile up in bufferedAmount, and past 1 MiB sendJson starts returning false — which sendControl ignores, so the events are dropped without a trace. That is the connection-speed dependence, exactly.

useTerminalTouch.ts:234 (per-line send loop) · useTerminalTransport.ts WS_SEND_HIGH_WATER · useTerminalSession.ts sendControl discards the boolean

There is no sensitivity control at any layer

xterm exposes scrollSensitivity, fastScrollSensitivity and smoothScrollDuration; none is set, so wheel scrolling runs on library defaults. Touch scrolling divides pixel delta by measured cell height with its own compile-time constants. The two calibrations were never compared to each other, and neither is reachable from settings.

TerminalPane.tsx:618 (Terminal options) · consts/config.ts:135–155

What to build
  • One scroll seam. A single scrollBy(lines, source) owned by the session layer. It decides local-vs-remote once, and both touch and wheel call it. Detect mouse-tracking byte sequences in onData and divert them to the control lane there, so the routing rule lives in one place instead of being re-derived per input device.
  • Batch and rate-limit remote scroll. Accumulate wheel deltas over a frame and emit one control payload carrying the repeat count, capped to a sane events-per-second. Never one WebSocket frame per line.
  • Close the loop. Stop generating momentum events while frames are unacknowledged or bufferedAmount is elevated — decay to zero instead of queueing into a link that cannot keep up.
  • Time-normalize momentum. Decay as v *= DECEL ** (dt / 16) so a flick behaves the same at 60 Hz and 120 Hz.
  • Ship sensitivity settings. Independent multipliers for touch and wheel, since they are physically different gestures, persisted per device alongside font size.
ZOOM

Font size has three sources of truth; the stepper reads one and writes another

Reported“You can change the terminal text size in the customization dialog, but the plus/minus buttons are broken, and it'd be convenient if there was proper pinch-to-zoom.”

The stepper is a correctly written controlled component. It is wired to two different pieces of state.

// TerminalPane.tsx:211 — what the terminal actually renders
paneFontSize = deviceFontSize[sessionId] ?? pane.fontSize ?? 14

// AppearanceModal.tsx:69 — what the stepper displays
currentFontSize = pane.fontSize ?? 14

// AppearanceModal.tsx:206 — what the stepper writes
<FontSizeStepper currentSize={currentFontSize}
                 onChangeSize={(size) => setDeviceFontSize(sessionId, size)} />

// FontSizeStepper.tsx:48 — the button
onClick={() => onChangeSize(currentSize + 1)}

So the first click works and every click after it does nothing:

click +  onChangeSize(14 + 1) → deviceFontSize = 15  terminal grows to 15
         currentSize still reads pane.fontSize    display still says 14
click +  onChangeSize(14 + 1) → deviceFontSize = 15  identical value, no change
click −  onChangeSize(14 − 1) → deviceFontSize = 13  jumps 15 → 13

Three stores, one setting

pane.fontSize, deviceFontSize[sessionId] and defaultFontSize all describe terminal text size. The render path prefers the device override, so whichever writer runs last is not necessarily the one that wins. “Reset to defaults” has the same defect from the other direction: it calls setPaneFontSize, which the device override then shadows — so once the stepper has been touched, reset is visually inert.

AppearanceModal.tsx:119 · stores/useWorkspaceStore.ts:404–413 · TerminalPane.tsx:211

“Apply to other panes” propagates the stale value

buildPayload() sends font_size: currentFontSize — the pane value the stepper never updates. Applying appearance to open panes therefore pushes the size the user started with, not the one they just chose.

AppearanceModal.tsx:89

The test asserts the call, not the outcome

appearance-modal.test.tsx:304 checks that setPaneFontSize was called with ("sess-1", 14). It passes. Nothing asserts that the displayed value moved, that a second click changes anything, or that the terminal's effective size followed. This is why a visibly broken control has green coverage.

Pinch is not partially implemented — it is entirely absent

onTouchStart returns immediately unless e.touches.length === 1, and the effect sets touchAction: "none" on the xterm screen, which also suppresses the browser's native pinch. So two-finger gestures reach nothing today. Adding it is a new gesture state, not a tweak — and it must write to the same single authority the stepper writes to, or it will reproduce this same bug in a second place.

useTerminalTouch.ts onTouchStart · screenEl.style.touchAction

What to build
  • Collapse to one authority. Pick deviceFontSize as the per-device effective value with pane.fontSize as the synced/shared default, and expose a single selector — useEffectiveFontSize(sessionId) — that every reader and the stepper both use. Delete the third path or make it explicitly “the default for new panes”.
  • Use the constant that already exists. FONT_SIZE_STEP is defined in fontSizeUtils.ts and referenced nowhere; the stepper hardcodes ± 1.
  • Pinch as a real gesture state. Track two touch points, compute scale from initial-to-current distance ratio, map to font delta with a dead zone (ignore scale within roughly ±3 %) so a two-finger scroll does not resize, clamp through clampFontSize, and commit on gesture end — every font change triggers a fit() and a resize frame, so a per-frame commit means a resize storm to the PTY.
  • Fix the test to assert effect. Two clicks should produce two different displayed values and two different effective sizes.
Also worth knowing

The font-size effect at TerminalPane.tsx:713 begins with if (followerFrame) return;. A pane that does not hold the size lease ignores font changes entirely — the follower layout effect sets the size from the device frame instead. Whatever you build for zoom needs a defined answer for followers, or the control will look broken again on the second device.

REDRAW

Why agents corrupt and an empty shell does not

Reported“Typing in an empty terminal works perfectly, but the text and cursor position very often get wonky and broken in interactive terminals like Claude Code.”

That contrast is the diagnostic. Something in the path is correct for a shell that echoes exactly what you typed, and wrong for a program that repositions the cursor and repaints. There are four candidates and the first one explains the symptom precisely.

Predictive local echo stays switched on inside agent TUIs

Local echo is disabled only while the app is in the alternate screen buffer. That check runs once, on the history_end frame, and is never re-evaluated — nothing subscribes to xterm's buffer.onBufferChange. Agent CLIs like Claude Code render in the normal buffer, so the check reads “not alt” and predictions stay enabled for the life of the connection.

Then, on every printable keystroke, the controller writes the character at xterm's current cursor while the agent is independently moving that cursor to repaint its input box. The prediction never matches the server bytes, and the mismatch branch drops the predictions without erasing anything — the comment claims xterm repaints from scrollback, which it does not do. The phantom character stays, the column is now wrong, and the next repaint lands offset.

In bash the server echoes back exactly the character you typed, the prediction matches, it is consumed silently, and the whole mechanism is invisible. That is why an empty terminal is perfect.

useTerminalSession.ts:340–345 (one-shot alt check) · lib/localEcho.ts:104–121 (mismatch, no erase) · useTerminalSession.ts:417

Coalesce trim cuts the byte stream at an arbitrary offset

When a client falls behind, output is coalesced into a 1 MiB per-client buffer. On overflow the buffer is re-sliced from the tail — a cut at whatever byte offset the arithmetic lands on, routinely mid-escape-sequence and mid-UTF-8. The truncated remainder is then written straight into xterm, whose parser consumes the fragment as garbage and can be left in a wrong SGR or cursor state.

The designed recovery is a SIGWINCH to make the app redraw — and maybeSIGWINCHRecovery returns immediately on the persistent backend. So on tmux-backed sessions, a trim has no recovery path at all. Bursty agent output is exactly the traffic that triggers it.

session/broadcast.go:100–106 (trim) · session/broadcast.go:176 (persistent backend returns early)

Synchronized-output framing is stripped from the client stream

sanitizeForClient removes \x1b[?2026h / \x1b[?2026l, and the ANSI responder tells apps that mode 2026 is unsupported. That is a deliberate, documented workaround for an xterm.js v6 parser crash and for mobile timer throttling — but the consequence is that every atomic repaint an agent emits is rendered progressively instead. Partial frames become visible as tearing during redraw, which reads to a user as exactly the same “wonky” symptom.

session/sanitize.go · session/ansi_responder.go ansiReplyFor

One class of terminal query is answered by nobody

The client strips terminal replies from the input stream with /\x1b\[[\x30-\x3f]*[\x20-\x2f]*[cnRy]/ — which includes R, the cursor-position report, and n, device status. The server-side responder answers only c, q and p finals, and is skipped entirely on the persistent backend because tmux answers for its own panes. On the standard backend a program that asks “where is the cursor?” gets xterm's answer thrown away by the client and no substitute from the server.

useTerminalSession.ts:64 (RE_TERMINAL_RESPONSE) · session/ansi_responder.go (no n case) · session/ansi_responder.go:45 (skipped when persistent)

What to build
  • Fix the echo gate first. Cheapest change with the largest effect: subscribe to buffer.onBufferChange so the alt-buffer decision is live, and treat any unmatched prediction as a hard reset. Better still, given the password-prompt hazard from the first review — delete predictive echo and measure whether anyone notices.
  • Resync from the emulator instead of poking the app. The server holds a complete, correct screen. On a trim, send that client a fresh snapshot and let it reset() — deterministic, backend-independent, and it retires the SIGWINCH heuristic, its alt-buffer settle window, and its cooldown. The sync_warning banner becomes a resync notice instead of a warning that something may be wrong with no way to fix it.
  • Never cut a stream mid-sequence. If the buffer must be trimmed, trim to a parser-safe boundary — or drop the buffer entirely and resync, which is simpler and now cheap.
  • Make the query contract symmetrical. Whatever the client strips, the server must answer, on both backends. Today the strip list and the reply list were written independently and do not match.

REORG

Two reorganizations worth doing

1

Decompose TerminalPane along its actual seams

880 lines and a 20-method imperative handle, because it was the only place holding a Terminal instance. The seams are already visible in the file: xterm lifecycle + fit (init effect, scrollAwareFit, ResizeObserver, maybeSendResize), follower presentation (followerFrame, the layout effect, DeviceFrame), speech (ensureSpeechChunks, auto-TTS baseline, every tts* handle method), attachments (upload, drag-drop, paste-capture, file input) and selection UI (context menu, input-error banner). Each becomes a hook or a sibling component taking the terminal as a prop; the handle shrinks to input, focus and selection.

unblocks: testing any one concern in isolation · stops the next feature landing here by default

2

Stop re-rendering the pane on every resize frame

The ResizeObserver callback calls setPaneSize unconditionally on every tick — the requestAnimationFrame guard protects scrollAwareFit but not the state update. So a mobile keyboard animation or a drag-resize re-renders the entire pane subtree, TTS state and context menu included, once per frame. Move setPaneSize inside the rAF, and only set it when the value actually changed.

retires: resize jank that gets misread as terminal lag
