Before the symptoms: the three things you've fixed are visible in the code, and they're why this pass could go deeper than the last one. Typing works because send-keys -l plus the #{pane_in_mode} guard is genuinely the correct tmux delivery discipline. Scrolling and resizing work because the size lease gave the grid a single owner. Every symptom below sits next to one of those fixes rather than inside it — which is consistent: the components are right, the wiring between them is where things leak.

01The four outstanding symptoms

Each one traced to a specific line of code. Three are new findings; the first confirms what the last pass predicted.

S1

"That input was rejected" on every refresh

Confirmed F1

"When I load/refresh, I get an 'That input was rejected — it never reached the terminal' message. But I haven't inputted anything."

This is the offset-ledger split from the last pass, and your symptom is the proof I didn't have. Here is the exact path from page load to toast:

Mechanism
  1. Server sends session_ready with accepted_through: 47 — the bytes you typed before the refresh
  2. Client's fresh hook has writeHead = 0
  3. stdin.reconcile(47) evaluates 47 > writeHead
  4. unreconcilableRef = true — latched, never cleared
  5. notifySettled(47, false, "unreconcilable")
  6. usePaneSelection's subscribeInputSettled listener fires
  7. setInputError(rejectedMessage) → the toast
The toast is the visible half. The invisible half is worse: from step 4 onward every keystroke in that pane returns {sent:false} and queues silently. You are being told about the wrong problem, and not told about the real one.

There's a second, independent defect stacked here. That listener has an escape hatch — selfReportedOffsetsRef — so a failed paste doesn't double-report, because the paste UI shows its own error. But a connect-time reconciliation failure isn't a payload at all; it matches no recorded offset, so it always renders as if a payload you sent had been rejected.

Fix — two separate things Rebase the offset space per connection (Lever 01 from the last pass), and stop routing connection-level reconciliation failures through the per-payload settled channel. A reconnect that can't reconcile is a pane-status event ("reconnected, some input may not have been delivered"), not a per-keystroke rejection. Two different facts currently share one callback.
S2

The unsent-input pill speaks in bytes, not actions

Design

"[4s] [A / [4s] [A — anything that's not normal characters means nothing to me… it'd have 11 lines, one for each letter and space… and there isn't a way to cancel."

[A is ESC [ A — you pressed Up twice. The pill is rendering raw CSI bytes with a single cosmetic substitution (\n → ⏎) and nothing else. You're right on all three counts, and they're three genuinely separate problems:

Discard all  ·  Send now

The queue's unit is wrong, not just its rendering. enqueue() pushes one entry per xterm.onData event. Coalescing adjacent same-intent entries at enqueue time fixes the display and cuts N wire frames to 1 on flush — they were going to be concatenated on the wire anyway.

For rendering, terminalKeys.ts already holds the forward map (key name → bytes). The pill needs the inverse: a byte-sequence decoder that turns ESC[A into ↑, \x03 into Ctrl+C, and leaves printable runs as quoted strings. That decoder belongs next to the forward map, not in the component.

The missing-cancel point is the important one, and it's a safety issue rather than a convenience one. A queued entry is replayed whenever the socket returns — which may be minutes later, in a shell that has since changed directory, exited, or started a different program. The queue also survives pane unmount through setPendingInputBuffer, so it can outlive the pane that created it. There is currently no way to inspect-and-discard before that happens, and no expiry.

Fix Coalesce at enqueue; add a byte→label decoder beside terminalKeys.ts; give the pill per-entry discard, discard-all, and send-now. Then add an age threshold beyond which queued input is held rather than auto-sent — the current behaviour (replay unconditionally, however stale) is the wrong default for a shell.
S3

Touch scroll dies because there are two scroll controllers

New — root cause

"Sometimes the scroll stops working on touchscreen for some reason."

Found it, and it's a clean instance of the identity-churn problem from F8. useTerminalTransport returns a fresh object literal on every render. That poisons everything downstream of it:

// useTerminalTransport.ts — new object identity every render
return { sendJson, sendReliableJson, currentGen, subscribe, onStateChange, state };

// useTerminalSession.ts — so this rebuilds every render…
const sendControl     = useCallback(..., [transport]);
const scrollController = useMemo(..., [sendControl]);

// useTerminalTouch.ts — …but this captured instance #1 and keeps it
}, [terminal, enabled]);   // scrollBy is NOT a dependency
Why it goes permanently dead
  1. Touch scroll calls instance #1 → unacknowledgedFrames++
  2. A stdout frame arrives → notifyOutput() decrements instance #N (current render's)
  3. Instance #1's counter only ever increases
  4. At 8 it hits maxUnacknowledgedFrames
  5. flush() now always takes the schedule() branch — a rAF loop that re-queues forever and never sends
Touch scroll is permanently dead for that pane after eight gestures, and it burns a requestAnimationFrame every frame from then on. It only affects mouse-tracking (TUI) panes — the non-tracking path does a local terminal.scrollLines with no gating at all. That's your "sometimes."
Fix — and it's bigger than this bug Make useTerminalTransport return a stable handle (build it once in a ref; the methods are already stable useCallbacks with empty deps). Hold the scroll controller in a ref rather than a memo. Then audit for the same shape elsewhere — the fresh-object-per-render return is the root, and it silently invalidates every downstream useMemo/useCallback without any type or lint error. This one happened to produce a visible symptom; the others just churn.
S4

The device frame appears because lease state rides the size channel

New — root cause

"It can falsely enter this mode sometimes when the screen is resized, but not every time."

"Not every time" is the tell — it's a dropped notification, and the drop is size-conditional. Two mechanisms compound:

Mechanism A — a lease change that coincides with a resize is discarded
  1. SizeCh has capacity 1; publishSizeLocked drops-and-replaces when full
  2. The forwarder reads a queued entry, then re-reads live state via SizeLeaseState
  3. if cols != size[0] || rows != size[1] { continue }
  4. The holdsLease value was fresh and correct — and it is thrown away by a size-equality staleness filter
During a drag-resize or a mobile keyboard opening, dimensions change faster than the channel drains. The lease-transfer notification is exactly the one that gets eaten, and the client stays a follower until something unrelated publishes again.
Mechanism B — the reconnect double-subscribe window
  1. A new WebSocket Subscribe()s before the server's read loop notices the old one died
  2. Both connections are in s.clients; s.leaseOwner is still the old channel
  3. The new connection's first size_info reports holdsLease: false → the frame appears
  4. Normally self-heals when Unsubscribe transfers the lease…
  5. …unless Mechanism A eats that notification too, in which case it sticks
This is why a single-viewer session can show a "another device owns this" frame with no other device involved.

And separately, the frame renders badly because it fights xterm for layout. useFollowerPresentation imperatively writes position, left, top, width, height and transform onto terminal.element, overrides terminal.options.fontSize, then calls fit.fit() and terminal.resize(). Three layout authorities on one element, with a 240 ms CSS transition running underneath — xterm measures its cell geometry from a DOM node that is mid-transition and scaled.

Fix Separate the concerns that are currently fused. Presence and lease are not size: give them their own frame and their own channel, never coalesced against dimensions. Require a confirmed second viewer (viewerCount > 1) before rendering the frame, so a transient nil-lease can't produce one. And for layout, scale a wrapper element — let xterm lay out naturally at the leader's grid inside an untransformed box, and put the transform on the parent. xterm should never be told a font size that isn't the one it's measuring.

02Storage: it isn't the database

Your instinct that something is growing wrong is right. The thing that's growing is 108× larger than the database, and it isn't terminal history.

First, a correction worth making

Terminal scrollback is not stored in the database at all — not one byte. It lives in three in-memory or process-owned places: the server emulator's ring (10,000 lines, ≈1–2 MB), tmux's own history-limit (set from the same constant), and xterm's client-side buffer. None of it is persisted. So "we're storing earlier terminal data pointlessly" isn't what's happening — but something else is.

Codex session homesstate/…/sessions/codex 45 GB
Grok session homesstate/…/sessions/grok 744 MB
The databasedata/…/web-console.db 425 MB
Uploads cachecache/…/uploads 13 MB

59,340 per-session Codex home directories exist. The sessions table has 275 rows. That's roughly 59,000 orphans, the oldest dating to May 27. Nothing reaps them: session teardown calls os.RemoveAll(uploadDir) in four places and never touches the agent home. The only code that deletes one is the manual archive-retention endpoint — which is dry-run by default. Clearing the backlog belongs to storage-manager; what belongs here is not generating it.

There's a second, cheaper problem underneath: session_factory.go sets CODEX_HOME for every session unconditionally, whether or not you ever run codex in it. Each empty scaffold is ~24 KB of directory inodes. At 59,340 directories that's about 1.4 GB of pure scaffolding for sessions that never used the feature.

Inside the 425 MB database

110 MB of real text, stored three times.

conversation_events.textthe actual content 110.4 MB
…fts_contentbyte-identical duplicate 110.4 MB
…fts_datathe inverted index — legitimate 62.6 MB
speech_paragraphsJSON re-slicing of the same text 51.6 MB

The 110 MB duplicate is a one-line schema fix. The FTS5 table was created as content-owning, so it keeps its own full copy of every string. It was declared fts5(event_id UNINDEXED, text, tokenize='unicode61') — declaring it content='conversation_events', content_rowid='rowid' instead (external-content FTS) eliminates the copy entirely. The three triggers already written in main.go are exactly the shape external-content FTS requires, so the migration is the table declaration plus a rebuild.

And there is no retention on conversation_events at all. 132,697 rows spanning 2026-05-20 to today — about 1,450 events per day, growing monotonically. The only DELETE is WHERE session_id = ?, which runs when a session is explicitly cleared. Nothing ages anything out.

On scrolling further back

This is cheap — WC_TERMINAL_SCROLLBACK_LINES accepts up to 100,000 and drives both the emulator ring and tmux's history-limit — but there's a coupling that will bite you. MaxSnapshotBytes caps one replay at 2 MiB, and the scrollback ring's own comment estimates 10,000 lines at ≈1–2 MB. You are already at the replay ceiling.

Raise scrollback without raising that cap and the extra history exists on the server but can never reach a reconnecting client — boundSnapshot silently trims it and emits a snapshot_notice. Raise both and every reconnect re-streams multiple megabytes of JSON-encoded ANSI. Which is the concrete reason output-delta resume (Lever 05) is the prerequisite for deeper scrollback rather than a separate nice-to-have.

04Portability: it compiles everywhere, it runs one place

The build is genuinely portable and the capability reporting is honest about what isn't. The gap is that "unsupported" is currently a runtime flag rather than a compile-time seam — which is exactly the difference between Windows being a file to write and Windows being an audit.

What already works — verified, not assumed

I cross-compiled every target and ran go vet, which typechecks test files as well as production code:

linux/amd64 ✓linux/arm64 ✓ darwin/amd64 ✓darwin/arm64 ✓ windows/amd64 ✓windows/arm64 ✓

Six for six, production and test code, zero errors. That is a real achievement and it is not the normal state of a Go service that shells out to tmux. It means the portability work already done is holding.

The rest of the foundation is in good shape too, and it's worth naming because these are the patterns to copy rather than replace:

  • No develop.sh. The lifecycle is declarative — "exec": ["web-console","hooks","register"] — so there is no bash interpreter on the startup path. This scenario is already Declared-Scenario shaped, which is the single biggest Windows blocker most scenarios still have.
  • capabilities.KnownForPlatform tells the truth. On Windows both terminal backends are downgraded to PlatformUnsupported with a specific reason string, rather than being advertised and then failing.
  • resolveShellForOS already knows the Git Bash trap — that a POSIX SHELL export can't be resolved by Windows LookPath — and prefers powershell.exe unless WC_DEFAULT_SHELL says otherwise.
  • filepreview is split correctly into hidden_unix.go / hidden_windows.go, using real Win32FileAttributeData rather than a dotfile-name guess.
  • The UI already parses Windows paths. lib/paths.ts handles drive letters, UNC prefixes and backslash separators — because a remote target might be Windows even when the server isn't. That's the right instinct.
  • Only three hardcoded POSIX paths in the whole Go API, and each is either inside a Unix-only code path or already guarded.
  • systemd-run is done exactly right — a LookPath probe behind a sync.Once, a GOOS check, a logged verdict, and a working fallback when it's absent. Copy this shape for every other host-tool dependency.

The one structural change that makes Windows easy later

Right now platform support is expressed as a runtime boolean:

// pty_supported.go   //go:build !windows
var localPTYAvailable = true
// pty_unsupported.go //go:build windows
var localPTYAvailable = false

// backend_registry.go — the flag only colours the descriptor…
reg.Register(backend.Descriptor{ID: backend.Standard, Available: standardAvailable}, defaultPTYFactory)
// …the factory is still registered and still callable.

So the old platform flag was advisory. defaultPTYFactory lives in the Unix-only pty.go and imports creackpty directly; pty_tmux.go's 737 lines of Unix-only tmux orchestration are now isolated by a build tag.

The change Move the platform decision from a flag to the file layout, behind the interface that already exists. pty.PTY (from session-core) is the correct seam; the implementations just aren't split along it.
pty_local_unix.go (!windows) — realPTY + creackpty, as today
pty_local_windows.go (windows) — a ConPTY realPTY: an explicit ErrUnsupported stub now, a real implementation later
pty_tmux.go (!windows) — build-tagged, and the persistent backend registered only where it can exist
Then the shared platform flag deletes itself: availability becomes a property of which file compiled. Adding Windows turns into writing one file against a known interface, instead of auditing 737 lines for Unix assumptions. That is precisely the "easy to add later" property you asked about.

The honest summary

Portability here is structurally sound and functionally shallow. The build system, the capability reporting, the lifecycle model and the shared platform package are all doing the right thing — you can ship a Windows binary today and it will start, serve the UI, and correctly tell the user it has no terminals.

What's missing is one seam and one signal: the PTY implementations aren't split along the interface that already exists, and the test suite can't run anywhere but Linux. Fix those two and Windows support becomes an additive task with a green/red indicator, rather than a research project.

05Suggested order

The dependency structure matters more than the individual items here.

  1. Stable transport handle — five lines, fixes S3 outright, and removes the churn that makes every other UI change hard to reason about. Do it first because everything else in the UI gets easier afterwards.
  2. Per-connection offset rebase + separate the reconciliation channel — kills S1's toast and the silent input death behind it. These are one change; shipping only the toast fix would hide the real bug.
  3. Split lease/presence off the size channel — fixes S4's false positives. The frame's appearance is a separate, smaller job: scale a wrapper instead of mutating terminal.element.
  4. Give the tests a platform contract — cheap, and it is the prerequisite for every other portability item. Without it you cannot tell whether a macOS or Windows change worked.
  5. Split the PTY implementations per-OS; fix darwin echo state — the structural move that converts "add Windows later" from an audit into writing one file. The macOS echo fix rides along for ~10 lines.
  6. External-content FTS, then a retention policy — the schema change is mechanical; the retention policy is a product decision only you can make.
  7. Pending-input queue rework — coalescing, the decoder, and cancel. Do it after (2), because a correctly-working input lane changes how often anyone sees this UI at all.
  8. Lazy CODEX_HOME + teardown deletion — stops generating orphans. Clearing the existing 45 GB stays with storage-manager.
  9. Tailer consolidation, then fold the checkpoint tables — the largest pure-refactor item, and the one with no user-visible payoff, so it goes last among the substantive work.
