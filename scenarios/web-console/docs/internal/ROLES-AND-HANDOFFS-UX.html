Roles and handoffs

Two new ideas, both deliberately generic: a group holds roles rather than loose tabs, and any role can hand off to another. Your plan-then-implement pair is one configuration of that — not the thing being built.

The design test I held myself to: nothing in the data model may know what a "plan" is. Plan detection ships as one deletable example rule sitting on top of a general mechanism.

Vocabulary

Four words, two of them new

Naming matters more than usual here, because the wrong noun is what locks a design into one workflow. These four carry no assumption about how many sessions you run or what they do.

Sessionexists
One terminal, one process. Unchanged.
Groupexists · re-framed
One piece of work, named for the task rather than the tools. Today it is a folder you drag tabs into afterwards; it should be the thing you create first. Same workspace.Group record — name, colour, order, collapsed. No schema change to re-frame it.
Rolenew
A named position inside a group. A role is either running (it has a session) or waiting (it has a command and no process yet). "Planner", "Implementer", "Reviewer", "Log watcher". Deliberately not "step" — a watcher tailing logs beside you is a role, not a stage in a sequence.
Handoffnew
Send a message to another role, starting it if it is waiting. That is the entire definition. Everything workflow-specific — the wording, the payload, whether it is suggested to you — is configuration layered on this one verb.
Group templatederived
A saved set of roles you can stamp out. Not a fifth concept so much as "a group, saved" — and the main way you author one is Save this group as a template.
Design constraints

Six things that must not be hardcoded

You asked for this explicitly, so I made it a checklist the implementation can be reviewed against. Each rule names the assumption it forbids.

1

A group holds 1..N roles

Solo work is a one-role group. Your pair is two. A plan → critique → implement chain is three. A dev server plus two agents plus a log tail is four, with no ordering at all.

Forbidden: anything named primary/secondary, any pair-shaped field, any UI that breaks past two.
2

A handoff targets any role, or a new one

Forward to a waiting role, to one already running, to several at once, or to a session created on the spot. Fan-out is the same operation with more than one target selected.

Forbidden: a handoff that can only start something, or that assumes exactly one destination.
3

The payload is generic text with one slot

A handoff carries a prompt template and an optional payload. The payload is whatever you were looking at: a file path, a selected passage, a command's output — or nothing.

Forbidden: a plan_path field. The variable is {{payload}}, and a plan is one kind of payload.
4

Suggestion is separable from mechanism

Capture rules decide when the console offers a handoff. Delete every rule and handoffs still work — you invoke them yourself. That separation is what keeps the feature honest for someone whose workflow you have never seen.

Forbidden: detection logic anywhere in the handoff execution path.
5

Templates are an accelerator, never a prerequisite

Every capability works on a group you assembled by hand. Templates only remove repetition.

Forbidden: a role that can only exist inside a templated group.
6

Shipped content is examples, not behaviour

The Plan → Implement template and the ~/.vrooli/plans/*.md rule ship as ordinary editable rows, indistinguishable from ones you write. Delete them and nothing degrades.

Forbidden: a built-in that cannot be renamed or removed — the state today's Codex sign-in card is in.
Redesign · New Session

The dialog spends its space on the wrong thing

You are right that it feels padded. Choosing a machine is a one-line decision that currently gets a stack of full-width readiness cards, while choosing an agent — the actual reason you opened the dialog — is a vertical list of eight identical rows you have to read one at a time.

And the Codex sign-in card is worth cutting outright. I searched: there is no signed-in detection anywhere in the codebase. The card is a hardcoded command shown unconditionally whether or not you are signed in. You find out you are logged out when the agent tells you, which is exactly when you can act on it. It belongs in the shortcut list like every other command, where you can edit or delete it.

The core verb

Where a handoff is offered

You described your real habit precisely: agent writes a plan, you switch to the Messages view, click the path, a viewer opens and renders the markdown. That viewer is the best possible place for this, and it already has what it needs — useFilePreviewController(sessionId) means the viewer knows both the file and the session it came from, which is exactly the pair a handoff requires.

The surface I would not build: detection inside the terminal view. The terminal is a raw byte stream with its own cursor addressing. Overlaying suggestion chips on it means hit-testing against reflowing text, fighting the alternate screen buffer, and getting it wrong whenever an agent redraws. The Messages view exists precisely because it is the structured surface — put structured affordances there. The terminal keeps the header button, which needs no text analysis at all.

Configuration

Capture rules — the customizable part

This is the piece that decides whether the feature generalizes. A capture rule is four fields: a name, where to look, what to match, and what to do about it. It produces a suggestion; it never performs one.

Match against paths with a glob, or against message text with a pattern. Both are just "find a payload in what this session said". Your plan rule ships as one row you can rename, edit, or delete.

Your call

Four decisions I would want from you

Is "role" the right word?

It carries no ordering, which is what lets a log watcher and an implementer coexist. The alternatives imply sequence (step, stage) or are jargon (slot, seat).

I'd keep "role". It also gives waiting roles a natural read — an unfilled position, not a broken session.

Does the prompt live on the sender or the receiver?

On the receiver, any session can hand off to the Critic and get the Critic's framing — handoffs compose. On the sender, you get per-source wording but N×M configuration.

Receiver, with a sender override. The composer is always editable, so the override costs nothing and the default stays composable.

Should closing the last session close its group?

Auto-close with undo keeps the manager clean, but can surprise you when you deliberately pre-create a group to fill later.

Auto-close, with an exemption while any role is still waiting. A half-started group is exactly the case where an empty group is intentional, and roles let the console tell the difference.

Is P6 worth building at all?

Once handoff is one click from the file viewer you already open, detection saves you a menu, not a workflow. It may not earn its complexity.

Ship P1–P5, then judge. If you find yourself reaching for the handoff button reflexively at the same moment every time, that moment is worth automating. If not, the rules engine is complexity you avoided.
