# Decisions — Ecosystem Manager

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation notes belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| Date | Decision | Rationale | Status |
|---|---|---|---|
| 2026-01 | Consolidate four legacy tools (resource/scenario × generator/improver) into one unified Ecosystem Manager. | A single control plane for generating and improving both scenarios and resources eliminates duplicated loop logic and gives one queue, one profile system, and one metrics store. | ACCEPTED |
| 2026-01 | Store auto-steer profiles on the filesystem (`profiles/*/profile.json` + `metadata.json`); keep only execution state and history in a relational store. | Profiles are human-authored, version-controlled configuration (objective functions). They belong in git alongside code, not in a database. The database holds only the mutable runtime state. `[CODE: profiles/]` | ACCEPTED (store was Postgres; cut over to embedded SQLite 2026-06 — see below) |
| 2026-01 | Persist the task queue as YAML under `queue/<status>/`, using the directory name as the status and atomic file-moves for transitions. | Directory-as-status makes state legible and transitions atomic at the filesystem level (move = commit), avoiding a separate transactional store for the queue. `[CODE: queue/]` | ACCEPTED |
| 2026-01 | Use REST/JSON transport for the API. | Predates the proto + Connect-RPC standard now used across Vrooli; was the available option at the time. | SUPERSEDED-IN-PRINCIPLE / drift — see Superseded Decisions and [`PROBLEMS.md`](PROBLEMS.md) |
| 2026-05-30 | Reframe auto-steer as a **closed-loop controller** and profiles as **objective functions** (rather than fixed ordered scripts). | The "profile = fixed ordered script" mental model undersells the system. Treating it as a controller — profiles define the objective, the loop adaptively selects skills against measured findings — is the correct frame and unlocks adaptive skill selection, findings-based state, an effectiveness table, DTV priors, and thrashing defense. Docs are written first to anchor the model; implementation is future work in [`PROBLEMS.md`](PROBLEMS.md). See [`../concepts/CONTROL-MODEL.md`](../concepts/CONTROL-MODEL.md). | ACCEPTED / DIRECTIONAL |
| 2026-05-31 | Aggregate per-skill DTV fitness **inside DTV** via a new `GetSkillFitness` RPC, rather than crunching raw validation records EM-side. | DTV owns the append-only records; deriving one skill's trust/cost/convergence client-side would mean N×M round-trips (enumerate every golden, paginate every tuple) and re-implementing aggregation in every consumer. One server-side fold is the "fix the substrate, design to the ideal" choice. EM consumes the aggregate through a Connect client. `[CODE: pkg/dtv/, scenarios/development-toolchain-validator/api/internal/report]` | ACCEPTED |
| 2026-05-31 | DTV is a **gate and a prior, never a source of efficacy**; the eligibility gate denies only RED, UNKNOWN fails open, and any DTV outage degrades to exact P1 (uniform prior, allow-all). | Goldens are pristine (zero findings), so DTV can never observe "skill closed N findings" — efficacy stays learned live by the bandit. Gating UNKNOWN would break first-run scenarios, and a synchronous DTV dependency would risk stalling the control loop; fail-open keeps P2 a strict enhancement of P1. The prior is blended via Bayesian shrinkage so live evidence washes it out regardless. `[CODE: pkg/autosteer/dtv_selection.go]` | ACCEPTED |
| 2026-06 | Hard cut-over from PostgreSQL to an **embedded SQLite** file, opened through the `api-core/storage` seam. No `vrooli-postgres-main` container, no `vrooli_ecosystem_manager` DB, no `POSTGRES_*` env. Schema is **domain-owned** (`api/pkg/{autosteer,effectiveness,steering}/schema.sql`, each with a `Schema()` func registered in `api/pkg/dbschema`'s `AllSchemas()`) and applied at boot by `database.EnsureSchemas`. The dead `task_executions` / `operation_metrics` tables and the central `initialization/postgres/schema.sql` were dropped. | EM is an internal single-operator control plane; an embedded file removes a heavyweight shared resource, makes storage variant-isolatable (Baseline Modes shadow), and lets each domain own its own schema. Backup is via data-backup-manager coverage of the storage root. `[CODE: api/pkg/storagepaths, api/pkg/dbschema]` | ACCEPTED |
| 2026-06-23 | **Delegate measurement to scenario-completeness-scoring**; delete EM's self-collected `MetricsSnapshot` subsystem (the ~24-metric `metrics*.go` collectors, the `make build` build-check, and the requirements re-parser). The controller reads the maturity rung, build/phase status, and operational-targets completion from completeness-scoring (`GetScore`) via one typed Connect client seam (`pkg/completeness`), consuming the findings vector it already gets from test-genie. **D1**: EM fetches the completeness score *after* its own test-genie audit writes fresh phase-results, so rung/OT% reflect the current iteration. **D2 (no fallback)**: measurement is load-bearing for termination, so a fetch failure degrades loudly — the start aborts, a mid-loop failure halts with stop reason `measurement_unavailable` — it does NOT fall back to a local collector (contrast the DTV seam, which fails open). **D4**: EM consumes the single maturity-go ladder evaluation completeness-scoring already performs (the working rung, capped at the profile's top rung) instead of re-deriving the rung from raw signals; EM no longer calls `ladder.Lowest`/`AllHold`/`Signals`. The ~22 analytics-only sub-metrics (accessibility/flaky/web-vitals/etc.) were crude string/regex heuristics gating nothing and are gone. `[CODE: pkg/completeness/, pkg/autosteer/{terminator,ladder_selection,execution_orchestrator}.go]` | ACCEPTED |
| 2026-06-23 | **Retire EM's insights / per-run-retrospective subsystem entirely (D3)** and route operators to **agent-manager investigation** for "how did this run go". Deleted the `insights` package, the queue insight generator/manager + process registry, the insights HTTP handler + 8 routes, the `insight-generator.md` prompt (incl. the obsolete `autosteer_profile` suggestion type), agent-manager's now-dead `ExecuteInsight` + insights agent profile, and the entire UI insights surface (components, tabs, API client, query keys, types). | The insights surface was an on-demand LLM retrospective: per-run pattern/suggestion generation that overlaps agent-manager's first-class investigation feature, plus a cross-task aggregation built *on top of* those per-run reports (so they could not be cleanly separated). The `autosteer_profile` suggestion type was already obsolete — profile direction is auto-derived from findings and no code path applied profile suggestions. No surviving insights surface was justified. `[CODE: removed pkg/insights, pkg/queue/insight*, pkg/handlers/insights.go, ui/src/components/insights]` | ACCEPTED |
| 2026-06-24 | **Delete the execution-feedback subsystem entirely** (run-level `user_rating`/`user_comments` + structured `execution_feedback_entries`). Removed the two `POST .../feedback[/entries]` endpoints, `HistoryService.SubmitFeedback`/`SubmitFeedbackEntry` + the `loadFeedbackEntries` history enrichment, the `execution_feedback_entries` table and `user_rating`/`user_comments`/`user_feedback_at` columns, `AvgRating` from analytics, the `UserFeedback`/`ExecutionFeedbackEntry`(`Payload`) types, and the UI panel/dialog + the avg-rating/per-row rating displays. | After the effectiveness ledger was removed (greedy-controller simplification) nothing consumes operator feedback for any decision — the greedy selector reads only test-genie findings — so it was a write-only, display-only annotation. It is the last fragment of the retired insights domain (D3, 2026-06-23). `[CODE: removed feedback from pkg/autosteer/{history_service,handlers,types,repositories}.go + schema.sql; ui ExecutionFeedbackPanel]` | ACCEPTED |
| 2026-06-24 | **Remove the `TimeoutWatchdog` polling backstop** (file + processor wiring + `GetTimedOutExecutions`/`MarkTimedOut`/`timedOut` registry surface + `TimeoutWatchdogInterval`). | agent-manager owns server-side run-timeout enforcement (`RunTimeoutMinutes`/`DefaultTimeout`/per-profile `timeout_ms`) and reaps stale/crashed runs (`ListStaleExtractions`); the normal execution path already enforces an EM-side deadline via `context.WithTimeout` around `WaitForRun` plus a `StopRun` cleanup closure (`execution_manager.go`). The separate polling goroutine was redundant defense-in-depth. `[CODE: removed pkg/queue/timeout_watchdog.go]` | ACCEPTED |
| 2026-06-24 | **Delete the two operator-authored UUID profiles** (`From Scratch`, `UX refactoring - major`); keep only the named template profiles. Added `contracts` to `production-ready` to preserve catalog reachability for the `proto-contract-audit` skill (the deleted `From Scratch` profile was the sole profile valuing that dimension; `TestCoverageGuardCatalogReachability` enforces this). | The ad-hoc UUID profiles were operator scratch; the named templates are the canonical set and `production-ready` ("covers all quality dimensions thoroughly") is the right home for `contracts`. `[CODE: profiles/metadata.json, profiles/production-ready/profile.json]` | ACCEPTED |
| 2026-06-23 | **Defer removal of the legacy `steer_phase_index` / `steer_phase_iteration` fields** (ExecutionHistory + proto `queue.proto` fields 22/23 + UI). | The plan listed this as a "zero-risk" cleanup, but it is not: the auto-steer iteration is already carried by `auto_steer_iteration` (proto field 20), yet the *queue*-steering path reuses `steer_phase_index` to carry the queue position and there is no separate `steering_queue_index` field — so a clean removal requires a shared-proto contract change *plus adding a replacement field* and rewiring the UI badge. That churn on the shared proto package is disproportionate to the value and orthogonal to this plan's measurement/insights purpose. The fields are vestigial but functional (they carry real data the UI displays), not dead code. | DEFERRED — see [`PROBLEMS.md`](PROBLEMS.md) |
