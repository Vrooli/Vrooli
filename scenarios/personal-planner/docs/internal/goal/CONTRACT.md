Integrated planning and calendar repair proposal
Prepared for scope review on Oct 3, 2026. Recommended option A accepts one finite Planner repair covering native calendar, goals/deadlines and progress, recorded actuals, capacity-based forecasts, honest learning and interface identity, retaining the accepted read-only provider boundary. It also delegates native ownership selection and conditional execution on verified existing subscription-included capacity in isolated local work/tests. Options and limits appear below. This recommendation is awaiting owner approval; no implementation has started.
The outcome to review
Make Personal Planner useful for one connected journey: define a goal and its evidence of success; break it into a project, milestones and work; fit that work around real calendar obligations; record what actually happened; and explain what the remaining work means for deadlines and future estimates. Calendars, progress and forecasts must agree about the same records while showing their different meanings.
The accepted specification already calls for this. Native tasks/events and correct time semantics belong to R0. Goals, milestones, commitments, dependencies, explainable forecasts, actuals and basic history-based learning belong to R1. This proposal repairs that integrated product, with demonstrable increments inside one outcome. It does not reduce Planner to a calendar or turn the coverage inventory into separate work orders.
Keep Google Calendar as the working event store during preparation. Apple Calendar should access the same Google-backed calendar after its device setup is verified. Planner remains the intended Vrooli scheduling authority for native planning and source-app scheduling; Google owns its provider events. Drive retains project requirements, evidence and decisions. No connection or automatic synchronization is established by linking these records.

One coherent repair, with explicit boundaries
1. Establish identity and calendar truth. Reconcile the UI/CLI/Connect profile discrepancy, authenticated actor/workspace, endpoint and source revisions. Reuse existing domain code and supported native commands. Preserve original records and explain inconsistent observations before personal-data migration. Deliver native timed, ordinary date-only and multiday events, useful empty Month navigation, stable reopen context, revision-aware edits and visible save/retry results. Keep events, work allocations, routines and source-owned content distinct. Respect the specification’s already-required native-event baseline and the already documented retired-calendar transition; no revival or further deletion follows from this proposal.
2. Make goals and project plans actionable. A goal has a purpose, target horizon, status and declared progress method: manual assessment, an explicit numerical metric or milestone completion. Numerical observations preserve baseline, target, unit, direction, date and origin; absent observations stay unknown. Milestones state observable completion criteria, prerequisite work, target/promise and evidence. Support lightweight native projects when needed, and source-owned project references when an existing app owns the work. Show unlinked goals and unlinked work honestly rather than requiring every obligation to be a productivity goal.
3. Connect planning to actuals and revised outlook. Keep original estimates, revisions, explicit remaining effort, desired targets, accepted promises, accepted allocations, current forecasts, actual finish and completion evidence distinct. A completed session, task, milestone and income outcome are different facts. Preserve manual approximate durations, interruptions and correction provenance; do not convert unrecorded time, unattended agent runtime or event attendance into productive human effort. Project timelines include finish-to-start dependencies, waiting and unresolved source states, with cycle rejection and clear source ownership.
4. Explain slippage and support better estimates. Compare original plan, latest accepted plan and current forecast without rewriting history. Forecast all competing accepted work against shared usable capacity, including calendar constraints and human review time. Show central/cautious scenarios, assumptions, remaining-effort uncertainty, dependency waits, source freshness and horizon limits. Explain material changes in scope, effort, capacity, interruptions or waiting. Forecast updates may happen automatically; accepted rescheduling, promise revisions and planning-policy adjustments require their proper explicit command.
5. Integrate provider events and verify the whole journey. Reuse the existing Google adapter rather than build a second one. The accepted D04/R1 boundary is read-only provider access; create/edit/delete across Planner, Google Calendar and Apple Calendar requires an explicit expansion to the later R3 writeback scope. An existing ChatGPT connection is not Planner's OAuth grant. Provisioning, authentication and any material persistent access remain separately authorized actions.
These five grouped outcomes form one repair commission. Small correctness fixes stay inside the relevant outcome; they do not become a fragmented set of work orders. A capable local producer can adjust internal sequence or epoch size while preserving the integrated result and acceptance. A finite delivery effort is proposed because the current inventory found no existing Planner execution plan or team; none has been created.
