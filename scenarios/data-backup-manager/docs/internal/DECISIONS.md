# Decisions — Data Backup Manager

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.


Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation notes belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| Date | Decision | Context | Consequences | Revisit Trigger |
|---|---|---|---|---|
| 2026-11-19 | A damaged destination volume may be rebuilt in place when it holds only backups, so preservation is an optional precondition rather than a rule. | The Elements volume is unrepairable on Linux (403 cross-linked MFT records), cannot shrink in place, and every source it held still exists locally. The staging path exists to preserve a drive's contents; when nothing on it is unique, that preservation costs a whole second drive and buys nothing. | `repair-drive.sh --rebuild-in-place` previews the loss, re-identifies the disk by serial, formats ext4, recreates the destination records, re-points every bound plan, and verifies the new repositories. It is the same script, so preservation and rebuild share the identity, mount, and ownership rules. The tradeoff is explicit: historical snapshots older than the local repository's oldest (2026-10-20 at the time) are gone. | Revisit if a drive's contents become unique (for example a destination with retention the local repo does not mirror), or if the control plane gains an executable format action that replaces the script's mkfs. |
| 2026-05-26 | Use the generated `react-vite` scenario documentation contract. | Scenario scaffold was generated from the template. | Docs start with stubs and maturity metadata in `docs/manifest.json`. | Revisit when scenario adopts a different template or doc contract. |
| 2026-05-26 | Wrap the new `kopia` resource as the backup engine rather than hand-rolling backup mechanics. | Backup needs dedup, encryption, compression, incrementals, multi-destination, retention, integrity checks, stats, and standalone restore. Building these is years of work that an established engine already solves. Follows the wrap-not-use principle. | The manager orchestrates kopia rather than reimplementing crypto/dedup. Snapshots remain restorable with the plain `kopia` CLI even if Vrooli is down — a deliberate disaster-recovery property. Companion plan: `plan-manager plans get kopia-resource-implementation-validation-plan`. | Revisit only if kopia is abandoned upstream or cannot meet a hard requirement (e.g., a backend it will never support). |
| 2026-05-26 | Decouple Sources from Destinations with an explicit five-noun model. | A backup target (what to protect) and a backup destination (where it lands) change independently, and the same target often needs more than one destination. | The domain is TARGET (a registered source) × DESTINATION (a kopia repository) × PLAN (a many-to-many binding carrying schedule + retention) → RUN → RESTORE. Plans, not targets or destinations, own scheduling and retention. | Revisit if a simpler model proves sufficient, or if a target/destination distinction collapses in practice. |
| 2026-05-26 | Support six source kinds in v1: filesystem, SQLite, Postgres, Redis, Qdrant, object-storage. | These cover the runtime state Vrooli scenarios actually own today. | Each kind captures into a consistent artifact: SQLite via `VACUUM INTO`, Postgres via `pg_dump`, Redis via prefix `SCAN`+`DUMP` (best-effort, non-transactional — accepted limitation), Qdrant via its snapshot API, object-storage via S3/MinIO mirror, filesystem directly. Redis's lack of point-in-time consistency is documented and accepted. | Add kinds as new runtime stores appear; revisit Redis semantics if a transactional snapshot path becomes available. |
| 2026-05-26 | Self-registration with a reconstructable catalog. | Scenarios own their runtime state and know best what to back up; the manager should not hard-code which scenarios exist. | Scenarios idempotently register/deregister targets (owner+name keyed, like agent-manager's `EnsureProfile`) and re-register on boot. The manager's SQLite DB is a cache + run history, not the source of truth — it can be rebuilt from re-registration. | Revisit if registration churn or boot ordering makes the cache-not-truth model painful. |
| 2026-05-26 | Encryption ON by default for every destination; repository and backend credentials use the credential authority. | Backups frequently contain secrets-bearing source data, and a leaked unencrypted repository is a full breach. | Every destination is an encrypted kopia repository. Repository passphrases and backend access keys are stored under per-repository credential-authority identities. Source resources retain ownership of their own credentials. Neither is read from config files or process arguments. See `SECURITY.md`. | Revisit only with a vetted reason to allow an unencrypted destination (none expected). |
| 2026-08-05 | Route all DBM and resource-kopia repository/backend credentials through the credential authority; remove Vault from this stack. | The authority already provides native OS keyring or encrypted portable storage plus operator-controlled recovery bundles. Vault's sealed bootstrap is not needed for the filesystem-first backup product and creates an avoidable lifecycle dependency. | Repository passphrases and future S3 credentials use per-repository authority identities; DBM and Kopia have no Vault dependency. Source resources retain their own credential contracts until separately migrated. Existing encrypted repositories remain preserved but require their original passphrases. | Revisit only if a concrete source resource requires an explicitly governed compatibility adapter. |
| 2026-05-26 | Storage limits default to alert+block, never silent eviction. | Safety over tidiness: a backup tool that quietly deletes backups to stay under a cap can destroy the only recovery copy. | Per-destination caps are configurable and default to alerting and blocking new writes when exceeded. Old snapshots are removed only by an explicit retention policy, never to free space. | Revisit only if an operator-controlled, clearly-labeled eviction mode is explicitly requested. |
| 2026-05-26 | Verified restore is first-class and gates removal of committed runtime data from git. | "We commit it so we don't lose it" is only safe to retire once restore is proven, not assumed. | A verify mode test-restores to scratch and checksums the result. No committed runtime data is removed from git until its target has a passing verified restore. | Revisit if the verify gate proves too slow to run at the needed cadence (optimize, don't drop the gate). |
| 2026-05-26 | Separate-root rule: a destination must not live under the storage root it protects. | A destination inside the protected tree is destroyed by the same incident that destroys the source. | Destinations are validated to be outside the protected root; an offsite destination is preferred for at least one tier. | Revisit when adding cross-destination replication (PRD OT-P2-002) — offsite tiering interacts with this rule. |
| 2026-05-26 | No n8n / no external orchestrator; in-process scheduler and greenfield per-domain SQLite. | The prior data-backup-manager leaned on n8n and was never used; an external orchestrator adds a moving part for a capability that must be maximally dependable. | Scheduling runs in-process. Catalog/run-history storage is greenfield per-domain SQLite (`modernc.org/sqlite`), no migrations folder. | Revisit if scheduling needs outgrow in-process (e.g., distributed multi-node execution). |
| 2026-08-19 | A preflight incident blocks only the units it applies to; the run proceeds with the rest. | A plan run aborted entirely whenever preflight produced any incident, and the fan-out loop then recorded every target as blocked — attributing an unrelated target's incident to it. Two stale target registrations in `elements-daily-runtime` blocked all 16 targets, so the plan produced zero backups. | `executeRun` aborts the whole run only when no unit could succeed anyway (a plan-scope incident, or every unit blocked by its target or destination). Otherwise it falls through to the normal fan-out, where `runOne` already blocks exactly the affected units. Such a run now ends `partial_failed` with accurate per-unit outcomes, and the grouped incident is still persisted as the root cause. | Revisit if an operator needs an explicit all-or-nothing plan mode, which would become a per-plan policy rather than the default. |
| 2026-08-19 | Volume remediation lives in the control plane; DBM plans, confirms and reports it. | The Elements destination sat read-only for 33 days because the NTFS dirty flag made `ntfs3` refuse a read/write mount, and DBM could detect that but not fix it. Embedding filesystem repair in the scenario would have put a host-repair implementation behind every scenario that happens to need one. | `internal/volumeremediation` owns the adapters and gates; `vrooli host volume` is the command surface; DBM gained `unmount`, `check-filesystem`, `repair-filesystem` and `mount-read-write` preparation actions that call it. On Linux the primary path is udisks2, which polkit authorises for a non-system device from an active session with no password and no root; hosts without it fall back to the setup-installed privilege broker. No scenario code spawns sudo. | Revisit if a platform gains an unprivileged repair path that udisks2 does not cover, or if the broker's mount-namespace isolation is changed so it can perform mounts. |
| 2026-08-19 | Attribute a read-only mount to a cause; never repair an unattributed one. | "Mounted read-only" has at least three unrelated causes — block-device write protection, a dirty filesystem, and a declared `ro` mount option — and only one of them is fixed by repair. The previous report named the symptom, so an operator had to guess. | `sysmounts` reads driver-published evidence from the platform's NTFS volume-info, block-device read-only, and filesystem-table sources and reports a typed `ReadOnlyCause` with its provenance. An unattributable cause stays `unknown` and the report explicitly refuses to propose a repair. | Revisit when adding a filesystem whose driver publishes state differently; Windows now has identity/read-only observation but still reports filesystem health as unknown, and macOS/Windows native recovery remains unproven. |
| 2026-11-03 | Auto-remount only after positive read-only check; gate destructive repair through a durable owner decision. | DBM's manual recovery journal had no automatic monitor or Notification Hub round trip, so a failed remount could neither recover safely nor obtain a verifiable repair approval and report its outcome. | A lifecycle-managed DBM worker observes registered strong-identity filesystems. It asks the control-plane volume owner to check first and auto-mounts only on `consistent=yes`, then verifies mounted/read-write state. Otherwise it raises an identity-bound Notification Hub decision. Only a signed resolution carrying a verified human and the exact approved repair key can resume the destructive step after fresh identity/plan validation. Result notifications use a persisted outbox so delivery retry cannot replay repair. | Revisit on native macOS/Windows runtime evidence, Notification Hub/credential-authority route failure, or a platform's inability to report trustworthy post-mount state. |
| 2026-08-19 | Repair is destructive; unmount, check and mount are not. | Requiring a data-loss acknowledgement on every step teaches operators to click through the one step where it matters. | `repair-filesystem` requires both a device-naming confirmation phrase and an explicit acknowledgement; the other three require only the phrase. The control plane enforces the acknowledgement independently of the scenario. | Revisit only if a non-repair action gains the ability to modify on-disk content. |
| 2026-05-26 | Replace the stale pre-2025 data-backup-manager. | The earlier scenario (n8n + MinIO) backed up the repo *source tree*, solved the wrong problem, and was never used. | This is a clean rebuild around runtime state, not source. The old scenario is preserved in the operator's temporary archive for reference only and is not carried forward. | Recorded under Superseded Decisions; no revisit expected. |
| 2026-11-10 | A backup that is blocked on a mounted drive gets a diagnosis and ONE plain question, and skipping unreadable leftovers is a recorded per-path exception, not a switch. | The Elements drive stopped backing up on 2026-08-19; the volume monitor only handled unmounted drives, and a mounted drive with 13 unreadable leftover temporary files in its kopia repository raised nothing for 82 days. The operator asked for the recoverable cases to be asked about, not discovered by an agent. | `repohealth` classifies each unreadable repository entry (leftover temporary upload vs repository content). Option A records the exact paths with approver, source and time; `UsageEngine` honours an exception only for the exact path that kopia's failure names and only while every unreadable entry is covered. Preflight, destination usage, cap checks and run accounting share that one rule. Repair delegates to the control-plane volume owner. Fresh-repository setup stays an agent task because registering a destination is not small and safe to do from a callback. | Revisit if kopia's usage listing learns to skip temporary files, if an exception is needed for something other than a leftover temporary file, or if the operator wants fresh-repository setup automated. |
| 2026-11-13 | Every DBM operator decision is keyed to its situation (`backup-failure:<destination-id>`, `volume-repair:<recovery-id>`) and is withdrawn by DBM when the situation clears; no new authority binding. | The operator saw several copies of "Backups to the Elements drive are blocked" (one per generation, re-asked after each expiry) and a copy that stayed open after the drive worked, because DBM only sent a "working again" notice and never closed or updated the decision. | The ask ledger (`decision_ledger.go`) raises with the subject key, re-asserts every 2 h (`reassert_within` 6 h as the hub's safety net), withdraws with a plain reason from `Settle` on every sweep, adopts keyless pre-change asks by `requester_ref`, and treats a `withdrawn` resolution or an answer to a withdrawn ask as a no-op. The lapse-and-renew loop stays, because the hub really closes a week-old unanswered question, but it can no longer leave two open. Withdrawal rides the existing event publisher; no new credential or grant. | Revisit if the hub changes subject semantics or a decision needs to survive DBM being down for more than 6 hours. |
| 2026-11-13 | Crypto Foundations authorizes the full DBM/control-plane recovery buildout and safe recovery work on the selected existing drive; destructive filesystem repair remains a verified-human, situation-bound Notification Hub decision. | Operator mode gate `crypto-foundations/runs/wallet-support-prepared-20261030/MODE.json` explicitly authorizes the full cross-scenario DBM recovery implementation and safe owner-routed recovery, with exact approval required for risky filesystem repair. That scope was missing from DB4's first mission wording. | Build and validate the complete DBM/Kopia/control-plane recovery path under the existing operator grant. Keep filesystem repair behind the existing `volume-repair:<recovery-id>` decision and verified callback; the authorization to build is not permission to bypass that runtime gate. | Revisit only if the operator changes the mode gate or the repair decision/callback contract. |
| 2026-11-13 | Restore an exact missing q-blob automatically only when resource-kopia proves a disposable orphan candidate. | The operator's verified-human 2026-11-04 approval covers future q-blob restores, but DBM still treated a missing blob only as a generic repository failure. | Diagnosis binds one canonical q-blob ID. Under the destination identity/operation lease, DBM requires resource-kopia proof of exact ID/hash/size, absent final target, read-only source and successful overlay listing; it commits that hash only, verifies a fresh snapshot listing, publishes a result notice, then retries the affected plans. Any missing or unsafe proof falls through to the existing one-decision path. | Revisit if the operator revokes the standing q-blob authorization or the resource-kopia candidate proof/commit contract changes. |
| 2026-11-19 | DBM owes both the usage and improve skill roles; no governed repair program is introduced yet. | DBM has five dependent scenarios (`infrastructure-manager`, `money-ledger`, `offer-desk`, `research-desk`, `secrets-manager`) and is a coverage source for the `infra-health` team, so the improve trigger is met even though `skill-set validate` reports only structural facts. The repair workflow is rare, destructive, and operator-confirmed, so it does not yet meet the recurring multi-operation threshold for a program. | `skills/data-backup-manager/SKILL.md` is the usage role; `skills/data-backup-manager-improve/SKILL.md` is the improve role; both are declared in `.vrooli/service.json`. The improve board records `setpoint-read` as a setup gap and routes its implementation to `program-runtime` when authorized. The repair path stays a script under `safe-operator-script` until it repeats unchanged. | Promote the repair workflow to a governed program after the same migration runs twice with stable inputs and joins; implement `setpoint-read` before claiming an executable improvement loop. |
| 2026-11-18 | A filesystem this host cannot repair is not admitted as a new destination without an explicit operator acknowledgement, and a repair the platform cannot perform is never offered. | The Elements drive's six unreadable entries all date from one ~10-second write burst (2026-11-10 05:04:41–50) of ~21 MB temp uploads. An interrupted write left inconsistent NTFS MFT records; `ntfsfix -d` resets the journal and schedules a Windows chkdsk that never runs, so the records stayed broken. DBM then offered "repair", ran `ntfsfix`, and reported the drive repaired — a fix that never happened. Because Linux has no tool that repairs arbitrary NTFS MFT records, adding a new NTFS destination recreates the same unrecoverable-after-one-crash risk. | Creation of a filesystem whose profile is not a real metadata repair on this host (NTFS on Linux) is refused unless `acknowledge_unrepairable_filesystem` (`--allow-unrepairable`) is set. `OffersFor` only offers repair when the profile can resolve the cause (a read-only mount for NTFS; any cause for ext4/exFAT/FAT). The question instead recommends a fresh set and names the real remedy. Readiness reports a `filesystem_repair` check so the CLI/UI can say "this host cannot repair this filesystem" without re-deriving it. | Revisit if a Linux NTFS tool gains real metadata repair, or if the host gains a Windows repair path. |\n| 2026-11-18 | The durable backup filesystem on a Linux-only host is ext4; NTFS is a temporary/import format, not a target. | ext4 replays its journal on mount and has `e2fsck`, so an unsafe shutdown is recoverable without a person or another OS. NTFS on Linux has neither: one interrupted write can leave MFT records that no local tool can repair, which is exactly the state the Elements drive reached. The requirement "safe even after an unsafe crash" cannot be met on NTFS here. | New destinations should be ext4. `destinations repair-options` states whether the current filesystem is repairable and, when it is not, prints the exact copy → `mkfs.ext4` → restore → `bind-recovery-identity` sequence. The destination id and plan bindings survive the conversion because the bundle path is preserved and only the volume UUID changes. `destinations safe-eject` flushes and unmounts before a copy or unplug. | Revisit if the drive must be shared with Windows; then use exFAT (repairable via `fsck.exfat`) or accept the NTFS risk explicitly. |\n| 2026-11-18 | Write admission is decided by one verdict and physical probe; copy count never gates a write; the degraded-policy layer is removed. | `DegradedDestinations` required another verified copy on a different device before an unobservable filesystem state could be written. That conflated a drive-loss risk with writability: a single-copy NTFS target was blocked entirely, so the data gained no new copy. The policy was also a second truth threaded from preflight to the write gate and retention. | `EvaluateWriteVerdict` is the only decision: corruption evidence (dirty/needs-check), read-only, write protection, or a failed probe blocks; an unobservable state with a passing bounded probe is a degraded warning. The write gate always probes. `AllowDegraded`, `DegradedDestinations`, the runs-side device-key computation, and the seam's boolean parameter are deleted. Copy count is reported once by coverage. | Revisit only if a real corruption signal appears that the probe cannot see. |\n| 2026-11-18 | A repair that the platform cannot perform is shown honestly and not recommended again; no standing grant for destructive repair and no inferred off-host level. | On this host NTFS repair is a dirty-flag reset, so recommending repair for metadata damage promises what the tool cannot deliver, and the operator was asked repeatedly. Off-host independence has no trustworthy evidence source in a single-host deployment (backend names and URLs are explicitly not identity), so claiming it would be false; a standing unattended-repair grant would add a new destructive authority for a repair that cannot fix the actual fault. | The diagnosis carries `RepairLimitation`/`RepairRemedy` from the drive profile; when repair cannot resolve the cause, the question recommends a fresh backup set and names the real remedy (`chkdsk /f`, or a filesystem this host can repair). `physical_independence_proven` is deprecated and stays false; same-host drives are reported as "protects against losing one drive, not the host". Destructive repair still requires a verified human decision. | Add off-host only with a real endpoint-identity source; add a standing grant only if a filesystem whose repair is a true metadata repair is in use and the operator explicitly asks for unattended repair. |\n| 2026-11-18 | Protection is graduated by storage device; filesystem behaviour is one shared table; coexistence is allowed but managed names are type-guarded; only leftover temp files self-heal. | The prior model called a target "physically independent" only when two destinations were on different hosts or a provider-hosted endpoint, so two real drives on one machine never counted and every target read as unprotected. Readiness, remediation, setup, and the UI each carried their own filesystem switch, so NTFS/exFAT behaviour could drift. A new destination on NTFS/exFAT was refused because the OS exposes no cleanliness signal, making a usable drive impossible to add. | Coverage classifies successful copies by distinct device key: two or more devices = protected, one = single-copy warning, none = unprotected. `packages/driveprofile` is the single table for check/repair tool, state signal, suitability, and next action; the control plane and DBM both read it. Creation accepts a profiled filesystem with an unobservable state; the write gate still decides admission. `FSBundleWriter` refuses a managed name occupied by the wrong type and never deletes foreign files. The worker auto-accepts only `leftover_temp`/EIO session markers (`DBM_AUTO_ACCEPT_LEFTOVER_TEMP`, on in production) and still asks for snapshot data. | Revisit if off-host/provider-hosted evidence is wired (add a distinct level), or if a standing human grant for destructive repair is introduced. |
| 2026-11-18 | Preflight owns the degraded-write policy and the executor consumes it; nested bundles are allowed; the host-volume lease is bounded and group-killed. | Round 2 found three divergent truths: preflight probed repositories through the write gate, the executor re-derived degraded readiness inside `resolveForUse`, and the locator check compared bundle roots. A legacy destination also had no persisted identity, so a real second copy could never count. Each produced "ready" preflight followed by blocked or `repository_invalid` writes, and a hung lease froze a run with no heartbeat. | `WithResolvedDestinationForWrite(ctx, id, allowDegraded, use)` is the single write gate, fed by `preflight.Result.DegradedDestinations`. `resolveForUse` uses `EvaluateWriteVerdict`. Preflight/health/usage use `WithResolvedDestinationForRead`. `destinationDeviceKey` falls back to the current mounted-filesystem identity. Collisions compare repository paths and exact bundle roots. The lease handshake is bounded and the process group is killed on release/cancel. | Revisit if the control plane makes the lease holder die with its parent, or if a destination gains a durable identity that makes the runtime fallback unnecessary. |
| 2026-11-18 | Snapshot identity is tag-first with a legacy source-suffix fallback; capacity separates immediate admission from the retention forecast; read access is separate from write readiness; unknown native filesystem state may degrade only with a passed write probe and a separate verified copy. | Live repositories contained hundreds of snapshots, which hit a 128-manifest cap; Kopia stores tags as a `tag:`-prefixed object, but the engine decoded only arrays, so every tagged snapshot looked unattributed; legacy snapshots identify the target as a `:/owner/name` source suffix. Capacity treated the sum of GFS tiers as full-copy multipliers, blocking 218 targets on a destination with ample incremental headroom. Read-only snapshot/usage calls also required write-ready filesystem evidence, so a mounted-but-unknown NTFS volume could not even be inspected. | `SnapshotList` is bounded by bytes (32 MiB) rather than manifest count and normalizes both Kopia tag shapes; `ListTargetSnapshots` selects by exact tags or the legacy source suffix and never fails on unrelated inventory. `internal/capacity` owns one pure admission model (first copy vs measured increment, reserve, advisory vs strict forecast). `WithResolvedDestinationForRead` proves identity, mount, bundle, containment and repository readability without requiring clean/rw state. `EvaluateWriteVerdict` is the explicit write state machine; `unknown` stays unknown unless `AllowDegraded`, a passed bounded write probe, and another verified copy are all present. | Revisit if Kopia changes its tag representation, a platform exposes a trustworthy native clean state, or a destination has no separate verified copy and the operator wants a different degraded policy. |
