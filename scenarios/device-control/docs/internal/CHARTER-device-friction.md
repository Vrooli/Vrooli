If we can't utilize our full ecosystem efficiently and powerfully then that's a big gap because then it seems more like we have a bunch of disconnected applications rather than one self improving ecosystem."

Go-ahead: "I think if you do all of these properly and also put significant effort into driving down debts and complexity and friction and gaps with [device] control. Also cleaning things up, removing things that don't need to be there, making implicit state machines explicit, replacing regression tests with gherkin tests, improving screaming architecture, all the sorts of tricks we use to make things more professional and more reliable. Do all your recommendations, but also go above and beyond."
(The operator's dictation wrote "voice control"; it means device control. Speech/voice scenarios are out of scope unless you find a direct dependency.)

Standing rules that apply (from operator memory): never use git; never bulk-run formatters across modules; dependencies only via scenario-dependency-analyzer; commits are never a gate; do not revoke node privileges; mockups and RCL are a floor; test the desired behaviour, not the current implementation; "improve test quality" = infra (generators, helpers, constants), net test LOC should drop; deliver decisions (DECISIONS.md with alternatives + switch costs), not just artifacts; dirty working tree is shared context, not a freeze, but coordinate with the other owner and never reset others' work. Lifecycle only via `make start`, `make test`, `make logs`, `make stop`, or `vrooli scenario ...`. Tests via `vrooli scenario test <name> --phases ...`, wait once with `test-genie runs wait --json`, never poll. A real TV and two Android phones are on the LAN, so validate on real devices where safe (never send disruptive commands to a household TV beyond wake, home, screenshot and app-launch the operator asked for).

## Outcomes
A. (device-control owner) Each of: screenshot, record, open-app, wake/home, state-read of a named TV or phone completes in ONE obvious call from a cold agent; capability gaps always carry the exact next command; ADB-over-network is a first-class, durable transport of the same physical TV (relation confirmation flow, ADB rung in connect, no second ephemeral identity); wake-before-capture handled inside the verb; evidence retrievable by CLI; compact list default; skill description/tags/command summaries/programs rewritten in user vocabulary (TV, Google TV, phone, Android, screenshot, record, open app, test on device); programs added for observe and app launch that reuse/generalize existing ones. Then go above and beyond: audit device-control for debt, dead code, duplicated logic, implicit state machines (lease, onboarding ladder, transport/identity lifecycle, capture/screen state) made explicit and tested; replace regression-style tests with Gherkin scenarios per `docs/TESTING.md`; improve package structure toward screaming architecture; simplify docs; net code and test LOC should go down where possible. Real-device validation on the TV and phones.
B. (search-hub owner) Make discovery a measured number: add golden eval cases (the 12 queries above plus a phone/app-testing set and a handful of other cross-scenario "do X" intents) to the relevant provider suites (`search-hub evals`), establish a baseline, and prove recall improves after A's description/program changes land (coordinate through shared files, not by editing device-control). Fix `--group` (accept a scenario name mapped to providers that hold that scenario's leaves, or fail loudly with a suggestion; never silent-empty). Investigate and fix or honestly document the unavailable classifier and why `prompt-manager.skill` returned 0 hits when queried alongside other types. Investigate the "CLI rebuilt ... restarting" tax in agent sessions (find the owning control-plane path; fix at the owner, do not paper over). Add a generic guard so any scenario whose skill/command descriptions don't recall its own core intents is visible (e.g. an eval-coverage gap report), then use it to list other scenarios with the same defect. Also reduce debt/complexity in search-hub as you find it.

## Boundaries (to avoid collisions)
- Device-control owner writes under `scenarios/device-control/**` (incl. its skills, programs, docs) and any control-plane/shared piece it must change for the transport model (state why).
- Search-hub owner writes under `scenarios/search-hub/**`, `scenarios/prompt-manager/**` provider config/search.json only if needed, and the control-plane CLI-rebuild owner path. It must not edit device-control files; it files requests to the device-control owner via SendMessage.
- Both: read the other's changes before editing shared files; re-verify after concurrent edits.
