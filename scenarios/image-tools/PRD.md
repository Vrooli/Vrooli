## 🎯 Overview
Purpose: image-tools is a local-first, capability-primitive scenario in Vrooli's `*-tools` family (alongside audio-tools, text-tools, data-tools). It delivers permanent, reusable image operations across four domains: (1) deterministic editing (zero-download, instant), (2) AI generation and editing, (3) AI enhancement and restoration, and (4) image-to-data analysis. Every operation runs fully headless from the CLI; the UI is an enhancer, not a gate; and heavy AI models spin up only on demand with hardware-aware selection.

Target users: End users needing a professional image toolbox; automation agents and other scenarios requiring programmatic image operations; and Vrooli scenarios that compose image-tools as a building block (campaign-content-studio, landing-page-business-suite, palette-gen, and future rich-media-studio).

Deployment surfaces: Go CLI (full parity, headless-complete); React+Vite+TypeScript+Tailwind UI (mobile camera capture, drag-and-drop, desktop clipboard paste, before/after slider, progress-with-cancel); Connect-RPC/REST API; automation hooks (batch processing, watch-folder, optional per-job signed webhook callbacks).

Value proposition: One permanent, reusable image capability the entire Vrooli system builds on. Cheap deterministic ops work instantly with zero downloads. AI ops are opt-in with CPU-capable defaults so the same scenario runs on a tiny laptop or a large GPU server. Hardware-aware model selection, a GPU-serializing async job queue, and a graceful Local-GPU → Local-CPU → BYOK-cloud fallback chain ensure reliability at every tier. Every other scenario that needs image work composes this one instead of reinventing it. image-tools is also a polished, standalone product in its own right — usable directly for manual, professional image work and deployable/monetizable on its own — while remaining the primitive that higher-level scenarios (branding-manager, AI-UGC content studios, rich-media-studio) compose. The UI is genuinely production-grade, not merely a thin enhancer over the headless core (the headless-completeness tenet still holds).

## 🎯 Operational Targets

Operational targets are measurable outcomes; checkboxes may auto-update based on validation.

### 🔴 P0 – Must ship for viability
- [ ] OT-P0-001 | Deterministic Editor Ops | All resize/crop/rotate/flip/straighten/deskew, format conversion (PNG/JPEG/WebP/AVIF/HEIC/GIF/TIFF/BMP, SVG→raster), compress/optimize with target-file-size, brightness/contrast/exposure/saturation/vibrance/hue/white-balance/levels/curves/gamma/shadows-highlights, filters and effects (grayscale/sepia/invert/blur/sharpen/vignette/noise/posterize/threshold/duotone/LUT), canvas ops (pad/extend/border/fill/letterbox), composite/overlay (merge, image+text watermark, text overlay, shapes/annotations), thumbnail generation, and metadata (EXIF/IPTC/XMP read, GPS-off-by-default strip, ICC convert, auto-orient) run zero-download and instant from the CLI with no UI and no ComfyUI dependency.
- [ ] OT-P0-002 | Core AI Generation & Editing | Text-to-image (seed control, N variations, size presets), image-to-image, inpaint (mask/box/text-guided), and object removal are all available via CLI and API through at least one standalone non-ComfyUI backend per operation, with ComfyUI accepted as an optional plug-in when already installed.
- [ ] OT-P0-003 | Core AI Enhancement | Upscale/super-resolution (CPU-capable default model), background removal (CPU-capable), and denoise/deblur/unblur are available headless via standalone backends with no ComfyUI requirement and a CPU fallback model installable on demand.
- [ ] OT-P0-004 | Core Analysis | OCR/text-extraction, NSFW/safety classification (standalone op plus configurable auto-scan of AI-generated output), and image info/probe are available from the CLI and API with no GPU requirement.
- [ ] OT-P0-005 | Backend Abstraction & Provider Interface | Every operation exposes a per-op provider interface with at minimum one standalone-lightweight backend; ComfyUI is a second optional provider; BYOK-cloud is a third fallback tier; CPU fallback is guaranteed for every AI op; the system enforces ≥1 standalone backend per operation at registration time.
- [ ] OT-P0-006 | Declarative Model Registry | A schema/proto-validated model registry stores per-entry id/name, operation(s) served, backend/provider, variant+quant+size, hardware requirements (min VRAM, min RAM, GPU-required, CPU-capable, OS/arch), supported input/output dimensions, content-capability labels (NSFW-capable, license + commercial-use, base-model lineage, known-risks), download source + checksum or local path, enabled flag, and default-for-operation marker; a selector picks the best-fit enabled model for the probed host, honoring per-op default and user override.
- [ ] OT-P0-007 | Model Management | CLI and Settings UI allow list/search/install/enable/disable/remove of models with per-model size, hardware-fit indicator, license, and capability labels; downloads are checksummed and opt-in; disk-space awareness is enforced; custom and fine-tuned local-model entries are supported.
- [ ] OT-P0-008 | Hardware-Aware Selection | Host capability is read via the root `vrooli host inventory --json` CLI (the shared `internal/hostinventory` collector), consumed through `packages/vrooli-cli-go` behind the `capabilities` seam (`CapabilityProbe`/`CLIProbe`, with a `FakeProbe` for tests); cheap deterministic ops work with zero downloads; every AI op ships a CPU-capable default standalone model as its opt-in install; the selector surfaces "needs ≥X GB VRAM" and time-warning messages when falling back.
- [ ] OT-P0-009 | Durable Async Job Queue | Jobs are server-owned and survive client disconnect; submission returns a job-id and ETA up front; CLI uses a block-once wait verb; UI uses SSE for live progress; heavy GPU jobs are serialized in a dedicated queue; cheap CPU ops run concurrently; the run-lifecycle mirrors the test-genie philosophy (no polling).
- [ ] OT-P0-010 | Persistent Storage & Output Ownership | Image binaries are stored via api-core storage/blobstore by default (outside repo); save location is overridable per request; outputs are user-owned and can be copied, moved, or deleted anywhere.
- [ ] OT-P0-011 | Graceful Fallback with Clear Messaging | Local-GPU → Local-CPU → BYOK-cloud fallback is automatic with explicit user-visible messaging at each tier transition, including hardware-fit indicators and BYOK cost estimates before cloud ops execute.
- [ ] OT-P0-012 | Observability Measures | cli/manifest.json measure blocks (enforced by the test-genie measures phase) capture per-model op latency (p50/p95), throughput, queue wait time, fallback-tier usage, and VRAM headroom at run time.
- [x] OT-P0-013 | Full-Parity Surfaces | React+Vite UI (mobile capture/upload, before/after slider, progress-cancel), Go CLI (complete headless parity with UI), and Connect-RPC/REST API all expose the full operation set with no ops gated behind a single surface.
- [ ] OT-P0-014 | Functional AI Substrate (Real Model & Backend Provisioning) | `models install` resolves and fetches the REAL weight asset(s) per model and backend file layout, validates the downloaded artifact (type/magic/size — not just self-checksum), and pins an upstream-verified checksum; a backend-program provisioning/detection path exists (or each op's CPU default is a provisionable pure-Go/ONNX backend); the selector reports runnable-vs-declared honestly; and at least one AI op runs end-to-end on CPU from the CLI and UI. Closes the validate-first gap — the prior install path fetched landing pages, not weights, so no AI op actually executed (see `docs/internal/PROBLEMS.md` 2026-06-18).

### 🟠 P1 – Should have post-launch

- [ ] OT-P1-002 | AI Enhancement Breadth | Colorize (B&W→color), old-photo restore, face restoration (standalone op), Segment Anything (SAM), and depth/normal map generation are available via opt-in model installs with CPU-capable defaults where feasible.
- [ ] OT-P1-003 | Analysis Breadth | Caption/alt-text (vision model), object detection/tagging, anonymous face detection (count + bounding boxes, no recognition), quality assessment (blur/resolution/score), duplicate/near-duplicate detection (perceptual hash), semantic embedding generation for image search, and QR/barcode read are all available from CLI and API.
- [ ] OT-P1-004 | Recipes & Pipelines | Users can save, name, and replay multi-step operation graphs (recipes) where the visual op-stack in the UI and the CLI pipeline are a unified representation; ComfyUI-style chaining is supported without ComfyUI being required.
- [ ] OT-P1-005 | Batch Processing & Watch-Folder Automation | Batch processing accepts glob patterns and folder inputs; watch-folder automation triggers configured recipes or single ops on new files with configurable debounce and output routing.
- [ ] OT-P1-006 | Webhook Callbacks | Each job accepts an optional signed callback URL; the system delivers a best-effort POST with retry on completion or failure; this is not an event bus and carries no additional pub/sub infrastructure.
- [ ] OT-P1-007 | Safety & Provenance | C2PA content credentials signing of AI-generated and AI-edited output is available as an opt-in setting (off by default); BYOK cost tracking surfaces a cost estimate before any cloud operation executes.
- [x] OT-P1-008 | Light Non-Destructive Editor Layer | The UI exposes an op-stack with undo/redo over the headless op core; interactive canvas widgets (mask-painting for inpaint/object-removal, drag-box for crop, brush for background-removal touch-up) are present only where the op benefits; all ops remain fully headless via mask file, coordinates, or text prompt.
- [ ] OT-P1-009 | Image Diff & Visual Comparison | A general-purpose image diff/visual-comparison capability is built as a first-class operation so test-genie can later adopt it without duplication.
- [x] OT-P1-010 | Meme & Preset Templates | A small set of compositing presets and meme-style text-overlay templates are available from the UI and CLI for quick social-content use cases.
- [ ] OT-P1-011 | Naturalize (De-Plasticize / Realism) | A first-class enhancement op reintroduces realistic skin/texture/grain to over-smoothed (restored/upscaled) images, with a fidelity↔realism knob and optional face-aware emphasis; CPU-capable default; full CLI/API/UI parity; auto-suggested after upscale/restore. The lowest consent-weight human edit and the first new feature built after the OT-P0-014 provisioning foundation.
- [ ] OT-P1-012 | Look / Style Library | A data-defined, thumbnail-backed, AI-aware library generalizing presets (OT-P1-010) + recipes (OT-P1-004): a Look compiles to {prompt + optional mask/selection + backend params}; adding a Look auto-generates its preview by applying it to a reference image; a UI picker (modal or full-page drawer) presents thumbnails; film/lens/camera-emulation looks may be pure-deterministic.
- [ ] OT-P1-013 | Smart-Select → Classify → Contextual Edit | A SAM-backed segment op + region classification feed a canvas selection tool that snaps to an object silhouette, classifies the region, and offers a context-specific edit menu compiling to an inpaint/instruction-edit {mask + prompt}; keyboard/file fallbacks preserved (no pointer-only op).
- [ ] OT-P1-014 | Instruction-Edit Model Class | An instruction-edit op + model class (Flux-Kontext / Qwen-Image-Edit-style) for identity-preserving, prompt-only semantic edits ("make him older", "change the jacket"), distinct from img2img (global+strength) and inpaint (masked); local on a capable GPU, BYOK-cloud as the CPU/low-VRAM path with hardware-fit + cost surfaced up front.
- [ ] OT-P1-015 | Responsible-Use Deployment Gate | Editing real people is gated at DEPLOYMENT, not at the capability: public/monetized deployment requires NSFW/CSAM auto-scan on by default, C2PA provenance on by default (≥ real-person edits), a published Acceptable-Use Policy, a consent affirmation + logging on identity-altering ops, and abuse rate-limiting; local/personal use is unrestricted and the hard non-goals remain enforced.

## 🧱 Tech Direction Snapshot
Preferred stacks: Go API server with Connect-RPC (proto-owned contracts) and a REST multipart edge for opaque binary uploads; React+Vite+TypeScript+Tailwind for the UI; Go CLI. Standalone AI backends: rembg (background removal), realesrgan-ncnn-vulkan (upscale), stable-diffusion.cpp or a small diffusers runner (text-to-image/img2img/inpaint), LaMa (object removal), GFPGAN/CodeFormer (face restoration), SAM (segmentation), Tesseract (OCR), small classifiers (NSFW/caption/detection/quality), perceptual hash library (duplicate detection). ComfyUI is an optional plug-in provider only.

Preferred storage: SQLite for scenario metadata (jobs, recipes, model registry state, measures); image binaries via api-core storage/blobstore (outside repo, overridable save location per request); metadata stays proto-typed; opaque binary uploads handled on the REST multipart edge.

Integration strategy: Shared workflows > resource CLI > direct API. Hardware capability and capacity are read from the root `vrooli host inventory --json` CLI (the shared `internal/hostinventory` collector), consumed through `packages/vrooli-cli-go` behind the image-tools `capabilities` seam; the prerequisite is extending the root CLI `cli/v1` host-inventory contract (GPU/VRAM/CPU/os) and building that seam (Phase 0, already done) — image-tools does not depend on system-monitor. Heavy resources (ComfyUI, per-op model resources) declared required:false with /ready gating; idle-shutdown delegated to the platform orchestrator (mirrors the audio-tools optional-resource pattern). BYOK cloud is a third-tier fallback provider; cost-tracking pattern reused from audio-tools. palette-gen is delegated to for palette extraction; image-tools owns image→text/OCR, text-tools owns document→text (boundary is clear and non-overlapping).

Non-goals: No face recognition or identity matching. No face-swap, deepfake, or virtual try-on. No video or motion content (belongs to rich-media-studio). No heavy model running by default. No reinvention of OS/hardware detection (owned by the platform `internal/hostinventory` collector, surfaced via the root CLI host-inventory contract) or persistent storage (owned by api-core). SVG is treated as an import/export raster format only; no vector editing.

## 🤝 Dependencies & Launch Plan
Required resources: claude-code (or configured agent) only where AI authoring or capability labeling is needed; no hard external dependency for deterministic ops. Optional resources: ComfyUI (opt-in backend, required:false), per-op model resources (required:false, on-demand with /ready gating), BYOK cloud providers (optional third-tier fallback).

Scenario dependencies: palette-gen (palette extraction delegated here; image-tools calls palette-gen rather than reimplementing); text-tools (boundary peer: image-tools owns image→text/OCR, text-tools owns document→text; no overlap). Host hardware facts are not a scenario dependency — they are read from the root `vrooli` CLI host-inventory contract (the shared `internal/hostinventory` collector) via `packages/vrooli-cli-go` behind the `capabilities` seam; system-monitor is not used.

Operational risks: GPU detection is currently strongest for NVIDIA; AMD/Intel/Apple-Silicon hardening is real engineering work deferred to P2 in the platform `internal/hostinventory` collector (surfaced through the root CLI host-inventory contract). Model download size and disk pressure require disk-space awareness and user confirmation before installs. GPU contention is mitigated by the serializing heavy-job queue but remains a risk under concurrent agent workloads. BYOK cost surprises are mitigated by the mandatory pre-op cost estimate but require ongoing provider-rate maintenance. Webhook callbacks are new infrastructure surface; keeping them minimal (signed URL + best-effort retry, no event bus) contains the risk. NSFW/safety classification accuracy is model-dependent; auto-scan is configurable and not a hard block by default. Large-image memory safety (decompression bomb) must be enforced at the ingestion boundary.

Launch sequencing: (1) extend the root CLI `cli/v1` host-inventory contract (GPU/VRAM/CPU/os) + build the image-tools `capabilities` seam consuming it via `packages/vrooli-cli-go` — prerequisite, already done (Phase 0); (2) deterministic op core + api-core storage integration + async job/queue infrastructure + model-registry/management spine — first real domain establishing the foundational primitive; (3) core AI ops via standalone backends (rembg, realesrgan, LaMa, sd.cpp, Tesseract, NSFW classifier) with hardware-aware model selection, CPU fallback, and BYOK tier — scenario becomes AI-capable; (4) P1 breadth ops (outpaint, bg-replace, colorize, face-restoration, SAM, caption, object detection, quality assessment, dup detection, embeddings, QR read) + recipes/pipelines + batch + watch-folder; (5) safety/provenance (C2PA opt-in, BYOK cost tracking, NSFW auto-scan hardening) + extras (meme templates, image diff/visual-comparison); (6) consumer integrations (rich-media-studio embeddable component, test-genie visual-diff adoption, AMD/Intel/Apple-Silicon GPU hardening).

## 🎨 UX & Branding
User experience: Clean, professional operational-console design language using the vrooli-default component kit. The UI is an enhancer over the headless core — interactive widgets (mask-painting canvas, drag-box crop, brush touch-up) appear only for the operations that genuinely benefit from direct manipulation; all other ops present as straightforward parameter forms. Before/after slider for enhancement ops provides immediate result validation. Mobile camera capture, drag-and-drop, and desktop clipboard paste are all first-class upload paths. Progress indicators include cancel controls and ETA for long-running async jobs. Model capability labels (size, NSFW-capable, license, hardware-fit) are surfaced at point of use so users make informed install decisions. Fallback-tier transitions and hardware warnings are displayed inline, not buried in logs.

Visual design: Consistent with Vrooli's operational-console aesthetic — simple, polished, works equally well on mobile and desktop. PWA install surface is maintained: ui/public/site.webmanifest, apple-icon-180.png, favicon-196.png, and maskable manifest icons remain valid. Generic placeholder icons are replaced with product-specific branding when Vrooli brand assets are available. Light and dark theme support via the vrooli-default kit theming primitives.

Accessibility: WCAG AA target across all UI surfaces. Full keyboard navigation for every operation and control. The caption/alt-text generation feature directly reinforces the platform's own accessibility posture. All template a11y primitives are preserved: role attributes, aria-* labels, and data-testid selectors for automated testing. i18n wiring is maintained throughout so localization can be added without structural changes. Interactive canvas widgets (mask brush, crop drag-box) include accessible fallback input paths (coordinate entry, file-based mask upload) so no operation is exclusively pointer-driven.
