# CLI Commands — Music Tools

> **Status (2026-09-19): composition commands are shipped headlessly.** The
> current CLI exposes styles, composition submission, style compilation, jobs
> wait/get/list/cancel, take listing and transitions, and pool
> draw/status/configure. Analysis, models, and
> durable infrastructure commands remain in the implementation plan.

Scenario-state and model operations run through the API. The bounded
`delivery arrange` file operation runs locally because its inputs are caller-local
media, not server paths. It starts no resources, writes no scenario state and
selects no takes. It is an explicit local-file exception, not a second job queue.
Move remote artifact arrangements into the server-owned job domain when required.

The CLI binary is built from `cli/`, installed by `make setup` to
`~/.vrooli/bin/music-tools`, and rebuilt automatically when its
sources change (cli-core's stale-detection rebuilds before any command
that touches the API).

## Source of truth: `cli/manifest.json`

The CLI's command surface (groups, commands, positionals, flags,
RPC bindings, governance metadata) is declared in
[`cli/manifest.json`](../../cli/manifest.json) and validated against the
project CLI-manifest schema (`path:.vrooli/schemas/cli-manifest.schema.json`)
(schema id `cli-manifest/v1`). The manifest is loaded at startup by
`cliapp.LoadFromManifestPrimitives`, which:

- builds each domain's `SubcommandGroup` from its manifest group
- wires each command's `binding.method` (e.g.
  `<Domain>Service.List<Entity>`) to a cli-core **primitive** registered in the
  domain's `register.go` bindings map (`cliapp.ProtoList` / `ProtoMutation` /
  `ProtoOperational`, each a `<name>Call` + `<name>Report` pair). The
  `<name>Call`/`<name>Report` funcs take a narrow `cliapp.OperationContext` — no
  `JSON()`, no renderers — so an operation *cannot* branch on the output format;
  renderer separation is enforced by the callback signature, not convention
- attaches the primitive's observed evidence to each command and **fails loudly
  if it disagrees with the manifest's `architecture.primitive` declaration** —
  this is what makes the declared L4 maturity *verified*, not self-certified
- fails loudly on missing handlers, dead handlers, or unknown groups

Declaring `architecture.primitive` in the manifest is intent; building the
handler with the matching primitive here is the proof. That proof is captured as
a committed **static** artifact: `.vrooli/generated/cli-primitive-evidence.json`
(schema `cli-primitive-evidence/v1`), generated from the assembled command tree
(no command is executed) and regenerated by the golden test in
[`cli/evidence_test.go`](../../cli/evidence_test.go) (`UPDATE_CLI_EVIDENCE=1`
rewrites it; scaffolding writes it once via a template postHook). CLI Health reads
that committed file **statically** to verify each declared primitive — it never
runs your commands. A declaration with no matching evidence is advisory
not-yet-verified debt, a mismatch is a gating error, and a stale/missing artifact
keeps declared primitives unverified. See the CLI architecture maturity
reference (`path:scenarios/cli-health/docs/reference/cli-architecture-maturity.md`).

Per-domain tests use `cliapp.RequireProtoServiceCoverage` to assert
that every RPC on the bound proto service either has a manifest command
binding or appears in the manifest's `omitted[]` list with a reason —
adding a new RPC without exposing it as a CLI command (or explicitly
omitting it) fails the test.

The manifest's `governance` block (`effect`, `run_eligible`,
`permissions`, `requires_confirmation`) is consumed by prompt-manager
to derive action certainty automatically; scenarios that adopt the
manifest don't need hand-classified action-safety lists.

`binding.kind` is currently `connect-rpc` only. REST-exception
commands (for example, a multipart file-upload command whose request
body carries opaque bytes) are appended to the loaded group outside the
manifest path in the domain's `register.go` and documented in the
manifest's `omitted[]` array.

For environment-variable precedence and CLI config-file shape, see
[`configuration.md`](configuration.md).

## Global flags (provided by cli-core)

Every command supports the following flags. **Do not reimplement them
in scenario commands.**

| Flag | Purpose |
|---|---|
| `--api-base <url>` | Override the API endpoint for this invocation |
| `--auto-start` | Run `vrooli scenario start music-tools` if the API is unreachable |
| `--json` | Emit machine-readable JSON instead of the human report |
| `--no-color` | Disable ANSI color (also respects the `NO_COLOR` env var) |
| `--color` | Force-enable color (overrides terminal detection) |
| `--help`, `-h` | Show command help |
| `--version`, `-v` | Show the CLI version |

## Built-in commands (auto-provided by `cli-core`)

### `music-tools status`

Health check. Calls `GET /health` and renders status + dependency
details. The output uses the **operational contract**:
`Status → Triage → Next Steps`.

```bash
music-tools status
music-tools status --json
```

### `music-tools configure <key> <value>`

Persist a setting to the per-user CLI config file (location resolved
per [`configuration.md`](configuration.md#cli-config-file)).

```bash
music-tools configure api_base http://localhost:15001/api/v1
music-tools configure token <token>
```

Read values back without an argument:

```bash
music-tools configure api_base
```

## Scenario commands — `<domain>`

Each product domain exposes its commands as a subcommand group
(`music-tools <domain> <verb>`). Every command calls a single API
endpoint and renders the result through one of the three output
contracts below. Document your domain's commands here as you build
them, one row/section per command, mirroring the endpoints they call
in [`api-endpoints.md`](api-endpoints.md).

The scaffold ships one fully worked CRUD command group as a copyable
reference (see the fenced example below); `template-manager detemplate
<scenario>` removes it once your real domains are green.

### Command surface and planned extensions

The first composition commands are implemented. The remaining rows are recorded
so the domain vocabulary stops being re-invented per conversation, and so
`DOMAINS.md`'s twelve domains have a concrete CLI shape to be measured against.
Requirement IDs are from
[`../../requirements/`](../../requirements/); every one is `status: planned`.

| Command | Domain | Requirement | Notes |
|---|---|---|---|
| `music-tools compose --style <id> --takes <n> [--seed <int64>] [--shift <1..5>]` | composition | `MUS-P0-012`, `MUS-P0-013` | Produces **N takes**, not one track — see the 2026-09-18 batch decision in [`../internal/DECISIONS.md`](../internal/DECISIONS.md). `--takes` defaults above 1. |
| `music-tools styles {list,get,create,compile}` | styles | `OT-P0-007` | A style compiles to a caption plus parameters. This is the unit a batch and an inventory are configured with. |
| `music-tools takes {list,get,reserve,consume,release,discard}` | composition | — | The reservation lifecycle in [`../concepts/DATA.md`](../concepts/DATA.md#the-reservation-lifecycle). `release` is the "give me a different one" path and must be cheap — it regenerates nothing. The scenario records what was reserved and passed over; it does not infer preference from it. |
| `music-tools pool {status,draw,configure}` | composition | `OT-P1-005` | `draw` is the consumer's one-call path: reserve a ready take in a named style, or say the pool is empty. `configure` sets target depth and replenish threshold per style. |
| `music-tools analyze <track>` | analysis | `MUS-P0-009`–`011`, `MUS-P1-001` | One decomposition contract: embeddings, structure, beats, tempo/key with retained disagreement, loudness, tags. |
| `music-tools separate <track>` | transformation | `MUS-P1-003` | Owned by the `music-mir` runtime, never assumed from the composition runtime. |
| `music-tools ops {trim,fade,concat,convert,loudness}` | ops | `MUS-P0-002` | Deterministic; no GPU, no model download. |
| `music-tools models {list,install,remove,doctor,explain}` | models | `MUS-P0-003`–`005` | Must surface licence lane on every row (`experience/pages/models.json` treats lane as decision-critical, not metadata). |
| `music-tools jobs {get,wait,list,cancel,watch}` | jobs | `MUS-P0-014` | Durable, server-owned, survives client disconnect. |

Two shape constraints inherited from decisions, not preferences:

- **`compose` is a job submit, not a synchronous call.** It returns a job id and
  an ETA; callers block once on `jobs wait`. A ten-take batch is minutes of GPU
  time and cannot ride a request.
- **`jobs wait` is a durable attachment.** The CLI uses a no-timeout request for
  this one command, so the ordinary CLI HTTP deadline cannot interrupt a long
  composition batch. Caller cancellation still ends the wait without canceling
  the server-owned job; use `jobs get` to recover its durable state.
- **Composition parameters use the generated submit contract.** The current
  style-based path is REST JSON; audio retrieval is separate. See
  [`api-endpoints.md`](api-endpoints.md).

## Portable style files

`music-tools styles create --file style.json` and `styles import --file style.json`
send a direct portable Style document. Use the flat shape documented in
[`api-endpoints.md`](api-endpoints.md#implemented-style-json-ingress), with BPM,
duration and the other parameters at the top level. A legitimate legacy nested
`params` file is also supported. Unknown/mixed fields and trailing JSON fail;
they do not silently become a parameter-free style. The portable ingress bound
is1MiB. Compilation, not draft creation, requires positive BPM and duration.

For a file using the example ID `driving-rave`:

```bash
music-tools styles create --file style.json
music-tools styles compile driving-rave
music-tools styles export driving-rave > style-export.json
# Import under a new custom ID so the existing record is not shadowed.
music-tools styles import --file style-export.json --id driving-rave-copy
music-tools styles compile driving-rave-copy
```

Compilation exposes the caption and complete parameter tuple; inspect that
result before submitting a composition job. Exported flat JSON can also be
used as a create input. Normal server adoption is required for newly repaired
ingress behavior; the CLI already forwards the file's fields unchanged.

## Song lyrics and repeatable comparisons

Create/import a separate vocal style with an original UTF-8 lyrics file:

```bash
music-tools styles create --file song-style.json --lyrics-file original-lyrics.txt
music-tools styles compile my-song
music-tools styles export my-song > my-song-export.json
music-tools styles import --file my-song-export.json --id my-song-copy
```

`--lyrics-file` works on both create and import and explicitly overrides a `lyrics`
field already in the JSON file. It preserves text/newlines and rejects unreadable,
empty, whitespace-only or invalid UTF-8 files. Omit the option for a legacy/default
instrumental style, or use `"lyrics":"[instrumental]"`. There is no compose-time
lyrics override; export/import carries the style's lyrics.

```bash
music-tools compose --style driving-rave --takes 1 --seed 424242 --shift 1
music-tools compose --style driving-rave --takes 1 --seed 424242 --shift 3
# Attach once to each returned job ID:
music-tools jobs wait <job-id>
```

Omitting `--seed` chooses a fresh base once at admission; explicit `--seed 0` is a
repeatable base. Signed-int64 bases derive uint32 effective per-take seeds. Keep
caption/model/profile and duration fixed for a useful shift comparison. Omitted
`--shift` preserves the loaded profile default; explicit values must be finite1..5.
Inspect actual job `generation_profiles` and source-job lyrics intent before
selection. Older takes' actual seeds are unknown without the verified receipt.
Song intent does not certify audible vocals, language or quality; launch videos
must use instrumental intent and be auditioned for actual lyric/vocal absence.

## Output contracts

Every scenario command should render through one of three human
contracts. Proto-backed commands should use `cliapp.RenderProtoList`
or `cliapp.RenderProtoMutation`: human consumers see the report, while
`--json` consumers receive the proto JSON response shape.

| Contract | Used by | Structure |
|---|---|---|
| **Operational** | `status`, `health`, `audit`, `validate`, `doctor` | Status → Triage → Next Steps |
| **Data Retrieval** | `list`, `get`, `view`, `search` | Summary → Results → Retrieval Hints |
| **Mutation** | `create`, `update`, `delete`, `start`, `stop` | Result → What Changed → Next Command |

For commands that aggregate multiple API calls or produce a
non-proto report, use the `RunContext` render helpers directly
(`ctx.RenderList`, `ctx.RenderMutation`, or the operational report
helpers).

**`--json` is an output contract, never an operation selector.** Declare each
command's `architecture.primitive` in the manifest (`proto_list` /
`proto_mutation` / `operational` / `action`) and either bind the matching
cli-core primitive builder (`cliapp.ProtoList` / `ProtoMutation` /
`ProtoOperational`) or render inline with `RenderProtoList` /
`RenderProtoMutation` / `RenderProtoOperational`. Both keep the operation outside
any `if ctx.JSON()` branch — the top rung of CLI Health's command-architecture
maturity capability. Legitimate special cases (streaming, upload, passthrough,
external delegation, durable runs) go in the manifest's top-level `exceptions[]`.

## Adding a new command

For a new domain, copy the worked CRUD command group in the fenced
example above first, then replace it once your real domain is green.

For a command inside an existing domain:

1. If the command needs a new API endpoint (RPC), add it first per
   [`api-endpoints.md`](api-endpoints.md#adding-a-new-endpoint). The
   manifest's coverage test will fail otherwise on the next CLI build.
2. Add a command entry to the matching group in
   [`cli/manifest.json`](../../cli/manifest.json): `name`, optional
   `description`, `positionals` / `flags`, the `binding` (service +
   method), the `governance` block (`effect`, `run_eligible`,
   `permissions`, optional `requires_confirmation`), and an
   `architecture` block (`{ "primitive": "proto_list" | "proto_mutation"
   | "operational" | "action" }`) matching the command's renderer. The
   schema in `.vrooli/schemas/cli-manifest.schema.json` is authoritative.
3. Implement the handler in `cli/domains/<domain>/handlers.go` (or a
   focused sibling file) with signature
   `func(ctx cliapp.RunContext) error`. Read values with
   `ctx.Flag(...)`, `ctx.BoolFlag(...)`, `ctx.Positional(...)`, and
   `ctx.JSON()`.
4. Add the handler to the bindings map in
   `cli/domains/<domain>/register.go` keyed by `"<Service>.<Method>"`
   so `cliapp.LoadFromManifest` can wire it. Missing handler or
   dead handler both fail at startup.
5. Handler implementation should:
   - Construct generated Connect clients with
     `cliapp.NewConnectHTTPClient(core)` for proto-typed operations.
   - Use `cliapp.UploadFile` only for documented multipart REST
     exceptions (append those outside the manifest path in
     `register.go` and document them in the manifest's `omitted[]`).
   - Render proto-backed responses with `cliapp.RenderProtoList` or
     `cliapp.RenderProtoMutation`.
6. Add endpoint metadata in the API handler module and bind the method
   (or list it in `omitted[]`) in `cli/manifest.json`. Then run
   `make endpoints`; do not edit [`.vrooli/endpoints.json`](../../.vrooli/endpoints.json)
   by hand.
7. Add a row to this document.
8. Add a handler test in
   `cli/domains/<domain>/handlers_test.go` using `clitest.NewTestApp`
   + `clitest.NewAPIServer` + `clitest.CaptureStdout` (see
   [`../internal/TESTING.md`](../internal/TESTING.md)). Driving the
   handler via `cliapp.NewTestRunContextFromArgs` against the manifest's
   schema gives the closest parity with the dispatched path.

## Command structure principles

- **Subcommand groups** (`<domain> list`, `<domain> create`) over flat
  verbs (`list-<entity>`, `create-<entity>`). Discoverability via
  `--help` is the goal.
- **Positional for required, flags for optional.** `<domain> get <id>`
  not `<domain> get --id <id>`.
- **One command per API endpoint.** If you find yourself making two
  endpoint calls, the API is missing a use-case.
- **Error messages must be actionable.** "API unreachable" is bad;
  "API unreachable at http://localhost:15001 — try `--auto-start` or
  `vrooli scenario start music-tools`" is good.

## `music-tools delivery arrange`

```bash
music-tools delivery arrange --recipe arrangement.json --out arranged-v2
```

No API, GPU or model download is needed. Requires an existing FFmpeg. Output must
be a new directory. It contains `arranged.wav`, exact `recipe.json`, and
`receipt.json` with source/recipe/output SHA-256, sample count, rate and channels.
Listening remains `unreviewed`. File output is automation-shaped JSON so a video
production can bind exact sample arithmetic and provenance without parsing prose.

Recipe version 1:

```json
{
  "version": 1,
  "segments": [
    {"source": "take.wav", "start": 0, "end": 22.069},
    {"source": "take.wav", "start": 11.034, "end": 13.793},
    {"source": "take.wav", "start": 22.069, "end": 31.4}
  ],
  "crossfade": 0.02,
  "expected_samples": 1637712
}
```

Paths resolve beside the recipe; optional per-segment `sha256` pins source bytes.
At 48 kHz, stereo, these segments imply exactly 34.119 seconds. The program checks
the caller's expected sample frames against independently rounded segment sample
bounds minus overlap. It snapshots each regular source, decodes separately into bounded disk PCM
spools and crossfades fixed-size blocks; it does not use the split/trim/acrossfade graph that shortened an earlier
34.119-second arrangement to 23.115 seconds. Float gain uses linear crossfades;
output is 16-bit PCM. Listen to seams and dynamics before accepting the edit.

Limits: 1–32 segments, at most eight sources, 600 seconds of output, 128 MiB per
decoded source, 256 MiB total decoded source bytes, 90-second deadline, two FFmpeg
threads. Crossfade is 0–2 seconds and at most half any segment. Changed hashes,
invalid sample arithmetic, out-of-source trims and existing output paths fail.
Raw snapshot limits are 256 MiB per source / 512 MiB total. Interrupt cancels
owned copy/decode/mix work. Output publishes as a complete staged bundle under a
sibling `.arrange-lock` directory; existing destinations fail. Cooperating owner
writers honor the lock; arbitrary external rename races are not fenced. Hard
termination may leave owned scratch/lock paths requiring explicit inspection and
cleanup. Receipt includes decoder and algorithm identity. No lifecycle or shared-tenant action occurs.

## Operator audition

The Audition page uses actual take-audio endpoints, pauses other players when a
new one starts, surfaces playback failures and retains all candidates. Keep/reject
is a cut-specific review choice; it does not delete or reserve pool takes. An
operator confirms listening, adds notes and exports a JSON review. Audio is loaded once into a bounded immutable browser blob. Playback and export
use that same byte hash. Export records listener, time, take/job and provenance. It
cannot approve a later final-video mix or establish that an agent heard audio.

Audition lists at most 20 candidates at once; filter by job to select another
batch. A session retains at most 100 candidate findings and 256 MiB of encoded
audio (64 MiB/source); decoder/heap costs are additional. Unload playback bytes
without deleting source takes or hash-bound findings. Save/restore a bounded local
review draft explicitly. Export records cut identity (or explicit unspecified
cut), reviewer, source identity, listening time and actual findings. A playback
failure invalidates that candidate's listening attestation until resolved.

`takes list --job <id> --limit 100` covers the largest supported batch. The limit
is 1–100; filter by job/style for additional inventory. HTTP listing sets
`X-Music-Takes-Truncated: true` when the requested limit omits peers.

Get/Wait can return a persistence-unavailable error after successful media work.
Retry the same job read to finalize retained metadata; do not submit new model
work to repair a database outage. Durable List remains a database observation.

Pool inventory targets accept 1–100, matching a supported composition batch.
When authorized cleanup has removed an available candidate, selection records its
pool state as `unavailable` and requests refill using the existing threshold.
The take's provenance remains queryable. Job terminal caching is bounded; evicted
terminal jobs still support durable Get/Wait and one-result terminal subscription.
This does not delete jobs or their output media.
