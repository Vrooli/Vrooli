# Team Operating Contract Greenfield Redesign Implementation Plan

Status: draft for workshop refinement.

## Purpose

Redesign Prompt Manager team/member heartbeat prompting around a first-class **Team Operating Contract** so durable team policy lives in one structured source of truth and heartbeat prompts receive a compact resolved contract section generated by `prompt-manager`.

This plan targets the current drift risk in long-running continuous-improvement teams: decision discipline, document authority, writable surfaces, member lanes, knowledge supersession, and output obligations are currently repeated across `TEAM.md`, agent `SOUL.md` / `AGENTS.md` / `TOOLS.md`, member `RESPONSIBILITIES.md`, and member `HEARTBEAT.md`. The goal is to preserve the hard-won behavioral rules while making them harder to drift, easier to audit, and cheaper to inject into agent heartbeats.

## Greenfield Constraint

This is a hard cutover, not an additive manifest layer.

Non-negotiable rules:

1. Do not introduce a temporary `docs.manifest.json` or separate intermediate manifest layer.
2. Do not dual-read old prompt prose and new contract fields for the same policy.
3. Do not keep compatibility fallback behavior for teams missing an operating contract after the cutover.
4. Do not preserve duplicate policy prose in member files once that policy is contract-owned.
5. Do not silently infer missing contract values from `TEAM.md`, `RESPONSIBILITIES.md`, `HEARTBEAT.md`, or agent files.
6. All bundled teams must be migrated in the same cutover commit/PR.
7. If a team contract is incomplete or invalid, prompt preview and heartbeat execution must fail with a specific validation error.

The implementation may use helper functions and mechanical migration scripts locally, but the final repository state must not contain transitional compatibility code or unused legacy fields.

## Problem Statement

Current heartbeat prompt assembly is defined in `api/heartbeat/prompt_builder.go` and includes:

1. all agent markdown files,
2. `shared/TEAM.md`,
3. member `RESPONSIBILITIES.md`,
4. generated org/coordination/durable-state sections,
5. inbox and handoff state,
6. member `HEARTBEAT.md`.

That layering is clear, but operational policy is duplicated across multiple editable prose files. Current evidence:

- Team member `HEARTBEAT.md` + `RESPONSIBILITIES.md` files total roughly 4,135 lines across bundled teams.
- Agent `SOUL.md` + `AGENTS.md` + `TOOLS.md` files total roughly 2,426 lines.
- Repeated decision-discipline concepts include team queue ceilings, read-only mode, supersession-before-stacking, stale decision scans, owned contexts, per-member caps, and knowledge supersession.
- Meta-optimization's `TEAM.md` already defines team-level policy, but member prompts also restate much of it.

This makes durable policy changes expensive. For example, changing a pending decision ceiling, adding a plan-of-record file, or updating a member's owned contexts can require edits in `TEAM.md`, multiple member `HEARTBEAT.md` files, agent `AGENTS.md`, and `TOOLS.md`. That is exactly the kind of entropy continuous-learning teams are meant to reduce.

## Scope

### In Scope

- New structured operating contract model for teams.
- Store schema, Go models, API DTOs, CLI models, and UI Zod schemas.
- Prompt-builder changes to inject a generated resolved operating contract section.
- Repo-root path normalization for every path rendered into heartbeat prompts.
- Hard migration of all bundled team files and contracts.
- Compression of agent and member prose files so contract-owned policy is not hand-copied.
- Prompt preview UI updates for the new prompt section.
- Validation/audit tests that prevent policy duplication and undeclared doc references from returning.
- Documentation updates for heartbeat prompt assembly, memory promotion, and team shared docs.

### Out of Scope

- Redesigning decision storage (`decisions.jsonl`) or decision status vocabulary.
- Changing operator approval flow.
- Changing `decision-add`, `decision-list`, `decision-accept`, `decision-reject`, or `decision-defer` semantics.
- Changing heartbeat scheduling or team execution queues except where prompts need the resolved contract.
- Changing the existing runtime/coordination/execution policy model except to reference it from the operating contract renderer.
- Creating new Actions or implementing the broader operation-contract plan.
- Adding new business rules, new caps, or new team behavior not already present in the bundled team files unless explicitly approved during workshop.

## Contract Decisions

### 1. Contract Location

Preferred storage: add an `operatingContract` object to `team.json`.

Rationale:

- It keeps the team entity self-contained.
- API/CLI/UI can expose one team object.
- Validation can run when teams are created, updated, loaded, and used for heartbeats.
- It avoids a separate manifest file that could drift from `team.json`.

If `team.json` becomes too large after concrete implementation, the only acceptable alternative is `store/teams/<team-id>/operating-contract.json` loaded as a required part of the team entity. That alternative must still be a hard cutover and must not coexist as a loose optional manifest.

### 2. Path Rules

All paths rendered into heartbeat prompts must be repo-root relative.

Examples:

```text
docs/meta-optimization/CONVERSION_PLAYBOOK.md
docs/monetization/CATALOG.md
scenarios/prompt-manager/store/teams/meta-optimization/shared/RUN_LESSONS.md
scenarios/prompt-manager/store/teams/meta-optimization/shared/knowledge.jsonl
```

Contract storage may use structured path references, but the renderer must normalize before prompt output. Do not render ambiguous paths like `shared/RUN_LESSONS.md` unless the rendered text explicitly states the base path; prefer repo-root paths always.

Validation requirements:

- Every path has a `base` enum such as `repo-root`, `team-shared`, or `team-member`.
- The renderer converts every path to repo-root form.
- Required files must exist at validation time.
- Optional paths must be explicitly marked optional with a reason.
- Paths must not escape the repo root after normalization.

### 3. Normative V1 Schema

The first implementation must treat this as the normative V1 contract shape. Field names may be adjusted during implementation only if all schema examples, Go structs, TypeScript schemas, tests, and docs are updated in the same change.

Top-level `Team` additions:

```json
{
  "operatingContract": {
    "schemaVersion": 1,
    "governance": {},
    "documents": {},
    "decisionContexts": {},
    "knowledgeTopics": {},
    "members": {}
  }
}
```

Required top-level fields:

| Field | Required | Notes |
|---|---:|---|
| `schemaVersion` | yes | integer, initially `1` |
| `governance` | yes | team-level decision and freshness policy |
| `documents` | yes | declared plan-of-record, notebook, and shared-state surfaces |
| `decisionContexts` | yes | all contexts the team may create or consume |
| `knowledgeTopics` | yes | topic families and supersession behavior |
| `members` | yes | one entry per active team member |

#### Governance

```json
{
  "decisionMode": "approval",
  "teamPendingCeiling": {
    "value": 12,
    "readOnlyWhenAtOrAbove": true,
    "rationale": "Tuned for a roughly 3/day operator review rate."
  },
  "supersession": {
    "requiredBeforeNewDecision": true,
    "allowedInReadOnlyMode": true,
    "replacementMustSetSupersedes": true
  },
  "staleDecisionPolicy": {
    "afterHeartbeats": 14,
    "ownerMemberId": "meta-contrarian",
    "requiredOutcomes": ["supersede", "reject", "still-relevant-note"]
  }
}
```

Required fields:

- `decisionMode`: must equal the persisted team `decisionMode`; do not allow divergence.
- `teamPendingCeiling.value`: non-negative integer.
- `teamPendingCeiling.readOnlyWhenAtOrAbove`: boolean.
- `supersession.requiredBeforeNewDecision`: boolean.
- `supersession.allowedInReadOnlyMode`: boolean.
- `supersession.replacementMustSetSupersedes`: boolean.
- `staleDecisionPolicy`: optional only for teams without an aging scan. When present, `afterHeartbeats`, `ownerMemberId`, and `requiredOutcomes` are required.

#### PathRef

All document and write surfaces use `PathRef`.

```json
{
  "base": "repo-root",
  "path": "docs/meta-optimization/README.md"
}
```

Allowed `base` values:

| Base | Meaning | Rendered prompt path |
|---|---|---|
| `repo-root` | path is already relative to repo root | `path` unchanged after clean/validation |
| `team-root` | path is relative to `scenarios/prompt-manager/store/teams/<team-id>/` | normalized to repo-root path |
| `team-shared` | path is relative to `scenarios/prompt-manager/store/teams/<team-id>/shared/` | normalized to repo-root path |
| `team-member` | path is relative to `scenarios/prompt-manager/store/teams/<team-id>/members/<member-id>/` | normalized to repo-root path; requires `memberId` or active member context |
| `agent-root` | path is relative to `scenarios/prompt-manager/store/agents/<agent-id>/` | normalized to repo-root path; requires `agentId` or active member context |

Path validation:

- `path` must be clean, non-empty, and relative.
- `path` must not contain `..` after cleaning.
- Rendered output must always be repo-root relative.
- Required paths must exist.
- Optional paths require `required: false` and `optionalReason`.

```json
{

      "id": "monetization-catalog",
      "paths": [{ "base": "repo-root", "path": "docs/monetization/CATALOG.md" }],

```

Allowed document/write-policy enums:

- `operator-curated-via-decisions`
- `append-any-member`
- `owner-member-writes`
- `read-only`

Allowed shared-state `kind` values:

- `rolling-artifact`
- `append-only-log`

#### Decision Contexts

```json
{
  "skill-improvement": {
    "ownerMemberIds": ["skill-optimizer"],
    "description": "Concrete edit to a high-usage skill.",
    "externalAuthorizedRaisers": []
  },
  "capability-gap": {
    "ownerMemberIds": ["toolchain-validator", "run-introspector"],
    "description": "Missing capability the system should have.",
    "externalAuthorizedRaisers": ["marketing-crew"]
  }
}
```

Rules:

- Every context mentioned in `members[*].ownedDecisionContexts` must exist here.
- Every context must have at least one `ownerMemberIds` entry unless it is explicitly external-only.
- Cross-team raisers must be represented in `externalAuthorizedRaisers`; do not bury cross-team authority in prose.

#### Knowledge Topics

```json
{
  "skill-audit-YYYY-MM-DD": {
    "ownerMemberId": "skill-optimizer",
    "supersedesPrevious": true,
    "retention": "snapshot"
  },
  "challenge-note/<decision-id>": {
    "ownerMemberId": "meta-contrarian",
    "supersedesPrevious": false,
    "retention": "append-only"
  }
}
```

Allowed `retention` values:

- `snapshot`
- `append-only`
- `visited-tracker`
- `operator-authored`

Rules:

- If `supersedesPrevious` is true, rendered prompts must tell the member to include `supersedes`.
- If false, rendered prompts must tell the member not to include `supersedes`.

#### Members

```json

      { "base": "repo-root", "path": "docs/meta-optimization/" }
```

Rules:

- One member entry is required for every active team member.
- Member IDs must match real `store/relations/team-member` agent IDs.
- `ownedDecisionContexts` must be declared at team level.
- `requiredKnowledgeTopics` must exist in `knowledgeTopics`.
- `allowedWrites` and `forbiddenWrites` may contain `PathRef` entries or special entries with `kind`.

Allowed special write `kind` values:

- `handoff`
- `decision`
- `knowledge`
- `task`
- `inbox-message`

### 5. What Moves Into Contract

Move these policy classes into the operating contract:

- team pending decision ceilings,
- read-only mode semantics,
- supersession-before-stacking rules,
- stale decision thresholds and owner,
- per-member owned decision contexts,
- per-member new decision caps,
- per-member pending-owned-context caps,
- knowledge topic families and supersession rules,
- plan-of-record and notebook surfaces,
- document authority and write policy,
- shared-state artifacts and owners,
- allowed write surfaces,
- forbidden write surfaces,
- required handoff behavior,
- member lanes,
- safety-critical rules that need deliberate short repetition,
- generated output-section requirements where they are common enough to validate.

### 6. What Remains Prose

Keep prose for:

- agent identity and communication posture in `SOUL.md`,
- nuanced reasoning frameworks in skills,
- team mission and strategic context in `shared/TEAM.md`,
- member-specific reasoning sequence when it is not just contract-owned policy,
- compact task loop in `HEARTBEAT.md`,
- non-machine-readable rationale where it genuinely helps humans understand why the policy exists.

If a statement contains a numeric cap, a decision context list, a writable path list, a forbidden path list, a stale threshold, or a team-level decision rule, it is contract-owned by default.

### 7. Decision Discipline Preservation

This redesign must preserve decision behavior. It only changes the source of truth and prompt rendering.

Preserve:

- team pending ceilings,
- per-member decision caps,
- read-only mode semantics,
- supersession-before-stacking rule,
- stale decision aging policy,
- owned context boundaries,
- knowledge/handoff obligations during read-only mode,
- challenge-note append-only behavior where currently specified,
- operator approval requirements.

Do not change:

- decision storage format,
- decision status vocabulary,
- operator approval process,
- existing decision CLI command behavior.

### Debt Curator Contract Example

The `debt-curator` member contract should preserve these behaviors from current files:

- Applies meta-optimization pressure inward.
- Scans `docs/meta-optimization/` plus relevant shared artifacts.
- Promotes mature notebook/doc debt into permanent structure or proposes retirement.
- Proposes only; never implements.
- Raises at most one `meta-self-improvement` decision per heartbeat.
- Skips new decisions at team queue capacity or when two owned decisions are pending.
- Still scans, writes `debt-scan-YYYY-MM-DD`, performs supersession, and writes handoff in read-only mode.
- Writes `debt-scan-YYYY-MM-DD` with supersession.
- Uses promotability criteria: repeated >=3 entries, stabilized >=7 heartbeats, or permanent solution now possible.
- Uses four promotion directions: skill, team-structure change, capability gap, or retirement.

Representative member contract:

```json
{
  "lane": "Promote or retire mature meta-optimization notebook debt.",
  "ownedDecisionContexts": ["meta-self-improvement"],
  "newDecisionCapPerHeartbeat": 1,
  "pendingOwnedDecisionCap": 2,
  "requiredKnowledgeTopics": ["debt-scan-YYYY-MM-DD"],
  "allowedWrites": [
    { "base": "team-shared", "path": "knowledge.jsonl" },
    { "base": "team-shared", "path": "decisions.jsonl" },
    { "kind": "handoff" }
  ],
  "forbiddenWrites": [
    { "base": "repo-root", "path": "docs/meta-optimization/" },
    { "base": "repo-root", "path": "scenarios/prompt-manager/store/skills/" },
    { "base": "repo-root", "path": "scenarios/prompt-manager/store/agents/" },
    { "base": "repo-root", "path": "scenarios/prompt-manager/store/teams/" }
  ],
  "safetyCriticalRules": [
    "Propose only. Never implement.",
    "Do not synthesize other members' proposals into strategy.",
    "Route accepted implementation to the owning lane."
  ],
  "readOnlyModeBehavior": {
    "skipNewDecisions": true,
    "stillWriteKnowledge": true,
    "stillRunSupersession": true,
    "stillWriteHandoff": true
  },
  "taskParameters": {
    "promotabilityCriteria": [
      "repeated >=3 separate entries",
      "stabilized >=7 heartbeats without revision or contradiction",
      "permanent solution now possible"
    ],
    "promotionDirections": [
      "skill",
      "team-structure-change",
      "capability-gap",
      "retirement"
    ],
    "maxCandidatesSelected": 1
  }
}
```

If `taskParameters` feels too member-specific for V1, keep it in `HEARTBEAT.md` prose. Do not leave caps, paths, decision contexts, or write rules in prose.

## Implementation Strategy

### Phase 1 - Finalize Contract Schema

Implement a new `teamcontract` or `teamops` package. Prefer `api/teamops` if used only by prompt-manager API; prefer `api/teamcontract` if the naming should align with persisted schema.

Deliverables:

- Go structs for `OperatingContract`.
- JSON schema updates in `store/schemas/team.schema.json`.
- TypeScript/Zod schema updates in `ui/src/lib/schemas/team.schema.ts`.
- Validation function that checks contract shape independently of prompt rendering.
- Path resolver that accepts structured path refs and returns repo-root-relative prompt paths.

Validation must check:

- every contract member exists in team membership,
- every active team member has a member contract,
- every decision context has at least one owner,
- every member-owned context exists in `decisionContexts`,
- numeric caps are non-negative and internally coherent,
- stale policy owner is a member when stale policy exists,
- notebook docs have curator and promotion context,
- plan-of-record docs have authority/write policy and at least one consumer or rationale,
- required files exist,
- rendered prompt paths are repo-root relative,
- no normalized path escapes repo root.

### Phase 2 - Store/API/CLI Cutover

Extend `store.Team` with required `OperatingContract`.

Update:

- `api/store/models.go`
- `api/store/team_store.go`
- `api/teams/models.go`
- `api/teams/handlers.go`
- `cli/teams/teams.go`
- `store/schemas/team.schema.json`
- `ui/src/lib/schemas/team.schema.ts`

Hard rule: after this phase, creating or updating a team without a valid operating contract should fail. The only acceptable exception is tests that intentionally verify validation errors.

CLI additions:

- `prompt-manager team operating-contract <team-id>` to print the resolved stored contract.
- `prompt-manager team validate-contract <team-id>` to run validation and print actionable errors.

These commands must be API-backed or use existing CLI app context patterns; do not add business logic only in CLI.

### Phase 3 - Prompt Builder Rendering

Update `api/heartbeat/prompt_builder.go`:

## Risks And Mitigations

| Risk | Mitigation |
|---|---|
| Contract becomes a second doc layer | Hard cutover: contract owns policy, prose copies removed, drift tests enforce no duplication. |
| JSON becomes too hard to author | Keep first UI read-only/validation-focused; author through code view initially, then add forms later if needed. |
| Agents lose important behavior due to over-compression | Preserve decision discipline and safety-critical rules in generated prompt; migrate by behavior inventory, not by line deletion. |
| Path confusion causes agents to read missing files | Render repo-root paths only; validate required files exist. |
| Tests become brittle string checks | Use focused checks for contract-owned constants and path declarations; keep allowlists for safety-critical repeated phrases. |
| Single-process leader-led flow misses contract | Add explicit `BuildTeamLeadPrompt()` tests. |
| UI pipeline parser breaks on new section order | Prefer structured preview data; update parser or retire legacy flat parsing. |

## Prohibited Patterns

- Optional `operatingContract` for bundled teams.
- Reading `TEAM.md` to infer missing contract policy.
- Keeping old policy text "just in case".
- Adding compatibility shims for teams without contracts.
- Rendering relative paths with unclear bases.
- Duplicating contract-owned doc inventories in `TOOLS.md`.
- Duplicating contract-owned caps in member `HEARTBEAT.md`.
- Changing decision behavior while performing this migration.

## Definition Of Done

The cutover is complete only when:

1. All bundled teams have valid operating contracts.
2. Prompt preview and heartbeat execution fail on invalid/missing operating contracts.
3. `Resolved Operating Contract` is rendered in every team member prompt.
4. Rendered contract paths are repo-root relative.
5. Contract-owned decision discipline is preserved and visible to the active member.
6. Member prompt files no longer duplicate contract-owned constants and doc inventories.
7. UI prompt preview shows the new section.
8. API, CLI, store schema, and UI schemas agree on the contract shape.
9. Docs describe the new source-of-truth model.
10. Drift-prevention tests pass.
11. `cd scenarios/prompt-manager && make test` passes.
12. `vrooli scenario test prompt-manager` passes or any failure is documented as unrelated with evidence.
