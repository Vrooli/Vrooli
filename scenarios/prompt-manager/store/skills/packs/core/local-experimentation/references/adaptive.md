# Adaptive and external experiments

Use this mode when previous results should select the next candidate or production-derived code must run outside the shared checkout. The main skill retains acquisition, capacity, execution, and cleanup ownership.

## Check source access

Apply this check when an API, dataset, quota, or credential affects the next result. Public sources need no credential setup.

1. Record the source, effective period, identifiers, field meanings, byte limits, pagination, quota, and retry limit needed for the selected route. Distinguish documentation, metadata, and verified retrieval. Retain original-source hashes and sanitized request locators separately from transformations.
2. For credentialed work, read `prompt-manager skill read secrets-manager`. Record its opaque item reference, approved destination, authentication placement, and observed access. A stored key does not prove that the chosen executor can use it. Keep credential values, capability tokens, and credential-bearing URLs out of research records.
3. Use the existing owner's bounded execution and acquisition path, or an operator-authorized isolated workaround as described in the main skill. For a rebuild, forecast unchanged interpreter/source archive transfers, missing hash-locked wheel indexes and every materialization as well as new inputs; an installed runtime does not prove a reusable build cache. Retain temporary-use identities and expiry. Mark an unavailable route unverified; do not replace its required facts with another source silently.
4. At closure, revoke task-owned sessions and leases and stop exposed task processes through their owners. Retain intentionally reusable provider keys with their owner. Provider-key rotation or deletion is a separate scoped action. Verify closure; stopping future delivery does not erase a credential from a running process.

## Freeze evaluation and adapt candidates

1. Fix the workload, metric definitions, behavior checks, acceptance criteria, candidate limit, retry limit, resource budgets, and absolute stop time before reviewing outputs.
2. Fix the editable implementation or configuration surface. Keep evaluator and confirmation inputs outside that surface.
   Choose the least costly existing owner route that can answer the screening question. Declare its missing measures. Reserve full measurement windows for resource questions and winner confirmation; keep screening and confirmation evidence separate. Include discarded warmups and every physical launch in the cost preview.
   Separate owner admission from measurement interference. Reuse maintained pressure policies. Require a quiet host only when the selected measurement needs it; paging or occupied swap alone does not establish exhaustion.
3. Record one hypothesis, candidate identity, and selection reason before each trial. Select the next trial from the largest remaining uncertainty or measured bottleneck.
4. Preserve failures and refused routes. Reconcile uncertain effects before another trial. Change a protocol only through a recorded prospective amendment; retain earlier results under their original protocol.
5. Recheck apparent winners with fresh confirmation runs. Compare representative production behavior before claiming transfer. Treat small-sample tails and reliability as unverified when the sample cannot support the claim.
6. Stop when the evidence answers the question, the search has exhausted its declared useful candidates, or a budget or stopping criterion fires. Do not build a scenario merely to retain a useful script or report.

## Copy the smallest applicable production subset

1. Use a task-owned physical directory outside the shared checkout, or an existing sandbox. Record its canonical path and owner.
2. Prefer maintained generated code and pinned artifacts when they exercise the relevant production path. Copy additional source only when a trial needs to edit it. Reuse the owner's declared interpreter and import environment, including packaged dependency directories; the interpreter path alone is not the runtime contract. For an installed managed Python runtime, use `vrooli resource acquisition runtime-probe <resource> --imports <modules> --out <new-receipt-directory>` before model loading or weight preparation. It resolves the service's declared import paths and uses a bounded native operation with read-only mounts and an isolated IP network. Import readiness does not qualify model fit or output quality. Qualify any additional task entrypoint separately.
3. Record each source path, copied path, hash, bytes, purpose, dependency identity, and intended maintained owner. Keep the unchanged source snapshot separate from editable candidates.
4. Reject writable symlinks and shared hardlinks into production source. Keep build outputs, user profiles, ports, and caches task-owned or explicitly registered as shared.
   Prepare command freshness before timing starts. A read-only CLI can rebuild itself; use canonical file reads during capture windows. Retain any observed interference and declare a recheck before running it.
   Inspect `vrooli resource acquisition explain <resource>` before rebuilding. A verified compose-part cache hit can be reused with `compose-candidate <resource> --out <new-directory> --offline`; a miss refuses acquisition in that mode. Installed wheels are not a cache. Unknown transfer, peak disk and external installer caps require an explicit budget decision.
5. Reproduce the unmodified baseline before optimization. Record packaging and environment differences and the comparison's applicability limits. Do not treat a toy substitute as proof of product behavior.
6. Use Scenario Dependency Analyzer for source dependency obligations and installation unless the operator explicitly authorizes an isolated workaround. A tree inventory is not proof of an entrypoint dependency closure. Reject undeclared ambient imports into the live checkout.
7. Retain patches against the frozen snapshot. Recheck current source before integration. Keep concurrent source differences visible.

An external cwd does not remove explicit instructions or global tool policy. Git is optional. File snapshots, hashes, and patches can retain candidates without Git mutations.

## Choose the next research question

Keep a short frontier in the existing checkpoint. For each proposed continuation, name the user decision it could change, the observed uncertainty, obtainable distinguishing evidence, total preparation/execution/review cost, and stop or pivot condition. Compare it with stopping, narrowing or reallocating. A possible new check or remaining time alone does not justify execution. Prefer the cheapest check with material decision value inside the same commission and remaining allowance.

Distinguish direct outcome evidence, a required enabling repair and an optional capability improvement. Give optional work its own bounded allocation; it cannot inherit the whole remaining horizon. Before expanding a quality study, qualify the evaluator against known accepted/rejected evidence. Technical integrity, schema or transcription scores cannot substitute for musical, visual or other usefulness judgments. If that evaluator is unavailable, retain the quality verdict as unqualified or rejected and bound any separately useful technical study explicitly.

A required gate failure stops that route and any dependent effects. It does not by itself end independent source research or offline checks whose gates pass. Keep refused trials `not_tested`; never bypass admission, silently substitute a different workload, or count preparation as the missing empirical result. Retry only after evidence that the failed condition changed and within the declared retry policy. Amend scope or evaluation prospectively and retain the earlier protocol and failures.

Close a route when its answer is supported, the remaining distinguishing facts are inaccessible, or no check beats the alternatives within its allowance. Retain answered/open questions and the reason. A negative finding can be useful; a new fixture family is not automatically useful. New objectives or external commitments need the applicable authority. Time allowances are ceilings, not targets.

Keep outcome acceptance, effect closure and discovery visibility separate. Use the [single persistence method](record.md#persist-and-discover); an indexing failure does not prolong research or change its empirical verdict.

## Start or resume one research chat

Use one primary chat and one task-owned workspace for each bounded experiment. Use a native goal when the next check depends on earlier findings. A normal prompt is sufficient for a short source check. Prompt Manager's experiments feature does not own this workflow.

1. Start from the existing topic guide and prior run's reading guide using the [record guide](record.md#reading-path). Record the question, useful deliverable, source/evaluator identities, authority, allowed effects, total budget and stopping criteria in `BRIEF.md`. Resolve the next experiment's subject before dispatch. Earlier example ideas are not launch commissions. Start a relative time allowance at actual dispatch, then retain the absolute stop time. Reserve time for evidence review and closure within that allowance.
2. Read the selected research skill explicitly in the receiving chat. Registry availability is not proof of native installation or consumption. Qualify a small write/readback in the exact retained workspace before substantial work; a history-preserving fork may inherit different write permissions. Writable operating-system temporary storage alone does not qualify durable retention. Record an authorized sandbox-path amendment if needed; do not silently change the workspace or bypass its policy. For a native goal, read `harness-goal-authoring` and keep its message under 2,048 characters. Point at the brief instead of pasting the whole discussion. Make the goal cover the commissioned outcome and its adaptive frontier; keep a trial's acceptance and attempt limit distinct from commission-level success and stopping conditions.
3. Resolve the chosen executor's current research role (`code.research` for Codex) unless the operator selected another role. Apply its model/effort through supported harness controls and verify the actual receiving settings; unsupported controls mean recorded inheritance, not an applied role. For the same investigation, fork when the current harness supports history-preserving forks. For a different investigation, start a fresh chat with its own brief and relevant source pointers. Neither a fork nor a new chat creates execution authority or proves that a goal is active. Record the receiving thread identity and verify its goal state through the harness.
4. Keep one replace-in-place `CHECKPOINT.md` as the [current-state view](record.md#current-state). Update it at material findings, waits or budget boundaries; link history and receipts. Charge phases, follow-ups, supervision and recovery to the original commission, including failed attempts. A completed phase creates no fresh allowance. Add acceptance/scope feedback to the brief before acting.
5. Preserve the baseline, failed routes and frozen evaluation on resume. Use the state table below before sending another work prompt. A fresh conversation does not reset the original allowance. A new commission may create a new cohort and budget; retain the earlier result.

| Observed state | Action |
|---|---|
| The same thread has an active turn or a live owner operation | Steer or wait through its owner. Reconcile an uncertain response before retrying. Keep one writer for the experiment. |
| The thread is idle and its native goal is active | Let the harness continue. If the harness reports suppressed continuation with useful work and allowance remaining, send a continuation to the same thread. Silence alone does not justify a replacement worker. |
| The native goal is blocked or complete while a turn still runs under a broader commission | Preserve both states and reconcile the commission-level frontier. Use an actual supported goal control if available; a queued slash-command string is ordinary text unless the harness confirms dispatch. Keep permitted same-chat follow-ups within the original allowance, explicitly marking automatic continuation unqualified. Do not clear or recreate the goal to erase its state or accounting. |
| Work was interrupted and the owner confirms no active turn/effect | Resume the same thread with the checkpoint and remaining allowance. If the thread cannot be recovered, start one replacement from the brief and checkpoint, and record the replacement identity. |
| A bounded phase completed but its broader commission still has a consequential permitted check and remaining allowance | Retain the completed result. Record a concrete prospective follow-up in the brief under existing delegated research authority. Reconcile the old writer/effects and native goal before continuing; preserve the original clocks. Completion alone is not a reason to respawn. |
| A usage warning or estimated token threshold is crossed | Report it to the supervisor and assess outcome and friction. A warning is not a stop or completion condition unless the operator or execution owner made it an actual limit. If a real provider or harness limit interrupts execution, checkpoint, report the exact status, and use the supported recovery route when available; do not claim completion or reset a hard budget. |
| The broader commission is answered, its allowance expired, or progress needs missing authority/access | Retain the result or exact blocker. Resume only with the required changed condition or a new authorized commission; do not invent authority or reset the allowance. |

For concurrent experiments, give each chat a separate workspace and a separate budget. Share source snapshots read-only with hashes. Keep shared documentation and integration under one writer or an explicit handoff. Admit resource-intensive jobs through their existing capacity owners; several chat allowances do not reserve several machines. Reconcile shared GPU/RAM/disk demand before overlapping heavy trials. Lightweight source research can run concurrently when its source quotas and host use permit it.

### Observe a commissioned research window

For study selection, shared direction, challenges and cumulative synthesis, use `research-coordination`. The observation and recovery rules here remain the shared execution method.

Commission a coherent permitted batch so ordinary reads and admitted operations need no command-by-command approval. Notify on a changed decision, blocked required dependency, scope/authority change, meaningful result, cleanup failure or closure. Keep routine progress in the current-state view. Preserve genuine human-only decisions and owner admission.

Read the changed checkpoint and decisive receipt. Reuse an applicable Program Runtime compound read; scenario health is not native chat/goal state. Measure calls, returned bytes and usage before claiming savings. Reconcile live effects before one intervention for a material change. Silence alone is not a stall; use an owner wait or notification for a real pending event.

Judge closure and follow-ups through the frontier value test. A recovering condition needs an explicit changed-evidence trigger, not unchanged retries or a new observer goal. Retain original clocks and earlier results. Before the closure cutoff, reconcile active work, goal state, uncertain effects and the cumulative handoff. A cooperative observer is neither crash recovery nor a hard timer; its record must name a pending decision and exit condition.

### Goal and time-limit checks

A skill does not keep a process alive. A goal supplies continuation; a host or execution owner supplies any enforced wall-clock limit. A deadline in prose is cooperative. Native goal token accounting does not establish cancellation of a separately submitted server job. Read the actual harness controls; do not invent a timeout flag or run an agent in a private respawn loop. Apply [the unattended qualification](#bound-unattended-work) when the operator requires enforced unattended limits.

For supervised or cooperative operation, state which limits are instructions and which the owner enforces. For a required hard deadline, verify the owner-supported expiry/cancellation route before launch; otherwise report that route unqualified and continue only independent preparation. Include a closure margin before expiry. Keep task-owned job cancellation separate from ending the chat.

An interactive launch can use `/goal` with this shape after replacing the fields:

```text
/goal Work until the bounded investigation in <absolute BRIEF.md path> has a source-backed finding or an evidence-backed partial result under its stopping criteria, a replayable check, and verified owned-effect closure.
Read first: prompt-manager skill read adaptive-research local-experimentation harness-goal-authoring; then the brief and any CHECKPOINT.md.
Show the evidence check and verdicts in the transcript. Keep frozen evaluation and counterevidence. Work only within the brief's effects and original allowance; checkpoint findings, live operations and the exact next action. At the stop time, finish closure and report changed, verified, remaining and unverified. Record FINAL.md and the research discovery handles. Do not create maintained capabilities unless commissioned.
```

If an entrypoint sends slash text as an ordinary prompt, request native goal creation explicitly and verify the resulting goal state. Do not report a goal as active from the submitted text alone. For resumption, point at the same brief/checkpoint and remaining allowance instead of issuing a fresh generic research request.

Close with `FINAL.md`, retained receipts and the discovery handles required by the main skill. Separate self-review from independent review. Require a second reviewer when the brief calls for one; otherwise disclose that independent acceptance is outstanding. A report's existence alone does not prove that its claims or experiment passed. Surface failures of closure or discovery without turning the experiment into a platform repair project.

## Bound unattended work

Use an existing managed execution owner. Record its run/session identity, absolute deadline, effective budget mode, checkpoint, and cancellation route. Verify its deadline independently of prompt compliance. A terminal expiry does not prove cancellation of server-owned work.

Qualify token accounting before launch: identify the unit, reporting interval, stop latency, and possible overshoot. Completion-only usage supports retrospective accounting. It cannot enforce a live ceiling. When a hard ceiling is required and the runner cannot provide it, do not admit that unattended run. Include supervisor context and review costs in the same budget.

Prefer existing owner runs or native execution sessions over a custom subprocess wrapper added only to collect output. When a custom wrapper is necessary, protect child creation, ownership registration and reaping across bookkeeping failures and interruption; a fallible metadata write after spawn can otherwise strand an untracked child. Qualify that failure path with public dummy children before sensitive effects. Successful final cleanup alone does not establish cancellation reliability.

Track only live owned effects with their owner identities; keep retained assets in the inventory. Reconcile uncertain submissions before retrying. A synchronous request can qualify through context cancellation, bounded execution, exact process scope, and cleanup readback. Add no asynchronous registry solely to satisfy this checklist.

Require the execution owner's containment proof when children can change groups or sanitize their environment. Marker absence alone does not prove cleanup. Keep application-native shutdown separate from cleanup forced by the harness.

Use bounded progress checkpoints and reuse the current review context. Increase check intervals after progress is established. At the deadline, stop the worker and cancel its owned operations through their owners. Report unresolved effects and notification receipts. Keep judgment in the skill and execution mechanics in the existing owners.

## Shared checkout, repair and integration

Use isolated copies for exploratory edits, comparisons and risky prototypes; a user-authorized research outcome does not automatically authorize integrating every candidate. The same commission may explicitly authorize maintained fixes or integration. Ordinary in-scope, reversible shared-source repairs needed to unblock the work may proceed under existing operator authority; do not invent a separate approval for each edit. Confirm the actual scope and executor permissions, inspect dirty and concurrent changes, coordinate one writer or a handoff, and avoid overwriting others. Preserve the baseline and ownership of shared effects.

For an authorized integration, recheck the current source and transfer assumptions, apply the smallest supported change at its owner, and use proportionate behavior validation and existing dependency/lifecycle rules. Record what was changed and validated versus a retained prototype; do not require the entire study to close first. Keep unrelated platform improvements or a larger adoption as a proposal unless already within the commission. Honor actual human-only decisions and explicit exclusions; effects such as purchases, publication, credential changes or destructive actions require the applicable authority. A failed owner admission or safety gate is not permission to bypass it.

At handoff retain the finding, prototype or candidate, source identity, test results, integration disposition and owned-effect cleanup. Research can conclude without maintained integration.
