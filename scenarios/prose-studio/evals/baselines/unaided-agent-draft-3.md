When an operator kicks off a long-running validation suite, the connection between their terminal and the running test should never be the single point of failure that dictates whether the test succeeds or disappears. For a long time, validation workflows in distributed systems have suffered from a fundamental fragility: when a client session terminates, the test run terminates with it. I have watched countless validation passes get wiped out simply because a network blip dropped an active shell, or because an agent reached the end of its session time before a deep suite completed its execution. That operational fragility forced us to rethink how we treat test execution entirely.

We realized that durable validation is not just a cosmetic feature of our tooling; durable validation is a product capability. To solve this, we updated our control plane so that long-running validation runs live independently on our server infrastructure rather than depending on a continuous, fragile terminal connection. In our protocol document, `docs/TESTING.md` -- the protocol this article summarises, we laid down the foundational rule for this model: the lifecycle of a scenario test run must be decoupled from the client process that triggered it.

To put this into practice, we rely on test-genie, our test execution and run management backend that tracks, executes, and retains validation suites across the platform. In our updated workflow, test-genie owns a scenario test run after the command returns. This single architectural shift completely alters how operators interact with long-running validation suites. When an operator triggers a suite, they do not need to keep an active process tied up for the entire duration of the test. The suite keeps its identity, logs, and result instead of disappearing with the caller.

This matters immensely when a suite takes longer than an agent session. In modern automated environments, agent sessions are frequently short-lived, ephemeral, or subject to abrupt restarts. If a validation run exists solely in the memory of an attached client, any interruption to that agent destroys the execution state. By ensuring that test-genie takes ownership of the run immediately upon registration, the run remains fully intact regardless of what happens to the initiating environment.

From the operator perspective, the workflow is clean, predictable, and simple. An operator starts by kicking off the suite using the command line interface. The operator invokes `vrooli scenario test` -- starts a scenario suite and returns once the run is registered. Because this command returns as soon as registration is complete, the operator immediately receives a unique run identifier. There is no lingering, fragile client attachment required at that moment.

Once the run is registered and the identifier is captured, the operator or automated agent records that run identifier. From there, the operator can inspect the state or synchronize with the execution whenever they are ready. When an operator needs to wait for completion, they use `test-genie runs wait --json` -- blocks once on a server-owned run; the documented alternative to polling. Instead of forcing clients into noisy, custom polling loops that repeatedly query status endpoints, this command allows the client to wait once cleanly against the server-owned run, receiving a structured payload when the run concludes.

Crucially, this design establishes a strict operational boundary: a cancelled client is not the same thing as an aborted run. If an operator disconnects, closes their laptop, or loses their network connection while `test-genie runs wait --json` is waiting, only the local client waiting process is interrupted. The underlying test run continues to execute on test-genie without missing a beat. This distinction is vital for preserving engineering effort and operational continuity.

When an operator genuinely intends to terminate a test run before it finishes, they do so explicitly through the control plane. To stop the actual execution, the operator runs `vrooli scenario test abort` -- ends the run itself, as opposed to cancelling the client. By providing a distinct, dedicated abort command, we ensure that an intentional cancellation of the run itself is an explicit, recorded operational action, completely separate from an accidental terminal disconnect.

The distinction between an interrupted client and an aborted run is operational, not cosmetic. A system that treats every disconnected terminal as a failed test loses the difference between infrastructure interruption and a product defect. When tests fail simply because a shell session disconnected, operators waste hours investigating spurious failures, confusing client-side transport disruptions with real regressions in the software under test. Server-owned runs preserve that distinction so the next operator can inspect the evidence and make a grounded decision.

Because the run is server-owned, it provides operators with durable evidence for long-running validation and makes a later handoff possible. If an engineer starts a scenario run at the end of their shift, they do not have to leave a laptop running overnight or worry about a workstation sleep cycle killing the test. They can simply record the run identifier and pass it to a teammate. The incoming operator can pick up the run identifier, attach with `test-genie runs wait --json`, or review the persisted logs and final outcomes directly from test-genie once execution finishes.

The broader result of this work is a control plane that can improve itself without asking every agent to stay attached to a terminal. In automated validation workflows, autonomous agents and human operators alike can trigger validation suites asynchronously, move on to other tasks, and inspect the outcomes when ready. Durable runs turn waiting into a governed capability: the work continues, the evidence remains addressable, and the final decision can be made from the same record that produced it.

By codifying these principles in `docs/TESTING.md`, we have shifted our validation posture from fragile terminal sessions to resilient, server-managed state. Every run launched via `vrooli scenario test` is guaranteed to maintain its lifecycle on test-genie, ensuring that long-running validation remains an asset rather than an operational liability. When testing distributed systems, durability must extend all the way to our validation infrastructure, and server-owned runs give us the foundation to validate our software with complete confidence.
