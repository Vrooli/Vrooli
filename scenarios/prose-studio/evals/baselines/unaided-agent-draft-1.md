When an engineer or automated agent triggers a long-running validation suite, what happens if the local terminal connection drops? In many traditional environments, losing a client connection means losing the entire validation run along with it, forcing teams to restart the work from scratch. But when validation is treated as a critical operational pillar, execution cannot afford to be tied to the fragile lifespan of an ephemeral client session. I am writing this post to share how we addressed this challenge by turning durable validation into a first-class product capability.

The foundation of this work is detailed in docs/TESTING.md -- the protocol this article summarises. Our goal was straightforward: decouple the lifecycle of a scenario test run from the interactive shell or agent session that initiated it. By placing the operational ownership directly on the server side, we ensure that long-running validation remains resilient, continuous, and fully addressable regardless of what happens to the caller.

To make this possible, we rely on test-genie, our dedicated backend test execution and management system. In our architecture, test-genie owns a scenario test run after the command returns. That matters when a suite takes longer than an agent session: the run keeps its identity, logs, and result instead of disappearing with the caller. Instead of requiring an interactive process to stay continuously tethered to the server, our command-line tooling registers the task and hands full ownership over to test-genie immediately.

The workflow begins at the command line. An operator initiates the validation process by invoking vrooli scenario test -- starts a scenario suite and returns once the run is registered. The moment this command returns, test-genie registers the execution context and assigns it a unique run identifier. The initiating client is not burdened with holding local state or maintaining an open connection to keep the execution alive.

From there, the day-to-day workflow is simple. Operators start the suite, record its run identifier, and wait once on the server-owned run. Because test-genie owns a scenario test run after the command returns, the run maintains its own persistent execution lifecycle on the server. The logs are captured, the scenario steps progress, and the overall state remains anchored to the assigned run identifier rather than an active terminal window.

When it comes time to collect the final outcome of the validation run, operators do not need to construct ad-hoc polling scripts or repeatedly query an endpoint. Instead, the workflow relies on test-genie runs wait --json -- blocks once on a server-owned run; the documented alternative to polling. This command allows an operator or automated agent to cleanly block until the server-owned execution finishes, returning structured output that contains the complete validation result once test-genie completes the run.

One of the most essential insights behind this design is that a cancelled client is not the same thing as an aborted run. If an operator closes their laptop, if an agent session reaches a timeout, or if a local network disconnects the terminal, only the client process is cancelled. The scenario test run itself continues running inside test-genie uninterrupted, preserving all logs, state transitions, and intermediate results.

When an operator genuinely needs to stop the actual validation suite from executing on the server, they use a dedicated and explicit command. They invoke vrooli scenario test abort -- ends the run itself, as opposed to cancelling the client. This command sends an explicit instruction to test-genie to terminate the server-owned run, freeing underlying resources and updating the run record to reflect that it was deliberately halted.

The distinction is operational, not cosmetic. A system that treats every disconnected terminal as a failed test loses the difference between infrastructure interruption and a product defect. When an execution fails simply because a local socket closed, teams waste valuable time chasing phantom failures instead of diagnosing real software bugs. Server-owned runs preserve that distinction so the next operator can inspect the evidence and make a grounded decision.

This operational stability gives operators durable evidence for long-running validation and makes a later handoff possible. In team environments and distributed workflows, the engineer who starts a test suite is not always the one who reviews the output. Because the run keeps its identity and logs within test-genie, an operator can start a suite in one session, hand off the recorded run identifier to a colleague or an autonomous agent, and allow that next operator to invoke test-genie runs wait --json to inspect the completed evidence.

The result is a control plane that can improve itself without asking every agent to stay attached to a terminal. Durable runs turn waiting into a governed capability: the work continues, the evidence remains addressable, and the final decision can be made from the same record that produced it.

By formalising these workflows in docs/TESTING.md, we have established a clear and predictable contract for how validation is initiated, monitored, and concluded. Using vrooli scenario test to register the run, test-genie runs wait --json to await completion, and vrooli scenario test abort to cleanly terminate execution when necessary, we ensure that test-genie maintains authoritative custody over every validation run.

Ultimately, building durable validation into our platform ensures that our engineering decisions are always supported by complete, reliable, and persistent evidence. When our tools handle long-running validation as a governed, server-owned process, we gain the confidence and operational rigor needed to deliver resilient software.
