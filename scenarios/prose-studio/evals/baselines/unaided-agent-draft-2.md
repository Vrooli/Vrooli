When a validation suite runs longer than the interactive terminal session that initiated it, the relationship between the client connection and the actual execution state becomes a critical operational boundary. For a long time, validation tooling across the industry has treated these two concepts as interchangeable. If a client disconnected, if a network socket dropped, or if an operator closed a laptop lid, the test run was often treated as an implicit failure or abandoned entirely. In our environment, we decided that durable validation is a product capability, not merely an incidental side effect of running scripts.

To make validation truly durable, we built our protocol around test-genie, our test execution and run management system that maintains ownership of test lifecycles independently of caller sessions. This article summarises the protocol documented in docs/TESTING.md, capturing why we shifted from client-bound test execution to server-owned validation runs and how that shift transforms the way operators interact with long-running validation suites.

In our workflow, test-genie owns a scenario test run after the command returns. That matters when a suite takes longer than an agent session: the run keeps its identity, logs, and result instead of disappearing with the caller. When an operator or automated process starts a validation suite, they do not need to hold an open, fragile connection for the entire duration of the workload. The execution belongs to the backend infrastructure, where its progress is tracked under a distinct run identifier that persists regardless of client connectivity.

Starting this workflow begins on the command line, where an operator initiates the suite using vrooli scenario test, which starts a scenario suite and returns once the run is registered. The command does not hang indefinitely while the scenario executes. Instead, it registers the execution request, hands ownership to test-genie, outputs the run identifier, and returns immediately. This clean break between test initiation and test execution ensures that the initiation step is deterministic and brief.

Once the command returns, operators start the suite, record its run identifier, and wait once on the server-owned run. The mechanism for synchronising with that background work is straightforward and explicit. Rather than writing ad-hoc polling loops that repeatedly query status endpoints, operators use test-genie runs wait --json, which blocks once on a server-owned run as the documented alternative to polling. This command establishes a clean, single-point wait against the existing run identifier, receiving structured JSON output when the server-owned run reaches completion.

This separation between client attachment and server ownership solves a fundamental operational problem. In traditional setups, if an operator's local environment resets or an automation agent session reaches its execution limit, the client process is cancelled. In naive systems, cancelling the client process implicitly cancels or corrupts the test run itself, or leaves it in an ambiguous state where logs are lost and outcomes cannot be evaluated. Under our design, a cancelled client is not the same thing as an aborted run.

If a client connection drops or an agent session times out while waiting, the server-owned execution inside test-genie continues undisturbed. The test identity remains intact, the execution logs continue to accumulate on the server, and the final validation result is securely recorded. When an operator reconnects or a new agent takes over, they do not need to restart the suite from scratch. They simply take the recorded run identifier and inspect the state or wait on the existing run.

When an operator genuinely intends to terminate execution before it completes naturally, they must perform an explicit lifecycle action. To achieve this, an operator issues vrooli scenario test abort, which ends the run itself, as opposed to cancelling the client. This command explicitly instructs test-genie to stop execution, release associated resources, and mark the run lifecycle as terminated. By requiring an explicit abort command to halt execution, we ensure that no run is ever stopped accidentally due to client-side network interruptions, closed shells, or dropped sessions.

The distinction is operational, not cosmetic. A system that treats every disconnected terminal as a failed test loses the difference between infrastructure interruption and a product defect. When an automated build or an operator cannot differentiate between a dropped network socket and an actual assertion failure in a scenario test, every failure requires manual triage and investigation. Server-owned runs preserve that distinction so the next operator can inspect the evidence and make a grounded decision.

Because the run identifier and its associated artifacts persist inside test-genie, handoffs between operators and automated agents become reliable. An automated agent can initiate a suite, record the run identifier, and cleanly complete its session. A human operator, or a subsequent automated step, can later pick up that exact run identifier, query test-genie runs wait --json to observe completion, and review the recorded evidence. The validation evidence remains fully addressable, structured, and auditable across different sessions and operational contexts.

The result is a control plane that can improve itself without asking every agent to stay attached to a terminal. Durable runs turn waiting into a governed capability: the work continues, the evidence remains addressable, and the final decision can be made from the same record that produced it. By implementing the principles outlined in docs/TESTING.md, we have established a validation model where long-running tests are treated as first-class, durable system operations, giving our engineering team reliable evidence whenever validation occurs.
