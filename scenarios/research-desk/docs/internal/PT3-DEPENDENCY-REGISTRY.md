# PT3 dependency registry

Operational registry for unattended problem-triage (PT3) and debt-reduction windows. The operator stance is: **“it must be antifragile to any infrastructure and fully flexible”**. This is a routing contract for injection, recovery, and eventual harness execution; it does not claim that unattended daily windows are already commissioned.

## State and recovery contract

For each dependency, record `up`, `down`, or `unknown` with a timestamp and evidence. `unknown` means the probe/control path could not establish health; never turn it into `up` or `down`. Inject one outage at a time, label it `injected:<dependency>:<UTC timestamp>`, keep independent work moving, and record the blocked work against the dependency. A recovered dependency is usable only after its measurable health predicate passes. Resume from the durable work item/checkpoint and disposition ledger: assign each item one stable ID and write exactly one terminal disposition (`fixed`, `deferred`, `duplicate`, or `not-actionable`). On replay, an existing disposition is authoritative and must not be replaced or duplicated.

Fallbacks are explicit routes, not silent success. Recovery/matrix validation must include **fallback removal expected-fail**: temporarily make the fallback unavailable and confirm the capability reports blocked/unknown and that the relevant matrix row fails. A matrix that passes only because an undeclared fallback still exists is invalid. Restore the fallback after the probe. Never use fallback removal against production data or a live maintenance window.

Documented topic-tool routes have an owner-side presence check: `python3 -I skills/research-coordination/scripts/topic_health.py --topic <topic> --require-fallbacks --json` exits nonzero when a monitored capability has no fallback or a scenario is outside the probe bound. Its test removes a fallback from temporary `TOOLS.md` and verifies matrix failure. This checks route presence only, not successful live recovery.

The Search Hub owner test also injects an unhealthy status in its fake control plane, confirms `rg` is the selected route, and runs `rg` against a disposable fixture directory. It does not interrupt the shared Search Hub or access private project data.

## Injection and acceptance record

For each daily window, retain one row per injected dependency: injection ID/time, dependency, precondition health evidence, injected state, affected work IDs, independent work completed, fallback exercised, fallback-removal expected-fail result, recovery health evidence, resumed work IDs, and terminal disposition IDs. A completed window requires:

1. Every injected outage has an explicit state; an unavailable observation remains `unknown`.
2. Independent work reaches its normal disposition despite the outage.
3. Dependent work resumes after the primary health predicate passes, with one disposition per stable item ID.
4. Each fallback route passes while available and fails closed when deliberately removed.
5. Policy and provider/harness identity are recorded for the window.

The current `research-coordination/scripts/topic_health.py` implements part of this contract: scenario health is `up` only when running and healthy, failed status queries are `unknown`, and it emits the Search Hub and Prompt Manager fallbacks. Its credential probe uses `research-desk commissions --json`; `--friction` uses Program Runtime. Steward packet-build/launch command timeouts now persist queue state as `unknown` with the failing phase; if a durable launch record exists, the steward clears the retry queue to avoid a duplicate session. This does not yet measure Test Genie admission capacity, disk admission, provider canary compatibility, `policy.json`, or disposition replay, so those checks remain explicit acceptance work rather than inferred health.
