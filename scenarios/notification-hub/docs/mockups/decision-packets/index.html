Decision Packets
Notification Hub · proposal · 13 Nov 2026

Decision packets: decisions you can catch up on in a minute

Right now a decision is one block of text and one multiple-choice answer. This page proposes making each decision a packet: a short cover, attached files you can open inside the Hub, and an answer form shaped to the question. It shows the options for each part, with mockups, and my recommendation for each.

What exists today (checked in the code)
One answer plus one noteAn answer is one option key and a note of up to 4,096 characters. A decision can have at most 8 options. There is no way to answer several questions at once.
Files open in a second appThe Hub turns file paths in the text into links that open Web Console in a new tab. It shows Markdown images inline. All other Markdown shows as plain text.
Web Console already views ~25 file typesMarkdown, images, video, audio, PDF, 3D models (GLB), folders, archives, SQLite, spreadsheets, slides, fonts and diffs. About 7,000 lines of UI and 5,500 lines of Go. Relative paths are found from a terminal session's folder.
Writing rules have landedThe other agent's work is in place. The notification-hub skill teaches the SBAR format, and the CLI reminds an agent that has not read the skill. The reminder never blocks the send.
The idea

A packet has three parts, and each can improve on its own

A · Cover

What and why

The question, the big picture and the recommendation. The skill already covers this. Below I add a check that the Hub runs when the packet is created.

B · Attachments

The evidence

Plans, mockups, renders, GLB models and folders. You open them inside the Hub with the same viewer as Web Console.

C · Answer form

Your reply

One question or several. Pick a variant, approve a plan section by section, choose several items. The answer goes back to the agent as structured data and as plain text.

Part B · Viewing attachments

How the Hub shows files

B1 · today

Link out to Web Console

  • Already built
  • Opens a new tab and loses your place on a phone
  • Breaks when Web Console is down
  • Shows the file as it is now, not as it was when the agent asked
B2

Embed Web Console's viewer in a frame

  • Fast: about a week of work
  • Viewer upgrades reach both apps at once
  • The Hub stops working well when Web Console fails, which goes against the anti-fragile goal
  • Sign-in has to work across two apps inside a frame
B3 · recommended

Move the viewer into shared packages

  • One viewer that both apps use, with no runtime link between them
  • Each app supplies its own file source: Web Console uses terminal sessions, the Hub uses the packet's attachments
  • Larger work. The renderers depend on Web Console only through text strings, selectors and one API client, so the split is clean.
Recommendation: B3, plus snapshots

When an agent attaches a file, the Hub copies it into its own store and records a hash. You see what the agent saw, even after a scratch folder is cleaned up or the plan is edited. When the original has changed, a "changed since asked" label appears with a link to the current version. Folders become a browsable copy of that subtree. Above a size limit (for example 200 MB per packet) the Hub keeps a reference and hash only. The Hub serves only the files the agent attached. It never serves any path on the host over the tunnel. That rule is also the security boundary.

Part C · Answering

How you reply

C1 · today

One choice plus a note

  • Fast for yes/no
  • "Mostly yes, but…" goes into one long note
  • Leads agents to send several separate decisions about one topic
C2 · recommended

Typed form with several questions

  • Choose one, choose several, rank, short text, pick a variant
  • Each question has its own recommendation and note
  • The Hub validates it and draws it the same way every time, so agent mistakes cannot lose your answer
  • The agent has to describe the form, which is about 10 lines of YAML
C3 · recommended

Section-by-section review

  • For "review this plan": each heading gets Approve, Change or Drop, with a note
  • Matches how you actually approve plans: mostly yes, with notes
  • Needs Markdown with real headings, which the plan-writing standard already requires
C4

Agent writes the whole page in HTML

  • Full freedom: side-by-side layouts, sliders, timelines
  • Every packet looks different, and an agent bug can lose your answer
  • Agent JavaScript would run in your signed-in browser
  • The answer has no fixed shape, so the next agent cannot rely on it
Recommendation: C2 + C3 for answering. HTML only as an attachment.

An agent may attach an HTML explainer when a layout helps, such as a before/after slider or an interactive timeline. The Hub shows it in a sealed frame with no network access and no access to your sign-in. The answer always comes from the Hub's own form below it. Later, the HTML page may pre-fill that form (tap mockup B, and question 1 changes to B), but it can never submit. This gives the agent full freedom in how it presents the packet, while your answer stays reliable.

What the agent sends and gets back 
# notification-hub conversations ask … \
#   --attach brief.md --attach mockups/ --attach character.glb \
#   --form form.yaml
questions:
  - id: set
    kind: pick-variant
    prompt: Which studio set should I build?
    variants:
      a: { label: Warm desk, attachment: mockups/set-a.png }
      b: { label: Open loft, attachment: mockups/set-b.png }
    recommend: b
    why: Reads better on a phone screen.
  - id: shots
    kind: choose-many
    prompt: Which shots should I make first?
    options: { intro: Intro walk-on, demo: Product demo, outro: Sign-off }
  - id: brief
    kind: review-sections
    attachment: brief.md
    unanswered: approve
# conversations wait --ask-id … --json
{
  "answers": {
    "set":   { "choice": "b", "note": "Less clutter on the back shelf." },
    "shots": { "choices": ["intro", "demo"] },
    "brief": { "sections": {
      "Timeline": { "verdict": "change",
        "note": "Two weeks. Review only after the first video." } } }
  },
  "file_comments": [
    { "file": "character.glb", "note": "Hair is too glossy." } ],
  "summary": "Set B (less clutter on the back shelf). First shots:
    intro, demo. Brief approved except Timeline: two weeks,
    review only after the first video. character.glb: hair
    is too glossy."
}

The summary line means an agent that never parses JSON still understands the answer. A plain --option decision with no --form works exactly as it does today, because it becomes a form with one question.

Part A, plus catching up on many decisions

Smaller ideas with a large effect

recommended · small

"I need more context"

A fourth button next to Answer and Dismiss. You type what is unclear. The decision stays open and goes back to the requesting agent, which rewrites it in place. Revising in place by subject key already works, so this is mostly one new state and one event.

recommended · small

Packet check when sent

The Hub checks a new packet: IDs in the question, no big picture, a missing attachment, a form option that names an attachment that does not exist. It returns warnings to the agent, the same way as the skill-read reminder. It never blocks.

medium

Review session

For the "few dozen waiting" case. Decisions open one after another as full-screen cards, grouped by objective, with reading time shown and a skip option. A short note says what changed since you last looked.

later · optional

Ask the packet

A chat box that answers "what does X mean here?" from the packet and its attachments, using a local model. It is useful but it adds a dependency, so it waits until the rest works.

Rules that keep it anti-fragile
You can always answerEvery packet keeps a flat fallback: the question, the options, "Accept all recommended" and "Reply in words". This works from a push action, from the CLI, or when a viewer or form fails to load.
Sending never fails on extrasA missing or oversized attachment, or a form that fails validation, gives a warning and a degraded packet. The core ask is still delivered.
No runtime link between appsThe Hub uses the shared viewer package, not a live Web Console. Either app can be down without breaking the other.
Unknown means plain textA question type that an older Hub does not know shows as a free-text question. Answers always include a plain-text summary.
Agent code stays sealedHTML attachments run with no network access and no same-origin access. They can only send a pre-fill message, never submit.

Your call · my recommendation is shown for each
1. How should the Hub show attached files?Recommend: move Web Console's viewer into shared packages (B3). Embedding it in a frame is faster, but then the Hub depends on Web Console being up.
2. Copy attachments when the agent asks, or link to the live file?Recommend: copy, with a size limit and a "changed since asked" label. Scratch folders get cleaned up, and you should judge exactly what the agent saw.
3. How much freedom do agents get with HTML?Recommend: HTML is allowed as a sealed attachment that can pre-fill the Hub form, and the Hub form always submits. Agent-built forms (C4) are not allowed.
4. Where should work start?Recommend: Stage 1 and the "I need more context" button together. The button is small, and it immediately helps with the decisions that are waiting now.

Risks I have not checked yet: how much of Web Console's viewer state (back/forward stack, relative-path search) depends on terminal sessions, and whether the React component library or a new package is the right home under its publishing rules. Both are short reads at the start of Stage 1.
