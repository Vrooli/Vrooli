# Decisions — Notification Hub

This document records durable decisions and tradeoffs future agents
should not accidentally relitigate.

## Purpose Of This Document

Use this document when a choice:

- affects multiple files or future agents,
- rejects a plausible alternative,
- changes architecture, deployment, data, security, monetization, or
  testing direction,
- needs a revisit trigger.

Routine implementation log entries belong in [`PROGRESS.md`](PROGRESS.md).
Known unresolved issues belong in [`PROBLEMS.md`](PROBLEMS.md).

## Decision Log

| Date | Decision | Context | Consequences | Revisit Trigger |
|---|---|---|---|---|
| 2026-08-17 | Use the generated `react-vite` scenario documentation contract. | Scenario scaffold was generated from the template. | Docs start with stubs and maturity metadata in `docs/manifest.json`. | Revisit when scenario adopts a different template or doc contract. |
| 2026-08-17 | Regenerate from the template rather than repair the previous scenario in place. | The previous notification-hub predated the `react-vite` template and had none of its eight structural markers. Six of twenty business endpoints were implemented; every send path terminated in a log line; the requirements registry was empty. Its `.vrooli/testing.json` had been swept to declare a `react-vite` policy profile it could not satisfy. | ~5,000 lines of API, UI, and test scaffold discarded. Worth porting: the twelve-table schema design and the channel/delivery-state taxonomy. `tunnel-manager` set the precedent by regenerating from `react-vite` 1.1 rather than migrating. | None. Relitigating this wastes the migration. |
| 2026-08-17 | Declare **no resource dependencies**. SQLite through the `api-core` storage seam; queue, retry schedule, and rate-limit counters in-process. | The old scenario declared `postgres` and `redis` as `required: true`. `path:docs/reference/platform-support.md` recorded both as unsupported outside Linux at the time, and their manifests confirm `managed_service.acquisition.kind: "oci-image"`. **Re-verified 2026-09-01:** the acquisition kind still holds, but both resources now declare `driver: managed-service` and neither requires a container runtime to start, so "Docker-backed" is no longer accurate. The decision stands on the surviving half — neither is `supported` on macOS (`postgres` is `build-verified` with no hardware run performed; the matrix's two tables disagree about `redis`), so either would put the macOS fleet node on unproven footing. | The same build runs on a Linux host and on a macOS fleet node, which is what makes cross-node relay possible at all. No Docker in the start path. Rejected alternative: keep Redis for the queue — it would have made the scenario Linux-only and silently vetoed the relay architecture. | Revisit only if `postgres` or `redis` earns a portable managed-service acquisition path like the one `searxng` now uses. Adding either back forfeits macOS. |
| 2026-08-17 | Own no identity. Verify `scenario-authenticator` tokens locally via `api-core/owneridentity`. | The old scenario carried profiles, per-profile API keys, bcrypt verification, and an `/admin` surface — the scaffolding of a notification product sold to third parties. | No password, no profile table, no scenario-issued API key here. Roughly half the old surface area disappears. Recipients key off the authenticator's `user_id`. | Revisit if a consumer outside the Vrooli trust boundary ever needs to send through this hub. That is a different product; prefer a new scenario. |
| 2026-08-17 | Treat multi-user support as a consequence of `trust_posture`, not as a feature to build. | `.vrooli/operator-state.json` carries `trust_posture` (`personal` \| `shared` \| `hosted`); this install is `personal`. `packages/api-core/trustposture` already exists. | In `personal` there is exactly one identity and the UI shows no picker. In `shared`/`hosted` the same tables hold several and routing is per-identity (OT-P2-003). Multi-user is earned by using the identity seam rather than by writing tenancy code. | Revisit when the operator moves this install to `shared` or `hosted`. |
| 2026-08-17 | Use Bridge **durable dispatch** for cross-node delivery, not `RelayService.Call`. | Bridge exposes both: a bounded synchronous relay and a queued, allowlist-checked, audited dispatch that creates a durable run. | A delivery survives a node that is briefly offline, which a synchronous call cannot. Costs a slower path and an extra state to model. | Revisit if a channel ever needs a synchronous acknowledgement from the remote node inside the request. |
| 2026-08-17 | Ship one real channel end to end before building any abstraction, and make it push to the owner's iPhone. | Everything the previous scenario ever did was simulated. | OT-P0-001 is a delivery requirement, not an architecture requirement. Push was chosen over email because it needs neither an Apple Developer account nor a Mac to build and sign an app — correcting the assumption that reaching an iPhone requires a Mac. A Mac is needed only to sign a first-party APNs app and for genuinely host-bound Apple channels. | None for the sequencing. The provider choice has its own row. |
| 2026-08-18 | Deliver push through **Web Push from this scenario's own installed progressive web app**. No push resource, no push server. | The scaffold already ships `ui/public/sw.js`; the template already calls `navigator.serviceWorker.register("sw.js")`; 39 scenarios in the fleet already carry a service worker. Web Push payloads are encrypted end to end under RFC 8291 with keys no push service holds. Standard Web Push with VAPID needs no Apple Developer account and no Firebase project. | The push adapter is a `push` listener plus a `notificationclick` listener added to a file that already exists, rather than a new resource with pinned per-platform artifacts. `dependencies.resources` stays empty, so OT-P0-009 is literally true. Rejected alternative: a self-hosted relay server. It would still route its wake-up through a third party to Apple, so it added a server without removing a dependency, and it required the phone to reach that server at delivery time or degrade to a contentless placeholder. Costs: subscription lifecycle churn (`410 Gone`, `pushsubscriptionchange`), an origin-scoped subscription so every notification is branded as this scenario, a hard dependency on a stable public origin, and no `curl`-able endpoint for scripts outside Vrooli. On Android this also gives up the fully de-googled path a self-hosted relay with its own client could offer. | Revisit if a `curl`-able endpoint for non-Vrooli scripts becomes necessary, or if fully de-googled Android delivery becomes a goal. The rejected design is preserved at `.vrooli/resources/blueprints/ntfy.json`, `status: candidate`. |
| 2026-08-18 | Take a **core-seed** grant so the public origin never expires. | A Web Push subscription is bound to an origin. `tunnel-manager` exposure is tiered: CORE members are always-on and never auto-expired, while LEASED hostnames are time-bounded at roughly a week and auto-reaped. A lapsed hostname silently unsubscribes every device at once. | `notification-hub` added to `core.seed` in `.vrooli/operator-state.json`, and `packages/api-core/coreset/coreset_test.go` updated because it pins exact membership as a review gate. Second consequence, not requested but correct: `vrooli-autoheal` marks every core member `Critical: true`, so this scenario gains monitoring and auto-recovery by default. A silently dead notifier is indistinguishable from having nothing to say. | Revisit if the scenario stops owning push subscriptions. |
| 2026-08-18 | Cross-node delivery works by **asking this scenario's own remote instance**. `vrooli-bridge` carries the call and never learns what a channel is. | An earlier design put a facility vocabulary and readiness verdicts into the bridge heartbeat. That would require a bridge change for every new channel type and create two owners for one fact. `device-control` already dispatches its own verbs (`observe`, `actuate`, `flow`) to remote nodes, and its `INTEGRATIONS.md` states the principle: the bridge owns the reach plane, and putting a second registry elsewhere would split the single answer to what the owner controls. The bridge's own `gate` package says the same of itself — Bridge supplies the capability, the domain scenario owns the verdict. | `notification-hub channels status --json` reports per-channel dispositions on whatever machine it runs on. Locally it is a direct call; remotely it is the identical verb through durable dispatch. Adding a channel touches this scenario's adapter registry and nothing else. Cost: readiness now needs a round trip rather than riding a heartbeat, so freshness becomes this scenario's responsibility — cache per machine with a stated lifetime, refresh on a schedule, re-check after a failed delivery before marking anything unroutable. | Revisit if per-notification routing latency makes the round trip unacceptable, which would argue for a push-based inventory again. |
| 2026-08-18 | Address the **machine**, not the bridge node. | The paired Mac has thirteen node registrations in the live bridge registry, resolving through `machine_node_lineage` to one machine with exactly one `is_current` node. That lineage layer works correctly. | Routing keys on machine id and resolves the current node at dispatch time, so stale node rows never become phantom routing candidates. | None. |
| 2026-08-18 | Require the `vrooli-bridge` dispatch vocabulary to be **derived**, not hand-maintained, before depending on it. | Every CLI command in the repository already declares `governance` with `effect`, `run_eligible`, and `permissions`, schema-enforced and non-optional. `packages/api-core/scopecatalog` reads all 70 scenario manifests plus the root and emits a scope per command, with no dependency on the authenticator or any scenario package. The bridge builds that catalog and then discards every non-project scope, so `dispatch.manifest.json` hand-copies governance that already exists at the source — `device-control actuate` is declared in two places today. | After the refactor, a scenario reaches another machine by declaring governance in its own manifest and being granted a node scope; no bridge file changes per scenario. This is the same split `scenario-authenticator` uses: carry the grant, let the relying party enforce the meaning. **The refactor has a mandatory second half.** `anyScopeMatches` treats a bare `vrooli-bridge:<effect>` grant as satisfying any verb of that effect, so what bounds a node today is that the vocabulary is small. Widening the vocabulary without narrowing grants would silently widen every node, including the paired Mac, which holds exactly that bare grant. Shipping only the first half is a security regression. | Revisit only if a future dispatch consumer needs a vocabulary the scope catalog cannot express. |
| 2026-08-17 | Sequence direct ingress before event ingress. | `vrooli-events` stores subscriptions but never fans them out: ingest publishes to the SSE broker only, and `Deliver` is reachable solely from a manual trigger endpoint. No matcher, no retry queue, no engine. | Direct Connect-RPC and CLI ingress is P0 because it is self-contained. Event ingress is P1 because it depends on work in a scenario this one does not own. | Revisit when the `vrooli-events` subscription fan-out engine exists. File the gap against that scenario, not this one. |
| 2026-08-17 | Promote acknowledgement and escalation from P2 to P1, and add a blocking `ask` primitive alongside them. | Market research found three adjacent markets: metered multi-tenant notification SaaS (Novu, Knock, Courier), free self-hosted push pipes (ntfy, Gotify, Pushover, Apprise), and agent-to-human attention, which has no established player. The first is the charter this scenario rejected; the second is transport we ride on. | Return traffic is what separates this from both. A pipe has no routing layer; a hosted platform has no fleet to route across. Promoting the trio makes the scenario the human-in-the-loop gate for the fleet rather than an outbound pipe, and it needs no second machine, so it sequences ahead of the bridge work. Costs: acknowledgement state, a callback path back to the requesting scenario, and a long-lived blocking call the API must hold open. Renumbered `OT-P2-004`/`OT-P2-005` to `OT-P1-009`/`OT-P1-011`; safe because neither was implemented or referenced by a test tag. | Revisit if acknowledgement ships and agents do not use it. Delivery without acknowledgement means the spine is being muted, and the oversight thesis fails before any pricing question matters. |
| 2026-08-17 | Never meter notifications. | Metering is how every SaaS competitor prices, and the obvious way to monetize this. | It penalizes exactly the high-frequency agent traffic the scenario exists to serve, and it contradicts OT-P0-009's promise that the thing runs on the owner's own hardware at zero marginal cost. Commercial role is bundle inclusion in the `business` base SKU, with an agent-oversight add-on gated on OT-P1-009 through OT-P1-011. | Revisit only for a hosted relay serving owners with no always-on machine — the one place a metered tier would be coherent. |
| 2026-08-17 | Sensitivity labelling is default-deny, and the label is carried on the ingress contract from day one. | A public push topic exposes its body to anyone holding the topic name. A label added after the proto exists would be a required-field retrofit across API, CLI, and UI. | Every notification carries a label at acceptance. A channel is **not** approved for a label unless it declares approval; the unapproved case sends a content-free pointer back to the console rather than the body. Costs a required field in v1 of the proto. | Revisit only to add labels, never to make the default permissive. |
| 2026-09-01 | Route conversational notification channels through Switchboard's shared adapter registry. | Duplicating Telegram, Slack, or iMessage senders here would create a second channel implementation and bypass Switchboard's descriptor and availability policy. | Web Push, e-mail, and desktop notifications remain owned by Notification Hub. The iMessage branch is retained for macOS desktop delivery because it serves the existing one-shot desktop contract; Switchboard owns conversational iMessage when its Mac-node lane is available. Notification delivery remains unmetered. | Revisit if Switchboard removes the shared one-shot send surface or the local iMessage sender loses platform support. |

## Superseded Decisions

| 2026-08-18 | Start with a hosted push provider as a `cloud-api` resource; promote to `managed-service` only when self-hosted. | Deliver push through Web Push from this scenario's own installed progressive web app (2026-08-18). | The resource never existed.
