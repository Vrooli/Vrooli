# Product Requirements Document (PRD)

## 🎯 Overview
Purpose: device-sync-hub adds a permanent, secure, server-relayed capability for moving files and text snippets between an owner's trusted devices. Any trusted device opens the web UI (or calls the CLI/API) to push content to the Vrooli server, which holds it and delivers it to the owner's other trusted devices in near-real-time. The scenario also exposes a stable "deliver this artifact to one of my devices" primitive that other Vrooli scenarios and agents can invoke programmatically.

Target users: A single owner operating multiple personal devices (phone, laptop, tablet, the server itself) who needs frictionless, private, self-hosted cross-device transfer. Secondary consumers are other Vrooli scenarios and agents that produce artifacts (images, files, snippets) and must hand them off to an owner device without involving a third-party cloud service.

Deployment surfaces: Polished, fully responsive web UI (primary); programmatic REST/Connect API; Go CLI with JSON output for scripting; real-time WebSocket channel for delivery and presence. No native mobile apps in v1.

Value proposition: Eliminates the daily friction of moving files and text between your own devices — securely, without third-party cloud services, on infrastructure you own. Every transfer stays on the owner-operated Vrooli server; untrusted network neighbors are locked out by device pairing and JWT-gated sessions, not by end-to-end encryption. Over time, the scenario becomes a reliable low-level primitive that any Vrooli automation can target when it needs to hand a produced artifact to the owner.

## 🎯 Operational Targets

Operational targets are measurable outcomes; checkboxes may auto-update based on validation.

### 🔴 P0 – Must ship for viability
- [ ] OT-P0-001 | Server-Relayed File & Text Transfer | Files and text snippets sent from any trusted device are relayed through the Vrooli server and delivered to the owner's other trusted devices; both item types are first-class with no feature disparity.
- [ ] OT-P0-002 | Secure Device Pairing | Devices are admitted to the trust group exclusively via a short-lived, single-use pairing code or QR code (with a request-and-approve banner as fallback); an unpaired device on the same network or tunnel can see no content and perform no actions.
- [ ] OT-P0-003 | Delegated Owner Auth & Immediate Revocation | Owner identity, JWT issuance (access + refresh), and token validation are consumed from scenario-authenticator over HTTP; revoking a device immediately invalidates its authenticator session and removes it from the trust group so no further reads or writes are possible.
- [ ] OT-P0-004 | Per-Item Retention Spectrum | Each item carries a retention policy — Live (deliver to connected devices then purge), Held (auto-purge after a configurable default, out-of-the-box 24 h), or Pinned (kept until manual deletion) — with a global owner-configurable default applied at upload time.
- [ ] OT-P0-005 | Real-Time Delivery & Device Presence | Pushed items appear on other trusted devices within one second for payloads under 10 MB over a persistent WebSocket; each device's online/offline presence is visible in the UI.
- [ ] OT-P0-006 | Polished Responsive Split-Screen UI | The primary interface is a full-screen split — Receive pane on top, Send pane on bottom — with image thumbnails, per-item retention and target controls, and correct empty, loading, and error states; the layout is fully usable from small phone widths through desktop.
- [ ] OT-P0-007 | Streaming Storage via api-core | Uploads stream directly to the api-core blobstore; downloads stream back preserving original filename; image thumbnails are generated server-side at ingest; the relational metadata store uses migrations and is never recreated on schema change.
- [ ] OT-P0-008 | Device Management & Settings | Owner can list, rename, and revoke devices; perform remote sign-out; configure the global retention default and per-device storage quotas; destructive actions (e.g., clear-all) require explicit confirmation and are permissioned to the owner.

### 🟠 P1 – Should have post-launch
- [ ] OT-P1-001 | Drag-and-Drop Upload with Chunked Resume | The Send pane accepts drag-and-drop with per-file progress indicators; large files use chunked, resumable upload so a network interruption does not require restarting from zero.
- [ ] OT-P1-002 | Storage Quotas Enforced at Upload | Per-device and global storage quotas are checked before a transfer is accepted; uploads that would breach the quota are rejected with a clear error before any bytes are written to the blobstore.
- [ ] OT-P1-003 | Directed Single-Device Delivery | A sender can target a specific trusted device instead of broadcasting to the whole trust group; the selection is exposed as a control on each staged item in the Send pane.
- [ ] OT-P1-004 | Search, Sort, Filter & View Toggle | The Receive pane provides full-text search over item names and snippets, sort by date/size/type, filter by item type or retention policy, and a toggle between card view and compact list view.
- [ ] OT-P1-005 | Cross-Device Notifications | "Item arrived" notifications and pairing-request approve/reject banners are pushed to the relevant trusted device in real-time via the existing WebSocket channel with no separate notification infrastructure required.
- [ ] OT-P1-006 | Programmatic CLI & API Surface | A Go CLI and the documented REST/Connect API let other scenarios and agents deliver an artifact to one of the owner's devices; all CLI commands emit structured JSON for scripting; the API contract is versioned and stable.
- [ ] OT-P1-007 | Optional At-Rest Blob Encryption | Owners can toggle AES-256 at-rest encryption for stored blobs; the toggle is surfaced in Settings, the key is derived from an owner-held passphrase stored nowhere on the server, and the default is off (no zero-knowledge guarantee is implied or promised).

### 🟢 P2 – Future / expansion
- [ ] OT-P2-001 | WebRTC Same-LAN Fast Path | When both devices are on the same local network, transfers are optionally routed peer-to-peer via WebRTC DataChannel for multi-gigabyte performance; the v1 server-relay path remains the always-available fallback and the transfer abstraction layer is unchanged.
- [ ] OT-P2-002 | Multi-User / Multi-Tenant Trust Groups | The device trust model is extended to support multiple owners sharing a Vrooli instance, each with an isolated trust group; v1's single-owner-many-devices structure is the clean foundation for this extension with no schema breakage.
- [ ] OT-P2-003 | Native Mobile Apps & PWA Polish | Dedicated iOS and Android apps (or a deeply integrated installable PWA) provide push notifications, share-sheet integration, and background sync; the existing web UI and API remain the canonical interface.
- [ ] OT-P2-004 | File Versioning, Tags & Categories | Items can carry user-defined tags and categories; files support versioning so previous transfers can be retrieved; search and filter are extended to cover version history and tag facets.

## 🧱 Tech Direction Snapshot
Preferred stacks: Go for the API server (Connect/REST, consistent with the react-vite template default); React + Vite + Tailwind CSS consuming the vrooli-default "Operational Console" design kit for the web UI; Go CLI binary with cobra-style subcommands and JSON output; WebSocket server co-located in the Go API process.

Preferred storage: api-core/storage `data` class rooted at `~/.vrooli/data/vrooli/device-sync-hub` for runtime state; api-core/blobstore for all binary payloads; relational metadata (device records, item metadata, retention state, pairing tokens) stored in SQLite for single-owner deployments or Postgres for multi-tenant readiness, accessed exclusively through versioned schema migrations — no drop-and-recreate on schema change; Redis optional for short-TTL pairing-code validation cache and WebSocket presence state.

Integration strategy: Shared workflows take precedence over resource CLI, which takes precedence over direct API calls. Identity, JWT issuance, access/refresh token validation, and session revocation are consumed from scenario-authenticator over HTTP; device-sync-hub does not reimplement or extend authenticator internals. The device registry, pairing flow, trust-group ACL enforcement, item ownership, per-item ACL, and WebSocket presence layer all live exclusively within this scenario. Other scenarios and agents interact with device-sync-hub through its versioned CLI/API surface, never by directly accessing its database or blobstore.

Non-goals: No peer-to-peer transfer in v1; no multi-tenant or multi-user in v1; no end-to-end or zero-knowledge encryption (TLS in transit + optional at-rest AES-256 is the security model); no cloud-storage backends (S3, GCS, etc.); no rewriting or extending scenario-authenticator; no production test-mode authentication bypass; no native mobile apps in v1; no DB schema recreation on migration.

## 🤝 Dependencies & Launch Plan
Required resources: Relational database (SQLite for v1, Postgres-compatible schema for forward compatibility); api-core blobstore and data-class storage; TLS termination (Cloudflare tunnel or reverse proxy in front of the Go server); Redis (optional, for pairing-code TTL cache and presence).

Scenario dependencies: scenario-authenticator — consumed over HTTP for all owner identity, JWT issuance, token validation, and session/device revocation; device-sync-hub is non-functional without a healthy authenticator endpoint and fails closed if the authenticator is unreachable.

Operational risks: (1) Large-file relay pressure — mitigated by streaming upload/download, chunked resumable transfers (P1), per-device storage quotas, and WebRTC P2P deferred to P2. (2) Trust bypass by a network or tunnel stranger — every read and write is gated on a paired-device JWT; pairing codes are single-use and short-TTL (≤ 5 minutes); no content is accessible before pairing completes. (3) Revocation correctness — device revocation must atomically call authenticator session invalidation and remove the device from the trust group; any race or partial failure must leave the device locked out. (4) Authenticator availability — device-sync-hub fails closed in production (no cached trust beyond a brief configurable window, default ≤ 60 s); a stale validation cache must never permit a revoked device to read or write. (5) Schema drift — all schema changes go through numbered migration files; CI must reject any code path that would drop or recreate the database.

Launch sequencing: (1) Scaffold repository structure, CI pipeline, and green health-check endpoint. (2) Integrate scenario-authenticator: owner login, JWT validation middleware, session revocation hook. (3) Device and pairing domain: device registry schema + migrations, pairing-code generation and QR, request-and-approve fallback, trust-group enforcement on all routes. (4) Transfer core: item metadata schema, blobstore integration, streaming upload and download, filename preservation, thumbnail generation, retention policy engine (Live/Held/Pinned), purge scheduler. (5) WebSocket layer: real-time item delivery, per-device presence broadcast, pairing-request banner events. (6) Device management and settings UI: list/rename/revoke, remote sign-out, retention default, storage quotas, clear-all with permission gate. (7) Go CLI with JSON output covering send, receive, device list, and revoke. (8) Polish responsive split-screen web UI: Send pane, Receive pane, thumbnails, empty/loading/error states, WCAG 2.1 AA pass. (9) Security hardening: quota enforcement, rate limiting on pairing endpoints, revocation correctness audit, penetration review of trust-group ACL. (10) GA readiness: load testing large-file relay, documentation, PWA manifest validation.

## 🎨 UX & Branding
User experience: The signature layout is a single full-screen split — the Receive pane occupies the top half, the Send pane the bottom half — so the owner can simultaneously see arriving items and stage outgoing ones without navigating away. The Send pane stages picked, dropped, or pasted items as cards; each card shows a thumbnail (for images), filename or snippet preview, a retention selector (Live / Held / Pinned), and an optional target-device selector (P1). A single prominent Send button dispatches all staged items. The Receive pane shows a calm empty-state illustration and message when no items are present; as items arrive they populate as downloadable cards (default) or a compact list (toggle). Owner-originated items expose inline edit and remove controls; a permissioned Clear All action is available with an explicit confirmation step. Device management and settings live in a separate settings surface, not embedded in the transfer view, to keep the primary interface uncluttered.

Visual design: vrooli-default "Operational Console" design tokens throughout — the same type scale, spacing system, elevation, and color palette used by other Vrooli scenarios. The Send and Receive panes use distinct but harmonious accent colors to reinforce directionality at a glance. The aesthetic is minimalist and professional: generous whitespace, no decorative chrome, information density tuned so the interface reads as "dead simple" on first open. The PWA manifest and maskable icons ship with valid placeholder assets; they are replaced with final branding assets when available. Dark mode is supported via the Operational Console token set from day one.

Accessibility: WCAG 2.1 AA compliance is required before GA. All interactive controls are reachable and operable by keyboard alone with a clearly visible focus ring. Every image thumbnail has a meaningful alt attribute; icon-only controls carry aria-label. The Send and Receive regions are marked with appropriate ARIA landmark roles. Drag-and-drop upload (P1) has an equivalent click-to-browse path that works without a pointer device. The layout reflows gracefully down to a 320 px viewport width — the split-screen collapses to a single-column stacked layout on small phones — with no horizontal scroll and no truncated controls. Color alone is never the sole indicator of state (e.g., online/offline presence uses both color and an icon/label).
