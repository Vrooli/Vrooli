The reframe

One pipe versus a switchboard

A voice-only phone scenario is a single channel bolted to a single agent. A presence plane is many channels — including the app's own — resolving into one routing decision: which agent is this person talking to, and what may it do for them? Everything downstream of that decision already exists, which is why widening the scope costs less than the narrow version would.

Architecture

You already built the return path

This is the finding that should change the plan. notification-hub is described in its own PRD as "the owner's notification spine… reaching a human reliably", and its macOS sender already drives Messages over osascript for an imessage channel — relayed to a Mac in the fleet by vrooli-bridge when this host is Linux. Egress is solved. Build ingress, and reuse the rest.

Hazard 1 · the expensive one

Trust is per (room × sender), not per contact

The tier table earlier is per-contact, which silently breaks the moment someone adds a fifth person to a group your agent is already in. The rule that holds: the room's ceiling is the lowest tier present, and a sender never gets more inside a group than they hold outside it. Adding a stranger must lower the room, never raise the stranger.

Hazard 2

A group reply is a broadcast

Anything the agent says in the room is said to everyone in it. So an answer that one member's tier unlocks must not be rendered there at all — it goes to a direct thread or it is refused out loud, as above. Getting this wrong is the incident that ends the product, and it cannot be handled by prompting.

Hazard 3

Two bots in a room will loop

Agents replying to agents is unbounded by default, and every turn is Class A metered — a runaway loop spends real money while everyone sleeps. Two mechanisms, both cheap: mark agent-authored messages so no adapter auto-triggers on one, and give every thread a turn budget per hour that fails closed.

Hazard 4

Whose wallet is this?

In a group, a non-owner's message spends the owner's credits. That is both a billing surprise and an abuse vector — anyone in the room can drain a wallet by talking. Needs a per-thread spend cap alongside the turn budget, and it should be visible to the owner, not buried.

The cheap part. Speaking discipline is one flag and it prevents most of the annoyance: default to speak_when = mentioned in any room with more than one human. One-to-one threads default to always. Slack proved the pattern years ago and everyone already expects it — an agent that answers every message in a group gets muted within a day, and a muted agent voids every promise downstream of it.
Your question · adding new options

Slack is a channel. GitHub mostly is not.

Before the extensibility mechanism, the split that decides which mechanism a thing goes through — because conflating these is what produces an "integration" that is half tool and half channel and owns neither well.

No → it is a tool, and it is already how Vrooli works: a scenario, a CLI verb, a prompt-manager action in the agent's capability grant. GitHub answers yes for exactly one surface — issue and PR comments where someone @mentions the bot — and no for everything else it does.

The rule that prevents the rot

Never branch on a channel name

Every if channel == "imessage" is a future edit site. Ask the descriptor instead — supports.images, group.speak_when, limits.file_mb. This single discipline is the difference between the two panels above, and it is worth a lint rule the day the second adapter lands, not the day the sixth does.

The thing that makes new adapters safe

A channel-conformance test-genie phase

One shared suite every adapter must pass: round-trip text, round-trip an image, reject oversized media by the declared limit, thread a reply, back off on rate limit, handle an inbound from an unknown sender, refuse to auto-reply to an agent-authored message. Writing an adapter becomes "implement the interface, run the existing phase." test-genie already has this exact shape in provider-conformance and profile-conformance.

Notifications are one-shot and stateless; conversations are not. notification-hub becomes a second caller into the same registry, not a layer above it.
D2The descriptor file is the source of truth; the database table is a cache rebuilt at boot.Copied verbatim from channel-manager, which already states it and already implements the loader. Two SSOTs for one fact is the bug this avoids.
D3The in-app chat is an adapter, not a special case in the core.The single cheapest guarantee that external channels stay first-class. If the core cannot tell in-app from Telegram, no feature can quietly become in-app-only.
D4Effective scope = min(sender tier, room ceiling, agent grant), resolved before the run starts, and empty means refuse.Fail-closed by construction rather than by prompt. Computing it after the run starts means the model has already seen data it should not have.
D5Idempotency at ingress, keyed on channel + remote_message_id.Every one of these transports redelivers. A webhook retry that spends metered inference twice is a billing bug that only shows up under load.
D6The agent descriptor stays in prompt-manager; this scenario stores only the binding and the thread.An agent must be usable outside a message thread. Duplicating the descriptor here creates a fork the moment someone edits one copy.
D7Never branch on a channel id anywhere above the adapter. Ask the descriptor.The one rule that keeps the blast radius at two files. Worth a lint rule when the second adapter lands.
D8Agent turns meter; notifications never do.notification-hub already recorded "Never meter notifications" on 2026-08-17. Keeping that line intact means a delivery failure can never be a billing event.
How the parts actually work

Six diagrams an implementer can build from

Smallest thing that proves it

One week, one channel, one agent

Do not start with iMessage, and definitely do not start with voice. Prove the loop where it is free and unblocked, then swap the adapter.

DAY 1–2

Two adapters at once — Telegram and in-app

One bot token and a long-poll loop; one WebSocket. Same contract, one hard-coded agent, an inbound message becomes an agent-manager run. Building the second adapter on day one is the cheap insurance that the contract is channel-neutral before anything depends on it — and the in-app one is nearly free.

DAY 3

Images both ways

Inbound photo → the run's context. Outbound chart → back into the thread. This is the claim that "multimodal" means something, and it is where the adapter contract earns its shape.

DAY 4

Bind an address to a profile

Read a real prompt-manager agent descriptor instead of the hard-coded one. Two agents, two bots, one process. Now the roster mockup is real.

DAY 5

The trust guard, fail-closed

An unknown sender gets chat and nothing else — enforced by handing a narrower scope to Attenuate(), not by a prompt instruction. Prove it with a hostile message from a second account.

DAY 6+

Swap in iMessage

The Mac already receives your notification-hub sends. Add a chat.db reader behind the same adapter contract and the differentiator arrives without touching anything above it.

SEPARATE

The two things that are not this plan

A trust guard worth trusting needs prompt-injection-arena redesigned from its operational targets up — scope it as its own plan, not a checkbox here. And audio-tools owes a fix before call mode ships: dictation never sends engine_id, so every session has been running CPU whisper while every signal read green.

That was wrong, and for a reason worth naming: I was reasoning about the chat UX as a redundant reading surface, when its actual job is conversion. A stranger cannot try an iMessage agent — that needs a Mac, an Apple ID, and for SMS a week of carrier registration. They can try an in-app thread in ten seconds. The chat UX is the only zero-setup path to the product, which makes it the funnel, not a duplicate.
