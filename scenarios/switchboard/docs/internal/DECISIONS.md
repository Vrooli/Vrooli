# Decisions — Switchboard

## Purpose Of This Document

The durable record of *why* this scenario is shaped the way it is. Each row
states the decision, what was rejected, the cost accepted, and what would make
it worth revisiting. A decision that is not written here can be re-litigated by
the next agent at full cost; one that is written here can be challenged cheaply
and on the merits.

Add a row when a choice closes off an alternative that a reasonable engineer
would otherwise take.

## Decision Log

| Date | Decision | Why, and what was rejected | Cost accepted | Revisit trigger |
|---|---|---|---|---|
| 2026-09-01 | **Name the scenario `switchboard`.** | The string appears nowhere in `.vrooli/`, `cli/`, any PRD, or `docs/concepts/`. Single-word scenario names have precedent (`persona`, `portal`, `treasury`, `calendar`, `notes`). Rejected: `reach` — 37 hits and "the reach plane" is settled vocabulary for `vrooli-bridge` in four documents, so taking it would put two owners on one phrase. Rejected: anything `channel-*` — `channel-manager` exists and means social platform identities. Rejected: `*-inbox` — `agent-inbox` and `signal-inbox` both exist and are surfaces the operator opens, whereas this one opens itself. | A bare noun is slightly looser in a list of 124 scenarios than an `agent-` prefixed name would be. | If the bare noun proves ambiguous in practice, `agent-switchboard` is the fallback; `front-desk` was the runner-up and remains unclaimed. |
| 2026-09-01 | **Widen the roadmap's `goal:phone-agent` from voice to a multi-channel presence plane.** | The roadmap scoped it to "voice/phone interface — hands-free". Voice-only is both the smallest version of the idea and the hardest place to start: it needs transcription, synthesis, turn-taking, barge-in and telephony before it says a word, while text and media need a webhook. Rejected: shipping voice first as written. | A larger P0 than the roadmap line implied. | None foreseen; voice remains in scope at P2 and the roadmap goal is satisfied rather than replaced. |
| 2026-09-01 | **Own inbound only; reuse everything already built for outbound.** | `notification-hub` already delivers to a human and already sends iMessage from a Mac through `osascript`. Nothing anywhere turns an arriving message into an agent turn. Building a second outbound stack would duplicate a working one. | This scenario is useless without `agent-manager` and `prompt-manager` running. | None. |
| 2026-09-01 | **A reply egresses through the adapter that ingressed it, never through `notification-hub`.** | Thread identity, reply-to identifiers and typing state live in the adapter's session. `notification-hub`'s senders are one-shot by design — title, body, address — and carry none of it. Rejected: routing conversational replies through the existing delivery spine. | Two delivery paths exist for channels both scenarios can reach. Mitigated by sharing the *adapters*, so a channel is implemented once. | If `notification-hub` ever grows a stateful session model, revisit whether one path can serve both. |
| 2026-09-01 | **The channel descriptor file is the source of truth; the database table is a cache.** | Copied from `channel-manager`, which already states this and whose loader comment reads "The same loader accepts any additional descriptor placed in either directory." Adding a channel must not require a migration. Rejected: descriptors as ordinary rows. | Boot does real file I/O and validation, and an invalid file fails boot. | Never — this is the extensibility mechanism. |
| 2026-09-01 | **Construct adapters through a package registry, not in `main.go`.** | A descriptor-only loader is not enough if production adapter construction still requires editing the process entrypoint. Built-ins register factories once; a new adapter file in the registry package is discovered when the binary is built. Rejected: a maintained adapter list in `main.go`. | Registration uses Go package initialization, so duplicate or accidentally omitted adapter files must be caught by focused registry tests and the conformance phase. | If adapters require runtime plugins or isolation, replace the in-process factory seam with a governed plugin boundary. |
| 2026-09-01 | **Never branch on a channel identifier above the adapter layer.** | `notification-hub`'s own `DECISIONS.md` (2026-08-17) records "Ship one real channel end to end before building any abstraction", which was correct for one channel and produced hardcoded switches at `transports.go:119`, `transports.go:134` and `service.go:531,796`. Its 2026-08-18 entry already names the target: "Adding a channel touches this scenario's adapter registry and nothing else." That registry does not exist in code yet. This scenario is the trigger that cashes it. | Every capability question needs a descriptor field, so the descriptor schema grows before the feature does. | Never. Worth a lint rule when the second adapter lands, not the sixth. |
| 2026-09-01 | **The in-app conversation surface is an ordinary channel adapter.** | If the core can distinguish in-app from Telegram, some feature eventually becomes in-app-only by accident. Making the native surface unprivileged is the cheapest guarantee that external channels stay first-class. Rejected: a direct in-process path for the local UI. | A small amount of ceremony for the simplest possible transport. | None. |
| 2026-09-01 | **Effective scope is `min(sender tier, room ceiling, agent grant)`, resolved before the agent reads the message.** | Resolving after dispatch means the model has already seen content it may not be allowed to act on. Rejected: enforcing permissions inside the agent's prompt, and rejected: an auth middleware — a middleware filter is bypassed by every new call path added later. | Every turn pays a resolution step before any work happens. | Never. |
| 2026-09-01 | **A group thread's ceiling is the lowest tier in its roster.** | The alternative silently escalates a stranger the moment somebody adds them to a group an agent is already in. Adding a lower-tier participant must narrow the room, never widen the participant. | An owner in a group with a stranger loses capability in that room and must move to a direct thread. Correct, and occasionally annoying. | None. |
| 2026-09-01 | **An owner-only scope is unreachable from a lower tier by construction, not by configuration.** | A permission that can be misconfigured will be. Rejected: a settings toggle that permits it. | Some legitimate delegation is impossible and must be done as the owner. | None. |
| 2026-09-01 | **De-duplicate at ingress on `(channel_id, remote_message_id)`, before any run.** | Every one of these transports redelivers. A duplicate that reaches dispatch is a duplicate charge against a metered wallet, and that class of bug only appears under load. Rejected: idempotency at the run layer. | An index and a 30-day retention sweep. | None. |
| 2026-09-01 | **An agent-authored message never starts a turn, and every thread has an hourly turn budget that fails closed.** | Two agents in one room exchange metered calls indefinitely. Both mechanisms are cost controls, not manners. Rejected: relying on prompt instructions to stop it. | An agent cannot deliberately answer another agent, which forecloses multi-agent collaboration in a thread. Accepted: that is currently a hazard to bound, not a capability to build. | If deliberate agent-to-agent collaboration is ever wanted, it needs an explicit opt-in and its own budget. |
| 2026-09-01 | **Agent descriptors are held by reference into `prompt-manager`; no copy is stored.** | An agent must be usable outside a message thread. A local copy forks the first time someone edits one side. `agent_ref` exists only as a display cache and never affects permission. Rejected: a local agent table. | This scenario cannot render agent detail when `prompt-manager` is down; bindings still resolve. | None. |
| 2026-09-01 | **Declare no resource dependency at P0.** | Rejected on macOS evidence, not on Docker — both resources declare `driver: managed-service` and neither requires a container runtime. Neither is recorded `supported` on macOS: `postgres` is `build-verified` there from checksum-pinned archives with **no macOS hardware run performed**, and `path:docs/reference/platform-support.md` contradicts itself on `redis` — its generated resource matrix says `build-verified` while its narrative capability table says `unsupported`. Either would put the Mac fleet node — the reason the iMessage lane exists, and the most valuable channel in the product — on unproven footing. Queue state, budgets and rate-limit windows are in-process and SQLite-backed. | No cross-process queue and no shared cache. Throughput expectations are conversational, not bulk. | A macOS hardware run for `postgres`, or macOS support for `redis`, *and* a workload SQLite cannot carry. |
| 2026-09-01 | **Ship Telegram and the in-app adapter together as the first two channels.** | Two adapters on day one is the only cheap proof that the contract is channel-neutral before anything depends on it. Telegram needs no account provisioning, no public origin and no marginal cost; the in-app adapter is nearly free. Rejected: starting with iMessage, which needs a Mac, and rejected: starting with SMS, which needs a week of carrier registration. | The most marketable channel is not the first one built. | None. |
| 2026-09-01 | **A hosted third-party message relay is never a default path.** | Routing private conversations through a vendor forfeits the custody promise that is the only durable advantage over hosted competitors. Rejected: using a hosted iMessage API to avoid requiring a Mac. | Owners without a Mac cannot use iMessage at all until an explicitly labelled fallback is offered at P2. | If offered, it must state its trade-off at the point of purchase, never in a footnote. |
| 2026-09-01 | **Metering routes through LPBS; notifications are never metered.** | `notification-hub` recorded "Never meter notifications" on 2026-08-17, and keeping that line intact means a delivery failure can never become a billing event. Reinventing credits or entitlements is forbidden by the paid-features contract. Local `spend_ledger` is a mirror for cap enforcement and display, never a second ledger of record. | Cap enforcement depends on a mirror that can drift from the authority. | None. |
| 2026-09-01 | **Author the full documentation set before any domain code.** | Operator instruction, and the right call for a scenario whose hardest problems — trust resolution, group semantics, loop and spend control — are design problems rather than implementation problems. | Reference docs describing the API and CLI surface necessarily describe the template's example domain until real domains exist. Called out rather than papered over. | Ends when the first real vertical slice lands. |
| 2026-09-01 | **Treat `prompt-injection-arena` as unavailable rather than as a dependency.** | It is stale — a flat pre-`api-core` `api/*.go` layout, a 12.9 MB binary committed in October 2025 — and, more importantly, it is the wrong shape: an offline tournament that scores models against an injection library and ranks them, not a runtime guard. Rejected: depending on it as-is. | Runtime injection defence has no owner, which is recorded as an open problem rather than hidden. | Before any non-owner tier is exposed in production, that scenario needs a redesign from its own operational targets. |
