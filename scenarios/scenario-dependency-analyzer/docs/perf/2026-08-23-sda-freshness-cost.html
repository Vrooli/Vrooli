The mechanism

Three measurements identify the bottleneck without ambiguity, and they rule out every explanation people usually reach for first.

The command spends 95% of its life blocked, not computing. Adding workers changes nothing. Removing the network changes everything.

Each of the 247 scenario Go surfaces gets one go mod tidy -diff subprocess, run through a worker pool. For 198 of them that subprocess reaches github.com/vrooli/envkit-go v0.0.0, finds no local replace directive pointing at packages/envkit-go, and concludes it must fetch the module from the internet. It cannot: the module is in-repo and has no upstream. So it asks proxy.golang.org, waits, fails, and reports an error.

The Go toolchain serializes those lookups on the module cache. That is why raising concurrency from 8 to 32 is worth nothing at all, and why the arithmetic lands exactly on the observed number: 198 lookups × ≈0.35 s each ≈ 69 s ≈ the whole run.

The last two rows matter for what comes after. Once the network is out of the picture, the fleet-wide sweep of 247 modules is a 1.5-second operation. The thing everyone has been treating as expensive is not expensive. It only looked that way through a failure that costs a third of a second and repeats itself two hundred times.

Findings

Nine, ordered by how much they cost. P1 and P2 are one problem seen from two sides; P3 is what makes the problem recur; P7 is a separate command with the same shape of defect.

P168 of 71 seconds are failed network lookups for a module with no upstreamSpeed21×

198 of the 199 error surfaces emit the same first line. runGo in cli/domains/health/freshness.go overlays only GOWORK=off and GOFLAGS=; GOPROXY passes through from the ambient environment, so every surface that is missing a local replace takes a full round trip to proxy.golang.org and sum.golang.org before it can fail.

go: downloading github.com/vrooli/envkit-go v0.0.0 × 198 surfaces go env GOPROXY → https://proxy.golang.org,direct GOPRIVATE, GONOSUMDB → unset

Fix: run the sweep offline and treat a genuine cache miss as its own status rather than an error. Detail in step 1.

P2The worker pool is inert — the Go module cache serializes the lookupsSpeed

Concurrency 8 and concurrency 32 produce the same wall clock, and the run uses 31 seconds of CPU across 70 seconds on a 32-core host. Any future tuning of --concurrency is wasted effort while P1 stands, and the knob will mislead whoever tries it. Once the network is gone, concurrency starts working again — 1.5 s at 8-way, 1.2 s at 32-way — which is the right time to size it.

P3There is no result cache anywhere in the CLISpeedRecurrence

Running the command twice back to back costs the same both times. Grepping the whole cli/ tree for caching finds three hits, and all three are directory names in a walk-skip list. Every invocation re-walks the repository, re-parses 315 go.mod files, and re-spawns 247 subprocesses to recompute answers that could not have changed.

go mod tidy -diff is a pure function of a small, hashable input set, which makes this cheap to fix properly rather than with mtimes. Design in the cache section below.

P4One missing replace directive produces 80% of the reportAccuracy

39 scenario surfaces declare replace github.com/vrooli/envkit-go => …/packages/envkit-go. 208 do not, and 198 of those reach envkit-go transitively through cli-core or api-core. The freshness gate is therefore reporting one defect 198 times, and the surfaces that error can never be assessed for actual staleness — the check stops before it gets there.

This is why speed and accuracy are the same work here. A precommit gate that is 80% noise gets ignored regardless of how fast it runs, and fixing the noise also removes the cost.

P5The repository is walked twice and the dependency closure is recomputed 247 timesSpeedCleanliness

discoverGoSurfaces walks scenarios/; discoverGoModules then walks the entire repository root, which contains scenarios/ — so every scenario go.mod is found and hand-parsed twice. Separately, impactedSurfaces calls transitiveRequirements once per surface with no memoization, re-deriving the same closures from the same 315-module map, and it does so even when the changed-module set is empty and the answer cannot matter.

Worth roughly 1.9 seconds warm, more on a cold page cache — which is most CI runs. Small next to P1, but it is the whole remaining budget once P1 is gone.

P668 modules are never checked; four synthetic test fixtures areAccuracyCoverage

Surfaces are discovered under scenarios/ only. That excludes 23 modules in packages/ — including envkit-go, api-core and cli-core, the shared spine every scenario depends on — plus 31 in resources/, 12 in templates/, the root module, and cmd/. A root go.mod edit is exactly what triggers the fleet-wide fan-out, and the module it edits is the one module the check will not look at.

In the other direction, the sweep includes four modules that are deliberately synthetic: go-code-graph/bas/fixtures/{go-cycles,go-usage-facts,go-tests,go-mislocated} and browser-automation-studio/bas/seeds. They exist to be malformed. Exclusion needs to be a declared rule, not a hardcoded directory-name list.

P7deps reconcile --all is serial, fail-fast, and re-walks the repo once per scenarioSpeedAccuracy

The CLI issues one RPC per scenario in a for loop and returns on the first error. Server-side, each request calls LoadTopology(repoRoot) — a fresh walk of all 315 modules — then, per surface, forks go mod edit -json for its own go.mod and for every in-repo module it requires, and AST-parses every .go file in the scenario.

Inside that parse, matchingInRepoModule linear-scans all 315 module paths for every import of every file — on the order of 108 prefix comparisons across the fleet, where a longest-prefix map would be one lookup.

The observable result is that deps reconcile --all spends 30.8 seconds, hits a {{SCENARIO_ID}} placeholder in a template module, and aborts with nothing to show for it. This is the command the freshness report itself recommends as the fix for P4.

reconcile go.mod replaces: internal: exit status 1: go: -require={{SCENARIO_ID}}@v0.0.0: invalid path: malformed import path "{{SCENARIO_ID}}": invalid char '{'
P8Two different go.mod parsers, both hand-rolled, neither correctMaintainability

freshness.go parses go.mod with a line scanner that ignores replace entirely and indexes strings.Fields(rest)[0] without a length check. gomodreconcile deliberately does the opposite — it shells out to go mod edit -json on the grounds that "the go binary is authoritative" — and pays a process fork per file for it. Both are solving the same problem with opposite trade-offs and different bugs.

golang.org/x/mod/modfile is the correct answer for both: authoritative, in-process, no fork. It is already resolved in the module cache transitively but is not an approved direct dependency, so adopting it goes through SDA's own governance — deps approved search then deps install, never a raw go get.

P9--touched cannot see a new file, and nothing bounds the total runAccuracy

changedPaths runs git diff --name-only HEAD and git diff --cached --name-only, with a fallback that passes --untracked-files=no. A brand-new, unstaged go.mod — the exact file a new scenario adds — is invisible to --touched. Separately, runGo caps each subprocess at 120 s but nothing caps the run, so the worst case is 247 × 120 s with no ceiling and no partial result.

What is not wrong

Two things that look like the problem, are not, and would absorb real effort if pursued.

The fan-out is honest — correcting it buys 3.6%

The natural read is that a root go.mod edit fans out to the whole fleet because impactedSurfaces takes a shortcut: when go.mod or go.sum changes at the root it marks every surface impacted unconditionally, without consulting the dependency graph at all. That shortcut is real. It is also very nearly right.

Computing the actual transitive require closure for all 247 surfaces gives 238 that genuinely reach github.com/vrooli/vrooli, almost all of them through packages/cli-core. Making the impact analysis exact removes nine surfaces — four of which are the synthetic fixtures from P6. A root module edit really does invalidate the fleet.

So the lever is not "compute impact more precisely so less work happens." It is "make each unit of work cost what it should" — 6 ms instead of 350 ms — and then cache it. This corrects the framing in the earlier portability report, which proposed reporting impact and deferring verification on the theory that the consumer list would be cheap and short. The list is cheap. It is not short.

Second: this is not a fork storm and not a memory problem. 247 subprocesses sounds alarming, but they are bounded by the worker pool, peak resident memory never approached the host's 60 GB, and the offline sweep completes in 1.5 seconds. The sys time of ~9 s across the run is ordinary process-spawn cost for 247 go invocations. Once the cache in step 3 lands, the steady-state number of spawns drops to the handful of surfaces that actually changed, and the question stops being interesting.

The sequence

Ordered by dependency, not by size. Steps 1 and 2 are independent and can land in either order, but 2 is far more pleasant after 1, and 7 is only honest after 1–4.

1

Run the sweep offline, with a typed retry tier for genuine cache misses

71.9 s → 3.4 s~15 linesfreshness.go

Add GOPROXY=off to the overlay in runGo alongside the existing GOWORK=off and GOFLAGS=. A blanket GOPROXY=off alone would be wrong — on a cold host it turns a legitimate first-time download into a failure — so pair it with a second tier keyed on the toolchain's own error text, which is stable and unambiguous:

go: probe imports github.com/nats-io/nats.go: module lookup disabled by GOPROXY=off

Surfaces that emit that string get re-run once with the network on. Surfaces that fail for any other reason — including all 198 envkit-go cases — never touch it. Report the retried ones as a distinct needs_download status rather than folding them into error, so a cold cache reads as a cold cache instead of a defect.

Verified on this host: identical verdicts at 21× the speed, and the offline sweep is provably reproducible outside SDA.

2

Repair the envkit-go replace fleet-wide, which requires fixing reconcile first

199 errors → ~1blocked by step 6

208 surfaces need one replace line. The primitive that generates it — gomodreconcile — already names this failure mode in its package doc and produces the right edit. It cannot currently be run across the fleet because of P7, so the ordering is: make reconcile survive a bad module (step 6), then apply it repo-wide, then re-measure freshness against a report that is signal.

Until this lands, treat the freshness gate's error count as one finding, not 199. It is the same finding.

3

Add a content-addressed result cache

3.4 s → tens of ms warmthe durable win

This is what turns a fast check into a free one, and it is what makes the fleet-wide fan-out from P6's root-module case permanently affordable. Keys and invalidation are spelled out in the next section — the important property is that it must hash content, not stat mtimes, because the whole point is to be trustworthy inside a precommit hook where files are being rewritten as it runs.

4

One walk, one parser, memoized closures

~1.9 s → ~0.3 scleanliness
  • Walk the repository root once and derive both the module map and the surface list from that single pass, rather than walking scenarios/ and then walking the root over it again.
  • Memoize transitiveRequirements by module path — the closure is identical for every surface that shares a root — and skip it entirely when changedModules is empty.
  • Replace the hand-rolled line scanner with golang.org/x/mod/modfile (P8), which also gives replace awareness for free and removes the unchecked slice index.
  • Make surface exclusion a declared rule that names bas/fixtures, bas/seeds and templates/ with a reason, replacing the inline switch d.Name() list that appears twice in the file.
5

Extend coverage past scenarios/

+68 modulesaccuracy

Once a surface costs ~6 ms and repeats are cached, there is no reason to check 247 of 315 modules. Include packages/, resources/, cmd/ and the root module in discovery; keep templates/ excluded by the declared rule from step 4, since those modules hold placeholders by design. This closes the gap where the module whose edit triggers the fan-out is itself unchecked.

6

Make reconcile collect errors, hoist topology, and drop the per-import linear scan

unblocks step 230.8 s → seconds
  • Stop aborting. Collect per-surface failures into the response instead of returning CodeInternal on the first one. A malformed template must not cost the other 120 scenarios their result.
  • Load topology once. Memoize LoadTopology per repository tree digest instead of re-walking 315 modules on every one of the ~121 RPCs.
  • Stop the per-scenario RPC loop. Either add a fleet-scoped request or fan out with an errgroup at the CLI — but only after the two items above, or parallel fan-out just multiplies the redundant walks.
  • Replace matchingInRepoModule with a longest-prefix map over module paths, turning a 315-entry scan per import into one lookup.
  • Replace the go mod edit -json fork with in-process parsing, per P8. The stated rationale — the go binary is authoritative — is satisfied by x/mod/modfile, which is the same parser the go binary uses.
7

Give the hygiene lane a budget it enforces on itself

control planekeeps it honest

Two things, and neither belongs to SDA. First, the Makefile defines VROOLI := go run ./cmd/vrooli, so every make hygiene recompiles the CLI — around 20 seconds on the commit path. setup already has a command -v vrooli fast path; hygiene should use the same one.

Second, hygiene.Registry.Run iterates providers serially with no time budget, which is how a 60-second lane silently became a two-minute one. Let each provider declare a budget, have the registry enforce it, and report an over-budget provider as a finding against itself. A gate that quietly grows past its lane is the same class of failure as a gate that quietly stops running — and unlike that one, this is measurable.

With steps 1–4 done, SDA's provider costs roughly 3 seconds cold and near-nothing warm, which fits the lane comfortably. It no longer needs to defer verification to a slower lane — the earlier proposal to report impact and verify elsewhere was solving a cost that will not exist.

Cache design

The one piece worth specifying before anyone writes it, because getting the key wrong produces a cache that is fast and silently wrong.

go mod tidy -diff depends on more than go.mod. It resolves the module's actual import graph, so a source file that adds or removes an import changes the answer with no manifest edit at all. An mtime- or manifest-only key would go stale in exactly the case the check exists to catch.

Key

sha256( go.mod bytes go.sum bytes sorted import set of every .go file under the module ← the non-obvious one go toolchain version (go env GOVERSION) tool schema version (bump to invalidate all entries on a logic change) )

The import set is cheap to derive with parser.ParseFile(..., parser.ImportsOnly), which reads only up to the import block — and step 6 needs that same scan for reconcile, so the two should share one implementation rather than growing a second copy.

Value, storage, and eviction

  • Store the full freshnessSurfaceReport — status, diff paths, error text — so a cached stale verdict is as actionable as a fresh one.
  • Write under the scenario's own data directory, not /tmp. Scratch directories on this host do not survive a few days, and a verification baseline that silently vanishes is worse than no cache.
  • Bound it. The scenario already carries an unbounded phase-cache/ at 56 MB and 362 files with no owner; a second unbounded cache would be a repeat, not a feature. Cap by entry count with LRU eviction and record the cap where an operator can see it.
  • Never cache a needs_download result from step 1 — that status describes the host's module cache, not the surface, and it changes without any file changing.

Expected steady state

A commit touching one scenario invalidates that scenario's surfaces and nothing else: a handful of subprocesses, tens of milliseconds. A commit touching the root go.mod invalidates all 238 dependent surfaces honestly — and at 6 ms each, offline, that is still under two seconds. Which is the real conclusion of this report: the fan-out was never the problem worth solving.

Where it ends up

What the seven steps are worth, split by how much of each number is measured and how much is inference.

The case you are actually living with — a long-lived branch with the root go.mod modified, so every commit re-checks 238 surfaces — goes from 71.9 seconds to roughly four tenths of a second.

One number in the cache design was worth checking before trusting any of this, because getting it wrong would invert the conclusion: if computing a cache key costs more than the check it replaces, the cache is theatre. Hashing all 20,972 Go files across the fleet — 159 MB — takes about 50 milliseconds warm on this host, which has SHA-NI. Key computation is noise. The cache can key on honest content rather than mtimes and still cost nothing.

Three caveats

The root module is a 2.4-second floor. go mod tidy -diff on the root module alone measures 2.4 s — 9.5 s user, 10.3 s sys; it is a large module. Once step 5 brings it into coverage, any run that genuinely invalidates it pays that, and concurrency cannot help because it is one item. That single measurement is what sets the ~3 s cold figure, not the other 314 modules. It is also why the cache in step 3 is not a nice-to-have: without it, that 2.4 s lands on every commit.

The reconcile number is the soft one. Its symptom is measured — 30.8 s, then abort — but its internals were not profiled. The 1–3 s projection is inference from the four defects in P7: topology loaded 121 times instead of once, a 315-entry linear scan per import, a process fork per file, and fail-fast. The direction is certain; the magnitude is not, and it should be re-measured rather than assumed once step 6 lands.

Cold CI is a different question. Every figure here assumes a warm GOMODCACHE. On a fresh runner, step 1's needs_download tier fires for real and the run pays actual downloads once. That is a CI-caching concern rather than an SDA one — but ~3 s is not the number a cold container will show.

What none of this fixes

Every number above is about cost, not correctness. Until step 2 lands, the report still carries 199 error rows for one missing replace directive. A gate that runs in 0.4 seconds and is 80% noise is still a gate people learn to ignore — and that failure mode does not show up in any timing.

Method

So the numbers can be reproduced or disputed.

Read-only. Every measurement was taken on this host on 2026-08-23 against the working tree on branch agi, using the installed scenario-dependency-analyzer binary and time. Verdict counts come from the tool's own --json summary. The offline comparisons re-ran the identical go mod tidy -diff invocation the tool issues, under xargs -P, to confirm the cost reproduces outside SDA. The transitive-closure figure in "What is not wrong" was computed by parsing every go.mod in the repository and walking the require graph, which is the same algorithm impactedSurfaces would use if it did not short-circuit. The GOPROXY=off error signature was confirmed against a scratch module requiring a version that does not exist. The cache-key figure in "Where it ends up" is a measured upper bound: SHA-256 over all 20,972 .go files under scenarios/, packages/, resources/ and cmd/, run 8-way, which completes in ~50 ms warm and is unchanged at 32-way.

No files in the repository were modified, no --apply path was exercised, and deps reconcile was run only in its default dry-run form. The one command that failed — deps reconcile --all — failed read-only and is reported as a finding.

Companion to the earlier portability report, which measured this same 71 seconds from the outside and attributed it to fan-out. That attribution is corrected in "What is not wrong": the fan-out is real and almost entirely justified. The cost is per-surface, and it is network.
