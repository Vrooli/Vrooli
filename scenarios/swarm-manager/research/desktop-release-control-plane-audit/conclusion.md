# Research Conclusion: Audit The Desktop Release Control Plane

## Research Question

Map the real desktop monetization release path end-to-end across deployment-manager, scenario-to-desktop, landing-page-business-suite (LPBS), scenario-to-cloud, and the prompt-manager deployment skills. Specifically:

1. Which surface owns canonical approval state?
2. Which surface owns release/build/version records?
3. Which step actually publishes artifacts and update manifests?
4. Where is LPBS app/app-key/channel/release-note state the source of truth?
5. Which actions already exist in API, UI, CLI, and skills versus which are still implicit or manual?

## Summary

The desktop release pipeline is a 4-system relay: **deployment-manager** (approval gate + orchestration) → **scenario-to-desktop** (build + publish pipeline) → **LPBS** (artifact storage + update manifests), with **scenario-to-cloud** ensuring LPBS itself is deployed and healthy. Each system owns distinct state, but there are 7 identified gaps — most critically, no git-commit traceability in LPBS artifacts and no version feedback loop from LPBS back to deployment-manager. The pipeline works end-to-end today via prompt-manager skills that encode the correct sequence of CLI commands, but several implicit contracts (service secret sync, deploy target config, version propagation) should be made explicit via API contracts.

## Methodology

- **Codebase exploration:** Read route registration, handler implementations, database schemas, and client files across all 5 scenarios to map ownership and data flow.
- **Code-only validation (per round 1 d4=A):** Traced the full release path through code rather than runtime, verifying each inter-system call via client files (`desktop_client.go`, `lpbs_client.go`, `freshness.go`).
- **Exhaustive action inventory (per round 1 d1=B):** Cataloged every API endpoint, CLI command, UI page, and skill step with paths and purposes.
- **Interface boundary contracts (per round 1 d2=A):** Documented owns/exposes/consumes/assumes for each system.
- **Cross-referencing:** Validated API endpoints against route registration, database schemas against handler code, and skill instructions against current API contracts.

## Findings

### Finding 1: Canonical Approval State → deployment-manager

Approval state lives exclusively in deployment-manager's `deployment_approvals` PostgreSQL table, keyed by `(profile_id, git_commit_hash, platform)`. The release-gate API (`GET /api/v1/profiles/{id}/release-gate?commit={hash}`) checks all required platforms are approved for a specific commit. New commits cause old approvals to go stale. No other system duplicates or caches approval state.

**Key files:** `scenarios/deployment-manager/api/deployments/approvals_handler.go`, `scenarios/deployment-manager/api/deployments/orchestrator.go`

### Finding 2: Release/Build/Version Records Are Split Across 3 Systems

| Record Type | Owner | Storage |
|-------------|-------|---------|
| Deployment profile + version history | deployment-manager | `profiles` + `profile_versions` (PostgreSQL) |
| Deployment execution log | deployment-manager | `deployments` table (PostgreSQL) |
| Build provenance (git commit, branch) | scenario-to-desktop | Pipeline state (file-based JSON) |
| Platform build results | scenario-to-desktop | Pipeline state (file-based JSON) |
| Published artifact metadata | LPBS | `download_artifacts` (PostgreSQL) |
| Published release version | LPBS | `download_assets` (PostgreSQL) |

There is no single place to query "what version is live for app X on platform Y in channel Z?" — you must query LPBS for published state and deployment-manager for approval/deployment state.

### Finding 3: Artifact Publishing Is a Two-Hop Flow

deployment-manager never talks to LPBS directly. The flow is:

```
deployment-manager → scenario-to-desktop (pipeline/run) → LPBS (presign→upload→commit→apply)
```

scenario-to-desktop's deploy stage (`stage_deploy.go`) calls LPBS via `lpbs_client.go` in sequence: `TestRemoteProfile` → `DeriveUpdateURL` → `PresignUpload` → S3 upload → `CommitArtifact` → `Apply`.

**Key files:** `scenarios/deployment-manager/api/deployments/desktop_client.go`, `scenarios/scenario-to-desktop/api/deploy/lpbs_client.go`, `scenarios/scenario-to-desktop/api/pipeline/stage_deploy.go`

### Finding 4: Update Manifests Are Dynamically Generated by LPBS

LPBS serves electron-updater manifests (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`) at `GET /api/v1/updates/{app_key}/{channel}/{file}`. These are NOT static files — LPBS builds the YAML from `download_artifacts` metadata (SHA512, size, version, filename) on each request. Channel `"stable"` maps to `variant_key="default"`. Optional per-app API key gating via `X-Update-Key` header.

**Key file:** `scenarios/landing-page-business-suite/api/update_handlers.go`

### Finding 5: LPBS Is Source of Truth for App/Channel/Release State

| State | Table | Key Fields |
|-------|-------|------------|
| App identity | `download_apps` | `bundle_key`, `app_key`, `name`, `update_api_key` |
| Release per platform/channel | `download_assets` | `(bundle_key, app_key, platform, variant_key)` → `release_version`, `release_notes`, `artifact_id` |
| Binary artifact | `download_artifacts` | `sha256`, `sha512`, `size_bytes`, `bucket`, `object_key` |
| Storage config | `download_storage_settings` | S3 endpoint, bucket, credentials per bundle |

**Key files:** `scenarios/landing-page-business-suite/api/download_hosting.go`, `scenarios/landing-page-business-suite/api/download_service.go`

### Finding 6: Auth Boundary — LPBS apply vs set-current

LPBS `presign-upload`, `commit`, and `apply` accept admin OR service auth (`requireAdminOrService` middleware), but `set-current` is admin-only (`requireAdmin`). scenario-to-desktop's deploy stage uses service auth, so it goes through `apply` (which accepts service auth) rather than `set-current`. This is an important distinction for the system contract: automated pipelines can upload and link artifacts but cannot override the "current" release pointer without admin credentials.

### Finding 7: scenario-to-cloud's Desktop Role

scenario-to-cloud deploys LPBS itself to VPS infrastructure. The `landing-page-desktop-upload` skill uses scenario-to-cloud to ensure LPBS is deployed and healthy before uploading desktop artifacts. `evaluateDeploymentFreshness()` compares deployed `scenario.ref` with local `service.json` version and bundle SHA256 fingerprint.

**Key file:** `scenarios/scenario-to-cloud/api/freshness.go`

### Finding 8: Prompt-Manager Skills Encode the Full Pipeline

Three skills encode the release pipeline:
- **`scenario-to-desktop`** — CLI reference for building desktop apps (stateless)
- **`landing-page-deploy-setup`** — 7 idempotent gates (A–G) to prepare LPBS control plane
- **`landing-page-desktop-upload`** — End-to-end orchestration across all 4 scenarios in 6 stages (-0 through 4)

Skills depend on all 4 scenario CLIs being installed and use `--auto-start` for lazy startup and `api-core/discovery` for URL resolution.

### Finding 9: 7 Gaps and 5 Implicit Contracts Identified

**Implicit contracts (should be made explicit):**
1. `LPBS_SERVICE_SECRET` synchronization between scenario-to-desktop and LPBS
2. Deploy target configuration references LPBS remote profile tags but is managed independently
3. No version propagation callback from publish to deployment-manager
4. No git commit forwarded from scenario-to-desktop to LPBS artifacts
5. Auth split: `apply` (service) vs `set-current` (admin) affects what automated pipelines can do

**Gaps (no API/automation):**
1. No publish webhook from LPBS
2. No "current live version" query spanning the full pipeline
3. No rollback API
4. No approval→deploy automation
5. Entitlement ↔ approval conceptual confusion (documentation gap)
6. No git commit in LPBS artifacts
7. No deployment-manager → LPBS version sync

## System Contracts: Interface Boundaries

### Contract 1: deployment-manager

**Owns (source of truth):** Deployment profiles, approval state (per profile × platform × commit), release gate decisions, visual validation records, deployment execution logs, cross-platform build orchestration, code signing configuration.

**Exposes:** `GET /profiles/{id}/release-gate?commit={hash}` (gate check), `POST /deploy-desktop` (orchestrated deployment), `POST /build` (cross-compilation), profile CRUD.

**Consumes:** scenario-to-desktop `POST /pipeline/run` via `desktop_client.go`.

**Assumes:** scenario-to-desktop is reachable; its pipeline stages will call LPBS; build artifacts are compatible with scenario-to-desktop's bundle stage.

### Contract 2: scenario-to-desktop

**Owns (source of truth):** Pipeline state (stage progression, build provenance, platform results), deploy targets, desktop app records, telemetry data, scenario state.

**Exposes:** `POST /pipeline/run` (called by deployment-manager), `GET /pipeline/{id}` (polled by deployment-manager), `GET /desktop/download/{scenario}/{platform}`.

**Consumes:** LPBS `presign-upload`, `commit`, `apply` via `lpbs_client.go`.

**Assumes:** `LPBS_SERVICE_SECRET` matches; deploy target's remote profile has active session; download app exists on remote LPBS; S3 storage configured.

### Contract 3: LPBS (Download Surface)

**Owns (source of truth):** App registry, release state per platform/channel, artifact metadata, S3 storage configuration, update manifests (dynamic), entitlement gating.

**Exposes:** `presign-upload`, `commit`, `apply` (service auth); `set-current` (admin only); update manifests (public/API key); user downloads (auth + entitlement).

**Consumes:** S3-compatible storage. No calls to other Vrooli scenarios.

**Assumes:** `LPBS_SERVICE_SECRET` shared with scenario-to-desktop; S3 pre-configured; remote profile sessions maintained by caller.

### Contract 4: scenario-to-cloud

**Owns (source of truth):** VPS deployment records, freshness state, VPS health, secrets management.

**Desktop role:** Deploys and health-checks LPBS before desktop artifact upload. Manages `LPBS_SERVICE_SECRET` on VPS side.

### Contract 5: Prompt-Manager Skills

**Own:** Nothing (stateless). **Encode:** Correct CLI sequence, prerequisite gates, error recovery, post-release verification. **Depend on:** All 4 scenario CLIs, `--auto-start`, `api-core/discovery`.

## Limitations

1. **Code-only validation:** Findings are based on reading code, not tracing a live release. Runtime behavior could differ if there are configuration-dependent code paths not exercised in the default configuration.
2. **File-based pipeline state:** scenario-to-desktop's pipeline state is file-based JSON, which means build provenance is transient and not queryable after the pipeline completes unless preserved elsewhere.
3. **Endpoint counts are approximate:** "86+" means at least 86 distinct route registrations were found; some may be aliases or deprecated. Exact counts would require runtime route introspection.
4. **Skills may drift:** Skill instructions are stateless text — they could become stale if APIs change. Cross-validated at time of audit but no automated drift detection exists.
5. **No peer review completed:** Findings have not been reviewed by someone with deep operational experience running the pipeline end-to-end.

## Actions

### Action 1: Create backlog item — Add git commit hash to LPBS download_artifacts

- **Kind**: fix
- **Title**: Add git_commit_hash field to LPBS download_artifacts table
- **Description**: The `download_artifacts` table in LPBS has no `git_commit_hash` field, making it impossible to trace a published artifact back to its source commit without going through scenario-to-desktop's transient pipeline state. Add `git_commit_hash TEXT` to `download_artifacts`, accept it in the `commit` endpoint, and pass it from scenario-to-desktop's `BuildProvenance` during `CommitArtifact`. See research conclusion Finding 2 and Finding 9 gap #6.
- **Initiative**: desktop-release-governance
- **Priority**: 1
- **Effort**: S
- **Tags**: lpbs, traceability, database

### Action 2: Create backlog item — Add version sync callback from scenario-to-desktop to deployment-manager

- **Kind**: execute
- **Title**: Add post-publish version sync from scenario-to-desktop to deployment-manager
- **Description**: After scenario-to-desktop's deploy stage successfully publishes to LPBS, there is no callback to deployment-manager recording what version was published for which platform. Add a callback from scenario-to-desktop's deploy stage completion to a new deployment-manager endpoint that records the published version per platform per profile. This closes the feedback loop so deployment-manager knows the current live state. See research conclusion Finding 9 gap #7.
- **Initiative**: desktop-release-governance
- **Priority**: 1
- **Effort**: M
- **Tags**: deployment-manager, scenario-to-desktop, version-sync

### Action 3: Create backlog item — Add rollback API to desktop release pipeline

- **Kind**: execute
- **Title**: Add rollback API for desktop releases
- **Description**: Currently, rolling back a desktop release requires manually calling LPBS `set-current` with a prior artifact ID — a multi-step process that requires knowing the artifact ID and having admin credentials. Add `POST /api/v1/rollback` to deployment-manager that: (1) looks up the prior artifact for the specified app/platform/channel via LPBS, (2) calls LPBS to promote it, (3) records the rollback event in the deployments table. See research conclusion Finding 9 gap #3.
- **Initiative**: desktop-release-governance
- **Priority**: 2
- **Effort**: M
- **Tags**: deployment-manager, lpbs, rollback

### Action 4: Create backlog item — Add publish webhook from LPBS

- **Kind**: execute
- **Title**: Add webhook/event notification on LPBS artifact publish
- **Description**: After an artifact is published via `apply` or `set-current`, LPBS does not notify any other system. Add a webhook mechanism (configurable URL per app or per bundle) that fires on artifact promotion, enabling deployment-manager and other systems to react to publish events rather than polling. See research conclusion Finding 9 gap #1.
- **Initiative**: desktop-release-governance
- **Priority**: 2
- **Effort**: M
- **Tags**: lpbs, webhook, event-driven
